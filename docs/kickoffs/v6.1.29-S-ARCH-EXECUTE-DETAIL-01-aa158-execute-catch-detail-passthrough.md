## 1. CONTEXT

**Found 2026-07-08, reported directly by John.** `api/capabilities/execute.js`'s top-level handler catch block (`~line 777`) is:

```js
  } catch (e) {
    console.error('[execute] error:', e);
    return res.status(e.status || 500).json({ error: e.message });
  }
```

This drops `e.detail` entirely from the HTTP response. `api/prompt/request-receivable.js`'s own top-level handler (`~line 494`) already does this correctly:

```js
    return res.status(status).json({ error: e.message, ...(e.detail ? { detail: e.detail } : {}) });
```

**Why this is a bigger deal than a one-line inconsistency between two files:** confirmed by direct code read that `execute.js` imports `callModel`/`sendRequest` directly from `request-receivable.js` (`import { sendRequest, callModel } from '../prompt/request-receivable.js'`, line 41) and calls them as plain functions inside `runCapability()` — not via HTTP, so `request-receivable.js`'s own correctly-fixed handler (the one at line 494) is never actually in the response path for any MI-screen call. Confirmed via `src/screens/MarketIntelligenceScreen.jsx`: every capability call (`fetch("/api/capabilities/execute", ...)`, 3 call sites) goes through `execute.js`'s handler exclusively — `/api/prompt/request-receivable` is never fetched directly by the frontend. So every `.detail`-carrying error thrown anywhere inside `callModel()` (`request-receivable.js` lines 150, 218, 232, 235 — including `AA-157`'s just-shipped retry-rejection detail, `v6.1.27`, commit `60c1525` on dev) has been silently discarded on the only response path that matters, since before `AA-157` existed. Also affects `AA-147`'s schema-validation errors and any other `.detail`-carrying throw anywhere in the `runCapability()` call graph (`execute.js` itself throws two undecorated errors at lines 688-689 with no `.detail` today, but any current or future throw with `.detail` set anywhere in that graph hits this same drop).

**Confirmed live 2026-07-08:** a 422 from a real `hyp-hypothesis-test-display-intent` failure returned only `{"error":"Parse failed and retry also failed"}` — no `detail` field — even though `callModel()` (post-`AA-157`) now correctly populates `e.detail` with the real Anthropic rejection body.

**Fix:** mirror `request-receivable.js`'s own pattern in `execute.js`'s handler — spread `e.detail` into the JSON response when present. One-line change, same file/line as the bug.

**Not in scope:** `execute.js`'s own two undecorated throws (`confirmation not found` / `confirmation already {status}`, lines 688-689) do not carry a `.detail` field today, so they're unaffected either way — no behavior change for them, and adding `.detail` to those throw sites is a separate, unscoped decision (they don't currently have anything meaningful to put in it). This session only fixes the passthrough, not which throw sites populate `.detail`.

## 5. TASKS (1 of 4 max, 1 file)

### Task 1 — `api/capabilities/execute.js`: pass `e.detail` through the top-level handler's error response

Currently (~line 775-778):

```js
  } catch (e) {
    console.error('[execute] error:', e);
    return res.status(e.status || 500).json({ error: e.message });
  }
```

Replace with:

```js
  } catch (e) {
    console.error('[execute] error:', e);
    // FEATURE: AA-158 -- mirror request-receivable.js's own handler (line ~494), which already
    // does this correctly. execute.js imports callModel()/sendRequest() from request-receivable.js
    // directly (function calls, not HTTP) and every MI-screen capability call routes exclusively
    // through THIS handler, never through request-receivable.js's own -- so any error thrown with a
    // .detail field anywhere in the runCapability() call graph (AA-157's retry-rejection detail,
    // AA-147's schema-validation errors, any future .detail-carrying throw) was silently dropped on
    // the only response path that matters, since before .detail existed anywhere in this codebase.
    return res.status(e.status || 500).json({ error: e.message, ...(e.detail ? { detail: e.detail } : {}) });
  }
```

**Why this design, not a bigger one:** pure passthrough, zero behavior change when `e.detail` is absent (the `...(e.detail ? {...} : {})` spread is a no-op), zero new throw sites, zero new fields invented — literally the same expression already proven correct in `request-receivable.js:494`. Does not add `.detail` to `execute.js`'s own two undecorated throws (out of scope, see CONTEXT).
