## 2. CONTEXT

Column 3's Agent Routing panel shows a "New question" divider line between groups of agent hops, so John can see at a glance where one user action's chain of work ends and the next one's begins. Today that divider only fires from one place: `submit()`, when the user types a brand-new question. Three other places where the user takes an action that kicks off a fresh chain of real agent hops never insert it — `onReview` (deeper-theories request), `onSelectHypothesis` (theory selection), and `onResolveConfirmation`'s three branches (forecast accept/reject/edit) — so those hops visually run together with whatever came before, with no line marking "this is a new chain." A fifth site, `onCommit` (the forecast request itself, which fires Elena's memory-consolidation hop then Nadia's patch-proposal hop), was found live during this design session as the same bug shape and confirmed in scope by John.

The mechanism already exists — CHI-56 (v6.3.120, shipped 2026-07-21) built `buildTransactionBoundaryEvent("start", ts)` in `src/lib/turnTracking.js` specifically so call sites wouldn't need to hand-roll the boundary-event literal `submit()` used to inline. This session is a pure reuse: call that same function at 4 more call sites (5 more insertion points, since `onResolveConfirmation` has 3 branches). No new component, no new event type, no schema change, no visual redesign — `QuestionDivider` and `groupEventsIntoHops()` (`MarketIntelligenceScreen.jsx`) already handle any `question_boundary` event correctly regardless of which function inserted it.

**Confirmed with John, this session:** the divider's rendered label stays the hardcoded string **"New question"** — unchanged, even though it will now also appear after non-question actions (theory selection, forecast decisions, etc.). Do not generalize or vary the copy per trigger type.

**Desktop/mobile parity:** all 4 functions this session touches are defined once in `MarketIntelligenceScreen.jsx` and passed as props to both `EvidenceColumn` (desktop) and `MobileBody` (mobile) — the fix lives in the handler, not the renderer, so both surfaces get it from the same edit. No separate mobile task needed.

```js
// test-CHI-57.mjs — pure Node.js, no app imports
let pass = 0, fail = 0;
function assert(desc, cond) {
  if (cond) { console.log(`  ✓ ${desc}`); pass++; }
  else       { console.error(`  ✗ ${desc}`); fail++; }
}

// Mirrors buildTransactionBoundaryEvent() (src/lib/turnTracking.js) — unchanged by this session,
// reproduced here only so the test has no app import.
function buildTransactionBoundaryEvent(kind, timestamp) {
  return { type: kind === "start" ? "question_boundary" : "transaction_complete", agentId: null, data: { timestamp }, durationMs: null };
}

// Mirrors groupEventsIntoHops() (MarketIntelligenceScreen.jsx) — unchanged by this session.
function groupEventsIntoHops(ordered) {
  const hops = [];
  for (const evt of ordered) {
    const last = hops[hops.length - 1];
    if (evt.type === "question_boundary" || evt.type === "transaction_complete") {
      hops.push({ agentId: evt.agentId, events: [evt], isBoundary: true });
      continue;
    }
    if (last && !last.isBoundary && last.agentId === evt.agentId) {
      last.events.push(evt);
    } else {
      hops.push({ agentId: evt.agentId, events: [evt] });
    }
  }
  return hops;
}

// T1: a realistic post-fix sequence — typed question, then a theory-selection chain, then a
// forecast-request chain, then a forecast-decision chain, each now inserting its own "start"
// marker (Tasks 1-4). Every marker must start its own hop group, never merge into a neighbor,
// regardless of which function emitted it.
const seq = [
  { agentId: "marcus", type: "qa_answer" },                                          // typed question's own answer
  buildTransactionBoundaryEvent("start", 1000),                                       // Task 2: onSelectHypothesis
  { agentId: "priya", type: "hypothesis_test" },
  buildTransactionBoundaryEvent("start", 2000),                                       // Task 3: onCommit
  { agentId: "elena", type: "memory_consolidation" },
  { agentId: "nadia", type: "patch_proposed" },
  buildTransactionBoundaryEvent("start", 3000),                                       // Task 4: onResolveConfirmation (accept branch)
  { agentId: "nadia", type: "patch_resolved" },
];
const hops = groupEventsIntoHops(seq);
assert("4 chains produce exactly 3 boundary markers, each its own hop entry",
  hops.filter(h => h.isBoundary).length === 3);
assert("boundary never merges with a same-agentId neighbor (nadia appears on both sides of the 3rd marker)",
  hops[5].isBoundary === true && hops[4].agentId === "nadia" && hops[6].agentId === "nadia" && hops[4] !== hops[6]);
assert("real hop count (drawer badge) excludes all 3 new markers, same as the pre-existing single-marker case",
  hops.filter(h => !h.isBoundary).length === 4);

// T2: every marker this session's 4 new call sites can produce is kind "start" — confirm the
// resulting event always has type "question_boundary" (never "transaction_complete", which is
// onGoodThanks's separate, unchanged mechanism) and durationMs:null (structurally non-measurable).
const marker = buildTransactionBoundaryEvent("start", 4242);
assert("kind:start always produces type:question_boundary", marker.type === "question_boundary");
assert("marker durationMs is always null (excluded from hop-duration math)", marker.durationMs === null);
assert("marker carries the exact timestamp passed in, unmodified", marker.data.timestamp === 4242);

console.log(`\n${pass + fail} tests — ${pass} passed, ${fail} failed`);
if (fail > 0) process.exit(1);
```
