## QA — three proofs, each with a red control

Scripts live in the session scratchpad and are never committed.

**1. Losslessness, at the moment of deletion.** For each of the three files, the ordered list of
ticket IDs scraped from the file being trimmed is compared **positionally** — element for element —
against the ordered list the snapshot records for that same `source_file` section. Positional, not
set-based, because that is what proves *order* survived and what handles the duplicate `CHI-48`
honestly.

```
PASS  docs/FEATURES.md        file=285  snapshot=285  declared=285   positional match on every row
PASS  docs/FEATURES-NEXT.md   file=23   snapshot=23   declared=23    positional match on every row
PASS  docs/FEATURES-LATER.md  file=247  snapshot=247  declared=247   positional match on every row
RESULT: lossless — every row survives in the snapshot, in order.     555 / 555
```

**Would it still pass if the change did nothing?** That is what the two red controls answer, and
both had to fail: **drop-one** (delete one ID from the snapshot side) fails on count *and*
position; **swap-two** (exchange two adjacent snapshot IDs) fails **with the counts still equal** —
which is the control that proves the test measures order rather than mere membership. Both exited
1. Run against `HEAD`, i.e. the rows as they existed the instant before deletion.

**2. Snapshot currency, before and after.** `scripts/export-backlog-snapshot.js --check` returned
`no drift` against the live table both before the trim and after it — 555 tickets, payload sha256

copy, and the trim did not perturb it.
