## 6. DESIGN RULES

**Why a FUNCTION and not more prose.** This runbook states its own strongest lesson nine times (`SES-86` phase 3, `v7.0.146`, `SES-101`, `SES-111`, `SES-127`, `SES-128`, `SES-129`, `SES-143`, `SES-189`): *a rule each cycle must remember is a rule that gets silently forgotten.* Gates A and B are currently a two-row table a cycle applies by hand at the very end of its run, when it is longest in the tooth. Three more hand-applied rungs would be three more chances to skip one. `scheduler_gate`, `resolve_day_token_cap`, `stall_watchdog`, `record_skip` and `close_directive` are the precedent; this is the same shape.

**Two numbers, and where each came from — neither is invented.**

- **`chain_max_noship_streak` defaults to 2** because **2 is what the incident measured**: cycles `edd2471d` and `5f0a62d7` ran, shipped nothing but cards, and a human judgment stopped the chain *after the second one*. The default encodes the stop that actually happened, rather than a number chosen for feel.
- **`chain_max_undecided_cards` defaults to `NULL` (off)** because **no measurement supports any particular value.** 23 cards are undecided today and the incident recorded 22; neither is a ceiling, and shipping one as a default would be the runner widening its own rule with a number nobody measured. The dial ships; the value is John's, and question `q-chain-card-ceiling` asks him for it.

**Why stopping is always the safe direction here, which is what licenses adding gates at all.** The runbook says it outright: *"A continuation that fails to open is a **note, never a wall**: the cron remains the fallback engine."* A chain that stops early loses nothing — the claim expires in 24h, the next scheduled fire resumes the drain with a fresh context. A chain that runs too long spends John's token budget and buries his briefing in cards he has to clear. The costs are asymmetric, so the gates fail toward stopping.

**What this does NOT do, stated so it is not rebuilt as a bug.** It does not touch `drain_epic_next()`'s pick predicate. Adding a `design_status` clause there was the tempting one-line fix and it is wrong twice over: the pick predicate feeds **step 5** as well, where a flagged member must still be *returned* so the cycle can `record_skip()` it and put the ask on John's §10 — silently filtering it there would delete the very signal that tells him a decision is owed. And `SES-154`'s boundary lives in that same function: the pick and retirement predicates differ on purpose. The terminator belongs at the **chain** boundary, not inside the picker.

**Gate A is still evaluated first, and Gate B is still not a preview.** `drain_epic_next()` writes a before-image and retires a completed drain when it runs; the runbook forbids dodging that with a dry-run form. So `drain_chain_gate()` evaluates A **before** calling it — a cycle that failed Gate A fired nothing before this change and calls nothing now.

**A named approximation, disclosed rather than hidden (the register B42 convention).** The no-ship streak counts consecutive non-shipping cycles by `started_at`, and under parallel cycles another session's rows interleave with this chain's. There is no `parent_cycle_id` on `runner_cycles` to walk, and adding one would put a protocol step back into every continuation INSERT — the exact class of forgetting this ticket removes. The contamination can only make the streak **larger**, i.e. stop the chain **sooner**, which is the fail-safe direction; the window is bounded to 6 hours so a quiet night cannot accumulate one. Named here and in the migration body, exactly as step 3 names the per-cycle-start budget slack.
