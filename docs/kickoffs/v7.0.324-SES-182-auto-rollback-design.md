## The design

### 0. Frame — three rollback mechanisms already exist; this composes them

1. **Revert-forward for code** (§19v Reversibility; runner-cycle step 8's self-revert).
2. **Before-images for data** (§19v: no before-image → the write does not happen).
3. **The parachute** — the `SES-191`-drilled full restore, measured at 99.996%.

What does **not** exist, and is this ticket's product: a **rolling record of the last green state**
(today "green" is known only inside the cycle that just shipped — after it ends, a CI red on `dev`
has no watcher and no anchor); a **schema rollback primitive** (before-images cover rows,
revert-forward covers files, an applied migration is covered by neither — migrations *"exist only in
the database; the repo has no `.sql` files"*); and an **actuator** with authority to act after the
shipping cycle is gone.

### 1. "Last green state" is a POINTER, not a snapshot

New table `runner_green_states`, one row per observed green: `commit_sha`, `ci_run_id`,
`observed_at`, `migration_watermark`, `version`. Green = **both** blocking CI jobs green.

Code state is fully recoverable from `commit_sha` by construction. Data state deliberately does
**not** belong in it — data is independently reversible per-write via before-images, and freezing it
at green time would give one fact a second home. Captured by the runner's existing blocker sweeps
(steps 4 and 8), so the cadence is cycle cadence and no daemon is added. Retain 50 rows.

**A per-green Supabase dump is rejected as the rolling primitive, on measurement:** a set is 156 MB,
a raw dump carries live credentials and needs the §7 redaction ceremony, offsite pushes need John's
word *each time* (`c98048a5`/`1c9609de`), and §5c forbids restoring `schema.sql` into a live
populated project — so a rolling dump could not even be *used* here. The dump lane stays the
attended parachute.

**Fail-direction:** a sweep that cannot read CI records nothing — the pointer goes *stale*, never
wrong.

### 2. The migration question — the M0 gate review's named gap

**The bounding fact first, and it shrinks the problem honestly:** §19v's gated lane already forbids
schema-destructive migrations unattended, at every trust rung. So the population an *auto*-rollback
can meet on an unattended red push is the additive/replace family only.

**(a) Every unattended migration ships with a captured-prior-state down, generated at apply time —
never authored from memory.** New table `runner_migration_downs`: `up_name`, `down_sql`,
`prior_ddl` (the `pg_get_functiondef`/`pg_get_viewdef`/column-list/ACL state of every object the up
touches, captured *before* it applies — §19v's before-image discipline extended from rows to DDL).
For a `CREATE OR REPLACE`, the down re-applies `prior_ddl` **plus** the stale-overload drop and the
`count(*) = 1` assertion from `.claude/rules/supabase-function-signature.md` — a down that recreates
the old signature beside the new one is the `DAT-12` outage rebuilt in reverse.

**(b) A migration whose lossless down cannot be stated is refused the unattended lane and becomes
`gated_before_build`** — the charter's own fail-closed sentence applied to reversibility.

**(c) What transactional DDL and quiesce windows do NOT buy, so the build cycle doesn't reach for
them:** a *failing* up already rolls back atomically, but this ticket's case is an up that
*succeeded* and was later proven red, which no transaction boundary reaches. Quiesce-and-restore is
out: free plan, no PITR, §5c's live-project prohibition, and the ticket's own "a day-old dump loses
data".

**The honest partial — what auto-rolls back and what cannot:**

| Migration class | Auto? | Mechanism / named miss |
|---|---|---|
| New table/column/index/view/function/trigger | **Yes** | Down = drop by identity. **Named miss:** rows written into a new table during the red window die with the drop — so the actuator copies them into the before-image ledger first and the card counts them. |
| `CREATE OR REPLACE` view/function | **Yes** | Re-apply `prior_ddl` + overload drop + count=1 |
| Grant/ACL changes | **Yes** | Re-apply captured exploded ACL; assert **both** directions |
| New constraint | **Yes** | Drop constraint |
| Data-transforming up (backfills, mass UPDATEs) | **No** | Refused unattended by (b); John's lane |
| Destructive DDL (DROP, ALTER TYPE, RLS) | **No** | Already gated by §19v; not this population |
| The 2 `pending_confirmations` jsonb-scalar-null rows | **Never** | Unrestorable over PostgREST — reported, not represented |

**Fail-direction:** a red range containing **any** migration the actuator cannot match to a stored,
classified down → **no automatic schema action at all**, incident card only, reason named. An
un-rolled-back migration plus a loud card is recoverable; a wrong down applied to production is not.

### 3. What consuming the drill evidence actually changes

99.996% is the parachute's ceiling **on a current-vintage set**, and it is not 100%: 53,211 of
53,213 rows, two permanently unrestorable. Both offsite sets still restore at **32.8%**. A restored
platform cannot take another backup (`SES-214`), needs two invocations for self-referential FKs
(`SES-242`, shipped by this same session), and prints ~114 noise errors (`SES-241`).

**Consequences, and this is what makes the design sound rather than optimistic:** the automatic path
uses only the **lossless** rungs — revert-forward, before-image restore, captured-DDL downs. **The
actuator may never fire the parachute**: it is sub-100% by measurement, forbidden against live
populated projects, and its inputs are attended-only by standing directive. The incident card
carries named misses in the drill's own house style — *reported, never silently dropped, never
represented*.

### 4. Trigger and the authority boundary

**Triggers at first build:** CI on `dev` completing red on a range whose tip is attributable to an
unattended cycle (attribution is checkable via `runner_cycles.push_sha` and the issued-versions
ledger). Deploy-serving-red is deferred to a later slice.

**Deliberately NOT a trigger: a red verifier verdict — and this is a real collision, not a
preference.** The ticket text names the reviewer lane going red as a trigger; John's own card
`10de5fb5` says the lane *"completes nothing, blocks nothing"* and no caller may use exit 1 to abort
a ship. Auto-reverting on `block` is using exit 1 to *undo* a ship — a wall by the back door, before
the keystone catch-rate metric exists. Superseding his card is his call → **Q1**.

**Who fires it: the next cycle's blocker sweep — no new daemon**, reusing the runbook's existing
`outcome='reverted'` path rather than paralleling it.

**The actuator is a new script and the verifier stays verdict-only, absolutely.** A design that had
the verifier perform the rollback would launder its founding invariant — the runbook already refused
that laundering once, for a mere file render.

**It may never touch:** attended sessions' pushes (an attended red gets a card, not a revert), the
parachute, `main`, or the verifier's verdict rows. **Every action it takes writes its own
before-image first**, which is what makes §5 possible.

### 5. The incident card

Carries the trigger evidence, the revert record (sha range + green anchor), the schema record (each
up downed with its `prior_ddl`), the data record (before-images restored; rows preserved-then-dropped,
named), and the ladder consequence (counts as a Reverse). **Reverse on the card undoes the
rollback** — revert the revert, re-apply the downed ups, restore the actuator's own before-images.
Symmetric by construction, because every actuator action was before-imaged.

### 6. The edits this design forbids

1. The verifier performing, gating or triggering the rollback — the founding invariant, laundered.
2. A per-push Supabase dump as the rolling primitive.
3. Auto-firing the restore parachute, ever.
4. A down that recreates a function without the overload drop (`DAT-12` inverted).
5. Any down that materialises a generated column as plain data (`LOG-124` rebuilt).
6. Force-push or history rewrite.
7. Auto-reverting an **attended** push — decided here, not asked: the machine yields to humans.
8. Borrowing a literal-count termination test into the actuator's verification (`SES-242`'s own
   forbidden edit).
