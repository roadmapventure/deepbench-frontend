## The decision this cycle made, and why

The platform figure that *does* exist is **John's meter**: `runner_usage_readings.all_models_pct` is
a number the platform produced and he typed in. While he is asleep the runner is the only spender,
so a night→morning bracket is a window in which the meter's movement and the runner's own
`est_tokens` describe **the same work**. Their ratio is therefore a property of John's *plan*, not
of that night's work — if `est_tokens` tracked the meter it would be near-constant. Measured on all
four clean brackets stored today, reproduced from raw readings and cycle rows rather than re-quoted
from the column:

| Bracket | Meter | est tokens | tokens/pct |
|---|---|---|---|
| 2026-08-23 03:36Z → 13:51Z | 32% → 37% | 13,255,000 | 2,651,000 |
| 2026-08-24 03:19Z → 14:40Z | 60% → 65% | 12,927,000 | 2,585,400 |
| 2026-08-25 04:57Z → 13:56Z | 84% → 92% | 7,363,000 | 920,375 |
| 2026-08-29 03:14Z → 14:47Z | 17% → 29% | 27,710,000 | 2,309,166.67 |

**A 2.88× spread across four windows that should each report one constant.** That is the check
`SES-161` says has never been made, and it says `est_tokens` and the meter are not the same
quantity.

**The spread is reported, never graded.** There is no principled line at which a spread becomes
"too wide", and this codebase has paid repeatedly for constants a cycle chose — `SES-146`'s *"a
column, not a literal"* correction, twice. So the **verdict** is a separate question whose every
input is a stored row: *can the day token cap brake anything before the weekly rest wall does?*
Convert the cap into percent-of-weekly-meter through a bracket's rate and compare against the
remaining headroom. Live, with John's standing 196M box against 37% headroom:

- **73.93%** of a whole weekly meter on the most generous bracket, **212.96%** on the least.
- So the day cap **cannot be reached before the 85% rest wall fires**. It is not a brake.
- The 10M standing default *would* bind: **3.77%** of a weekly meter. That is the positive arm.

**The alert uses the most generous bracket** — the highest rate, so the smallest slice of the meter
the cap represents. A non-binding verdict therefore means non-binding even on the reading most
favourable to the wall. The fail direction is away from acting, the same asymmetry
`check-deploy-serving.js` draws for an unknown deploy and `check-cycle-cadence.js` for an
unmeasurable board.

**The cap is passed in, never resolved here.** `public.resolve_day_token_cap()` is the one home of
the five-rung cap ladder; this script must not become a second one, so the cycle reads the resolver
and hands the number to `--day-cap` — exactly as `rollback-on-red.js` takes its CI conclusion by
`--jobs` rather than fetching it. The guard grades this on the REST paths the script actually
reaches for (only `runner_usage_readings` and `runner_cycles`), not on whether the words appear:
the payload deliberately *names* the resolver so John's reader is told where the number came from.

## QA — a discriminating bar, stated with what it would and would not catch

- **Live end-to-end, not a seam proof.** `node scripts/check-token-wall-binding.js
  --day-cap=196000000 --cap-source=daily-max-box` against real Supabase returned `wall-non-binding`,
  exit 1, and **reproduced all four stored `tokens_per_pct` values exactly** from raw readings and
  cycle rows — independent confirmation, since the script never reads that column.
- **Would it still pass if the change did nothing?** No. `aSmallerCapReallyDoesBind()` is a positive
  arm: the same fixture with the 10M standing default returns `wall-binding` / exit 0. A build that
  answered "non-binding" unconditionally passes every other clause and fails that one.
- **Two retired designs run on the SAME fixture and lose.** The single-bracket form (the instruction
  step 3 itself used to carry — *"the two most recent readings"*) has no spread to report at all,
  and defined as a one-bracket ratio it is **1.0× — perfect agreement** — on a board that disagrees
  by 2.88×. The unit-blind form (today's est spend against the cap, both in est-token units: 25M
  against 196M) reports the wall **healthy**.
- **Three mutations, each asserted RED, restored tree green.** (1) alert off the *least* generous
  bracket → `212.96 !== 73.93`; (2) `MIN_BRACKETS = 1` → the single-bracket control fails;
  (3) `Number(c.est_tokens_dev)` with no finite-check → `0 !== 1` (the `Number(null) is 0` defect).
- `npm run build` green; `tests/regression/run-all.js` at baseline.
