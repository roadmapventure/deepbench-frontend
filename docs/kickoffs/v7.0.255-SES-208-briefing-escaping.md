**Class** `P9 - Bug Fixes` · tier `now` · epic *Selfbuild M3 — Independent Verification*

## How it was found — SES-135's test earned its keep before it shipped

This cycle's drain pick was `SES-135` (a permanent briefing-page render test). Building that test
meant rendering the page and asserting the locked section order. **The first render found this.**
`SES-135` was then released unbuilt and returns to the drain: a user-blocking failure on John's
daily surface preempts everything (step 4), and the render test is worth more written against a
page that works.

## The defect, measured in a real browser

Rendered the freshly built page in headless Chromium (`--dump-dom`), then again in jsdom:

| | sections rendered | `script` elements in `#page` | characters swallowed |
|---|---|---|---|
| before | **9** (`2 … 9`) | 1 | **51,860** |
| after | **16** (`2 … 15`) | 0 | 0 |

§9.1, §10 *waiting on your input*, §11, §12 vision claims, §13 the ladder, §14 and §15 Selfbuild
milestones were **absent**, held inside a script element as inert text. Zero console errors, zero
`pageerror`s, and the page still ends on a section boundary — which is why it went unnoticed.

## Root cause — one line wide, and a class

`question()` in `docs/runbooks/briefing-template.html` interpolated its database prose — `text`,
`ctx`, `yesMeans`, `noMeans` — **without `esc()`**, while `esc()` sits forty lines above it and is
used 55 times elsewhere in the same file. Open question `q-artifact-read-path-unreachable`
(`runner_questions` `0c8129f1`) has a `context` that quotes a literal `<script>` tag while
explaining the `SES-188` truncation measurement. That opened a real element mid-§9.

Surveyed rather than assumed, and fixed in the same breath: `plainBlock()` (`runner_items.plain_*`,
written by a cycle on **every ship**) and `card()`'s `title` (from `backlog_display_title()`) and
`tid` had the identical hole. `scripts/build-briefing.mjs:201` passes all of them through `J()`,
which is JSON-for-JavaScript and **not** HTML escaping — so the render boundary is the only place
this can be fixed.

## The rule, written next to `esc()` itself

> **Escape what came out of the database; never escape what the builder composed.**

`techHtml` and `idLine` are markup the builder wrote (tags, links, bold). Escaping them renders the
card bodies as visible source — the same defect facing the other way. The guard asserts **both**
halves, so an escape-everything sweep fails it exactly as the pre-fix file does.

## QA

- **Real-browser before/after above**, same build, same binary, one variable.
- The behavioural clause **slices the shipped `esc` / `question` / `plainBlock` out of the template
  by brace-matching and runs those** — it does not reimplement them (`SES-45`'s rule). It renders
  hostile prose in jsdom and asserts 0 script elements, the following section intact, **and the
  bracket still visible as text** — so a "fix" that strips the text instead of escaping it fails.
- **File-level negative control:** against `origin/dev`'s pre-change template, **5 of 7 clauses
  fail** and the behavioural one swallows 1,286 characters. The 2 that pass on both are the
  builder-markup boundary, kept deliberately.
- Every per-clause control is itself asserted to have teeth — **and that caught a real defect in
  this file's own first draft**: the `card-does-NOT-escape-builder-markup` control mutated a string
  the template does not contain, so it changed nothing. Reported rather than quietly repaired,
  because it is the `SES-158` vacuous-control failure reproducing inside its own guard.
- `npm run build` green; suite **70/70**.
