## Why the header sentence was false, which is the part worth writing down

This is not a wording slip, and reading it as one is how it comes back. **GitHub never auto-exposes
a repository secret to a step.** `secrets.*` is an expression that resolves only where it is
written, so a step with no `env:` block runs with no secrets in its environment regardless of how
many are configured on the repository.

That means the v7.0.286 promise described a future that could not arrive on its own. John added
both secrets and verified them live on 2026-08-29, reading the repository secrets page — and
nothing would have changed. The suite would have gone on seeing an environment with neither key,
and its credentialed halves would have gone on declaring themselves not-run, forever.

**The reason this could sit undetected is the reason it earns a regression guard.** A declared
not-run part looks *identical* whether the secret is absent or merely unexposed. The run is green
either way; the log reads the same; there is no failure to notice. The only place the difference is
visible at all is the workflow's own text — which is what `tests/regression/SES-180d-ci-credentialed-regression.js`
reads. It reads the shipped file rather than restating it (John's rule 2026-08-23, *"you should
never be throwing away tests"*), because a test that copies what it guards passes forever while the
shipped file rots.

### (b) The rename is part of the fix, not tidiness

`(no credentials)` becomes false in the log of every run on `dev` and `main` the moment the `env:`
block lands. A step whose name misreports its own environment is the header's defect one line
further down — which is why John's directive named the rename as its own lettered item rather than
folding it into (a).

**Named caveat rather than hidden.** On a `pull_request` from a **fork**, GitHub resolves both
secrets to the empty string by design. That is the correct and safe behaviour and this file must not
try to defeat it — but on that one path the new name over-promises. The run still reports the truth,
because the credentialed halves declare themselves not-run loudly and countably exactly as before,
so the log is self-correcting where the name cannot be. Said out loud in the workflow header.

### (c) The false claim is struck, not deleted

The retired sentence stays visible under a `[CORRECTED v7.0.304]` marker. A header that quietly
drops its own wrong claim teaches the next reader nothing, and the clause `false-claim-corrected`
pins that: the sentence may appear **only** as text the header explicitly marks corrected.

## The edit this ship forbids

In addition to v7.0.286's two, which remain in force and are both pinned by clauses of the new
guard: **reaching for `continue-on-error` when a credentialed half now FAILS.**

Those halves have never once been graded in CI. The first credentialed run is therefore the first
real verdict on them, and a genuine failure there is the single most valuable thing this ticket can
produce. A red run means the platform is broken, not that the gate is. Fix the finding.
