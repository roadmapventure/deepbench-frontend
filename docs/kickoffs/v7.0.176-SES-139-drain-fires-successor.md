### Two gates, both required

| Gate | Test | On failure |
|---|---|---|
| **A — this cycle did a cycle's work** | own `outcome` ∈ `shipped` / `gated_before_build` / `reverted` | fire nothing |
| **B — a standing drain still has claimable work** | `drain_epic_next('<your cycle id>')` → `outcome = 'pick'` | fire nothing |

Both pass → **exactly one** `fire_trigger` on `trig_017TZ3JZcLBK6AYH6DKURqMH` via the attached
`Claude_Code_Remote` connection. Record the result in the cycle row. A failed fire is a note, never
a wall — the 3-hour cron stays the fallback engine.

### Gate A is not in the ticket, and it is the whole safety of the feature

The ticket's bound (2) reads *"one successor per cycle, only from a cycle that ran its tail."*
A wall-stop **does** run its tail — step 3, verbatim: *"A wall-stop still runs the step-9 serial
tail (its record must be written), then ends."* So implemented exactly as written, a cycle that
stops at the token wall fires a successor, which stops at the same wall, which fires another: an
unbounded loop of `did_not_run` rows, each consuming a session and a few thousand tokens, with
nothing to break it but John noticing. **That turns the budget wall from a brake into a
metronome** — the precise inversion of what a wall is for.

This is not hypothetical arithmetic. Measured at cycle open, 03:14Z: the America/Chicago day stood
at **20,851,000 estimated tokens across 27 cycles**, against John's `budget_override` `43a9d4ae`
(`max_tokens` 25,000,000) which **expires at 05:00Z**. After that the allowance reverts to the 10M
uncalibrated cap, which the day has already passed — so the first cycle to fire after 05:00Z
wall-stops. Gate A is what makes that wall-stop the **end** of the chain rather than the start of
the loop.

### Gate B's call has a side effect on exactly one path, and that is correct

`drain_epic_next(p_cycle_id uuid)`, read from `pg_get_functiondef` this session rather than
assumed: when the epic's `now` tier is empty it **INSERTs a `runner_before_images` row and closes
the directive** before returning `retired`. So the tail's call is not a read-only preview. Leave
it that way: the last cycle of a drain closes the drain and fires nothing, which is exactly the
behaviour wanted, in the place the emptiness is first observed. Do **not** add a dry-run form to
dodge the write.

### The parameter is a stamp, not a selector — pass your cycle id

The function ignores its argument when choosing the drain (it reads the single oldest queued
`drain-epic` row regardless) and uses it **only** to stamp the retirement before-image. Passing the
wrong uuid therefore succeeds silently and returns the correct answer on every path except
retirement, where it attributes a before-image to a cycle that never existed.

Found this cycle, and recorded rather than hidden: step 5's call was made with the **epic** id
(`19a234f6-…`) instead of the cycle id. It returned a correct `pick`, so nothing was written and
nothing is owed — but SES-139 adds a *second* call site on the one path where the mistake costs
something, so the trap is written into the step rather than left for the next cycle.

### What does NOT self-terminate — stated, not papered over

The ticket's bound (3) — *"the chain self-terminates; drain retires at `open_now = 0`"* — holds only
if the epic's `now` tier can actually empty. Today it cannot: `SES-110` is `partial` with a
`.claude/` half an unattended cycle may not make (register B39, carded `9e7d8bf2`), and
`drain_epic_next`'s pick predicate reads `queue` and claims, **never `design_status`** — so a
`needs-desktop` member still comes back as a `pick`, is skipped procedurally at step 5 (`SES-114`),
and the cycle falls through to the class-sorted board and builds normally.

So the chain keeps running on real board work, and what bounds it is **Gate A plus the token
wall**, not the drain retiring. That is a genuine bound, but it is a different one than bound (3)
claims, and John should not read bound (3) as the thing that stops this.

### What is untouched

Drain **creation** stays John-only — property 5 of `drain_epic_next`, verbatim: *"Nothing creates a
drain row but John… The runner may read one; it may never write one."* This step continues a drain
he already wrote; it can never start one. Fleet size is stable rather than exponential: one
successor per cycle means N concurrent cycles stay N, each replacing itself, and the 3-hour cron
adds to that fleet without multiplying it.
