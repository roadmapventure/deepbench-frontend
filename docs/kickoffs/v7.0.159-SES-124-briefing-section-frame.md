## QA bar — and what makes it discriminating

`npm install && npm run build` green and `tests/regression/run-all.js` green are necessary but
prove nothing about this change: **the template is a doc, not a build input** — nothing imports it,
so both would pass if this ticket did nothing at all. Said plainly rather than dressed up.

The discriminating test is therefore a **structural assertion run against the rendered template**,
and it is built to fail on the pre-change file:

- Render the template's own `render()` output in Node (jsdom-free: the render chain is pure string
  concatenation over a stubbed `state`), then assert on the produced HTML.
- **Positive:** `Daily activity — today, 12:00 AM to 11:59 PM CST` present in the §2 heading; the
  tokens stat carries both an absolute figure and a `%`; both `gated before build` and `did not
  run` definitions present; `Today's findings` and a default-closed `Earlier today` card present;
  `decisions waiting` present in the masthead; both `.barlbl` bar labels present; the `.recorded`
  reading line on the reading card.
- **Negative control, which is what carries the proof:** the same assertions run against the
  **pre-change** template from `origin/dev` must **fail**, and the two removals must be present
  there and absent here (`Needs your call`, the footer `class="note"` paragraph). An
  implementation that merely added the new headings while leaving the removals in place would pass
  a completeness check and fail this.
- **Counter arithmetic, tested on state rather than eyeballed:** with 2 undecided cards + 1
  undecided question the masthead must read `3 decisions waiting`; with none it must read
  `Nothing needs you ✓`; with exactly 1 it must read `1 decision waiting` (singular) — the
  off-by-one plural is the bug a "looks right" check misses.
