## 2. CONTEXT

### The problem, stated plainly

Every AI-pattern display today is **catalog-driven**: it starts from the 24-entry static
`PATTERN_CATALOG` in `shared/ai-patterns.js`, renders that list, and then counts real log rows
into it. A pattern that has never run still gets a row. A pattern that *is* running but isn't in
the file lands in a fallback bucket.

**John's rule, stated this session, verbatim:**

> "for all displays, it should only show patterns that have logs. There should not be patterns
> hardcoded into the display, then it looks up the log. The list of logs in the display should be
> dynamic by what is available. For instance, if only 8 patterns have logs today, then only the 8
> patterns should show up in the displays. If the log table gets wiped out, then 0 logs and
> patterns will show up in the displays."

**This is not a new architectural decision — it is already LOCKED.** `ARCHITECTURE.md §19i`'s
corollary (locked 2026-07-22) says the same thing:

> "read Layer A/log data as it currently exists, read Layer C as it currently exists, join them
> live, and let anything with no current match fall into the existing generic 'not yet
> catalogued' fallback (already built, `useAIActivity.js`)"

The log drives. The vocabulary is a name lookup. The code simply never obeyed it.

### What this session is NOT

- **Not** a reconciliation table, alias column, or legacy-slug→new-slug map. `§19i`'s corollary
  bans these outright. If a logged slug has no `pattern_vocabulary` match, it falls back to a
  humanized slug. **Do not "fix" an ugly name by adding a special case or by falling back to
  `PATTERN_CATALOG` names — that is the banned artifact wearing a nicer coat.**
- **Not** a write-path change. `patterns_used` keeps getting written exactly as it is today.
- **Not** a backfill. No historical row is rewritten (`§19i`: "Historical data cannot be
  retroactively corrected").

### The Structural/Reasoning split is removed, not preserved — and why

The "By Pattern" section currently splits into **Structural** and **Reasoning** subsections,
driven by a `patternType` field that exists **only** in the static file. `pattern_vocabulary` has
no equivalent column (all 11 columns checked live).

John asked this session to web-research whether that taxonomy is standard **before** adopting it.
It is not — verified against two published sources, both fetched directly:

- **Anthropic, "Building Effective Agents"** (already cited inside `PATTERN_CATALOG`) does not use
  it. It splits **Workflows** from **Agents**, ordered simplest→most complex.
- **Huang & Zhou, "A Two-Dimensional Framework for AI Agent Design Patterns: Cognitive Function
  and Execution Topology"** (arXiv 2605.13850) uses **two perpendicular axes** — Cognitive
  Function (Perception, Memory, **Reasoning**, Action, Reflection, Collaboration, Governance) ×
  Execution Topology (Chain, Route, Parallel, Orchestrate, Loop, Hierarchy), the latter described
  as six ***structural*** archetypes.

DeepBench took "reasoning" from one axis and "structural" from the *other* and made them mutually
exclusive. They are orthogonal, not opposites — the binary cannot be correct by construction.
Choosing a real taxonomy is **`LOG-58` (Architecture)**, its own session, Tier 3. Until then this
session ships **one flat list ordered by call count** (John's explicit call).

### Task 1 — `src/hooks/useAIActivity.js`: make the log the driver
