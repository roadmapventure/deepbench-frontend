## The premise, revalidated live rather than quoted

Step 4a requires *the cycle* — not a script — to read CI's conclusion for `dev`'s head and hand it
to `scripts/rollback-on-red.js` as `--jobs`. The engine holds no credential and fetches nothing;
that is John's accepted `SES-182` design, not an accident. **This cycle hit the failure at its own
step 4a, before it had picked the ticket that describes it.**

Three measurements, all taken this cycle:

| Route | Result |
|---|---|
| GitHub MCP listing for one `ci.yml` run on `dev`, `per_page=1` | **71,575 characters** — over the tool-result cap, overflow into the `~/.claude/…/tool-results/` path **register B39 forbids an unattended cycle to shell-process**. Cycle `b0a3dde5` measured 71,371 the cycle before. |
| Raw HTTPS `api.github.com/repos/.../commits/<sha>/check-runs`, with the `GITHUB_TOKEN` this environment carries | **HTTP 403** — `"GitHub access is not enabled for this session. An org admin must connect the Claude GitHub App for this organization."` Refused at the proxy, **regardless of credential**. |
| Unauthenticated `api.github.com` | HTTP 403 |

No `gh` CLI. `git fetch` works (the git proxy serves it), but a git-level read carries no check
conclusions.

**A correction to this cycle's own first reading, recorded because it nearly went into the ledger
wrong.** The orchestrator initially concluded from the 403s that *there is no network path to the
GitHub API at all*, which would have made the ticket's own "bounded proxy — ordinary cycle work"
route impossible and forced a gated card. The Fable 5 subagent re-ran the MCP call and **got 71,575
characters back**: the connector path *is* reachable and only raw HTTPS is proxy-blocked. So the
ticket's original diagnosis — **size cap, compounded by B39** — was right all along, and the
would-be finding was wrong. It is written down here rather than quietly dropped.

What the subagent then established by search, and what actually decides the design: **there is no
bounded `sha → conclusion` read on any surface a cycle has.** `actions_list` takes no `head_sha`
filter and no minimal-output flag (one run object alone is ~70KB); the bounded `actions_get` /
`get_check_run` need an id obtainable only from the oversized listing; the `pull_request_*` forms
need a PR number and a `dev` push is not a PR; the Vercel signal is explicitly *not* CI (step 4a-bis:
*"a web server answered … is not evidence that CI graded anything"*).

## The decision: invert the direction

A proxy the cycle *hosts* would still have to call `api.github.com`, which needs a GitHub
credential — and the ticket's own decision boundary reserves **provisioning a secret** to John. So
the grader publishes its own grade instead:

`.github/workflows/ci.yml` gains a `report-conclusion` job that reads `needs.<job>.result` for every
blocking job and upserts one row into `public.ci_run_conclusions`. Step 4a reads that row from
Supabase — a path the cycle demonstrably already has — and hands `jobs` to `--jobs` verbatim.

**No secret is provisioned.** Both keys are the repository secrets `SES-180 (d)` (`v7.0.304`)
already exposes to the regression step. That is what keeps this out of the John-only lane
`ci.yml`'s own header names (adding secrets; branch protection).

## The three verdicts, and the one a rebuild drops

| `jobs` says | Step 4a does |
|---|---|
| every conclusion `success` | run the command — engine takes `record-green` |
| any conclusion `failure` | run it with `trigger=ci-red` — a real red |
| anything else (`cancelled`, `skipped`, empty, **no row**) | **could not tell — invoke nothing** |

**This is not defensive habit; it was measured.** ARM F below hands the engine a `cancelled` and it
lands on the **red** branch — `isRunGreen()` refuses it as green, which is *not* the same claim as
"this run was red". `concurrency: cancel-in-progress` cancels superseded runs routinely, so a
`cancelled` handed in as `ci-red` would send `decide()` toward a revert on a run that graded nothing.
Same asymmetry step 4a-bis already draws for the deploy probe: unknown is not red.

**A missing row is likewise not a red.** The reporting job cannot report its own failure — if it
dies, no row is written, the anchor goes **stale**, which is `rollback-on-red.js`'s own stated fail
direction (stale, never wrong).

## The two guards on the job, which fail in opposite directions

- **`always()`** — a run whose `checks` job **failed** is the case the anchor most needs recorded,
  and the default `success()` condition skips exactly it.
- **`github.event_name == 'push'`** — on a fork PR both secrets resolve to the empty string by
  GitHub's design, so without this the `curl` fails and paints an innocent contributor's PR red, and
  it would write rows for PR-branch shas never pushed to `dev`.

## Scope

## What this does NOT claim

The anchor is only as fresh as CI has actually graded, and at step 4a the row for a just-pushed head
usually will not exist yet — the read rule is head-sha, else the newest row whose `commit_sha` is an
**ancestor** of head, verified with `git merge-base --is-ancestor`, never assumed. And this ship
records no anchor of its own: its own CI run has not happened yet at the time of writing.
