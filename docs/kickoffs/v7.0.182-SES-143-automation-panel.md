## 6. DESIGN RULES

- **The gate is CODE, not prose.** This platform has now paid seven times for a rule each cycle must remember (`SES-86` phase 3, `v7.0.146`, `SES-101`, `SES-111`, `SES-127`, `SES-128`, `SES-129`). The runbook calls one function and reads a verdict; it does not re-derive pacing arithmetic per cycle.
- **THE ONE THAT WOULD HAVE SHIPPED WRONG — the predecessor must be a cycle that actually RAN.** The obvious implementation reads "the most recent `runner_cycles` row before mine". Under an hourly cron and a 3-hour interval that **wedges the runner shut forever**: `t=0` runs, `t=1h` is paced, and from then on every fire's predecessor is the *paced* row an hour earlier, which is always `< 3h` old — so the runner never runs again and the only thing that would notice is John. `scheduler_gate()` therefore reads the most recent row **whose outcome is not `did_not_run`** (a `failed` cycle counts — it consumed a slot). This is QA'd with a negative control, not reasoned about.
- **It fails OPEN in every unknown.** No settings row, a NULL column, no predecessor, an unrecognised trigger → `verdict = 'run'`. A gate that can silently stop the whole fleet must never stop it by accident; John's explicit `scheduler_on = false` is the only thing that switches the runner off, and that is a decision he made, not a default the code fell into.
- **The scheduler governs SCHEDULED cycles only** (spec, verbatim). A chained drain successor (`trigger: chained (drain continuation)`, `SES-141`) is exempt and runs regardless of interval; scheduler OFF + drain ON = the chain still runs; both off = nothing runs, and the panel says exactly that.
- **A manual fire is exempt, by the convention this repo already uses for the same question.** `runner-cycle.md` step 1 already distinguishes a manual fire from a scheduled one by whether the start time *sits off the cron grid*. The same test decides pacing, because the alternative is that John taps his own *"▶ Run a cycle now"* link — which the spec puts **on this very panel** — and nothing happens, silently. The cron minute is a **column** (`cron_minute`, default 40, read live from `list_triggers` this cycle) rather than a literal, so correcting it is one `UPDATE` and not a migration. **This is the one place the spec is silent and the implementation had to choose**, so it is not buried: it is stated on the card and filed as question `q-manual-fire-pacing` for John, and the choice made is the one that cannot make his own button dead.
- **A paced cycle still runs the serial tail.** The standing prohibition — *"never end a cycle without running the tail"* — has no exception and this cycle does not invent one. The cost is real (a rebuild on every paced fire) and is named on the card rather than quietly optimised away.
- **Checking the drain box is John naming a drain, and that is already sanctioned.** `drain_epic_next()` property 5 reads *"Nothing creates a drain row but John's own declaration — a directive row **or a briefing tap**."* The harvest writes the directive and captures the named scope per `SES-142`; the runner still never creates one on its own initiative.
- **The panel is a control, not a decision owed** — its rows carry **no** `data-awaits`, the same call `SES-127` made for §10 and `SES-132` for §9.1. Inflating §1's counter with a switch is the masthead-disagrees-with-the-page failure `countWaiting()` exists to prevent.
- **The locked order is extended, never renumbered** (`SES-124`'s rule, and how §4.1/§7.1/§9.1 already work). The section is `§2b`, the name the spec itself gives it.
- **John's un-harvested tap wins the render.** The checkbox shows `state.settings` when he has touched it, the DB value otherwise — the same precedence `items` / `answers` already use, so a tap never appears to have been discarded while it waits for a harvest.
