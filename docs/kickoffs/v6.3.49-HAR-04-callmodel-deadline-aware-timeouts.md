## 1. CONTEXT

**The problem, in plain terms:** a single agent turn (e.g. Marcus answering a Channel Intelligence question) makes an Anthropic call with up to 55 seconds to finish. If that response comes back malformed (missing a required schema field), the code retries once — and that retry *also* gets up to 55 seconds of its own. But the whole request only has 60 seconds total before Vercel kills the function outright, with no graceful handling — the connection just dies, no error surfaced, nothing logged beyond a generic timeout. From the user's side: a spinner, then silence.

**Root cause, confirmed by reading the code directly (not assumed):** `request-receivable.js`'s `postToAnthropicWithRetry()` (the main call) and the parse-failure retry fetch (`callModel()`, ~line 213) each hardcode their own independent `AbortSignal.timeout(55000)`, with zero awareness of how much of the caller's actual `maxDuration` budget is already spent. `sendRequest()`'s guardrails check adds a further independent `AbortSignal.timeout(20000)`. None of these three coordinate with each other or with the surrounding function's real ceiling.

**Confirmed relevant to Channel Intelligence, not just Project Management's `plan.js`:** `execute.js`'s `runLoop()` (CI's real agent loop) calls `callModel()` directly for every hop (~line 542) and `sendRequest()` for the final terminal answer (~line 622). `runLoop()` already computes and checks a real `deadline` before starting each hop (`AA-139`'s hybrid checkpoint trigger, using `getHopBudgetReserveMs()`'s p99-latency estimates, `AA-196`) — real protection, but it estimates *typical* hop latency, not the doubled-latency tail case where `callModel()`'s own internal parse-failure retry fires. A hop can pass the pre-hop check and then blow the ceiling from inside `callModel()` itself, because the loop's own `deadline` value is never threaded into the `callModel()`/`sendRequest()` calls it makes. This matches the already-observed "Intermittent 504s under load" symptom (`AA-69`'s original finding).

**Split from `AA-69` 2026-07-17 (`S-SES003-TSR-design`):** the original finding bundled this shared-Harness issue with a separate, `plan.js`-specific gap (that file's `prompt-service` action has zero budget-checking between its own pipeline steps at all, unlike `execute.js`). That half is not Channel-Intelligence-relevant and stays in `docs/FEATURES-LATER.md` as `AA-69`, out of scope here. This session is the CI-relevant half only.

**Fix direction (reuses an existing pattern, invents nothing new):** `execute.js` already threads a `deadline` value end-to-end for its own hop-budget checks (`_deadline` param, `AA-139`). Extend that same value one level deeper — into `callModel()`/`sendRequest()` themselves — so each of their internal Anthropic calls is bounded by whatever time is *actually* left, not a blind fixed constant. When there isn't enough time left to viably attempt a call, fail fast with a clear, immediate error instead of attempting one Vercel will likely kill anyway with zero trace.

**Byte-identical for every caller that doesn't opt in:** `deadline` is a new *optional* parameter. Any caller that omits it (`plan.js`, `api/_lib/handlers/confirmation.js`) gets exactly today's behavior — a fresh 55s/20s window computed at call time, unchanged. This session touches zero behavior for `plan.js`'s own `AA-69` risk; that stays exactly as it is today, tracked separately.

## 4. TASKS (max 4)

### Task 1 — `request-receivable.js`: deadline-aware main call + parse-failure retry

In `callModel()`:
- Add an optional `deadline` param (epoch ms). When omitted, default to `Date.now() + 55000` at the moment `callModel()` is invoked — this preserves today's exact behavior for any caller that doesn't pass one.
- Add a constant `MIN_VIABLE_CALL_MS = 8000` — below this much remaining time, don't attempt a call at all; fail fast instead.
- `postToAnthropicWithRetry(body, headers, deadline)`: compute `remainingMs = deadline - Date.now()` before each attempt. If `remainingMs < MIN_VIABLE_CALL_MS`, throw immediately (`status: 504`, message like `Insufficient time remaining for Anthropic call (Xms left)`) rather than attempting a doomed fetch. Otherwise use `signal: AbortSignal.timeout(Math.min(55000, remainingMs))`.
- The parse-failure retry (the second fetch, ~line 213): before attempting, compute remaining time against the same `deadline`. If below `MIN_VIABLE_CALL_MS`, skip the retry entirely and throw the existing `"Parse failed and retry also failed"` (422) error immediately, with a detail noting the retry was skipped for insufficient time — do not attempt the second fetch. Otherwise bound its `AbortSignal.timeout()` the same way (`Math.min(55000, remainingMs)`).
- `FEATURE: HAR-04` comment at each change location, per `STANDARDS.md`'s "Always Required" checklist.

### Task 2 — `request-receivable.js`: `sendRequest()` threads `deadline` through

- `sendRequest()` accepts the same optional `deadline` param (same default-when-omitted rule: `Date.now() + 55000` at call time for its own `callModel()` call if not otherwise specified — see below for the exact default derivation).
- When calling its own `callModel()` (the non-`precomputed_turn` branch), pass `deadline` through unchanged.
- The guardrails check (~line 401): compute remaining time against `deadline` (default `Date.now() + 20000` when `sendRequest()` itself received no `deadline`). If below a small floor (`3000ms` — guardrails already fails open on any error today, so skipping it outright under time pressure is safe and consistent with existing behavior), skip the call entirely (same as today's existing catch-branch: `guardrails_passed` stays `true`, `guardrailsRan` stays `false`). Otherwise bound its `AbortSignal.timeout()` to `Math.min(20000, remainingMs)`.

### Task 3 — `execute.js`: thread the loop's existing `deadline` into both call sites

- The `callModel()` call in `runLoop()` (~line 542): add `deadline` (the value `runLoop()` already computes and uses for its own hop-budget check — no new computation, just pass the existing variable through).
- The `sendRequest()` call in `runLoop()` (~line 622): same — add `deadline`.
- No other logic in `execute.js` changes. `MAX_LOOP_DEPTH`, `getHopBudgetReserveMs()`, and the existing pre-hop/pre-dispatch checkpoint checks are untouched and orthogonal to this fix.
