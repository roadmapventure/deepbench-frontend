## CONTEXT

**There is no React error boundary anywhere in `src/`.** Verified fresh 2026-07-23 — `componentDidCatch`, `getDerivedStateFromError`, `ErrorBoundary`, `error-boundary` all return zero hits across `src/` and `api/`. React's default with no boundary is to unmount the entire tree, which is why `CHI-65`'s single malformed field takes the whole page down.

The cost is not the white screen. `MarketIntelligenceScreen.jsx:3007` holds the conversation in `const [messages, setMessages] = useState([])` with **no persistence of any kind** — no `localStorage`, no server rehydrate. When the tree unmounts, every turn of the conversation is destroyed permanently.

**Placement is the entire design.** A boundary unmounts everything *below* it. A boundary at the app root, or one wrapping the screen, still unmounts `MarketIntelligenceScreen` and takes `messages` with it — it converts a white screen into a nicer white screen and saves nothing. Only a boundary *inside* the screen leaves the chat column mounted. That is why this session wraps `Drawer`'s children rather than the screen.

`Drawer` (`src/components/SharedUI.jsx:349`) is rendered 11 times by Channel Intelligence, and `CHI-65`'s crash site (`MarketIntelligenceScreen.jsx:2106-2108`) sits inside one of them — `<Drawer title={\`${intentLabel} Result\`}>` at line 2063. Wrapping the shared component covers all 11 in one edit and requires no change to `MarketIntelligenceScreen.jsx` at all.

**Why the two fallbacks differ.** Inside a drawer the boundary is standing in a slot where Alex Reeves' — Screen Controls Editor — rendered content belongs, so §19j's rule applies: the screen never writes about the analysis. It does *not* forbid the platform reporting that the platform broke — that is the same reasoning that already permits the five `kind: "error"` chat bubbles in `MarketIntelligenceScreen.jsx` ("Something went wrong reaching Marcus — try again."). A crash notice is platform-about-platform. So the drawer speaks, but says nothing about what the agent did or didn't find.

**Why the drawer fallback has no retry button.** When a drawer crashes the data is still in state and intact — what failed is the code rendering it. A retry that re-renders the same subtree hands React the identical bad value and throws again, every time. The only real recovery is a fresh call, which the user reaches through the chat. Hence the copy directs them there.

## TASKS (3)

### Task 1 — `src/components/ErrorBoundary.jsx` (new file)

A class component (boundaries cannot be written as hooks). One `variant` prop selects the fallback; everything else is shared.

```jsx
// DeepBench v6.3.137 | ErrorBoundary.jsx | CHI-66 — the platform's only React error boundary
// FEATURE: CHI-66 — before this, src/ had zero boundaries, so any render error unmounted the whole
// tree and destroyed MarketIntelligenceScreen's unpersisted `messages` state (the entire
// conversation). Two variants: "page" at the app root, where there is nothing left to preserve and
// a reload is the only recovery; "inline" inside Drawer, where the surrounding screen stays mounted
// and the conversation survives.
//
// The fallback copy is platform-about-platform — it reports that the platform broke and never
// describes, labels, or stands in for agent content. ARCHITECTURE.md §19j ("The screen holds no
// content policy") governs the drawer case specifically: do not add wording about what the agent
// found, did not find, or should have returned.
import { Component } from "react";
import { T, body } from "../tokens.js";

export default class ErrorBoundary extends Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    // console only, deliberately. ai_activity_log holds AI call facts (ARCHITECTURE.md §19i); a
    // React render crash is not an AI call and must not be written there.
    console.error("[ErrorBoundary]", this.props.variant, error, info?.componentStack);
  }

  render() {
    if (!this.state.hasError) return this.props.children;

    if (this.props.variant === "page") {
      return (
        <div style={{fontFamily:body,fontSize:13,color:T.ink,padding:"40px 24px",display:"flex",flexDirection:"column",alignItems:"flex-start",gap:12}}>
          <div>Something went wrong — reload the page.</div>
          <button onClick={() => window.location.reload()}
            style={{fontFamily:body,fontSize:12,color:T.ink,background:T.card,border:`1px solid ${T.line}`,padding:"7px 14px",cursor:"pointer"}}>
            Reload
          </button>
        </div>
      );
    }

    return (
      <div style={{fontFamily:body,fontSize:11.5,lineHeight:1.5,color:T.muted}}>
        Something went wrong displaying this — ask your latest question in chat again.
      </div>
    );
  }
}
```

Both copy strings are final and were approved verbatim by John this session. Do not reword either one.

## DESIGN RULES

- **Tokens only** (`.claude/rules/design-tokens.md`). Every colour comes from `T`; fonts from `tokens.js`'s `body`. No literal hex, no new token, no new font.
- **No new visual element beyond the two fallbacks specified.** No icon, no glyph, no coloured error banner, no border treatment. The inline fallback is one muted line of text; the page fallback is one line plus one button.
- **The inline fallback must never gain a retry/refresh control.** It would re-render the same failing subtree and re-crash. This is the constraint most likely to be "improved" by a later reader — it is deliberate.
- **Neither fallback may say anything about agent content** — nothing about what was found, missing, empty, or expected (`ARCHITECTURE.md` §19j).

**Known and accepted limits, recorded so they are not mistaken for oversights:**
- Boundaries catch **render and lifecycle errors only** — not event handlers, not async/promise rejections. The existing "Something went wrong reaching Marcus — try again." class of failure is async and stays on its current try/catch, untouched.
- The conversation survives a crash **inside a drawer**. A crash in Column 1's chat, or in the screen's own top-level render, still hits the root boundary and loses it. Deliberate — every render crash actually observed to date is the `CHI-65` one, inside a drawer.
- `Drawer`'s only consumer today is `MarketIntelligenceScreen` (`DashboardScreen`'s `drawerOpen` references are unrelated local state — verified this session). Drawer-level protection is therefore Channel Intelligence only in practice.
