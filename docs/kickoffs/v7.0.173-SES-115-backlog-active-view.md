## The two things that would have shipped wrong, both found by measuring

These are the whole reason this ticket is not a five-line view.

**(1) `runner_items.kind` is `ship`, never `'shipped'`.** The ticket's own wording says *"an open
shipped `runner_items` card"*. Live values are exactly two: `ship` (50) and `gated_before_build`
(28). A view written from the ticket's string matches **zero rows**, so `'in review'` could never
fire — and nothing would look broken, because every row would simply keep its stored status.

**(2) `runner_items.backlog_id` is a DISPLAY STRING, not a ticket id.** Live values look like
`"SES-132 (Runner · P10 - Tooling)"`. The natural join `ri.backlog_id = b.backlog_id` matches
**zero rows**. Census of all 78 card rows: **61 carry a leading `XX-N` id, 16 do not**
(directive cards, invention proposals, `"no ticket yet …"`), 1 is NULL. The link is therefore
`substring(ri.backlog_id from '^[A-Za-z]+-[0-9]+')`, which yields NULL for exactly the 16 rows
that name no ticket — the right answer for them.

This is the `backlog_items.title` trap (`SES-91`) and `runner_cycles.item_id` (`SES-129`) in a
third costume: an id-shaped column that is really prose. **Negative control for the QA:** the
naive join returns `in review = 0`; the extraction returns `in review = 1` (`SES-132`, `done`
with an undecided `ship` card) and drops `done` from 38 to 37.

## The dependency the ticket did not anticipate — stated, not papered over

The ticket says check 3 should *"flag only if such a row still holds a queue number, claim, or
pin"*. **The snapshot the lint reads carries none of those three columns.** Its header is
`| # | ID | Type | Priority class | Title | Status | Session | Harvest | Description | Epic |
Design status | Kickoff |`, and `check-session-docs.js` is deliberately credential-free and
network-free (its own header: *"A network round trip does not belong in this path"*). So the
retarget is unbuildable as specified until the snapshot can show residue.

**Resolution: append ONE column, `History residue`,** following the established
append-last extension pattern (`SES-110` added `Epic`; `SES-112` added `Design status` /
`Kickoff`; the mirror reader addresses cells by index and tolerates short rows).

**Why one derived column and not three raw ones.** Exporting `queue` / `claimed_at` /
`pinned_position` raw would destroy the snapshot's defining property — *"a diff here always means
the board actually moved"*. `claimed_at` changes twice per cycle on 8 cycles a day, and `queue`
churns all 601 rows on every recompute, neither of which is board content. `History residue` is
computed **only for `done`/`removed` rows** and is empty for every other row and for a clean
history row — so today it adds **zero bytes of churn** and produces a diff precisely when there
is drift to see, which is when John wants one.

## Why mode is a FUNCTION and the view is thin

The ticket specifies `CREATE VIEW backlog_active AS SELECT *, computed mode … WHERE status NOT IN
('done','removed')`. Written that way, the `'done'` branch of the mode expression is **dead code
by construction** — a `done` row can never appear in a view that filters `done` out. Putting the
definition in `public.backlog_mode()` and letting the view call it keeps the ticket's "one owning
definition for every display/summary" true for **history rows too**, which is what §11-style
census queries and the promised live epic shipped-counts (`"Automation: N done, M open"`) need.
The view's shape is otherwise exactly as specified.

| mode | rule | n |

Precedence is top-down and deliberate: a re-opened ticket someone is actively building reads
`in development` even if an old card of its is still undecided.
