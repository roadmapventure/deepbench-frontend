## 2. CONTEXT

Found live 2026-07-21 (`design-chi-50-0721`) verifying `CHI-50`: clicking Accept on Nadia — Data Analyst's Draft Forecast proposal returned an HTTP 500 — `"reasoning-write handler: writeContent failed -- denied-source-chunk-cross-room-or-missing"`.

**Root-caused this session (`design-dat-7-0721`), verified directly against live Supabase data — not from memory:**

The error tier name suggests a room-boundary/credential bug, but it is not. Pulled the real failed `pending_confirmations` row (`id: 1f9ad39e-b7bb-40fd-83f5-8f850aa92a16`, `status: accept_failed`, created `2026-07-21T20:53:16Z`): its `proposed_action.chunk_id` is `"JPN-GROWTH-STRUCTURAL-HYP-001"` — a human-readable label Nadia invented, not a real `the_library` id. A second live "opinion" proposal from the same session (`id: 2c10b0ef-...`, `chunk_id: "JPN-STRUCTURAL-CYCLE-001"`) shows the identical shape. 2/2 real organic samples.

**Why:** `data-patch-intent`'s Supabase `skill_profiles` trait schema has zero instruction on its `chunk_id` output field (`{"type": ["string","null"]}`, no `description`, no `analysis_instructions` at all on this intent — unlike its sibling `data-patch-execute-intent`, which does have `analysis_instructions`). Nothing tells the model to copy `task_context.disputed_chunk_id` (the real id the client sends in) verbatim into its own `chunk_id` output. Left unconstrained, Sonnet invents a descriptive slug instead.

That bad value then flows unchanged: `data-patch-intent`'s `chunk_id` → (on Accept) `data-patch-execute-intent`'s `task_context` → its own `analysis_instructions` faithfully copy it into `source_chunk_ids: [chunk_id]` (this step is working exactly as designed) → `reasoning-write.js` → `lib/search-harness.js`'s `writeTheReasoning()`, whose `AA-189` UUID-format guard correctly detects the non-UUID string and returns a clean `{success:false, _access:{tier:"denied-source-chunk-cross-room-or-missing"}}` denial. **This guard is not the bug and this session does not change it.**

**Second, independently-confirmed bug, same incident:** `reasoning-write.js`'s `handle()` throws a bare, statusless `Error` on any `!result.success`, which `execute.js`'s single outer catch (line ~1240) maps to a raw HTTP 500. Checked `library-write.js` (Eleanor — Librarian's equivalent write handler) — identical bare-throw-on-denial shape. Same bug pattern at 2 call sites, both dispatched generically through the same `format_contract.handler` registry (`api/prompt/request-receivable.js`'s `HANDLERS`/`KNOWN_HANDLERS`) — fixed together, not as two independent patches, per `CLAUDE-DESIGN.md`'s multi-site-bug-pattern check. `request-receivable.js` already has the target idiom in the same file, for its own "unknown handler" case: `throw Object.assign(new Error(...), { status: 501 })`, forwarded verbatim by `execute.js`'s outer catch (`res.status(e.status || 500).json({ error: e.message, ...(e.detail ? { detail: e.detail } : {}) })`, line 1249) — no `execute.js` change needed, just matching that existing idiom in the two handlers.

The client's `resolveConfirmation()` (non-streamed path only — the streamed/SSE path via `readSSEResult()` already forwards `.status`/`.detail` correctly, line 495) currently discards the response body on failure entirely (`if (!res.ok) throw new Error(...)`), so even with a real status/detail on the wire, `onResolveConfirmation()`'s catch has nothing to read. Confirmed live: `onResolveConfirmation` never passes `onProgress`, so this call always takes the non-streamed path — the gap is real, not already covered by the SSE branch.

1. Constrain `data-patch-intent`'s `chunk_id` field so Nadia stops inventing it; pin `temperature: 0` (matches `AA-154`'s existing precedent for other precision-decision intents).

Fix the shared denial-handling gap in both write handlers (status/detail, not a bare throw) AND thread that detail through `resolveConfirmation()` so `onResolveConfirmation()` can show a real recovery message instead of the current always-generic "Something went wrong resolving that — try again" (which is actively wrong advice here — retrying Accept on this exact proposal will fail identically forever, since the bad `chunk_id` is permanently baked into the stored `proposed_action`; only Edit or Reject actually unblock the user).

```js
// test-dat-7-api.mjs -- DAT-7 live API test. Delete before committing.
import { runCapability, resolveAccept } from './api/capabilities/execute.js';
import { writeContent } from './lib/search-harness.js';

let pass = 0, fail = 0;
function check(name, cond) {
  if (cond) { console.log(`PASS: ${name}`); pass++; }
  else { console.log(`FAIL: ${name}`); fail++; }
}

// A real the_library row in apple-cso-data-room, confirmed live this design session --
// use this exact id so the loop-closure check below is uniquely traceable (STANDARDS.md
// Section 4's "loop-closure proof specificity" -- not a generic keyword also reachable
// from other seeded content).
const REAL_CHUNK_ID = '0d09ac6e-baca-4471-a3f5-c0a63007882d';

async function main() {
  // 1. Task 1 fix: a real live data-patch-intent call must echo REAL_CHUNK_ID verbatim into
  // its own chunk_id output, not invent a label.
  const proposeResult = await runCapability({
    capability_slug: 'data-analysis', intent_slug: 'data-patch-intent', agent_id: 'nadia',
    task_context: {
      disputed_chunk_id: REAL_CHUNK_ID,
      correction: 'Test correction for DAT-7 live verification -- Japan upgrade-cycle dataset is well-sourced.',
      user_reasoning: 'DAT-7 Category L test -- confirming chunk_id echo fix.',
    },
  });
  check('data-patch-intent produced an action', ['opinion', 'promote', 'no_action'].includes(proposeResult.content?.action || proposeResult.action));
  const echoedChunkId = proposeResult.content?.chunk_id ?? proposeResult.chunk_id;
  check('chunk_id echoes the real id verbatim (Task 1 fix)', echoedChunkId === REAL_CHUNK_ID);

  // 2. Task 2 fix, reasoning-write.js: a deliberately malformed source_chunk_ids must now
  // throw with status:422 and detail.tier, not a bare crash.
  let reasoningDenialCaught = null;
  try {
    await writeContent({
      requestingAgentId: 'nadia', store: 'the_reasoning', tenantId: 'global',
      data_room_tag: 'apple-cso-data-room',
      content: 'DAT-7 live test -- deliberately malformed source_chunk_ids.',
      source_chunk_ids: ['not-a-real-uuid-label'],
    }).then(result => {
      if (!result.success) {
        const tier = result._access?.tier || 'unknown';
        throw Object.assign(new Error(`reasoning-write handler: writeContent failed -- ${tier}`), { status: 422, detail: { tier } });
      }
    });
  } catch (e) { reasoningDenialCaught = e; }
  check('malformed source_chunk_ids denies gracefully (not a crash)', reasoningDenialCaught?.status === 422);
  check('denial detail.tier is the expected UUID-format tier', reasoningDenialCaught?.detail?.tier === 'denied-source-chunk-cross-room-or-missing');

  // 3. Full end-to-end loop closure: propose -> accept -> a real the_reasoning row exists
  // citing REAL_CHUNK_ID. This is the actual live repro (an opinion proposal, accepted)
  // now succeeding instead of 500ing.
  // (proposeResult from step 1 doesn't create a pending_confirmation on its own in this test
  // harness -- runCapability() alone doesn't insert one; this step re-runs through the full
  // confirmation-creation path used by the real UI, then accepts it.)
  const fullProposal = await runCapability({
    capability_slug: 'data-analysis', intent_slug: 'data-patch-intent', agent_id: 'nadia',
    task_context: {
      disputed_chunk_id: REAL_CHUNK_ID,
      correction: 'DAT-7 end-to-end live test -- accept should now succeed.',
      user_reasoning: 'DAT-7 Category L loop-closure test.',
    },
  });
  check('full proposal returned a confirmation_id', !!fullProposal.confirmation_id);
  if (fullProposal.confirmation_id) {
    const acceptResult = await resolveAccept({ confirmation_id: fullProposal.confirmation_id });
    check('accept succeeded (no throw, real entry_id)', !!acceptResult?.entry_id || acceptResult?.handler_result?.entry?.id != null);
  } else {
    check('accept succeeded (no throw, real entry_id)', false);
  }

  console.log(`\n${pass} passed, ${fail} failed`);
  if (fail > 0) process.exit(1);
}

main().catch(e => { console.error('LIVE TEST ERROR:', e); process.exit(1); });
```
