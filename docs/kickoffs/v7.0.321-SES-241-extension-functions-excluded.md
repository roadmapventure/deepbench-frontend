## Premise revalidation (`SES-87`, register B7) — HOLDS, with an exact number

Read from `pg_get_viewdef` and the live catalog, not recalled. The `functions` branch of
`public._backup_schema_ddl` is filtered on schema and `prokind` alone:

```sql
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public' AND p.prokind = 'f'      -- no ownership test at all
```

| | count | of which `LANGUAGE c` |
|---|---|---|
| public functions total | **146** | — |
| **extension-owned** (`pg_depend` deptype `e`) | **114** | **114** |
| our own | **32** | **0** |

The ticket's "~114" is exactly 114. Each is already created by `CREATE EXTENSION vector` at
`sort_key 0` of the same file, and no Supabase role may create a `LANGUAGE c` function, so each
fails `42501 permission denied for language c`.

**Why it is worth a cycle even though the restore succeeds.** The extension supplies the
functions, so nothing is lost — this is a **signal** defect. A clean restore prints ~114 expected
errors, and a *real* error printed among them is invisible. `SES-223 (c)` exists to make the
restore say what actually went wrong; this buries it.

## The design choice: ownership, never language

`pg_depend deptype = 'e'` identifies extension-owned objects exactly. The tempting shortcut is
`prolang <> 'c'`, and it is **wrong twice**:

- it would silently start dropping **our own** functions if one were ever written in C; and
- it would still emit a future extension's `plpgsql`/`sql` functions, which fail for a different
  reason — already created, and not ours to redefine.

The two forms are indistinguishable on today's catalog (all 114 extension functions are C, none of
ours is), which is precisely why the choice had to be made on the rule rather than on the numbers.

**What makes the exclusion provably lossless:** `ours_and_c = 0`. The excluded set and our own set
are disjoint by measurement, not by assumption.

## QA — asserted in both directions, never from the migration's success flag

`.claude/rules/supabase-column-grants.md`'s lesson generalised: *the denied thing must fail **and**
the legitimate thing must still work.* Measured after apply:

| assertion | before | after |
|---|---|---|
| `functions` statements | 146 | **32** (−114 exactly) |
| pgvector functions emitted | 60 named | **0** |
| `LANGUAGE c` statements emitted | 114 | **0** |
| `$libdir` / `LANGUAGE internal` emitted | 114 | **0** |
| the 10 load-bearing platform functions | present | **all 10 present** |
| every other section | — | **byte-identical** (extensions 5, sequences 2, tables 56, constraints 175, indexes 33, views 10, triggers 3, policies 3, acl-raw 70, grants 224) |

`migrations` moved 149 → 150 because this migration records itself; that is the one intended
difference outside the `functions` section.

**The negative control is the retired predicate applied to the same catalog** — so the guard proves
a *difference*, not a property both forms share. Against the pre-change form: clause (a) fails on
**114**, clause (b) on **60**, clause (d) on **114**.

**Stated honestly: clause (c) passes on both forms.** It is the *losslessness* guard — our 32
functions were emitted before and are emitted now — and it exists to catch a careless exclusion
that takes the wrong rows, which is the direction a count-only test cannot see. Calling it a
discriminating clause would be overclaiming.

**The guard is credential-gated and says so.** The object under test is a database view, not a
file, so there is no offline half; without credentials it declares `notRun` rather than passing
quietly (`SES-180 (b)`). Both arms were exercised at the ship.
