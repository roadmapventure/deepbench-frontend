## The function, and why each property is deliberate

```sql
SELECT public.claim_automation_lane_top('<TICKET-ID>');   -- returns the rank it assigned
```

- **Idempotent.** A ticket already at or above the open lane's minimum is left alone and its held
  rank returned, so a second call is a no-op and cannot ratchet a ticket to −2, −3 on every re-run.
- **It runs `recompute_backlog_queue()` itself.** `B4` makes a rank change a recompute event.
  Making the caller remember a second statement is the exact class of forgetting this ticket
  exists to remove — the same reasoning as `SES-86` phase 3 (prose → `automation_rank`) and
  `v7.0.146` (render-time prose → `plain_cant` columns).
- **The open lane is the lane.** `min()` reads only `status NOT IN ('done','removed')`, so closed
  tickets keep their historical rank (`ADM-1` = 1, `SES-100` = 8) without competing. An empty lane
  gives `coalesce(min, 1) − 1 = 0`, so the first automation ticket gets rank 0.
- **`backlog_id` is not unique** (`SES-86` phase 2 QA; `CHI-48` occupies two rows). An `UPDATE` by
  `backlog_id` writes every row carrying that id — correct here, both copies are one ticket — so
  the `ROW_COUNT` guard proves *at least one*, never *exactly one*, and says so in the header.
- **Invoker rights, not `SECURITY DEFINER`** (unlike `recompute_backlog_queue()`, which is
  definer). `anon`/`authenticated` hold zero write privileges on `backlog_items` (`DAT-18`), so the
  inner `UPDATE` would fail for them anyway; the revoke makes that a gate rather than a side effect.

*queue number*, not just that a rank was written, is what separates "top of the lane" from "bottom

## Found live during this migration's own QA — a rule general to every future function

`REVOKE EXECUTE ON FUNCTION … FROM anon, authenticated` **reported success and changed nothing.**
`has_function_privilege('anon', …)` still returned `true` afterwards, because Postgres grants
`EXECUTE` to `PUBLIC` by default and the narrower revoke cannot subtract from the broader grant.

This is the **exact function-level twin of `.claude/rules/supabase-column-grants.md`**, which
records the same shape for a column `REVOKE` against a table-level `GRANT` — and it was caught for
the same reason that rule insists on: the QA asserted the denial *and* the still-working
permission, instead of trusting the migration's success flag. The working form:

```sql
REVOKE EXECUTE ON FUNCTION public.claim_automation_lane_top(text) FROM PUBLIC, anon, authenticated;
GRANT  EXECUTE ON FUNCTION public.claim_automation_lane_top(text) TO postgres, service_role;
```

Written into `runner-cycle.md` step 5 alongside the lane rule. It arguably belongs in
`.claude/rules/supabase-column-grants.md` as an addendum — which an unattended cycle may not write;
that is on the card below with the rest.
