## 6. DESIGN RULES

- **The order is not re-derived — it is copied.** The function's `ORDER BY` is the step-5 query's
  `ORDER BY`, clause for clause, including all five traps the runbook documents: numeric class
  extract (`P10` must not sort before `P2`), suffix tolerance (`P9 - Bug Fixes · FLAGGED`), the
  `(Beta-gate|Post-beta)` regex rather than `ILIKE '%beta%'`, `created_at DESC` for newest-first,
  and `backlog_id` last as the deterministic tie-break. Those warnings move to the function; they
  do not stop applying.
- **The renumber must never touch `updated_at`.** Every recompute would otherwise rewrite the
  whole board's modification time, which would destroy the "sort-field edit" signal the recompute
  is triggered *by*, and would make `BACKLOG-SNAPSHOT.md` churn on cycles that changed nothing.
- **`claimed_by` does not affect the number.** A claimed ticket keeps its queue position while a
  session works it; claims filter **selection**, not the board. Otherwise every claim would
  renumber everything beneath it and John's view would shuffle for no reason.
- **Gated tickets get numbers too** (B15) — gated-ness is a lane flag, never a missing position.
- **Before-image before every Supabase write** (§19v). The `queue` column is new, so its prior
  value for every row is definitionally NULL; that fact is recorded as one schema-level
  before-image naming the exact Reverse action, following step 8b's precedent that a
  `row_data = NULL` before-image means "this did not exist."
- **`.claude/` is not touched.** Step 0's rule stands: an unattended cycle does not enter that
  permission gate. `session-setup`'s step 2c would eventually want the same recompute call for
  manual sessions; that is carded, not attempted here.

## 9. CLAUDE CODE VERIFICATION CHECKLIST

Each check states what it would look like if the change did nothing:

1. **Order agreement.** The first 10 rows by `ORDER BY queue` are identical, in the same order, to
   the first 10 rows of the runbook's 5-clause query. *If the change did nothing, `queue` would be
   NULL everywhere and this returns no rows at all.*
2. **The discriminating half — a wrong sort would pass a weaker test.** Assert directly that no
   `P10 - Tooling` ticket outranks a `P2 - Inventive` ticket in the same tier (the lexical-sort
   trap), and that `P9 - Bug Fixes · FLAGGED` rows received numbers (the suffix trap). *A naive
   `ORDER BY priority_class` implementation passes "every row has a number" and fails both of
   these.*
3. **Idempotence.** A second immediate `recompute_backlog_queue()` returns **0** rows changed.
   *An implementation that renumbers unconditionally returns ~550 and would churn the board on
   every cycle.*
   **RESULT — this check failed, and the failure is the most useful thing this cycle found.**
   The first run pair read `550 → 0` and looked clean. It was **luck**. After filing a real new
   ticket (`SES-97`) the sequence read `435 → 2 → 0`: two rows kept moving on a board where
   nothing had changed. Root cause: `backlog_id` carries **no unique constraint** and `CHI-48`
   occupies two rows that are identical on all five sort keys, so `row_number()` is
   **non-deterministic** for that pair and can order it either way per run. Fixed in migration
   `ses86b_queue_deterministic_tiebreak` by appending the primary key `id` as a sixth and
   absolutely-unique final clause — which changes no position that was ever well-defined and only
   decides ties that had no defined answer. Re-verified: one settle run of 2, then **six
   consecutive recomputes at 0**. The duplicate itself is filed as `SES-97` (`P9 - Bug Fixes`,
   queue 116) and deliberately not fixed here.
   **Lesson worth keeping:** a single "second call returned 0" is not an idempotence proof on a
   board that has not changed shape. The test that actually discriminates is *insert a real row,
   recompute, then recompute again.*
4. **Fail-closed set.** Every `status = 'done'` or `priority_class IS NULL` ticket has
   `queue IS NULL`, and the numbered set is exactly `1..N` with no gaps or duplicates.
5. **`updated_at` untouched.** `max(updated_at)` over the board is unchanged across a recompute
   that moved rows.
6. **Function overload check** (`.claude/rules/supabase-function-signature.md`): exactly one
   `recompute_backlog_queue` in `pg_proc`.
7. **Grants** (`.claude/rules/supabase-column-grants.md`): verified before building that
   `backlog_items` carries **no** `anon`/`authenticated` grants at all (only `postgres` and
   `service_role`), so the new column has no public reader to break and no fail-closed gap to
   patch. Re-asserted after the migration.
8. `npm run build` green; `tests/regression/run-all.js` green.
