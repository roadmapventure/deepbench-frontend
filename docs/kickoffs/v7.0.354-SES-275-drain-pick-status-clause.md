## 1. How this ticket came to exist — a step-5 blocker preemption, disclosed rather than buried

This cycle did **not** set out to build `SES-275`; the ticket did not exist when the cycle opened.
Under the Selfbuild Prime Directive (`a0ef9525`) §2, selection is (a) mission directives, (b) the
declared drain, (c) a buildable Selfbuild ticket, "and nothing else". The cycle reached §2(b), and
the drain call itself returned a wrong answer. Fixing the instrument the Prime Directive orders you
to use is step 4's *"a blocker preempts everything — fix it first, root-cause-first"* rule arriving
one step later, and it is the same shape as two cycles earlier the same day: `e89251a2` (step-4a
blocker, shipped `v7.0.342`) and `fefa6728` (CI red at step 4a → filed and shipped `SES-273`,
`v7.0.353`, also no epic, also `P10 - Tooling`).

**The named deviation** (`SES-196` convention): a brand-new ticket is not a Selfbuild-epic member,
so §2(c) does not literally authorise it. It is claimed here as a preemption, not as a §2(c) pick,
and the ticket carries **no epic** precisely so it can never hold a drain open.

## 2. The defect

`public.drain_epic_next()`'s **pick** predicate had no `status` clause for `done`/`removed`. It
excluded finished members only through `b.queue IS NOT NULL`, on the strength of its own comment:

> `'done'/'removed' need no clause (the recompute strips their queue)`

That is an invariant maintained by **other writers** — whoever sets a ticket `done` must also run
`recompute_backlog_queue()`. The **retirement** predicate in the same function has always carried
the clause explicitly, so the two halves of one function already disagreed about whether the
invariant may be assumed.

**Measured live, 2026-09-01T00:2xZ, on the real board:** the attended session `ses-258-244` set
`SES-244` to `done` at `2026-08-31T23:11:30Z` without running the recompute. The row kept
**queue 265**, and this cycle's step-5 call returned `outcome = 'pick'`, `backlog_id = 'SES-244'`.

## 3. What it costs — the outcome word, not a wrong build

Step 5's atomic claim carries `AND status <> 'done'`, so the claim returns 0 rows and the cycle
drops to the next ticket (B24). **No duplicate build is reachable from here** — and reading only
that far is how this defect gets under-fixed and the clause gets dropped as unnecessary.

What *is* reachable is the chain. Tail (8)'s **Gate B** fails only when `drain_epic_next()` returns
anything but `pick`; **Gate C** reads the pick's `design_status`, which is `NULL` on a finished row.
So **both gates pass** and a continuation cycle opens on a drain with nothing claimable — the
`SES-197` / `SES-218` inversion one level down: the chain running on because the terminator was
handed the wrong word.

## 5. The edit this forbids

**Adding the clause to the RETIREMENT predicate.** It is already there. This is the **fourth**
statement of that one boundary — `SES-154` (`delivered`), `SES-196` (the `design_status` flags),
`SES-218` (`blocked_by`) — and the failure is identical every time: a pick-side clause moved to the
retirement side returns `open_now = 0` and **retires**, closing John's standing directive on the
runner's own say-so.

**And: running the recompute is not a substitute.** It repairs the board it finds; it does nothing
about the next writer of `done` who skips it. *A rule each cycle must remember is a rule that gets
silently forgotten* — the `record_skip()` precedent this runbook records eight times over.
