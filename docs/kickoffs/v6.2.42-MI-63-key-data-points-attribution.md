## 2. CONTEXT

`key_data_points[]` renders identically in two places today — the Q&A chat bubble (`msg.keyDataPoints`) and `EvidenceColumn`'s hypothesis-test result (`st.key_data_points`) — as one flat, ambiguous list: `Label: Value · Source · Confidence`. Found live (design session, John's screenshots): `source` sometimes shows a raw `the_library` citation UUID (Q&A path) and sometimes a human-readable label (hypothesis-test path), with no indication of which case a user is looking at.

**Root cause, traced this design session against the live Supabase schema and the actual execution path (not the first, since-superseded mechanism this session initially and incorrectly assumed — corrected mid-session, see below):**

1. Neither `qa-answer-format` nor `intelligence-review-format`'s `key_data_points.items.properties.source` schema property has a `description` — confirmed via live `execute_sql` against `skill_profiles.traits`.
2. `lib/librarian.js`'s `formatLibraryEntry()` shows the model every retrieved `the_library` chunk as `--- LIBRARY ENTRY [id: <uuid>]: <title> ---`, with an explicit instruction to "cite the `[id: ...]` value exactly as shown" for the `citations` array. With no distinguishing instruction for `key_data_points.source`, the display agent over-applies that citation habit to a field meant to hold prose, not a citation key.
3. **Correction made mid-session:** this session first traced `execute.js`'s `fetchFormatOverride()` (the old "`AA-77` format-last" pattern) and concluded a Format Skill's `method`/`objective` never reaches the model. That pattern is dead — `MarketIntelligenceScreen.jsx`'s own comment (~L761) confirms it: "the old bundled `format_skill_profile_slug`/`display_agent_id` override (`AA-77` format-last pattern) is gone entirely." The live mechanism is a genuine, separate, agent-reasoned delegation: the content specialist (Marcus/Priya) completes their own turn first, then a second call (`ci-answer-display-intent` / `hyp-hypothesis-test-display-intent`) runs Michelle's real `request_help → agent-selection-intent → delegate_to_agent(is_final:true)` hand-off to whichever display agent she picks (Alex is "one candidate... not a guaranteed/hardcoded target," per the code comment). `db-assembly.js`'s `buildSections()` "intent" branch (L123-190, confirmed live) assembles that agent's `objective`+`method` **and** `traits.schema` normally — both channels genuinely reach the model. This does not change the fix (schema `description` is still the correct lever, same as the platform's existing `visualization` precedent, `ARCHITECTURE.md` §19g), it only corrects why the current behavior is inconsistent — the display agent's `method` text already governs `citations`, it simply never addresses `key_data_points.source`, a different field.
4. Confirmed the underlying data supports both real and theorized numbers by design: every `the_library` entry carries `data_type` (`sourced`/`inferred`/`synthesized`) and `citeable`; a non-citeable entry is explicitly tagged "`NOT CITEABLE AS FACT — reference only to inform your own inferred/synthesized reasoning, never assert as a sourced number`" — the model is meant to produce theorized values from these, not forbidden to.
5. Confirmed (hypothesis-test path specifically) this is a genuine two-turn sequence: Priya's own `hyp-hypothesis-test-intent` turn writes `supports`/`complicates`/`consider` first; the second, separate display-agent turn receives that already-written narrative as `task_context` and extracts `key_data_points` from it — so a per-point "which section this came from" attribution is reliable, not a guess.
6. Confirmed `EvidenceColumn` (Column 2) only ever renders hypothesis-test results (`st = hypFlow.hypothesisTest`) — Q&A never appears there. Confirmed (post-`MI-65`) the chat bubble's `hypothesis_test` case no longer renders `key_data_points` at all (only `supports`/`complicates`/`consider` + the resolution stamp) — so `key_data_points` now renders in exactly two places: the Q&A chat bubble, and `EvidenceColumn`.

**John's design decisions this session:**
- Split the one ambiguous list into two titled tables per message, grouped by origin: **"Actual Data Points from the Library"** (`sourced`, or `synthesized`+`is_baseline`) and **"Theorized Data Points from Analysis"** (`inferred`, or `synthesized` non-baseline) — reusing the exact `sourced`/`inferred`/`synthesized`/`is_baseline` vocabulary already locked in `STYLE-GUIDE.md` §19, no new taxonomy.
- Real columnar layout (an actual `<table>`, not the current inline flex row) — Title and Amount adjacent so the Amount column scans top-to-bottom at a glance.
- Actual table columns: Title, Amount, Data source, Type (Sourced/Source Simulation badge, `describeDataType()`'s existing colors).
- Theorized table columns: Title, Amount, Reasoned from, Section (`supports`/`complicates`/`consider`) — the Section column only exists where the data has it (`intelligence-review-format`; `qa-answer-format` has no sections concept at all, so a Q&A card's Theorized table naturally renders 3 columns, not 4 — driven by data presence, not a capability check).
- The old bespoke per-point `confidence: high/medium/low` field is dropped — `data_type`/`is_baseline` already carries a more precise, consistent reliability signal using the app's real taxonomy; keeping both would reintroduce the two-vocabulary problem this session found.

**Duplicate-functionality check:** `describeDataType()` (existing, `STYLE-GUIDE.md` §19) is reused verbatim for the Type badge — no new label/color mapping introduced. `groupDataSources()` (existing) is the direct precedent this session's new `groupKeyDataPoints()` mirrors (bucket rows by one `describeDataType()` call each, Category M — one mapping, one call site per row).

**Layer check:** the new `data_type`/`is_baseline`/`reasoned_from_section` fields are model-reasoned output on each display agent's own Skill Profile schema (Supabase content only) — Layer 2 (`MarketIntelligenceScreen.jsx`) only groups an already-labeled flat array into two tables; it never inspects `capability_slug` or hardcodes which capability is "theorized," matching `§19g`'s established dispatch-by-data-field pattern (the same shape as `ChartRenderer`/`CHART_RENDERERS`).

**Cross-reference integrity confirmed:** `STYLE-GUIDE.md` §19's locked table and `describeDataType()`'s switch statement agree on all 5 raw values; this session adds no new value to either, only a new caller.

// FEATURE: MI-63 -- buckets a flat key_data_points array into Actual (Sourced/Source Simulation)
// vs Theorized (Analysis) groups, reusing describeDataType() (STYLE-GUIDE.md §19) -- no new
// taxonomy. Mirrors groupDataSources()'s existing bucket-by-describeDataType() pattern exactly
// (Category M -- one mapping, one call site per row).
function groupKeyDataPoints(points) {
  const actual = [];
  const theorized = [];
  for (const p of (points || [])) {
    const display = describeDataType(p.data_type, { isBaseline: p.is_baseline });
    const decorated = { ...p, _display: display };
    (display.label === "Sourced" || display.label === "Source Simulation" ? actual : theorized).push(decorated);
  }
  return { actual, theorized };
}

function describeDataType(dataType, { isBaseline, source } = {}) {
  const whoTag = source === 'user' ? "Human" : source === 'agent' ? "AI" : null;
