## 2. CONTEXT

**Why (John's yes, 2026-09-02):** DeepBench's claim is expertise — the right Agent, grounded in the Library, using its Skills — and nothing measures whether that happened on a real run. The verifier lane grades code; nothing grades answers. The Report Card is one judging Capability that reads a finished run's logged hops and the Library content it used and scores, per Agent: **delegation fit** (did the Intent go to an Agent whose Skills cover it), **groundedness** (is each claim traceable to retrieved Library content), **Skill use** (were the Agent's own assembled Skills used). Scores are rows; a low score names the Skill row to improve. Standard technique: rubric-based LLM-as-judge with an explicit *Unknown* out (Anthropic, 2026-01-09).

**Measured before this kickoff:** `api/` holds **12 functions**, the Vercel Hobby cap — so the judge is a capability through the existing generic executor, never a new route (also §19b). `durable_hops` has **zero rows** for a fast CHI run (checkpoint-only), so the judge's inputs are the `ai_activity_log` rows of the trace: agent-turn rows carry `capability_slug`, `assembled_skill_slugs`, `traits`; the `librarian` rows (agent `eleanor`) carry `retrieved_chunk_ids` + `retrieval_method`; the format row carries `self_reported_claims`. The answer text itself is not logged — the client has it and hands it in. `quality-gate` (Owen Marsh — The Proofreader) is the existing pre-display reviewer, `ai`, held by `owen`; its shape (identity + behavior + intent skill profiles, Haiku) is the template. **Duplicate check:** `quality-gate` judges an answer *before* display against guardrails; the Report Card grades a *finished* run per Agent across runs — different question, different table, same holder.

**Librarian gate (Rule #1 / §19c):** the judge never reads `the_library` directly. Chunk texts for the groundedness check come through Eleanor Voss — The Librarian: the judge's task_context carries the run's `retrieved_chunk_ids`; the executor's existing knowledge path (`api/_lib/handlers/library-lookup.js`) fetches by id **only if that handler already supports an id list** — read it first; if it does not, this part adds one deterministic intent on `data-room-custody` (`library-cite-lookup-intent`, handler `library-lookup.js` extended by an `ids` param) and the judge's intent delegates to it via the normal `request_help` path. Either way the read runs under Eleanor's capability, never under Owen's.
