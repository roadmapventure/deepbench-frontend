## 1. SESSION

**S-ARCH-LOOP-PATCH-02** — one-file surgical bug fix in `api/prompt/request-receivable.js`. Fixes a structural gap found live during `S-ARCH-AGENT-LOOP-02`'s coding session: `parseModelTurn()` has no way for the model to end a turn with plain text whenever `canRequestHelp` is true but the capability has no schema tool. Priya's `hyp-stress-test-intent` (`can_request_help: true`, no schema) was the first real profile to combine both — it looped to `MAX_LOOP_DEPTH` (5 hops) with no error and no content, because every turn was structurally forced to be a tool call.

---

## 2. CONTEXT

`buildCallBody()` already sets `tool_choice: { type: 'auto', ... }` whenever `harnessTools.length > 0` — regardless of whether a schema tool also exists (`request-receivable.js` line 68). Anthropic's `'auto'` tool_choice means the model is genuinely allowed to respond with plain text instead of calling a tool. The request side of the mechanism is correct.

The bug is entirely on the parsing side. `parseModelTurn(responseData, tools)` branches on `tools.length > 0`:
```js
if (tools.length > 0) {
  const toolUseBlock = responseData.content?.find(b => b.type === 'tool_use');
  if (!toolUseBlock) throw new Error('No tool_use block in response');
  ...
}
```
This is correct when a schema tool exists and `tool_choice` is forced to `{ type: 'tool', name: schemaTool.name }` — a tool_use block is mandatory there, by construction. But when `canRequestHelp` is true and there's **no** schema tool, `tools` still has length > 0 (the two harness tools), so this same branch fires — except `tool_choice` was `'auto'` for this case, meaning a legitimate text-only final answer gets treated as a parse failure. In practice the model didn't even hit that throw — it kept calling harness tools every turn (the only structurally "complete" action available to it) until `execute.js`'s `hopCounter` hit `MAX_LOOP_DEPTH` and returned `{ status: 'depth_exceeded' }` — no error, no content, exactly what was observed.

This is not a new architectural decision — `ARCHITECTURE.md` §19d never required every `can_request_help` capability to also carry a schema (schema-less Intent Skill Profiles are already legitimate per §13 rule 14, format-skill exclusivity). It's an implementation gap: the parser's branching didn't account for the combination `canRequestHelp: true` + no schema. **No `ARCHITECTURE.md` change needed** — the design already allowed this, the code just didn't implement it.

File: `api/prompt/request-receivable.js`

Replace the current `parseModelTurn` function (lines 73–90):
```js

// data-driven match against a delegates array anymore -- that array no longer exists.
function parseModelTurn(responseData, tools) {
  if (tools.length > 0) {
    const toolUseBlock = responseData.content?.find(b => b.type === 'tool_use');
    if (!toolUseBlock) throw new Error('No tool_use block in response');
    const isHarnessTool = toolUseBlock.name === 'request_help' || toolUseBlock.name === 'delegate_to_agent';

```

```js
// FEATURE: AA-97 -- accepts a plain-text final turn whenever no schema tool was offered
// (hasSchemaTool=false). tool_choice is 'auto' in that regime (harnessTools present, no
// schemaTool) -- the model is always allowed to finish with text instead of a tool call, but
// the old branch (keyed on tools.length > 0) required a tool_use block whenever ANY tools were
// offered, making it structurally impossible for a can_request_help capability with no schema
// (e.g. hyp-stress-test-intent) to ever end its own loop turn -- it could only call
// request_help/delegate_to_agent, looping to depth_exceeded. Root-caused live in
// S-ARCH-AGENT-LOOP-02 (Priya's hyp-stress-test-intent, first real profile to combine
// can_request_help with no schema). No ARCHITECTURE.md change -- §19d never required a schema
// alongside can_request_help, this is a parser gap, not a design change. ARCHITECTURE.md §19d.
export function parseModelTurn(responseData, hasSchemaTool) {
  const toolUseBlock = responseData.content?.find(b => b.type === 'tool_use');
  if (toolUseBlock) {
    const isHarnessTool = toolUseBlock.name === 'request_help' || toolUseBlock.name === 'delegate_to_agent';
    return {
      is_delegate_call: isHarnessTool,
      tool_name: toolUseBlock.name,
      tool_use_id: toolUseBlock.id,
      tool_input: toolUseBlock.input,
    };
  }
  if (hasSchemaTool) throw new Error('No tool_use block in response');
  const textBlock = responseData.content?.find(b => b.type === 'text');
  if (!textBlock) throw new Error('No text block in response');
  return { is_delegate_call: false, tool_name: null, tool_use_id: null, tool_input: textBlock.text };
}
```
