## 1. CONTEXT

Live-reproduced 2026-07-08 (John's report + design-session verification via `claude-in-chrome` against the real dev URL, cross-checked against `ai_activity_log`/`durable_hops` in Supabase): asking Marcus a Q&A question produced a final answer that was narration about a delegation ("Done. Alex has formatted your answer...") instead of Alex's real formatted content, flagged `NEEDS REVIEW`, with Michelle and Alex both absent from the Agent Routing panel.

This is **not** a recurrence of `AA-142`'s original bug (Marcus narrating *instead of* delegating at all — `traits.delegation_required: true` is confirmed correctly set on `ci-answer-display-intent` in Supabase, and `AA-142`'s retry-once-then-throw guard is present and otherwise correct in `execute.js`). Backend telemetry from the live reproduction proves real delegation occurred: Michelle really ran `agent-selection-intent` and picked Alex, and Alex really ran `screen-controls:qa-answer-format` and generated real output (~8s of real model work, `ai_activity_log` id `3020`). The leak happens **after** that real delegation:

**Root cause, two compounding gaps, both confirmed against live code and live data:**

1. **`is_final` is left as model judgment when there is no legitimate `false` case.** `ci-answer-display-intent`'s live `skill_profiles.method` text tells Marcus: *"Set is_final true if you are confident nothing further is required of you once formatting completes; set it false if you would need to review or act on what comes back before your own task is actually done."* But the same method text also says *"A Format Skill only restructures presentation -- it never changes the facts, citations, or review status you hand it"* — meaning there is never a legitimate reason for Marcus to need another turn after a Display agent responds. (`hyp-hypothesis-test-display-intent` has the identical pattern — same fix applies to both, same one `delegationRequired` code path.) When Marcus's `delegate_to_agent` call omits `is_final:true`, `execute.js`'s existing `if (turn.tool_input.is_final === true)` branch (line 441) is skipped, control returns to Marcus for a superfluous wrap-up turn, and — with nothing substantive left to add — that turn produces narration. Because the delegation never reached the `is_final` branch, `buildFinalDelegationResult()` never ran, so `display.selection`/`display.display_agent_id` never get populated — this is why Michelle and Alex are invisible in the Agent Routing panel (`MarketIntelligenceScreen.jsx`'s `onEvent()` calls for `agent_selection`/`display_format`'s secondary agent chip both depend on those fields). Not a separate logging bug — a downstream symptom of the same gap.

2. **The wrap-up narration should still have been caught by `AA-142`'s guard, but wasn't — because `resumeCapability()` silently drops `delegationRequired` on any request that checkpoints mid-flight.** `execute.js` line 595 (`resumeCapability()`) hardcodes `delegationRequired: false`, with an existing comment from `AA-142`'s own session: *"durable_hops does not persist delegationRequired... A resumed chain's post-checkpoint hop runs without this guard -- pre-existing behavior, not a regression; real need to persist it can be its own future session."* That deferred gap is exactly what fired here: the live reproduction's `durable_hops` table shows a `channel-intelligence`/`ci-answer-display-intent` row (id `34bdfc18-...`) that reached `status: complete`, proving this exact request checkpointed and resumed via `resumeCapability()` mid-flight (its own multi-hop latency exceeded `HOP_BUDGET_RESERVE_MS`, per `AA-139`'s hybrid budget check). Once resumed, `delegationRequired` was silently `false` for the rest of the request — so when Marcus's post-delegation wrap-up turn produced plain text, `AA-142`'s guard (`if (delegationRequired && !delegationRetried) {...}`) was completely inert and the narration sailed through to `sendRequest()` as an ordinary valid final answer, no retry, no throw.

Gap 1 alone is fully sufficient to explain the reported leak. Gap 2 is a distinct, already-documented "accepted gap" that this live reproduction proves is not hypothetical — it silently disabled the platform's own narration guard in production. Both are fixed this session: fixing only Gap 1 would close today's specific leak but leave the guard blind for any future `delegation_required` intent that happens to checkpoint mid-request; fixing only Gap 2 would still leave a real, currently-exposed narration path open every time a well-formed delegation completes without `is_final:true`.

Same continuity/information-transfer bug family as `AA-126`/`AA-135`/`AA-141`/`AA-142`/`AA-144`/`AA-145`/`AA-147`.

Resolved: this is not a new judgment being taken away from the model — `delegation_required` is itself already an established harness-level structural trait (`AA-142`), defined as "this capability's entire job is handing off, never answering directly." A hand-off that is, by definition, the capability's entire job cannot legitimately be followed by more of that same capability's own work — so "is this delegation final" is not a live judgment call for these intents, it's a fixed consequence of `delegation_required` already being true. The live evidence in this doc (both intents' method text stating a Format Skill never changes what it's handed) confirms there is no real branch here to preserve. `is_final` remains genuine model judgment for every other capability that doesn't declare `delegation_required` (Owen's retry, Priya's Escalate) — unaffected by this change.

This session adds a short note to §19d recording the new rule (see Section 11 close-out below), it does not amend a LOCKED decision.
