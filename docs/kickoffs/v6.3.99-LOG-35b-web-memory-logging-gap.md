## 2. CONTEXT

Found live 2026-07-21 during `LOG-35`'s own scoping conversation — John asked "are we telling the model what to use, or is the response telling us?", which led to actually tracing the call chain instead of just fixing the string in place. Two independent, real bugs, not one:

**Bug 1 — the real AI call is never logged.** `api/web-memory.js`'s POST handler (triggered by Brent's fetch agent after a run completes) makes a real Anthropic call to generate a learning note (`api/web-memory.js:132-144`), already using the correct canonical model. It has **zero `logActivity()` call anywhere around it** — confirmed via `scripts/check-ai-logging-coverage.js`, freshly run this session (not assumed from a prior run): `api/web-memory.js: 2 real external call marker(s) but only 1 logActivity() call(s)`. The 1 existing call (line ~239) covers a separate embedding operation later in the same file; the Claude summarization call has no coverage at all.

**Bug 2 — a different file logs a call that isn't happening.** `src/contexts/FetchContext.jsx:152` fires `logAICall({type:"summarization", model:"claude-haiku-4-5", ...})` in the browser, timed to fire immediately before a `PATCH /api/web-memory` request (`FetchContext.jsx:153`) that only updates `steps_taken`/`total_time_seconds` — **no AI call happens in the PATCH handler at all** (confirmed by reading `api/web-memory.js`'s PATCH branch, `~line 261` on). The client-side log call is asserting that a summarization is happening at this moment; it isn't — the real one already happened earlier, server-side, via the POST Brent's agent triggers independently (traced: no client-side caller of that POST exists anywhere in `src/`, meaning it's invoked by Brent's own fetch-agent process, not this React code — consistent with `LOO-008`'s existing note that Brent's agent runtime is separate from this harness). The client call is also using the stale short-form model string `LOG-35`'s own row already flagged.

**The fix treats these as one coordinated change, not two patches:** delete the misplaced client-side log (it records nothing real), and add the real log where the real call actually happens — using the model value the Anthropic **response** itself reports (`claudeData.model`), not a re-typed literal or even `MODELS.HAIKU`. This is the most robust option available: the response is authoritative about what was actually used, so logging it directly makes this specific call site immune to ever drifting again, by construction, regardless of what the request side does in the future. (The request side still needs `MODELS.HAIKU` from `LOG-35a` to know what to *ask* for — this doesn't replace that, it's the logging half specifically.)

**Not fixed this session, flagged as a future cleanup, not a new backlog ID (John's standing call):** `api/prompt/request-receivable.js`'s existing `guardrailsModel`-based `logActivity()` call (found live while researching this) logs the request-side variable instead of the response's own `model` field, same pattern as this bug's root cause — but that call site is already correct today (no drift currently present), so changing it isn't fixing a bug, just hardening against a future one. Touching a third, working, unrelated file this session isn't warranted.
