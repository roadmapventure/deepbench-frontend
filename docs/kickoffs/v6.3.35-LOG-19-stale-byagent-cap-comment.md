## 1. CONTEXT

Found 2026-07-16 during a design session auditing consistency between the global AI Audit screen and the MI screen's Agents panel (`S-AUDITLOG-design`). The comment block directly above `useAgentActivitySummary()` in `useAgents.js` (~line 82) still says:

> "Also distinct from `useAIActivity()`'s `byAgent` (`src/hooks/useAIActivity.js`): that aggregation is backed by an in-memory log capped at 500 rows (`hydrateFromSupabase()`'s `.limit(500)`) — a rolling window, not full history, so an occasionally-used agent could scroll out of it and be wrongly reported as unused."

This was true when written but is no longer accurate: `AI-184` (already shipped) rewrote `hydrateFromSupabase()` to page through the **entire** `ai_activity_log` table via a `.range()` loop (`PAGE_SIZE = 1000`), with no `.limit(500)` anywhere in the current code. `useAIActivity()`'s `byAgent` reflects full history now, same as this hook. Verified live this session: `hydrateFromSupabase()` (`useAIActivity.js` lines ~389-431) has no `.limit()` call at all — the 500-row cap only ever applied to the *legacy client-side* `_log` array's push-time cap (`logAICall()`'s `.slice(0, 500)`, a different code path entirely, unrelated to what `hydrateFromSupabase()` loads on mount).

This is cosmetic — no code reads the stale claim, nothing behaves incorrectly — but it's exactly the kind of locked-comment drift that misleads whoever reads this file next, especially since this hook's own docstring is the one place a future session would look to understand why two separate agent-activity hooks exist side by side. The comment's *other* claim (this hook queries Supabase independently, regardless of whether `useAIActivity()`'s module-level store has been hydrated) is still true and worth keeping — that's a real, still-valid reason these are two different hooks, just not because of a row cap anymore.
