## CONTEXT

Found live 2026-07-21, John's own screenshot: a Jordan → Michelle → Brent chain shows only 2 hops — Brent and Michelle. Jordan, the actual requester whose real work started the whole chain, is **completely absent** — not misordered (`LOO-014`'s bug), not blank content (`LOO-012`'s bug), genuinely erased with zero trace anywhere in the drawer.

**Root cause, precise — the same erasure mechanism as the original Owen/Marcus bug this whole track exists to fix, on a branch that never got the equivalent of `LOO-011`'s fix:** in `dispatchDelegation()`'s `request_help` branch, the very first event fired is `onEvent({type:'delegation', fromAgentId: agent_id, toAgentId: pmAgentId, ...})` — Jordan's own row, created at the earliest possible array position. Once Michelle's own broker-leg credit (`LOO-009d`) fires, it claims that exact row and overwrites it entirely (`{...evt, id: pending.id}` replaces every field, including `agentId`) — correct behavior for resolving Jordan's *announcement*, but it means Jordan's own identity never survives anywhere else in the array. Unlike the plain `delegate_to_agent` branch (`LOO-011`'s fix), nothing here ever fires a second, independent credit for the requester — and `callCapability()`'s automatic Shape-1 detection (`LOO-010`) never fires either, because this branch always resolves via a delegation (`finalResult.display_agent_id` always ends up set for a `delegationRequired` capability), which is exactly the condition that Shape-1 detection uses to stay silent.

**Why `LOO-011` didn't already cover this:** it was deliberately scoped to the plain `delegate_to_agent`+final branch only, reasoning at the time that a `delegationRequired` capability's requester "does no real work of its own by definition." That reasoning holds for capabilities where the requester is purely a router (e.g. Marcus's `ci-answer-display-intent`, which never does anything before calling `request_help`) — it does **not** hold for a capability like `web-search-news`, where the requester's whole job is to do real work (search) and *then* ask for formatting help. The requester's real turn happening before the hand-off — not which tool it uses to hand off — is what actually determines whether it deserves its own credit. `LOO-011` conflated "which branch" with "did real work happen," which was the wrong proxy.

**The fix — same pattern as `LOO-011`/`LOO-014`, applied to the other branch, positioned correctly the first time (learning `LOO-014`'s lesson directly):** fire the requester's own credit *before* the branch's first `delegation` announcement, gated on `delegationRequired` (already known at function entry, no dependency on any nested call). This mirrors `LOO-014`'s exact ordering fix — the requester's row must be created at the true earliest array position, not after the broker's placeholder already claimed it.

**Confirmed no double-credit risk:** gating on `delegationRequired` means this only fires for capabilities whose Shape-1 auto-detection (`LOO-010`) will never otherwise fire for this requester — the ordinary (non-`delegationRequired`) `request_help` case (e.g. Owen asking Michelle for escalation advice) is completely untouched, still credited exactly as before via `LOO-010`'s existing mechanism once that call resolves directly.
