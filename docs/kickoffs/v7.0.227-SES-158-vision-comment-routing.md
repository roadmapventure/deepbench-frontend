## What the schema already decides (read live, not designed here)

`public.briefing_comments`: `target_kind ∈ (ticket, question, vision, invention)`,
`author ∈ (john, runner)`, `kind ∈ (question, answer, requirement, routing, note)` defaulting to
`question`, plus `harvested_cycle` and `routed_to`. `public.vision_claims`:
`claim_ref ~ '^VC-[A-Z0-9]+-[0-9]{3}$'`, `status ∈ (proposed, ratified, rejected, rewritten)`,
`confidence ∈ (low, medium, high)`, `judgment_class` constrained to the four P1–P4 strings,
`ck_vision_claim_decided` requiring `provenance` on anything past `proposed`.

The rule is therefore written **against real columns**, not against a hypothetical shape — which is
the difference between this and a rule that has to be rewritten the first time it fires.

## The design call, stated because an editor will collapse it

Decision 5 contains two sentences that look like one:

> "The runner routes a vision comment into corpus update / research ticket / feature ticket, and
> **reports the routing back on the card**"

> "**Every interaction must leave the corpus richer:** the harvest writes what the thread taught
> back into the claims table, never just a status flip."

Read as one rule, `corpus-update` is merely one of three routes — and then a comment routed to
`feature-ticket` leaves the corpus **no richer**, which contradicts the second sentence outright.
So they are two obligations, and the rule says so:

- **The route** names the artifact the comment BECAME. Exactly one of three, never zero, never two.
- **The corpus write is unconditional** and runs on every route, including `feature-ticket`.

`corpus-update` as a *route* therefore means "the artifact is the claim itself" — not "this is the
one path where the corpus gets written."
