## 2. CONTEXT

After `S-CHI-26b`'s Rules-of-Hooks patch shipped, the design session re-verified live against the real deployed dev preview: asked a real question (Vietnam reseller network), got a full analysis answer with a headline, several prose sections, and a 6-row data table — genuinely long enough to overflow Column 2's scroll box. **No crash this time** (`CHI-26b`'s fix confirmed working) — but the bottom-edge fade+chevron affordance (`CHI-29`'s whole point) never appeared, even though direct DOM measurement confirmed real, substantial overflow (`scrollHeight: 865`, `clientHeight: 377` — 488px of hidden content).

**Root cause:** `useScrollFadeHint(scrollRef, deps)` only recomputes `canScrollMore` in two situations — once inside a `useEffect` keyed to `deps`, and again whenever the scrolling element's own `onScroll` fires. For the mobile Agent Routing feed (the hook's original, working call site), `deps` is `[ordered.length]` — a value that changes repeatedly throughout a live conversation as new hops arrive, so the effect re-fires many times, giving the check many chances to land on the real, settled content height. For Column 2's new call site, `deps` is `[qaEvidence, hypFlow]` — object references that are set **once**, atomically, the instant a full answer arrives. The effect fires exactly once for that answer. If the browser's layout isn't fully settled at that exact instant (a plausible cause here: this app loads custom `mono`/`body`/`display` webfonts via `@font-face`, and a font swap after the initial paint measureably changes text-wrapping height for a prose-and-table block like `QaEvidenceCard` — a well-known class of "measured too early" bug for this kind of scroll-affordance code), there's no second chance to recheck, since nothing about `qaEvidence`/`hypFlow` changes again afterward. **This is an architectural gap in the shared hook itself, not a mistake specific to how Column 2 calls it** — the hook's reliability was accidentally riding on how often the *caller's* dependency array happens to change, not on genuinely observing the scrolling content's real size. The mobile feed's own instance works today only because hop counts churn constantly; it would exhibit the identical bug on a single long-static hop, it just isn't exercised that way in practice.

**Live-reproduced, not theorized:** confirmed via direct DOM measurement (`scrollHeight`/`clientHeight`) that Column 2's box genuinely overflows; confirmed via a real user-driven scroll (`scrollTop` moved from 0 to 50, well after the page had been open for minutes with fonts fully loaded — `document.fonts.status: "loaded"` checked directly) that the fade still never appears, ruling out "just hasn't rechecked yet" as an ongoing transient state.

## 5. TASKS (1)

### Task 1 (`CHI-29` second patch) — Make `useScrollFadeHint` self-healing instead of purely `deps`-driven

In `src/components/SharedUI.jsx`, replace the current implementation:
```js
export function useScrollFadeHint(scrollRef, deps) {
  const [canScrollMore, setCanScrollMore] = useState(false);
  const check = () => {
    const el = scrollRef.current;
    if (!el) return;
    setCanScrollMore(el.scrollHeight - el.scrollTop - el.clientHeight > 4);
  };
  useEffect(() => { check(); }, deps);
  return { canScrollMore, onScroll: check };
}
```
with:
```js
// FEATURE: CHI-29 — second patch (S-CHI-26c): the original deps-only recheck was accidentally
// coupled to how often the CALLER's deps array changes, not to the scrolling content's real size.
// Works for the mobile Agent Routing feed (deps=[ordered.length] churns constantly as hops arrive)
// but silently never recovers for a single atomic content change (Column 2's deps=[qaEvidence,
// hypFlow], set once when an answer arrives) if the browser's layout isn't fully settled at that
// exact instant (e.g. a webfont swap reflowing prose/table text after first paint). Fixed by making
// the hook observe the scrolling element's actual content for changes, instead of trusting the
// caller's deps array alone: a MutationObserver on the scroll container (catches new/changed DOM
// content, e.g. QaEvidenceCard mounting) plus a document.fonts.ready hook (catches webfont-driven
// reflow specifically) both re-run the same check(). deps is kept only to re-attach the observer
// when the scrollRef's target element itself is swapped out (rare, but matches the original
// contract) -- it is no longer the only thing that can trigger a recheck.
export function useScrollFadeHint(scrollRef, deps) {
  const [canScrollMore, setCanScrollMore] = useState(false);
  const check = () => {
    const el = scrollRef.current;
    if (!el) return;
    setCanScrollMore(el.scrollHeight - el.scrollTop - el.clientHeight > 4);
  };
  useEffect(() => {
    const el = scrollRef.current;
    if (!el) return;
    check();
    const mo = new MutationObserver(check);
    mo.observe(el, { childList: true, subtree: true, characterData: true });
    document.fonts?.ready?.then(check);
    return () => mo.disconnect();
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, deps);
  return { canScrollMore, onScroll: check };
}
```
Do not change the hook's public signature/return shape (`{ canScrollMore, onScroll }`) or either call site (`MobileBody`'s routing feed, `EvidenceColumn`'s analysis box) — both already call it correctly; this patch only changes what happens inside the hook.
