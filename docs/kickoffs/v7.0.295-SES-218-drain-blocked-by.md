## 2. The decision John already made, and what it rules out

The filing cycle named three candidate shapes and chose none. Directive `07dea95e` chooses the
criterion in John's own words:

> *pick the one that keeps partial re-pickable when the remainder IS buildable (SES-51/SES-180 both
> shipped further halves from partial today) while excluding a partial whose declared remainder
> names an open blocking ticket.*

That is candidate **(a)** — a `blocked_by` reference — and it is the only one of the three that can
satisfy both halves at once:

- **(b) a `runner_skips` row with `reason_kind = 'blocked-by-ticket'`** reuses machinery that
  exists, but `runner_skips` feeds §10 *waiting on **your** input*, and this ask is not John's — the
  blocker is another ticket. `SES-127` forbids recording a skip he cannot action, and `SES-166` is
  written from exactly the failure of putting an Unblock button in front of him with nothing to
  unblock.
- **(c) let the chain gate refuse when its pick equals the cycle's own `item_id`** is the cheapest
  and fixes only the in-session chain: the next *scheduled* fire has a different `item_id` and takes
  the same wedged pick. It also cannot distinguish a buildable remainder from a blocked one at all,
  so it fails John's first half.

**The blanket one-liner is what this ticket exists to refuse.** Adding `AND b.status <> 'partial'`
to the pick predicate strands every partial whose remainder *is* buildable — `SES-51` and `SES-180`
both shipped further halves from `partial` on 2026-08-28 — so it fails John's first half outright.

**And what must not be done, named because it is the tempting shortcut** (the ticket names it too):
writing `design_status = 'needs-john'` or `'john-paced'` onto the blocked ticket to get it out of the
picker. Both put an ask on John's §10 that he cannot act on, and the runbook forbids a cycle
assigning `john-paced` at all.

## 3. The build

### 3a. Migration `ses218_blocked_by` (database, not this repo)

1. `backlog_items.blocked_by uuid REFERENCES public.backlog_items(id)` — NULL means not blocked.
   **Keyed on `id`, never `backlog_id`** (`SES-142` / `SES-86` phase 2: `backlog_id` carries no
   unique constraint and `CHI-48` occupies two rows, so a text key silently means both).
   `ck_backlog_items_blocked_by_not_self` rejects a self-reference. A column comment carries the
   contract so it travels with the schema.
2. `drain_epic_next()` **pick** predicate gains one clause:
   `AND NOT EXISTS (SELECT 1 FROM backlog_items bb WHERE bb.id = b.blocked_by AND bb.status NOT IN ('done','removed','delivered'))`
3. `blocked_detail` gains a blocked-by count and list, so the new population is never a silent empty
   (`SES-196`, John's own QA arm (b)).
4. **The RETIREMENT predicate is untouched.** `SES-154`/`SES-196` boundary: a drain every remaining
   member of which is blocked is `blocked`, never `retired` — putting the clause on the retirement
   side returns `open_now = 0` and closes John's standing directive on the runner's own say-so.

**Signature:** the argument list stays `(p_cycle_id uuid)` and the `RETURNS TABLE` is unchanged, so
`CREATE OR REPLACE` genuinely replaces rather than overloading. Asserted anyway at `count(*) = 1`
per `.claude/rules/supabase-function-signature.md`, because that rule's whole point is that the
success flag is not evidence.

**Grants:** surveyed before the ALTER rather than assumed — `backlog_items` carries **table-level**
grants to `postgres` and `service_role` only; `anon` and `authenticated` hold **zero** privileges of
any type. A table-level grant covers a new column automatically, so the fail-closed new-column
problem in `.claude/rules/supabase-column-grants.md` does not arise here and no grant statement is
owed. Asserted both directions after the ALTER regardless (`SES-101`).

### 3b. Two design calls, stated rather than left to be re-derived

**`delivered` UNBLOCKS a dependent, though it is not itself pickable.** John's own sentence in the
directive is the authority: *"After (1) ships, SES-191's remainder becomes buildable"* — **ships**,
not *is accepted*. The code is on `dev` the moment a cycle pushes it; John's Accept confers
completion, not availability. Treating `delivered` as still-blocking would reproduce this very stall
one ticket further along — `SES-191` would sit excluded behind a `SES-216` that had already landed.

**The asymmetry is deliberate and an editor will want to remove it.** `delivered` is excluded from
the **pick** (`SES-154` — a delivered ticket is not work) and counts as **unblocking** for a
dependent. Those answer two different questions: *"is there work here?"* and *"has the code I depend
on landed?"* Collapsing them to one set breaks one of the two.
*Bounded honestly:* if John **Reverses** a delivered blocker, its commits are reverted and its row
reopens — which re-blocks the dependent for every future pick, but cannot un-build work already
done in the gap. That window is real, it is the same window every ship already has between
`delivered` and Accept, and it is not widened by this clause.

**The clause is status-agnostic — it is NOT scoped to `partial`.** John's sentence says *"a partial
whose…"*, and the deviation is named rather than buried (the `SES-196` convention). The reason it is
not a widening: `blocked_by` is a **brand-new column, NULL on every one of the board's rows**, and
it is only ever written deliberately by a cycle that discovers a block. So partial-only and
status-agnostic are byte-identical on today's board and can differ only on a row some future cycle
explicitly marks — at which point making the column inert because the row happened to be `open`
rather than `partial` would give one column two meanings depending on a second column. `partial` is
the *symptom* John saw; `blocked_by` is the *fact*, and the fact is what the predicate reads.

**Nobody has to clear it.** The clause is a `NOT EXISTS` over the blocker's live status, so the
ticket is re-admitted the instant the blocker reaches `done`/`removed`/`delivered`, with no write
anyone must remember. Same shape as `record_skip()`'s row being cleared by the ticket going `done`
rather than by a cycle deciding it has waited long enough — and this runbook records eight times
over that a rule each cycle must remember is a rule that gets silently forgotten.

## 4. NOT DONE, deliberately, and said here rather than discovered later

**No row is backfilled — `SES-191.blocked_by` is left NULL.** `SES-216` is `delivered`, so under
this ship's own rule it no longer blocks; setting the column now would strand `SES-191` on a
dependency that has already landed, which is the exact error the ticket's *"WHAT MUST NOT BE DONE"*
paragraph warns about wearing a different hat. The mechanism ships with zero rows set, exactly as
`SES-158` shipped its routing rule before its inputs existed and for the same stated reason.

**Consequence, stated plainly:** this ship changes **no** pick on today's board. Its evidence is
fixture-based (§5), and that is the honest position rather than a live before/after this cycle
cannot manufacture without setting a row it has just argued must not be set.
