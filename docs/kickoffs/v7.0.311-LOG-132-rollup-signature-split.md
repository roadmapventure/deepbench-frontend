## Premise, revalidated live before building

Every number below was measured by this cycle against this database, not read off the ticket.

| | Measured `2026-08-29T14:5xZ` |
|---|---|
| `anon` `statement_timeout` | **3 s** (`pg_roles.rolconfig`; `authenticated` is 8 s) |
| `ai_pattern_classification_rollup`, warm | **2,871.986 ms** — 96% of the cap, one view, alone |
| of which the `sig` CTE's Seq Scan | **1,879.275 ms** over 34,840 rows |
| `ai_activity_log` rows | 34,840 (12,548 carry `span_id`, 5,337 a `parent_span_id`) |
| distinct signatures × active patterns | 2,372 × 14 = 33,208 `pattern_criteria_matches()` calls |

**The premise holds and the ticket's own re-measurement is confirmed rather than quoted.** Its
2026-08-11 line reads *"2,202 ms warm / 4,164 ms cold … no longer latent — at/over the line"*;
warm is now **2,872 ms**, so the gap has closed by a further ~670 ms while the ticket waited. A
single warm view is 128 ms under `anon`'s cap and the AI Audit mount issues a **concurrent pair**.

**Root cause, confirmed from the live definitions rather than the plan alone.**
`log_row_signature(l ai_activity_log)` is a `STABLE SQL` function whose `sub_calls_chained` and
`integration_followed` branches each contain an `EXISTS (SELECT 1 FROM public.ai_activity_log …)`
sublink. Postgres's `inline_function()` refuses a body containing subplans, so the `sig` CTE
(`SELECT l.id, l.cost_usd, log_row_signature(l.*) FROM ai_activity_log l`, read from
`pg_get_viewdef`) pays one opaque invocation per row and loses all hashed-SubPlan sharing.

## What ships

Fix direction **(a) and (b) together** — the ticket names them as alternatives to *"pick +
measure"*, and they compose: (b) precomputes the two span-derived facts once per query, which is
what makes (a)'s inlinable config-half expression legal to write in the view.

**One migration, `log132_rollup_signature_split`, two `CREATE OR REPLACE VIEW` statements:**

- **`parents`** CTE — `SELECT DISTINCT parent_span_id` where non-null (1,408 rows), `LEFT JOIN`ed
  on `span_id`. Exactly equivalent to the `EXISTS` it replaces: `c.parent_span_id = l.span_id`
  can never match a NULL on either side, and `DISTINCT` means the join cannot duplicate a row.
- **`base`** CTE — one `WindowAgg`:
  `coalesce(bool_or(flag) OVER (PARTITION BY span_id ORDER BY created_at DESC, id DESC ROWS
  BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING), false)`. In `DESC` order the preceding frame is
  precisely the set `(t.created_at, t.id) > (l.created_at, l.id)` the `EXISTS` scans for.
  **`id` is `integer` and the primary key**, so the ordering is total and the `ROWS` frame has no
  ties to mis-handle — that was checked, not assumed. `bool_or` over an empty frame is `NULL`,
  hence the `coalesce` to `false`, which is what the `EXISTS` returns.
- **`sig`** CTE — the config half of the signature written out verbatim, concatenation for
  concatenation, in the same left-associative order as the function body, with the two facts
  substituted in.

**`log_row_signature()` itself is not touched.** No signature change, so
`.claude/rules/supabase-function-signature.md`'s stale-overload trap cannot fire (asserted at
`count(*) = 1` anyway). **`ai_call_patterns`, the point-lookup view, keeps calling the whole
function** — it reads one row, where the per-row cost is ~150 ms and irrelevant, and leaving it
alone keeps a live caller of the function so the two forms cannot silently diverge unobserved.

### The edit this ship forbids

**Do not "simplify" by moving the two precomputed facts back inside `log_row_signature()`** — for
instance by rewriting the `EXISTS` clauses as lateral joins in the function body. The function is
called per row from `ai_call_patterns` with a single row in hand; a set-level precompute there
would scan the whole log to answer a point lookup, which is this defect inverted. The split is
between *a function that answers about one row* and *views that answer about all of them*, and
that is the boundary to keep.

**Do not fold the `matched` CTE's cost into this ticket.** After the fix the dominant node is the
`pattern_criteria_matches()` nested loop (~640 ms). That is real and it will need its own ticket
when the pattern count grows again — it is not `LOG-132`'s premise, and widening the ship to
chase it would put a second unmeasured change behind one equivalence gate.

## The equivalence gate, run before the views were replaced

Not a proxy for correctness — the thing itself, over the whole table:

```
rows_compared 34,840 · mismatches 0 · old_distinct 2,372 · new_distinct 2,372
```

The old form (`log_row_signature(l.*)`) and the new expression were computed side by side in one
query and compared with `IS DISTINCT FROM` on the full 34,840 rows. Zero disagreements, and the
distinct-signature count is unmoved — which is the number the `uniq`/`matched` CTEs key on, so
an identical count is what guarantees the rollup's grouping cannot shift.
