## 2. CONTEXT

Retiring a fact in The Library currently takes **two independent model-issued operations**: an `insert` carrying `supersedes_id`, then a separate `update_status` flipping the old row to `superseded`. Nothing binds them. Either half can land alone, and both directions have happened in production data:

- **Flip lands alone** → the fact disappears with no replacement. `59eede59` (Scenario — Signal Mobile) sat orphan-superseded; `match_the_library` filters `status='active'`, so it was an instant retrieval hole that broke case 8's designed comparison. Repaired 2026-07-29.
- **Insert lands alone** → both versions stay live and retrievable. **Five rows are in this state right now**, verified live this session:

| Old row (still `active`) | Title | `is_baseline` | Superseder |
|---|---|---|---|
| `94794176-6f65-40f7-958d-374b5f1023e9` | Scenario — Vitrine Tech (Brazil): Training Compliance Gap | true | `92131ed8` (itself `superseded` by `2e1c1f2c`) |
| `0d09ac6e-baca-4471-a3f5-c0a63007882d` | Smartphone Upgrade Cycles by Country (2009-2026) | true | `01a3a549` — **"DAT-7 End-to-End Live Test — Loop-Closure Confirmed"** |
| `1c7104c5-9bc1-4ee7-9b61-d6070dc5aba8` | Scenario — Nordholm Retail Group (EMEA): Co-op Budget Underutilization Q3 | true | `b88cf8cd` |
| `b88cf8cd-2502-4702-afe8-73eb4320f6ba` | Nordholm Retail Group — Utilization Gap: Process-Friction & Leakage Hypothesis | false | `629f2184` |
| `fe58cadd-b16b-46dd-a8d3-360bf1550c49` | Scenario — Elevate Mobility (India): Rapid Expansion | true | `85fa8d76` |

Four are baseline rows, not three — `DAT-11`'s prose says "three of the five" but its own list says four, and the live count is four. The list is right.

**Enforcement semantics — John's call, decided 2026-07-29: gate, don't hard-block.** An agent may retire an `is_baseline` row, but only through an operation that guarantees a replacement lands in the same transaction. A bare status change may no longer retire one.

Why not a hard block: `is_baseline` is the **Demo Reset marker** (§19f — `archive where is_baseline=false` / `restore where is_baseline=true`), not a permission flag, and §19c states *"Rows are never overwritten, only ever inserted — a correction always supersedes via a new row."* Blocking baseline supersession outright would contradict locked architecture and would turn every legitimate correction (e.g. the real Vitrine correction) into a permanent duplicate.

**This is a service change, not a harness guardrail.** `lib/librarian.js` is the registered platform service **Library Custodian** (`library-custodian`, layer `data-model`, `code_anchor: lib/librarian.js`, functions `search/write/catalog/record lookup`). The invariant is about one store's content model, so it belongs to the service that owns that store. None of the four harness files (`execute.js`, `db-assembly.js`, `ai-enrichment.js`, `request-receivable.js`) are touched, and the service's registry row needs no change — `write` is already a declared function and `supersede` is a verb under it.

## 5. TASKS (4)

### Task 1 — Postgres function `supersede_library_entry`

Apply via the Supabase MCP `apply_migration` (project `rallojeqnkgtxgsdsnqm`). There is no `supabase/` directory in this repo; migrations are not repo-tracked.

Verified schema facts you must honor: `the_library.embedding` is `vector(1536)` **nullable**; `id` defaults `gen_random_uuid()`; `created_at` defaults `now()`; `status` defaults `'active'`; `tenant_id` is **NOT NULL** default `'global'`; `title` and `content` are **NOT NULL**.

```sql
CREATE OR REPLACE FUNCTION supersede_library_entry(
  p_entry          jsonb,
  p_embedding      text,          -- pgvector text form, e.g. '[0.1,0.2,...]'
  p_target_id      uuid,
  p_data_room_tag  text
) RETURNS SETOF the_library
LANGUAGE plpgsql
AS $$
DECLARE
  v_status  text;
  v_new_id  uuid;
BEGIN
  SELECT status INTO v_status
    FROM the_library
   WHERE id = p_target_id AND data_room_tag = p_data_room_tag
   FOR UPDATE;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'supersede-target-not-in-data-room';
  END IF;

  IF v_status <> 'active' THEN
    RAISE EXCEPTION 'supersede-target-not-active';
  END IF;

  INSERT INTO the_library
  SELECT (jsonb_populate_record(
            NULL::the_library,
            (p_entry - 'embedding' - 'id' - 'created_at')
              || jsonb_build_object(
                   'id',             gen_random_uuid(),
                   'created_at',     now(),
                   'data_room_tag',  p_data_room_tag,
                   'supersedes_id',  p_target_id,
                   'status',         'active',
                   'is_baseline',    false)
          )).*
  RETURNING id INTO v_new_id;

  IF p_embedding IS NOT NULL THEN
    UPDATE the_library SET embedding = p_embedding::vector(1536) WHERE id = v_new_id;
  END IF;

  UPDATE the_library SET status = 'superseded' WHERE id = p_target_id;

  -- Postcondition: exactly one active row may claim to supersede this target.
  IF (SELECT count(*) FROM the_library
       WHERE supersedes_id = p_target_id AND status = 'active') <> 1 THEN
    RAISE EXCEPTION 'supersede-postcondition-failed';
  END IF;

  RETURN QUERY SELECT * FROM the_library WHERE id = v_new_id;
END;
$$;
```

Two things this shape depends on, both deliberate:

- **`p_embedding` is `text`, not `vector`.** PostgREST sends a JS array as a JSON array, which does not coerce to `vector`. Pass `JSON.stringify(embedding)` from JS — that produces exactly pgvector's text input format. Do not change this to a `vector` parameter without proving the RPC round-trip works.
- **`jsonb_populate_record` sets every absent column to NULL, overriding column defaults.** The caller must therefore pass a *complete* record. `writeTheLibraryEntry()` already builds one (it applies `citeable`/`is_baseline`/`data_type` defaults in JS). Reuse that payload-building path — do not hand-assemble a partial object.
