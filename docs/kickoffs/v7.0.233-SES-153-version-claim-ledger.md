## The decision, and the two candidates it rejects

The ticket lists three shapes and chooses none. A Fable 5 subagent was given the live facts and
returned a verdict; this is that verdict with one divergence, recorded below.

**Chosen: a ledger of ISSUED numbers, fed by a trigger on the counter.**

- **Candidate (2), "assert CLAUDE-STATE.md's version line beats `origin/dev`'s", is dead on
  arrival.** That line is now generated from `runner_cycles.version`, which is one ship behind by
  design, inconsistently spelled, and **has no row at all for an attended session** — the exact
  population that caused this bug. It would misfire on the lag and miss the real case.
- **Candidate (3) as a literal read-back is weak** for the reason `session-setup.md` §3b already
  states: reading is never a reservation. In the actual incident a close-out read-back would have
  returned `196` — the very number that was hand-counted — and passed.
- **Candidate (1) is right, but "written at close-out" is not.** A ledger written by each session at
  close-out records only the sessions that follow the procedure, and the sessions that cause this
  defect are **by definition** the ones that do not. So issuance is recorded by the **claim itself**:
  an `AFTER UPDATE` trigger on `dev_version_counter`. No protocol change, no step to remember —
  the `SES-86` phase 3 / `SES-101` / `SES-111` / `SES-128` / `SES-129` correction, once more.
  *(This is the one place the subagent's verdict was not taken: it proposed rewriting the §3 claim
  SQL as a CTE. A CTE only ledgers callers of the new SQL; the trigger ledgers every caller of the
  counter.)*

**The cheaper check that must never replace this.** *"Is my version ≤ the counter?"* passes **both**
colliding ships: `v7.0.195` and `v7.0.196` were both ≤ the counter's 196. Only a ledger answers
*issued to **whom***.

## What shipped

1. **Migration `ses153_issued_versions`** (+ `ses153_issued_versions_numeric_unique`) — lives in the
   database, not this repo. `public.issued_versions` (`version` PK, `major/minor/patch`,
   `issued_to text NOT NULL`, `issued_at`), the trigger `trg_dev_version_counter_issue`, and
   `uq_issued_versions_numeric UNIQUE (major, minor, patch)`.
   - **No FK to `runner_cycles`, deliberately.** The adjacent `runner_before_images` wears that FK
     and `SES-150` records what it costs: attended sessions cannot satisfy it. An FK here would
     exclude the only population that has actually caused this bug.
   - **The numeric UNIQUE is not decoration.** A text key cannot see `v7.0.233` colliding with
     `v07.0.233`, and both spellings of a version already occur live in `runner_cycles.version`.
   - Public roles hold nothing on the table; the checker reads with the service key.
2. **`scripts/check-version-claim.js`** — the gate. Asserts the version is in the ledger **and
   issued to this session**; `--audit` sweeps `runner_cycles.version` against the ledger. Exit 0 /
   1 / 2 with this repo's existing meaning (2 = could not run, never a pass).
3. **`docs/runbooks/runner-cycle.md` step 7** — the pre-push bullet that makes a cycle run it,
   carrying the rejected-cheaper-check reasoning so it cannot be "simplified" back.
4. **`tests/regression/SES-153-version-claim.js`** — reads the rule out of the runbook, never
   restates it; every doc clause paired with a negative control, every control itself checked for
   being vacuous.

**Not backfilled, and said so.** The counter forgets, so the ledger starts at `v7.0.233`
(seeded from the counter's own row, before-image first). A version below that floor is reported
**not assertable** — neither flagged nor waved through.
