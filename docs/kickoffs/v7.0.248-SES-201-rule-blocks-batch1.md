## 6. DESIGN RULES

**The one that decided the shape of this ship — and the edit a later cycle will be tempted to make.** Check 12 exempts a rule-id occurrence when the **enclosing paragraph** contains the marker. So dropping a marker *beside* a surviving hand-copy turns the check green and removes **no drift at all**: the copy still cannot move when the registry row does, and now nothing reports it. Migrating means the old sentence **leaves**, not that a marker arrives near it. This is the whole reason the guard pairs an absence assertion with a presence assertion at each site.

**Why B12's site is the one to read twice.** Its restatement lives in a numbered procedure a cycle executes mid-run, so the words could not simply be deleted. What moved instead was the bare `(B12)` citation: the rendered block now heads step 4b and the list item points at it. Deleting a rule id purely to silence a checker *would* be gaming — so it is worth being explicit that the id did not leave the document. It left an uncheckable parenthesis and arrived in a checked block seven lines above, which is more traceability than before, not less.

**A fallback is a signal, never a formatting problem.** Same family as the ticket-title rule at the head of the runbook: where the registry statement is terser than the prose it replaces, the operative detail is kept beside the block as prose. It is never smuggled *into* the rendered line, which `render-rule-blocks.js --write` would silently revert on the next run.
