The pinned family query (run fresh, embed fresh numbers in the candidates):

```sql
with w as materialized (
  select l.id, log_row_signature(l.*) as sig from ai_activity_log l
  where l.model is not null and l.ai_type='agent-turn'
),
u as materialized (
  select * from w where not exists (select 1 from pattern_vocabulary pv
    where pv.criteria is not null and pv.superseded_by is null
      and pattern_criteria_matches(w.sig, pv.criteria)))
select sig->>'intent' as intent, count(*) as calls, min(id) as sample_row, max(id) as latest_row
from u
where sig#>>'{traits,schema}' = 'true'
  and sig->'tool_calls' @> to_jsonb(array[sig->>'intent'])
group by 1 order by calls desc;
```

**Why one candidate per intent, not grouped:** grouping shapes into fewer candidates would be this session doing the pattern judgment — semantics are Susan's (§19i: "semantics happen once, when the Pattern Definer defines the pattern"). The `merge` decision exists exactly so SHE can collapse siblings; `buildReviewContext()` hands her every other pending candidate, so while reviewing shape #1 she sees the other 16 as context. That visibility is intended — this batch is a family presented together, the same way the original 2026-07-22 seeding filed 24 candidates for her to rule on (she merged 4).
