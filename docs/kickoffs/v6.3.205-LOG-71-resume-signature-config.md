## 2. CONTEXT — the defect, measured

Owen Okafor — Quality Gate Reviewer runs a multi-hop review chain. The 60s serverless budget runs out mid-chain, the chain checkpoints to `durable_hops`, and a later invocation resumes it. On the Agent Routing drawer the first hops carry a pattern line; every hop after the resume is blank. Same agent, same conversation, same work — suddenly unclassifiable.

**Root cause, read fresh from source this session.** `LOG-67` (✅ done, v6.3.142) threads the §19k config-half snapshot into `logAgentTurn()` through a `runLoop()` parameter. Exactly one caller supplies it — `runCapability()` at `execute.js:1184`, reading `promptRequest.signature_config`. `resumeCapability()` re-enters `runLoop()` at **three** sites — `execute.js:1289`, `execute.js:1326`, `execute.js:1343` — and **none** passes `signatureConfig`. It defaults `null`, `mergeCallFacts()` writes the fact-half alone, and the row can never match a config-half criterion.

> Correction to the `LOG-71` row and to `BETA.md` §3 bucket 5 item 1, which both say *"both resume re-entries"*: there are **three**. All three need the fix.

**Verified in Supabase this session** (`durable_hops`, 29 columns listed): there is **no `signature_config` column**. `resumeCapability()` rebuilds its whole world from that row, so the value is simply not available to it.

**Measured, live** — `ai_type='agent-turn'` rows created on/after 2026-07-26 (fully after `LOG-67` deployed):

| | |
|---|---|
| agent-turn rows written | **1,979** |
| carrying fact-half but **no** config-half | **221 (11.2%)** |
| of those, whose `span_id` matches a `durable_hops` row (= a resumed continuation) | **214 — 97%** |
| unexplained residue | **7** |

Control that rules out coincidence: among the *healthy* config-bearing rows, only **17%** span-match a `durable_hops` row, versus **97%** of the broken ones.

**`LOG-103` is confirmed the same defect** observed from the row side (verified by code read + the span join above). Merge it into `LOG-71` — no separate work.

**Decision, John, 2026-07-28: persist the frozen original; do not recompute on resume.**

Three options were weighed:

1. **Persist on `durable_hops`** ← chosen. Follows the four precedents that already closed this exact gap for other fields: `task_context` (`AA-145`), `delegation_required` (`AA-148`), `requires_human_confirmation` (`LOO-20`), `enable_web_search` (`HAR-17`).
2. **Recompute via `buildSignatureConfig()` on resume.** Rejected — it re-reads *today's* skill profiles, so a resumed hop's signature reflects resume-time config, quietly reintroducing the drift `LOG-67` shipped to eliminate.
3. **Read the config-half back from the sibling `ai_activity_log` row.** Rejected on two grounds: `logAgentTurn()` at `execute.js:855` is **fire-and-forget (no `await`)**, so the row may not exist when the checkpoint fires (8% of affected spans have no config-bearing sibling at all); and it would make the audit log a runtime read-dependency of the executor, inverting the layering.

**Forward-only.** The already-broken historical rows are **not** in scope — they are `LOG-111` (Architecture), logged this session with the evidence.

## 6. DESIGN RULES

- **Frozen, never recomputed.** No call to `buildSignatureConfig()` anywhere on the resume path.
- **Generic — no conditionals.** No branch keyed on `agent_id`, `capability_slug`, or `intent_slug` anywhere in this change (`.claude/rules/capabilities-are-data.md`).
- **Never erase.** The persist is conditional on non-null. A checkpoint without a snapshot leaves any existing value alone.
- **Fire-and-forget stays fire-and-forget.** Use `patchDurableHopRow()`'s existing path; do **not** promote this write to `patchDurableHopRowChecked()`. An unpersisted signature costs one blank pattern line — it does not break a safety bound, which is the only thing `HAR-17` reserved the checked variant for.

## 7. SCOPE RULES (do NOT touch)

- **Do not edit `api/_lib/handlers/durable-loop.js`.** `loadDurableHopRow()` already selects `*`; `createDurableHopRow()` deliberately stays out of this — the always-run patch in `checkpointAndReturn()` covers both the create and the pre-existing-row paths, per `LOG-49`'s precedent.
- **Do not backfill any historical row.** That is `LOG-111`, a separate Supabase-data session.
- Do not change `logAgentTurn()`, `mergeCallFacts()`, `buildSignatureConfig()`, or anything in `db-assembly.js` / `request-receivable.js`.
- Do not touch `pattern_vocabulary`, its `criteria`, or the `ai_call_patterns` view.
- Do not alter checkpoint/resume control flow, the recovery ledger, span identity, or `trace_id` threading.
- **Max files: `api/capabilities/execute.js` only**, plus the migration and the deleted-before-commit test file.
