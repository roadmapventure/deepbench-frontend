## 1. CONTEXT

`callModel()`'s retry-once-on-parse-failure logic (`api/prompt/request-receivable.js`, `catch (parseErr)` block) replays the conversation on a parse failure by appending the failed assistant turn followed by a plain-text corrective `user` message:

```js
messages: [...callBody.messages, { role: 'assistant', content: llmData.content }, { role: 'user', content: 'Your response did not conform to the required schema...' }],
```

Anthropic's Messages API requires that any `assistant` turn containing a `tool_use` block be immediately followed by a `user` turn containing a matching `tool_result` block — a plain-text `user` message does not satisfy this. Whenever the failed turn being retried included a `tool_use` block (which is true for effectively every case in this codebase: any JSON/schema-output intent always calls its schema tool, and any `canRequestHelp` intent may call `request_help`/`delegate_to_agent`), the retry call itself is rejected by Anthropic with a 400 — `!retryRes.ok` becomes true, and the code throws `Object.assign(new Error('Parse failed and retry also failed'), { status: 422 })`. The "retry once" safety net silently never fires for the majority of realistic parse-failure cases; it just produces the same hard 422 the first failure would have, one HTTP round-trip later.

**Discovery history:** `AA-150` (Owen's `qg-review-intent`) was live-found 2026-07-08 during `session/speed-rootcause-0708` — a repeat call with identical input that had just succeeded failed with this exact error. The root cause above was independently found twice the same day: once during `AA-152`'s own coding session, and once by a design session that live-reproduced it as a "Something went wrong reaching Marcus" error. Separately, `AA-151` (durable-checkpoint stall theory, "Column 2 charts don't render") was filed the same day from `session/charts-column2-0708`, diagnosed as a `durable_hops` freeze — a different mechanism entirely.

**Today's live-repro session (`parse-retry-fix-0708`, answering John's "can we ship to Apple with these known bugs" question) found the two are the same bug:** 15 real calls against dev. Owen's `qg-review-intent`: 1/10 raw calls (10%) hit this exact error. Priya's `hyp-hypothesis-test-display-intent` — the only call in the app that can ever produce a Column 2 chart — hit the *identical* error **4/5 attempts (80%)**, and **0/5 attempts ever reproduced `AA-151`'s originally-filed checkpoint-freeze symptom** (no attempt ever reached `in_progress`/got a `job_id`; every failure happened before checkpointing). Priya's much higher rate is consistent with her call chaining more `tool_use` turns (delegation-required intent: `request_help` → `agent-selection-intent` → `delegate_to_agent`) than Owen's single-shot review, so there are proportionally more chances for any one turn's retry to hit this bug.

## 5. TASKS (1 of 4 max, 1 file)

### Task 1 — `api/prompt/request-receivable.js`: fix `callModel()`'s retry correction message to include a `tool_result` block when the failed turn contained a `tool_use`

Currently (lines 177–192):

```js
  } catch (parseErr) {
    if (tools.length > 0) {
      retryCount = 1;
      const retryBody = {
        ...callBody,
        messages: [...callBody.messages, { role: 'assistant', content: llmData.content }, { role: 'user', content: 'Your response did not conform to the required schema. Please try again and return the structured output exactly as specified.' }],
      };
      const retryRes = await fetch('https://api.anthropic.com/v1/messages', { method: 'POST', headers: anthropicHeaders, body: JSON.stringify(retryBody), signal: AbortSignal.timeout(55000) });
      if (!retryRes.ok) throw Object.assign(new Error('Parse failed and retry also failed'), { status: 422, detail: parseErr.message });
      llmData = await retryRes.json();
      usage = { input_tokens: usage.input_tokens + (llmData.usage?.input_tokens || 0), output_tokens: usage.output_tokens + (llmData.usage?.output_tokens || 0) };
      turn = parseModelTurn(llmData, hasSchemaTool, schemaTool);
    } else {
      throw Object.assign(new Error('Parse failed'), { status: 422, detail: parseErr.message });
    }
  }
```

Replace with:

```js
  } catch (parseErr) {
    if (tools.length > 0) {
      retryCount = 1;
      // FEATURE: AA-150/AA-151 -- Anthropic's API requires a tool_result block immediately after any
      // assistant turn containing a tool_use block. The prior corrective message was always plain text,
      // which Anthropic rejects with a 400 whenever the failed turn included a tool_use -- true for
      // effectively every JSON/schema intent and any canRequestHelp intent, making this "retry once"
      // safety net a silent no-op in the majority of real cases (confirmed live: 10% of Owen's
      // qg-review-intent calls, 80% of Priya's hyp-hypothesis-test-display-intent calls). Reuses the
      // exact tool_result shape execute.js:543 already uses for delegate-hop resume, not a new pattern.
      const correctionText = 'Your response did not conform to the required schema. Please try again and return the structured output exactly as specified.';
      const failedToolUse = llmData.content?.find(b => b.type === 'tool_use');
      const correctionMessage = failedToolUse
        ? { role: 'user', content: [{ type: 'tool_result', tool_use_id: failedToolUse.id, content: correctionText, is_error: true }] }
        : { role: 'user', content: correctionText };
      const retryBody = {
        ...callBody,
        messages: [...callBody.messages, { role: 'assistant', content: llmData.content }, correctionMessage],
      };
      const retryRes = await fetch('https://api.anthropic.com/v1/messages', { method: 'POST', headers: anthropicHeaders, body: JSON.stringify(retryBody), signal: AbortSignal.timeout(55000) });
      if (!retryRes.ok) throw Object.assign(new Error('Parse failed and retry also failed'), { status: 422, detail: parseErr.message });
      llmData = await retryRes.json();
      usage = { input_tokens: usage.input_tokens + (llmData.usage?.input_tokens || 0), output_tokens: usage.output_tokens + (llmData.usage?.output_tokens || 0) };
      turn = parseModelTurn(llmData, hasSchemaTool, schemaTool);
    } else {
      throw Object.assign(new Error('Parse failed'), { status: 422, detail: parseErr.message });
    }
  }
```

**Why this design, not a bigger one:** still retry-once-then-throw, zero new retry attempts added. The only change is the *shape* of the one corrective message, branching on whether the failed turn actually requires a `tool_result` (has a `tool_use` block) or not (plain text turn, existing behavior unchanged — this path was never broken). Does not touch `parseModelTurn()` itself (already correct per `AA-147`), does not touch `execute.js`'s separate `AA-142`/`AA-148` delegation-required terminal guard (a different failure mode — narration instead of delegation — not implicated here).
