## What this slice is, and what it deliberately is not

**Is:** the probe that answers *"is the deployment the public is being served actually red?"* and, on
a red, hands the existing engine the facts it already knows how to act on.

**Is not:** any new authority. It applies no DDL, pushes no commits, and makes no Vercel API call
beyond reading the deployment list — the design's *"no Vercel API actuation (the revert push **is**
the deploy fix)"*, decided without asking and unchanged here.

## The three decisions, each with its fail direction stated

**1. The probe is RED-ONLY. It may never write a green anchor.** This is the whole of the slice's
risk and the edit a later cycle is most likely to make, because step 4a's command is byte-identical
in shape. Handing a green probe's samples to the engine as `jobs` takes `decide()`'s `RECORD_GREEN`
branch and stores the probed commit in `runner_green_states` — as the anchor **every later red is
measured against** — on the evidence that a web server answered. The anchor's meaning is *both
blocking CI jobs concluded success*; a page that loads says nothing about the test suite. Made
structural rather than remembered: `engineArgsFor()` returns `null` on anything but `serving-red`,
and the jobs it emits on a red always carry a `failure` conclusion, so the green branch is
unreachable from this file.

**2. The commit judged is the SERVING one, never `dev`'s head.** `SES-015` measured this project's
push→serve lag at a median of 37s, a p90 of 852s and a max of 2,973s, with 28% of commits waiting
over five minutes — so the two are routinely different commits, and reverting a commit the public was
never served is the one direction this ticket must never fail in. `pickServing()` is imported from
`check-deploy-current.js`, never re-derived (`SES-45`).

**3. Unknown is a third verdict, not a synonym for red.** The fail direction *looks* opposite to the
watermark rule (where unknown is treated as moved) and is in fact the same — away from acting. A DNS
blip, a proxy 407, a rotated bypass secret or one bad second on the runner's own network must not
revert a healthy `dev`. Deployment protection (401/403) and rate limiting (429) are facts about *this
probe's access*, not the site's health, and report `unknown`. Exit 2 is *could not run*, never a pass.

**And a single bad response is not a red:** `MIN_SAMPLES = 3` consecutive reds are required, and any
one green sample makes the whole probe green — the runbook's own *"flake is not a root cause"*
discipline applied where it costs something.

## The named blind spot, and the half of it that was closed

An HTTP probe cannot see a **client-side render failure**: a shell that loads and then throws in
React reads green from here, and no amount of status-code reading changes that. It is published in
`PROBE_LIMITS` and asserted by the guard rather than left to be discovered.

What *was* closed is the common half: the probe follows the shell's **own entry-module reference**
(read from the shell, never guessed — Vite rehashes the filename every build) and a shell served
beside a bundle that 404s is red. That is the overwhelming shape of a real blank-page deploy — assets
that did not upload — and it is server-side observable. Proven against the live deployment, which
served `/assets/index-C5wASfTj.js` at HTTP 200.

## QA — six live arms over real HTTP, one variable each, nothing written

| # | Arm | Result |
|---|---|---|
| 1 | The real dev deployment, both secrets | `serving-green`, exit 0, **engine `null`**, entry bundle `/assets/index-C5wASfTj.js` 200 |
| 2 | **The same healthy deployment, bypass secret withheld** | HTTP 403 → `unknown`, exit 2, no trigger |
| 3 | Controlled origin serving 503 at `/` | `serving-red`, exit 1, reason names the 503 |
| 4 | Controlled origin: shell served, entry bundle 404s | `serving-red`, exit 1, reason names the bundle |
| 5 | Controlled origin: HTTP 200, empty body | `serving-red`, exit 1, blank-page shape named |
| 6 | **Seam proof** — red origin + real resolved serving sha → real engine, **dry run** | `revert-and-card`, attributed to the cycle that pushed `211aa1c`; `applied: false`, no card filed |

Arm 2 is the one that earns its keep: it proves a rotated or absent credential cannot revert a
working site. Arm 6 is labeled a **seam proof** because its two facts come from different sources by
construction (a local red origin, the real Vercel serving sha); it was run **without `--apply`**, so
no incident card was filed and nothing was written.

**A non-arm, reported rather than quietly re-rolled.** The first attempt at a live red pointed the
probe at `/assets` on the real deployment and came back **green** — Vercel's SPA rewrite serves the
shell for unknown paths, which is correct behaviour and simply not a red. The arm was replaced with
controlled origins rather than written up as a finding.

**File-level negative control:** the guard cannot even *load* against `origin/dev` — the module it
pins does not exist there — and passes on the shipped tree. Every clause additionally carries an
inline control, and three of those controls are the **retired designs** applied to the same fixture
and asserted to lose (pass-everything-through reaching `record-green`; any-red-is-red;
not-green-is-red), plus the `theControlsAreNotVacuous()` meta-check.
