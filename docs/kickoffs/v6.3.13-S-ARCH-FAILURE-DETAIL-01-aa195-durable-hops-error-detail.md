## 1. CONTEXT

`AA-195` (live "Something went wrong reaching Marcus" failure, found 2026-07-16) is not yet root-caused — the specific evidence needed (the exact request Anthropic rejected with a 400) exists in memory at the moment of failure but is currently discarded before it reaches anywhere durable. This session does not fix `AA-195` — it makes the platform capable of diagnosing it (and any future failure of this shape) from Supabase alone, no external Vercel log access required, matching the platform's existing self-observability philosophy (the same reason `logAICall()`/AI Audit wiring is mandatory on every route).

**Two confirmed gaps, found scoping this session (read directly, not assumed):**

1. `postToAnthropicWithRetry()` (`api/prompt/request-receivable.js:154`) already attaches the full rejected-request body to the thrown error's `.detail` property — `throw Object.assign(new Error('Anthropic call failed: ${res.status}'), { status: 502, detail: text })`. The only place in `execute.js` that persists a failure to `durable_hops` (`resumeCapability()`'s catch, line 704) stores `error: e.message` only — `.detail` is silently dropped before it reaches the database.
2. `runCapability()` (the fresh, top-level call path, lines 550-620) has **no try/catch at all** around its `runLoop()` call — confirmed by direct read, not assumed. If a fresh call throws, nothing is persisted to `durable_hops` — the exception only reaches the HTTP response (which already includes `.detail`, `execute.js:855` — that part is fine) and is never durably recorded. Only a *resumed* call's failure gets written to `durable_hops` today.

**Relevance to `AA-195`'s own root cause, found as a side effect of this scoping (worth recording even though it's not what this session fixes):** since only `resumeCapability()` persists `status: 'failed'`, and Owen's failed row from the original incident had `hop_counter: 0` with no resume markers of its own, the sequence must have been: Owen's fresh call checkpointed gracefully (nested checkpoint from Marcus's own regenerate chain inheriting Owen's shrinking deadline, the same mechanism `AA-187` already partially fixed) → something then resumed Owen's job → **that resume attempt is where the real 400 happened.** This narrows `AA-195`'s eventual root-cause search to `resumeCapability()`'s reconstruction/re-dispatch of a `pending_delegation`, not "somewhere in a nested chain" generally. Logged here for whichever session picks up `AA-195`'s actual fix.

**Why permanent, not a temporary diagnostic hack (John's explicit call, 2026-07-16):** a one-off instrumentation add would need to be re-built the next time a different failure needs this same evidence. Generic, harness-level, and reused by every capability by construction — no `if(capability_slug===)` anywhere in this fix.

**Why this doesn't slow anything down:** `.detail` is already computed (already-fetched `res.text()`) before either fix point is reached — this only changes what gets written into a database update that already happens, and only on a failure path that, by definition, isn't the common case. Zero added latency on any successful request.

### Task 1 — `api/capabilities/execute.js`: persist full error detail on every `durable_hops` failure, fresh or resumed

**Add a shared helper**, placed near `checkpointAndReturn()` (both operate on the same table, same shape of "create a row if none exists yet, then patch it"):

```js
// FEATURE: AA-195 (S-ARCH-FAILURE-DETAIL-01) -- captures the full rejected-request detail
// postToAnthropicWithRetry() already attaches to a thrown error (.detail, request-receivable.js)
// but which was previously dropped before reaching durable_hops -- Supabase-only observability,
// no external log access required (John's explicit call, 2026-07-16: permanent, not temporary).
// Truncated to 2000 chars, same defensive precedent as AA-157's retryDetail.slice(0, 1000).
function formatErrorForPersistence(e) {
  const detail = typeof e.detail === 'string' ? e.detail.slice(0, 2000) : null;
  return detail ? `${e.message}\n\nDetail: ${detail}` : e.message;
}

// FEATURE: AA-195 -- also extends persistence to runCapability()'s fresh-call path, which
// previously had zero failure record at all (only resumeCapability() persisted anything --
// confirmed by direct read, not assumed). Creates a row first when job_id is null (fresh call),
// otherwise patches the existing one (resumed call) -- same create-if-absent shape
// checkpointAndReturn() already uses for the success/checkpoint path.
async function persistFailureAndRethrow(e, { job_id, tenant_id, capability_slug, intent_slug, agent_id, enriched, canRequestHelp, delegationRequired, task_context }) {
  let row_id = job_id;
  if (!row_id) {
    const row = await createDurableHopRow({
      tenant_id, capability_slug, intent_slug, agent_id, task_context,
      system_prompt: enriched.system_prompt, format_contract: enriched.format_contract,
      llm: { model: enriched.llm.model, max_tokens: enriched.llm.max_tokens, temperature: enriched.llm.temperature },
      can_request_help: canRequestHelp, delegation_required: delegationRequired === true,
    });
    row_id = row.id;
  }
  await patchDurableHopRow(row_id, { status: 'failed', error: formatErrorForPersistence(e) });
  throw e;
}
```
