## 2. CONTEXT

`AI-35` (the AI Pattern Tracking redefinition, `ARCHITECTURE.md §19i`) has a 6-step ordered build sequence. Step 1 (the architecture rewrite) is done. This session is Step 2a: the governed pattern vocabulary table plus the mechanism that keeps it current over time, so the platform can answer "how do we know we're not missing a new pattern, and how do we know our names are industry-standard" on an ongoing basis, not just at a one-time launch audit.

**Live design conversation with John, 2026-07-21, this session, established the following, in order:**

1. **Self-maintenance is triggered per-recognition, in real time, not batched.** When a call's facts don't match any known pattern, that's the trigger — not a scheduled scan.
2. **The trigger fires async and never blocks the user-facing response.** Whatever produced the ambiguous facts already returned its answer; new-pattern review happens after, off the critical path.
3. **Candidates are staged in an append-only log, not written directly to the governed vocabulary.** Multiple simultaneous triggers can't collide with each other this way — same reasoning that already fixed `dev_version_counter` (`AZ-19`/`S-MOBILE-ROSTER-01` collision) and `feature_id_counter` (`AA-197`/`AA-198`, `CHI-13`/`CHI-14`), applied here to a vocabulary table instead of a counter.
4. **One agent owns promotion out of the staging log — Susan Smith (Trainer Agent).** She reviews a candidate, checks it against both the existing governed vocabulary and other pending candidates (so two calls that surface the same new behavior don't get promoted twice), researches a real citation, and promotes or discards. This is the same structural Resource-Ownership-Broker pattern Eleanor Voss already uses for `the_Library` (`ARCHITECTURE.md §19c`/`§19e`) — sole ownership enforced by which Skill Profile is wired to the write handler, never a runtime `agent_id ===` check.
5. **Sequencing correction, found live this session:** the *live, automatic* trigger (item 1 above) cannot actually work yet — it depends on Layer A's rich fact capture (`AI-35` Step 3) and Layer B's rule evaluator (Step 4), neither of which exist today (confirmed live: `request-receivable.js`/`api/capabilities/execute.js`'s write path only captures a handful of booleans, not the rich fact set `§19i`'s Layer A calls for). This session builds and ships everything that doesn't depend on that — the tables, and Susan's full review/promote capability — tested via directly-inserted candidates. The live automatic trigger itself is deferred to Step 4, the earliest point "no rule matches" is actually computable.
6. **The existing `PATTERN_CATALOG` (`shared/ai-patterns.js`) is not being replaced or duplicated this session.** It's a static file (not a table) that today's 4 real display areas already read correctly (confirmed live: AI Audit screen's "By Pattern" section and "Patterns Active" count in `AIActivityPanel.jsx`, the Agent Routing drawer's pattern badges + `byPattern` stats in `MarketIntelligenceScreen.jsx`, and the pattern-count tile in `AboutPanel.jsx` — none of them read the new governance fields this session adds). This session's new `pattern_vocabulary` table starts empty and is not wired into display — it exists so Susan has somewhere real to research into and write. Whether/when display gets pointed at it instead of the static file is a separate, later decision, not part of this session.
7. **Population discipline for the next session (`2b`, not this one):** when the existing 24 `PATTERN_CATALOG` entries get run through Susan's process, each one is individually researched — never bulk-copied from the old file's text. A pattern only lands in `pattern_vocabulary` with a citation Susan actually found and verified.

### Task 1 — Supabase: two new tables + Susan's Capability/Skill Profile seed

**New table `pattern_vocabulary`** (the governed Layer C list — not read by any display code this session):
```sql
CREATE TABLE pattern_vocabulary (
  pattern_slug text PRIMARY KEY,
  name text NOT NULL,
  description text,
  citation text NOT NULL,
  maturity_status text NOT NULL DEFAULT 'experimental' CHECK (maturity_status IN ('experimental','stable','roadmap')),
  last_reviewed_date date NOT NULL DEFAULT now(),
  superseded_by text REFERENCES pattern_vocabulary(pattern_slug),
  linked_rule_version text,
  promoted_by text NOT NULL DEFAULT 'susan',
  tenant_id text NOT NULL DEFAULT 'global',
  created_at timestamptz NOT NULL DEFAULT now()
);
```

**New table `pattern_candidates`** (append-only staging log):
```sql
CREATE TABLE pattern_candidates (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id text NOT NULL DEFAULT 'global',
  observed_description text NOT NULL,
  source_ai_activity_log_id integer REFERENCES ai_activity_log(id),
  submitted_by text NOT NULL DEFAULT 'manual',
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','promoted','merged','discarded')),
  reviewed_by text,
  resolution jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  resolved_at timestamptz
);
```

### Task 2 — `lib/pattern-vocabulary.js` (new)

Structural precedent: `lib/librarian.js`. No internal `agent_id === 'susan'` check anywhere in this file — ownership is enforced entirely by which Skill Profile sets `handler: 'pattern-vocabulary-write'` (Task 1), same as the header comment in `library-write.js` states for Eleanor.

Exports:
- `buildReviewContext(candidate_id)` — reads the target `pattern_candidates` row, the full current `pattern_vocabulary` table, and every other `status = 'pending'` row in `pattern_candidates`, returns the shape needed for `task_context` when invoking Susan's capability. Plain read, no credential gate (this is governance metadata, not tenant/data-room-scoped content, unlike `the_Library`).
- `reviewCandidate({ candidate_id, decision, pattern_slug, name, description, citation, maturity_status, matched_existing_slug, matched_candidate_id, reasoning })` — the single write primitive. On `decision: 'promote'`: insert into `pattern_vocabulary` (citation required, reject/throw if missing — never silently promote without one, per `§19i`'s "an entry without one may not exist"), mark the candidate `status: 'promoted'`. On `decision: 'merge'`: mark the candidate `status: 'merged'`, store `matched_existing_slug`/`matched_candidate_id` in `resolution`, no new `pattern_vocabulary` row. On `decision: 'discard'`: mark `status: 'discarded'`. Always set `reviewed_by: 'susan'`, `resolved_at: now()`, and `resolution` to the full decision payload (mirrors `pending_confirmations.resolution`'s existing shape).

Follow `lib/librarian.js`'s exact fetch/header/error-handling style (raw `fetch()` against `${supabaseUrl}/rest/v1/...`, not a different Supabase client pattern) for consistency with the rest of `lib/`.

import { reviewCandidate } from '../../../lib/pattern-vocabulary.js';

export async function handle({ content }) {
  const { candidate_id, decision, ...rest } = content || {};
  if (!candidate_id) throw new Error('pattern-vocabulary-write handler: candidate_id required in structured output');
  if (!decision) throw new Error('pattern-vocabulary-write handler: decision required in structured output');
  const result = await reviewCandidate({ candidate_id, decision, ...rest });
  return { deliverable_id: null, handler_result: result };
}
