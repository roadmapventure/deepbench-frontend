## 1. CONTEXT

Found during `S-APPLE-04b`'s own Category L test (2026-07-03): Nadia's `data-patch-intent` consistently returned a generic, input-blind response (`action: "no_action"` / boilerplate) regardless of what correction was actually described in `task_context`. Root-caused, not patched at the symptom: `db-assembly.js`'s `assemblePrompt()` only ever injects the caller's actual task into the model's prompt through one of three paths —
1. A RAG section (`knowledge`-type Skill Profile) — but this only surfaces *semantically retrieved chunks*, never the literal request text itself.
2. A Reflect section (`reflect`-type Skill Profile) — confirmed via live query (this session) that **zero capabilities on the platform have one today** — this path is entirely dormant.
3. The `WORK ORDER` section — fires only when `task_context.goal` is a plain string.

Any capability whose `task_context` is a custom object without a `.goal` field, and which has no RAG-enabled Knowledge Skill Profile, has **no path at all** by which its actual task ever reaches the model. It reasons over its (call-independent) identity/behavior text and a schema to fill in, with zero information about the specific thing it was actually asked to do.

**Confirmed blast radius (live query against `capability_skill_profiles`, this session) — capabilities with no `knowledge`-type Skill Profile at all, meaning they have zero RAG signal and are fully dependent on the missing path: `data-analysis`** (Nadia — `data-escalate-intent`, live since `S-APPLE-04a`; `data-patch-intent`/`data-patch-execute-intent`, not yet shipped), **`pipeline-triage`** (Sam Reyes — `intake-commit-intent`/`intake-failure-intent`, live since `S-APPLE-03b`), **`quality-gate`** (Owen Marsh — `qg-review-intent`, live). Capabilities *with* a `knowledge`-type profile (`channel-intelligence`, `hypothesis-evaluation`, `data-room-custody`, `project-manager`) are partially masked by RAG's indirect signal but likely still miss literal task fidelity for the same reason — not confirmed live this session, logged to `FEATURES.md` for a future verification pass rather than expanding this session's scope (John's explicit call: fix the mechanism now, don't turn this into a full-platform audit).

This means several already-shipped, QA-passed capabilities have likely been reasoning over their own identity text and nothing else since the day they shipped — undetected because their existing Category L tests only asserted output *shape* (an array, a required field present), never that the output was actually *responsive to the specific input*. That testing gap is itself worth a `STANDARDS.md` note (see Section 6, SCOPE RULES) but is not this session's job to enforce platform-wide.

**The fix:** a new, generic fallback section — `TASK DETAILS` — that renders whenever `task_context` is a non-empty plain object and the existing `.goal`-string `WORK ORDER` path does *not* fire. Mutually exclusive with `WORK ORDER` (never both — no duplicate task text for existing `.goal`-shaped callers, e.g. `api/plan.js`'s Work Orders). Fires based purely on the shape of `task_context`, never a capability or agent identity check (`AR-1.1`).

```js
  if (goalText && goalText.trim()) {
    const workOrderParts = [`Goal: ${goalText.trim()}`];
    if (deliverableType) workOrderParts.push(`Deliverable type: ${deliverableType}`);
    sections.push({
      slug: 'work-order',
      label: 'WORK ORDER',
      skill_profile_slug: null,
      type: 'stored',
      content: workOrderParts.join('\n'),
      fetch_instruction: null,
      required: true,
      order: 2.5,
    });
    sections.sort((a, b) => (a.order || 0) - (b.order || 0));
  } else if (typeof task_context === 'object' && task_context !== null && Object.keys(task_context).length > 0) {
    // FEATURE: AI-44 -- TASK DETAILS: generic fallback for any capability whose task_context is a
    // plain object without a .goal field (e.g. Nadia's {disputed_chunk_id, correction, ...}, Sam's
    // {intent, hypothesis, correction_text, ...}). Without this, a capability with neither a RAG
    // section nor a Reflect section never sees its own specific task at all -- confirmed live
    // 2026-07-03 during S-APPLE-04b QA (data-patch-intent returned a generic, input-blind response

    // both, no duplicate task text for existing .goal-shaped callers (api/plan.js Work Orders).
    // Shape-driven, not identity-driven -- AR-1.1.
    const taskDetailsText = Object.entries(task_context)
      .filter(([, v]) => v !== null && v !== undefined && v !== '')
      .map(([k, v]) => `${k}: ${typeof v === 'object' ? JSON.stringify(v) : v}`)
      .join('\n');
    if (taskDetailsText) {
      sections.push({
        slug: 'task-details',
        label: 'TASK DETAILS',
        skill_profile_slug: null,
        type: 'stored',
        content: taskDetailsText,
        fetch_instruction: null,
        required: true,
        order: 2.5,
      });
      sections.sort((a, b) => (a.order || 0) - (b.order || 0));
    }
  }
```

```js
async function testCategoryM() {
```
