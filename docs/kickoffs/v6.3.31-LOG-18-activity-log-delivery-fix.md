## 1. CONTEXT

`LOG-18` (found live during `S-AI-46b`'s own Category L test, 2026-07-16): a capability with REFLECT genuinely enabled produced zero `ai_activity_log` row for the `reflect`/`synthesis` `logActivity()` calls, despite `ai-enrichment.js`'s code correctly calling `logActivity()` when `reflectRan`/`synthesisRan` are true.

**Root cause, confirmed live this session (not assumed from the prior report — independently re-verified with a fresh test):**

Triggered a real `preview-prompt` call (`api/plan.js`, `agent_id: michelle`, `capability_slug: project-manager`) at `2026-07-16T21:40:07Z`, completing at `21:40:29Z` (~22s). Response confirmed `patterns.reflect: true, patterns.synthesis: true` — both genuinely ran. Queried `ai_activity_log` for the full window immediately after: only 2 rows landed (`agent-directory` and `similarity`, both timestamped `21:40:07`, i.e. fired in the first second of the request) — **zero** `reflect`/`synthesis` rows, despite `ai-enrichment.js`'s own code (read directly, lines ~280-297) correctly calling `logActivity()` for both when they ran. This is the 3rd independent live observation of the exact same failure (2 from `S-AI-46b`'s own QA, 1 fresh here) — **100% reproduction rate on every REFLECT/synthesis call checked so far**, not intermittent.

**The mechanism:** `lib/activity-log.js`'s `logActivity()` is deliberately fire-and-forget — a bare `fetch(...).catch(() => {})` with no `await`, no `return`. The rows that consistently land are the ones fired early in a request, with substantial subsequent `await`-ed work (more Supabase/Anthropic calls) still ahead of them before the handler responds — the event loop gets many more ticks to let that earlier fetch complete. The rows that consistently vanish are the ones fired as the *last* async operation before the handler's `return`/response — `ai-enrichment.js`'s reflect/synthesis calls happen in `enrichPrompt()`'s final steps, and `plan.js`'s `preview-prompt` handler does only synchronous string-building after `enrichPrompt()` returns before responding, leaving the fire-and-forget fetch almost no wall-clock time before Vercel's Node.js function execution context is torn down. This is not `reflect`/`synthesis`-specific — **any** `logActivity()` call that happens to be the last async work before a handler responds is at risk, meaning some fraction of *every* service's rows on the platform may already be silently missing, not just misattributed (the concern `LOG-18`'s original finding raised).

**Confirmed NOT the cause:** not a bug in `ai-enrichment.js`'s gating logic (`reflectRan && reflectTokensUsed > 0`) — the code is correct; the write attempt genuinely fires, it just doesn't survive to complete.

### Task 1 — `lib/activity-log.js`: replace bare fire-and-forget with `waitUntil()`-wrapped fetch

Current:
```js
export function logActivity({
  tenantId = 'global',
  agentId = null,
  aiType,
  feature = null,
  model = null,
  inputTokens = null,
  outputTokens = null,
  latencyMs = null,
  taskId = null,
  knowledgeTier = null,
  patternsUsed = [],
  traceId = null,
}) {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  if (!supabaseUrl || !supabaseKey || !aiType) return;
  for (const slug of patternsUsed) {
    if (!VALID_PATTERN_SLUGS.has(slug)) {
      console.warn(`[activity-log] unrecognized pattern slug "${slug}" on aiType="${aiType}" feature="${feature}" -- check for a stale/renamed PATTERN_CATALOG slug`);
    }
  }
  fetch(`${supabaseUrl}/rest/v1/ai_activity_log`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', apikey: supabaseKey, Authorization: `Bearer ${supabaseKey}`, Prefer: 'return=minimal' },
    body: JSON.stringify({
      tenant_id: tenantId,
      agent_id: agentId,
      ai_type: aiType,
      feature,
      model,
      input_tokens: inputTokens,
      output_tokens: outputTokens,
      latency_ms: latencyMs,
      task_id: taskId,
      knowledge_tier: knowledgeTier,
      patterns_used: patternsUsed.length > 0 ? patternsUsed : null,
      created_at: new Date().toISOString(),
    }),
  }).catch(() => {});
}
```
becomes:
```js
import { waitUntil } from '@vercel/functions';

export function logActivity({
  tenantId = 'global',
  agentId = null,
  aiType,
  feature = null,
  model = null,
  inputTokens = null,
  outputTokens = null,
  latencyMs = null,
  taskId = null,
  knowledgeTier = null,
  patternsUsed = [],
  traceId = null,
}) {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  if (!supabaseUrl || !supabaseKey || !aiType) return;
  for (const slug of patternsUsed) {
    if (!VALID_PATTERN_SLUGS.has(slug)) {
      console.warn(`[activity-log] unrecognized pattern slug "${slug}" on aiType="${aiType}" feature="${feature}" -- check for a stale/renamed PATTERN_CATALOG slug`);
    }
  }
  const write = fetch(`${supabaseUrl}/rest/v1/ai_activity_log`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', apikey: supabaseKey, Authorization: `Bearer ${supabaseKey}`, Prefer: 'return=minimal' },
    body: JSON.stringify({
      tenant_id: tenantId,
      agent_id: agentId,
      ai_type: aiType,
      feature,
      model,
      input_tokens: inputTokens,
      output_tokens: outputTokens,
      latency_ms: latencyMs,
      task_id: taskId,
      knowledge_tier: knowledgeTier,
      patterns_used: patternsUsed.length > 0 ? patternsUsed : null,
      created_at: new Date().toISOString(),
    }),
  }).catch(() => {});
  // FEATURE: LOG-18 -- fire-and-forget without waitUntil() lets Vercel tear down the function's
  // execution context as soon as the response is sent, silently abandoning any write still in
  // flight (confirmed live: reflect/synthesis rows -- the last async work before a handler
  // responds -- never landed, 3/3 real observations). waitUntil() extends the invocation's
  // lifetime just long enough for this specific promise to settle, without adding latency to the
  // actual response (unlike awaiting it inline, which was considered and rejected -- see kickoff
  // CONTEXT). Wrapped in try/catch: waitUntil() throws if called outside a real Vercel request
  // context (e.g. a future local/non-Vercel test runner) -- degrade to the original fire-and-forget
  // behavior in that case rather than crashing every caller everywhere logActivity() is used.
  try {
    waitUntil(write);
  } catch {
    // Not running inside a Vercel invocation context -- write promise above already started;
    // same best-effort behavior as before this session.
  }
}
```

**Task 1b — fallback, only if Task 1's own live test (Section 8) shows `waitUntil()` doesn't actually extend delivery** on this project's classic `(req, res)` handler shape: replace the `waitUntil(write)` call with `await write` instead, and change every call site of `logActivity()` platform-wide to `await logActivity({...})` (it's currently called synchronously, un-awaited, everywhere). **This fallback touches every caller and would blow this session's 2-file/4-task cap** — if Task 1's live test fails, stop, do not attempt the fallback in this same session; report the failure and treat the fallback as its own follow-up kickoff (`LOG-18b`) instead of silently expanding scope.
