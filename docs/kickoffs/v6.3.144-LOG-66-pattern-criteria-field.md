## 2. CONTEXT

The runtime signature model (§19k) derives a pattern **name** at read time by matching a log row's **signature** against each gold pattern's structured **`criteria`** — no hardcoded pattern naming. `criteria` is the machine-executable form of a pattern's identity; a plain SQL view can't match a signature against the prose `description`, so the pattern needs a second, matchable representation. That representation is authored by the **Pattern Definer (Susan)** — the semantic act happens once, at definition time, with a citation.

Verified live this session (Supabase, project `rallojeqnkgtxgsdsnqm`):
1. `pattern_vocabulary` has **no `criteria` column** today (columns: `pattern_slug, name, description, citation, maturity_status, last_reviewed_date, superseded_by, linked_rule_version, promoted_by, tenant_id, created_at`).
2. **21 gold patterns** exist (AI-35 2b promotions), all with `criteria` implicitly null.
3. Susan's output is a JSON Schema on the `pattern-vocabulary-review-intent` skill profile (`skill_profiles.traits.schema`); the `pattern-vocabulary-write` handler forwards all output fields via `...rest` into `reviewCandidate()`, which inserts the `pattern_vocabulary` row on `promote`.
4. `retrieval_method` and `retrieved_chunk_ids` are captured **independently** ([request-receivable.js:421-430](api/prompt/request-receivable.js:421)) — `retrieval_method` present ≠ chunks returned (live: `direct-lookup`/0-chunk rows exist).

**Settled by LOG-64/65 POCs (§19k):**
- `criteria` is `jsonb`, matched by a **bounded three-operator set**: `@>`/equality (presence), `in` (enumeration), numeric `>` (contingent facts). Not an open expression language.
- **Shape B:** one gold row per pattern; multiple intents enumerated inside one row via `intent in [...]`.

**Decisions reached in this design conversation (record — applied in LOG-72's authoring pass, NOT hand-coded here):**
- **RAG's fingerprint is the retrieval *attempt*, not the result** — `criteria: {retrieval_method: {in: ["similarity-search","mixed"]}}` — crediting a genuine vector query even at 0 results, excluding `direct-lookup` (straight SQL, not RAG) and true false-`rag` (no `retrieval_method` at all). Citeable: Lewis et al. 2020, arXiv:2005.11401. **This is the intended criteria for RAG but is authored by Susan in LOG-72, not seeded by this session.**
- Pattern names + criteria are **Susan's Layer-3 output**; this session builds only the mechanism + the fact-vocabulary + the operator grammar. We never hand-write a pattern's name or criteria in code or a migration.

## 4. STUB DEFINITIONS
- **Signature field vocabulary (the criteria allowlist)** — the 16 fields locked in `§19k`'s field order: `intent, retrieval_method, tool_calls, gated_subroutine_fired, sub_calls_chained, retrieved_chunk_ids, assembled_skill_slugs, model_modality, capability_slug, traits.schema, traits.source, input_references_other_deliverable, self_reported_claims, traits.intent_allowlist, execution_type`. `trace_id` is plumbing (never a criteria key). Some fields are captured today, some unbuilt (`LOG-49`); the allowlist is about what's a *legal* criteria key, not what's populated yet.
- **Operator grammar:** bare scalar/string/bool ⇒ `@>` containment; `{ "in": [...] }` ⇒ enumeration (value must be a non-empty array); `{ ">": N }` ⇒ numeric threshold (value must be a number). Anything else is invalid.
