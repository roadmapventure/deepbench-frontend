## CONTEXT

**One root cause behind two backlog items, confirmed via direct Supabase evidence (`durable_hops`/`deliverables` tables), not guesswork.** The durable-loop checkpoint/resume mechanism (`AA-139`) has two related gaps:

1. **`resumeCapability()` hardcodes `task_context: null`** (a known, documented gap since `AA-139` shipped). Live-confirmed instance: a resumed Marcus (`ci-answer-display-intent`) chain reached its `delegate_to_agent(is_final)` hand-off to Alex with no real task_context, falling back to only the free-text `task` paraphrase — Alex's own stored response literally reads *"I don't see the raw answer data in your message."* This is `AA-145` — not model flakiness, a real data-loss bug.
2. **No handling for a *nested* checkpoint.** In the same live run, the resumed chain's delegate call to Alex *itself* needed to checkpoint (budget nearly exhausted). `runLoop()`'s `is_final` branch has no check for `delegateResult.status === 'in_progress'` — it falls straight into `buildFinalDelegationResult()`, which sees no `.content`, and throws. That throw is what the frontend saw as a generic "Something went wrong reaching Marcus — try again" 500. This is `AA-141`'s real mechanism (not a generic Anthropic hiccup as originally assumed). The outer `durable_hops` row is left orphaned at `status: 'in_progress'` forever — the schema already has a `'failed'` status value (`durable_hops.status` check constraint includes it), nothing ever writes it.

Both gaps live in the same two functions (`runLoop()`, `resumeCapability()`) and the same table (`durable_hops`) — one session, not two.

**Task 2 — `api/_lib/handlers/durable-loop.js`: thread `task_context` through.** Add `task_context` to `createDurableHopRow()`'s destructured params and its insert body (alongside `system_prompt`/`format_contract`/`llm`). `loadDurableHopRow()` needs no change (`select=*` already returns it).

**Task 3 — `api/capabilities/execute.js`: extract `checkpointAndReturn()`, use it in two places.** Extract the existing top-of-loop checkpoint block (creates/patches the `durable_hops` row, returns `{status:'in_progress', job_id}`) into a small helper that also accepts and persists `task_context`:
```js
async function checkpointAndReturn({ job_id, tenant_id, capability_slug, intent_slug, agent_id, enriched, canRequestHelp, task_context, conversationHistory, depth, delegationOccurred, lastHelpSelection }) {
  let row_id = job_id;
  if (!row_id) {
    const row = await createDurableHopRow({
      tenant_id, capability_slug, intent_slug, agent_id, task_context,
      system_prompt: enriched.system_prompt, format_contract: enriched.format_contract,
      llm: { model: enriched.llm.model, max_tokens: enriched.llm.max_tokens }, can_request_help: canRequestHelp,
    });
    row_id = row.id;
  }
  await patchDurableHopRow(row_id, {
    conversation_history: conversationHistory, hop_counter: depth,
    delegation_occurred: delegationOccurred, last_help_selection: lastHelpSelection,
  });
  return { status: 'in_progress', job_id: row_id };
}
```
Call it from the existing top-of-loop budget check (unchanged behavior, just routed through the helper — pass `depth` as the loop's current `depth` var). Then add a **second call site**: immediately after `delegateResult = await runCapability({...})` in the `turn.tool_name === 'delegate_to_agent'` branch, **before** the `if (turn.tool_input.is_final === true)` check:
```js
if (delegateResult.status === 'in_progress') {
  return checkpointAndReturn({ job_id, tenant_id, capability_slug, intent_slug, agent_id, enriched, canRequestHelp, task_context, conversationHistory, depth, delegationOccurred, lastHelpSelection });
}
```
This is the actual `AA-141` fix — a nested in-progress result now correctly checkpoints the *outer* call and returns cleanly instead of falling through into `buildFinalDelegationResult()` and throwing. On the next `continue`, the outer call resumes from persisted `conversationHistory`/`hop_counter` and retries its own reasoning turn — it does not need to "remember" the nested delegate's partial state; the delegate is invoked fresh again, which is acceptable given delegate turns observed in production run 1-9s (Haiku) vs. the ~25-35s Sonnet turns that actually exhaust the budget. **Scope note:** the parallel case on the `request_help` branch (`delegateResult` from the `project-manager` call also possibly being `in_progress`) is not touched — that read already uses optional chaining (`delegateResult?.content?.reasoning ?? null`), so it degrades to `null` rather than crashing; a real but much lower-severity gap, left for a future session if it's ever observed live.
