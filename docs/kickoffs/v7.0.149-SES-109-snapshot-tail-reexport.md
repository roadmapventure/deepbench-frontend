# Kickoff — v7.0.149 · SES-109 — backlog snapshot re-exported in the serial tail

**Runner cycle** `cb8e87ce-d60f-4850-80f6-6d9d9bd9bb09` (scheduled 6:00 PM CST fire, 2026-08-21) · model Opus 5 · class **P10 - Tooling**, tier `now`.

## The bug (premise, revalidated live)
`runner-cycle.md` step 7 runs `scripts/export-backlog-snapshot.js` and pushes
`docs/backlog/BACKLOG-SNAPSHOT.md` in the single batched ship push — **before** the step-9 serial
tail. Register B42 (2026-08-21) moved the harvest **writes** (John's Accept/Reverse/Rework,
answers that file tickets, a released pin) into that tail. So every board change a tap causes
lands *after* the export meant to capture it, and the board's only repo-side copy (the `SES-81`
restore path) is systematically one harvest behind.

Found live by cycle `ff23297c` (v7.0.148): its snapshot in `61fd3e4` recorded 571 tickets and
did not contain `SES-98` going `done`, `SES-105` losing its pin, or `SES-108` existing — all
three written minutes later in that same cycle's tail. Confirmed this cycle by reading the live
procedure: step 7's push precedes the step-9 tail, and the tail is where harvest writes now run.

## The fix (one of the ticket's two options)
The ticket offered two: (a) re-export inside the tail after the harvest writes, or (b) move the
export into the tail entirely. **Take (a).** Option (b) is not free: the export must ride the
step-7 *code* push, and that push is deliberately kept OUT of the serial section so parallel
cycles rebase-retry instead of serialising (B42). Moving it wholesale would either drag the code
push into the serial tail (a throughput regression B42 exists to prevent) or create a second
push anyway. Option (a) is the minimal change.

A new sub-step **(4)** in the serial tail: after the harvest writes land, re-run the export. The
script is deterministic and prints `unchanged`/writes nothing when no board row moved (the common
case) — then there is nothing to push. Only on a real diff does the tail commit the snapshot and
push it (`git fetch/rebase/push HEAD:dev`, rebase-retry×3). This is the **one sanctioned second
push** of a cycle: snapshot-only, guarded by the publish lease already held (the ticket claim is
released at step-7 close-out, so it is not the token here), firing only when John's taps actually
changed the board — so the "one push per ship point" spirit holds. A rebase conflict outliving
the retries degrades to exactly today's one-harvest lag (next cycle's step-7 export catches up),
never a wall.

## Scope

script already behaves as needed), no site change. Close-out ceremony: `CLAUDE-STATE.md`,
`docs/SESSIONS.md`, `BACKLOG-SNAPSHOT.md` regenerated.

## QA (discriminating)
`export-backlog-snapshot.js --check` before/after: the committed snapshot's drift state is read,
the export is run to make it current, and `--check` returns exit 0 — proving the export captures
the live board (which is exactly what the new tail re-export does after harvest). A non-working
export would still show drift after. Plus `npm install && npm run build` and the regression suite.
Doc-only correctness (the reordering) is argued, not testable by build; the seam proof is the
`--check`/export/`--check` round-trip against the real board.
