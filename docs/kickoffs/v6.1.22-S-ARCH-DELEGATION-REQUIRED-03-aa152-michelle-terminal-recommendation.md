## 1. CONTEXT

Live investigation, 2026-07-08, following up on `AA-148`: even after `AA-148` made delegation-required hand-offs terminal, a real risk remained — the *choice* of which candidate to delegate to is made by the requesting agent's own second model turn, reasoning over the ranked candidate list `agent-selection-intent` (whoever holds `project-manager`) already produced. A live baseline (5 direct calls to `agent-selection-intent` with an identical, realistic MI-screen Q&A display need) showed her own reasoning is already reliable — Alex ranked #1 with correct justification in 5/5 runs, Riley correctly ranked lower with an honest caveat ("if you need a styled, rendered chat component rather than pure JSON"). But that same honest caveat is exactly the kind of text a second, independent model turn (Marcus's) can plausibly misread as a stronger fit than intended — the actual production failure (Riley getting delegated to for an in-chat need) happens in that *second* reasoning pass, not in the ranking itself.

**This session removes that second, redundant reasoning pass — but only for capabilities that already declare `delegation_required`.** `AA-142` established that trait to mean "this capability's entire job is handing off, never answering directly." `AA-148` extended it to mean "and that hand-off is always terminal — no legitimate case where the requester needs another turn after the delegate responds." This session extends it one step further, following the identical logic: no legitimate case where the requester needs to *re-choose* who to hand off to, either, once `agent-selection-intent` has already produced a real, reasoned recommendation. All three extensions rest on the same fact already established by `delegation_required`'s own definition — nothing new is being assumed.

**Not agent-identity hardcoding.** `request_help` already resolves live via `resolveCapabilityHolder('project-manager')` — never a literal `"michelle"` anywhere in the code — and this session does not change that. The fix is phrased entirely in terms of two capabilities' own data (the requester's `delegation_required` trait, `agent-selection-intent`'s own structured recommendation) — if a second PM agent were added or roster ownership changed tomorrow, this code is unaffected.

**Scoped narrowly, deliberately.** `request_help` is the single delegation path for the entire platform — making its resolution *always* final regardless of caller would be a platform-wide behavioral change whose safety for every other current/future caller (e.g. Owen's retry-review pattern, if it uses `request_help`) has not been investigated. This session only changes behavior when the *requesting* capability already declares `delegation_required` — today, exactly `ci-answer-display-intent` and `hyp-hypothesis-test-display-intent`. Every other `request_help` caller is completely unaffected; the existing two-step (candidates returned, requester independently calls `delegate_to_agent`) continues exactly as today. Extending this further platform-wide is explicitly out of scope — flagged as a real follow-on, not attempted here.

**Cross-reference note (not this session's scope):** two other live-found issues touch adjacent durable-resume machinery — `AA-150` (Owen's `qg-review-intent` parse failure on a repeat call) and `AA-151` (checkpoint/resume stall on `hyp-hypothesis-test-display-intent`, `hop_counter` never advancing across `continue` calls). Neither is caused by or fixed by this session's change (this session touches the `request_help` resolution step, before any checkpoint would occur on that hop) — noted for whichever session picks up `AA-151` next, per its own cross-reference request.

What changes is only whether a *second* agent (the original requester) gets an additional model turn to independently re-decide the same question. Removing that second turn does not remove reasoning from the decision — it removes a redundant re-litigation of a decision that was already reasoned, once, in the open, with its own logged `reasoning` field. This is categorically different from the previously-rejected `capability_slug → agent_id` deterministic lookup (`§19d`'s "Correction" note) — that alternative had **zero** LLM reasoning behind it; this one has exactly the same LLM reasoning step the platform already trusted before, just without asking a second, less-informed model call to grade it again. Scoped exclusively to `delegation_required` capabilities, where `AA-142`/`AA-148` already established there is no legitimate second judgment to make.

### Task 2 — `api/capabilities/execute.js`: extract `finalizeDelegation()` helper

The existing `delegate_to_agent` branch's `is_final === true` block (inside `runLoop()`, currently the block starting `if (turn.tool_input.is_final === true) { const finalPatterns = ... return finalResult; }`) becomes a shared, top-level function so Task 3 can reuse it without duplicating logic:

```js
// FEATURE: AA-152 -- extracted from the delegate_to_agent branch's is_final block so the new
// delegationRequired auto-resolve path (Task 3) reuses the exact same finalize-and-checkpoint
// logic instead of a second copy -- same "extract when a real second call site needs it"
// discipline checkpointAndReturn() was built under (AA-139).
async function finalizeDelegation({ delegateResult, targetAgentId, targetCapabilitySlug, targetIntentSlug, lastHelpSelection, job_id }) {
  const finalPatterns = Array.from(new Set([...(delegateResult.patterns_used || []), 'agent-delegation']));
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  const headers = getSupabaseHeaders(supabaseKey);
  const finalResult = buildFinalDelegationResult({
    delegateResult, targetAgentId, targetCapabilitySlug, targetIntentSlug,
    finalPatterns, displayAgentCard: await fetchAgentCard(targetAgentId, headers, supabaseUrl),
    lastHelpSelection,
  });
  if (job_id) {
    await patchDurableHopRow(job_id, { status: 'complete', result: finalResult });
  }
  return finalResult;
}
```

### Task 3 — `api/capabilities/execute.js`: auto-resolve terminal delegations for `delegation_required` capabilities

Inside the `request_help` branch, immediately after the existing `lastHelpSelection = {...}` assignment (and before the shared `conversationHistory = [...]; }` fallthrough at the bottom of the loop body), insert:

```js
// FEATURE: AA-152 -- when the REQUESTING capability declares delegationRequired, AA-142/AA-148
// already established there is no legitimate case where more of the requester's own judgment is
// needed after a hand-off -- this extends that one step further: no legitimate case where the
// requester needs a second model turn to re-choose WHO, either, once agent-selection-intent has
// already produced a real, reasoned recommendation. Skips straight to the same terminal-delegation
// path a manual delegate_to_agent(is_final:true) call would have taken. Scoped exclusively to
// delegationRequired capabilities (today: ci-answer-display-intent, hyp-hypothesis-test-display-
// intent) -- every other request_help caller is completely unaffected, falls through to the
// existing two-step behavior unchanged. Never a static agent/capability name: recommended_agent_id/
// recommended_capability_slug come from agent-selection-intent's own live reasoning, validated
// against its own candidates array below, never asserted directly (ARCHITECTURE.md §19d).
if (delegationRequired) {
  const rec = delegateResult?.content;
  const matchedCandidate = rec?.candidates?.find(
    c => c.agent_id === rec.recommended_agent_id && c.capability_slug === rec.recommended_capability_slug
  );
  if (!rec?.recommended_agent_id || !matchedCandidate) {
    // FEATURE: AA-152 -- fail loudly rather than silently falling through to a requester turn
    // that would just re-litigate what delegationRequired already says is resolved. Same "fail
    // safe, never fake" posture as AA-108/AA-126 -- a mismatched/missing recommendation here is a
    // genuine platform fault, not something to paper over.
    throw new Error(`request_help: delegationRequired capability's agent-selection-intent response had no valid recommended_agent_id matching a real candidate (capability_slug: ${capability_slug}/${intent_slug})`);
  }
  const delegateTaskContext = (task_context && typeof task_context === 'object')
    ? { ...task_context, delegation_task: turn.tool_input.task_description || turn.tool_input.skill_needed }
    : { delegation_task: turn.tool_input.task_description || turn.tool_input.skill_needed };
  const autoResolvedResult = await runCapability({
    capability_slug: rec.recommended_capability_slug,
    intent_slug: matchedCandidate.intent_slug || null,
    agent_id: rec.recommended_agent_id,
    task_context: delegateTaskContext,
    tenant_id, _hop_counter: hopCounter, _deadline: deadline,
  });
  if (autoResolvedResult.status === 'in_progress') {
    return checkpointAndReturn({
      job_id, tenant_id, capability_slug, intent_slug, agent_id, enriched, canRequestHelp, delegationRequired,
      task_context, conversationHistory, depth, delegationOccurred, lastHelpSelection,
    });
  }
  return await finalizeDelegation({
    delegateResult: autoResolvedResult, targetAgentId: rec.recommended_agent_id,
    targetCapabilitySlug: rec.recommended_capability_slug, targetIntentSlug: matchedCandidate.intent_slug || null,
    lastHelpSelection, job_id,
  });
}
```

**Why this design, not a bigger one:** reuses `finalizeDelegation()` (Task 2) and `checkpointAndReturn()` (existing, unchanged) exactly as the manual `delegate_to_agent` path does — the auto-resolve path is not a parallel implementation, it is the same terminal-delegation mechanism, entered one hop earlier. Zero new persistence, zero new error class beyond the one validation throw. Gated entirely on `delegationRequired`, already in scope as a `runLoop()` parameter — no new state threaded through.
