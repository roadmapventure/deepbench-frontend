## 2. CONTEXT

### The problem, in one sentence

Every executor result shape carries the `trace_id`/`span_id` of the execution it credits (§19p) —
except the `pending_confirmation` return (and the rare `depth_exceeded` return), so any caller
that terminates at the human-confirmation gate cannot know which trace produced its confirmation,
and the regression driver's `REPORT_JSON.trace_ids` silently omits exactly those legs.

### How it was found (measured 2026-07-31, `design-chi-96`, case 6, both runs)

The Forecast edit journey's `patch` and edit-`resolve` calls each ran a full
`data-analysis:data-patch-intent` chain (~80–100 s, 5 model calls apiece — traces `48bedc07…` and
`7756f6e2…` in run 1) that never appeared in the driver's report; only a time-window
`ai_activity_log` query found them. The wall-clock RCA initially read as a ~200 s idle gap.
Verified against fresh `origin/dev` (`d76cc79`, 2026-07-31): both bare literals unchanged.

### Root cause, verified in code

- `api/capabilities/execute.js` — the normal terminal path attaches identity
  (`finalResult = { …, trace_id, span_id }`, ~line 1127). The confirmation-gate return
  (`return { status: 'pending_confirmation', confirmation_id, … }`, ~line 1088) and its
  `durable_hops` result mirror (~line 1085) do not — nor do the two
  `return { status: 'depth_exceeded', … }` literals (~lines 1037, 1138). `trace_id`/`span_id` are
  in scope at the confirmation site (used at ~1057 `_trace_id: trace_id`); **verify** they are in
  scope at both `depth_exceeded` sites before touching those two — if either isn't, narrow to the
  confirmation pair and flag it in the report.
- `scripts/chi-true-regression.mjs` — **needs zero changes.** `call()` already pushes any
  top-level `unwrapped.trace_id` (~line 274), and `unwrapTerminal()`'s status-branch returns the
  body as-is, so the new fields flow into `ctx.trace_ids` automatically.

### Why this is additive-only

Consumers destructure known fields from these bodies (`confirmation_id`, `proposed_action`,
`critique`, …). Adding `trace_id`/`span_id` removes nothing and renames nothing — the CHI screen,
the resolve handlers, and the driver are all unaffected except that the driver now captures what
was always missing. The `durable_hops` mirror is stored JSON; additive fields are safe and make
the resume path (`resumeCapability()`'s already-terminal early return) serve identity too.
