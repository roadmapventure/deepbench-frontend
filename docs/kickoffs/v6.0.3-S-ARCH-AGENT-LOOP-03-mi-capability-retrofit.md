## 2. CONTEXT

`AA-82`'s original `FEATURES.md` wording treated all four capabilities as one retrofit. This design session walked each capability's handoff-shaped output field individually against `ARCHITECTURE.md` §19d's sniff test ("does this show real reasoning, or hardcoded routing dressed up as intelligence?") and found five distinct decision points, not one:

1. **`ci-routing-intent` (Marcus)** — `intent` classification. PASS — Marcus's own inference on whether a question needs specialist backup, conditional on his Behavior Skill Profile instructing him to attempt a direct sourced answer first (same two-layer judgment `needs_review` already uses on `ci-answer-intent`, §5.2).
2. **`intake-commit-intent` (Sam) — Reasoner leg of `route_to`.** Not a decision at all — Memory Consolidation fires deterministically on every committed Forecast/Correct (§5.10), no per-instance judgment to make. **Carved out as its own idea, flagged `AA-98` for `S-APPLE-05`** (a generic "the model itself flags whether this moment is worth consolidating" primitive, John's framing) rather than forced into this session's `request_help` shape. Out of scope here.
3. **`intake-commit-intent` (Sam) — Data Expert leg of `route_to`.** PASS — real per-call judgment on whether a correction disputes a specific existing Data Room chunk.
4. **`intake-failure-intent` (Sam)** — `recommend_escalate`/`suggested_research_request` stay exactly as designed (human-facing honest diagnosis, §5.9's "fail safe, never fake" principle, unchanged). **Separately, PASS on a distinct point:** Sam checking his own confidence in the diagnosis before presenting it to the director — real variance (an obvious gap needs no check, an ambiguous one might).
5. **`qg-review-intent` (Owen)** — `guardrail.result: block` → retry to Marcus. PASS, but **not via a new mechanism** — corrected mid-session after re-reading `request-receivable.js`'s `DELEGATE_TO_AGENT_TOOL` description in full (not just `execute.js`'s dispatch branches, see `CLAUDE-DESIGN.md`'s Delegation legitimacy bullet, updated this session): `delegate_to_agent` already permits dispatching to any legitimately-supplied candidate agent_id, and `request_help`'s returned list is only cited as *one example* source — Owen's own task_context (which agent produced the answer under review) is an equally legitimate source. No new harness code needed; Owen judges whether the failure is worth one retry, and if so calls the already-built `delegate_to_agent` directly with Marcus's `agent_id`.

**What ships this session — four `can_request_help: true` additions:**
- `ci-routing-intent` (Marcus / `channel-intelligence`)
- `intake-commit-intent` (Sam / `pipeline-triage`) — covers finding #3 only; the Reasoner leg (#2) is out of scope, see `AA-98`
- `intake-failure-intent` (Sam / `pipeline-triage`)
- `qg-review-intent` (Owen / `quality-gate`) — plus a `notes` field documenting that any future caller of `quality-gate` must pass the reviewed answer's `agent_id`/`capability_slug`/`intent_slug` into Owen's `task_context`, since `delegate_to_agent` requires a legitimately-supplied candidate and none exists yet (no live caller of any of these four capabilities exists today — confirmed via `grep` of `src/`, zero hits beyond `useAIActivity.js`'s `SERVICE_CATALOG` listing)

**Confirmed zero regression risk:** no Work-screen or Market Intelligence-screen caller reaches any of these four capabilities today (`S-MARKET-INTEL-01` still not built) — same backward-compatibility note `AA-82`'s original `FEATURES.md` entry already made.

  const res = await fetch(`${SUPABASE_URL}/rest/v1/skill_profiles?slug=eq.${slug}&select=slug,traits,notes`, { headers: HEADERS });
