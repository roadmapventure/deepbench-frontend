## 1. CONTEXT

**This is a re-scope, not a resume.** The original `v6.0.8` kickoff doc (`docs/kickoffs/v6.0.8-S-APPLE-04b-nadia-data-integrity-patch.md`) targeted a design that `AA-104` superseded: a single-writer model where every correction (`patch`/`supersede`/`restore`) was business fact, written only through Eleanor, costing 2 delegate round trips (4 of 5 hops) every time. `AA-104`'s resolution (`ARCHITECTURE.md` §19f, shipped via `S-ARCH-REASONING-LAYER-01a`/`01b`) recognized that most of Nadia's corrections are her own opinion, not fact — and gave opinion content a physical home (`the_reasoning`) that she writes herself, no Eleanor, no round trip.

**What carries over unchanged from `v6.0.8`:** `AA-103`, the generic accept hand-off (`on_accept_intent_slug` trait + `execute.js`'s `resolveAccept()`). A coding agent already applied this correctly before the session was parked — confirmed by direct diff read this design session, byte-identical to what's still needed. Task 1 below is verify-and-commit, not re-implement.

**What's new this session, replacing `v6.0.8`'s Tasks 2/3:**
- `data-patch-intent`'s output shape changes from `action: patch|supersede|restore|no_action` to `action: opinion|promote|no_action` (`APPLE-AGENT-1-v5-DESIGN.md` §5.6).
- **Gate model (design decision made this session, John):** every decision still goes through one human accept/reject step — `requires_human_confirmation: true` stays on `data-patch-intent`, unchanged, no harness change to `execute.js`/`db-assembly.js`. What accepting *does* differs by `action`: `opinion` records itself in `the_reasoning`, nothing else; `promote` records the same `the_reasoning` entry *and* delegates to Eleanor to rewrite `the_library`; `no_action`/reject do nothing (still produces an empty-approval card, same accepted quirk as the original design).
- A new handler, `api/_lib/handlers/reasoning-write.js`, dispatched via `format_contract.handler === 'reasoning-write'` — same registry pattern as `library-write.js`. This is what actually writes to `the_reasoning` on accept. Deferred here on purpose from `AA-107` (`S-ARCH-REASONING-LAYER-01b`), same precedent as `S-LIBRARIAN-04` building `library-write.js` alongside the capability that used it, not before.
- **Lineage linking (`the_library.promoted_from_reasoning_id` / `the_reasoning.promoted_to_library_id`) is explicitly out of scope this session** — deferred, documented (design decision, John, 2026-07-03). `promote` still archives the disputed chunk (`status: superseded`, never deleted) and inserts the new fact — just without the two lineage columns populated yet.
- The live Supabase rows for `data-patch-intent`/`data-patch-execute-intent` still carry the **old**, now-wrong schema (confirmed by direct query this design session) — Task 4 replaces their `traits`/`notes` in place (same slugs, same `capability_skill_profiles` links, no new rows needed there).

**Confirmed unaffected, needs no session action:** `data-escalate-intent`'s `can_request_help` removal (`v6.0.8` Task 3) is already correctly live (confirmed by direct query this design session) — nothing to redo.

**Hop-budget note, updated:** `opinion`/`no_action` now cost zero delegate hops (the actual fix). `promote` still costs 2 delegate round trips (4 of 5 hops) inside `data-patch-execute-intent` — same cost as the original design, just now the rare exception instead of the default outcome of every correction.

### Task 2 — new file `api/_lib/handlers/reasoning-write.js`

```js
// DeepBench v6.0.13 | api/_lib/handlers/reasoning-write.js | S-APPLE-04b re-scope -- Nadia's the_reasoning write handler
// FEATURE: AA-104/AA-107 (ARCHITECTURE.md §19f) -- dispatched generically via format_contract.handler
// === 'reasoning-write', same registry pattern as library-write.js. Self-write, no Eleanor: Nadia is
// the_reasoning's Content-Owner, not routed through an arbitrating owner's broker -- this file performs
// no agent-identity check of its own, same reasoning as library-write.js's comment -- the Skill Profile
// that sets handler: 'reasoning-write' (only data-patch-execute-intent does) is what scopes access.
// action: 'no_action' is a documented no-op -- nothing to record, same accepted-quirk shape as the
// pending_confirmation-with-nothing-to-approve behavior already accepted for this intent (S-APPLE-04b).

import { writeContent } from '../../../lib/search-harness.js';

export async function handle({ agent_id, tenant_id, content }) {
  const { action, content: reasoningContent, confidence, source_chunk_ids, source_question } = content || {};
  if (!action) throw new Error('reasoning-write handler: action required in structured output');

  if (action === 'no_action') {
    return { deliverable_id: null, entry_id: null, skipped: true };
  }

  if (!reasoningContent) throw new Error('reasoning-write handler: content required in structured output for action=' + action);

  const result = await writeContent({
    requestingAgentId: agent_id,
    store: 'the_reasoning',
    tenantId: tenant_id,
    content: reasoningContent,
    source_chunk_ids: Array.isArray(source_chunk_ids) ? source_chunk_ids : [],
    source_question: source_question || null,
    confidence: confidence || null,
  });

  if (!result.success) {
    throw new Error(`reasoning-write handler: writeContent failed -- ${result._access?.tier || 'unknown reason'}`);
  }

  return { deliverable_id: null, entry_id: result.entry?.id || null, handler_result: result };
}
```

**Deliberately no `data_room_tag` param passed to `writeContent()`.** Nadia's `agents.data_room_access` is `["apple-cso-data-room"]` (single entry, confirmed live this design session) — `lib/search-harness.js`'s `resolveTag()` resolves a single-data-room agent's tag automatically regardless of any requested tag. Passing one here would be a hardcoded value this handler doesn't need and can't verify.
