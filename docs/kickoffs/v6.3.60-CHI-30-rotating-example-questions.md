**New rotation mechanic (John's explicit design, confirmed this session):**
- Position 2 (the new "library" question) is **static** — always shown, never rotates.
- Positions 1, 3, 4, 5, 6, 7 (6 visible slots) draw randomly from a **10-question pool** = today's positions 1, 3–11.
- The 4 pool questions **not** picked in a given roll move to the **front of the drawer**, ahead of a **fixed 12-question tail** = today's positions 12–23 (never rotates, never reorders).
- **Correction caught during this design session, flagging explicitly:** the drawer is **always 16 questions** ("Browse 16 more"), not 12 — this holds in both the default and rotated states, since only 6 of the 10 pool questions are ever visible at once; the other 4 always sit in the drawer, whether chosen deterministically (default) or randomly (rotated).
- **Default vs. rotated, gated on the existing `WelcomeSplash.jsx` mechanism (no new storage key):** `WelcomeSplash.jsx` already sets `sessionStorage.setItem("db_splash_dismissed", "1")` the first time a user dismisses the splash in a tab session, and `sessionStorage` persists across a page refresh but resets when the tab/browser closes. This session reuses that same flag, read-only:
  - **Flag not yet set** (user's genuine first load this tab session, splash is showing) → deterministic default: slots 1,3–7 = pool items in their natural order (today's positions 1,3–11's first 6), drawer = pool's remaining 4 (in natural order) + the fixed 12-tail — i.e., pixel-identical to today's confirmed 23-question order, front to back.
  - **Flag already set** (any later refresh in that tab, or clicking Clear — Clear can only be reached after the splash was already dismissed) → random 6-of-10 draw for slots 1,3–7, remaining 4 pool items lead the drawer. Pure random each roll, repeats allowed, no history tracking.
- Confirmed via direct code read: `InteractColumn`'s empty-state block (`messages.length === 0`) is the single render site for both desktop and mobile (`MobileBody` reuses `InteractColumn`'s `bare` branch, no separate mobile JSX) — no mobile-parity gap, one code path covers both.
