## 2. CONTEXT

**`HAR-21` made the failure graceful. This session makes it correct.** After `HAR-21`, Store as Forecast completes even when Elena Cho — The Reasoner copies a truncated `(id: 0cecd001)` out of prose — the Claim Resolver drops the malformed id and the write lands with `source_chunk_ids: []`. **The fix is not to ask her more carefully. It is to stop asking.** Two instruction-only attempts have failed — `AGT-37`'s own v6.3.214 edit and `DAT-7`'s earlier `chunk_id` mitigation. The standing generalization is recorded in `docs/harvests/AGT-37.md`: **an id-shaped decoy defeats instruction-level guards; no third wording is to be attempted.** This session removes `source_chunk_ids` from her output contract entirely, so there is no model step left to get wrong.

**The ids already exist and are already in scope at the call site.** `MarketIntelligenceScreen.jsx:4198` destructures `citations` alongside `flaggedAnswer` from `hypFlow`; `:4204` passes `citations[0]` to Nadia Farouk — Data Expert as `disputed_chunk_id`. Elena Cho — The Reasoner's `task_context` at `:4212` receives prose only. Verified live shape in `ai_activity_log`: `ci-answer-intent` → `citations: ["6bef824b-c56e-487b-a976-cccdefe567c4"]` — full 36-character UUIDs, exactly what the AA-189 guard wants. Priya Nair — Forecast/Theory/Performance Expert's theory-test sections are `{text, citations}` objects (`CHI-65`) and `:4205` joins only the `.text` halves, discarding three more citation arrays.

**Why a new field rather than reusing `task_context` — the correction that defines this session.** The obvious move is to add the ids to `task_context`, which already flows most of the way. **That is wrong, and it is the trap this kickoff exists to avoid.** `task_context` is not a delivery channel, it is *prompt material*: `db-assembly.js` serializes every non-empty key into the agent's prompt — `HAR-06` on the `.goal` branch (~L548) and `AI-44`'s TASK DETAILS fallback (~L572). Elena Cho — The Reasoner's `task_context` carries no `goal`, so it takes the AI-44 branch and **every key lands in her prompt**. Putting a real chunk id there would render it in front of the one agent this entire ticket exists to keep away from ids. It would still function — she has no output slot for it and the handler prefers the caller's value — but it would hand `AGT-39`'s decoy problem a fresh source: a real id in her context is material she can write into her `content`, which becomes the *next* step's prose decoy, exactly as Nadia Farouk — Data Expert demonstrably already does. Hence `handler_context`: a sibling field that reaches the handler and never the model.

**Why the plumbing is two files.** Nothing carries a handler-facing field today. `sendRequest()` (`request-receivable.js` L577) accepts a fixed parameter list and dispatches handlers with a fixed field object (L782); `prompt_request` destructures to `{task_id, sections, system_prompt, format_contract, llm, enableWebSearch, intent_technical_services, debug}` with no back door. So `execute.js` must pass the new field and `request-receivable.js` must accept and forward it — one line each, plus the accept-path addition in Task 2.

**Harness-vs-service check.** Both harness files carry `handler_context` as an opaque envelope and never open it — no citation vocabulary, no agent id, no capability slug enters either. The only code that knows what a citation is remains `lib/claim-resolver.js` (the service) and its caller. `.claude/rules/capabilities-are-data.md` holds.

**What this establishes beyond `AGT-37`.** `handler_context` is a general harness capability: any write handler can now be handed facts the model must not see. That distinction — agent-facing context versus handler-facing facts — did not exist in the platform before this session, and its absence is what made the wrong design look obvious.

**Trust-boundary note, deliberate and flagged (John's walkthrough).** This makes `source_chunk_ids` caller-supplied, one line from `search-harness.js:141`'s `agent_id: requestingAgentId, // self-attributed -- never taken from caller-supplied params`. That precedent is about *identity*, where caller-supplied means impersonation. This is *provenance*, and both existing guards — the AA-189 UUID check and the cross-room check — still run on whatever arrives, so a caller cannot smuggle in a chunk from another data room. The screen is already trusted for exactly this on the same click (`disputed_chunk_id` to Nadia Farouk — Data Expert). Do not weaken either guard to make this work; if a supplied id is refused, that refusal is correct.
