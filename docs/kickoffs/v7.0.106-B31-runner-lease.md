## 2. CONTEXT

At 20:07:43Z cycle `4da5a7bd` inserted its open `runner_cycles` row. At ~20:08:00Z cycle
`e36d4379` ran step-0 assertion (2) — `SELECT id FROM runner_cycles WHERE ended_at IS NULL` —
and got **zero rows**. Both then picked the same top-of-queue item and both built `ADM-1 v1`.
`4da5a7bd` pushed first (`a7c66ad`, v7.0.104); `e36d4379`'s commit `5c425d5` never reached the
remote and was reset away, leaving `v7.0.103` a permanent gap in `dev_version_counter`
(atomic counters are never rolled back — that part is correct behaviour).

**Root cause, stated plainly:** a read cannot serialise against a concurrent write. Assertion
(2) was read-then-open with no lock, so any two cycles whose starts fall inside one another's
read window both see an empty ledger. Read-replica lag or query routing widens the window; it
does not create the bug. This cycle's collision was benign only because both cycles designed
the same thing.

The directive offered three fixes — (a) `pg_try_advisory_lock`, (b) a `runner_lease` singleton
row, (c) a post-pick uniqueness recheck — and recommended (b). **(b) is what ships.** (a) is
invisible: an advisory lock leaves no row to inspect, and a cloud session that dies drops the
lock silently with no record it ever held one. (c) fixes the symptom after both cycles have
already spent their build tokens.

## 6. DESIGN RULES

- **The gate is a single-row UPDATE.** Postgres serialises concurrent UPDATEs of one row: the
  second claimer blocks on the row lock, re-evaluates its `WHERE` after the first commits, and
  matches nothing. That is the whole mechanism.
- **`holder` is not a foreign key, deliberately.** The claim mints the cycle id with
  `gen_random_uuid()` inside the claiming UPDATE and step 1 inserts the cycle row with that id.
  Claim-then-bind inside a single statement does not work — Postgres silently drops a second
  UPDATE of the same row in the same statement, which would leave `holder` NULL and the lease
  looking free. Found while writing this cycle's own QA, before the runbook text was written.
- **A 45-minute TTL, not an indefinite hold.** Fail-closed must not mean fail-forever: a cloud
  session killed mid-cycle never releases. Longest real cycle to date is ~18 minutes against a
  3-hour cadence, so a stolen lease means the holder is dead, not slow. Steals are counted.
- **Release is holder-guarded** (`AND holder = '<own id>'`) so a stolen-from cycle cannot
  clobber its successor, and release happens on *every* exit path — ship, wall-stop, abort.
- **The lease is ledger state**, like `runner_cycles`: its own columns are the audit trail, so
  claim and release need no `runner_before_images` row. Every other write to it does.
- **Grants:** new table ⇒ `REVOKE ALL FROM anon, authenticated` in the creating migration, then
  prove both directions live (`.claude/rules/supabase-column-grants.md`).
