## CONTEXT

Live-reproduced 2026-07-07 (John's own MI screen test): a Q&A answer came back with an **empty card** — nothing but a "Formatted by Riley Torres" byline, no headline/body/citations. Traced via `ai_activity_log`: Marcus's `request_help` → Michelle's `agent-selection-intent` → Marcus's own `delegate_to_agent` chose **Riley Torres** (`capability_slug: html-display`, `intent_slug: null`) instead of Alex Reeves. Riley's `html-display-format` Skill Profile (confirmed via Supabase) has `traits.output_type: "html"` — she renders full semantic HTML documents, not the `headline`/`body`/`citations`/`confidence_tier` shape `MarketIntelligenceScreen.jsx` needs. Her output got spread onto the result object exactly like Alex's normally does, but none of the expected fields exist on it — hence a blank card.

**Not a new regression** — confirmed via full history query, Riley has been picked this same way 3 times before, as far back as 2026-07-06 19:51, well before any of today's other fixes.

**Root cause: Michelle's roster context has zero visibility into format-output shape.** Read `lib/project-manager.js` directly: `fetchRoster()` already fetches each capability's `intent_slugs` (added by `AA-108`, for exactly this class of problem — giving the model real declared data instead of letting it guess/invent) but never fetches anything about a capability's **Format** Skill Profile or its declared `output_type`. `ci-answer-display-intent`'s own method text already explicitly says "not a full HTML document, not a PDF" — Marcus had the right instruction but no way to act on it, because Michelle's candidate list never told him Riley produces HTML. He wasn't ignoring the rule; he was choosing blind on that dimension.

**Fix, same shape as `AA-108`:** extend `fetchRoster()`/`rosterToContext()` to also fetch each capability's linked Format-type Skill Profile(s) (`skill_profiles` where `skill_type_slug = 'format'`, joined via the same `capability_skill_profiles` table already used for `intent_slugs`) and surface their `output_type` (`traits.output_type`, defaulting to `'json'` exactly like `execute.js`'s `fetchFormatOverride()` already does) as `format_output_types` on each capability in the roster context — plus one added sentence in the context's own instructional header telling Michelle to call out a non-`json` shape in that candidate's `fit_summary`.

**No hardcoding — confirmed against the delegation-legitimacy sniff test (`ARCHITECTURE.md` §19d):** this never names a specific `agent_id` or `capability_slug` anywhere in code. It's the exact same declarative-data pattern `AA-108` already established for `intent_slugs` — Michelle still does her own reasoning over real, declared facts about every candidate; the only change is that one more true fact (their format skill's output shape) is now visible to her, the same way `intent_slugs` made intent-fabrication impossible by giving her something real to copy instead of guess. Marcus still makes the final `delegate_to_agent` choice himself, now with the actual information his own existing instructions need to act on.

```js
function rosterToContext(roster) {
  const lines = roster.map(a => {
    const caps = a.capabilities.length
      ? a.capabilities.map(c => {
          const intents = c.intent_slugs.length ? `, intents: [${c.intent_slugs.join(', ')}]` : '';
          const formats = c.format_output_types.length ? `, format_output_types: [${c.format_output_types.join(', ')}]` : '';
          return `${c.capability_slug}${c.description ? ` (${c.description})` : ''}${intents}${formats}`;
        }).join('; ')
      : 'no assigned capability';
    return `--- ${a.agent_id} — ${a.name}, ${a.role} ---\ncapabilities: ${caps}\nskill_score: ${a.skill_score ?? 'n/a'}, situational_awareness: ${a.situational_awareness ?? 'n/a'}, rating: ${a.rating ?? 'n/a'}, activity_count: ${a.activity_count ?? 'n/a'}\nactive: ${a.is_active}`;
  });
  return `PLATFORM AGENT ROSTER (${roster.length} agents). Use agent_id exactly as shown when selecting a candidate. When a candidate's capability lists intents, intent_slug MUST be copied exactly from that list -- never invented. If a capability has no listed intents, or none clearly matches, return intent_slug: null. When a capability's format_output_types includes anything other than "json" (e.g. html, pdf), call that out explicitly in that candidate's fit_summary -- the requesting agent needs to know a candidate produces a different document shape than an ordinary structured response before choosing them:\n\n${lines.join('\n\n')}`;
}
```
