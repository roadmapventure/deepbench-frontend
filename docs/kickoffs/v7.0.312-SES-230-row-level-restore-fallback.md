## 2. CONTEXT — what John actually chose, and what he chose against

`SES-230` was filed as a **format decision**: three candidate representations for a jsonb scalar
`null` (A sentinel on the wire, B restore-side coercion from `_backup_inventory.jsonb_notnull_cols`,
C edit the two production rows). The ticket recommended **B**. John's session measured B
unimplementable and he picked **route 1** instead, which is a different shape of answer and a
better one: **stop trying to make every row survive, and stop letting one row cost the other 311.**

His words, from the directive, are the spec:

> add row-level fallback — when a batch POST fails, retry the batch row-by-row, load every loadable
> row, and emit a named report of each row that could not load (table, pk, SQLSTATE, reason); exit
> non-zero only per the runbook's existing contract, never silently drop.

That is format-agnostic. It fixes the *cost* of an unrepresentable row without picking a wire
format for it — so options A/B/C stay open, and any later format fix reduces the report rather than
being blocked behind it.

## 4. THE DESIGN DECISION THIS SHIP OWNS — where the fallback fires

The directive says *"when a batch POST fails, retry the batch row-by-row."* Read literally, that
means split on the **first** batch failure. **That literal reading is wrong here, and the reason is
in the file already:** the restore is a *multi-pass* loop precisely because foreign keys mean a
table can fail on pass 1 and succeed on pass 3 with nothing wrong with any row (lines 111–113). A
first-failure split would take a table whose only problem is ordering and issue one HTTP request
per row — every one of them doomed — before the pass that would have loaded it in one shot.

**So the fallback fires after the batch loop has finished with a table, not during it.** By then
`pending` holds exactly the tables no batch pass could load, on both exit paths (the stall break and
pass-6 exhaustion), which is the population the directive is about. FK ordering keeps its full
chance first; row-level splitting is the last resort it was asked to be.

**The second decision, and it is the one that makes the fallback usable on the real population.**
`ai_activity_log` is 34,761 rows and fails for a *table-wide* reason (generated columns, `428C9` —
`SES-220`'s defect, not this one). Splitting it row-by-row is 34,761 requests that all fail. So:
while splitting, if the first **25** individually-attempted rows all fail with **one** SQLSTATE and
none succeeds, the failure is declared **table-wide** and the table is not split further — reported
as one line naming the table, the unloaded row count, the SQLSTATE and the server's own reason.
That is not a silent drop: it names strictly more than today's output does. It is the difference
between a fallback that runs in seconds on the live sets and one nobody would leave enabled.

## 5. EXIT CODE — the existing contract, at row granularity

`restore-from-backup.md` §5b states the contract: *"a genuinely stuck table … is named at the end
and exits non-zero."* This ship keeps that sentence true and makes it finer-grained:

- Any row (or table-wide block) that could not load → **named in the report, exit non-zero.**
- Every row rescued by the fallback → the table is no longer stuck → **exit 0**, including the case
  where the batch loop had already set exit 1 on a stall. That is the whole point: on the live
  `pending_confirmations` population, a run that exits 1 having loaded 0 of 312 becomes a run that
  exits 1 having loaded **310 of 312 and named the 2**.

No new failure condition is invented, per the directive's *"only per the runbook's existing
contract."*

  what changes is that it says so in one honest line instead of taking a table's worth of requests
  to say it.

  refresh needs his word each time, and this ship does not have it and does not need it.
