## The two design questions the ticket left to this cycle

The ticket names them and refuses to answer them: *"a stable finding SIGNATURE so a re-run updates
the existing row instead of filing a duplicate"*, and *"aggregation policy is part of this ticket's
design, not an afterthought."*

### 1. The signature is the CHECK ID — and the reason is that `detail` is not stable

A finding is `{check, severity, detail}`. Hashing `detail` is the obvious move and it is wrong,
measured rather than argued: check 6's detail reads *"docs/STANDARDS.md is 52.0 KB, over the ~34 KB
baseline"* — the KB figure moves on every ship — and check 3d's 18 findings differ only by which
ticket id and char count they name. A detail hash therefore files a **new ticket on every run**,
which is precisely the defect this ticket exists to close, one level down.

Digit-collapsing the detail (`heal-engine.js`'s `normalizeErrorClass`) fixes the numbers and not the
subject: check 3d would still shatter into 18 signatures keyed on 18 ticket ids.

So the signature is `tripwire|check|<id>`, hashed sha256/12 in heal-engine's own format so the same
substring dedup works unchanged. **The hash adds no entropy over the check id and this file says so
rather than implying otherwise** — it is a token format inherited so the two engines dedup alike,
not a derivation.

### 2. Aggregation is ONE ROW PER CHECK CLASS, and that is the same decision as (1)

The ticket's own worked example is the constraint: *"18 of today's 33 FLAGs are check 3d over-cap
descriptions, one per ticket, so filing them one-for-one would bury the board rather than surface
it."* Within one check every finding shares a rule and a fix shape — clearing check 3d is one job
(trim descriptions into `docs/harvests/`), not eighteen. The member list lives in the description,
so the row stays accurate as members come and go while the signature does not move.

There is no threshold to tune, which is deliberate: heal-engine needs one because a single failed
hop is noise, whereas a tripwire FLAG is already a rule the platform wrote down and broke.

## What is eligible, and the two exclusions stated as decisions

- **`FLAG` only. `WARN` never files.** Read the live WARNs: check 3c *"these are later-tier rows
  (compliant, nothing to do)"*, 3e *"not new drift — expected until it lands"*, 14 *"HISTORICAL
  kickoffs predating this lint — a migration backlog, not new drift"*. The script itself classifies
  these as known and deferred. A ticket for each is board noise for work already decided.
- **Gating checks never file** — `GATING_CHECKS` = {9, 10, 11} at FLAG, read from the module rather

  unnoticed is the entire problem this ticket solves. Filing a ticket for a red build adds a row
  nobody needed. The set is imported, so if `SES-199`'s gating policy widens, this exclusion widens
  with it and cannot drift.

## Boundary: filing is not fixing

Rows land `status='open'`, `tier='next'`, `type='Tooling'`, `priority_class='P10 - Tooling'`,
`source_file='tripwire-to-backlog'`, and ride the normal queue through the full ceremony later,
exactly as heal tickets do. `tier='next'` rather than heal's `now`: doc drift is not user-blocking,
and putting it in `now` would push it ahead of John's named drain members.
`ck_backlog_type_when_promoted` rejects a blank `type` on a `next` row, so `type` is set — read off
the live table (`Tooling`, 144 rows), not guessed.

Every filing is stamped `size_stamp` / `gate_count` at filing time (John, directive `db84b784`):
`gate_count` **0** — a doc-drift fix crosses no external gate — and `size_stamp` `S` at ≤3 members,
`M` above, since a check with eighteen members is not a one-shape one-cycle fix.

**Ids are never minted here.** `--backlog-ids` is required with `--apply`, claimed by the cycle as
one contiguous `feature_id_counter` block (`CLAUDE.md`; `SES-18` is the collision that rule is
written from). Prefix `SES` — these are session-hygiene tickets and the family already exists, so
no new prefix and nothing for `check-new-id-prefixes.js` to flag.

**Before-image first, `row_data = NULL`** — the INSERT convention `SES-89` introduced: a Reverse of
a filing is a DELETE of that pk. Its success is what authorises the ticket insert (§19v).
