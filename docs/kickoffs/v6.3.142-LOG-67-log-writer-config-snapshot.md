## 2. CONTEXT

**What this is, plainly:** every AI call writes a row to `ai_activity_log`. Part of that row's "signature" (the data that later decodes which AI pattern the call used) is currently *re-derived from live config at read time* — so when an agent's config changes, old rows silently start describing today's setup instead of what actually ran. That drift is the root of the false-`rag` labels (`LOG-42`/`53`/`59`). LOG-67 freezes the **config-half** of the signature onto the row **at write time**, so the row can never drift.

**This is settled architecture, not new design.** The runtime signature model is `ARCHITECTURE.md §19k` (discovery `design-log-38-0724`), and two POCs already de-risked it:
- `LOG-64` proved the signature→pattern join live on row `19329` and **locked the field order** (§19k lines 1446–1468).
- `LOG-65` ran the full anomaly set through it, added `model_modality` (#8), and settled criteria shape.

LOG-67 is the **Log Writer** service (§19k table, Layer A): it snapshots the config-half into `ai_activity_log.call_facts` at write time. `LOG-37` already snapshots the **fact-half** into the same `call_facts` column via `buildCallFacts()`; LOG-67 is the second, additive half of that same unified capture — **not a parallel mechanism**.

**The config-half** (§19k "The signature"): the assembled `knowledge` / `intent` / `format` skill slugs (identity + behavior **stripped** — agent-agnostic), their `traits` (`source` / `schema` / `intent_allowlist`), the `capability_slug`, and `execution_type`.

**Three findings from the design session that shape the build (all verified live this session against project `rallojeqnkgtxgsdsnqm`):**

1. **The fired-intent scoping LOG-64 flagged as a LOG-67 requirement is ALREADY implemented.** `db-assembly.js`'s existing intent filter (`:412–428`, the S-APPLE-02b / AA-108 / AA-188 logic) reduces `skillProfiles` to exactly the fired-intent-scoped set — sibling intents are already dropped. Verified live: on `project-manager` with `intent_slug='agent-selection-intent'`, the sibling `work-order-decomposition` is filtered out, so the config-half snapshot taken *after* that filter inherits the correct scoping for free. **No new WHERE clause needed** — the snapshot just has to happen at the right point (after line 428, and *before* the enrichment merge at 430).

2. **`model_modality` (#8) is OUT OF SCOPE for LOG-67.** `LOG-65` §7 nominally handed it here, but §19k §3 is explicit that it is a **read-time derivation** from the existing `ai_activity_log.model` column — *not captured, not stored in `call_facts`*. Storing it would duplicate a derivation of a frozen column. It belongs to the **Log Displayer** (`LOG-38`). LOG-67 writes nothing for it. (Flagged to John in design; confirmed.)

3. **The "ordered projection" (§19k caveat b) is satisfied without a redundant stored copy.** `assembled_skill_slugs` is stored as an **ordered jsonb array** (k→i→f, gaps-removed) — jsonb arrays *do* preserve order (only jsonb object *keys* are unordered, which is the trap the caveat warns about). The signature's *field-level* canonical order is a fixed constant the Displayer applies at read time; we do **not** store a second ordered copy of the whole signature. (Decided in design; correctness rationale: same "don't store a derivation" principle that keeps `model_modality` out.)

**Verified config-half on the POC's real row** (`project-manager` / `agent-selection-intent`, live query this session) — the build must reproduce exactly this:
`assembled_skill_slugs = [capability-registry-knowledge, pm-roster-knowledge, agent-selection-intent]` (sibling `work-order-decomposition` absent; `capability-assignment` + `planning-behavior` stripped as `behavior`), `traits.source = 'roster'` (from `pm-roster-knowledge`), `traits.schema` present (from `agent-selection-intent`), `capability_slug = 'project-manager'`, `execution_type = 'ai'`.

## 5. TASKS

> **The stored shape (the contract every task shares).** The config-half is merged into the *same* `call_facts` jsonb object the fact-half already writes. Canonical shape:
> ```jsonc
> {
>   // fact-half (LOG-37, unchanged): tool_calls, retrieved_chunk_ids, retrieval_method, gated_subroutine_fired
>   "assembled_skill_slugs": ["capability-registry-knowledge","pm-roster-knowledge","agent-selection-intent"], // ordered k→i→f, gaps-removed, identity/behavior stripped, intent = fired only
>   "capability_slug": "project-manager",
>   "traits": { "source": ["roster"], "schema": true, "intent_allowlist": ["…"] },  // each key omitted when empty; whole `traits` omitted when all empty
>   "execution_type": "ai"
> }
> ```
> **Omission posture matches the fact-half exactly:** a key whose value is empty is *omitted entirely* (so "no source declared" stays distinguishable from "not captured"). If the whole config-half is empty (e.g. no `capability_slug`), `signature_config` is `null`. These are top-level keys of `call_facts` (LOG-66's `criteria` will target them directly), NOT a nested `signature_config` sub-object inside `call_facts`.

### Task 1 — `api/prompt/db-assembly.js`: build the config-half + shared merge helper

**1a. Two new exported pure functions** (place near the top-level helpers, e.g. after `buildProfileNames`/before `assemblePrompt`):

```js
// FEATURE: LOG-67 -- ARCHITECTURE.md §19k Log Writer, config-half. Projects the assembled skill
// set into the agent-agnostic config-half of the runtime signature. identity/behavior stripped
// (agent-agnostic, §19k rule 2); knowledge/intent/format only (rule 3). Ordered k→i→f, gaps
// removed -- the ordered jsonb array IS the "ordered projection" §19k caveat (b) requires (jsonb
// arrays preserve order; only object keys don't). Intent-type profiles arrive already scoped to
// the fired intent by assemblePrompt()'s existing S-APPLE-02b/AA-108 filter -- this function does
// not re-scope, it just projects what it's given (and includes only k/i/f, so a stray sibling
// intent could never enter anyway). Empty keys omitted; returns null when nothing to record.
const SIGNATURE_SKILL_TYPE_ORDER = ['knowledge', 'intent', 'format'];

export function buildSignatureConfig(skillProfiles = [], { capability_slug = null, execution_type = null } = {}) {
  const kept = (skillProfiles || []).filter(sp => SIGNATURE_SKILL_TYPE_ORDER.includes(sp.skill_type_slug));
  const ordered = [...kept].sort((a, b) =>
    (SIGNATURE_SKILL_TYPE_ORDER.indexOf(a.skill_type_slug) - SIGNATURE_SKILL_TYPE_ORDER.indexOf(b.skill_type_slug))
    || ((a.display_order ?? 0) - (b.display_order ?? 0)));

  const cfg = {};
  const slugs = ordered.map(sp => sp.slug).filter(Boolean);
  if (slugs.length) cfg.assembled_skill_slugs = slugs;
  if (capability_slug) cfg.capability_slug = capability_slug;

  const sources = [...new Set(ordered.map(sp => sp.traits?.source).filter(Boolean))];
  const allowlists = [...new Set(ordered.flatMap(sp => Array.isArray(sp.traits?.intent_allowlist) ? sp.traits.intent_allowlist : []).filter(Boolean))];
  const hasSchema = ordered.some(sp => sp.traits?.schema != null);
  const traits = {};
  if (sources.length) traits.source = sources;
  if (hasSchema) traits.schema = true;
  if (allowlists.length) traits.intent_allowlist = allowlists;
  if (Object.keys(traits).length) cfg.traits = traits;

  if (execution_type) cfg.execution_type = execution_type;
  return Object.keys(cfg).length ? cfg : null;
}

// FEATURE: LOG-67 -- merges the fact-half (buildCallFacts / logAgentTurn inline) with the
// config-half (buildSignatureConfig) into one call_facts object. Same "null when empty" contract
// logActivity() already relies on: {} or null both write SQL NULL. Config-half keys are disjoint
// from fact-half keys, so a flat spread is safe -- no key can collide.
export function mergeCallFacts(factHalf, configHalf) {
  const merged = { ...(factHalf || {}), ...(configHalf || {}) };
  return Object.keys(merged).length ? merged : null;
}
```
