## The ask, and whose it is

John's ruling, 2026-08-22, in his own words: **"what if I reject the proposal?"** A ticket the
runner has proposed for removal is a ticket **awaiting John's verdict** — and until he gives it,
it is still a live ticket. Today it is stripped of its queue number the instant the proposal is
filed, which means it vanishes from every ranked view he has: "Next up", the "Next 3" line, the
`now`-tier census, the snapshot's ordering. If he then taps **Reverse** ("no, keep it"), the
ticket has to be re-inserted from nowhere and lands wherever the renumber happens to put it —
its earned position is gone.

That is an **asymmetry with `needs-john`**, and the asymmetry is the bug. Both are tickets
parked on John's verdict. One keeps its number and is merely skipped; the other is deleted from
the standings. Nothing ever justified the difference.

## The change

**One function, three predicates.** `public.recompute_backlog_queue()` mentions
`'removal proposed'` in exactly three places — the ineligible-clear `WHERE`, the `v_total` count,
and the `eligible` CTE. All three become `status NOT IN ('done','removed')`.

Everything else in the function is left byte-for-byte alone. In particular:

- **The five documented ordering traps are preserved verbatim** — numeric class extract
  (`substring(priority_class FROM 'P([0-9]+)')::int`, never a lexical sort), suffix tolerance,
  the `(Beta-gate|Post-beta)` declaration regex (never `ILIKE '%beta%'`), `filed_at`-before-
  `created_at` recency, and the `id` primary-key tie-break that `SES-86` phase 2 paid for.
- **The pin-clear stays `status IN ('done','removed')`** — it already was. A removal-proposed
  ticket now correctly keeps its pin as well as its number, which is the same rule, applied
  consistently for the first time.

## The half that is NOT optional, and would have shipped a live hazard without it

The migration alone makes `CHI-89` **selectable**. Step 5's read is
`WHERE queue IS NOT NULL AND (claim expired)` ORDER BY queue — it does **not** filter on status.
So the moment a removal-proposed ticket has a number, the next cycle can pick and build a ticket
whose premise the runner has already argued is **dead**, while John's verdict is still pending.

The ticket anticipates this and names the fix: *"selection skips removal-proposed procedurally —
status is already in the step-5 SELECT — dropping to next per B24, same pattern as needs-john."*
`status` is indeed already a projected column of that query. So the procedural skip ships **in
the same commit as the migration**, not in a later one. `SES-114` (queue 3) generalises the skip
across `design_status` as well; this ship covers the one case it opens.

## QA bar — what would fail if the change did nothing

- **Negative control, run FIRST (the `v7.0.130` pattern).** `CHI-89.queue` is `NULL` and 558
  tickets are numbered — recorded above, before the migration. A no-op change leaves both.
- **Discriminating expectation, computed by a query that never calls the function.** The same
  seven `ORDER BY` clauses, run as a standalone `row_number()` over the new eligible set, put
  `CHI-89` at slot **23** — not 559. So an implementation that merely *appended* the ticket, or
  gave it *some* number, fails this test while passing a completeness check.
- **Position held through a recompute** (the ticket's own named bar): run the recompute twice;
  `CHI-89` keeps slot 23 and the second run returns **0** rows moved.
- **Ordering integrity:** 0 tier inversions and 0 class inversions across all 559 numbered rows,
  and `1..559` with no gaps and no duplicates.
- **Relative order of the other 558 is unchanged** — every ticket that was above `CHI-89` stays
  above it, every ticket below stays below, shifted by exactly +1 from slot 23 down.
- Build green; regression suite green; before-image written for every Supabase write.
