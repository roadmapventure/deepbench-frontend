## 2. CONTEXT

John's live screenshot (Channel Sales Intelligence screen, 2026-07-16): he asked a question, it finished (hops numbered up through the low single digits), he clicked **Clear**, then asked a second question — the Agent Routing panel (Column 3) kept every hop from the first question and the new hops just kept appending on top with no visual break, reading as one continuous, unlabeled sequence.

**Confirmed by reading the code (not assumed):**
- `onClear()` (~L2175) resets `messages`/`hypFlow`/`qaEvidence`/`workingStatus` but never touches `pipelineEvents` — the state `AuditColumn`'s "Agent Routing" drawer renders from (`groupEventsIntoTurns()`). Clear does not reset the one column John was actually looking at.
- `pendingDelegationsRef` (~L2198, `useRef(new Map())`) also survives Clear — its keys are `awaitingAgentId` values used by `logEvent()`'s replace-in-place check (MI-52). A stale pending marker left over from an abandoned chain could mis-target a future event's replace-in-place splice once ids restart from 0 post-Clear.
- Hop numbering itself is **not** broken — `groupEventsIntoTurns()` (~L709) renumbers fresh from the full `pipelineEvents` array every render (`turnNumber: total - i`), so a second question's hops already continue incrementing correctly today. The only real gap is **no visual marker** for where one question ends and the next begins when the user doesn't hit Clear in between.
- **Separately, found while scoping this:** `onClear()` has no interlock with an in-flight request. `submit()`'s `loading` flag blocks a *second* chat submission while one is running, but does nothing to the *first* one if Clear fires mid-flight — the in-flight `await` chain keeps running, and when it eventually resolves, its `setMessages`/`setQaEvidence`/`setHypFlow`/`logEvent` calls land anyway, silently repopulating a screen the user just cleared. Same gap exists for `enterHypothesisFlow()`, `onSelectHypothesis()`, `onCommit()`, and `onResolveConfirmation()` — none of them check whether Clear happened after they started.

**Design walkthrough with John, 2026-07-16 — scope confirmed:**
1. `onClear()` also resets `pipelineEvents`/`pendingDelegationsRef`, and establishes a cancellation signal every in-flight call can check.
2. That signal gates a shared stale-response guard: an in-flight request whose Clear fired mid-way stops making further calls in its own chain and never touches state once it (partially) resolves. **Scoped to the frontend only** — confirmed live by reading the code that every continuation hop (`resolveInProgress()`'s `{action:"continue"}` loop) is a separate client-issued `fetch()`, so a client-side guard is sufficient to stop the *client* from continuing or displaying a stale result. It does **not** kill the one hop already executing server-side at the instant Clear is pressed — that would need a real change to `api/capabilities/execute.js` (harness-level, touches the shared execution path every capability goes through, not MI-specific). Logged separately as `HAR-03` (`docs/FEATURES.md`), deliberately not folded into this session.
3. A line + timestamp divider renders in the Agent Routing drawer above the first hop of a new question, whenever that question is asked without an intervening Clear (Clear itself already wipes the whole panel per Task 1 — nothing to divide there).

**Explicitly NOT in this session:** killing the one server-side hop already in flight at the instant of Clear (`HAR-03`, separate harness-level session) — see Task 2's design note on why a frontend guard alone is the correct, sufficient scope for this session's stated goal.

### Task 2 — Stale-generation guard, threaded through every existing async call chain

**Design note (why frontend-only is correct and sufficient here):** every multi-step chain in this file — `resolveInProgress()`'s `{action:"continue"}` polling loop, and the multi-`callCapability()` sequences in `runQaWithQualityGate()`/`runHypothesisTest()`/`onCommit()` — is driven entirely by the client awaiting one `fetch()` at a time and deciding whether to issue the next one. Nothing server-side is a long-running stream the client merely listens to. So a client-side check before each `fetch()` genuinely stops the chain from continuing, and a check before each `setState`/`logEvent` genuinely stops a result from ever being displayed. The one thing this can't do — abort the single hop already executing on the server at the instant Clear fires — is `HAR-03` (Context, above), a real but separately-scoped gap.

**Mechanism:** every function in the call graph below gains an `isStale` parameter (a zero-arg predicate, default `() => false` for safety), threaded one level deeper each time, checked immediately after every `await` that reaches the network — before any subsequent `onEvent`/`logEvent`/state mutation or further call:

- `resolveInProgress(result, onProgress = null, isStale = () => false)` (~L781) — check inside the `while` loop, before firing the next `continue` fetch:
  ```jsx
  while (result.status === "in_progress") {
    if (isStale()) return result; // FEATURE: CHI-04 — Clear fired mid-chain; caller already bails on this via its own isStale() check
    if (++iterations > MAX_CONTINUE_ITERATIONS) { /* unchanged */ }
    ...
  }
  ```
- `callCapability({ ..., onProgress = null, isStale = () => false })` (~L798) — pass `isStale` into its `resolveInProgress()` call: `await resolveInProgress(first, onProgress, isStale)`. No other change.
- `resolveConfirmation({ ..., onProgress = null, isStale = () => false })` (~L823) — same, pass into its own `resolveInProgress()` call.
- `runIntentPipeline(message, conversationContext, onEvent, setStatus, onProgress, isStale = () => false)` (~L955) — pass `isStale` into its `callCapability()` call and into `runQaWithQualityGate(...)`; check right after the routing call resolves, before `onEvent(...)`:
  ```jsx

  if (isStale()) return { kind: "non_qa", text: "" }; // FEATURE: CHI-04 — discarded by submit()'s own isStale() check regardless; value here is never rendered
  onEvent({ type: "intent_routing", ... });
  ```

- `runQaWithQualityGate(message, conversationContext, onEvent, setStatus, onProgress, isStale = () => false)` (~L841) — pass `isStale` into all 3 of its `callCapability()` calls (`qa`, `gate`, `display`); check after each, before using its result:
  ```jsx

  if (isStale()) return qa; // FEATURE: CHI-04 — stop before Owen's quality-gate hop
  onEvent({ type: "qa_answer", ... });
  ...
  const gate = await callCapability({ ..., onProgress, isStale });
  if (isStale()) return gate; // FEATURE: CHI-04 — stop before the display hand-off hop
  ...
  const display = await callCapability({ ..., onProgress, isStale });
  ```

- `runHypothesisTest({ ..., isStale = () => false })` (~L995) — pass into both of its `callCapability()` calls (analysis + display); check after the first, before proceeding to the second (mirrors `runQaWithQualityGate`'s pattern — read the full existing body before editing, it is not shown in full above).

### Task 3 — Question-boundary divider in the Agent Routing drawer

`groupEventsIntoTurns()` (~L709) gains a special case for a marker event, and stops counting/numbering it as a real turn:
```jsx
function groupEventsIntoTurns(ordered) {
  const turns = [];
  for (const evt of ordered) {
    const last = turns[turns.length - 1];
    // FEATURE: CHI-04 — a question-boundary marker always starts its own entry (never merges into
    // an adjacent turn regardless of agentId) and is excluded from hop numbering below — it's a
    // visual divider, not a real agent turn.
    if (evt.type === "question_boundary") {
      turns.push({ agentId: evt.agentId, events: [evt], isBoundary: true });
      continue;
    }
    if (last && !last.isBoundary && last.agentId === evt.agentId) {
      last.events.push(evt);
    } else {
      turns.push({ agentId: evt.agentId, events: [evt] });
    }
  }
  const total = turns.filter(t => !t.isBoundary).length;
  let seen = 0;
  return turns.map(t => {
    if (t.isBoundary) return t;
    seen += 1;
    return { ...t, turnNumber: total - (seen - 1) };
  });
}
```
(Confirmed safe: `pipelineEvents`/`events` has exactly one consumer, `AuditColumn`'s "Agent Routing" drawer — the other 4 drawers, `AuditDrawersBody`, take only `agents`/`agentActivity`, never raw events. No other render path is affected by a foreign event shape.)

```js
function assert(desc, cond) {

function makeGeneration() {
  let gen = 0;

const my = g.snapshot();
```
