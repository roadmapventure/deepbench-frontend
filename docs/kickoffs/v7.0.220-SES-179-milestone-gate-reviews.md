- `docs/SELFBUILD-CHARTER.md` names `SES-179` gate reviews in **nine** places as a mechanism the

- **Two milestone drains have already retired ungated.** `runner_directives` holds

## What ships

Two repo files and one additive migration. One item, ≤3 files, 4 tasks — inside the caps.

### 1. Migration `ses179_runner_items_epic_id`

`ALTER TABLE public.runner_items ADD COLUMN epic_id uuid REFERENCES public.epics(id)` — nullable,
additive, no backfill, nothing destructive.

**Why a column and not a string match.** The sweep's whole job is to ask *"has this epic been
gate-reviewed?"*, and the only alternative was matching a display string in `title` /
`display_ref`. That is precisely the defect `SES-116` (`v7.0.174`) shipped a `CHECK` constraint to
end: a display string in a position that answers a key question mis-joins silently. The column's
contract, written into the migration comment so it travels with the schema: **`epic_id` is set on
gate-review cards and on nothing else**, which is what makes `ri.epic_id = e.id` a complete test
with no marker text to drift.

### 2. `docs/runbooks/gate-review.md` (new) — the procedure

The card, the two lenses, the three mandatory directions, the burndown query, and the four
properties that must not be re-derived. Cited from `runner-cycle.md`, never restated there — the
same anti-drift convention `SES-124`/`SES-188` used after step 5 and step 7 drifted before
`v7.0.114`.

### 3. `docs/runbooks/runner-cycle.md` — new step 8d, the trigger

A Phase-3 sweep beside 8b (heal) and 8c (revalidation), because it has exactly their shape:
idempotent, evidence-keyed, never preempting the build.

**The trigger is a sweep over evidence, not a branch on a return value — and that choice is the
ticket's one real design decision.** The obvious implementation catches `drain_epic_next()`
returning `retired` at the call site. It is wrong twice over:

- `drain_epic_next()` has **two** call sites (step 5 and step 9's tail Gate B — `SES-139`), and
  since `SES-189` one call may retire **more than one** directive while returning the *last* one's
  ids. A call-site branch therefore misses retirements by construction.
- It could never have caught M0 and M1, which retired before this step existed. A sweep asks the
  standing question — *is there a retired drain whose epic has no gate-review card?* — so a
  retirement observed by anyone, at any time, is still caught.

Bounded at **one review per cycle** (`ORDER BY d.created_at LIMIT 1`), the same self-limiting shape
as step 4b's invention pass. Consequence stated rather than discovered: the next cycle to run
step 8d files M0's review, the one after that M1's, and then the sweep goes quiet until M2 retires.

`status='cancelled'` is deliberately **excluded** from the trigger. A cancelled drain is John
withdrawing a standing order (`b74009ea`, the Automation epic, untick), not a milestone finishing —
reviewing it would hand him a verdict on work he had just called off.

## The card

`kind = 'gated_before_build'` — **forced by measurement, not chosen for convenience.**
`runner_items_kind_check` admits exactly `'ship'` and `'gated_before_build'`, so a third kind would
need a constraint change plus harvest semantics in every place that reads a card (ladder, §5/§6
render, `briefing_open_cards()`), and an unhandled `kind` lands on a card John has already tapped.
The existing gated semantics are also the correct ones: an Accept on a gated card is **permission,
not a rating** — it touches no ladder rung (register B34, John's "no") — and a gate-review verdict
is exactly that transaction, since the runner did not build the milestone's next members and is
asking whether they may be filed.

`backlog_id` stays `NULL` (a gate review is not about one ticket; the bare-id `CHECK` would reject a
composed string anyway — `SES-116`), `display_ref` carries `'<Epic name> — milestone gate review'`,
and `epic_id` carries the join key.

## The property that must not be weakened

**A gate review proposes successor members; John's Accept files them.** Charter §Closure discipline
item 3 is verbatim: *"Only a gate review (SES-179) can add members to a later milestone — batched
and visible to John, never a cycle's solo close-out call."* The review therefore writes **no**
`backlog_items` row and **no** `runner_drain_scope` row, and it may never create or activate a drain
(`drain_epic_next()` property 5, untouched: *"Nothing creates a drain row but John"*). It files one
card and stops. A gate review that filed its own successors would convert a check on the runner into
a widening of it.

## QA plan — discriminating, with the negative control named

Would it still pass if the change did nothing?

1. **Trigger predicate, on the live board with a negative control.** The shipped predicate must
   return M0 (the oldest retired, unreviewed drain). Then, inside a **rolled-back** transaction,
   insert a gate-review card for M0 and re-run: it must return M1 instead. A predicate that ignored
   the card — i.e. the pre-change state, where no such test exists at all — returns M0 both times.
   Fixtures live inside the transaction and are never committed, because a committed
   `runner_items` row is a card John would see (register B42: peers are running concurrently).
2. **`cancelled` exclusion.** The Automation drain is `cancelled` with no review; it must **not**
   appear in any result. A predicate written as `status <> 'queued'` returns it — that is the wrong
   build this control catches.
3. **Column contract.** `epic_id` is nullable and additive: all 130 existing `runner_items` rows
   still read back, and a card written without it still inserts.
4. `npm run build` green; `node tests/regression/run-all.js` green (no `src/`/`api/`/`lib/` change
   in this ship, so the suite is a regression guard, not the proof).
