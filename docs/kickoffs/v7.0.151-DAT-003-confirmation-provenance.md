## 2. CONTEXT

`the_library` had no way to record **who or what confirmed** a promoted (`data_type: consolidated`) fact.

The gate is real: §19d's consequential-action gate means `requires_human_confirmation: true` on Nadia's `data-patch-intent` / `data-patch-execute-intent` flow, so a human does review every promotion today. But that fact was written nowhere on the resulting row. It could only be *trusted*, never *checked* — and nothing structurally stopped a future capability from writing `data_type: consolidated` outside the gated flow at all.

Verified live this session, not recalled:

- `public.the_library` carried no confirmation column of any kind (full column list read from `information_schema`).
- **111 `data_type='consolidated'` rows exist**, none carrying any verifiable confirmation record.
- **128 `accepted` rows in `pending_confirmations`** that cannot be tied back to the rows they produced.

John's framing on the ticket is that this is a showcase piece as much as an integrity fix — AI-confirmed vs. human-confirmed facts, visibly distinguishable.

**The ticket's own open question — new column vs. extending `source` — is settled here by measurement, not preference.** `source` is not an enum; live values include `'agent'`, `'user'`, `"inferred from Crest Wireless scenario (id: 0cecd001-…)"`, `"Analyst hypothesis submitted for escalation review — not yet empirically confirmed"`, and `"test"`. Giving it confirmation semantics would retype live prose rows. Two new columns instead.

**Gated-lane classification, stated because it was the close call.** `the_library` is governed by `ARCHITECTURE.md` §19c, which is marked `[LOCKED]`, and §19v's standing prohibitions name LOCKED sections. §19c's **body** (`ARCHITECTURE.md:1061-1078`) was read rather than reasoning from the tag: it locks exactly three things — two physically separate RAG stores, Data Rooms as a `data_room_tag` *field* rather than a table, and the single write path through `lib/librarian.js`. An additive nullable column written through the existing single write path changes none of the three, and §19v prohibits schema-**destructive** migrations specifically. ## 6. DESIGN RULES

- **The provenance fields are NOT model-reachable, and this is the load-bearing property.** `writeLibrary()` spreads model-supplied `...params` into `buildLibraryEntryPayload()`. Had the two fields been added to that builder, Eleanor's own structured output could assert `confirmed_by: 'human'` on a fact no human ever saw — and the column would look perfectly populated. They are therefore written **only** by `recordLibraryConfirmation()`, from the confirmation row, and nowhere else. The regression test guards this directly, because it is a silent regression that no amount of live data would reveal.
- **Write-once by filter, not by discipline** — `confirmed_by=is.null` on the PATCH means a later confirmation can never overwrite an earlier stamp.
- **Fails to NULL, never to a guess.** No match, no config, no ids → `{ stamped: false }` and the row honestly stays unconfirmed.
- **The stamp never fails the accept.** It is wrapped and best-effort: a promote the human already approved must not be failed by its own bookkeeping. The only outcome that would matter is a false `'confirmed'`, and that cannot arise here.
- **Not a second write path** (§19c): the write lives inside `lib/librarian.js`, and `confirmation.js` reaches it exactly as `api/_lib/handlers/library-write.js` already reaches `writeLibrary()` — verified live, both `library-write.js` and `library-lookup.js` already import that module directly.
- **Stamp after resolution, not threaded through the write.** Rejected the write-time alternative on evidence: `handler_context` is not persisted to `durable_hops`, and §19d's own CHI-60 note records that this exact flow checkpoints on essentially every real invocation — so a write-time stamp would be dropped precisely when it mattered, and would have cost `execute.js` plus another migration.

**Deliberately not done, and why:**

- **No backfill of the 111 existing consolidated rows.** Their true confirmer is not recoverable from the row; the only candidate reconstruction (joining 128 accepted confirmations by `chunk_id` and timestamp) is inference — chunks were patched repeatedly and timestamps overlap. `NULL` now *means* "predates provenance tracking, or no verifiable confirmation," which is honest and displayable. An invented confirmer would be worse than a blank.
- **No `'agent'`-confirmed writer.** The vocabulary is reserved in the CHECK so John's showcase distinction is schema-real, but no AI-confirmation flow exists to write it yet; building one is its own feature, not a rider on this one.
- **Accepted residual, stated rather than hidden:** a promote whose resolution carries no `entry_id` *and* records no supersession (a brand-new-insight promote with nothing to supersede) stays `NULL` — visibly unconfirmed rather than guessed. The stamp is also a separate transaction from the insert, so a crash between them leaves `NULL`. Both failure modes point the fail-closed direction the ticket asks for.

**Found live during this session's own QA, and fixed in the test:** `the_library.supersedes_id` is a self-FK, so a teardown that deletes the superseded target before its replacement fails silently through PostgREST and leaks the fixture row on every run. Five orphaned rows accumulated in the real table before the loop was reversed; all five were removed, with before-images filed first.
