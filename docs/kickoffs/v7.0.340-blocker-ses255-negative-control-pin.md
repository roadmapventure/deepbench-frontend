## Root cause of (1) — a negative control keyed to a moving branch tip

`originDevFailsTheSameAssertions()` runs `git show origin/dev:.github/workflows/ci.yml` and asserts
the shipped reporter assertions **fail** there. That premise is true only while the change is
unmerged. `SES-255` merged as `8ec18ea`, so `origin/dev`'s `ci.yml` **is** the post-change file, all
the assertions pass, and the control throws — permanently, on every run, in CI and locally.

The failing assertion's own message names both branches and the live one is the first:

> *"Either the change already landed (**re-baseline this control**) or the assertions above have been
> weakened into something true of any workflow."*

Nothing re-baselined it.

**Why this is a blocker and not a nit.** The red job is `blocking`. It is one of `verifier.js`'s
three gates, so **every** future cycle's verdict is `block` by construction — the `SES-213` defect
rebuilt one storey up. And step 4a can never record a green anchor again, which disables the
auto-rollback capability `SES-182` and `SES-255` were built across six ships to provide.

## The fix, and it is not a new design

`SES-242` hit this identical defect on 2026-08-29, *minutes* after `v7.0.323` shipped, and its
header states the rule and the remedy:

> *"A file-level control keyed to a branch tip is self-defeating by construction: it is only correct
> in the window before its own ship, which is the one window nobody re-runs it in."*
> *"`PRE_CHANGE_BLOB` is the runbook at `bafcd9c7^` … a blob sha is immutable, so this control means
> the same thing forever."*

So: pin to the blob, exactly as `SES-242` does. `.github/workflows/ci.yml` at `8ec18ea^` is blob
`91c17db16746b875c11948ed39329e8d0e08fabe` (HEAD's is `50ae1562…`, so they genuinely differ), and
that blob contains **zero** occurrences of `report-conclusion` or `ci_run_conclusions` — it cannot
satisfy the reporter assertions under any reading, which is what makes the control discriminating
rather than merely green.

**The edit this forbids, and it is the tempting one because it turns the suite green in one line:**
deleting the control, or softening it to *"if origin/dev passes, declare not-run"*. Both make the
guard vacuous — `SES-255`'s own header calls an unrunnable control *"not a control"*, and a control
that excuses itself whenever it would fail is weaker still. The blob keeps the assertion's teeth and
removes only its expiry date.

**Read from `git cat-file`, never from the filesystem or a branch ref.** `git show <blob>` resolves
the same object, but the retired call is what a later editor would reach for and re-parameterise
with a ref; `git cat-file -p <sha>` takes an object id and nothing else, so the moving-ref form
cannot be reintroduced by editing one string.

## Discriminating QA — would it still pass if the change did nothing?

Stated as the runbook requires. Three arms, all offline:

- **Arm A (the fix works):** `run-all.js` goes 127/129 → 129/129.
- **Arm B (the control still has teeth):** run the shipped assertions against the pinned blob
  directly and assert they **throw**. A control that passes because it stopped asserting anything
  would fail this arm. This is the arm that distinguishes the fix from a deletion.
- **Arm C (the negative control on the negative control):** run the shipped assertions against the
  **working tree** `ci.yml` and assert they **pass**. Arms B and C together prove the predicate
  discriminates between the two files rather than being uniformly true or uniformly false.

Arm A alone is not QA — deleting `originDevFailsTheSameAssertions()` entirely would also produce
129/129. B and C are what make the evidence mean something.
