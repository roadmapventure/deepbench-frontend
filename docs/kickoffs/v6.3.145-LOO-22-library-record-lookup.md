## 2. CONTEXT — the problem (root-caused live, not hypothesized)

**Symptom (John's live repro):** on the Channel Sales Intelligence screen, asking Marcus — CSO Expert about the "Apple Adds 36-Month Carrier Financing for Cellular iPads" news article returned a wall of text — *"Marcus couldn't produce an answer that passed review (synthesized_as_fact)… I cannot verify whether those records exist in the Data Room — the platform lacks a record-level library lookup capability…"* — with **seven raw `the_library` record UUIDs dumped into the chat bubble.**

**Root cause (verified against the live `ai_activity_log` trace + Supabase):**
1. Marcus's `ci-answer-intent` retrieved **10 real `the_library` rows** via similarity search and cited 7. All 7 UUIDs exist (`4e55d9e1…`, `b3293810…`, `d538f08f…`, `fe58cadd…`, `0e40d9b7…`, `59eede59…`, `0cecd001…` — 6 `source_simulation`, 1 genuinely `synthesized`). The answer was well-grounded.
2. Because one cited record (`59eede59…`) is genuinely `data_type: synthesized`, Marcus correctly tagged the whole answer `confidence_tier: synthesized` (weakest-link rule — working as designed).
3. Owen — The Proofreader's `qg-review-intent` has a **mandatory pre-block verification step** (the `LOO-006` rule): before blocking a `synthesized_as_fact` violation, he **must** `request_help` → `delegate_to_agent` to "whichever agent can check the Library" to confirm the claim traces to a real record and its `data_type` matches. If it does, the rule says **pass, not block**.
4. **The trap:** no capability on the roster does a record-level lookup. Eleanor — The Librarian's `data-room-custody` capability has only `library-catalog-intent` (aggregate "what categories exist") and `library-write-intent` (writes). `lib/librarian.js` has `describeLibraryCatalog`, `queryLibrary` (similarity), `writeLibrary` — **no read-a-record-by-id**. So Michelle — Project Manager's model-level `agent-selection` had no correct target and fell back to Sam — The Intake Assistant's `intake-failure-intent` (failure triage). Owen never got verification, the block stood, and Sam's triage output (`suggested_research_request`, containing the raw UUIDs) is what surfaced to the user via `buildFailureText()`.

**In one line:** `LOO-006` mandates a verification step that depends on a capability that was never built, so correctly-grounded synthesized answers get false-blocked as if hallucinated. Owen's "the platform lacks a record-level library lookup capability" is literally true — this session builds that capability.

**Relationship to existing rows (do NOT conflate):** `AA-99`/`AA-178` (both `LOO`) concern the *existing* enrichment-time RAG read (`ai-enrichment.js` calling `queryLibrary()` directly) and are blocked on a John rule-interpretation decision. **This session does not touch `ai-enrichment.js` and does not resolve `AA-178`.** LOO-22 adds a *new* by-id verification lookup reached *through Eleanor* via the legitimate §19d delegation — the compliant Eleanor-delegation read `AA-99` envisions — leaving `AA-178`'s separate question exactly where it is.

## 5. TASKS

**Task 1 — `lib/librarian.js`: add `lookupRecordsByIds`.**
- Signature: `export async function lookupRecordsByIds({ requestingAgentId, tenantId, ids, data_room_tag })`.
- Credential-check the caller the same way `queryLibrary` does (reuse the same access resolution against `agents.data_room_access`/`uber_access`; do not add a second parallel check).
- Read-only: `select id, data_type from the_library where id in (…) and data_room_tag = …` (scoped to the resolved tag; parameterize the id list safely). Never embed, never write.
- Return an array `[{ id, exists: boolean, data_type: string|null }]` — one entry per requested id, `exists:false` (data_type `null`) for ids not found.
- Mirror `queryLibrary`'s logging call (`logLibrarianCall()` or whatever it uses) so the read attributes to `ai_activity_log` like every other librarian op.

**Task 2 — `api/_lib/handlers/library-lookup.js` (NEW): the handler.**
- Mirror `api/_lib/handlers/library-write.js` structure. Read `record_ids` from the structured output; if empty/missing, return an empty verification result (not an error).
- Call `lookupRecordsByIds({ requestingAgentId, tenantId, ids: record_ids, data_room_tag })` using the execution context's agent (Eleanor, since this runs under her capability) and tenant/data_room_tag already threaded to other handlers.
- Return `{ verification: [{ id, exists, data_type }] }` as the handler result so it surfaces on the delegate response (same surfacing path `library-write`'s result uses, `request-receivable.js` ~L717). No agent-id conditional in the handler (§19c enforcement is which Skill sets `handler:'library-lookup'`, i.e. only this intent — exactly like `library-write.js`'s own comment).

**Task 3 — `api/prompt/request-receivable.js` + Supabase data.**
- `request-receivable.js`: import the new handler and add `'library-lookup': libraryLookupHandle` to the `HANDLERS` map (2 lines — logic stays in the dispatched handler file, per harness discipline).
- **Supabase (data, via MCP `execute_sql`, project `rallojeqnkgtxgsdsnqm`):**
  - New `skill_profiles` row: slug `library-record-lookup-intent`, name **"Verify Library Records"**, `skill_type_slug: 'intent'`, `execution_type: 'ai'`, model/temperature/max_tokens mirroring `library-write-intent`.
    - `objective`: "Confirm whether specific the_library records exist and report each one's data_type, for a caller that needs to verify a claim traces to a real Data Room record before trusting or blocking an answer."
