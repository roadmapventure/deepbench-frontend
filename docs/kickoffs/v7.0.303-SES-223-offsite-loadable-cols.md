## Premise, revalidated live before a line changed

Three facts, each read this cycle rather than taken from the ticket:

1. **The metadata exists.** `public._backup_inventory` publishes `loadable_cols` and
   `jsonb_notnull_cols` — both `text`, comma-separated (not arrays; a first attempt to call
   `array_length()` on them errored, which is how the type was established).
2. **Nothing consumes it.** `dump-supabase.mjs` at `5a99272` still asks for `?select=*` in **both**
   pagination branches (keyset, line 133; offset, line 135).
3. **The gap is real and bounded.** Exactly **two** tables differ between "all columns" and
   "loadable columns" — `ai_activity_log` (28 vs 27) and `ip_org_cache` (14 vs 13). In both the
   difference is the single `GENERATED ALWAYS` column `caller_ip_masked`. That is 34,785 rows whose
   NDJSON carries a key PostgREST rejects on insert.

## What shipped

Two files, both in `roadmapventure/deepbench-backups-offsite`:

**`dump-supabase.mjs`** — `loadInventory()` now carries `loadable_cols` / `jsonb_notnull_cols` per
table; `dump()` builds `select=<loadable_cols>` instead of `select=*`, falling back to `*` when the
list is absent; the manifest records both lists per table so the metadata travels **with the set**.
**Views deliberately keep `select=*`** — a restore recreates a view from `schema.sql` and never
loads its rows, so a view's column list is not a loader concern.

**`restore-supabase.mjs`** — drops any key absent from the manifest's `loadable_cols` before the
upsert and says so on the console; the stall path now prints the **server's own error** per table
instead of one confident sentence about a phantom foreign key (`SES-216`'s named diagnostic hole:
the HTTP body was printed only on pass 6, which a stall never reaches).

## What this ship deliberately does NOT do

- **The jsonb-scalar-null defect is untouched**, on John's explicit scope guard in `f365aed4`:
  *"defect (4) … is EXCLUDED from this build … bring the measured format proposal as a card, do not
  pick a representation unattended."* A `NOT NULL` jsonb column holding the JSON scalar `null` dumps
  as `null` and reloads as SQL `NULL`. The measured population is carried to John as a card.
- **It repairs no set that already exists.** Both offsite sets predate this change, so their NDJSON
  still carries the generated column and their manifests carry no column list. The restore-side
  filter is metadata-driven and therefore inert on them **by design** — stated here rather than left
  to be discovered, because it is the reason scoring charter exit criterion 5 needs a *fresh* dump.
- **It takes no offsite push of a dump.** `f365aed4` sanctions one push of the *scripts* to that
  repo's `main` and says so explicitly: it *"does NOT authorize taking or pushing a dump."* The drill
  dump taken as QA below is drill evidence under `1c9609de` and stays on the container.

## QA — three arms, each with its own negative control

**Arm 1 (live end-to-end, the whole point).** The shipped `dump-supabase.mjs` run against the real
database. `ai_activity_log`: **27 keys per row, `caller_ip_masked` on 0 of 34,761 rows.** The
negative control is not reconstructed — it is the set on disk that the *unmodified* script produced
(`refresh-2026-08-28`): **28 keys, `caller_ip_masked` on 34,761 of 34,761.** Same table, same
database, one variable. A change that did nothing scores 34,761.

**Arm 2 (restore key filtering, fixture, real script).** A two-row set whose manifest carries
`loadable_cols = "id,name"` and whose NDJSON carries a third key. Shipped script, dry run:
`dropping 1 non-loadable column(s): computed_x`. **Negative control, one variable:** the identical
set with `loadable_cols` removed → `no loadable_cols in this manifest (set predates SES-223)` and
nothing dropped. The filter fires on the metadata and only on the metadata.

**Arm 3 (the stall diagnostic).** A set naming a table the target does not have, `--confirm`, so
every table fails and the stall path is reached. Shipped script prints the server's `HTTP 404 …`
body per table; `origin/main`'s copy of the script, same fixture, prints the table name and the
phantom-FK sentence with no error at all.
