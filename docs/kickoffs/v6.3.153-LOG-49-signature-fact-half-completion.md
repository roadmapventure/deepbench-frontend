## 2. CONTEXT

### Use case

**Problem.** The log can't see three things agents actually do, so those behaviors can never be named later:
1. **Orchestration vs routing** — when Marcus — GEO CSO Expert coordinates a team (spawns Jordan — Web Search Expert and Eleanor — The Librarian, integrates their results) it looks *identical* in the log to an agent that handed a question off once. There is no parent→child link between calls today, only a shared `trace_id` (which calls belong together) and a bare `depth` counter — so a fan-out is indistinguishable from a linear chain.
2. **Building on another agent's output** — a call that *integrated* an upstream agent's returned result is not distinguishable from one that worked alone.
3. **Self-reported claims** — when an agent's own structured output declares what it drew on (`source_chunk_ids`, a prior reasoning entry id), that declaration is used once and thrown away.

**Fix.** Capture the evidence for all three onto the log row — nothing more. This is the **Log Writer** (§19k, Layer A) only.

**Expected after.** Every call records who spawned it, whether it integrated an upstream result, and any reference-ids it claimed. The **Displayer** (`LOG-38`, separate session) later reads that evidence to name `Orchestration` vs `Request Routing` in the audit. Nothing is displayed by this session.

**Example.** Marcus fans a question out to two workers, then synthesizes. *Before:* his row and a simple routing row look the same. *After:* his execution row carries a `span_id`, each worker's row carries `parent_span_id = Marcus's span_id`, his synthesizing turn carries `input_references_other_deliverable: true`. The tree is reconstructable; orchestration is finally provable — once the Displayer reads it.

### This is settled architecture, not new design

The runtime signature model is `ARCHITECTURE.md §19k` (discovery `design-log-38-0724`). §19i's Layer A list (`:1180`+) defines six facts; `LOG-37`/`LOG-67` shipped the first four + the config-half. **This session ships the remaining three**, closing the fact-half:
- `sub_calls_chained` — §19i: "did this call chain to sub-calls."
- `input_references_other_deliverable` — §19i: "did this call's input structurally embed another capability's real prior output."
- `self_reported_claims` — §19i: "whatever structured fields the model's own output declared (e.g. a case/reasoning-entry id) — captured, never trusted alone."

### Two design decisions that diverge from the original `LOG-49` ticket wording — both deliberate, confirmed with John

1. **A migration IS in scope.** The ticket assumed all three facts extend the existing `call_facts` jsonb with no schema change. `sub_calls_chained` instead needs a real parent→child link, and the right shape is the **OpenTelemetry trace model the architecture already cites** — `trace_id` → `span_id` → `parent_span_id`. `span_id`/`parent_span_id` are added as **real columns** (like `trace_id` already is), because the read-time derivation is a self-join on them — far cleaner/faster as indexed columns than buried in jsonb. Facts 2 and 3 still go into `call_facts` (no schema change for those two).
2. **`sub_calls_chained` is never written as a fact.** Only the raw `span_id`/`parent_span_id` links are captured. The chain itself — "this call orchestrated N children" — is **derived at read time** by the Displayer (`LOG-38`), exactly as `model_modality` was made a read-time derivation in `LOG-65`. This session writes the links, not the conclusion.

### The hops model is untouched — a locked invariant (John's explicit constraint)

The Agent Routing drawer counts every call as a "hop." It is built entirely client-side by `groupEventsIntoHops()` (`src/lib/turnTracking.js`) off the live delegation event stream — **it never reads `ai_activity_log`.** Adding `span_id`/`parent_span_id` columns and `call_facts` keys cannot touch it. **A call is never removed from being a hop because of its pattern classification; orchestration is a label on top of the hops, never a re-count.** Do not alter any hop/routing-drawer code.

## 5. TASKS

> ```jsonc
> // columns:  span_id: "<uuid>",  parent_span_id: "<uuid>" | null
> // call_facts (additive; each key omitted when empty, same "null not {}" contract as today):
> {
>   // …existing LOG-37/LOG-67 keys unchanged…
>   "input_references_other_deliverable": true,          // omitted when false/unknown
>   "self_reported_claims": { "source_chunk_ids": ["…"] } // omitted when the model declared none

> ```

### Task 1 — Migration: add `span_id` / `parent_span_id` columns (both tables)

Via the Supabase MCP (`apply_migration`, project `rallojeqnkgtxgsdsnqm`):
```sql
ALTER TABLE ai_activity_log ADD COLUMN IF NOT EXISTS span_id text;
ALTER TABLE ai_activity_log ADD COLUMN IF NOT EXISTS parent_span_id text;
CREATE INDEX IF NOT EXISTS ai_activity_log_parent_span_id_idx ON ai_activity_log (parent_span_id);
-- durable_hops carries the span across a checkpoint/resume, exactly as it already carries trace_id:
ALTER TABLE durable_hops ADD COLUMN IF NOT EXISTS span_id text;
ALTER TABLE durable_hops ADD COLUMN IF NOT EXISTS parent_span_id text;
```
All nullable (historical rows and any non-capability writer stay null — expected). The `ai_activity_log` index backs the Displayer's future self-join.

### Task 2 — Capture the chain links (`span_id`/`parent_span_id`)

Thread a span identifier exactly like `trace_id` is already threaded, at **capability-execution granularity** (one span per `runCapability()` invocation; every turn/row of that execution shares it; a delegated child execution points its `parent_span_id` at the caller's `span_id`).

**`lib/activity-log.js`** — add `spanId = null`, `parentSpanId = null` to `logActivity()`'s params (`:32`) and to the insert body (`:59`): `span_id: spanId, parent_span_id: parentSpanId,`.

**`api/capabilities/execute.js`:**
- `runCapability()` — add `_parent_span_id = null` param (mirror `_trace_id`). After the `traceId` line (~`:893`): `const spanId = crypto.randomUUID(); const parentSpanId = _parent_span_id;`
- Every **nested** `runCapability()` call (delegation dispatch ~`:513`/`:553`/`:596`, critique ~`:754`) passes `_parent_span_id: spanId` — this execution's own span becomes the child's parent. (These already pass `_trace_id: trace_id`; add the one field alongside.)
- Thread `spanId`/`parentSpanId` into `runLoop()` and into `logAgentTurn()` (add params; pass through to `logActivity()`).
- `sendRequest()`/the model-call write in `request-receivable.js` (`:730`) also stamps `spanId`/`parentSpanId` — thread them from `runCapability()` through the same passthrough that already carries `trace_id` to `sendRequest()`.
- **Confirm the exact threading points against the real code** — the sketch names the sites; verify each `_trace_id` handoff and add the parallel `_parent_span_id`/`spanId` beside it. Where `trace_id` reaches a write, `span_id`/`parent_span_id` must reach it too.

**Resume path — persisted, no gap (this is the identical pattern `trace_id` already uses).** `durable_hops` already carries `trace_id` across a checkpoint (`checkpointAndReturn` ~`:418` writes it; `resumeCapability` reads `row.trace_id` ~`:974`). Mirror it for the span, so a resumed continuation keeps the *same* span identity rather than minting a new one:
- At every checkpoint-write site — `checkpointAndReturn` (~`:418`/`:426`), `persistFailureAndRethrow` (~`:453`/`:461`), and the `insertPendingConfirmation` durable write (~`:765`) — persist `span_id`/`parent_span_id` into the `durable_hops` row alongside the `trace_id` they already write.
- In `resumeCapability()` (~`:974`), read them back beside `const traceId = row.trace_id`: `const spanId = row.span_id || crypto.randomUUID();` (fallback covers pre-migration rows only), `const parentSpanId = row.parent_span_id ?? null;` — then thread them into the resumed `runLoop()` exactly as `traceId` is. A resumed hop keeps its original span and parent, so the parent→child tree stays intact across a checkpoint.

### Task 3 — Capture facts 2 & 3 into `call_facts` (both write paths)

Add to **both** the agent-turn write (`execute.js logAgentTurn`, merged via the existing `mergeCallFacts`) and the model-call write (`request-receivable.js`, into the `buildCallFacts` result):

**3a. `input_references_other_deliverable` (boolean).** True on a turn whose input (`conversationHistory`) contains a returned result from a prior sub-call **within this same `runLoop`** (the "integrate" step). Mechanism: set a flag in `runLoop()` once a delegate's result has been folded back into `conversationHistory` after a nested `runCapability()` returns (~`:797`+); stamp `input_references_other_deliverable: true` on every `logAgentTurn` row from that point on in the loop. **Confirm the exact delegate-result append site before wiring** — set the flag there. Omit the key when false.

**3b. `self_reported_claims` (object).** From the model's own structured output (`turn.tool_input` in `execute.js`; the parsed output in `request-receivable.js`), extract only the **reference-id-shaped fields** the model declared — a bounded allowlist, never the whole output:
```js
// FEATURE: LOG-49 -- ARCHITECTURE.md §19k/§19i. The model's OWN declared reference-ids, captured
// as an assertion and quarantined in its own key -- never merged into the trusted fact-half,
// never trusted alone (corroboration is LOG-38/read-time's job, not the writer's).
const SELF_REPORTED_CLAIM_FIELDS = ['source_chunk_ids','citation_ids','citations','reasoning_entry_id','entry_id','case_id','deliverable_id','based_on'];
```
Build `self_reported_claims` as `{ field: value }` for each allowlisted field actually present (and non-empty) in the structured output. Omit the whole key when none present. **Do not** invent values, normalize, or validate against reality — capture verbatim what the model declared. Keep the allowlist a single shared constant (extensible in one place).
