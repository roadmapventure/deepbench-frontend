## 2. CONTEXT

John: *"if you did not call from the UI, you did it during session checks — call it 'Claude Session QA' — I want to make sure we are tracking how much QA you test before a release."*

**The gap, plainly.** Only a browser call can carry a name in the By Platform User drawer, because the name rides on a cookie (`db_visitor`). A raw script call — the kind this design session runs directly against a live route to verify a fix — has no cookie and never will; `derive()` only ever reads `visitorId` from `readCookie()`. So even a script call John and I both know came from Claude's own verification has nothing to attach a label to. That's not a missing label, it's a missing *identity slot* for non-browser callers.

**Mechanism, decided in the design conversation before this kickoff:** a new header, `x-db-visitor-id`, read into the exact same `visitorId` field a cookie already fills — but **only when `callSource !== 'ui'`**. A real browser's identity always comes from its cookie alone; this header is never consulted for a `ui` call, so no browser request can use it to impersonate a labelled caller. This is the same accepted-limits posture `call_source` itself already carries (self-declared, spoofable by design, not a security boundary — its job is separating traffic John controls) — documented in `docs/harvests/LOG-121.md` and restated in this file's own header comment; extending that same posture to one more self-declared field is a direct continuation of it, not a new risk class.

Once a request carries that header, the existing, **already-shipped and unmodified** identity machinery in `useAIActivity.js` (`buildIdentityIndex`/`identityForRow`, `LOG-121`/`LOG-127`) picks it up automatically — it already resolves any `visitor_id` against `known_callers`, regardless of how that id arrived. Proven working today: labelling John's mobile `visitor_id` produced a correct "John" row in both By Source and By Caller with zero code change, same day. This session only needs to give non-browser callers a `visitor_id` to label in the first place; nothing downstream of `request-context.js` changes.

**No backfill.** The two existing `Script` rows from earlier today keep no name — consistent with every other historical gap this feature has hit (§19i, restated explicitly to John and agreed when `LOG-127` was designed). Only calls made from this header's existence forward can carry it.

**The `known_callers` row is data, not code — the design session inserts it directly** (`.claude/skills` convention already established: `S-LOG-121b`'s scope rules explicitly forbid seeding `known_callers` from application code). Not part of this kickoff's tasks; done separately by the parent session after this ships.

## 5. TASKS (2)

**Task 1 — `lib/request-context.js`: read the header, gated to non-browser callers only.**

Add a new function, placed near `deriveCallerIp`/`deriveDeviceType` (same style — pure, no throw, header-only):

```js
// FEATURE: LOG-130 -- lets a non-browser caller self-identify the same way a browser's cookie
// already does, so John can see total Claude QA volume/cost before a release (his ask, 2026-08-02).
// Gated to callSource !== 'ui' ONLY: a real browser's identity comes from its cookie alone, full
// stop -- this header is never consulted for a 'ui' call, so no browser request can use it to
// impersonate a labelled caller. Same accepted-limits posture call_source itself already carries
// (self-declared, spoofable by design, not a security boundary -- see this file's own header
// comment and docs/harvests/LOG-121.md): a length cap guards against nonsense, not spoofing.
function deriveVisitorTag(headers, callSource) {
  if (callSource === 'ui') return null;
  const raw = headers['x-db-visitor-id'];
  if (!raw) return null;
  const trimmed = String(raw).trim();
  return trimmed && trimmed.length <= 128 ? trimmed : null;
}
```

**Task 2 — `lib/request-context.js`: wire it into `derive()`'s returned `visitorId`.**

In `derive()`, the returned object currently sets `visitorId: sentVisitorId` (~L150). Change to:

```js
visitorId: sentVisitorId || deriveVisitorTag(headers, callSource),
```

`sentVisitorId` (the cookie) wins if somehow both are present — cookie is the stronger, browser-verified signal; the header is only ever the *fallback* identity slot a non-browser caller has no other way to fill. Do not touch the cookie-minting logic (~L134, `if (callSource === 'ui' && !sentVisitorId) mintVisitorCookie(res)`) — it is unrelated and already correctly gated to `ui` only.

## 8. NODE.JS TEST (full code — save as `test-log-130.mjs`, delete before committing)

```js
// test-log-130.mjs — S-LOG-130 (v7.0.48). Category B.
import assert from 'node:assert';
import { withRequestContext, getRequestContext } from './lib/request-context.js';

async function contextFor(headers) {
  let seen;
  await withRequestContext(async () => { seen = getRequestContext(); })(
    { headers }, { setHeader() {}, headersSent: false });
  return seen;
}

// --- the header fills visitorId for a non-browser call
let ctx = await contextFor({ 'x-db-call-source': 'script', 'x-db-visitor-id': 'claude-session-qa' });
assert.equal(ctx.callSource, 'script');
assert.equal(ctx.visitorId, 'claude-session-qa', 'the header must fill visitorId for a non-ui call');

// --- the SAME header is IGNORED for a browser call -- this is the actual security property
ctx = await contextFor({ 'sec-fetch-site': 'same-origin', 'x-db-visitor-id': 'claude-session-qa' });
assert.equal(ctx.callSource, 'ui');
assert.equal(ctx.visitorId, null, 'a browser call must NEVER take an identity from this header -- only its own cookie may set visitorId for ui traffic');

// --- session-test and regression can use it too -- not special-cased to 'script' only
ctx = await contextFor({ 'x-db-call-source': 'session-test', 'x-db-visitor-id': 'claude-session-qa' });
assert.equal(ctx.visitorId, 'claude-session-qa');
ctx = await contextFor({ 'x-db-call-source': 'regression', 'x-db-visitor-id': 'nightly-regression' });
assert.equal(ctx.visitorId, 'nightly-regression');

// --- a real cookie still wins over the header if a non-ui call somehow carries both
ctx = await contextFor({ 'x-db-call-source': 'script', cookie: 'db_visitor=cookie-wins', 'x-db-visitor-id': 'header-loses' });
assert.equal(ctx.visitorId, 'cookie-wins');

// --- absent header degrades to null, never throws (this file's own standing rule)
ctx = await contextFor({ 'x-db-call-source': 'script' });
assert.equal(ctx.visitorId, null);
ctx = await contextFor({});
assert.equal(ctx.visitorId, null, 'no call_source header at all, no browser signal -> script, no tag -> null, no throw');

// --- a malformed/oversized header degrades to null rather than polluting the column
ctx = await contextFor({ 'x-db-call-source': 'script', 'x-db-visitor-id': 'x'.repeat(200) });
assert.equal(ctx.visitorId, null, 'an oversized tag must be rejected, not truncated silently into something else');

console.log('ALL TESTS PASS');
```
