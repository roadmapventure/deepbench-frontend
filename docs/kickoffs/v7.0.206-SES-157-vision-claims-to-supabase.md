## Why this ticket exists

The vision corpus is what the runner scores an invention proposal against, and until this ship every
claim in it was **prose inside nine markdown essays**, with its *state* — ratified, rejected, rewritten
— recorded by a cycle editing the claim's own line. Two consequences the spec names:

- A **rejection was a deletion.** `docs/vision/rejected-paths.md` held the rejected paths as a
  separate document; the drip card's Reverse deleted the claim and appended there. John's ruling
  (decision 5, verbatim): *"a rejected claim is a kept row, since rejections teach what not to build."*
- The **roots were never his.** The four `§19v` judgment-class purposes are the criteria every P1–P4
  call is made against, and the runner had only the doc's paraphrase of them. Decision 7: they are
  seeded as claims **and simultaneously asked**, so his answer is the ratified root.

## What shipped

### 1. `public.vision_claims` (migration `ses157_vision_claims`)

`claim_ref` (unique) · `source_doc` · `claim_text` · `judgment_class` · `confidence` · `status` ·
`is_root` · `decided_at` · `provenance` · `superseded_by` (self-FK) · `created_cycle` · timestamps.

Two constraints carry decisions rather than tidiness, and both are the `SES-112` precedent — *a status
may not claim an artifact it does not carry*:

- `ck_vision_claim_decided` — `status = 'proposed' OR provenance IS NOT NULL`. **No cycle can record a
  verdict on a claim without saying what decided it.** This is what makes a `rejected` row teach
  something instead of merely existing.
- `ck_vision_claim_rewritten` — a `rewritten` row must name its `superseded_by`. John's typed line
  INSERTs a new ratified row in his words and points the old one at it, so his wording **replaces** the
  claim without destroying what it replaced.

`ck_vision_claim_class` admits only the four **named** forms (`P1 - Improves John's Skills`, …), never a
bare `P1` — John's language rule made structural rather than remembered.

### The course correction, recorded because it changed what shipped

This cycle first delegated the extraction to a **Fable 5** subagent, on the assumption that the essays
were prose a model had to tease claims out of, and briefed it for *"roughly 8-15 per doc, ~90-120 rows
total"*. **That assumption was wrong, and checking it is what caught it:** `SES-84` phase 1 had already
written every claim as an id'd, confidence-marked bullet with a `*grounds:*` tail — **262 of them,
all nine docs, 262 of 262 carrying a confidence marker and grounds** (measured, not recalled). So the
delegated brief would have silently dropped roughly **140 real claims** and paraphrased text the docs
already state exactly — including `C-thesis-2`, the **LOCKED** investor pitch, which is 451 characters
of quoted wording that has to survive the move byte-for-byte.

The subagent was stopped and the import re-run **one tier up** as a deterministic parser (register
B21's attempts-per-tier ≤ 1, satisfied: one Fable attempt, then Opus — never a second attempt at the
same tier). The `JOHN-DECISION-PATTERNS.md` half is genuinely a distillation and stayed with its
**Sonnet 5** subagent, which returned 40 rows.

**The faithfulness check is the QA that matters here, and it ran against the live table rather than the
intermediate file:** every `[C-…]` bullet in the nine docs was re-parsed and matched to its shipped row
by `claim_ref` — **262 checked, 0 missing, 0 text differences, 0 wrong statuses, 0 wrong confidences**,
against 306 rows in the table. A count-only check would have passed on a paraphrasing import; this one
does not.

**`judgment_class` is deliberately NULL on all 302 imported rows**, and that is a decision rather than
an omission. The essays carry no per-claim P-class, so assigning 302 of them would have been this
cycle inventing 302 classifications in one pass and storing them as if the corpus had said so — the
opposite of the `.claude/rules` discipline this repo runs on. The four **roots** carry their class
because §19v states it. Thickening class criteria is what `SES-159`/`SES-160` (Chain B 3 and 4) exist
to do, one ratified answer at a time.

**`decided_at` is NULL on the 51 rejected rows too**, for the same reason: stamping the import minute
onto a path John rejected months ago would assert a date nobody observed. The historical reason lives
in `provenance`, which `ck_vision_claim_decided` already requires. Only a tap sets `decided_at`.

Every one of the 306 rows has its `runner_before_images` row (`row_data = NULL`, the `SES-142` INSERT
convention) — **306 written, 306 rows, verified equal.**

### 4. `docs/runbooks/briefing-page.md` — the §12 contract repointed

The drip section's source becomes the table, the three taps become row writes (with the tap table), and
the row-id form becomes `vision-<claim_ref>`. The `vision-` **prefix rule is unchanged** — it is still
the only thing separating a claim's tap from a `runner_questions` tap under the shared `answers` key —
but the suffix is now a unique key into a table instead of a doc-plus-line coordinate. The contract now
says explicitly: **harvest by `claim_ref`, never by matching the claim's text**, because John's typed
line rewrites that text, which is exactly the moment a text match would silently stop finding its row.

## Deliberately NOT done, said plainly rather than discovered later

- **No regression test file.** The three shipped surfaces are a schema, a seed and a doc contract; the
  §12 renderer in `briefing-template.html` is **unchanged** (it already draws vision rows through
  `question()`, and only the row's *source* moved). The repo's regression tests are network-free
  template harnesses, so a test here would have had no template delta to assert and would have been
  ceremony. The QA above is live and reproducible from this document.
- **`SES-158` (the routing rule) is not in this ship** and is not owed by it: it is Chain B 2 of 4 and
  its own description declares `Depends on SES-155 + SES-157.` This ship closes the second half of that
  dependency only.
- **No `vision_drip_next()` function, and it is the one candidate this ship consciously declined.**
  The §12 selection is written as SQL in `briefing-page.md` for a cycle to run, which is exactly the
  *"a rule each cycle re-derives is a rule that gets re-derived differently"* shape this platform has
  now corrected ten times (`SES-86` phase 3, `v7.0.146`, `SES-101`, `SES-111`, `SES-127`, `SES-128`,
  `SES-129`, `SES-143`, `SES-147`, dir `16b3ff73`). It is not folded in here because it is the same
  edit as deriving the §12 builder field, and doing half of `SES-163`'s job inside `SES-157` would
  leave two partial fixes instead of one. Named here so the next cycle to touch §12 does it once.
- **The `§12` builder field is still cycle-supplied.** `scripts/build-briefing.mjs` lists §12 under
  *"NOT DERIVED — supplied by the cycle in `--data`"*. Deriving it from `public.vision_claims` is now
  a two-line query and is exactly the shape `SES-163` was filed to fix wholesale; folding it in here
  would have widened this ticket into that one.
