## 1. CONTEXT

John live-tested the MI screen's Q&A path on dev and hit a `hallucinated_internal_data` guardrail block: Marcus (channel-intelligence, `ci-answer-intent`) answered "Japan is Apple's fastest-growing GEO — what is driving that?" by citing a real-but-synthetic seeded Data Room row (`nippo-carrier-jp`, `data_type: "synthesized"`, `citeable: false`) with specific metrics as though it were sourced fact. Owen (quality-gate, `qg-review-intent`) correctly caught it and escalated to Sam — the guardrail pipeline worked exactly as designed (`docs/kickoffs/v5.3.7-S-APPLE-02c-quality-gate.md`'s `RULE_ENUM` has covered `hallucinated_internal_data` since 2026-06-xx).

The open question John raised: why does the *same* question sometimes pass and sometimes block? This is not new — `AA-130` (`docs/FEATURES-ARCHIVE.md`) already documented this exact canned question flip-flopping: Supabase showed the first-ever `guardrail_result: block` after **9 prior passing reviews** of the identical question since 2026-07-02, and named the root cause as "an inherently non-deterministic LLM-as-judge finally tipping a genuinely borderline answer to a hard block" — but no fix was made at the time.

**Confirmed this design session (repo-wide grep, zero matches):** `temperature` is never set anywhere in `api/` or `lib/`. Every `callModel()` call in the platform — including Marcus's `ci-answer-intent` and Owen's `qg-review-intent` — runs at Anthropic's unset default (temperature 1.0), the most randomized setting available. Both calls are structured/schema-driven JSON outputs (fact extraction and rule-based judging respectively), not creative-writing tasks — there is no legitimate reason either should be sampling at the "creative" default.

**What this session does and does not fix:** setting a low temperature makes the *same input* produce the *same output* far more reliably — it converts "sometimes wrong" into "predictably right or predictably wrong," which is what makes the deeper issue testable and fixable at all. It does **not** fix why the synthetic Nippo row is textually indistinguishable from real sourced data in the rendered RAG context (tracked separately as `AA-155`), and does **not** add server-side validation that Marcus's `citations` UUIDs actually match what RAG retrieved (tracked separately as `AA-156`). Both are logged in `docs/FEATURES.md` this session per the Backlog Capture rule, explicitly out of scope here — John's call was to fix temperature first (cheapest, most generic, and the direct explanation for the flip-flop) and queue the other two behind it, inserted ahead of `AA-149` in the MI Loop track given this blocks trusting any Q&A answer shown to Apple, the same category as `AA-150`/`AA-151`'s ship-readiness gate.
