## 2. CONTEXT

John's desktop run showed **two "Verification" phases** in the Assembly drawer, each with a
different agent — Owen Marsh (gate review, `qg-review-intent`) and Eleanor Voss (record
verification, `library-record-lookup-intent`). Both intents map to the same `verification`
stage in `STAGE_OF_INTENT`, and §19s's contract table allocates record verification as
*nested under* Verification — one phase. The drift: the fold's **start path** already nests
onto an already-filled same-stage section (the LAV-25 T3 revision case, ~L442: "a revision
round is work INSIDE a stage, not a new one"), but the **completion path** (~L402–414) has no
mirror rule — when `findLast(s => !s.filled && s.stage === stage)` finds nothing because the
stage's section is already **filled**, it falls through to `open()` and creates a sibling
section with the same label.

**The fix (John-approved 2026-08-08):** the completion path gains the start path's rule — a
stage-deriving completion whose stage already has a **filled** section nests as a sub-entry
under it instead of opening a duplicate. One Verification phase: Owen's review fills it,
Eleanor's record check is an indented sub-line with her own account. Fully generic — keyed on
the stage key only, no agent, no intent special-case (Rule #1/§19d; a second gate re-review
on a revision round collapses identically). The mobile Assembly tracker band chips render one
chip per section off this same fold (`MOB-15`), so `MOB-16`'s duplicate-chip question
collapses in the same change — that's why it closes here.

## 5. TASKS (1)

### T1 — Completion-path nesting in `buildAssemblyStages()` (`src/components/AssemblyView.jsx`)

Inside the `if (stage) { ... }` completion branch (~L402), between the existing unfilled-target
resolution and the `else open(...)` fallback, add the filled-host case. Exact change — replace:

```js
      if (target) Object.assign(target, filledProps, { spanId: d.span_id ?? target.spanId ?? null });
      else open({ ...filledProps, spanId: d.span_id ?? null });
      continue;
```

with:

```js
      if (target) { Object.assign(target, filledProps, { spanId: d.span_id ?? target.spanId ?? null }); continue; }
      // FEATURE: LAV-36 (§19s) -- the completion-path mirror of LAV-25 T3's revision rule above:
      // work whose stage is already FILLED is work INSIDE that stage, never a second section with
      // the same label. The section keeps its own agent and ✓; the later completion nests as a
      // sub-entry carrying the doer's own account and took-time. Keyed on the stage key only --
      // no agent, no intent named (Rule #1). This is what makes the drawer show ONE Verification
      // phase when the gate's review has filled it and the record check lands after (John's
      // 2026-08-08 report), and it collapses the mobile tracker band's duplicate chips for free
      // (MOB-16 -- one chip per section, same fold).
      const filledHost = findLast(s => s.filled && s.stage === stage);
      if (filledHost) {
        filledHost.subEntries.push({ key, ...whoOf(evt.agentId, byId), did, timeSignature });
        continue;
      }
      open({ ...filledProps, spanId: d.span_id ?? null });
      continue;
```

Behavior notes the diff must preserve:
- The unfilled-ghost fill (`target`) path is byte-identical in effect — only restructured to
  `continue` inline so the new case can sit between it and `open()`.
- The sub-entry shape matches the revision sub-entry (~L454): `key`, `whoOf`, `did`,
  `timeSignature` — no `asked` (a completion is not an ask), no `detail` flag (this is
  deliverable work, it renders; the §19s account is the line).
- Nothing else in the fold changes. `STAGE_OF_INTENT`, `COMPLETION_STAGE`, the start path,
  briefing-fetch exclusion, and terminal-cap logic are untouched.
- Update the file's version-header comment to v7.0.74 with a one-line LAV-36 note.
