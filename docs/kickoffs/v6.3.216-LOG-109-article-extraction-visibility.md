## 2. CONTEXT

**The problem, in one click.** A user clicks a news card on Channel Intelligence. `analyzeNewsCard()` posts the URL to `api/fetch-article`, which tries to fetch and extract the article itself, and falls back to a Claude web-search summary if that fails. When the whole thing fails, the screen submits `article_content: null` and Marcus Webb — GEO CSO Expert answers "Article text needed…".

At that moment four different things could have happened and **nothing distinguishes them**: the publisher blocked us, the page loaded but Readability pulled 80 characters of nav chrome, the request never completed, or the route was never called at all. Each has a different fix. This is `S-SES-29`'s case 24, still undecidable.

**Why nothing distinguishes them.** Only the *fallback* path logs (`fetch-article.js:72-79`, `ai_type: 'fallback-summary'`). The primary path writes no row on any outcome, success included. Measured live 2026-07-29: **9 rows total for `feature='article-extraction'`, all of them fallback rows, zero primary rows.** `platform_services.article-extractor` is marked `tracking_status: 'partial'` for exactly this reason — one match key, covering one of two paths.

**And the reason is thrown away twice.** The route knows precisely why it failed at the instant it fails, then collapses everything into a generic 500/502. The screen writes `res.status` to a browser console (`MarketIntelligenceScreen.jsx:4024`) and submits blank. So the user gets an unexplained non-answer and the agent gets no explanation either.

### The `ai_type` value — use the catalog slug, do not invent one

`LOG-109`'s row proposes `ai_type: 'deterministic'`. **Do not use it.** Verified live this session: that value is legacy (6 rows total, none written since 2026-07-17) and matches **no** `platform_services.match_keys`, so rows carrying it land in the unregistered-services bucket — the same defect `LOG-14` fixed for `guardrails-check`. `.claude/rules/capability-logging.md` still names it; that staleness is `SES-54`, not this session's to fix.

The live convention is `aiType: SERVICE_SLUG.X` — the generated constant, not a literal (`AI-53`: "generated from `SERVICE_CATALOG` itself so a slug constant can never diverge from the catalog it's derived from"). `api/extract.js:116` and `:184` are the two shipped examples. `SERVICE_SLUG.ARTICLE_EXTRACTION` already exists and is already referenced at `useAIActivity.js:376`.

**Consequence: no `AI_TYPE_TO_SERVICE` entry is needed and none may be added.** With `ai_type === 'article-extraction'` — equal to its own `SERVICE_CATALOG` slug — `capabilitySlugForRow()`'s existing `|| rawSlug` fallback resolves it correctly, the same way `channel-intelligence`, `quality-gate`, `data-analysis` and `agent-turn` all resolve with no entry. Adding one would be a second hand-written literal that must agree with the first forever — the exact shape `AI-53` removed.

The two paths stay tellable apart without it: the primary row carries `model: null` plus its `call_facts`; the fallback row carries `claude-sonnet-4-6`.

### `call_facts` carries a band, never a raw count

`LOG-109`'s row asks for "response status + byte count." Status yes; **raw count no.**

`ai_call_patterns` assembles `COALESCE(call_facts,'{}')` **whole** into the signature, then `SELECT DISTINCT`s it and matches every distinct value against every gold pattern (verified this session by reading the view definition). Anything that varies per call permanently enlarges that matching set. `LOG-91` measured exactly this at **720 → 24,826 distinct signatures** when a per-call millisecond value was proposed for `call_facts`, re-crossing the 3 s anon statement timeout `LOG-99` had just brought back to ~289 ms — which is why `dispatch_latency_ms` is a column instead. Measured live 2026-07-29: **14,750 rows with `call_facts` collapse to 651 distinct fact sets.** Keep it that way.

`extraction_outcome` is 4 values and `http_status` is a small set, so the pair adds a bounded handful of signatures. An exact character count would add one per fetch, forever.

Both keys stay **off** `SIGNATURE_FIELDS` — they are diagnostic facts, not pattern vocabulary. Do not add them to the allowlist in `lib/pattern-vocabulary.js`, and do not write any `pattern_vocabulary.criteria` referencing them.

### The user-facing half (`CHI-91`) and why the screen is allowed to speak

`.claude/rules/agent-section-rendering.md` says the screen holds no content policy and never writes copy an agent failed to supply. **That rule governs an agent's structured output; it does not govern a platform fault report.** `HAR-15`'s `CREDIT_EXHAUSTED_TEXT` (`MarketIntelligenceScreen.jsx:1140`) is the standing precedent, tagged in-file as "Platform fault report, not agent content (§19j)". A publisher blocking DeepBench is DeepBench reporting its own failure, not the platform putting words in Marcus Webb — GEO CSO Expert's mouth.

Marcus's own acknowledgment is handled the other way round, and must be: the screen passes **facts**, and `ci-answer-intent`'s `method` tells him to phrase them himself. Never pass him a prewritten sentence — that would be the §19j violation the rule above actually forbids. Same shape `AGT-36` (v6.3.220) used two days ago for its designed-gap instruction.

`HAR-15`'s other half applies too: the copy is honest about whether retrying helps. A blocked publisher and an unreadable page will fail identically forever; a timeout may not.

```js
// FEATURE: LOG-109 -- the two Layer A facts the primary path captures, deliberately banded.
// http_status describes the REQUEST; extraction_outcome describes the EXTRACTION. Orthogonal on
// purpose: 403+not_attempted (blocked) and 200+empty (extractor found nothing) are different
// bugs with different fixes, and case 24 could not tell them apart. `text` is the already-
// trimmed Readability output, or "" when Readability never ran.
// NEVER add the raw character count here: ai_call_patterns assembles call_facts whole into the
// §19k signature and SELECT DISTINCTs it, so a per-call value adds one distinct signature per
// fetch forever -- LOG-91 measured that exact mistake at 720 -> 24,826 signatures and a blown
// 3s statement timeout. The 500 threshold below is fetch-article's own long-standing cutoff.
export function classifyExtraction(httpStatus, text) {
  if (httpStatus == null || httpStatus < 200 || httpStatus >= 300) return "not_attempted";
  const len = (text || "").length;
  if (len > 500) return "full_text";
  return len > 0 ? "below_threshold" : "empty";
}
```

  // the generated SERVICE_SLUG constant (AI-53) so it can never diverge from SERVICE_CATALOG.
  // Equal to its own catalog slug, so capabilitySlugForRow()'s `|| rawSlug` fallback resolves it
  // with no AI_TYPE_TO_SERVICE entry -- same as channel-intelligence/quality-gate/agent-turn.

      const dom = new JSDOM(html, { url });

// FEATURE: LOG-109/CHI-91 -- platform fault copy for a news-card article that could not be read.
// A platform fault report, NOT agent content: .claude/rules/agent-section-rendering.md forbids the
// screen writing copy an AGENT failed to supply; this is DeepBench reporting its own failure, the
// same carve-out CREDIT_EXHAUSTED_TEXT above already occupies (§19j). HAR-15's other half applies
// too -- the sentence is honest about whether retrying helps, because a blocked publisher and an
// unreadable page fail identically forever while a timeout may not. Returns null when there is
// nothing to report, so the caller renders nothing rather than an empty bubble.
export function articleFaultText(primaryFailure) {
  if (!primaryFailure) return null;
  const tail = " Answering from the headline alone.";
  if (primaryFailure.http_status == null) {
    return "This publisher didn't respond in time — retrying may work." + tail;
  }
  if (primaryFailure.extraction_outcome === "empty" || primaryFailure.extraction_outcome === "below_threshold") {
    return "This page had no readable article text — retrying won't help." + tail;
  }
  return "This publisher blocks automated readers — retrying won't help." + tail;
}
