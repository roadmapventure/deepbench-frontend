## CONTEXT

Feature/backlog IDs (`CHI-`, `LOG-`, `SES-`, `LOO-`, etc.) are still assigned by "read the highest existing number across `docs/FEATURES*.md`, add one" — the exact race `dev_version_counter` already solved for version numbers on 2026-07-15, but never extended to feature IDs. Real, repeated cost, not theoretical: `AA-197`/`AA-198` were independently claimed by two concurrent sessions the same day; `CHI-13` was independently claimed and shipped by one session while another session's draft still held it; `HAR-02`/`AA-197` were the same finding logged twice under two different IDs the same day. Each collision cost a live rebase-conflict scramble (renumber, rename the kickoff file, re-commit).

**Fix:** a new Supabase table, `feature_id_counter`, keyed by prefix instead of `dev_version_counter`'s single row — claimed via the identical atomic-UPSERT pattern, race-free by construction. Full backstory: `SES-006` in `docs/FEATURES-ARCHIVE.md` (moved there at this session's own close-out).

Claim via the Supabase MCP's `execute_sql` (project `rallojeqnkgtxgsdsnqm`):
> ```sql
> INSERT INTO feature_id_counter (prefix, next_number, updated_by_session)
> VALUES ('<PREFIX>', 1, '<short-session-name>')
> ON CONFLICT (prefix) DO UPDATE
>   SET next_number = feature_id_counter.next_number + 1,
>       updated_at = now(),
>       updated_by_session = EXCLUDED.updated_by_session
> RETURNING next_number;
> ```
> The returned `next_number` is the ID to use directly (`<PREFIX>-<next_number>`) — works identically whether the prefix already has claimed rows or is being used for the first time (lazily starts at 1, no separate seeding step needed for a genuinely new prefix). Postgres serializes this the same way it already serializes `dev_version_counter` claims — race-free by construction, no re-check-before-push step needed. Confirm the prefix itself is legitimate against `docs/SCREEN-INVENTORY.md`'s taxonomy before claiming — this table doesn't govern which prefixes are valid, only the number. Legacy area-prefixed IDs (`AA`, `MI`, `AI`, etc.) are frozen per the 2026-07-15 taxonomy rule and have no counter row — never claim a new legacy-prefixed ID through this mechanism or any other.
```

## NODE.JS TEST

Run with `node test-ses-006-atomic-feature-id-counter.mjs` from the worktree root. Delete before committing.

```js
// test-ses-006-atomic-feature-id-counter.mjs
// Pure Node.js — no app imports. Re-derives each prefix's current highest
// existing number directly from the live repo files, so it self-corrects
// if a concurrent session landed a new row since this kickoff doc was written.
import fs from 'fs';

const DOCS = [
  'docs/FEATURES.md',
  'docs/FEATURES-NEXT.md',
  'docs/FEATURES-LATER.md',
  'docs/FEATURES-ARCHIVE.md',
];

const ACTIVE_PREFIXES = [
  'CHI', 'PRO', 'SPA', 'AGR', 'HOM', 'TMT', 'AIA', 'ABT',
  'HAR', 'LOO', 'SCA', 'LOG', 'MCP', 'MKT', 'DAT', 'AGT', 'SES', 'MOB',
];

function computeMaxByPrefix(text, maxes) {
  const re = /\b([A-Z]{2,4})-(\d+)[a-z]?\b/g;
  let m;
  while ((m = re.exec(text))) {
    const prefix = m[1];
    if (!ACTIVE_PREFIXES.includes(prefix)) continue;
    const num = parseInt(m[2], 10);
    if (!maxes[prefix] || num > maxes[prefix]) maxes[prefix] = num;
  }
}

const maxes = {};
for (const doc of DOCS) {
  const text = fs.readFileSync(doc, 'utf8');
  computeMaxByPrefix(text, maxes);
}

// Test 1 (Category B — Logic): computed next-number matches the values
// hand-derived during design and used in Task 2's seed INSERT.
const EXPECTED_SEED = {
  CHI: 47, LOG: 35, LOO: 16, AGT: 27, SES: 13, HAR: 7,
  DAT: 5, AGR: 3, PRO: 2, AIA: 2, MCP: 2, MOB: 2,
};

let pass = true;
for (const [prefix, expectedNext] of Object.entries(EXPECTED_SEED)) {
  const max = maxes[prefix] || 0;
  const computedNext = max + 1;
  const ok = computedNext === expectedNext;
  console.log(
    `${prefix}: highest=${max} computedNext=${computedNext} expected=${expectedNext} ${ok ? 'PASS' : 'FAIL'}`
  );
  if (!ok) pass = false;
}

// Test 2 (Category A — Data Shape): zero-row prefixes must stay at zero,
// confirming they should NOT get a seed row (lazy-create via upsert instead).
for (const prefix of ['SPA', 'HOM', 'TMT', 'ABT', 'MKT']) {
  const max = maxes[prefix] || 0;
  const ok = max === 0;
  console.log(`${prefix}: highest=${max} (expect 0, no seed row) ${ok ? 'PASS' : 'FAIL'}`);
  if (!ok) pass = false;
}

// Test 3 (Category C — String Safety): mixed zero-padding (AGR-01 vs
// AGR-002) must not break max detection — both parse to a plain int.
const paddingSample = 'AGR-01 and AGR-002 and AGR-2 all appear in this corpus.';
const paddingMaxes = {};
computeMaxByPrefix(paddingSample, paddingMaxes);
const paddingOk = paddingMaxes.AGR === 2;
console.log(`Padding-safety: AGR max=${paddingMaxes.AGR} (expect 2) ${paddingOk ? 'PASS' : 'FAIL'}`);
if (!paddingOk) pass = false;

console.log(pass ? 'ALL TESTS PASS' : 'TESTS FAILED');
process.exit(pass ? 0 : 1);
```

If this fails on any real prefix (not the synthetic padding sample), do not seed with Task 2's hardcoded values — use this script's live-computed `computedNext` instead, and note in the close-out report which prefix drifted and why (almost certainly a concurrent session landing a new row in the gap between this doc being written and executed — exactly the scenario this whole feature exists to make survivable).
