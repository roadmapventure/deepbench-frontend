# v7.0.347 — SES-261: the CLAUDE-STATE check stops racing the cycle's own close

**Ticket:** `SES-261` — Every runner ship makes CI red by construction — the CLAUDE-STATE check races
the cycle's own close
**Class:** `P10 - Tooling` · tier `now` · epic `Selfbuild M4 - Infrastructure Floor` · size `M` ·

**Cycle:** `c6780beb-4d6f-44aa-9c25-ccc37a272df3`, scheduled, model claude-opus-5
**Design:** delegated to a Fable 5 subagent per register B21; its shape adopted with one correction

## The defect, revalidated live this cycle rather than quoted

`scripts/render-claude-state.js --check` re-renders `CLAUDE-STATE.md` from the **live** ledger
(`runner_cycles WHERE outcome='shipped'`, top 10 by `started_at desc`) and byte-compares it against
the **committed** file. `tests/regression/SES-177-claude-state-renderer.js`'s credentialed half runs
that `--check` in CI on every `dev` push.

A cycle renders and pushes at step 7a; its own row does not reach `outcome='shipped'` until its
step-9 tail, i.e. **after** the push. So the committed file can never contain the pushing cycle's own
ship, and the instant that tail closes, the committed file is stale against the live ledger.

**Measured this cycle, not inferred:**

- Cycle `a906b726` closed `shipped` at `2026-08-31T17:08:22Z` (v7.0.345, push `52a3d7f`).
- Its own pushes `4170428` (17:05Z) and `52a3d7f` (17:08Z) concluded **success** — CI won that race.
- Every dev commit pushed *after* that close is **red**: `05506b0` (17:24Z) and `b7f97081` (17:43Z),
  both `Build (blocking)=success`, both `Tripwire + regression (blocking)=failure`.
- Reproduced locally on `b7f97081`: **130/131**, `SES-177-claude-state-renderer.js` the sole failure.
- The drift is exactly one ship: the committed file says `v7.0.343`/`SES-183`; the ledger renders
  `v7.0.345`/`SES-47`.

**The scope is wider than the ticket states, and this is the correction worth recording.** The ticket
frames it as the pushing cycle's own commit racing its own close. The live evidence shows the red
outlasts that commit: *every later commit by anyone* — including the two attended `SES-263` pushes —
is red until some cycle happens to re-render. The check asserts "the committed file equals what the
ledger renders **right now**", which is a moving target no commit can satisfy for long.

## The decision

Shape **(d)** from the ticket — *pin the comparison to the ledger state the commit was rendered from*
— implemented as a **pin carried in the generated file itself**.

**The correction made to the subagent's brief, and it is load-bearing:** the pin is the explicit
**list of rendered cycle ids**, never a timestamp cutoff. A `started_at <= basis` window is unsound
on this platform because a cloud cycle can be suspended and resumed across wall-clock gaps invisible
from inside it — `633fe486` started 05:07Z and was still executing at 13:10Z — so a cycle can close
`shipped` long after a later-started cycle already did. A time window would then silently admit rows
the render never saw. An id list is immune to that by construction.

Rejected, with reasons:

- **(a) ignore the newest just-closed cycle** — fails on today's own evidence: two further commits
  went red after the close, so a `k=1` tolerance does not cover it, and widening `k` erodes the
  check. It also assumes a past render is a contiguous window of today's ledger, which concurrent
  cycles falsify (the committed file's own `v7.0.343` current / `v7.0.344` prior inversion).
- **(b) run the check only outside CI** — deletes the gate from the one venue where it is enforced.
- **(c) render after the close and push twice** — rejected by the ticket on its face; it breaks the
  one-push-per-ship-point rule.

## What changes

1. `renderBody()` appends `ledger-pin: <id>,<id>,…` inside the existing trailing `GENERATED` HTML
   comment — one line, invisible in rendered markdown, ~400 chars.
2. `--check` becomes pin-anchored: parse the pin, fetch exactly those rows by id, re-order to pin
   order, re-render, byte-compare. The comparator is a **pure exported function** so the guard tests
   the real predicate rather than a copy (the `DIR-603f44ea` / `SES-176` precedent).
3. Fail-closed exits, each asserted: missing / empty / unparseable pin → **1** (a stripped pin is a
   hand-edit); a pinned row absent from the ledger or no longer `shipped` → **1**; REST or env
   failure → **2**, never a pass.
4. A **non-gating freshness WARN** (still exit 0) when the pinned newest id differs from the live
   newest shipped id — see the honest trade below.

## The acceptance bar, both directions (SES-101)

- **Ship → close → CI green.** The cycle renders from rows R and pins R. Its tail closing changes the
  live top-10 but not R, so `--check` re-renders R and matches. Later commits carry the same pin and
  stay green.
- **A genuine hand-edit still fails.** Any edit to a generated section mismatches the re-render of
  the pinned rows' live content. Editing the pin does not escape: fabricated ids → missing rows →
  exit 1; substituting other real ids → their render does not match the hand-kept body → exit 1.

## The discriminating control (a DIFFERENCE, not a shared property)

One fixture: ledger S of 10 cycles, file F = the new renderer's output for S; then simulate the tail
by adding a newly shipped cycle N.

- **Shipped comparator** (pin-anchored) → **no drift**.
- **Retired comparator** (`renderBody(live top-10) === F`, reconstructed from the same *imported*
  `renderBody`) → **drift**.

The control asserts old = red **and** new = green on that same fixture. A test asserting only "new is
green" is satisfied by an always-green comparator, which is the failure mode that matters most here.
Paired with the shared-direction assertion: a hand-mutated byte makes **both** forms drift.

## The honest trade, named rather than buried

This converts the check from a **freshness** gate into an **authenticity** gate. A valid old render
stays green indefinitely, so if step 7a's render silently stopped running, nothing would go red. That
is deliberate — the freshness half is precisely what is unsatisfiable under the one-push rule — and
it is why the non-gating WARN ships with it. A hard freshness bound is a separate ticket, not this
one.

Residual redness that is correct and not vacuous: retroactively editing a pinned cycle row re-reds
the file until the next render. That is honest drift — the file no longer matches the rows it claims.
