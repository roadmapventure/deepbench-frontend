## 1. CONTEXT

Part `a` (`v6.3.25`) generates a `trace_id` once per top-level interaction inside `execute.js` and now passes it into both `enrichPrompt()` and `sendRequest()` — but neither function reads it yet, so today it's a silently-ignored extra argument. This session (`b`) makes both functions actually use it: forward it into their own existing `logActivity()` calls, and forward it one layer further into `fetchSection()` so the still-unwired embedding calls (`queryRAG()`/`queryContent()`, kickoff `c`) will already be receiving a real `trace_id` the moment `c` teaches them to log it — no second threading pass needed.

**Why split from `a`:** `a` touches the recursive checkpoint/resume loop (`execute.js`) — the riskiest, most failure-prone code in this area (`AA-195` shipped last session fixing a real bug there). `b` touches two files that don't recurse and don't checkpoint — pure "read a param, pass it along" plumbing. Shipping and live-verifying `a` first means a bug found in `b` can never be confused with a bug in the loop itself.
