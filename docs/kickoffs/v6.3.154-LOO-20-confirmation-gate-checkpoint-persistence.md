## CONTEXT

**This is LOO‑20, root-caused live from a real broken run — not guesswork.** It is the confirmation-gate half of the same "persist-on-checkpoint, recover-on-resume" gap that `AA‑145` (`task_context`) and `AA‑148` (`delegation_required`) already closed for their fields. `ARCHITECTURE.md` §19d already documents this exact gap ("Known gap, found live 2026‑07‑22") and predicts this exact fix.

**What breaks, from the DB:** on 2026‑07‑27 a user ran a forecast (theory → "Create Forecast"). Nadia's `data-analysis`/`data-patch-intent` turn ran fine (647 output tokens, `ai_activity_log` id 20168) and produced a full draft. But the Draft Forecast card came back **empty** and **no `pending_confirmations` row was written** (newest in that table is 2026‑07‑22). The `durable_hops` row for that run (id `0dff0618-814b-4bcb-a14a-b3e5ac1a947a`, created 14:03:46, resumed to `complete` at 14:04:12) holds the answer: Nadia's actual draft is sitting under `result.content` (`{action:"opinion", content:"Greater China's multi-year revenue decline…", …}`), and the result has **no `proposed_action`, no `confirmation_id`, no `status`**.

**Mechanism:**
1. `data-patch-intent` now delegates for real (`CHI‑60`). Its `request_help`→Michelle round trip realistically exhausts the ~60s hop budget, so the loop **checkpoints** (that's why a `durable_hops` row exists at all).
2. `resumeCapability()` picks it up, but all three of its `runLoop()` call sites hardcode `requiresHumanConfirmation: false, critiqueCapabilitySlug: null, critiqueIntentSlug: null` — because those override fields are **not persisted** on `durable_hops`, so the resume cannot recover them.
3. Nadia's resumed final turn produces her `tool_input` (the proposed action), but the gate at `execute.js:743` is now `false`, so it falls through to the plain terminal return at `execute.js:774–785` — `sendRequest` result, **no `insertPendingConfirmation`**, no `proposed_action`/`confirmation_id`.
4. Client-side `onCommit` sets `hypFlow.confirmation` from an empty object → the card renders Nadia's header and nothing else.

**Two faces of one bug.** §19d and the `LOO‑20` row describe the *data-integrity* danger (a `promote` write could complete unseen). This run exposed the *visible-breakage* face: even when nothing is written (here the action was `"opinion"`, no Library write), the card still breaks. One fix closes both.

**Client is already correct — do not touch it.** Verified: `resolveInProgress()` (`MarketIntelligenceScreen.jsx`) exits its poll on any non-`in_progress` status, and `callCapability()` returns any `status`-bearing result as-is (L1257). Once the resume path returns the `{status:'pending_confirmation', …}` shape, the existing client fills the card unchanged.

**Task 4 — `api/capabilities/execute.js`: mark the durable row terminal when the gate fires on a resumed job.** The confirmation branch returns at `execute.js:771` **without** patching the `durable_hops` row. On a fresh call that's fine (no row), but on a resumed one it leaves the row orphaned at `in_progress` and re-resumable into a **duplicate** `pending_confirmations` insert. Before the `return { status: 'pending_confirmation', … }` at L771, add:
```js
if (job_id) {
  await patchDurableHopRow(job_id, {
    status: 'complete',
    result: { status: 'pending_confirmation', confirmation_id, proposed_action: turn.tool_input, critique, depth, agent_id, capability_slug },
  });
}
```
Mirrors the plain terminal path's own `if (job_id) patchDurableHopRow(job_id, {status:'complete', result})` at L782–784, and makes a stray re-resume idempotent via `resumeCapability()`'s existing already-terminal early-return (L968–970). The `'continue'` handler's LOO‑17 linked-confirmation lookup (L1253–1255) is unaffected — a freshly-gated confirmation has no `checkpoint_job_id` link (only the accept→delegate path calls `linkCheckpointJob`), so `getConfirmationByCheckpointJobId` returns null and nothing else fires.
