## The named deviation — the ticket's own root cause is half wrong

`SES-220` places both defects *"in `public._backup_schema_ddl` / the dump's column selection …
**NOT** in `dump-supabase.mjs`"*. Measured against the live view this cycle:

```
caller_ip_masked text GENERATED ALWAYS AS (
CASE
    WHEN (caller_ip IS NULL) THEN NULL::text
    ...
END) STORED,
```

`_backup_schema_ddl` **already emits the column faithfully**, so the restored *table* is correct
and there is nothing to repair on the schema path. The failing statement is the **INSERT** — and
both it and the over-wide `SELECT` are issued by `dump-supabase.mjs` / `restore-supabase.mjs`,
which live in the **offsite repo and are not in this clone**. So the ticket's own instruction
cannot be carried out as written, and the honest scope is smaller than the ticket implies.

**Consequence, stated rather than smoothed over: this ship fixes neither defect.** It ships the
in-repo half — the database publishing the machine-readable truth the offsite scripts need — and
`SES-220` closes `partial`, not `delivered`.

## What shipped

1. **Migration `ses220_backup_inventory_loadable_columns`** — `public._backup_inventory`, the view
   the dumper reads its table list from, gains two appended columns:
   - `loadable_cols` — every live column except `STORED GENERATED` ones, `quote_ident()`ed.
   - `jsonb_notnull_cols` — that relation's `jsonb NOT NULL` columns. For these and only these an
     NDJSON `null` is unambiguous, because SQL `NULL` could never have been dumped *out of* a
     `NOT NULL` column — so the loader may coerce it back with `'null'::jsonb`.

   `CREATE OR REPLACE` with the three original columns **first** and the new two **appended** is
   the one shape Postgres accepts without a `DROP`, so the view's grants survive and no second
   definition can linger. Column comments carry the definitions (the `SES-218` precedent).
2. **`docs/runbooks/restore-from-backup.md`** — §9 records the contract, the named deviation, the
   forbidden edit, the two-27s warning, and what this ship deliberately does not do.
3. **`tests/regression/SES-220-loadable-columns.js`** — new guard, Part A + Part B.

## What was deliberately not done

- **The 2 poisoned `pending_confirmations` rows were not patched.** Rewriting live application data
  to work around a tooling defect hides it and leaves the class armed for `durable_hops` — 73 MB,
  3 `jsonb NOT NULL` columns, the largest table on the platform.
- **`SES-191.blocked_by` was NOT cleared.** Directive `b3475af4` conditions that on `SES-220`
  reaching `done`; it reaches `partial`. The re-drill cannot score better until the offsite half
  lands *and* a fresh set is dumped, so clearing it would hand the next cycle a ticket that still
  cannot move.
- **`GENERATED ALWAYS AS IDENTITY`** is a named unhandled shape with a zero population — it needs
  `OVERRIDING SYSTEM VALUE`, not omission, and omitting it would drop primary keys.
- **No dump was taken.** Directive `1c9609de` pre-authorises drill dumps, but a dump is only useful
  once the offsite loader consumes this metadata, which is not this cycle's to change.
