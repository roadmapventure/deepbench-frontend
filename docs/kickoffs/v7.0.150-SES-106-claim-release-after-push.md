## The defect, in one sentence

`docs/runbooks/runner-cycle.md` step 7 tells a cycle to clear its ticket claim **in the same
UPDATE that sets the ticket's status**, and two bullets later tells the same cycle that
re-asserting that claim is a **hard gate on the push** — so by the time the gate runs, the token
it checks has already been dropped by the cycle's own previous instruction.

## Why it is not a harmless wording clash

The re-assertion gate exists because of a measured near-miss: cycle `633fe486` (directive
`c4d95dc7`, `v7.0.123`) kept working for ~8 hours after losing its coordination token, came one
command short of pushing a duplicate to `dev`, and was saved only by an incidental `git fetch`.
The gate is the enforcement point that near-miss bought. A cycle that follows the close-out
bullet literally re-asserts a claim it just cleared: the `SELECT` returns **0 rows**, which the
runbook defines as *"your claim is gone — do NOT push"*. Followed to the letter, the two rules
deadlock every ship. In practice cycles have been resolving the contradiction by hand, each one
picking an order — which is exactly the class of silent, per-cycle re-derivation that
`SES-86` phase 3 and `v7.0.146` were both filed to end.

## The order the runbook will state

```
status write (before-image first; claim UNTOUCHED)
  → recompute_backlog_queue()
  → re-assert the claim            ← the gate; 1 row required
  → git fetch / rebase / push HEAD:dev
  → release the claim              ← one holder-guarded UPDATE, only now
```

Abort or wall-stop: no push, so the release happens at the stop point instead. A claim that is
never released still expires on the 24h boundary, so no ordering choice here can strand a ticket.
