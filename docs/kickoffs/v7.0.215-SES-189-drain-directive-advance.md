  *"the retired `ses142` body picks SES-154"*).

**This session ships the function-side loop.** Three reasons, stated so John can Reject on the
record if he meant the runbook form:

1. **A rule each cycle must remember is a rule that gets silently forgotten.** `runner-cycle.md`

   consumes step 5's — so the chain declines to continue while a real pick is sitting behind a

3. **The outcome the ticket asks for is unchanged either way:** *"acts on the first

# QA — DISCRIMINATING, AND WHY THE FIXTURE IS ROLLED BACK RATHER THAN CLEANED UP

The ticket's own QA design is the right one: *two retire-ready directives ahead of a pickable one;
the old body ships a board ticket, the fixed body returns the pick, same cycle.* Two constraints
shape how it is run:

- **A runner may never create a drain row** (standing prohibition, `drain_epic_next` property 5) —
  and a QA fixture is still a drain row. Worse, a committed fixture drain is visible to the peer
  cycles running right now (`register B42`), which could pick from it.
- So the entire fixture — the control function carrying the **old** body, three directives, their
  scope rows — is created and exercised inside **one transaction that is rolled back**. Uncommitted
  rows are invisible to every other session under read-committed, and nothing is left to clean up.
  This is *stronger* than the step-7 "before-image then clean up after" rule, not an exemption from
  it: no row is ever committed for a before-image to describe.

**Would it still pass if the change did nothing?** No — that is the point of the control. Same
fixture, same instant, one variable (function body): the retired body must return `retired` and no
`backlog_id`; the shipped body must return `pick` naming the third directive's member, having
retired both stale directives in that same call.
