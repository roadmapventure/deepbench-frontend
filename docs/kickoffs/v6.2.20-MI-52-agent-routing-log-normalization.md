## 2. CONTEXT

The Agent Routing log (desktop: `AuditColumn`'s "Agent Routing" `Drawer`; mobile: `MobileBody`'s pinned condensed feed — both render from the same `RoutingEventRow`/`describePipelineEvent()`) is fed by two event systems built independently, in different sessions, that were never unified:

1. **Checkpoint events** (`MI-04`→`MI-19`→`MI-23`, etc.): `intent_routing`, `qa_answer`, `proofreader`, `hypothesis_test`, `memory_consolidation`, `patch_proposed`, `agent_selection`, `display_format`, `hypothesis_generation`. Each has a `capability` (renders the subline), a `summary`, a `color`, and (from the push call site) a `durationMs`. Logged once per capability call that actually completed.
2. **Live delegation events** (`MI-42`/`MI-47`/`MI-48`): `delegation`/`delegation_return`. Fired in real time while a hand-off is in flight, mirroring the chat status line. By deliberate design (`describePipelineEvent()`'s own case: `capability: null`) these have no subline and no duration (`durationMs: null`, "in-flight signal, not a completed duration" per the `MI-47` code comment). `STYLE-GUIDE.md` §5 (`MI-47`'s "Drawer logging" note) confirms this was explicitly additive — "alongside the pre-existing coarse checkpoint events... does not replace/dedupe any existing event type."

That split is the root cause of most of what John flagged. Two additional confirmed bugs, found by reading the actual event-push call sites, not just the rendered output:

- **Duplicated duration:** `agent_selection` and its sibling `display_format` (in `runQaWithQualityGate()`, lines ~517–527; and the parallel hypothesis-test path, lines ~610–619) share one `t0` — the client only ever observes one real round-trip time for the underlying `callCapability()` call, so both rows show the identical number (confirmed live: two screenshot rows both read `33.4s`, two others both read `18.3s`). Two other `agent_selection` call sites (lines 476, 502 — Marcus's/Owen's own internal `request_help` hops) hardcode `durationMs: 0` instead, a third, different behavior for the same event type.
- **Arrow/secondary-agent semantics are inconsistent:** today's `secondaryAgentId` sometimes names who a call is handing off *to* (`delegation` events), sometimes names the actual reasoner while the visible arrow points at the *requester* instead (`agent_selection`: `agentId` = requester, `secondaryAgentId` = the PM broker who reasoned — but the *picked* candidate named in the row's own text never gets an avatar at all).

**Confirmed accurate, not a bug (checked, not assumed):** the `confidence_tier` em-dash rendering John also flagged is `describeDataType()`'s own `default` case (`{label: "—", ...}`) firing correctly when a call's `data.confidence_tier` is genuinely null/missing — real upstream data-completeness gap on specific calls, not a display defect. No fix needed or attempted here.

**Explicitly out of scope, logged separately (`AI-50`, `docs/FEATURES.md`):** John separately asked whether the pattern list shown in this drawer's subline, and the AI Audit screen's "By Pattern" call counts, are accurate. They are not — both are static/rolled-up from `SERVICE_CATALOG`'s hardcoded per-service pattern tags, not derived from real per-call data (confirmed: `buildPatternsUsed()` already writes a real, narrower `patterns_used` array to `ai_activity_log` on every call, but nothing in the frontend reads that column, anywhere — grepped, zero matches). Fixing this properly needs backend instrumentation work (extending `buildPatternsUsed()` to capture RAG/Case-Based Reasoning/Memory Consolidation/etc. at the call level, not just its current 3 mechanical categories) before either display surface can show it — bigger than this session, and shared across two screens, so it's tracked as its own item rather than folded in here.

### Task 2 — Replace in-flight delegation rows with their real completion event, don't append both

**Problem:** `logEvent()` (~line 1493) is strictly append-only: `setPipelineEvents(prev => [...prev, {...evt, id: prev.length}])`. `onDelegationProgress` (~line 1498) logs every live `delegation`/`delegation_return` narration as its own permanent row via this same function — nothing ever removes or updates it once the real outcome (a checkpoint event) lands, so both sit in the list forever (the doubled-up pairs John saw: "Marcus is asking Michelle…" + "Alex Reeves is the clear fit," etc.).

**Fix:**
- Give `logEvent` a second, additive call shape: `logEvent(evt, { replaces: correlationKey })`. When `replaces` matches a still-pending in-flight row's own stored key, splice/update that row in place (same array index, same `id`) instead of appending a new entry. Everywhere else, `logEvent(evt)` behaves exactly as it does today (backward-compatible, not a rewrite of the function's contract).
- Correlation key for a `delegation` event: `${fromAgentId}:${toAgentId}:${viaTool}` (all already present on the event `onDelegationProgress` receives). The row that should replace it is the next event logged whose `agentId` matches that `toAgentId` — since only one agent ever executes at a time on this platform (confirmed elsewhere in the codebase/design history), the very next event for that agent is unambiguously its outcome; no fuzzier matching needed.
- Correlation key for `delegation_return`: same shape, keyed on the returning agent (`toAgentId` on the return event). Confirmed via `api/capabilities/execute.js` (~line 578) that `delegation_return` only fires on the non-terminal loop-continuation path and is always immediately followed by another turn for that same `agent_id` — which will always produce its own checkpoint event (e.g. Owen's retry-via-Marcus produces a subsequent `proofreader` row). No dead-end case where a `delegation_return` would be stranded with nothing to replace it.
- **If a delegation row is never replaced** (e.g. the request errors before completing), it must stay visible exactly as logged — never silently removed. Only a genuine completion replaces it; absence of one is itself real information, not something to hide.

### Task 3 — Fix the duplicated-duration bug on `agent_selection`/`display_format`/`proofreader` pairs

Per Task 1, `agent_selection` becomes the picker's own reasoning row and `display_format` becomes the formatter's completion row — they describe two sub-phases of one un-separable server round trip (one `callCapability()` call, one client-observable elapsed time). Showing the same number on both is not two independent measurements; it's one number copy-pasted onto two rows.

- **Fix:** the row that completes the round trip (`display_format`) keeps its real `durationMs: Date.now() - t0`. The paired `agent_selection` row shows no duration at all (`durationMs: null`) — honest "not separately measurable from the client," not a fabricated split.
- Apply the same treatment to the two hardcoded-`durationMs: 0` `agent_selection` sites (lines 476, 502, Marcus's/Owen's internal `request_help` hops) — `0` reads as "instant," which isn't true either. Use `durationMs: null` there too. (The real, already-measured durations for the surrounding calls remain correctly shown on their own `qa_answer`/`proofreader` rows — nothing about those changes.)

## 6. DESIGN RULES

- Every visible row names exactly one agent — first name + role, no arrows, no second avatar, ever.
- A row shows a duration only when it was independently, actually measured for that specific step — never a duplicate of a sibling row's number, never a fabricated `0`.
- In-flight delegation narration is transient by intent: shown live while genuinely waiting, replaced by the real outcome once it lands. It is never left as a permanent, separate "nothing happened yet" record once something did.
- If a genuine "still waiting, never resolved" state exists (an error path), it stays visible honestly — replacement only happens on an actual completion, never assumed.
