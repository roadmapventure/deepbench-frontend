## The five tables that could not load, each root-caused

Each was diagnosed by replaying the script's own 500-row batching outside it, because the script
prints the underlying HTTP error only on pass 6 and its stall guard breaks at pass 1.

| table | rows | error | cause |
|---|---|---|---|
| `ai_activity_log` | 34,761 | `428C9` | `caller_ip_masked` is `GENERATED ALWAYS`; the dump writes it |
| `ip_org_cache` | 24 | `428C9` | same |
| `pattern_candidates` | 124 | `23503` | FK to `ai_activity_log` — **cascading**, not independent |
| `pending_confirmations` | 312 | `23502` | 2 rows hold the JSON scalar `null` in a `jsonb NOT NULL` column |
| `runner_secrets` | 5 | `23502` | redacted offsite values are `NULL` against a `NOT NULL` column |

The `pending_confirmations` one is the subtle one and it is worth stating precisely: those two rows
are `'null'::jsonb` — `pg_typeof` `jsonb`, `length(…::text)` = 4 — which **satisfies** `NOT NULL`.
Production has **zero** SQL `NULL`s in that column. NDJSON cannot distinguish a JSON `null` from a
SQL `NULL`, so the value is legal going out and illegal coming back. No manifest, checksum or
`--verify-only` can ever see this; only a real restore can.

| `ai_activity_log` | **ok 1** | **`42501` denied** | ✗ *column grant missing* |

The `backlog_active` row is the one most likely to be misread: a **denial reproduced faithfully** is
evidence the grant restore is correct, not a failure. Production denies `anon` there too.

The `ai_activity_log` row is the real divergence, and it is defect (2) of `SES-216`: production
carries **column-level** ACLs on `ai_activity_log` (27 columns, `caller_ip` excluded — the
`LOG-124` privacy fix) and `ip_org_cache` (7 columns), and `schema.sql` reads `pg_class.relacl`
only, never `pg_attribute.attacl`. **No backup set contains them in any form.**

**The trap that finding sets, named here because the next cycle will walk into it:** the obvious way
to bring the AI Audit screen back on a restored platform is `GRANT SELECT ON ai_activity_log TO
anon`, and that **rebuilds the `LOG-124` leak** — every visitor IP publicly readable, the exact
incident `.claude/rules/supabase-column-grants.md` exists to prevent. The correct restore is the
column list.

## Charter exit criterion 5 is NOT scored, and that is the honest answer

The criterion reads *"one full restore-from-backup drill … executed **successfully**."* A restore
that returns a third of the rows, needs a hand-built grant repair to start at all, and rebuilds a
platform whose largest audit table is empty and whose Audit screen is dark has not succeeded.
Scoring it green here would be the same falsehood as scoring it on the structural half was at
`v7.0.285`. `SES-191` stays `partial`; it is the re-run after `SES-216` and `SES-214` land that
scores the criterion.

**What did change**, and it is most of the remaining unknown: before this cycle, nobody knew whether
the data in the recovery net was recoverable at all. Now it is measured — 51 tables exactly, 5
tables not at all, and each of the 5 with a named, reproduced root cause.

## What was deliberately NOT done

- **The four defects were not fixed.** Three of them live in `public._backup_schema_ddl`, a
  **production** view, exactly where `SES-214`'s two already sit; fixing them changes what every
  future dump contains and needs a re-dump to prove. That is `SES-216`, filed this cycle, not a
  widening of a ticket claimed for the drill. Same boundary `v7.0.285` kept for `SES-214`.
- **`anon` was never granted anything it does not hold in production.** The grant repair
  reconstructs the set's *recorded* ACLs and nothing else — `anon` on `ai_activity_log` came back
  as `INSERT, MAINTAIN`, which is why the read is denied. The `v7.0.290` cycle's refusal to
  force the load through a temporary `anon` write grant is upheld, not quietly reversed.
- **Nothing was written to production** beyond this cycle's own ledger rows and the `SES-216`
  filing. No migration, no schema change, no site change.
