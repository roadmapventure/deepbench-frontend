## CONTEXT

Second of two root causes behind the live Channel Sales Intelligence Q&A failure investigated this design session (see `S-ARCH-DURABLE-RESUME-02`'s kickoff for the other). Owen's Quality Gate correctly blocked Marcus's answer as `synthesized_as_fact`: Marcus cited 5 specific Data Room entry IDs but asserted specific numeric benchmarks (training completion rates, annual turnover, retention, co-op/MDF utilization, fund leakage, claim processing timelines, partner onboarding windows) that Nadia's triage confirmed were not actually verifiable as present in those entries. The guardrail did its job — this session is not about the guardrail, it's about why the underlying answer was ungrounded in the first place.

**Root cause, confirmed via `api/prompt/db-assembly.js`:** every Knowledge Skill Profile's RAG fetch is hardcoded to `match_count: 5` (line 73), with no per-profile override — already flagged in `CLAUDE-STATE.md`'s queue as `AA-173`'s follow-up. Marcus's own `ci-knowledge` Skill Profile (`source: the_library`, `intent_allowlist: ["ci-answer-intent"]`, confirmed via direct Supabase query — no `match_count` trait set today) retrieves only 5 chunks for every question, including broad synthesis questions spanning many partner scenarios and GEOs. When the real supporting data for a specific claim isn't among those 5 chunks, the model can still produce a plausible-sounding, specific-sounding number from its own general reasoning rather than the retrieved context — and (per `AA-155`/`AA-156`'s still-queued citeable/UUID-validation gaps) nothing today forces every asserted number to trace back to a chunk actually in context.

**The fix, scoped narrowly:** `api/prompt/ai-enrichment.js`'s consumer side already reads `fi.match_count || 5` (an existing, generic per-fetch override — confirmed by reading the file, not assumed). The only gap is that `db-assembly.js` never populates `fi.match_count` from anything — it's a bare literal. This session threads an optional `traits.match_count` through, mirroring the exact pattern already used for `traits.source`/`traits.data_room_tag` (generic opt-in trait, not hardcoded to any agent). Then sets `ci-knowledge.traits.match_count: 10` via direct Supabase update — a content change, not a code change, scoped to the one Skill Profile with live-confirmed evidence of the gap. No other Knowledge Skill Profile is touched — there's no evidence today that any other agent has the same problem, and per `feedback-scope-live-tests-to-novel-risk`/this session's own "one feature, no scope creep" discipline, this isn't the session to speculatively widen everyone's retrieval.

**Honest limitation, stated up front:** widening retrieval breadth reduces the *chance* the real supporting data is in context — it does not guarantee every number the model states is grounded, and it does not replace `AA-155`/`AA-156` (citeable/UUID validation, still queued, still the structural fix for "is this claim actually traceable"). Owen's Quality Gate remains the real backstop. This session is a targeted mitigation of the specific gap this live question exposed, not a claim that fabrication is now impossible.
