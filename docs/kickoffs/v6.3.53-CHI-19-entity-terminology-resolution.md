## 2. CONTEXT

John flagged live (2026-07-17, design session `design-chi-ux-0717`): Marcus Webb — GEO CSO Expert's Q&A answers dive straight into partner-specific findings (e.g. "Nordholm is using 55%...") without ever stating which real-world entity a generic question ("our EMEA retail partner") resolved to — question and answer read as if about two different things.

**Ticket's own proposed fix location was wrong — corrected this session, verified live against Supabase, not assumed from the ticket text (`docs/FEATURES.md`'s own instruction on this row: "verify live against Supabase first"):**

- `docs/FEATURES.md`'s `CHI-19` row named `qa-answer-format` (`method`/`output_desc`) as the target. Live query confirmed `qa-answer-format` is not attached to the `channel-intelligence` capability at all — `capability_skill_profiles` shows it belongs to `screen-controls`, and `agent_capability_assignments` shows `screen-controls` is owned by Alex Reeves — Screen Controls Editor, not Marcus.
- `qa-answer-format`'s own `method` text explicitly forbids the kind of change CHI-19 needs: *"Never invent, add, or omit facts... your only job is presentation structure... never content judgment."* It only reformats whatever raw answer text it's handed — it has no access to *why* an entity was named, only the finished text.
- The actual content generation happens one step earlier, in **`ci-answer-intent`** — confirmed via `capability_skill_profiles` to be genuinely attached to `channel-intelligence`, and via `agent_capability_assignments` to be assigned to `marcus` alone. Its `traits.schema` requires a free-text `answer` field — this is where the opening sentence is actually written.
- **Also confirmed: `output_desc` is not a valid second target either**, for a different reason than `qa-answer-format`. Reading `api/prompt/db-assembly.js`'s `typeSlug === "intent"` branch (lines 123-128) shows only `sp.objective`, `sp.method`, and `traits.analysis_instructions` are concatenated into the model prompt for Intent-type Skills — `output_desc` is never read into the prompt at all (same shape as the `AA-167` finding for Format-type Skills, one type over). `ci-answer-intent.output_desc` is currently `null`; editing it would have zero effect on model behavior. **This session touches `method` only.**

**Second correction, from John's own follow-up this session:** the first draft fix ("Our EMEA retail partner is Nordholm Retail Group, which is using 55%...") named the entity but still didn't establish *why* Nordholm is "our EMEA retail partner" — a bare name swap, not a real resolution. Checked the actual Data Room record (`the_library`, id `1c7104c5-9bc1-4ee7-9b61-d6070dc5aba8`, `data_type: synthesized`): *"Nordholm Retail Group, a 34-store consumer electronics chain operating across Germany and the Netherlands and one of Apple's larger EMEA authorized resellers..."* — the real relationship is "EMEA authorized reseller," not just a label. The fix must pull the entity's relationship/role from whatever the retrieved record actually says, not restate a fixed fact — a future Data Room entry will have a different partner with a different relationship, so this can't be hardcoded into the instruction text.

**Third addition, John's follow-up:** John also asked what "EMEA" itself is — confirmed it's a standard geographic/business-region abbreviation (Europe, the Middle East, and Africa), not an organization or entity. Checked `the_library`'s own `geo` column values to confirm this is how the platform already uses the term: `Americas`, `Brazil`, `EMEA`, `EMEA Emerging`, `Europe`, `Greater China`, `India`, `Japan`, `Latin America`, `Southeast Asia` — a region list, consistent with the standard meaning. John's resulting instruction: the first time an answer uses an abbreviation like this, spell out the full term before abbreviating; on later use **within the same chat**, it's fine to abbreviate without redefining.

**Verified this session that "within the same chat" is checkable by the model, not just an aspiration:** `MarketIntelligenceScreen.jsx`'s `conversationContext()` (line 2592) joins every prior message in the current chat into plain text and passes it as `runtime_context` on every `ci-answer-intent` call (`runQaWithQualityGate`, line 1068). Server-side, `api/prompt/db-assembly.js` (lines 509-527) injects this verbatim into the model's prompt as a `PRIOR CONVERSATION (context only...)` section, placed before `CURRENT TASK`. Marcus genuinely has the full prior chat transcript available to check against before deciding whether to re-expand an abbreviation.
