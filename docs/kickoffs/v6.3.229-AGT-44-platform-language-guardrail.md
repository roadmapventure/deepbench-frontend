## 2. CONTEXT

**Agents write text a VP of Channel Sales reads, and that text currently narrates how DeepBench works instead of answering the business question.**

Measured live, 2026-07-29 pre-regression check (`design-arch-beta-0729`, 3 cases, 9 min — full result in `docs/BETA.md` §3 bucket 1): **4 artifacts failed `platform_language_detected`, and 3 of them failed nothing else.** Every other criterion passed with real quoted business content. Owen — Proofreader's verbatim critique: *"Platform back-office narration dominates."* It is not confined to one agent, one artifact type, or one case — `theory_test` and `forecast_draft` both leaked, on both case 9 (a direct question) and case 6.

**Root cause, verified live in Supabase this session.** The standard *"write business content, not platform narration"* exists in exactly one place on the platform: inside Owen's own `qg-content-context-intent` judging criteria. It appears in **no** producing agent's Skill. The writers are graded on a rule they were never given. Priya Nair — Forecast/Theory/Performance Expert's Skill goes further and hands her a worked sentence that commits the violation — her `hyp-hypothesis-test-intent.method` tells her, when a section would be empty, to write *"I checked for contradicting figures, missing agreements, and timing gaps, and found none in the Data Room."*

**The mechanism, John's call.** One shared Guardrails Skill carrying the standard, attached to every Capability whose output a user reads. Not per-agent copies of the same prose — one row, four attachments, zero lines of code. `api/prompt/db-assembly.js` already composes multiple Skills per Capability and already renders a `guardrails`-type Skill as a `CONSTRAINTS & GUARDRAILS` section; nothing in the assembler changes.

**Why this is not the banned-phrase list rejected earlier the same day** (`AGT-36`/`AGT-41`, John's explicit distinction, 2026-07-29): that rejection was about verifying whether *a number is real* — where no known-correct value exists to substitute, so a blocklist would be a content hardcode. This is a **writing standard**: who the reader is and what good content looks like for them. The governing precedent is the shipped **VOICE** section in `db-assembly.js` (`AA-127`) — a platform-wide register instruction, appended to every call, created for the identical failure shape (*the model mirroring third-person framing from its own instructional text*) and explicitly covering the same structured fields. This Skill is that pattern, expressed as data instead of a hardcoded string.

**Three facts that shape the tasks, all verified live this session:**
1. **No Capability on the platform has a Guardrails Skill today** — every one is identity + behavior + knowledge + intents. This is the first.
2. **`skill_types` has no `guardrails` row**, and `skill_profiles.skill_type_slug` carries a foreign key to it (`skill_profiles_skill_type_slug_fkey`). The type row must be inserted first or the Skill insert fails.
3. **No Skill is currently attached to more than one Capability.** `capability_skill_profiles` is many-to-many in shape and this is the first shared Skill — deliberate, not accidental.

### Task 1 — the `guardrails` Skill type, then the Skill itself (`skill_types` + `skill_profiles`)

**1a.** Insert the missing type row. Existing rows for reference: `identity` (display_order 1), `behavior` (2), `knowledge` (3), `intent` (4), `format` (5).

```sql
INSERT INTO skill_types (slug, name, description, display_order)
VALUES ('guardrails', 'Guardrails', 'Constraints the agent must respect in what it produces', 6);
```

`6` matches `SKILL_ORDER.guardrails` in `db-assembly.js`, which already expects this slug.

**1b.** Insert the Skill. **The rule text goes in the `guardrails` column — NOT `method`, NOT `objective`.** This is load-bearing: `buildSections()`'s `guardrails` branch reads only `sp.guardrails` (plus `agent_configs` guardrail entries). Text placed in `method` or `objective` is **silently dropped** — the model never sees it, and every text-level check still passes. That is precisely the failure `AGT-36b` shipped into QA (`STANDARDS.md` Section 5, "A Skill's instruction text and its output schema change together").

Use a **jsonb array of strings**, not the `{must, must_not}` object shape the intent Skills carry. The branch spreads an array into the section verbatim (`if (Array.isArray(g)) guardParts.push(...g)`); an object is `JSON.stringify`'d into the prompt as raw JSON.

```sql
INSERT INTO skill_profiles (slug, name, description, skill_type_slug, guardrails, traits, technical_services, execution_type, tenant_id)
VALUES (
  'platform-language-guardrail',
  'Business Content Standard',
  'Platform-wide content standard for every agent whose output a user reads: business content for a VP of Channel Sales, never narration of platform machinery.',
  'guardrails',
  '["Your reader is a VP of Channel Sales who will act on what you write. Every field you produce is business content for that reader -- not a status report on how it was produced.",
    "Write what you found and what it means for the business. Do not describe the machinery that produced it: never name the Data Room or any other store, delegation or hand-offs, capabilities, intents, skill profiles, tool calls, field names, agent routing, hops, pipelines, or review/flagging/consolidation status.",
    "When something is missing, say what is missing in business terms and what would resolve it. \"No comparable partner has reported this\" -- never \"the Data Room contains no record of this\".",
    "This applies to every field you emit, including structured ones such as supports, complicates, consider, content and critique -- not only conversational replies."]'::jsonb,
  '{}'::jsonb,
  '[]'::jsonb,
  'ai',
  (select tenant_id from skill_profiles where slug = 'hyp-hypothesis-test-intent')
);
```

Read the `tenant_id` off an existing row as shown rather than hardcoding a literal.
