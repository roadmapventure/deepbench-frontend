## CONTEXT

Found live-verifying `MI-19`'s Pipeline Log rendering (2026-07-07): asked "How is our authorized reseller network performing in Vietnam?" after an earlier "Japan is Apple's fastest-growing GEO" question in the same session. Marcus answered about Japan again — the wrong question entirely. Owen's Proofreader correctly caught it (`eval.result: "revise"`, `critique: "Answer addresses Japan's growth drivers instead of Vietnam's reseller network performance — a complete topic mismatch"`), but the final chat card rendered completely blank instead of showing anything. Pulled the real `deliverables` rows for this exact run from Supabase — two distinct, unrelated root causes, confirmed from real data, not guessed:

**`AA-136` — prior conversation renders after, not before, the current task.** `assemblePrompt()` (`db-assembly.js`) builds an ordered `sections` array. The current-turn goal gets pushed as a `CURRENT TASK` section (today still labeled `WORK ORDER` — see rename below) with `order: 2.5`, and the array is sorted immediately after (`sections.sort(...)`, lines 420/445). But the `runtime_context` (prior conversation) section is pushed **after** that sort, with **no `order` field at all** (lines 449-455) — so it silently lands at the literal end of the array (`.push()` appends), after `CURRENT TASK`, right before the always-final `VOICE` section. Since the model reads whatever comes last as most current/salient (the same reasoning `AA-127` used to justify placing `VOICE` last on purpose), a prior turn's topic sitting closer to the end of the prompt than the actual current goal can win out. Confirmed via the real routing call too: `ci-routing-intent`'s `extracted_hypothesis` for this exact turn came back as `"Japan is Apple's fastest-growing GEO in 2025"` — the *previous* turn's text, not this one's — consistent with the model treating older conversation content as more salient than intended. **Second, smaller defect in the same block:** that same runtime_context section object never sets `.label` at all — `renderSection()` (`ai-enrichment.js`) renders every section as `` `=== ${section.label} ===\n${content}` ``, so this section currently renders with a literal `=== undefined ===` header, which cannot be helping the model recognize it as "prior conversation, not your instructions." Both defects share one cause (this section was never built as a first-class, ordered section like every other one in this function) and are fixed together.

**Platform-wide, not `channel-intelligence`-specific:** `assemblePrompt()` is shared infrastructure — every capability that passes `runtime_context` (any multi-turn interaction on the MI screen: two Q&A questions in a row, a Q&A after a hypothesis test, etc.) is exposed to this, not just the exact repro path.

**Bundled rename, per John's request:** the section is labeled `WORK ORDER` today — a name that predates its current use as `assemblePrompt()`'s generic "here's this call's goal" section (per its own existing comment: "no duplicate task text for existing `.goal`-shaped callers (`api/plan.js` Work Orders)" — `api/plan.js`'s real Work Order flow was the original, only caller). Every other capability using `assemblePrompt()` today (Q&A, hypothesis tests, quality-gate reviews — none of which are Work Orders in the screen/feature sense) also gets this label, which reads as a direct reference to the unrelated Work Order screen/feature. Renamed to `CURRENT TASK`, unambiguous regardless of caller. Confirmed via repo-wide grep: `WORK ORDER`/`work-order` appear nowhere outside this one file — zero cross-reference risk.

**`AA-137` — a legitimate display-agent refusal renders as an empty card, discarding real content.** Same incident: Marcus's `ci-answer-display-intent` call recognized the topic mismatch itself and declined to call `request_help`/`delegate_to_agent` — instead returning a plain-text explanation ("This is a topic mismatch, not a formatting problem... did you mean to ask about Vietnam?"). `callCapability()` returns whatever `result.content` is; when the model's final turn is plain text rather than a tool call, that's a raw string, not the expected `{headline, body, ...}` object. `runQaWithQualityGate()`'s return statement (line 230-236) reads `display.headline`/`display.body`/etc unconditionally — all `undefined` off a string — so the card renders with just the agent name and nothing else. The model's own useful, self-aware message is silently discarded. **Same defect exists in `runHypothesisTest()`** (line 296, `return display;` directly) — any consumer reading `st.supports`/`st.headline`/`st.display_agent_card` would hit the identical blank-card failure if Priya's own display hand-off ever declines the same way; fixed in both call sites together since it's the same pattern, not two separate bugs. **This also closes `AA-135`** (logged separately during `MI-19`'s live QA as "`display_format`'s `confidence_tier: undefined`") — same root cause: `display` was a string, so `evt.data.confidence_tier` in the Pipeline Log event was reading a property off a string, always `undefined`. No separate fix needed for `AA-135` once this ships.

**Not the same bug, deliberately not touched:** fixing `AA-136` should make this specific *trigger* (topic drift) far less likely, but `AA-137`'s fallback is worth keeping regardless — a display agent can decline to format for other legitimate reasons too, and the harness should never silently discard a model's real output just because it didn't take the expected shape.

```js
  // FEATURE: AA-62 + AA-67 — CURRENT TASK section: goal + deliverable_type always present when goal
  // exists. Renamed from "WORK ORDER" (AA-136) -- this label is generic assemblePrompt() output used
  // by every capability (Q&A, hypothesis tests, quality-gate, actual Work Orders via api/plan.js),
  // not specific to the Work Order screen/feature; the old name read as a direct reference to that
  // unrelated feature.
  const goalText = typeof task_context === 'object' && task_context !== null
    ? (task_context.goal || null)
    : (typeof task_context === 'string' ? task_context : null);
  const deliverableType = typeof task_context === 'object' && task_context !== null
    ? (task_context.deliverable_type || null)
    : null;

  if (goalText && goalText.trim()) {
    const workOrderParts = [`Goal: ${goalText.trim()}`];
    if (deliverableType) workOrderParts.push(`Deliverable type: ${deliverableType}`);
    sections.push({
      slug: 'current-task',
      label: 'CURRENT TASK',
      skill_profile_slug: null,
      type: 'stored',
      content: workOrderParts.join('\n'),
      fetch_instruction: null,
      required: true,
      order: 2.5,
    });
    sections.sort((a, b) => (a.order || 0) - (b.order || 0));
  } else if (typeof task_context === 'object' && task_context !== null && Object.keys(task_context).length > 0) {
    // FEATURE: AI-44 -- TASK DETAILS: generic fallback for any capability whose task_context is a
    // plain object without a .goal field (e.g. Nadia's {disputed_chunk_id, correction, ...}, Sam's
    // {intent, hypothesis, correction_text, ...}). Without this, a capability with neither a RAG
    // section nor a Reflect section never sees its own specific task at all -- confirmed live
    // 2026-07-03 during S-APPLE-04b QA (data-patch-intent returned a generic, input-blind response
    // regardless of task_context content). Fires only when the .goal path above does NOT -- never
    // both, no duplicate task text for existing .goal-shaped callers (api/plan.js Work Orders).
    // Shape-driven, not identity-driven -- AR-1.1.
    const taskDetailsText = Object.entries(task_context)
      .filter(([, v]) => v !== null && v !== undefined && v !== '')
      .map(([k, v]) => `${k}: ${typeof v === 'object' ? JSON.stringify(v) : v}`)
      .join('\n');
    if (taskDetailsText) {
      sections.push({
        slug: 'task-details',
        label: 'TASK DETAILS',
        skill_profile_slug: null,
        type: 'stored',
        content: taskDetailsText,
        fetch_instruction: null,
        required: true,
        order: 2.5,
      });
      sections.sort((a, b) => (a.order || 0) - (b.order || 0));
    }
  }

  // FEATURE: AA-136 — runtime_context (prior conversation) must render BEFORE CURRENT TASK/TASK
  // DETAILS, not silently after. Previously this section had no `order` (landed at array-push end,
  // after the sort above -- i.e. after the actual current-turn goal, closest of anything to the
  // always-final VOICE section, read by the model as most current) and no `label` (rendered as a
  // literal "=== undefined ===" header via ai-enrichment.js's renderSection()). Both stemmed from
  // this section never being built as a first-class section like every other one in this function --
  // fixed together. order: 2.4 places it just before CURRENT TASK/TASK DETAILS (2.5) and before the
  // agent's own identity/behavior/knowledge sections (3/4/5) -- background context first, agent's own
  // instructions next, current task last before RAG/VOICE.
  if (runtime_context && typeof runtime_context === 'string' && runtime_context.trim()) {
    sections.push({
      slug: 'prior-conversation',
      label: 'PRIOR CONVERSATION (context only — see CURRENT TASK for what to actually do)',
      skill_profile_slug: null,
      type: 'stored',
      content: runtime_context.trim(),
      fetch_instruction: null,
      required: false,
      order: 2.4,
    });
    sections.sort((a, b) => (a.order || 0) - (b.order || 0));
  }
```

Also update the `VOICE` section's own comment (line 462) — it currently says "same unconditional-append pattern as the WORK ORDER/TASK DETAILS/runtime_context sections above" — change `WORK ORDER` to `CURRENT TASK` there too (comment-only, no logic change).
