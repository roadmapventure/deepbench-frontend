## 1. CONTEXT

**Found 2026-07-14 investigating why `data-analysis` (Nadia Farouk) calls showed empty `patterns_used` in AI Audit's By Pattern view (the `AI-51` follow-up question).** Traced the real root cause through the full call chain, live:

Owen's `quality-gate` flagged Marcus's answer to "what data is available that i can ask questions?" for citing 5 Data Room entry IDs as "sourced" facts with no retrieval evidence they exist — a genuine data-integrity concern. Owen delegated (`request_help`) to decide whether this warrants escalating to Eleanor for verification. That request routed through Michelle's `agent-selection-intent` (`project-manager`), who recommended **Nadia** (`data-analysis`) with `intent_slug: null`.

**Two independent, compounding problems, confirmed live via direct Supabase queries and code trace:**

**Problem 1 (code bug):** `db-assembly.js`'s `assemblePrompt()` only filters down to the one matching Intent Skill Profile when `intent_slug` is truthy (line 402: `if (intent_slug) { ...filter... }`). When Michelle legitimately returns `intent_slug: null` — an intentional, designed outcome, not a bug on her side (see Problem 2's context below) — that filter is skipped entirely, so **every** Intent-type Skill Profile linked to the target capability flows through unfiltered into `buildSections()`. Since `buildSections()`'s intent-content push (line 123-128) isn't itself gated by an intent match (it relies on the caller having already filtered), it stacks **all** of that capability's intents' `objective`/`method`/`analysis_instructions` together into one contradictory prompt — while also silently losing the schema, `can_request_help`, and `delegation_required` flags (those only copy over inside the `if (intentSlug && sp.slug === intentSlug)` gate at line 142, which never matches anything when `intentSlug` is null). Confirmed live: Nadia's resulting turn had no schema, produced a free-text response (`isJson: false`), and correctly-but-uninformatively logged zero patterns — the empty audit data was a downstream symptom of a garbled prompt, not a missing-content gap on its own.

**Problem 2 (content gap):** Michelle's roster-context builder (`lib/project-manager.js`) explicitly instructs her model: *"If a capability has no listed intents, or none clearly matches, return `intent_slug: null`"* — added deliberately after a real 2026-07-02 incident (`AA-108`/`S-ARCH-HITL-RESUME-02`) where forcing her to always guess an intent caused a **hallucinated** one, silently corrupting a downstream write. So `null` itself is by design, not a mistake. But **why she picked Nadia at all** traces to a real content gap: Nadia's 4 Intent Skill Profiles (`data-patch-intent`, `data-patch-execute-intent`, `data-escalate-intent`, `data-escalate-execute-intent`) all have `objective`/`output_desc` **null** — confirmed via direct query — so Michelle had zero real signal about what any of them actually do, only Nadia's generic capability blurb ("drafts new Data Room content or corrections"), vague enough to look plausibly relevant. Meanwhile Sam Reyes's `intake-failure-intent` — the capability actually built for exactly this task ("Given a hard guardrail failure, decide whether to offer the user an Escalate path instead of a dead end") — already has a precise, real objective authored. Same root-cause shape as `library-write-intent`'s earlier gap (`S-ARCH-ROSTER-WRITE-GUARD-01`, 2026-07-14): nobody had ever authored this specific agent's intent-level content.

**These are complementary, not duplicate fixes — confirmed with John before scoping.** Problem 1's fix is capability-agnostic (names no specific agent/intent) and stays necessary permanently: `intent_slug: null` is a deliberately-designed, ongoing possibility (capabilities with zero declared intents, genuinely novel/ambiguous requests, ordinary model uncertainty) — content authoring reduces *how often* Nadia specifically gets misrouted to, but never eliminates the null case for any capability. Problem 2's fix directly improves routing precision for this specific agent going forward.

## 4. TASKS (max 4)

### Task 1 — `api/prompt/db-assembly.js`: graceful fallback when `intent_slug` is null

Add an `else` branch to the existing `if (intent_slug)` block (~line 402-408). When no intent is specified, filter out **all** intent-type Skill Profiles instead of leaving them all in — falling back to just Identity/Behavior/Knowledge/Guardrails (the capability's baseline reasoning), the same coherent-but-general mode a capability with zero declared intents already runs in today:

```js
  if (intent_slug) {
    const matchedIntent = skillProfiles.some(sp => sp.skill_type_slug === 'intent' && sp.slug === intent_slug);
    if (!matchedIntent) {
      throw new Error(`assemblePrompt: intent_slug "${intent_slug}" does not match any Intent Skill Profile for capability "${capability_slug}"`);
    }
    skillProfiles = skillProfiles.filter(sp => sp.skill_type_slug !== 'intent' || sp.slug === intent_slug);
  } else {
    // FEATURE: AA-188 -- intent_slug is null when the routing agent legitimately couldn't map
    // the request to one specific intent (project-manager.js's own roster prompt explicitly
    // instructs this rather than risk a hallucinated guess, per AA-108's postmortem). Stacking
    // every intent-type Skill Profile's objective/method/analysis_instructions together would
    // produce a contradictory, garbled prompt (confirmed live: Nadia's data-analysis capability
    // received all 4 of her intents' instructions at once, no schema, no can_request_help).
    // Skip all intent-type profiles entirely instead -- same coherent baseline mode a capability
    // with zero declared intents already runs in, just Identity/Behavior/Knowledge/Guardrails.
    skillProfiles = skillProfiles.filter(sp => sp.skill_type_slug !== 'intent');
  }
```

No other line in `assemblePrompt()`/`buildSections()` needs to change — `buildSections()`'s existing schema/llm/`can_request_help`/`delegation_required` gate (line 142, `if (intentSlug && sp.slug === intentSlug)`) already naturally stays inert when no intent-type profiles remain in the set.

## 7. NODE.JS TEST

Save as `test-AA-188.mjs` at the repo root, run with `node test-AA-188.mjs`, then delete the file. Tests `assemblePrompt()`'s null-intent_slug fallback directly against real Supabase data (capability `data-analysis`, no `intent_slug` passed) — this is a live-data integration check, not a pure-function mock, since `assemblePrompt()` itself queries Supabase.

```js
import { assemblePrompt } from './api/prompt/db-assembly.js';

let failures = 0;
function assert(cond, label) {
  if (!cond) { failures++; console.error(`FAIL: ${label}`); }
  else { console.log(`PASS: ${label}`); }
}

const result = await assemblePrompt({
  capability_slug: 'data-analysis',
  agent_id: 'nadia',
  tenant_id: 'global',
  task_context: { test: 'AA-188 null intent_slug fallback check' },
  intent_slug: null,
});

const intentSections = result.sections.filter(s => s.type === 'intent');
assert(intentSections.length === 0, 'null intent_slug: zero intent-type sections in the assembled prompt (no stacking)');

const behaviorSections = result.sections.filter(s => s.type === 'behavior' || s.type === 'identity');
assert(behaviorSections.length > 0, 'null intent_slug: baseline Identity/Behavior sections still present');

// Regression: a REAL intent_slug must still filter down to exactly that one intent, unaffected
const resultWithIntent = await assemblePrompt({
  capability_slug: 'data-analysis',
  agent_id: 'nadia',
  tenant_id: 'global',
  task_context: { test: 'AA-188 regression check' },
  intent_slug: 'data-patch-intent',
});
const matchedIntentSections = resultWithIntent.sections.filter(s => s.type === 'intent');
assert(matchedIntentSections.length === 1 && matchedIntentSections[0].skill_profile_slug === 'data-patch-intent',
  'real intent_slug still filters to exactly the one matching intent, unaffected by the null-branch change');

if (failures > 0) {
  console.error(`\n${failures} test(s) FAILED`);
  process.exit(1);
} else {
  console.log('\nALL TESTS PASS');
}
```
