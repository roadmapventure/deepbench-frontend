## 2. CONTEXT

Original design doc (`§5.5`) had Nadia reusing `ingest.js`'s embed-and-upsert pattern directly and calling `writeLibrary()` herself. That was corrected over the course of this design session, in order, against `docs/PLATFORM-AGENT-RULEBOOK.md`:

- **`AR-3.1`** — only Eleanor (the Librarian) may call `queryLibrary()`/`writeLibrary()`, full CRUD, no exceptions, even for an agent with valid credentials. Nadia never touches `the_Library` directly.
- **`AR-2.3`** — reaching Eleanor still goes through the full `request_help` → Michelle → `delegate_to_agent` round trip, no constant-resolution shortcut, decided deliberately after weighing the hop-budget cost against the silent-failure risk already logged as `AA-93`.
- **`AR-1.3`** — Eleanor currently has zero real capability (`agent_capability_assignments` empty) to delegate to. **Explicitly out of scope for this session, by John's direction** — her capability build is its own future session. Nadia's `can_request_help` path to her is real, correct data — it will simply find no candidate until that session ships. Not a bug in this session's output.
- **`AR-4.1`/`AR-4.2`** — writing to the Data Room always requires an explicit human commit. Nadia's proposed `new_chunks` is that consequential moment, gated by `requires_human_confirmation: true`. **The generic "resume after accept" harness mechanism doesn't exist anywhere in the platform yet** (confirmed zero live Skill Profiles use this trait as of this session) — also explicitly out of scope, its own future harness-patch session, same shape as `S-ARCH-LOOP-PATCH-01`/`02`.
- **Trigger shape** — Escalate is one of `§3`'s five top-level intents, not a decision nested inside Priya's Stress Test loop. Dispatched directly (front door, via Marcus's `ci-routing-intent`, which already has `"escalate"` live in its enum) rather than via Priya's own `request_help`. Avoids both the hop-budget squeeze (a nested Priya→Nadia→Eleanor chain would burn 4 of the platform's 5-hop ceiling) and a structural dead end (a nested capability's `pending_confirmation` has no way to reach an actual human — it just becomes the parent's tool_result).
- **"Hands control back to Stress Test"** — resolved as a Layer 2 concern, not an Agent Loop mechanism. Once Escalate's (future, Eleanor-executed) write completes, the screen re-invokes Priya's `hyp-stress-test-intent` fresh — the same way it would after any other commit. No `delegate_to_agent` call from Nadia back to Priya is needed or correct.
- **Capability naming** — `data-room-operations` (original name) implied she operates on the Data Room. She doesn't; renamed to `data-analysis`.
- **Persona correction** — role changed live in Supabase this design session from "Data Expert" to "Data Analyst"; bio rewritten to remove "corpus" and state the Eleanor-delegation boundary explicitly. Already done, not a task in this kickoff doc.
- **`data-knowledge` is deliberately not built this session** — `db-assembly.js` (`buildSections()`, line 49) treats *any* `skill_type_slug: "knowledge"` row as an unconditional RAG fetch (`sectionType: "rag"`). Giving her one with `traits.source: "the_library"` would be the exact live violation already logged as `AA-99` (`api/prompt/ai-enrichment.js` calling `queryLibrary()` directly for Marcus/Priya's reads) — this session does not add a third instance of it. Omitting `traits.source` instead would just auto-RAG-query her own (empty, unseeded) `knowledge_entries` — harmless but pointless. She gets `data-identity`/`data-behavior` only.

function check(label, cond) {
  if (cond) { console.log(`PASS: ${label}`); pass++; }
  else { console.log(`FAIL: ${label}`); fail++; }

function testCategoryF() {
  console.log('\n--- Category F: environment ---');

async function fetchRow(table, filter) {
  const res = await fetch(`${SUPABASE_URL}/rest/v1/${table}?${filter}`, { headers: HEADERS });
  if (!res.ok) throw new Error(`Fetch failed for ${table}?${filter}: ${res.status}`);
  const rows = await res.json();
  return rows;
}
