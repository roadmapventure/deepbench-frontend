## 2. CONTEXT

Found live during `S-MI-65-design`'s own Manual QA: clicking "Accept" on Nadia's `ConfirmationCard` review for a hypothesis-test-derived opinion crashed with a raw 500 (`invalid input syntax for type uuid`). Traced end-to-end this session, not assumed:

1. **Root cause:** `source_chunk_ids` is free-text from Nadia's own LLM structured output ([reasoning-write.js:13](../../api/_lib/handlers/reasoning-write.js)), never format-validated. Priya's hypothesis-test citations are human-readable labels ("Dataset 1," `"JPN-GEO-GROWTH-NIPPO-2025-01"`), not real `the_library` UUIDs — that citation style flows into Nadia's context and she echoes it back as a "source." `writeTheReasoning()` ([search-harness.js:78](../../lib/search-harness.js)) runs `the_library?id=in.(...)` against Postgres with zero format check first; a non-UUID id throws `22P02`, and there's no try/catch around that specific fetch — an unhandled `throw`.
2. **This is not actually an unhandled server crash** — `api/capabilities/execute.js`'s top-level handler (L853-863) already catches every thrown error and returns clean JSON (`{error: e.message}`, status 500). Confirmed by direct source read.
3. **The real user-facing bug is on the frontend.** `resolveConfirmation()` throws on `!res.ok` (generic message, doesn't even surface the JSON body's `error` field), and `onResolveConfirmation()` (the caller) has a `try { ... } finally { ... }` with **no `catch`** — unlike `onCommit()`, which already catches and pushes a chat error message. So today, *any* resolve failure (this bug, or any future one) is silently swallowed: no message reaches the user, `ConfirmationCard` just sits there looking broken with zero feedback.

**Fix, confirmed with John (walkthrough this session):**
- **Backend:** validate every `source_chunk_ids` entry is UUID-shaped *before* the Postgres query. A malformed id can never resolve to a real `the_library` row anyway, so treat it exactly like the existing "missing/cross-room" case — reuse the graceful `{success:false, _access:{granted:false, tier:"denied-source-chunk-cross-room-or-missing"}}` denial already returned by this function, no new response shape, no new consumer-side branch needed anywhere downstream.
- **Frontend:** add the missing `catch` to `onResolveConfirmation()`, symmetric to `onCommit()`'s existing one (chat error message + `logEvent`). **John's explicit call: do NOT reset `hypFlow` on this catch** — unlike `onCommit`'s failure path (which resets to the `"result"` stage, losing the draft), the confirmation itself is still valid here; only the resolve action failed. Leaving `hypFlow.confirmation` untouched keeps `ConfirmationCard` open so the user can just retry Accept/Reject without regenerating the whole proposal.

This closes both the immediate crash (backend) and the general "resolve failures are invisible" gap (frontend) — the frontend fix also protects against any *future* resolve failure reason, not just this one.

**No existing UUID-validation helper found in the codebase** (checked before writing this — no duplicate to reuse or extend).

**Harness-vs-service check:** `writeTheReasoning()` is a fully generic harness-layer function (`lib/search-harness.js`) used by any capability that writes to `the_reasoning` — this validation is not Nadia/`data-patch-intent`-specific, so it belongs exactly where it's being added, no extraction needed.

## 5. TASKS

### Task 1 — `lib/search-harness.js`: validate `source_chunk_ids` are UUID-shaped before querying Postgres

```js
  const chunkIds = Array.isArray(source_chunk_ids) ? source_chunk_ids : [];

  // FEATURE: AA-189 — source_chunk_ids is free-text from an agent's own structured output
  // (reasoning-write.js), never format-validated before this point. A non-UUID id (e.g. a
  // human-readable citation label from Priya's hypothesis-test content) used to reach the
  // Postgres `id=in.(...)` filter below and throw a raw 22P02 syntax error, an unhandled crash.
  // A malformed id can never resolve to a real the_library row anyway, so it's treated exactly
  // like the existing missing/cross-room case below -- same graceful denial, no new shape.
  const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
  if (chunkIds.some(id => typeof id !== "string" || !UUID_RE.test(id))) {
    return { success: false, _access: { granted: false, tier: "denied-source-chunk-cross-room-or-missing" } };
  }

  // Cross-room integrity: every cited the_library chunk must belong to this same data_room_tag --
  // same category of check as AG-33's supersedes_id fix on the_library itself.
  if (chunkIds.length) {
    const idFilter = chunkIds.map(id => encodeURIComponent(id)).join(",");
    const chunkRes = await fetch(`${supabaseUrl}/rest/v1/the_library?id=in.(${idFilter})&select=id,data_room_tag`, { headers });
    if (!chunkRes.ok) throw new Error("source_chunk_ids lookup failed: " + (await chunkRes.text()).slice(0, 200));
    const chunkRows = await chunkRes.json();
    const crossRoom = chunkRows.length !== chunkIds.length || chunkRows.some(r => r.data_room_tag !== tag);
    if (crossRoom) return { success: false, _access: { granted: false, tier: "denied-source-chunk-cross-room-or-missing" } };
  }
```

Only the new `UUID_RE`/`if` block is inserted, immediately after `chunkIds` is computed and before the existing cross-room block. Nothing else in the function changes.

### Task 2 — `MarketIntelligenceScreen.jsx`: `onResolveConfirmation` gets the missing `catch`, deliberately without a `hypFlow` reset

```js
    try {
      const result = await resolveConfirmation({ confirmation_id, resolution, edited_task_context });

      if (resolution === "edit") {
        logEvent({ type: "patch_resolved", agentId: "nadia", data: { resolution, result }, durationMs: Date.now() - t0 });
        setHypFlow(prev => prev && ({
          ...prev,
          confirmation: { ...prev.confirmation, confirmation_id: result.confirmation_id, proposed_action: result.proposed_action, critique: result.critique },
        }));
        return;
      }

      logEvent({ type: "patch_resolved", agentId: "nadia", data: { resolution, result }, durationMs: Date.now() - t0 });
      {
        const st = hypFlow?.hypothesisTest || {};
        setMessages(prev => [...prev, {
          role: "assistant", kind: "hypothesis_test", hypothesisTest: st,
          displayAgentCard: st.display_agent_card, displayAgentId: st.display_agent_id,
          totalElapsedMs: hypFlow?.testElapsedMs ?? null,
          resolution: resolution === "accept"
            ? { status: "stored", note: "Saved — Nadia (Data Expert) logged this. Find it anytime under Agent & Data Info → Analysis." }
            : { status: "rejected", note: "Nadia's proposal was rejected — not recorded." },
        }]);
      }
      setHypFlow(null);
    } catch (e) {
      // FEATURE: AA-189 — this catch was previously missing entirely; any resolve failure (this
      // bug or a future one) silently stuck ConfirmationCard open with zero feedback. Symmetric to
      // onCommit()'s existing catch, but deliberately does NOT reset hypFlow (John's explicit call,
      // S-AA-189-design) — the drafted confirmation is still valid, only the resolve action failed,
      // so the user can retry Accept/Reject on the same card instead of losing the draft.
      console.error("[MarketIntelligenceScreen] onResolveConfirmation", e.message);
      logEvent({ type: "error", agentId: "nadia", data: { step: "resolve_confirmation", resolution, message: e.message }, durationMs: Date.now() - t0 });
      setMessages(prev => [...prev, { role: "assistant", text: "Something went wrong resolving that — try again.", kind: "error" }]);
    } finally {
      setWorkingStatus(null);
    }
```

Everything inside the existing `try` block is unchanged — only the new `catch` clause is added, between the existing `try` body and the existing `finally`.

## 6. DESIGN RULES

- The backend denial reuses the existing `"denied-source-chunk-cross-room-or-missing"` tier verbatim — do not invent a new tier for the malformed-format case, it's semantically the same outcome ("this id will never resolve to a real row").
- The frontend catch's chat-error copy ("Something went wrong resolving that — try again.") follows the exact phrasing convention `onCommit`'s existing catch already established ("Something went wrong committing that — try again.") — same `kind:"error"` shape, same sentence structure.
- Do **not** reset `hypFlow` in the new catch — this is the one deliberate asymmetry from `onCommit`'s pattern, per John's explicit call this session.
