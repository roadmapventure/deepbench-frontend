## CONTEXT

Found 2026-07-07 during a design session live-testing the MI screen's guardrail-block path, using John's recurring "Japan is Apple's fastest-growing GEO in 2025" canned question. Live Supabase query confirmed this was the **first-ever `guardrail_result: block`** Owen (`qg-review-intent`) has returned for this exact question across 9 reviews since 2026-07-02 — every prior review passed. Root cause of the block itself is **not a bug**: Marcus's own self-review had already flagged the same causal-inference concern on 07-04, 07-06, and earlier the same day (16:43, `confidence_tier: synthesized`) — this is an inherently non-deterministic LLM-as-judge finally tipping a genuinely borderline answer to a hard block. No fix needed for that part, and this session does not touch it.

**Separate, real bug found alongside it, in scope here:** `buildFailureText()` (lines 38-47) hardcodes the phrase `Sam's diagnosis: this looks like a Data Room coverage gap` whenever `triage.recommend_escalate` is `true` — regardless of the real `rule_violated`. Confirmed via direct Supabase query of `skill_profiles` (`slug = 'intake-failure-intent'`): Sam's actual output schema (`traits.schema`) only ever defines two fields —

```json
{"recommend_escalate": "boolean", "suggested_research_request": "string | null"}
```

— matching the original spec exactly (`docs/APPLE-AGENT-1-v5-DESIGN.md` §5.9: `// output: { "recommend_escalate": true, "suggested_research_request": "string | null" }`). There is no diagnosis field. Sam was never designed to explain *why* — his `method` text only decides *whether* escalating would help ("Recommend escalate when the failure suggests missing or insufficient Data Room coverage... rather than a structural answer problem"). The "Data Room coverage gap" phrase in the UI is invented at the frontend layer, attributed to an agent who never said it — the same fabricated-agent-attribution class as `AA-108`.

**In the live case that surfaced this, the fabricated phrase was also substantively wrong.** The real `rule_violated` was `synthesized_as_fact` — Owen's guardrail blocked Marcus for blending real, cited Data Room facts (Japan's 26-month upgrade cycle, Nippo Carrier's NPI/training metrics) with unlabeled analytical inference presented as fact, not for a coverage gap. Owen's own guardrail object already carries a real, specific `reason` field explaining exactly this (verified live, `deliverables.content.guardrail.reason` for this call) — it is computed today, stored today, and simply never read by the failure-path UI.

**Design resolved 2026-07-07 (John):** drop the fabricated phrase entirely. Surface Owen's real `guardrail.reason` — correctly attributed to Owen (the Proofreader / quality-gate), not Sam — plus Sam's real `suggested_research_request` when he provides one. No change to Sam's Skill Profile schema, no new LLM call. Same "deterministic display fix, not a capability change" precedent as `AA-125`'s Pipeline Log shaping fix, and directly against the alternative (giving Sam a new schema field) which was considered and explicitly rejected this session in favor of the zero-schema-change option, matching the current MI-loop-speed priority.

```js
// FEATURE: MI-01d — Sam Reyes (pipeline-triage/intake-failure-intent) replaces the static failure
// message with a real diagnosis, per design doc §5.9's "fail safe, never fake" principle.
function buildFailureText(guardrail, triage) {
  const base = `Marcus couldn't produce an answer that passed review (${guardrail?.rule_violated || "review failed"}).`;
  if (!triage) return `${base} Try rephrasing the question.`;
  const suggestion = triage.suggested_research_request ? ` Sam suggests: "${triage.suggested_research_request}"` : "";
  return triage.recommend_escalate

}
```

with:

```js
// FEATURE: AA-130 — Sam's intake-failure-intent schema (traits.schema, confirmed live in Supabase)
// only ever outputs recommend_escalate/suggested_research_request, per the original spec
// (APPLE-AGENT-1-v5-DESIGN.md §5.9) — he was never designed to produce a diagnosis string, and the
// prior "Sam's diagnosis: ...coverage gap" text was a fabricated phrase attributed to him
// unconditionally, wrong in the live case that surfaced this (AA-130). Owen's guardrail object
// already carries a real, specific `reason` explaining the actual failure — this now surfaces that,
// correctly attributed to Owen, instead of inventing something on Sam's behalf.
function buildFailureText(guardrail, triage) {
  const base = `Marcus couldn't produce an answer that passed review (${guardrail?.rule_violated || "review failed"}).`;
  const reason = guardrail?.reason ? ` ${guardrail.reason}` : "";
  if (!triage) return `${base}${reason} Try rephrasing the question.`;
  const suggestion = triage.suggested_research_request ? ` Suggested next step: "${triage.suggested_research_request}"` : "";
  return triage.recommend_escalate
    ? `${base}${reason}${suggestion}`
    : `${base}${reason} Try rephrasing the question.`;
}
```
