## What this ships

**One migration, in three ordered parts, and the order is the whole mechanism.**

1. **Capture the down first** (`capture_migration_down`, step 6's rule) — before `apply_migration`,
   never after.
2. **Repair the four violating rows** — `epic_id = NULL`, one `runner_before_images` row each
   (§19v). This must precede the constraint: added first, the CHECK rejects them and the migration
   fails.
3. **Add the CHECK**, `VALID`:

```sql
ALTER TABLE public.runner_items
  ADD CONSTRAINT ck_runner_items_epic_id_review_only
  CHECK (epic_id IS NULL OR (kind = 'gated_before_build' AND backlog_id IS NULL));
```

**Why the repair is `NULL` and not something cleverer.** The four rows are ship and permission
cards for ordinary tickets; their `epic_id` was never meaningful data, it was the defect. Nothing
in the repo reads the column (surveyed above), so nulling it changes no rendered surface — the
briefing's §15 burn-down and §8 queue matrix both read `backlog_items.epic_id`, a different
column on a different table. Each row's full prior state is preserved in `runner_before_images`,
so a Reverse restores it byte-for-byte.

## THE EDIT THIS SHIP FORBIDS, and it is the tempting one because the ticket offers it as an
## alternative: also narrowing step 8d's predicate to `kind='gated_before_build' AND backlog_id IS NULL`.

The ticket names the constraint and the predicate-narrowing as **alternatives** and prefers the
constraint, and doing both is not belt-and-braces — it is the failure this platform has paid for at
`SES-116`, `SES-113` and `SES-86` phase 3, arriving one level up. With the CHECK in force,
`ri.epic_id = e.id` can only ever match a review card **by construction**, so a second copy of the
discriminator in runbook prose is a fact with two homes that can drift apart, and the prose copy is
the one no test can see. One enforced home; the runbook cites it.

**The inverse failure is untouched and stays untouched.** `gate-review.md`'s prohibition — a review
card filed *without* `epic_id` makes the sweep repeat that review forever — is about a missing
value, and this CHECK admits `epic_id IS NULL` on every row precisely so that filing rule stays
`gate-review.md`'s to enforce. This constraint answers *"who may carry one"*, never *"who must"*.

**Why `VALID` rather than `NOT VALID`** — the `SES-116` lesson, applied. A `NOT VALID` CHECK is
still enforced on UPDATE, so leaving the four violators in place behind one would make them
**un-updatable**, and the decision harvest UPDATEs `runner_items` to record John's taps. `SES-182`'s
row is `decision = NULL` — an undecided ship card sitting on his page right now — so that failure
would land on a card he has just tapped. Repair first, then a VALID constraint, is the only ordering
that cannot do that.

## QA plan — discriminating, and stated as the test before it is run

Would each arm still pass if the change did nothing? Stated per arm:

1. **The four review cards still satisfy the predicate** — a positive control. Fails if the
   discriminator is wrong about the legitimate population.
2. **A ship card carrying `epic_id` is REFUSED at INSERT** (error `23514`). On today's schema this
   INSERT **succeeds**, so the arm cannot pass vacuously.
3. **A gated card carrying `epic_id` AND a `backlog_id` is REFUSED** — the `SES-210`/`SES-45` shape,
   which arm 2 alone does not cover (they are `gated_before_build`, so a `kind`-only constraint
   would let them through). This is the arm that discriminates the shipped constraint from the
   obvious weaker one.
4. **A real gate-review card (`gated_before_build`, `backlog_id` NULL) is still ACCEPTED** — the
   both-directions rule (`SES-101`): a one-directional check passes on a constraint that rejects
   everything.
5. **Step 8d's sweep, run for real against the repaired table**, returns the same answer it should:
   `NOT EXISTS` no longer matches on M3 via a ship card.

Every write arm runs inside a deliberately failing `DO` block and is rolled back; the tree is
re-read afterwards for stray rows.

**File-level negative control:** the new guard is written so that it cannot pass against
`origin/dev` — the constraint it pins does not exist there.
