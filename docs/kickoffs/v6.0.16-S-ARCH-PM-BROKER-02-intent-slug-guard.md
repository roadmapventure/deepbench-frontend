## 1. CONTEXT

**This is a bug-fix session, not a feature session.** `S-ARCH-HITL-RESUME-02`'s live round-trip test (2026-07-03) was the first test ever to exercise `request_help` → `delegate_to_agent` all the way through to a capability call that depends on a specific `intent_slug` (Eleanor's `data-room-custody`/`library-write-intent`). It exposed a silent-fabrication bug: nothing was actually written to `the_library`, despite every layer reporting success.

**Root cause, traced through `ai_activity_log`/`deliverables` and the actual code (not assumed):**
1. `agent-selection-intent`'s schema requires the model to return an `intent_slug` per candidate — but `lib/project-manager.js`'s `getRosterCandidates()`/`rosterToContext()` never supplies real intent slugs, only `capability_slug`. The model had no ground truth and guessed a plausible-sounding but nonexistent one (`library-write-execution` instead of the real `library-write-intent`). `agent-selection-intent.traits.analysis_instructions` is also `null` (confirmed by live query) — no guidance telling the model `null` is a safe, preferred answer over guessing.
2. `api/prompt/db-assembly.js`'s `assemblePrompt()` (line 349-351) silently filters to **zero** Intent Skill Profiles when `intent_slug` doesn't match anything, instead of throwing. The downstream call proceeds with no schema, no `handler: 'library-write'` — nothing constrains the model's output.
3. With nothing constraining it, Eleanor's model turn free-wrote a fully fabricated, realistic "✅ INSERTED" write confirmation. Independently confirmed: zero `the_library` rows exist anywhere in the entire test window, table-wide, no filter.

**The fix has two parts, deliberately both included — one closes the actual gap, one is a safety net for any future path that hits the same class of bug:**
- **Task 1 (the real fix):** give the model real ground truth. Extend the roster broker to include each capability's actual intent slugs, so `agent-selection-intent` can copy an exact value instead of guessing.
- **Task 2:** explicit instructions on `agent-selection-intent` reinforcing "copy exactly, or return null" — belt-and-suspenders with Task 1's data fix, since a schema field alone doesn't guarantee the model reads the roster text carefully.
- **Task 3 (the safety net):** `assemblePrompt()` throws a clear error when a caller passes an `intent_slug` that doesn't match any real Intent Skill Profile for that capability, instead of silently degrading. This is the platform's own "fail safe, never fake" principle applied structurally — even if some future caller reintroduces a bad `intent_slug` through a path Task 1/2 didn't anticipate, the system fails loudly instead of letting a model quietly fabricate success. Matches the existing precedent of `resolveCapabilityHolder()`'s unhandled throws (`execute.js`) — a genuine system fault, not something the calling agent is expected to gracefully recover from.

**Why this session also finally proves `S-ARCH-HITL-RESUME-02`:** that session's Tasks 1-2 (the two Supabase rows) are confirmed correct and already live — this bug was entirely upstream of its scope. This session's own live test re-runs the exact same Escalate propose→accept scenario as the conclusive proof that now actually lands a real `the_library` row. If it passes, `S-ARCH-HITL-RESUME-02` can move to `FEATURES-ARCHIVE.md` off the back of this session's test, not a new one.

Replace `fetchRoster()` and `rosterToContext()` with:

```js
async function fetchRoster(supabaseUrl, supabaseKey) {
  const headers = { apikey: supabaseKey, Authorization: `Bearer ${supabaseKey}` };
  // NOTE: found in QA, 2026-07-02 -- docs/classes/chunks (kickoff's original select list) don't
  // exist on the Supabase `agents` table; that per-agent activity data is frontend-only mock
  // content in src/data/agents.js, never persisted server-side. Dropped from the select (which
  // 404'd the whole roster fetch); activity_count reports null until a real server-side source
  // exists. agent-selection-intent's schema already types this field ["number","null"].
  const [agentsRes, assignmentsRes, capabilitiesRes, linksRes, intentProfilesRes] = await Promise.all([
    fetch(`${supabaseUrl}/rest/v1/agents?select=id,name,role,skill_score,situational_awareness,rating,is_active`, { headers }),
    fetch(`${supabaseUrl}/rest/v1/agent_capability_assignments?select=agent_id,capability_slug`, { headers }),
    fetch(`${supabaseUrl}/rest/v1/capabilities?select=slug,name,description`, { headers }),
    fetch(`${supabaseUrl}/rest/v1/capability_skill_profiles?select=capability_slug,skill_profile_slug`, { headers }),
    fetch(`${supabaseUrl}/rest/v1/skill_profiles?skill_type_slug=eq.intent&select=slug`, { headers }),
  ]);
  if (!agentsRes.ok || !assignmentsRes.ok || !capabilitiesRes.ok || !linksRes.ok || !intentProfilesRes.ok) {
    throw new Error('Roster fetch failed');
  }
  const [agents, assignments, capabilities, links, intentProfiles] = await Promise.all([
    agentsRes.json(), assignmentsRes.json(), capabilitiesRes.json(), linksRes.json(), intentProfilesRes.json(),
  ]);

  const capBySlug = Object.fromEntries(capabilities.map(c => [c.slug, c]));
  const assignmentsByAgent = {};
  for (const a of assignments) {
    (assignmentsByAgent[a.agent_id] ||= []).push(a.capability_slug);
  }

  // FEATURE: AA-108 -- real intent slugs per capability, so agent-selection-intent's model can
  // copy an exact value instead of guessing one from the capability name. Prior to this, the
  // roster context named only capability_slug -- the schema's own intent_slug field had no
  // ground truth to draw from, confirmed as the root cause of a live silent-fabrication bug
  // (S-ARCH-HITL-RESUME-02, 2026-07-03: a hallucinated intent_slug caused a downstream write to
  // be silently skipped while every layer reported success).
  const intentSlugSet = new Set(intentProfiles.map(p => p.slug));
  const intentSlugsByCapability = {};
  for (const link of links) {
    if (intentSlugSet.has(link.skill_profile_slug)) {
      (intentSlugsByCapability[link.capability_slug] ||= []).push(link.skill_profile_slug);
    }
  }

  return agents.map(a => ({
    agent_id: a.id, name: a.name, role: a.role,
    skill_score: a.skill_score, situational_awareness: a.situational_awareness,
    rating: a.rating, activity_count: null,
    is_active: a.is_active,
    capabilities: (assignmentsByAgent[a.id] || []).map(slug => ({
      capability_slug: slug, description: capBySlug[slug]?.description || null,
      intent_slugs: intentSlugsByCapability[slug] || [],
    })),
  }));
}

function rosterToContext(roster) {
  const lines = roster.map(a => {
    const caps = a.capabilities.length
      ? a.capabilities.map(c => {
          const intents = c.intent_slugs.length ? `, intents: [${c.intent_slugs.join(', ')}]` : '';
          return `${c.capability_slug}${c.description ? ` (${c.description})` : ''}${intents}`;
        }).join('; ')
      : 'no assigned capability';
    return `--- ${a.agent_id} — ${a.name}, ${a.role} ---\ncapabilities: ${caps}\nskill_score: ${a.skill_score ?? 'n/a'}, situational_awareness: ${a.situational_awareness ?? 'n/a'}, rating: ${a.rating ?? 'n/a'}, activity_count: ${a.activity_count ?? 'n/a'}\nactive: ${a.is_active}`;
  });
  return `PLATFORM AGENT ROSTER (${roster.length} agents). Use agent_id exactly as shown when selecting a candidate. When a candidate's capability lists intents, intent_slug MUST be copied exactly from that list -- never invented. If a capability has no listed intents, or none clearly matches, return intent_slug: null:\n\n${lines.join('\n\n')}`;
}
```
