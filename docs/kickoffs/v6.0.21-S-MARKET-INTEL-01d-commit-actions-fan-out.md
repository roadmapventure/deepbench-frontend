## 2. CONTEXT

Three independent pieces, each already fully resolved in design conversation — no open questions remain, only implementation.

**Piece A — Commit actions (Track as Assumption / Make Permanent).** These buttons currently render `disabled` in `EvidenceColumn` (`MarketIntelligenceScreen.jsx` lines 375-382). Clicking either must call two agents directly and unconditionally — **no Intake Assistant (Sam) involvement, no delegation, no nesting**:

- **Elena Cho (`memory-consolidation`/`reasoner-intent`)** — already built and proven live (`S-APPLE-05`, v6.0.17). Fires on every commit, self-gates `action: consolidate | no_action`, no confirmation gate. Logged to the Pipeline Log and nothing else.
- **Nadia Farouk (`data-analysis`/`data-patch-intent`)** — already built and proven live (`S-APPLE-04b` re-scope, v6.0.13). Fires on every commit, self-gates `action: opinion | promote | no_action`, but **always** returns `status: 'pending_confirmation'` (`requires_human_confirmation: true` on every branch, including `no_action` — a known, already-accepted quirk, not fixed here). This is the first live UI caller either capability has ever had.

**Design decision made this session (John):** the original design doc's §5.8 Commit Triage (`intake-commit-intent`'s `route_to` fan-out through Sam) is **not used for this flow**. Two reasons, both confirmed this session: (1) `S-APPLE-05` already deleted the "reasoner" leg of Sam's `route_to` entirely — Elena is unconditional, nothing routes her. (2) Sam delegating to Nadia via `request_help`/`delegate_to_agent` would nest Nadia's `pending_confirmation` several stack frames inside Sam's own tool-call loop — `intake-commit-intent`'s schema has no field to carry a `confirmation_id` back out, so the human would never actually see Nadia's proposal to accept/reject/edit it. Nadia's `data-patch-intent` already accepts a nullable `disputed_chunk_id` and already has a graceful `no_action` outcome — she doesn't need Sam's upstream triage to function correctly; calling her directly is both simpler and more architecturally honest (the real judgment sits with the one agent equipped to make it, not a redundant routing layer in front of her). Sam's `intake-commit-intent` capability is **not called anywhere by this session** — it goes unused by this screen. (It remains available for a future session if a real use for it surfaces; not deleted, not deprecated.)

**Disputed chunk resolution (session-specific scope boundary, decided this session):** `data-patch-intent` takes a single nullable `disputed_chunk_id`, not an array. When the commit descends from a flagged Q&A answer with **exactly one** citation, pass that citation as `disputed_chunk_id`. In every other case (a self-authored claim with no prior answer, or a flagged answer citing zero or multiple chunks), pass `null` — Nadia's own judgment already handles a null chunk gracefully (`action: no_action` or `opinion` with no `chunk_id`). Resolving "which of several cited chunks is actually disputed" without RAG access is out of scope this session — `no_action`/`opinion` is a safe, honest fallback, not a broken one.

**Confirmation UI (design decision, John):** one generic `ConfirmationCard` component, not a bespoke one per capability. It takes runtime props (`agent`, `proposedAction`, `critique`, `onResolve`) and renders identically regardless of which agent or capability produced the `pending_confirmation` — this is the first frontend implementation of the platform's `requires_human_confirmation` gate (confirmed this design session via grep of `src/`: zero prior UI exists for `pending_confirmation`/`confirmation_id` anywhere). It lives in `SharedUI.jsx`, not `MarketIntelligenceScreen.jsx`, so it's reusable platform-wide, not screen-specific. Both commit buttons call the same handler (`onCommit(intent)`), differing only in which `intent` string (`"forecast"` vs `"correct"`) gets passed to Elena/Nadia's `task_context` — one code path, not two.

**Piece B — Sam's Failure Triage.** The `qa_failed` path (currently a static `QA_FAILURE_TEXT` string, `MarketIntelligenceScreen.jsx` line 27-28, fired when `runQaWithQualityGate` exhausts its retry) gets replaced with a real call to Sam Reyes's `pipeline-triage`/`intake-failure-intent` (already built, `can_request_help: true`, proven live in isolation by `S-ARCH-AGENT-LOOP-03`, never wired to a real caller until this session) — turns a dead-end message into an actual diagnosis (`recommend_escalate`/`suggested_research_request`), per design doc §5.9's "fail safe, never fake" principle. **Piece C — Owen's real retry (fixes a confirmed architecture regression in already-shipped code).** `AI-39`'s retry-on-block mechanism (`S-MARKET-INTEL-01c`, v6.0.20, already live in dev) implements the retry as Layer 2 screen code (`runQaWithQualityGate` calling `ci-answer-intent` a second time itself when `gate.guardrail.result === 'block'`) and cites the superseded `ARCHITECTURE.md §19b` cross-capability-handoff language in its own code comment — that paragraph was superseded by §19d two days before `01c` shipped. `S-ARCH-AGENT-LOOP-03` (`AA-82` Task 4) had already specifically designed this exact case: Owen's own `delegate_to_agent` call, using `agent_id`/`capability_slug`/`intent_slug` supplied in his own `task_context`, and documented in `qg-review-intent`'s `notes` field: *"No live caller exists yet — whichever session builds one must satisfy this."* `01c` is that live caller, and did not satisfy it. **Design decision made this session (John, confirmed as standard practice):** this is the **orchestrator-workers pattern** (Anthropic, "Building Effective Agents") — the delegating agent's own final output must carry forward (synthesize) the delegated result, since nothing inside a tool-call loop is visible to the original caller otherwise. `qg-review-intent`'s schema gains one new nullable field, `final_answer` — populated only when Owen actually delegated and regenerated; the screen displays `final_answer` when present, else the original answer. This mirrors the exact same pattern Nadia's `data-patch-execute-intent`'s `confirmation_note` field already uses for her `promote` action's Eleanor delegation (`S-APPLE-04b`) — not a new mechanism, the same one applied a second time.

export function ConfirmationCard({ agent, proposedAction, critique, onResolve }) {
  const [editing, setEditing] = useState(false);
  const [editText, setEditText] = useState("");
  const [busy, setBusy] = useState(false);

  const resolve = async (resolution, editedText = null) => {
    setBusy(true);
    try {
      await onResolve(resolution, editedText);
    } finally {
      setBusy(false);
    }
  };

  return (
    <div style={{background:T.card,border:`1px solid ${T.brassLight}`,borderLeft:`4px solid ${T.brass}`,borderRadius:3}}>

      </div>

// FEATURE: MI-01d — resolve a pending_confirmation (accept/reject/edit). Generic across any
// capability — the confirmation_id already encodes which capability/agent/intent it belongs to.
async function resolveConfirmation({ confirmation_id, resolution, edited_task_context = null }) {
  const res = await fetch("/api/capabilities/execute", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ action: "resolve", confirmation_id, resolution, edited_task_context }),
  });
  if (!res.ok) throw new Error(`resolve ${resolution} failed: ${res.status}`);
  return res.json();
}

async function runQaWithQualityGate(message, conversationContext, onEvent) {
  const qa = await callCapability({
    capability_slug: "channel-intelligence", intent_slug: "ci-answer-intent", agent_id: "marcus",
    task_context: { goal: message }, runtime_context: conversationContext,

  const gate = await callCapability({
    capability_slug: "quality-gate", intent_slug: "qg-review-intent", agent_id: "owen",
    task_context: {
      question: message, candidate_answer: qa.answer, confidence_tier: qa.confidence_tier, citations: qa.citations,
      agent_id: "marcus", capability_slug: "channel-intelligence", intent_slug: "ci-answer-intent",
    },
  });

      task_context: { guardrail_failure: gate.guardrail, original_question: message },
    });
    onEvent({ type: "failure_triage", agentId: "sam", data: triage });
    return { kind: "qa_failed", text: buildFailureText(gate.guardrail, triage) };
  }

  const finalAnswer = retried ? gate.final_answer : qa;
  const needs_review = !!qa.needs_review || gate.eval?.result === "revise";
