# SES-116 — `runner_items.backlog_id` holds display strings — repair + bare-ID CHECK

**Version:** `v7.0.174` · **Ticket:** `SES-116` (`P10 - Tooling`, tier `now`, Automation epic,
queue 1) · **Cycle:** `f6e50900` · **Picked by:** selection layer 1b, John's standing Automation
drain (`drain_epic_next` → `pick`, `open_now = 18`).

## Premise revalidation (step 6, register B7) — HOLDS, and the ticket **under-counted it 20×**

Checked live this cycle, not recalled. The ticket says *"3 of 4 open `gated_before_build` cards"*.

| Census 2026-08-23T02:1xZ | Rows |
|---|---|
| `runner_items` rows with a non-NULL `backlog_id` | **80** |

So the premise is not merely intact, it is broader than filed in two directions: the pollution
covers `ship` cards as well as gated ones, and **seven** cards are affected rather than three —
including `CHI-84` (queue 20) and `AGT-015` (queue 11), both sitting undecided on the briefing
while mis-joining to nothing.

**Corroboration that this was already costing real work, not a theoretical defect.** One cycle
earlier, `v7.0.173` (`SES-115`) could not join its own new `backlog_active` view to the ticket
table and had to reach it through
`substring(ri.backlog_id from '^[A-Za-z]+-[0-9]+')`. Its kickoff doc records the reason in as many
words: *"The natural join `ri.backlog_id = b.backlog_id` matches **zero rows**."* That workaround
exists because of this bug.

## Root cause — and it is a sentence in our own runbook

`runner-cycle.md` step 9 told every cycle to file the card with *"backlog ID + Type + named
P-class per the Language block above"*. The Language block (John, 2026-08-20) governs what **John
reads** — `P10 - Tooling`, never a bare digit — and it never governed a key column. Following step
9 literally produces `'SES-115 (Tooling · P10 - Tooling)'` **inside a join key**.

This is why the fix is not only a constraint: **without the step-9 rewording, the very next cycle
to file a card would have its INSERT rejected by the new CHECK.** Both ship in this commit.

## What shipped

**Migration `ses116_backlog_id_bare_check`** (one migration, four statements):

1. `ALTER TABLE public.runner_items ADD COLUMN IF NOT EXISTS display_ref text` — nullable,
   additive, with a `COMMENT` carrying its own rule.
2. A `runner_before_images` row for **all 63** rows about to be rewritten (§19v — no before-image,
   no write).
3. The repair: `display_ref := ` the raw string, `backlog_id := ` the resolved bare id or `NULL`.
   Resolution tries the **suffixed** head first (`SES-83b`) then the unsuffixed (`SES-83`), and a
   head matching no `backlog_items` row resolves to `NULL` rather than inventing a join.
4. `ck_runner_items_backlog_id_bare` — `CHECK (backlog_id IS NULL OR backlog_id ~
   '^[A-Z]+-[0-9]+[a-z]?$')`, **VALID**.

**Doc changes (2 files, under the 3-file cap):** `runner-cycle.md` step 9 (the filing rule +
`display_ref` + the render note) and `briefing-page.md` regeneration step 1 (the id chip's source).

### The pattern was surveyed, not chosen

The ticket required this before picking a form: `'^[A-Z]+-[0-9]+[a-z]?$'` matches **all 603** rows
of `backlog_items.backlog_id`, **zero exceptions**. The CHECK cannot reject a legitimate ticket
reference. The ticket's suggested form survived its own precondition unchanged.

### The half the ticket did not anticipate — why `display_ref`, not `NULL`

The ticket says *"NULL stays allowed for non-ticket cards (e.g. invention proposals)"*. That is
right for a card that never had a reference. But of the 22 unresolvable rows, **most carry the
only copy of a real one**: eleven name a directive by uuid (`directive 603f44ea`), two a
governance register (`B17 BACKFILL`, `B31`), two an `ARCHITECTURE.md` clause, one an invention
proposal, and four name `SES-78`/`78a`/`78d` — pre-board cards whose tickets never existed in
`backlog_items`. Nulling those **destroys** the reference, which §19v forbids, and blanks the id
chip on two cards John has not yet decided. Moving the raw string to `display_ref` makes the
repair lossless for all 63 rows by construction.

### The one that would have shipped a live hazard: `NOT VALID`

`NOT VALID` is the obvious way to add a constraint without touching history, and here it is the
**opposite** of safe. A `NOT VALID` CHECK is still enforced **on UPDATE** — so the 22 unrepairable
legacy rows would have become un-updatable, and the step-9 tail **UPDATEs `runner_items` to record
John's taps**. The failure would land on a card he had just tapped: his decision silently lost, on
the one table whose entire job is to hold his decisions. Repairing every row first is what makes a
fully `VALID` constraint the safe option rather than the ambitious one. This arm is proved (D
below), not reasoned about.

## QA — discriminating, both directions (§19v; `SES-101`'s both-directions rule)

Read-only assertions after the migration:

| Assertion | Before | After |
|---|---|---|
| rows violating the pattern | **63** | **0** |
| repaired rows that now join to their ticket | **0** | **41** |
| raw strings preserved in `display_ref` | 0 | **63** |
| before-image rows written by this cycle | 0 | **63** |
| constraint `convalidated` | — | **true** (VALID, not NOT VALID) |

Five live arms on fixtures, inside a **deliberately rolled-back** transaction (the block ends in
`RAISE EXCEPTION`, so the report *is* the error message and nothing persists):

- **A = PASS** — a display-string INSERT is rejected, **by the constraint's own name**
  (`ck_runner_items_backlog_id_bare`), not by some unrelated error.
- **B = PASS** — a bare-id INSERT succeeds. *(A gate nobody can pass would satisfy A alone.)*
- **C = PASS** — `NULL` still accepted: a card with no ticket.
- **D = PASS** — **the arm the design turned on**: the harvest UPDATE
  (`SET decision='accept' … WHERE decision IS NULL`) on `477454d7`, a `display_ref`-only row,
  succeeds. Under `NOT VALID` this fails and John's tap is lost.
- **E = PASS** — re-polluting an existing row via **UPDATE** is rejected too, not just INSERT.

**Would it still pass if the change did nothing?** No, and that is checked rather than asserted:
before the migration all 63 rows violated and **0** of the 7 undecided cards joined; arms A and E
both require the constraint to exist, and D requires the repair to have happened.

**Cleanup proved, not assumed:** `0` fixture rows remain, card `477454d7` is **still undecided**,
and card `8c8deaae` still reads `SES-133`.

**Regression on the one existing reader.** `SES-115`'s `backlog_active` view reads this column
through `substring()`. After the repair its census is unchanged — `in review` **1**,
`in development` **1**, `partial` **50**, `missing` **511** — and `substring` vs. direct now agree
exactly (**3 = 3**), so the workaround is redundant but harmless. It is deliberately **not**
removed here: that is a separate edit to a file this ticket does not own.

**No application code reads `runner_items`** — `grep -rn "runner_items" --include=*.js` over the
clone returns one comment line in `tests/regression/HAR-41-feature-flags.js` and nothing else — so
this cannot reach the product surface. Doc + schema only; no `src/`/`api/`/`lib/` change.
