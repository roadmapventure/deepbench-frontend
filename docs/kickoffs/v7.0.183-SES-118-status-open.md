## Why

John, 2026-08-22: `'missing'` is markdown-audit-era vocabulary. A `FEATURES.md` row asked *"does
this capability exist in the product?"* and answered `❌ Missing`. As a **ticket status** it is
opaque — it describes an audit verdict, not a state of work. `'open'` says what it means.

## What shipped

replaced with `('open','partial','done','removal proposed','removed')`. Before-image per row
first (§19v) — 510 rows into `runner_before_images`, capturing the full prior row.

**2. `scripts/heal-engine.js`** — the filed ticket draft's `status` literal.

**3. `tests/regression/SES-89-heal-detector.js`** — the assertion that guards it.

## The ticket's blast-radius survey was incomplete, and the gap was a live hazard

`SES-118` named `recompute_backlog_queue()`, the step-5 selection query and `check-session-docs.js`,
and correctly observed that all three match `done`/`removed`/`removal proposed` and never `'missing'`.
Re-measured live this cycle rather than taken on trust, that list **misses the one place that
writes the value**:

- `scripts/heal-engine.js:272` sets `status: "missing"` on every ticket the Heal engine files.
- `tests/regression/SES-89-heal-detector.js:197` asserts exactly that string.

Replacing the CHECK without those two lines would have made **step 8b's Heal sweep raise `23514`
on the next recurring failure it detected** — a break that only surfaces when something else has
already gone wrong, which is the worst time to find it. Both ship in this same commit.

Verified there is nothing else: no public function (`pg_proc.prosrc`), view (`pg_get_viewdef`) or
other CHECK (`pg_get_constraintdef`) references the value.

## Two decisions that are load-bearing

**`updated_at` is deliberately NOT touched.** The obvious form of this migration stamps
`updated_at` on all 510 rows, and that **silently disables step 8c's background revalidation sweep
for thirty days** — its predicate is `updated_at < now() - INTERVAL '30 days'`, so stamping every
row hides the whole sinking tail until 2026-09-22. Same reasoning `recompute_backlog_queue()`
already uses for not stamping on a renumber (`SES-86` phase 2, `v7.0.130`): a bulk vocabulary
change is not a per-ticket edit and must not look like one. **Proven, not asserted** — the
`md5` fingerprint over `(id, updated_at)` for the affected rows is byte-identical before and
after: `9e8f827523a4fa3385351d1c4a6745bc`.

**The CHECK is replaced, not widened.** Accepting both values transitionally would let the retired
one creep back — precisely the *"instruction-only rules have failed twice"* failure `SES-117`
cites. The cost is stated rather than hidden; see *Not done* below.

## The template edit that would have shipped wrong

`briefing-template.html` uses the bare word `missing` for **two unrelated things**. `.missing` /
`td.missing` / `class="missing"` (lines 187, 313, 490, 682, 764) are the page's **red defect
vocabulary** — what draws the line when a card ships without its plain-language summary
(`v7.0.145`/`v7.0.146`) or a `done` directive carries a NULL outcome (`SES-129`). A find-and-replace
over the file destroys that, turning every defect marker into dead CSS **while looking like a clean
rename**. Only the 5th positional argument of
`queueRow(queue, id, epic, class, STATUS, designStatus, title)` was changed. The two
`&ldquo;missing&rdquo;` occurrences inside SES-118's own row title are untouched — that title names
the value being renamed. Post-sweep check: zero single-quoted `'missing'` literals remain.
