## 2. CONTEXT

**The loop's last third never runs unattended.** Verified this session at `origin/dev` `7f82a585`:

- `scripts/heal-engine.js`, the `detections.length === 0` branch (around line 1313): under `--apply` it calls `persistSignatureState()` (the SES-277 fix), then `finish(0, …)`. Without `--apply` it writes nothing and **also** exits 0.
- `docs/runbooks/runner-cycle.md` step 8b, verbatim: *"Exit 1 means it found recurring failure signatures that are over threshold, classified `product`, and not yet filed. Only then … re-run with `--apply`."* and *"Exit 0 is 'nothing new' — the normal, quiet case."*
- So an unattended cycle whose only event is "a ticketed failure went quiet for its window" runs the dry run, gets exit 0, and never re-runs with `--apply`. The confirmation it computed is printed in `confirmLine` and thrown away. Every row in `public.runner_heal_signatures` today carries `updated_at = 2026-09-02T16:14:42Z` — the supervised drill cycle `277d0000-…`. No unattended cycle has ever written a signature state.

**What "pending verdict" means, read from `assessConfirmations()` rather than assumed:**

- A `confirmed` entry is produced only for a row in state `watching` that has a `backlog_id` and whose `last_seen_at` is older than its window. Once `confirmed_fixed` is persisted the row leaves `watching`, so a confirmation is **always** pending when computed, and never re-computed after it lands. Idempotent by construction.
- A `recurred` entry is produced for any row in state `confirmed_fixed` **or `recurred`** that is seen again in the window — and here is a latent defect in the same function: a row already in state `recurred` with `last_recurrence_at` set is reported as a *new* recurrence on every run while the signature stays in the 14-day window, and `verdictPatches()` would increment `recurrence_count` each time. The drill ran the recurrence step exactly once, so it never saw this. **It matters for this ticket:** if exit 1 fires on every computed recurrence, an unattended cycle would re-apply (and re-increment) every fire. So `assessConfirmations()` must treat a sighting as a new recurrence only when the newest sighting is later than the stored `last_recurrence_at`; an older sighting is `stillWatching` with a reason.

**`--apply` with nothing to file already works without `--backlog-ids`:** `parseBacklogIds()` is called *after* the nothing-to-file branch returns, so a cycle re-running with `--apply --cycle-id=<id>` and no ids takes the nothing-to-file path and persists verdicts. Nothing to change there — but the runbook must say so, because today it tells the cycle to claim ids first.

**Not this ticket:** widening what the engine classifies as `product` (the CI-red blind spot the gate review named is M6-gate material), the alarm half of `SES-269`, anything in the scoreboard.
