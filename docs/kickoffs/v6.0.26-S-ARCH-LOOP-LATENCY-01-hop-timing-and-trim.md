## CONTEXT

`ci-answer-display-intent`'s (and, generically, any `request_help`-using capability's) 504 timeout was diagnosed this design session using data we already had — `ai_activity_log`'s existing `latency_ms` column, queried and grouped by timestamp gap, not new instrumentation. Direct evidence, live Vercel log export (`deepbench-frontend-log-export-2026-07-06T21-25-35.csv`) cross-referenced against `ai_activity_log`:

- Five separate 504s, every one at **59,930–60,261ms** duration — never wildly over, never under. Not an occasional slow blip; every attempt at this chain takes >60s.
- One full `request_help` round trip (`librarian` RAG lookup → `agent-directory` roster fetch → `guardrails-check` → `project-manager`'s actual model call) takes **~27 seconds by itself** (e.g. `librarian` @ 21:07:29.757 → `project-manager` completing @ 21:07:56.97). The gap between `agent-directory` (roster fetch, 21:07:35.5) and `guardrails-check` (21:07:55.2) — ~20 seconds — is almost entirely Michelle's own `agent-selection-intent` model call sitting there.
- That's one hop. The full chain still needs the requesting agent's own follow-up turn (decide to `delegate_to_agent`) plus the target agent's own full call afterward — three genuinely-serial LLM-involving steps at ~20-27s each lands almost exactly on the observed 60-60.2s wall. **The mechanism isn't looping pathologically — each hop, especially Michelle's, is individually slower than it needs to be.**
- Root cause of why this took timestamp-gap detective work instead of a one-query answer: `librarian`, `agent-directory`, and `guardrails-check` all log `latency_ms: null` — the already-logged `AI-43` gap. Fixing this is the cheap, immediate part of this session.
- Root cause of Michelle's own call being slow: her Skill Profile's `objective` ("review the full agent roster and return ranked candidates") has no cap on how many candidates to return or how much detail per candidate — with 21 agents in the roster and a default `max_tokens: 4000`, she has room to generate a `fit_summary` for every single agent instead of just the genuinely relevant few. That's the safe, concrete trim: narrow her instructions and cap her output, not cut a hop the ownership rules require.

**Explicitly not touched by this session, because they're locked architecture decisions, not overhead:** Michelle never unilaterally selecting (the requesting agent still makes its own follow-up call) and Owen re-confirming a regenerated answer before finalizing. Cutting either would violate `ARCHITECTURE.md` §19d/§19e's already-settled delegation-legitimacy rules — this session speeds up the existing hops, it does not remove any.

### Task 1 — `lib/librarian.js`: real `latency_ms` for `librarian`/`librarian-write`

`logLibrarianCall`/`logLibrarianWrite` currently omit `latency_ms` entirely from their `ai_activity_log` POST body (defaults to `null` in Postgres). Add a `latency_ms` parameter to both functions and pass it through in the JSON body:

```js
function logLibrarianCall({ supabaseUrl, supabaseKey, requestingAgentId, tier, granted, latency_ms }) {
  if (!supabaseUrl || !supabaseKey) return;
  fetch(`${supabaseUrl}/rest/v1/ai_activity_log`, {
    method: "POST",
    headers: { "Content-Type": "application/json", apikey: supabaseKey, Authorization: `Bearer ${supabaseKey}`, Prefer: "return=minimal" },
    body: JSON.stringify({
      tenant_id: "global", agent_id: "eleanor", ai_type: "librarian", feature: "librarian",
      patterns_used: ["rag"], created_at: new Date().toISOString(), latency_ms: latency_ms ?? null,
    }),
  }).catch(() => {});
  void requestingAgentId; void tier; void granted;
}
```
(same pattern for `logLibrarianWrite`, `ai_type: "librarian-write"`.)

In `queryLibrary()`: capture `const startTime = Date.now();` as the very first line inside the function, and pass `latency_ms: Date.now() - startTime` at every one of the 4 existing `logLibrarianCall(...)` call sites (lines ~128, 135, 140, 144 in the current file — grep to confirm exact lines after Task edits, do not hardcode against these numbers).

In `writeLibrary()`: same pattern — `const startTime = Date.now();` as the first line, `latency_ms: Date.now() - startTime` at every `logLibrarianWrite(...)` call site.

### Task 4 — Supabase: narrow `agent-selection-intent`'s scope + cap her output

```sql
UPDATE skill_profiles
SET objective = 'Given a described skill need, review the full agent roster and return ONLY the top 3-5 genuinely relevant candidates with their competency signal -- never a single unilateral pick, and never a rating for every agent in the roster regardless of fit. The requesting agent makes the final choice.',
    max_tokens = 1200
WHERE slug = 'agent-selection-intent';
```

Rationale, confirmed this design session: her current `objective` has no cap ("review the full agent roster and return ranked candidates") and she inherits the platform default `max_tokens: 4000` (no per-profile override was ever set) — with 21 agents in the roster, nothing stops her from generating a `fit_summary` for every one of them. Capping the instruction to "top 3-5" and `max_tokens` to 1200 bounds her output size directly without touching her schema (`candidates`/`reasoning` unchanged), her model (`claude-sonnet-4-6`, unchanged — this is a verbosity cap, not a capability downgrade), or the "never unilaterally selects" rule (still explicit in the updated text).
