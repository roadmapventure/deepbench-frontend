## 2. CONTEXT

**Original problem (found 2026-07-16, live-testing the Agent Routing drawer):** `describePipelineEvent()` hardcodes `capability: "channel-intelligence"` for the `agent_selection` and `display_format` event cases, regardless of who's actually involved — Michelle's own selection call and Alex's/Riley's/Claire's formatting call both display "Channel Intelligence" instead of their own real capability. `agent_selection` events also carry zero pattern data.

**Scope significantly widened 2026-07-17 (design session `ai-audit-triage-0717`), John's explicit hard rule, from a live screenshot review:** the fix is not "show the correct capability" — it's **no capability may ever display in the Agent Routing drawer, period.** Agent identity (who did the hop) is unaffected by this — already shown separately at the hop-card header (`RoutingHopCard`, driven by `agentId`/`agentById()`), verified independent of the capability badge this session. The per-event line under that header shows **only** real, industry-named AI patterns, formatted `"AI patterns used: [names]"`.

**Root cause, confirmed by direct code read, not guessed:** every capability call's `patterns_used` is already computed correctly and generically by the platform's one shared write-side authority, `request-receivable.js`'s `buildPatternsUsed(isJson, guardrailsRan, delegationOccurred, ragRetrieved)` — real, per-call, mechanical facts, never a static declaration read off an agent's Skill Profile (`ARCHITECTURE.md §19i`'s documented model, directly verified this session against the real function signature). `callCapability()`'s own wrapper already surfaces this as a top-level `patterns_used` field on every capability result (`MI-67`'s fix). **The bug is not missing detection — it's 3 places where an event is built from a narrower slice of a real result instead of the result itself, silently dropping the `patterns_used` field that only ever lived on the full result:**

1. **`lastHelpSelection`** (`execute.js` ~line 451) — a hand-assembled object (`{selected_by_agent_id, reasoning, candidates_considered}`), never carried `patterns_used`. This single object is reused 3 ways downstream (`last_help_selection` on non-final results, `selection` inside `buildFinalDelegationResult()`'s return, confirmed via direct read of line 323: `selection: lastHelpSelection`) — fixing it once at its single construction point fixes all 4 client-side `agent_selection` call sites at once, not 4 separate patches.
2. **`gate.triage`** (feeds `failure_triage` events) — a real field on Owen's own schema output, but `patterns_used` lives on `gate` itself, one level up, not nested inside `gate.triage`.
3. **`{resolution, result}`** (feeds `patch_resolved` events, 2 call sites) — a wrapper object; `result.patterns_used` exists (same shared mechanism, traced through `resolveConfirmation()`) but isn't hoisted to the top level the renderer reads.

**Confirmed already safe, no fix needed:** `intent_routing`, `qa_answer`, `proofreader`, `display_format`, `hypothesis_test`, `hypothesis_generation`, `memory_consolidation`, `patch_proposed` — all 8 already carry real `patterns_used` at the level the renderer reads (7 via the shared `callCapability()` wrapper directly, `hypothesis_test`/`hypothesis_generation` via their own already-fixed explicit threading, `MI-67b`).

**Explicitly out of scope this session (John's direct call — separate session):** the `delegation`/`delegation_return` event type (live micro-hop mechanism, `§19h`) has zero capability and zero pattern data structurally — no `patterns_used` field exists in its payload at all. Fixing this needs `LOG-23` (a real "Routing" pattern doesn't exist in the catalog yet) and `LOG-26` (whether pattern naming here should be reasoning-derived rather than catalog-matched) resolved first. These rows, plus `LOG-24` (persistent anti-hardcoding rule) and `LOG-25` (catalog retirement question), are logged in `docs/FEATURES.md` and fully detailed in `docs/S-AI-AUDIT-TRIAGE-01-FINDINGS.md` — do not fold any of them into this session.

**Grep-verified before scoping (Architect Review — duplicate/cross-reference check):** `SERVICE_LABEL` (`MarketIntelligenceScreen.jsx` ~line 401) is referenced in exactly one place in the entire codebase — `RoutingActivityLine`'s `const svc = SERVICE_LABEL[capability]`. Once capability display is removed, this object and its one call site become fully dead code — delete both, don't leave an orphaned label dictionary sitting in the file (matches the standing concern that led to this whole investigation: an unused capability→label dictionary is exactly the shape of thing that invites being hand-extended later instead of questioned).

**Multi-site bug pattern check:** confirmed this is genuinely 3 real root causes (not artificially split, not artificially merged) — `lastHelpSelection`'s single-point fix cascades to 4 call sites; `gate.triage` and `{resolution, result}` are each their own distinct narrower-slice/wrapper shape and need their own one-line fix apiece.

// T1: lastHelpSelection-equivalent construction includes patterns_used from delegateResult
function buildLastHelpSelection(pmAgentId, delegateResult) {
  return {

function describeEventNoCapability(type) {

    display_format: { summary: "Formatting data for display", color: "moss" },
    proofreader: { summary: "Reviewing the answer", color: "moss" },

function patternLine(patternsUsed, nameMap) {
  const real = Array.isArray(patternsUsed) ? patternsUsed : null;
  if (!real || real.length === 0) return null;
  return `AI patterns used: ${real.map(slug => nameMap[slug] || slug).join(', ')}`;

const NAME_MAP = { rag: "RAG", "structured-output": "Structured Output" };
