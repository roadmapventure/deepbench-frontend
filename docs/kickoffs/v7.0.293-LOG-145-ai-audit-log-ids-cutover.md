## 1. CONTEXT — the premise, revalidated with the measured numbers

What `LOG-145` states is true and holds:

- `ai_pattern_classification_rollup` (13 rows) carries `log_ids` — `array_agg` of every matching
  `ai_activity_log.id`: **32,441 ids, 190,808 bytes** across the 13 patterns
  (`sum(octet_length(log_ids::text))`, measured this cycle).
- `src/hooks/useAIActivity.js:1243` still selects `log_ids` on every
  `fetchPatternClassification()` read, and re-buckets the ids in JavaScript.
- `ai_pattern_agent_hop_rollup` (`LOG-41`, v7.0.289; 122 rows: `pattern_slug`, `pattern_name`,
  `dim` `'agent'|'hop'`, `agent_id`, `hop_depth`, `call_count`, `cost_sum`) answers the by-agent
  and by-hop questions in 122 rows — and is read by **nothing** in `src/`, `api/`, `lib/`, or
  `scripts/` (grep, this worktree, verified again against the clone).
- The binding timing constraint (measured at `LOG-41`'s ship, as `anon`): new view **2,353 ms**,
  existing platform rollup **2,194 ms**, one anon run of the new view returned **57014**
  (statement timeout) against the 3-second cap. Two ~2.3 s queries per page load would be
  strictly worse than today. The cutover must **replace** payload, never add a query alongside.

**What does not hold is the ticket's implicit assumption that a cutover exists to be done.**
The per-surface analysis below is the deliverable the ticket asked for ("the cutover must decide
per surface what moves and what still needs row identity") — and the honest answer is that
**zero of the four consumers can move**. This kickoff therefore ships the one genuinely
defensible reduction that is available inside the caps (one module-level cache, mirroring the
four caches this same file already uses), pins the binding constraint with a regression guard so
no later session "finishes the cutover" by quietly breaking a reconciled number, and puts the
disposition of `LOG-145` and of the zero-reader view to John on a gated card.

## 2. The per-surface decision table — what moves, what stays, and why

`log_ids` serves four distinct client-side jobs (the ticket names three; job 3 is a distinct
derivation from job 2's data). Each was read in source this session, not recalled:

| # | Surface (feature, location) | Moves to `ai_pattern_agent_hop_rollup`? | Why it still needs row identity |
|---|---|---|---|
| 1 | `costBySlug` — By Pattern cost (`LOG-97`, `useAIActivity.js:1282-1293`) | **No** | Per-pattern cost = sum of the hydrated log's own per-row `cost`, which `computeCallCost()` derives (single source of pricing truth, incl. `HAR-02a` cache-token rates) and which hydrate already zeroed for AI-51 paired duplicates. The view's `cost_sum` is a naive SQL token-sum — the exact ~$26-vs-$10 misreport `LOG-97` fixed (66% of request-routing's rows are paired duplicates, per the code's own measured comment). Joining server classification × client pricing requires the ids. |
| 2 | `classified[].total` — By Pattern countable totals (`LOG-81`, `:1301-1313`) | **No** | Countable = `model` non-null AND not the AI-51 duplicate half. The pairing decision is a client-side legacy-window heuristic (`PAIR_LEGACY_CUTOFF_MS` + 2 s window) that exists only in JS; both rollup views' `call_count` count every classified row including duplicate halves. Re-deriving the total means filtering *this pattern's ids* against the client's countable set — identity again. |
| 3 | `reclassificationCount` (`LOG-81`, `:1319-1327`) | **No** | `countableIds.size` minus the **union** of classified countable ids. A union over overlapping per-pattern id sets (one call can carry multiple patterns) is set algebra — definitionally inexpressible from per-pattern aggregates; summing would subtract overlap twice (the code comment says exactly this). |
| 4 | `buildAgentPatternRows` — MI Agents drawer per-agent × pattern rows (`LOG-112`, `:327-347`; consumed at `MarketIntelligenceScreen.jsx:3110-3151`) | **No — not even the counts** | Two independent blockers: (a) the drawer's rows are avg/max **latency**, which the view does not carry (the ticket knew this); (b) the drawer joins the agent's **scoped, windowed** row set (`useAgentActivitySummary`: `MI_LOOP_SCOPE`, `RECENCY_WINDOW_DAYS = 30`, tenant filter — `useAgents.js:145-182`), while the view is all-time and unscoped. Substituting its counts would let a pattern sub-row exceed the agent's own CALLS headline — the exact defect `LOG-112` shipped to kill ("`1,801 CALLS`, sub-row `3,450 calls`"). |

**Conclusion, stated plainly rather than implied:** the "deliberately deferred half" of `LOG-41`
turns out to be structurally empty, not deferred. All four jobs join server-side classification
facts (which rows matched — computed in the DB, per §19k, never client-side) against client-side
facts (pricing, AI-51 pairing, countability, scope/window/latency — which live only in JS, per
`LOG-21`'s single-shared-math rule). That join *is* row identity. The 190,808 bytes are the price
of every By Pattern number reconciling with Total Cost / Total Calls, riding a query that already
happens, at zero extra round trips. `ai_pattern_agent_hop_rollup` answers a question — all-time
by-agent / by-hop pattern aggregates — that **no shipped surface asks**. Moving the countable
definition or pricing into the view would fork `LOG-21`'s shared math into SQL and is an
architecture decision for John, not a cutover (named on the card, Task 4).

## 3. The defensible piece that IS in scope — stop re-paying for the payload

`fetchPatternClassification()` (`useAIActivity.js:1237-1262`) is the **only** per-page-load
Supabase read in this file with no module-level cache. Its four siblings all cache:
`fetchPatternVocabulary` (`:1196-1216`), `fetchPlatformServices` (`:438-459`),
`fetchCapabilityDirectory` (`:478-498`), and the caller directory — each with the same
"cache success, never cache a failure, share the in-flight promise" discipline.

Meanwhile it has **two mount sites** — `AIActivityPanel.jsx:403` (AI Audit, with the `log`
argument) and `MarketIntelligenceScreen.jsx:3110` (`AuditDrawersBody`, no argument) — and every
mount of either re-runs the ~2,194 ms anon rollup query, re-ships the 190,808-byte `log_ids`
array, and re-runs the reclassification-count query. Every SPA navigation back to either screen
pays again. The refetch buys nothing: the log it is re-derived against hydrates **once** per page
load (module-level `_log`/`_hydrated`), so a "fresher" classification can only drift from the
cached log it joins — caching makes the two *more* consistent, not less.

**The change: give `fetchPatternClassification()` the exact cache shape its siblings use.**
No view change, no select-list change, no new query, no behavior change on first load.

```js
export function fetchPatternClassification() {
  if (_pclassCache) return Promise.resolve(_pclassCache);
  if (!_pclassPromise) {
    _pclassPromise = Promise.all([
      supabase.from('ai_pattern_classification_rollup').select('pattern_slug, pattern_name, pattern_description, call_count, cost_sum, log_ids'),
      supabase.from('ai_pattern_reclassification_count').select('reclassification_count').single(),
    ]).then(([rollup, recl]) => {
      if (rollup.error) throw rollup.error;
      if (recl.error) throw recl.error;
      const classified = (rollup.data || []).map(r => ({
        slug: r.pattern_slug,
        name: r.pattern_name,
        desc: r.pattern_description,
        total: r.call_count,
        cost: Number(r.cost_sum) || 0,
        logIds: r.log_ids || [],
        active: true,
      }));
      _pclassCache = { classified, reclassificationCount: recl.data?.reclassification_count ?? 0 };
      return _pclassCache;
    }).catch(e => {
      console.warn('[LOG-38] pattern classification fetch failed; By Pattern section will show empty', e);
      _pclassPromise = null; // allow a later mount to retry; never cache a failure
      return { classified: [], reclassificationCount: 0 };
    });
  }
  return _pclassPromise;
}
```

load. **Stated honestly: the first-load 190,808 B payload itself is NOT reduced** — Section 2 is
the proof that reducing it means abandoning row identity that every consumer needs, which is
John's architecture call (Task 4), not a session's line change.

// already have, and the "cutover" LOG-145 imagined is pinned as impossible-by-design:
//
//   1. A FAILED read is never cached (preservation control -- passes before and after; a cache
//      that swallows failures would freeze By Pattern empty for the whole session, LOG-102's
//      failure-honesty concern).

//      Pre-change: 2 queries, each shipping the 190,808-byte log_ids payload at ~2.2 s as anon
//      against the 3 s cap. This is the discriminating assertion -- it FAILS on unchanged source.
//   3. A LATER mount is served from the cache: zero new queries, zero re-shipped bytes.
//   4. Source-level pins of LOG-145's binding constraint: the read KEEPS selecting log_ids

// captures at client creation is the stub) and restored in `finally` (run-all.js runs every
// guard in one process). This guard leaves the module's classification cache populated with stub
// data; no other guard reads it (verified at design time: no other test file references

import assert from "assert";
import fs from "fs";
import path from "path";
import { fileURLToPath } from "url";
import { selfRun } from "./_lib/self-run.js";

const __dirname = path.dirname(fileURLToPath(import.meta.url));
const ROOT = path.resolve(__dirname, "../..");

export default async function run() {
  const realFetch = globalThis.fetch;
  const calls = [];

  const json = (body) => new Response(JSON.stringify(body), {
    status: 200, headers: { "Content-Type": "application/json" },
  });
  globalThis.fetch = async (url) => {
    const u = String(url);
    calls.push(u);
    if (mode === "fail") throw new Error("LOG-145 stub: simulated network failure");
    if (u.includes("ai_pattern_classification_rollup")) {
      return json([{ pattern_slug: "stub-pattern", pattern_name: "Stub Pattern",
        pattern_description: "d", call_count: 2, cost_sum: "1.5", log_ids: [11, 12] }]);
    }
    if (u.includes("ai_pattern_reclassification_count")) {
      return json({ reclassification_count: 7 }); // .single() resolves an object
    }
    return json([]);
  };
  try {
    // Placeholder Supabase env so the module graph loads under plain `node` (same as LOG-112's
    // guard); no real network call is made -- fetch is the stub above.
    if (!process.env.VITE_SUPABASE_URL) process.env.VITE_SUPABASE_URL = "http://localhost:54321";
    if (!process.env.VITE_SUPABASE_ANON_KEY) process.env.VITE_SUPABASE_ANON_KEY = "regression-placeholder";
    const { fetchPatternClassification } = await import("../../src/hooks/useAIActivity.js");
    const rollupCalls = () =>
      calls.filter(u => u.includes("ai_pattern_classification_rollup")).length;

    // -- 1. A failure is never cached (preservation control) --
    const r1 = await fetchPatternClassification();
    assert.deepStrictEqual(r1, { classified: [], reclassificationCount: 0 },
      "on fetch failure the hook must resolve to the empty fallback shape");
    assert.ok(calls.length > 0, "the failure phase must actually have attempted a query");
    mode = "ok"; calls.length = 0;

    // -- 2. Concurrent mounts share ONE in-flight read (fails on unchanged source: 2 !== 1) --
    const [r2a, r2b] = await Promise.all([fetchPatternClassification(), fetchPatternClassification()]);
    assert.strictEqual(rollupCalls(), 1,
      "two concurrent mounts (AI Audit + MI Agents drawer) must share one in-flight rollup " +

      "~2.2 s anon read against the 3 s statement-timeout cap");

    assert.deepStrictEqual(r2a.classified[0].logIds, [11, 12], "log_ids still hydrate logIds");
    assert.strictEqual(r2a.reclassificationCount, 7, "reclassification count survives");
    assert.deepStrictEqual(r2b, r2a, "both concurrent callers see the same result");

    // -- 3. A later mount is served from the module cache: zero new queries --

      "zero re-shipped bytes (same cache discipline as fetchPatternVocabulary)");
