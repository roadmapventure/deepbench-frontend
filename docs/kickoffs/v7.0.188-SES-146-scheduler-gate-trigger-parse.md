## Premise, revalidated live this cycle

`SES-143` shipped the settings gate so John's §2b Automation panel would become **binding**: the cron
stays hourly permanently and each cycle paces *itself* down to his `interval_hours`. Read live at
13:44Z, `runner_settings` is `scheduler_on = true, interval_hours = 1, cron_minute = 40`.

The gate does not do that for every cycle. It has two independent defects, both of which **fail
open**, so nothing has broken and nothing in the ledger shows it.

### Defect 1 — the contract mismatch

Step 1b tells every cycle, verbatim:

```sql
SELECT * FROM public.scheduler_gate('<your cycle id>', '<your prompt''s trigger: line, verbatim>', now());
```

and reinforces it in prose: *"Pass your prompt's `trigger:` line **as written**."* The routine
prompt's line reads `trigger: scheduled`. The function tests:

```sql
v_scheduled := (coalesce(p_trigger, '') = 'scheduled');
```

Exact equality against the **bare word**. A cycle that follows the runbook literally — which the
stored prompt commands (*"execute it EXACTLY"*) — passes `trigger: scheduled`, never matches, and
takes the fail-open branch *"not a scheduled cycle — your scheduler setting governs scheduled fires
only."* **Pacing is skipped entirely, and so is the `scheduler_on = false` branch**, which sits
below `v_scheduled` on the same path.

**Negative control, run live on this cycle's own id, same instant, one variable changed:**

| `p_trigger` | `reason` returned |
|---|---|
| `trigger: scheduled` (the runbook's literal instruction) | `not a scheduled cycle — your scheduler setting governs scheduled fires only` |
| `scheduled` (the bare word) | `manual fire (started off the cron grid) — never paced` |

The five paced rows to date (06:41Z, 07:41Z, 10:41Z and two earlier) all passed the **bare** word —
every cycle so far read the instruction loosely and got lucky. This cycle read it literally and the
gate went inert.

### Defect 2 — the grid test measures the wrong clock

```sql
v_dist   := abs(extract(minute from p_started)::int - v_minute);
v_dist   := least(v_dist, 60 - v_dist);
v_manual := v_scheduled and v_dist > 2;
```

`p_started` is `now()` **at the moment the cycle reaches step 1b**, not the moment the routine fired.
This cycle fired at 13:40:52Z and reached the gate at 13:43:12Z — `v_dist = 3` — so **even with the
bare word it is classified a manual fire and exempted from pacing.** Any cycle whose step-0/0b work
takes more than ~2 minutes is silently exempt from John's interval. Predecessors reached the gate
inside two minutes and were paced; this one did not, because step 2 now reads a 65k-token runbook.
The tolerance was never wrong in principle — it was measured against a clock that drifts with how
much work the cycle does first, so it gets **worse as the runbook grows**.

### Net effect

John's Automation interval is inert for any cycle that either follows the runbook literally or is
slower than ~2 minutes to step 1b. This is the same failure family the platform has now paid for
repeatedly (`SES-101`'s revoke that reported success and changed nothing; `SES-128`'s calibration
that had never once been carried out): **a control that looks shipped, reports success, and never
fires.**

## The fix — one migration, one runbook block

`ses146_scheduler_gate_trigger_parse`.

1. **Normalise the trigger inside the function.** Strip a leading `trigger:` and surrounding
   whitespace, lowercase, then match. Both forms then work, and the runbook's verbatim instruction
   becomes **true** rather than lucky. `chained (drain continuation)` (`SES-141`) still normalises to
   something that is not `scheduled`, so the drain chain stays exempt — preserved, not re-derived.
2. **Anchor the grid test to the cycle row's `started_at`**, not to `p_started`, falling back to
   `p_started` when the cycle id resolves to nothing. `started_at` is stamped at step 1, immediately
   after step 0, so it is the earliest fire-time proxy available inside SQL and does not drift with
   how long the cycle spends reading.
3. **Make the tolerance a column, not a literal** — `runner_settings.grid_tolerance_min`, default
   **10**, `CHECK 0..30`. This is `SES-143`'s own precedent applied one step further (it made the
   cron minute a column *"not a literal"* for exactly this reason): correcting it is one `UPDATE`,
   never a migration. Ten minutes covers realistic step-0 latency; with an hourly cron a genuine
   manual fire still lands off-grid ~83% of the time, and when it does not, the only consequence is
   that a tap arriving within ten minutes of a scheduled fire is paced — at which point a cycle has
   just run anyway.

**Explicitly preserved, all four `SES-143` properties:**

- **Predecessor predicate untouched** — still the most recent row whose `outcome` is not
  `did_not_run`. This is the property whose naive form *wedges the runner shut permanently*; it is
  not touched, and the QA re-asserts it.
- **Fails open on every unknown** — no settings row, NULL column, no predecessor, unrecognised
  trigger word → `run`.
- **Scheduled cycles only** — a chained drain successor stays exempt.
- **A manual fire is exempt** — same test, now measured against a clock that does not drift.

Signature is **unchanged** (`uuid, text, timestamptz`), so `CREATE OR REPLACE` replaces in place and
creates no overload — `.claude/rules/supabase-function-signature.md`. Asserted after apply.

## QA bar — discriminating, not merely complete

The question each arm must survive: *would it still pass if the change did nothing?*

| # | Arm | Retired build | Shipped build |
|---|---|---|---|
| A | `p_trigger = 'trigger: scheduled'`, predecessor < interval | `run` ("not a scheduled cycle") | **`paced`** |
| B | `p_trigger = 'scheduled'`, predecessor < interval, gate reached 3 min late | `run` ("manual fire") | **`paced`** |
| C | `p_trigger = 'chained (drain continuation)'` | `run` | `run` — drain chain still exempt |
| D | `scheduler_on = false`, literal trigger line | `run` (defect 1 skipped the branch) | **`scheduler-off`** |
| E | Genuine manual fire, far off grid | `run` (manual) | `run` (manual) — not broken by the anchor |
| F | Fail-open: no settings row / NULL interval / no predecessor | `run` | `run` |
| G | Predecessor predicate: a `did_not_run` row is never the predecessor | correct | correct — unchanged |

A/B/D are the discriminating arms — each returns a **different verdict** on the two builds against
identical inputs. C/E/F/G are the preservation arms.

All arms run on fixtures inside a **deliberately rolled-back transaction**; grants asserted **both
directions** after apply (`SES-101`).
