## 1. What was left, and why this is a slice rather than an assumption

Slices 1–3 shipped the green anchor and decision engine (`v7.0.332`), migration down-capture
(`v7.0.333`) and the deploy-serving-red trigger (`v7.0.334`). The ticket's own declared remainder:

> **(a) DATA RESTORE** — before-images in a reverted range are REPORTED, never replayed; replaying
> rows needs per-table pk resolution and an insert/update/delete discrimination a wrong guess writes
> into production, so **whether it is built at all is a design question**, not a slice a cycle should
> assume.

That sentence is right about *applying* and wrong about *knowing*. This slice builds the knowing and
touches none of the applying. The card's line has said, since slice 1:

> `N before-image(s) across M table(s) were written in this range. They are REPORTED, not replayed.`

True and useless — it says something was touched and nothing about whether it could be put back.

## 2. What shipped

`public.plan_data_restore(p_cycle_id uuid)` (migration `ses182d_restore_plan`) classifies every
before-image in a cycle's range and **applies nothing**. The engine calls it, and
`summarizeRestorePlan()` renders it onto the incident card.

**Why Postgres and not the engine** — three facts, not taste:
1. SQL `NULL` and the jsonb scalar `'null'` are indistinguishable through a PostgREST read, and the
   whole INSERT-vs-UPDATE discrimination rests on telling them apart.
2. The primary key of an arbitrary table is a catalog question (`pg_index` / `pg_attribute`), and the
   repo carries no schema SQL to read it from.
3. The **oldest** image per `(table, pk)` is the true pre-range state; collapsing that in JS means
   shipping the whole image set over REST first.

**The vocabulary** — three classes, and the two refusal grounds that must never merge:

| class | meaning |
|---|---|
| `restorable` | the row can be addressed and nothing has written it since (`action` = `delete` for an image the range inserted, `upsert` to put a prior state back) |
| `unverifiable` | **cannot check** — the table carries no `updated_at`, so a later legitimate write cannot be ruled out |
| `refused` | ledger table · not a table · no pk · composite pk · pk type mismatch · **checked and it moved** |

`refused`-for-staleness means *I checked and it moved*; `unverifiable` means *I cannot check*. Both
are unsafe to apply and they are **different facts John acts on differently**. Collapsing them into
one "not restorable" bucket is the edit this slice forbids, and
`tests/regression/SES-182d-restore-plan.js` pins it with exactly that retired form run on the **same
fixture** and asserted to LOSE.

## 3. Two things found live that the design did not predict

Measured this cycle over all 3,109 attributed before-images, not recalled:

- **`table_name` is not always a table.** 19 images carry a free-text provenance label where a table
  name belongs — `pg_proc:scheduler_gate`, `the_library (DDL)`, `pg_catalog.schema:backlog_items`,
  and a whole sentence beginning `drill-project itcimllfniypelrxsuoh: DROP SCHEMA public CASCADE`.
  An engine that treated the column as a table would resolve garbage and, on an upsert, **write a
  junk row into production** — precisely the failure the ticket feared, arriving from a direction it
  did not name. Hence `to_regclass` is checked before anything else.
- **136 images store something that is not the primary key** — 135 on `backlog_items` (the
  `backlog_id`, e.g. `SES-99`, or prose such as `(schema) queue column + recompute_backlog_queue()`)
  and 1 on `epics`. Those images **cannot address their row at all**, so §19v's "no before-image, no
  write" promise is, for them, unredeemable today. Note the trap in the obvious repair: `backlog_id`
  carries **no unique constraint** (`CHI-48` occupies two rows, `SES-97`), so a resolver that "helpfully"
  fell back to it would restore **both** rows. Filed as its own ticket rather than patched here.

**Live distribution across all attributed images (3,109 rows → 3,109 planned):**
`refused` 2,127 (ledger 1,207 · stale 765 · pk-mismatch 136 · not-a-table 19) ·
`restorable` 958 (391 delete, 567 upsert) · `unverifiable` 24.

## 4. QA

- **Discriminating, and it would not pass if the change did nothing:** all five classes fire on real
  rows, and the control is the retired one-bucket summary on the same fixture, asserted to differ.
- **The guard caught a defect before the ship:** the unreadable-plan clause matched the phrase inside
  the honest sentence *"what could be put back is UNKNOWN"*. The assertion was tightened to the real
  defect — a **numeric** claim on a plan never read — rather than the message being weakened.
- **File-level negative control:** the guard cannot even load against `origin/dev`'s engine (the
  exports it pins do not exist) and passes on the shipped one.
- **Grants asserted BOTH directions inside the migration** (`SES-101`): `anon` EXECUTE false,
  `service_role` true, and `count(*) = 1` on the overload
  (`.claude/rules/supabase-function-signature.md`).
- **Nothing was written to production data.** The function is read-only; every QA call was a SELECT.

## 5. Named remainder — and it is John's, not a cycle's

The **apply lane** is untouched and deliberately so. The question goes on this slice's ship card:
should the runner ever put the safe rows back itself — automatically during a rollback, or on a
Reverse — or should it only ever show the list? **Recommendation: list-only**, because the rows it
would refuse are refused precisely because it cannot *prove* nobody wrote them since, and a wrong
automatic row-write is production data nobody can un-guess. Unanswered defaults to list-only, which
is fail-closed and costs nothing.

`SES-182` therefore stays `partial` with `design_status = 'needs-john'`: the remaining work is a
decision only he can make, and that is what the flag means.
