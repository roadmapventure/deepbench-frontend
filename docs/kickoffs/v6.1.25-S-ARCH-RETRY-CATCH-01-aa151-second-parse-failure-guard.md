## 1. CONTEXT

`S-ARCH-RETRY-TOOLRESULT-01` (v6.1.24) fixed `AA-150`/`AA-151`'s dominant cause — a missing `tool_result` block in `callModel()`'s retry-once correction message — which fully resolved Owen's `qg-review-intent` (10%→0% failure, independently confirmed) but only cut Priya's chart-blocking `hyp-hypothesis-test-display-intent` failure rate roughly in half (80%→40-60%, not resolved). Two independent live re-tests after that fix (the coding session's own: 2/5 fail; the design session's independent re-check: 3/5 fail) confirmed a real, distinct second bug.

**Root cause (confirmed by reading the shipped code and matching the actual error payloads from both re-tests):** `callModel()`'s retry-once block now correctly builds a `tool_result` message and gets an HTTP-level success back from Anthropic on retry — the `AA-150` fix works. But the retried response is still passed through `parseModelTurn(llmData, hasSchemaTool, schemaTool)` a second time (`request-receivable.js`, immediately after `if (!retryRes.ok) throw ...`), and this second call has **no `try/catch` around it**. If the model's retried attempt *also* fails validation — e.g. it omits a required schema field again — `parseModelTurn()`'s own error (`AA-147`'s `Schema tool "X" called with missing required field(s): Y`) propagates straight out of `callModel()` uncaught, surfacing upstream as a raw, unhandled 500 instead of the graceful `"Parse failed and retry also failed"` 422 this entire retry block exists to produce.

**Confirmed live, both re-tests, exact payloads captured:**
- `{"error":"Schema tool \"agent-selection-intent\" called with missing required field(s): recommended_agent_id"}` (HTTP 500)
- `{"error":"Schema tool \"intelligence-review-format\" called with missing required field(s): key_data_points, override_warning"}` (HTTP 500)

Both are `AA-147`'s exact required-field-check error text, both surfaced as a raw 500 rather than the intended 422 — confirming the second `parseModelTurn()` call is the unguarded one, not a new/different validation gap.

## 5. TASKS (1 of 4 max, 1 file)

### Task 1 — `api/prompt/request-receivable.js`: wrap the post-retry `parseModelTurn()` call in its own `try/catch`

Currently (inside the `if (tools.length > 0) { ... }` branch, after the retry `fetch`):

```js
      llmData = await retryRes.json();
      usage = { input_tokens: usage.input_tokens + (llmData.usage?.input_tokens || 0), output_tokens: usage.output_tokens + (llmData.usage?.output_tokens || 0) };
      turn = parseModelTurn(llmData, hasSchemaTool, schemaTool);
    } else {
```

Replace with:

```js
      llmData = await retryRes.json();
      usage = { input_tokens: usage.input_tokens + (llmData.usage?.input_tokens || 0), output_tokens: usage.output_tokens + (llmData.usage?.output_tokens || 0) };
      // FEATURE: AA-151 -- the retry HTTP call can now succeed (AA-150's tool_result fix) while the
      // model's retried response still fails validation itself (e.g. omits a required schema field
      // again). This second parseModelTurn() call was previously unguarded, so that failure propagated
      // uncaught as a raw error (an unhandled 500) instead of the graceful "retry also failed" 422 this
      // whole block exists to produce. Confirmed live: agent-selection-intent missing
      // recommended_agent_id, intelligence-review-format missing key_data_points/override_warning, both
      // on the retried attempt, ~40-60% of Priya's hyp-hypothesis-test-display-intent calls.
      try {
        turn = parseModelTurn(llmData, hasSchemaTool, schemaTool);
      } catch (retryParseErr) {
        throw Object.assign(new Error('Parse failed and retry also failed'), { status: 422, detail: retryParseErr.message });
      }
    } else {
```

**Why this design, not a bigger one:** still retry-once-then-throw — no new retry attempt, no change to when a retry is triggered. This only ensures the *outcome* of the one existing retry (success or failure) is reported through the single existing graceful-failure shape (`"Parse failed and retry also failed"`, 422) instead of leaking a second, differently-shaped raw error depending on which of the two `parseModelTurn()` calls happened to fail. Does not address *why* the model sometimes repeats the same omission on retry (a prompting/model-reliability question, not a harness bug) — that's explicitly out of scope; this session only ensures the failure is reported consistently and gracefully either way.
