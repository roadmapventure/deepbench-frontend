## Premise, revalidated live before building

Not recalled — measured this cycle against the stored set `selfbuild-step0-2026-08-23`:

- **62 of 62** manifest entries carry a Windows backslash (`data\<table>.ndjson`). **0** carry `/`.

The set is byte-perfect; only the separator is wrong. Both readers report an unresolvable path as an
**altered file**, so the message points whoever is mid-outage at the integrity of their last backup
rather than at a separator. The premise holds.

## The change — 3 files, in `roadmapventure/deepbench-backups-offsite`

On branch **`ses191/backup-path-portability`**. Never `main`: that repo is what the platform falls
back to, and John's authorization was for a reviewable branch.

| File | Site | Change |
|---|---|---|
| `dump-supabase.mjs` | was 159, 204 | new `relPosix()`; manifest paths stored POSIX **always**, so future sets are clean |
| `restore-supabase.mjs` | was 68 **and 102** | new `entryPath()`; resolves either separator |
| `verify-backup.mjs` | was 28 | same `entryPath()` helper |

**The site the ticket did not name.** `restore-supabase.mjs` resolved `rec.file` in **two** places —
the integrity check *and* the data read at line 102. The card named only line 68. Fixing that one
alone produces a run that verifies clean and then fails the actual restore, which is a worse failure
than the one being fixed, because it fails later and with more confidence behind it.

**Why the reader fix is not redundant once the writer is clean.** The writer fix only helps sets
taken *after* it. The reader fix is what repairs sets **already taken** — including the one standing
as the live recovery net right now, which cannot be retaken retroactively. Both halves ship, and the
readers stay separator-agnostic permanently rather than narrowing to POSIX later: the whole defect
was a reader that understood only its own platform.

**`tests/regression/SES-191-backup-path-portability.js` gains Part 3**, which runs the *real*
`verify-backup.mjs` against a fixture set whose manifest carries a foreign separator and is sound in
every other respect. Negative controls, both required:

- Against the **pre-fix** script (`git show origin/main:verify-backup.mjs`) the new part **FAILS**,

Part 3 is env-gated on `DEEPBENCH_BACKUP_TOOLING` and **declared `notRun`** when absent, because the
tooling is not in this repo. It deliberately runs the script rather than grepping its source: a
source check passes on a script that imports the helper and forgets to call it at one of the two
sites — exactly the bug that was there.

## What this does NOT do — named, not implied

1. **The fix is on a branch and is NOT merged.** Anyone cloning the backups repo fresh during an
   outage still gets the broken readers until `ses191/backup-path-portability` lands on its `main`.
   That merge is John's call, not an unattended one.
2. **The second tooling copy at `C:/Projects/deepbench-backups` is untouched** and will diverge.
3. **The restore drill itself has not run.** Charter exit criterion 5 is still unscored. John's
   authorization for the $0 scratch slot stands and is now waiting on execution, not on a decision.

So `SES-191` closes **`partial`, not `done`** — and that is deliberate rather than conservative:
the verifier's interim auto-done bar governs `delivered` vs `done`, and neither is honest for a
ticket whose headline deliverable (the drill) has not been executed.
