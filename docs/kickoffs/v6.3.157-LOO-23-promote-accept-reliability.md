# v6.3.157 — LOO-23: Channel Sales Intelligence "Accept" reliability (Nadia data-patch promote)

**Session:** `process-0727` · **Type:** live discovery → fix (John-directed, P0) · **Version:** v6.3.157
**Feature:** LOO-23 (Agent Loop) · **Screen:** Channel Sales Intelligence (CHI)

## Problem (as reported)

John tested a theory, requested a forecast, and clicked **Accept** on Nadia Farouk — Data Expert's
Draft Forecast. It returned "Something went wrong resolving that — try again." He required Reject,
Edit, and Accept all verified working end-to-end.

## Root cause — three independent defects on the Accept path

Accept on a Nadia draft runs the confirmed correction through `data-patch-execute-intent` (Nadia's
"execute the promote" step), which delegates to Eleanor Voss — The Librarian via `request_help` to
write the Data Room. Replaying John's exact draft (`pending_confirmations.7fef4cd8`, `action:promote`,
`chunk_id:null`, 2534-char content) against the live dev preview produced **four different outcomes
from identical input** — a coin-flip. Three root causes:

1. **Model conformance (John's exact failure).** `data-patch-execute-intent` ran on **Haiku**
   (`max_tokens:1500`). On the multi-turn structured `request_help` loop it intermittently failed
   schema-parse twice → "Parse failed and retry also failed" (HTTP 422, `detail` a plain string, so
   the frontend's DAT-7 `denied-` branch didn't match → generic "something went wrong"). The failed
   call logged **nothing** to `ai_activity_log` (the throw precedes `logAICall()`), so only the
   `pending_confirmations.resolution.error` message survived. Not truncation (2534 chars ≈ ~640
   tokens, well under 1500) — a smaller-model conformance problem.

2. **Impossible lineage FK.** On the "correct an existing record" (with-chunk) promote, Eleanor's
   `library-write-intent` schema asked the model for `promoted_from_reasoning_id` ("the the_reasoning
   row this was promoted from"). But Nadia writes her reasoning row **last**, so at insert time it does
   not exist — the model either omitted it (lineage silently lost) or filled the superseded chunk id
   (a the_library id) → raw Postgres **23503 FK violation** ("… not present in the_reasoning"). This
   field is **write-only — never read anywhere in the codebase.**

3. **Stray-supersede raw crash.** On a brand-new insight (null chunk_id) the model occasionally still
   fired the "supersede" step; `writeLibrary`'s `update_status` had no id-format guard (unlike
   `insert`, per DAT-6/AA-189) and **raw-threw** "status update failed" on the bad id — sinking the
   whole Accept even though the insert had already saved the correction.

Reject and Edit were never broken (Reject just marks the row; Edit re-runs the draft on Sonnet).

## Fix

Two data changes + one code file (`lib/librarian.js`), all in the platform's own graceful-denial idiom:

- **Data — `data-patch-execute-intent.llm_model`:** `claude-haiku-4-5-20251001` → `claude-sonnet-4-6`
  (the same model its own draft half, `data-patch-intent`, already uses). Fixes #1.
- **Data — `library-write-intent`:** removed `promoted_from_reasoning_id` from the schema — stop
  asking the model for a value it structurally cannot know. Addresses #2 at the data layer.
- **Data — `data-patch-execute-intent.analysis_instructions`:** branch the promote on chunk_id —
  chunk present ⇒ insert-consolidated + supersede (unchanged); chunk null/absent ⇒ **insert only, do
  NOT supersede**; and `source_chunk_ids` is `[chunk_id]` only when a real id was given, else `[]`
  (previously hardcoded `[chunk_id]`, which sent `[null]` for new insights). Reduces #3's trigger.
- **Code — `lib/librarian.js` (`writeLibrary`):**
  - `insert`: validate-or-drop `promoted_from_reasoning_id` (UUID + resolves in `the_reasoning`,
    same room) → null. Never deny (non-load-bearing). Backstop for #2.
  - `update_status`: UUID-guard `id` → graceful `denied-row-not-in-data-room` instead of a raw
    22P02/throw. Fixes #3 (a stray/absent supersede can no longer crash a promote whose insert
    succeeded).

Data lives in Supabase (`skill_profiles`) per "capabilities are data" — no repo seed exists; applied
via MCP. Eleanor remains the sole `the_library` writer (gatekeeper untouched); the model still
orchestrates via `request_help`.

## Follow-ups logged

- The promote remains **model-orchestrated** (Nadia decides insert-vs-supersede via `request_help`),
  so it is reliability-hardened, not provably deterministic. A deterministic promote (platform decides
  insert/supersede from `chunk_id`, model out of the orchestration) is the durable fix — separate
  design, touches the gatekeeper. → new backlog item.
- Bidirectional promote lineage (`promoted_from_reasoning_id` / `promoted_to_library_id`, AG-023) is
  **dead / never populated correctly** (write-only, unknowable at insert time). If real lineage is
  wanted it needs deterministic post-write stitching. → new backlog item.
