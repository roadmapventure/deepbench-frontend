## 2. CONTEXT

The Agent Routing log (Column 3, desktop; pinned feed, mobile) shows an AI-pattern tag line per row (e.g. "Structured Output, RAG, Case-Based Reasoning"). This is meant to be real per-call data — `RoutingEventRow` already prefers `evt.data.patterns_used` over a static fallback (`AI-50c`, `SERVICE_LABEL[capability].patterns`) — but for most event types on this screen, real data never arrives, so the fallback always fires.

**Root cause, traced precisely this design session:**
1. `sendRequest()` (`request-receivable.js` L470-486) computes real `patterns_used` (`buildPatternsUsed(isJson, guardrailsRan, delegationOccurred)` merged with the skill profile's own declared `intent_technical_services`) and returns it as a **sibling** field alongside `content: parsedResponse`.
2. `execute.js`'s `runLoop()` ordinary-terminal branch (L486, `finalResult = { ...result, ... }`) preserves it — `patterns_used` genuinely reaches the HTTP response.
3. `callCapability()` (`MarketIntelligenceScreen.jsx` L586, `return result.content || {}`) **discards it** — only `content` survives. Every event built from a `callCapability()` return (`intent_routing`, `qa_answer`, `proofreader`, `hypothesis_generation`, `hypothesis_test`, `patch_proposed`, `patch_resolved`, `memory_consolidation`, `failure_triage`) therefore never carries real `patterns_used`, and `RoutingEventRow` always falls through to the static `SERVICE_LABEL` string for these — confirmed live against `skill_profiles`: `ci-routing-intent`/`qg-review-intent` really only use `structured-output`, not the 3-4 patterns the screen currently shows.
4. Only `agent_selection`/`display_format` (built from a separate, delegation-specific return path, `buildFinalDelegationResult`) carry real data today — this is why those two rows already show accurate patterns.
5. `case-based-reasoning` and `llm-as-judge` are declared `active: true` in `PATTERN_CATALOG` (real, shippable patterns platform-wide) but **no server-side `patterns_used` producer ever emits either slug for any intent this screen calls** (`buildPatternsUsed`, `execute.js`'s `logAgentTurn`, `ai-enrichment.js` all checked) — so on this screen, both can currently only ever appear via the static fallback, never as verified data.

**Locked decision (John, this design session — "I want real data"):** once real `patterns_used` flows through, remove the static fallback pattern strings entirely rather than leaving them as unreachable-but-present dead weight — a future change could otherwise silently reintroduce the same false-data bug. `SERVICE_LABEL[capability].name` (the capability display name, e.g. "Channel Intelligence") is unaffected and stays — only the `.patterns` sub-field is decorative/fabricated and goes.

**Bundled data correction (John, this design session — "bundle"):** `qg-review-intent`'s `technical_services` in Supabase is itself under-tagged, independent of the code bug above. Owen's `qg-review-intent` call is conceptually **both** `llm-as-judge` (`PATTERN_CATALOG`: "a second model evaluates the quality, accuracy, or compliance of a first model's output" — exactly what reviewing Marcus's answer is) and `guardrails` (`PATTERN_CATALOG`: "post-generation safety and quality enforcement — checking model output against declared rules... before returning to caller" — exactly what the guardrail pass/block check is), but its `technical_services` today is only `["structured-output"]`. Corrected to `["structured-output", "llm-as-judge", "guardrails"]` so real data is complete, not just honest. No other intent's `technical_services` needs correction — `ci-routing-intent`, `ci-answer-intent`, `ci-answer-display-intent`, `hyp-generation-intent`, `hyp-hypothesis-test-intent`, `hyp-hypothesis-test-display-intent`, and `agent-selection-intent` were all checked live and are already accurately tagged for what they do. (Whether `hyp-generation-intent`'s *method text* should more explicitly instruct a fresh Data Room query is a separate, already-queued item — `MI-62` — not touched here; this session only corrects the `technical_services` tag data, not method prose.)

**Schema alignment confirmed:** `skill_profiles.technical_services` is a real `jsonb` column (`information_schema.columns`, checked live). Traced end to end: `db-assembly.js` (L143/L564) reads `sp.technical_services` directly into `intent_technical_services`, unchanged through `ai-enrichment.js` (L118/L325) into `sendRequest()`'s `patternsUsed` computation (`request-receivable.js` L435-438). The Task 2 Supabase edit below requires **zero code changes** to take effect — confirmed, purely additive.

**Layer check:** this is un-discarding already-computed, already-returned server data at the client boundary — no new business logic moves layers. `patterns_used` is computed in Layer 3 (`api/`) exactly as today; Layer 2 (`MarketIntelligenceScreen.jsx`) just stops throwing away a field it already received.

**Duplicate-functionality check:** `callCapability()` is the single, already-shared point every affected event type routes through — no parallel implementation exists or is being created.

### Task 1 — `src/screens/MarketIntelligenceScreen.jsx`: preserve real `patterns_used`, remove the dead fallback

**1a. `callCapability()` (~L571-587)** — merge `patterns_used` onto the returned object instead of discarding every field but `content`:

```jsx
async function callCapability({ capability_slug, intent_slug, agent_id, task_context, runtime_context = null, format_skill_profile_slug = null, display_agent_id = null, onProgress = null }) {
  const res = await fetch("/api/capabilities/execute", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      capability_slug, intent_slug, agent_id, task_context, runtime_context,
      format_skill_profile_slug, display_agent_id,
      tenant_id: TENANT_ID,
      stream: !!onProgress,
    }),
  });
  if (!res.ok) throw new Error(`${capability_slug} ${intent_slug} failed: ${res.status}`);
  const first = onProgress ? await readSSEResult(res, onProgress) : await res.json();
  const result = await resolveInProgress(first, onProgress);
  if (result.status) return result;
  // FEATURE: MI-67 — patterns_used was a real, already-computed sibling field on `result` that
  // this unwrap discarded; every event built from this return needs it for an accurate Agent
  // Routing log.
  return { ...(result.content || {}), patterns_used: result.patterns_used || [] };
}
```

**1c. `RoutingEventRow` (~L1324-1347)** — simplify to real data only, no string fallback:

```jsx
function RoutingEventRow({ evt, agentById }) {
  const { capability, summary, color } = describePipelineEvent(evt);
  const svc = SERVICE_LABEL[capability];
  // FEATURE: MI-67 — real patterns_used only; the static-string fallback this replaced could
  // show patterns (Case-Based Reasoning, LLM-as-Judge, RAG on non-RAG intents) that never
  // actually ran. An event with no real patterns_used now shows no pattern line at all, rather
  // than a fabricated one.
  const realPatterns = Array.isArray(evt.data?.patterns_used) ? evt.data.patterns_used : null;
  const patternLabel = realPatterns && realPatterns.length > 0
    ? realPatterns.map(slug => PATTERN_NAME[slug] || slug).join(', ')
    : null;
  const primary = agentById(evt.agentId);
  return (
    <div style={{borderLeft:`3px solid ${color}`,paddingLeft:10,display:"flex",flexDirection:"column",gap:4}}>
      <div style={{display:"flex",alignItems:"center",flexWrap:"wrap",gap:6}}>
        <span style={{fontFamily:mono,fontSize:9,color:T.muted}}>{evt.id + 1}</span>
        {primary && <AgentAvatar who={primary.id} size={20}/>}
        <span style={{fontFamily:body,fontSize:11.5,fontWeight:600,color:T.ink}}>{primary ? firstNameFor(evt.agentId, agentById) : evt.agentId}</span>
        <span style={{fontFamily:mono,fontSize:9,color:T.muted}}>{primary ? primary.role : ""}</span>
      </div>
      {(svc || patternLabel) && <div style={{fontFamily:mono,fontSize:9,color:T.muted}}>{svc?.name}{svc?.name && patternLabel ? ' · ' : ''}{patternLabel}</div>}
      <div style={{fontFamily:body,fontSize:11.5,color:T.ink}}>{summary}{evt.durationMs != null ? ` · ${formatDuration(evt.durationMs)}` : ""}</div>
    </div>
  );
}
```

Nothing else in either function changes. `PATTERN_NAME` (already built from `PATTERN_CATALOG`) is untouched — it already has correct entries for every real slug, including `llm-as-judge` and `guardrails`.

let pass = 0, fail = 0;
function assert(desc, cond) {
  if (cond) { console.log(`  ✓ ${desc}`); pass++; }

// T1: callCapability()'s merge — mirrors the fixed unwrap

}
assert("T1a: patterns_used survives the unwrap alongside content fields",

  JSON.stringify(unwrapCapabilityResult({ status: "pending_confirmation", confirmation_id: "x" }))
