## 3. The build — one function, and the gate is its signature

Migration `ses182e_apply_data_restore` ships `public.apply_data_restore(p_actor_cycle uuid,
p_item_id uuid)`.

**THE GATE IS A `WHERE` CLAUSE, NOT A SENTENCE IN THIS FILE.** The function resolves `p_item_id`
and refuses unless that card is **`kind = 'ship'` AND `decision = 'reverse'`**. At rollback time no
such row exists — the incident card is filed `gated_before_build` and undecided — so *"apply it
automatically during a rollback"* is unreachable **by construction** rather than by a rule the next
cycle has to remember. This file records eight times over (`record_skip`'s precedent) that a rule
each cycle must remember is a rule that gets silently forgotten; John's constraint is too expensive
to leave to memory, so it is spent on a predicate instead.

**WHY `kind = 'ship'` IS HALF THE GATE AND NOT DECORATION — the boundary a later editor will
collapse.** A Reverse means two opposite things on the two card kinds, and only one of them is this
function's business:

| Card kind | What John's Reverse means there | This function |
|---|---|---|
| `ship` | *"I reject this delivery"* — undo what that cycle wrote | **applies** (the range is that card's own `cycle_id`) |
| `gated_before_build` (the incident card) | *"the rollback was wrong — put the code BACK"* (slice 1) | **refuses** |

Widening the predicate to *"any reversed card"* would make an incident-card Reverse — which asks to
**re-apply** reverted code — replay the before-images of the **observing** cycle instead. That is
not a near-miss; it is the opposite operation on the wrong range's rows, written into production.

**The range is `runner_items.cycle_id` of the reversed ship card, never a passed-in parameter.** A
ship card's `cycle_id` *is* the cycle that made the writes, so the binding is exact and there is no
third argument for a caller to get wrong. It is also the same *"passed in, never fetched"* discipline
inverted for the right reason: the engine takes CI conclusions as arguments because it holds no
credential, whereas this function runs **inside** the database, where the authoritative link is a
column it can read.

**What it applies, and what it only counts.** It iterates `plan_data_restore(card.cycle_id)` and acts
on `classification = 'restorable'` alone — `action='delete'` deletes by primary key, `action='upsert'`
restores the stored prior row at its primary key. `unverifiable` and `refused` are **returned as
counts with their grounds and never written**, which is constraint 2 above.

**The freshness check is at APPLY time, for free, and that is why the plan is re-derived rather than
passed in.** `plan_data_restore` refuses a row whose `updated_at` has moved past the image; calling
it *inside* the apply means that test runs against the state at the moment of writing, not against a
plan computed minutes earlier on a card John has been reading since. A stale plan handed in as an
argument would be exactly the *"authored from memory"* the slice-2 design forbids for downs.

**Ledger tables are excluded by inheritance, not by a second list.** `plan_data_restore` already
classifies every `runner_*` table `refused` ("its undo is the Reverse ceremony, never a row replay"),
including a `LIKE 'runner\_%'` arm so a table added later is ledger by default. Restating that list
here would give one fact two homes — the `SES-116` / `SES-113` / `SES-86` phase 3 defect.

**Idempotence is structural (`runner_items.restore_applied_at`)** — the `apply_ladder_decision`
shape, and load-bearing for the same reason: under parallel cycles (B42) two peers can harvest one
tap, and a double-applied restore does not merely look wrong, it re-deletes a row a later write
legitimately re-created. A second call returns `already_applied = true` and writes nothing.

**§19v holds in both directions:** every write gets its own `runner_before_images` row first,
attributed to `p_actor_cycle`, so the restore is itself reversible.

## 6. QA plan — discriminating, and the negative control is the widened gate

Live arms against real Supabase inside a **deliberately failing DO block** (every write rolled
back), one variable each:

- (a) a `ship` + `reverse` card → applies the restorable rows, deletes what the range inserted;
- (b) the **negative control**: the SAME fixture on a `gated_before_build` + `reverse` card — the
  shipped predicate applies **nothing**, the retired *"any reversed card"* form applies the rows.
  This proves a **difference** from the forbidden build rather than a property both share;
- (c) an accepted ship card → refuses (the gate is `reverse`, not merely "decided");
- (d) `unverifiable` / `refused` rows are counted and **not** written;
- (e) a second call → `already_applied`, nothing written twice;
- (f) grants asserted **both** directions (`SES-101`): `anon`/`authenticated` denied, `service_role`
  permitted — a one-directional check passes on a function nobody can call at all.

Then: `npm run build`, the full regression suite, `verifier.js`, and a tree re-read asserting zero
fixture residue.
