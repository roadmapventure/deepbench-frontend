## 1. CONTEXT

`CHI-31` found (2026-07-18) that the MI screen's always-visible static question ("What data is in the library and how can i use it?", `CHI-30`) reliably fails: Marcus's aggregate catalog answer necessarily touches multiple `the_library` categories, several of which are tagged `data_type: synthesized` — Geo Briefings (3 rows) and Partner Scenarios (10 rows) — and Owen's `qg-review-intent` guardrail legitimately blocks on `synthesized_as_fact` when the answer's confidence tier doesn't cleanly resolve.

Live-verified against the real trace (`durable_hops` `6e3b4a65`/`03517cb4`, 2026-07-21): Marcus correctly delegated to Eleanor for the real catalog, wrote an accurate answer citing 6 real records, but tagged the answer `synthesized`; Owen escalated to Priya, who confirmed the real gap — there's no rule for how to tier a meta/inventory-level answer that describes objects of mixed data types.

Two other backlog items cover the same underlying topic and were explicitly flagged (`design-chi-ux-0719`, 2026-07-19) as needing reconciliation with `CHI-31`:
- `AA-143` — Owen legitimately blocks Marcus's answers because demo/seed content (Nordholm, Japan GEO, etc.) isn't "sourced" enough; explicitly deferred twice as a content/data change, not a code fix.
- `CHI-20` — tier vocabulary ("synthesized") leaks to the end user generically instead of being reserved for one deliberate demo moment showcasing the guardrail.

**John's direction (this session, 2026-07-21):** fix this with a data reclassification, not a tiering-rule rewrite — recategorize the bulk of the demo's `synthesized` content to a new, more accurate value, `source_simulation` (name is John's own — already a real, shipped UI label in `describeDataType()`/`MarketIntelligenceScreen.jsx` for baseline-synthesized rows, currently only a *derived* label, not an explicit `data_type` value). Deliberately hold out exactly one Partner Scenario row as plain `synthesized`, unchanged, and add one new question that reliably demonstrates Owen's guardrail catching a real problem — so the mechanism stays demonstrable, just not tripped by ordinary demo traffic.

**Why this isn't pure data work (found during this session's Architect Review):** Owen's `qg-review-intent` verification step checks that "the answer's confidence_tier accurately matches the record's data_type" literally. If Marcus tags an answer `sourced` because its only citations are `source_simulation`-tagged, Owen's current method text would read `sourced` vs. `source_simulation` as a mismatch and block anyway — recreating the exact bug. Both `ci-answer-intent` (Marcus) and `qg-review-intent` (Owen) need a small explicit rule addition, not just the data change.

**Unrelated, out of scope, not touched this session:** ~10 leftover engineering test-artifact rows found in `the_library`'s Compliance category during this session's investigation (`AGT-023`/`S-LIBRARIAN-04` test rows, never archived) — flag as a future cleanup item, not part of this fix.
