### Task 2 — `scripts/check-new-id-prefixes.js`

Retargeted from the three stubs to the snapshot — but **not** by re-pointing its line diff, which
would be wrong in a way that is easy to miss. The snapshot is ordered
`source_file.asc, row_ordinal.asc` and carries a leading sequential `| N |` column, so filing one
ticket **renumbers every row beneath it**; a `git diff` then presents hundreds of untouched legacy
rows as newly added, and the prefix allowlist would flag them all. The check instead compares
**ID sets** — the IDs present in the snapshot at the merge-base versus at HEAD — which is immune
to renumbering. The ID is column **2** in the snapshot (it was column 1 in the old files), so the
matcher is column-aware. A snapshot absent at the merge-base reports and skips rather than
flagging all 556.

## QA PLAN — discriminating, with an armed red control

The trap in testing a checker is that "it printed no findings" is the very bug being fixed, so a
green run proves nothing on its own. Each assertion is therefore paired with a **red control**:

1. **Would it still pass if the change did nothing?** The retargeted checks are run against the
   pre-change scripts; they must FAIL there (the old code cannot see the snapshot at all).
2. **Fixture-driven, both directions.** A synthetic stub carrying one ticket row must FLAG
   (proving the stub-integrity check fires), and the real stubs must stay silent.
3. **Counts are asserted against independently measured live values** — 5 done, 3 over-cap, 228
   blank Type, 458 unclassed — not against whatever the script happens to emit.
4. **The renumbering trap is tested explicitly:** a fixture that inserts one ticket and shifts
   every row number beneath must yield exactly **one** newly-filed ID, not hundreds.
5. `npm run build` green and `tests/regression/run-all.js` green.
