## 1. CONTEXT

**Confirmed live Rule #1 violation, found 2026-07-08/09 (overnight autonomous session) via a dedicated hardcoded-routing audit.** `MarketIntelligenceScreen.jsx`'s `runQaWithQualityGate()` (lines ~466-476): when Owen's `qg-review-intent` returns `guardrail.result === "block"` for a failure that isn't fixable by his own one-shot retry, the SCREEN itself hardcodes the next call — `capability_slug: "pipeline-triage", intent_slug: "intake-failure-intent", agent_id: "sam"` — instead of Owen deciding for himself whether/who to ask. This is exactly the anti-pattern `ARCHITECTURE.md` §19d exists to prevent: a screen inspecting a peer capability's structured output (`gate.guardrail.result`) and deciding what to call next on the agent's behalf. Confirmed not covered by the §19e Ownership Matrix (no row exists for `pipeline-triage`/Sam), not resolved via `resolveCapabilityHolder()`, and not model-reasoned in any way today.

**Root cause:** `docs/kickoffs/v6.0.3-S-ARCH-AGENT-LOOP-03-mi-capability-retrofit.md` (`AA-82`) retrofitted the sibling "retry to Marcus" leg of this same function (now genuinely agent-reasoned via Owen's own `delegate_to_agent` call, see the existing `qg-review-intent` method text on the retry path) — but that kickoff predates `MarketIntelligenceScreen.jsx`'s existence and never touched this "route to Sam on an unfixable block" leg. It was never revisited.

**Confirmed via direct Supabase query this session (`skill_profiles`, project `rallojeqnkgtxgsdsnqm`):** `qg-review-intent` already has `traits.can_request_help: true` — the primitive this fix needs already exists on Owen's own capability, unused for this specific case. `intake-failure-intent` (Sam's capability) also already has `can_request_help: true` and requires `recommend_escalate`/`suggested_research_request` — its own shape is untouched by this session.

**The fix (additive, matches AA-171's own recommendation):** extend `qg-review-intent`'s `method` so Owen calls `request_help` (routing through whoever holds `project-manager`, resolved live, per §19d) when a block isn't fixable by his own retry, describing the failure and asking for triage guidance. Once Michelle's `agent-selection-intent` responds with a real, reasoned recommendation, Owen calls `delegate_to_agent` — **non-final** (he still has his own required schema turn left to complete, exactly mirroring his existing, already-proven-safe retry-to-Marcus pattern, not the `delegation_required`/always-terminal shape used elsewhere). Owen then completes his own final answer, copying the delegate's real `recommend_escalate`/`suggested_research_request` verbatim into a new, optional `triage` field on his own schema. The screen then reads `gate.triage` instead of making a second, hardcoded call.

**Zero harness changes needed.** Read `api/capabilities/execute.js`'s `runLoop()` end to end this session (Architect Review, below) — the generic `request_help`/`delegate_to_agent` mechanism (`AA-87`, extended by `AA-142`/`AA-148`/`AA-152`) already supports exactly this shape (a non-`delegationRequired` capability requesting help mid-turn, then choosing for itself whether/who/`is_final` on the follow-up `delegate_to_agent` call) with no new code path. This is Supabase content + one screen file, not a harness change.

**Not in scope:** `AA-140` (a different, already-accepted risk — the screen's hardcoded *entry-point* `agent_id` for the very first call in a flow, which the §19e Ownership Matrix already documents as a legitimate exception) is a distinct finding and untouched by this session — do not conflate the two.
