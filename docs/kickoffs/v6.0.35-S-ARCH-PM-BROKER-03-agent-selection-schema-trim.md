## CONTEXT

Live-measured 2026-07-07 (John's own MI screen test, real Q&A question): Michelle's `agent-selection-intent` PM-broker call took 12.8s and 13.4s on the same interaction (two separate broker hops — one selecting Owen for review, one selecting Alex for display). Checked against this intent's full history in `ai_activity_log` (`project-manager:agent-selection-intent:depth0`, every row since this morning): latency has always ranged 6.6s–15.2s — **this is not a new regression from today's other fixes** (`AI-43`/`AA-124` don't touch this intent at all), it's a pre-existing, never-diagnosed high-variance cost that just happened to land on the slow end of its range during this test.

**Root cause, found by reading the Skill Profile directly:** `agent-selection-intent`'s own structured-output `schema` (in `skill_profiles.traits`) has **no `maxLength` on `reasoning` (top-level) or `fit_summary` (per candidate, up to 3-5 candidates)** — unlike every other intent already fixed this session (`ci-answer-display-intent`, `hyp-hypothesis-test-display-intent`), which have brevity caps either on the harness-generic tool schema (`AA-113`, `maxLength: 300`) or their own `method` text (`AA-120`). This intent's `method` is `null` and its `traits.analysis_instructions` only covers `intent_slug` correctness, not verbosity — there is nothing anywhere telling the model to keep `reasoning`/`fit_summary` short.

**Different mechanism from the other two fixes, same lever:** `ci-answer-display-intent`/`hyp-hypothesis-test-display-intent` had `canRequestHelp: true` with no schema tool, so `tool_choice: 'auto'` let the model ramble in free text before calling a harness tool — the fix there was cutting `max_tokens` + a brevity sentence. `agent-selection-intent` has a real schema tool and (per `request-receivable.js`'s `buildCallBody()`) is therefore forced (`tool_choice: { type: 'tool', name: ... }`) — the model can't ramble in free text, but with no length limit on `reasoning`/`fit_summary` it can still generate a long structured payload *inside* the forced tool call, which is real output-token generation time regardless of the tool_choice mode. The fix here is a `maxLength` constraint directly on those two schema properties — the same mechanical lever `AA-113` already proved works (Anthropic respects `maxLength` on tool-call string properties reasonably well in practice).

**This is a Supabase data change, not a code change** — no `api/` files touched, same category as `AA-124`.

## TASKS (1)

### Task 1 — Supabase: add `maxLength` to `agent-selection-intent`'s schema

Run directly via Supabase MCP (`execute_sql`):

```sql
UPDATE skill_profiles
SET traits = jsonb_set(
  jsonb_set(
    traits,
    '{schema,properties,reasoning,maxLength}',
    '300'::jsonb
  ),
  '{schema,properties,candidates,items,properties,fit_summary,maxLength}',
  '150'::jsonb
)
WHERE slug = 'agent-selection-intent';
```

`reasoning` gets the same `300` cap already proven on the harness-generic tools (`AA-113`). `fit_summary` gets `150` — it's one of up to 3-5 per call, so each one needs to be shorter than a single top-level reasoning field, not the same length. Nothing else in `traits` (`schema.required`, `analysis_instructions`, the rest of the candidate object shape) changes — verify with a direct re-query after the update that `schema.properties.candidates.items.required` and `analysis_instructions` are byte-identical to before.
