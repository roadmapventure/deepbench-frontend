## CONTEXT

`AA-113` was found live on 2026-07-04 (during `S-APPLE-04b`/`01d`'s own QA): a real `pending_confirmation` accept call 500'd once, then succeeded cleanly on an immediate manual retry with no duplicate write. Logged, scoped, never scheduled — until now.

**Re-surfaced 2026-07-07** while investigating a second live "Something went wrong reaching Marcus" report on the Market Intelligence screen. The first report (`AA-120`, already shipped) was a genuine latency/observability gap in the `ci-answer-display-intent` chain. This second report does not fit that same explanation: John confirmed it happens even when Owen's quality-gate retry path is never invoked, which rules out a chain-specific latency story. Checking the actual failed call's `ai_activity_log` trail directly: the `ci-answer-display-intent` invocation that failed had only ~21 seconds of logged activity before going silent — nowhere near the 60s `maxDuration` ceiling. And `MarketIntelligenceScreen.jsx`'s `callCapability()` (the only fetch site this screen uses) has no client-side `AbortController`/timeout of its own, so a client-side abort racing ahead of the server doesn't explain it either.

**Root cause: `callModel()` has zero retry on a transient non-2xx Anthropic HTTP error, and this is shared by every single turn on the platform** — Marcus's, Michelle's, Owen's, everyone's, at every depth of `execute.js`'s delegation loop:

```js
const llmRes = await fetch('https://api.anthropic.com/v1/messages', { ... });
if (!llmRes.ok) {
  const text = await llmRes.text();
  throw Object.assign(new Error(`Anthropic call failed: ${llmRes.status}`), { status: 502, detail: text });
}
```

If Anthropic returns any transient error (a 5xx, an overload/`529`, a rate limit/`429`) at *any* hop, the whole `execute.js` invocation throws immediately, its handler's `catch` returns an error response to the browser, and — critically — **nothing gets logged for that failed attempt**, because `AA-120`'s `logAgentTurn()` only fires *after* `callModel()` returns successfully. This is a better fit for the reported symptom than any latency explanation: a single bad API response with zero retry, no trace, at whichever hop happens to hit it — which explains why the failure isn't tied to any one capability pair (Owen retrying Marcus, or Marcus asking Michelle) and doesn't correlate with call duration.

**This is the same class of gap `callModel()` already handles for a different failure mode** — it already retries once, automatically, when the model's response fails to parse against the expected schema (the existing `parseErr` branch). It has simply never had the equivalent for a transient HTTP-level failure on the *initial* call. This session adds that missing half, mirroring the existing retry-once philosophy exactly — it does not touch the existing parse-failure retry logic at all.

**Non-transient errors are explicitly excluded from retry** — a `400` (malformed request), `401`/`403` (auth), or other non-transient `4xx` will never succeed on a bare retry; retrying those would just add latency for no benefit. Only `429`, `500`, `502`, `503`, `529` are treated as worth one retry attempt.

**Deliberately scoped narrowly:** this session touches only the *initial* Anthropic call inside `callModel()`. The existing parse-failure retry's own second `fetch()` call is left exactly as it is today — unchanged, no added transient-retry wrapping there. Widening this further is a larger, separate consideration if it's ever needed.

### Task 1 — `api/prompt/request-receivable.js`: retry once on a transient Anthropic HTTP error

Add a small helper near the top of the file, after the existing tool constants (~after line 52, before `buildCallBody()`):

```js
// FEATURE: AA-113 -- retry once on a transient non-2xx Anthropic HTTP error (429/500/502/503/529),
// with a short backoff, before giving up. Every callModel() caller across the whole platform
// (execute.js's delegation loop, sendRequest()'s own non-precomputed path) shares this helper --
// generic infrastructure, not capability-specific. Previously any transient API hiccup at any hop
// threw immediately with zero retry, killing the whole call with no trace (confirmed live 2026-07-04:
// a pending_confirmation accept 500'd once then succeeded cleanly on an immediate manual retry with
// no duplicate write). Non-transient errors (4xx other than 429) still fail fast, unchanged --
// retrying a malformed request or an auth failure would never help. Deliberately scoped to the
// initial call only -- the existing parse-failure retry's own second fetch() is untouched.
const TRANSIENT_ANTHROPIC_STATUS = new Set([429, 500, 502, 503, 529]);
const API_RETRY_BACKOFF_MS = 1000;

async function postToAnthropicWithRetry(body, headers) {
  for (let attempt = 0; ; attempt++) {
    const res = await fetch('https://api.anthropic.com/v1/messages', {
      method: 'POST', headers, body: JSON.stringify(body), signal: AbortSignal.timeout(55000),
    });
    if (res.ok) return { res, apiRetryCount: attempt };
    if (attempt > 0 || !TRANSIENT_ANTHROPIC_STATUS.has(res.status)) {
      const text = await res.text();
      throw Object.assign(new Error(`Anthropic call failed: ${res.status}`), { status: 502, detail: text });
    }
    await new Promise(resolve => setTimeout(resolve, API_RETRY_BACKOFF_MS));
  }
}
```

Then in `callModel()`, replace only the initial `fetch()` call and its `if (!llmRes.ok)` block:

```js
  let llmData = await llmRes.json();
  let usage = llmData.usage || { input_tokens: 0, output_tokens: 0 };
  let retryCount = 0;
  let turn;
```

(Everything from `try { turn = parseModelTurn(...) }` onward, including the existing parse-failure retry's own raw `fetch()` call, is unchanged — do not touch it.)

### Task 2 — `api/capabilities/execute.js`: surface `apiRetryCount` in the existing turn-latency log

Extend `logAgentTurn()` (added by `AA-120`) to accept and log whether this specific turn needed an API-level retry — makes the fix verifiable directly via `ai_activity_log`, without needing raw Vercel logs:

```js
async function logAgentTurn({ capability_slug, intent_slug, agent_id, tenant_id, model, depth, latency_ms, is_delegate_call, api_retry_count }) {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  if (!supabaseUrl || !supabaseKey) return;
  fetch(`${supabaseUrl}/rest/v1/ai_activity_log`, {
    method: 'POST',
    headers: getSupabaseHeaders(supabaseKey),
    body: JSON.stringify({
      tenant_id: tenant_id || 'global',
      agent_id: agent_id || null,
      ai_type: 'agent-turn',
      feature: `${capability_slug || 'unknown'}:${intent_slug || 'none'}:depth${depth}${api_retry_count ? `:apiRetry${api_retry_count}` : ''}`,
      model: model || null,
      latency_ms,
      patterns_used: is_delegate_call ? ['agent-delegation'] : [],
      created_at: new Date().toISOString(),
    }),
  }).catch(() => {});
}
```

Only the new `api_retry_count` parameter and its conditional suffix on `feature` change — every other field byte-identical to `AA-120`'s version.
