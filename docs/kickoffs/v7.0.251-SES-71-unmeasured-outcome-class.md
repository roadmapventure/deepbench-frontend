## The two decisions, and why they are what they are

**`case_pass` has THREE values and `null` is not `false`.** The expression that caused this bug is
`record.case_pass ? "PASS" : "FAIL"` — correct-looking, and it prints FAIL over `null` because
`null` is falsy. Every verdict site now tests `=== true` / `=== null` explicitly. `null` is also the
fail-closed direction: every reader written before this ship tests for truthiness, so an unmeasured
run can never be read as green by old code, and it is still distinguishable from a real FAIL, which
is the conflation the ticket names.

**`err.upstreamStatus`, never `err.status`.** `postJSON()` attaches both: `status` is *our* API's
HTTP status, `upstreamStatus` is the model provider's. A 400 from our own
`api/capabilities/execute` is a malformed request — a real defect that must still FAIL. A 400 from
upstream on a request our API already accepted is the usage-cap signature (`SES-66`'s class). Keying
this on `status` is the obvious simplification and it would reclassify genuine request-shape bugs as
"unmeasured", leaving the suite structurally unable to fail — this bug with the sign flipped. The
guard pins both directions.

**`ACCOUNT_DEATH_ABORT_N = 2`, and it was not chosen for feel.** The incident ran **15** consecutive
cases into a dead account, so any `N >= 1` would have caught it; the binding constraint is the other
direction. `N = 1` aborts a whole run on one unlucky case. The smallest value that cannot fire on a
single case is 2 — and a case is only account-dead when **both** its attempts died account-level, so
`N = 2` already means four consecutive account-level errors. The streak resets on any measured case.

**A mixed case stays a FAIL.** A case counts as account-dead only when *every* attempt was
account-level. That is deliberately the conservative direction: calling a real failure "unmeasured"
ships a regression, while the reverse costs one wasted investigation.
