YAML, because **a check that looks blocking and is not is worse than no check**:

| Job | Gates? | Why |

`npm ci` rather than `npm install`, deliberately: it installs exactly the lockfile and fails on
`package.json`↔`package-lock.json` drift, which is a check worth having on its own.

## `partial` — what SES-180 still owes, and why none of it is the runner's to do
1. **The skip-vs-fail distinction** (the ticket's own *"absorbs the SES-92 skip-vs-fail fix"*): a
   test must **declare** "I cannot run here" and the harness must count it as skipped — never as
   passed, never as failed. It has to be declared by the test, never inferred by the harness, or the
   harness will swallow real failures. That is a change to the shared contract every regression test
   uses; shipping it in the same unattended cycle that also introduces CI would mean changing what
   "green" means and what enforces it in one move, with no one watching.
2. **Repository secrets** (`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`) so the credentialed tests and the
   grants assertions run here. Only John can add those — a runner must never print a secret, let
   alone install one.
3. **Branch protection** — *"Red = no merge, regardless of author"* is a repository setting, not a
   file. This workflow makes the signal; only John can make it binding.

Until (1) and (2) land, a red `build` is authoritative and the other two are information. Said on
the ticket and in the file rather than implied by a green tick.
