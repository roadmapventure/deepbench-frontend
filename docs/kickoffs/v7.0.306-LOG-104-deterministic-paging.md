## 2. CONTEXT

`ai_activity_log` is read into the browser by paging: `PAGE_SIZE = 1000`, repeated `.range(from, from + 999)` until a short page. Both paged readers use a sort key that is **not unique**, so Postgres is free to order tied rows differently between two `.range()` calls. A tie group straddling a page boundary can therefore have a row served twice, or never served at all — silently, with no error and no visible symptom.

**Premise revalidated live this cycle, against the database and the source, not recalled:**

| Fact | Measured now | Ticket's figure (2026-07-28) |
|---|---|---|
| Rows in `ai_activity_log` | **34,812** (≈35 pages) | — |
| Rows sharing a `created_at` with another row | **320** | 74 |
| `id` column type | `integer` (unique, NOT NULL) | — |
| `created_at` column type | `timestamp with time zone` | — |

The premise is not merely alive — **the exposed population has grown 4.3× since the ticket was filed**, which is what the ticket predicted would happen ("boundaries drift constantly because the platform logs continuously").

**Both call sites confirmed on this branch:**

- `src/hooks/useAIActivity.js` **L1129–1131** — `hydrateFromSupabase()` orders by `created_at` descending only, then `.range()`. Non-unique sort key.
- `src/hooks/useAgents.js` **L179–183** — `useAgentActivitySummary()`'s `fetchAll()` has **no `.order()` at all**, then `.range()`. Wholly unspecified order across 17 pages; this is the worse of the two, exactly as the ticket's 2026-07-29 addendum records.

**Why this is worth a cycle:** a skipped row is simply absent from Total Calls, Total Cost, By LLM, By Agent and By Service alike, and from the whole CHI Agents drawer. There is no error, no warning, and no way to notice from the screen — the number is just quietly wrong. The ticket's own words: *"Worth doing before anyone treats these totals as exact."*

## 6. TASKS

**Task 1 — `src/hooks/useAIActivity.js`: add the unique tiebreak to `hydrateFromSupabase()`.**
Append `.order('id', { ascending: false })` after the existing `created_at` order. The `created_at` ordering is kept and kept first — the row set is consumed newest-first — so this only decides ties that previously had no defined answer. Direction matches `created_at` descending so the total order stays monotonically newest-first.

**Task 2 — `src/hooks/useAgents.js`: give `fetchAll()` a defined order.**
Add `.order('id', { ascending: false })` before `.range()`. This site had no ordering at all, so this establishes one rather than refining one. `buildActivitySummary()` aggregates and is order-independent, so no consumer behaviour changes — only which rows arrive.

## 7. QA — THE DISCRIMINATING TEST

The honest difficulty: the failure is Postgres choosing a different order between two `.range()` calls. It is **permitted**, not **guaranteed** — the ticket itself records that on the day it was QA'd "every agent's rows matched SQL exactly … but that is the planner happening to be stable, not a guarantee." So a live "page it twice and diff" test can pass while the bug is fully present. That test would be theatre, and it is deliberately not the one written here.

What is checkable, and what the guard asserts:

1. **`useAIActivity.js` pairs its `.range()` with a unique tiebreak** — comment-stripped source carries `.order('id'` in the same query chain.
2. **`useAgents.js` pairs its `.range()` with a unique tiebreak** — same, on the site that previously had no order at all.
3. **NEGATIVE CONTROL (pure, no credentials).** The same matcher is run against both **retired** forms — the `created_at`-only chain and the order-less chain, held verbatim in the test as fixtures — and must **fail** on both. This is what stops assertions 1–2 passing vacuously against a matcher that would accept anything: the guard proves a *difference* from the code that shipped before, not a property both share.
4. **CREDENTIALED (skips loudly without `SUPABASE_URL` / `SUPABASE_SERVICE_KEY`, per the `SES-135` policy on card `1abe473a`).** Measured against the live table: `created_at` is **non-unique** (there exist values with `count(*) > 1`), and `(created_at, id)` **is** unique across every row. Together these are the premise and the sufficiency of the fix — the sort key was ambiguous, and the new one cannot be.

**Would it still pass if the change did nothing?** No. Assertions 1 and 2 were verified to fail against this branch's pre-change source (`useAIActivity.js` L1130 and `useAgents.js` L183 as they stand at `origin/dev@f7f3cd0d`), and assertion 3 fails deliberately on those same retired forms.

**Proof type:** assertions 1–3 are a **source-scan + pure fixture proof**; assertion 4 is a **live database measurement** (not a full end-to-end render). Labeled as such rather than claimed as end-to-end.
