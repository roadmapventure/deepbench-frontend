## 2. CONTEXT

**John's report:** *"the pattern total amounts need to have a scroll as well, they sit at 0 until calculated."*

**Verified live on the deployed preview (sampled every 400 ms through a cold open):**

| Time after open | Calls | Cost |
|---|---|---|
| 0.5 s | skeletons | — |
| **1.5 – 3.5 s** | 2,666 | **`<$0.01`** ← false, stated as fact |
| 6.2 s | 2,666 | $10.50 |

So for roughly **five seconds** the pattern rows assert that Request Routing cost less than a penny, when it cost $10.50. This is precisely the false-zero class `LOG-98` removed from the header tiles, resurfacing in the rows.

**Why it appears now, and why only here.** `LOG-99` made classification fast (289 ms), so pattern rows render almost immediately — but `LOG-97` derives each pattern's **cost** by summing the hydrated in-memory log, and that hydrate still takes ~23 sequential paged requests (~5 s; that's `LOG-99`'s remaining half / `LOG-104`'s neighbour, out of scope here). Until the log lands, `costBySlug` is empty and each row falls back to the view's `cost_sum`, which is structurally `0` — rendered by `fmt$` as `<$0.01`. The existing skeleton gate is `patternsLoaded` only, which no longer covers the cost dependency.

**Note the two cells have different readiness, and the fix must respect that:** `Calls` is correct the moment the rows render (it comes from the same classification read); only `Cost` waits on the log. Treating them identically would either delay a correct number or expose a wrong one.
