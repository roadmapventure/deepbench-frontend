## 2. CONTEXT

Found live 2026-07-21 during `DAT-6`'s own investigation and confirmed independently twice more since (a real Anthropic `529` overload during `DAT-6`'s live verification, and a direct, controlled repro against the real deployed API this session). Traced end-to-end, not assumed:

`resolveAccept()` (`api/capabilities/execute.js`) calls `runCapability()` for a confirmed intent's `on_accept_intent_slug` follow-up (`AA-103`'s mechanism — e.g. Nadia's `data-patch-intent` → Eleanor's `library-write-intent`) and treats **any** return value as a completed accept — including `{status:'in_progress', job_id}`, the checkpoint placeholder Loop returns when a call risks the Vercel timeout (`ARCHITECTURE.md` §1's Loop entry, "a third outcome... Loop can also pause and checkpoint"). `markAcceptedDelegated()` then unconditionally flips the confirmation to `status:'accepted'`, even though nothing has actually finished yet. Confirmed live via direct Supabase query on 2 real stuck rows: `status:'accepted'`, `resolution:{job_id:'...', status:'in_progress'}` — a checkpoint pointer being stored as if it were a real result.

**The consequence:** if the resumed job (`action:'continue'`) later fails, there is no path back. The confirmation is already `accepted`; further Accept clicks just re-hit the same dead job via `continue`, and Edit/Reject both hard-refuse with 409 (`status !== 'pending'`). Generic to **every** `requires_human_confirmation` capability that declares `on_accept_intent_slug` and can checkpoint — not specific to `DAT-6`'s bug, which merely happened to be what surfaced it live.

**Fix, confirmed with John across this session's own walkthrough:**
1. A checkpoint is not a completed accept. Don't call `markAcceptedDelegated()` on it — record the `job_id` (reusing the existing `resolution` jsonb column, no schema change) and move the confirmation to a new transitional status, `accepting` — which still blocks concurrent Edit/Reject exactly like `accepted` does today (no new race introduced during the wait).
2. Whenever a linked job actually reaches a terminal state — success **or** exhausted failure (after `HAR-8`'s 3 attempts) — close the confirmation out for real: `accepted` on success, a new **`accept_failed`** status on failure (John's explicit call: a visible "this failed" state, not a silent revert to `pending` — see the "why `accept_failed`, not revert-to-pending" note below).
3. **Consistency completion, found during this session's own design, same bug shape at 2 more sites (Architect Review's multi-site check):** the exact same "silently leaves the confirmation at `pending` on failure, with zero durable record of what happened" gap also exists in `resolveAccept()`'s own *fast/synchronous* failure path (a `runCapability()` throw that never even reaches a checkpoint) and in `resolvePendingConfirmation()`'s plain accept path (used by any confirmed intent with no `on_accept_intent_slug`). Both get the identical `accept_failed` treatment on failure, for the same reason — `HAR-8`'s 3 attempts already happen *inside* a single synchronous call too, so a fast failure there is exactly as "exhausted" as one that failed after a checkpoint. Fixing all three call sites in this one session — same root cause, same fix shape, not three separate bugs (per the "multi-site bug pattern → shared-service check" Architect Review rule).
4. **Necessary completion, not optional:** `accept_failed` is only useful if the user can actually act on it. The existing `status !== 'pending'` eligibility guard (checked at 3 sites: `resolveAccept()`, `resolvePendingConfirmation()`, and the `edit` route branch) would otherwise hard-block Retry/Reject on an `accept_failed` card too — the exact same dead end as today's bug, just under a different label. Widened at all 3 sites to treat `accept_failed` as actionable, same as `pending`.

**Why `accept_failed`, not revert-to-`pending` (John's explicit call, this session's walkthrough):** revert-to-`pending` is invisible by default — the card would look exactly like it was never touched, with the only signal being a chat-error line that scrolls out of view. John wants a real "this failed, you decide" state the user can actually see on the card itself.

**Explicitly deferred, not in this session's scope:** the new `accept_failed` *visual* treatment (a distinct card state/copy) is real UI work needing its own mock and John's sign-off (per `WORKING-WITH-JOHN.md`'s "UI appearance decisions" approval gate) — **not decided here, and not blocking this backend fix.** This session ships the correct backend state machine only; the existing card UI will render an `accept_failed` confirmation using whatever branch it currently falls into by default (need to confirm live in QA which one that is — see Manual QA item 5) until a follow-up UI session gives it a proper look.

**Harness-vs-service check:** all four fixes live entirely inside the confirmation-resolution mechanism (`confirmation.js`/`execute.js`'s own dispatch) — none of them touch `runCapability()`/`runLoop()`/`checkpointAndReturn()`, the generic machinery every other capability call also shares. Confirmed no plumbing changes needed there: the `continue` route handler already receives `job_id` as its only input, and a reverse lookup (`resolution->>job_id`) is sufficient to find any linked confirmation — no new `durable_hops` column, no schema migration.

### Task 1 — `api/_lib/handlers/confirmation.js`: new helpers for the checkpoint-linked lifecycle

```js
// FEATURE: LOO-17 -- links a checkpointed accept to its job_id without marking it resolved yet
// (deliberately does NOT set resolved_at -- 'accepting' isn't a resolution, it's still in flight).
// Reuses the existing resolution jsonb column -- no schema change.
export async function linkCheckpointJob(confirmation_id, job_id) {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  const headers = getSupabaseHeaders(supabaseKey);
  await fetch(`${supabaseUrl}/rest/v1/pending_confirmations?id=eq.${encodeURIComponent(confirmation_id)}`, {
    method: 'PATCH', headers,
    body: JSON.stringify({ status: 'accepting', resolution: { job_id, status: 'in_progress' } }),
  });
}

// FEATURE: LOO-17 -- reverse lookup so the `continue` route handler can find which confirmation
// (if any) a durable_hops job_id belongs to, once that job reaches a genuine terminal state.
export async function getConfirmationByCheckpointJobId(job_id) {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  const headers = getSupabaseHeaders(supabaseKey);
  const res = await fetch(`${supabaseUrl}/rest/v1/pending_confirmations?resolution->>job_id=eq.${encodeURIComponent(job_id)}&status=eq.accepting&select=id&limit=1`, { headers });
  if (!res.ok) return null;
  const [row] = await res.json();
  return row?.id || null;
}

// FEATURE: LOO-17 -- the visible "this failed, you decide" terminal state (John's explicit call,
// not a silent revert to pending). Used by every exhausted-failure path: a checkpoint's resumed
// job failing, a fast/synchronous accept failure, and resolvePendingConfirmation()'s own plain
// accept path -- same root cause, same fix, at all three sites (Architect Review multi-site check).
export async function markAcceptFailed(confirmation_id, error) {
  await updateStatus(confirmation_id, { status: 'accept_failed', resolution: { error: String(error?.message || error) } });
}
```

Add these three exports; nothing existing in this file changes except the two guard widenings in Task 2/3 below (`resolvePendingConfirmation()`'s own 409 check and accept-path try/catch).

### Task 2 — `api/_lib/handlers/confirmation.js`: widen the eligibility guard + add the accept-failure try/catch to `resolvePendingConfirmation()`

```js
export async function resolvePendingConfirmation({ confirmation_id, resolution }) {
  if (!['accept', 'reject'].includes(resolution)) {
    throw Object.assign(new Error(`resolution must be accept or reject, got "${resolution}"`), { status: 400 });
  }

  const row = await getPendingConfirmation(confirmation_id);
  if (!row) throw Object.assign(new Error('confirmation not found'), { status: 404 });
  // FEATURE: LOO-17 -- accept_failed is a "you decide what's next" state, not a dead end -- widened
  // from `row.status !== 'pending'` so Reject/retry-Accept both still work on it.
  if (!['pending', 'accept_failed'].includes(row.status)) {
    throw Object.assign(new Error(`confirmation already ${row.status}`), { status: 409 });
  }

  if (resolution === 'reject') {
    await updateStatus(confirmation_id, { status: 'rejected' });
    return { status: 'rejected', confirmation_id };
  }

  // accept — let the paused step finish exactly as it would have without the gate
  let result;
  try {
    result = await sendRequest({
      prompt_request: row.prompt_request,
      agent_id: row.agent_id,
      capability_slug: row.capability_slug,
      tenant_id: row.tenant_id,
      precomputed_turn: { tool_input: row.proposed_action, usage: { input_tokens: 0, output_tokens: 0 }, retryCount: 0 },
      delegation_occurred: row.delegation_occurred,
    });
  } catch (e) {
    // FEATURE: LOO-17 -- same consistency fix as resolveAccept()'s try/catch (Task 3): this path
    // (no on_accept_intent_slug) can never checkpoint (sendRequest() has no loop), so any failure
    // here is already a fast, fully-exhausted one (HAR-8's 3 attempts happened inside this one call).
    await markAcceptFailed(confirmation_id, e);
    throw e;
  }
  await updateStatus(confirmation_id, { status: 'accepted', resolution: result });
  return result;
}
```

Only the guard line and the new try/catch around the existing `sendRequest()` call change. The reject branch and everything else is byte-identical.

### Task 3 — `api/capabilities/execute.js`: `resolveAccept()` — don't mark accepted on a checkpoint, and catch fast failures

```js
export async function resolveAccept({ confirmation_id, _onEvent = null }) {
  const row = await getPendingConfirmation(confirmation_id);
  if (!row) throw Object.assign(new Error('confirmation not found'), { status: 404 });
  // FEATURE: LOO-17 -- same guard widening as resolvePendingConfirmation() (Task 2).
  if (!['pending', 'accept_failed'].includes(row.status)) {
    throw Object.assign(new Error(`confirmation already ${row.status}`), { status: 409 });
  }

  const onAcceptIntentSlug = await getOnAcceptIntentSlug(row.intent_slug);
  if (!onAcceptIntentSlug) {
    return resolvePendingConfirmation({ confirmation_id, resolution: 'accept' });
  }

  let result;
  try {
    result = await runCapability({
      capability_slug: row.capability_slug,
      intent_slug: onAcceptIntentSlug,
      agent_id: row.agent_id,
      task_context: row.proposed_action,
      tenant_id: row.tenant_id,
      _onEvent,
    });
  } catch (e) {
    // FEATURE: LOO-17 -- a fast/synchronous failure is exactly as exhausted as one that failed
    // after a checkpoint (HAR-8's 3 attempts already happened inside this call before this throw
    // surfaced) -- mark it accept_failed consistently, not silently pending.
    await markAcceptFailed(confirmation_id, e);
    throw e;
  }

  // FEATURE: LOO-17 -- a checkpoint is not a completed result. Link the job so the `continue`
  // branch (Task 4) can close this out for real once it actually finishes.
  if (result.status === 'in_progress') {
    await linkCheckpointJob(confirmation_id, result.job_id);
    return result;
  }
  await markAcceptedDelegated(confirmation_id, result);
  return result;
}
```

Add `linkCheckpointJob`/`markAcceptFailed` to this file's existing import from `confirmation.js` (already imports `insertPendingConfirmation, getPendingConfirmation, markEdited, resolvePendingConfirmation, getOnAcceptIntentSlug, markAcceptedDelegated` — extend that line).

## 6. DESIGN RULES

- `accepting` never gets `resolved_at` (it isn't resolved) — `linkCheckpointJob()` is a raw PATCH, deliberately not reusing `updateStatus()`. `accept_failed` **does** get `resolved_at` via `updateStatus()`/`markAcceptFailed()` — it's a genuine terminal outcome (failed, not pending), same as `accepted`/`rejected`.
- `accept_failed`'s `resolution` shape is `{ error: string }` — deliberately different shape from a genuine result's `resolution` (`markAcceptedDelegated`'s payload). No consumer reads `resolution.error` today; this is new, additive.
- Reuse the exact same `accept_failed` treatment at all three failure sites (checkpoint-then-fail, fast-synchronous-fail, `resolvePendingConfirmation`'s own fail) — one fix, one shape, not three bespoke ones.

// inline copy of resolveAccept()'s post-fix decision logic
function decideAcceptOutcome(runCapabilityOutcome) {

function decideContinueOutcome(resumeOutcome) {
  if (resumeOutcome.threw) return { action: 'markAcceptFailed' };
