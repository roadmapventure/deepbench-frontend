## 2. CONTEXT

`CHI-82` (v6.3.162) introduced journey step numbering (§19n): each drawer title wears a `StepChip`,
and the handoff chat bubble that announces a step echoes the same chip via `msg.stepRef`. The chip
is **visual only** — `StepChip` (`src/screens/MarketIntelligenceScreen.jsx:558`) renders a `<span>`
with no handler. `CHI-84` was deliberately deferred out of `CHI-82` v1 as the interaction layer on
top: tapping the chip should open that step's drawer in Column 2 and scroll it into view; on mobile
the Steps & Evidence tab must be selected first.

**Premise re-verified live this cycle (not taken from the ticket):** `StepChip` is still handler-less
at :558; the chip render at :1934 passes only `n` and `label`; the three `stepRef` build sites
(:4112, :4410, :4561) still construct `{n, label}` with no drawer key; `Drawer`
(`src/components/SharedUI.jsx:395`) still renders `data-drawer-key={scrollKey}` at :432 on its
always-rendered outer div. Premise holds.

**Three corrections to the ticket's own wording, each measured against the source:**

1. **"`useDrawerStack` already exposes toggle + `scrollKey` targeting — wire, don't rebuild" is half
   wrong.** `useDrawerStack` (:2189) returns only `{ isOpen, toggle }` (:2234). The scroll-into-view
   math exists but is **trapped inside the private `autoCurrent` effect** (:2193–2207) and is not
   callable from outside. The hook must grow one seam. This is the missing export, not a rebuild —
   the design reuses `data-drawer-key`, the `manualOverride` channel and the identical `scrollTo`
   arithmetic rather than inventing a second mechanism.
2. **The ticket assumes the chip knows its drawer. It does not.** `stepRef` carries `{n, label}`
   only. Threading the drawer key is a required part of this ticket, not incidental.
3. **"Mobile must switch to the Steps & Evidence tab first" is under-specified in a way that decides
   the architecture.** `mobileTab` is `MobileBody`-local state (:3493) and **`EvidenceColumn` is
   fully unmounted while `mobileTab === "chat"`** (ternary :3627–3655). So on mobile there is no
   drawer stack in the tree at the moment the chip is tapped — a direct function call cannot work,
   and the reveal must be a *persisted request* consumed after mount.

**Accepted non-goal, documented rather than silently ignored:** messages persist across journeys
while `nextJourney` (:528) renumbers steps. A chip minted in journey 1 and tapped after journey 2
begins reveals the drawer its **key** names, which now holds journey 2's content — the chip's frozen
`n` may not match. That mismatch is inherited from `CHI-82`'s visuals and is not introduced here; no
mitigation in v1.

## 4. STUB DEFINITIONS

New module `src/lib/stepReveal.js` — two pure functions, no imports, no I/O:

- `nextRevealRequest(prev, key)` → `{ key, token: (prev?.token ?? 0) + 1 }`.
  **The token increments even when `key` is unchanged** — that is the whole point: React state
  equality would otherwise swallow a second tap on the same chip.
- `resolveStepChipKey(stepRef)` → the key string, or `null` unless `stepRef?.key` is a non-empty
  string. This is the gate `MessageBubble` uses to decide tappable-vs-plain.

No stubbed data, no placeholder content, no invented rows.

## 6. DESIGN RULES

- **Reuse, do not reimplement.** The reveal effect opens through the **same `manualOverride`
  channel** a drawer-header click already uses, and scrolls with the **same**
  `container.scrollTo({top: container.scrollTop + (eRect.top - cRect.top), behavior:"smooth"})`
  arithmetic and the **same** `[data-drawer-key="…"]` lookup as the auto-open effect. No second
  scrolling mechanism enters this file.
- **It cannot fight the existing machinery, by construction.** The auto-open effect's deps are
  `[autoCurrent, ...transitionDeps]`; a reveal changes neither, so it never re-fires against the
  reveal. `isOpen` (:2228) consults `manualOverride` *before* `effectiveAutoCurrent`, so a reveal
  also wins during the `CHI-51` post-resolution suppression — correct, because the user explicitly
  asked for that drawer. The next genuine transition clears the override (:2194), so a reveal
  inherits `toggle`'s lifecycle exactly and adds no new cleanup path.
- **Design tokens only** (`.claude/rules/`): the chip's visual is unchanged and keeps taking its
  colours and fonts from `T` / `mono`. The button wrapper sets no colour of its own.
- **Exposure rule (§19v):** this changes what an approved surface looks like, so it ships behind a
  **default-off** flag — `chi-84-step-chip-tap`, a **data row** in `public.feature_flags` per
  `HAR-41`, never a code constant. Flag OFF must be byte-identical to today: `onTap` is never
  passed, `StepChip` takes its no-`onTap` branch, and no `<button>`, cursor change, aria attribute
  or handler appears in the DOM.
- **Fail closed.** `useFeatureFlag` starts false, so a failed flag fetch renders today's inert chip.
- **Silent no-op over a wrong guess.** A chip whose key names a drawer not currently rendered must
  do nothing — no throw, and specifically **no scroll-to-top "fallback"**, which would move the
  user's view for a step that no longer exists.

## 8. NODE.JS TEST

`tests/regression/CHI-84-step-chip-reveal.js`, default-export + `selfRun`, auto-discovered by
`run-all.js`. It runs under plain Node with no DOM and no JSX transform.

1. **Re-fire lock — the discriminating assertion.**
   `const a = nextRevealRequest(null, "qa"); const b = nextRevealRequest(a, "qa");`
   assert `b.token > a.token` **with the key unchanged**. This fails against the plausible wrong
   implementation (keying the token off a key change, or holding a bare string in state), which is
   exactly the bug class that would make a second tap on the same chip do nothing.
2. **Defensive gate.** `resolveStepChipKey({n:2,label:"Theories"})` → `null`;
   `resolveStepChipKey(undefined)` → `null`; `resolveStepChipKey({key:"hyp-result"})` →
   `"hyp-result"`.
3. **Source-scan anti-drift locks** (the `SES-57`/`LOG-109` house pattern — `readFileSync` the
   `.jsx` and assert): the screen imports from `../lib/stepReveal.js` and defines no local copy of
   either function; all three `stepRef` build sites go through `stepRefFor(`; the chip is gated on
   `useFeatureFlag("chi-84-step-chip-tap")`; `useDrawerStack`'s signature carries `revealRequest`.

**What this proves, and what it does not.** It proves the re-fire token contract, the defensive key
gate, and that the wiring exists in source under the right flag slug. It does **not** prove that a
tap scrolls the real container, opens the real drawer, or flips the real tab — no test in this
harness can, because the harness has no DOM. That residue is §11, which this session runs itself.
