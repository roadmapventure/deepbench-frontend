## 2. CONTEXT

### The user-facing symptom

John asks Marcus Webb — GEO CSO Expert a broad Data-Room-spanning question in Channel Intelligence. The chain reaches Eleanor Voss — The Librarian for the catalog. She starts the multi-category breakdown her own `method` instructs, runs out of token budget mid-sentence, and the required top-level `citations` array — last field in her schema — never gets written. The harness reports a schema violation, retries once, fails identically, and John sees the generic "Something went wrong reaching Marcus."

### Root cause — two distinct failure modes collapsed into one error

Verified live this session by querying `durable_hops` for every `Schema tool … missing required field(s)` failure, grouping by the Skill Profile named *inside the error text* (not the row's own `intent_slug` — nested delegations file under the delegator's hop):

| Failing Skill Profile | Failures | `max_tokens` | Captured output shape |
|---|---|---|---|
| `library-catalog-intent` — Eleanor Voss, The Librarian | 28 | 1500 | Cut off mid-word, `citations` never started |
| `qg-review-intent` — Owen Marsh, The Proofreader | 5 | 1500 | **Complete, well-formed JSON**, 337–1134 chars, full `eval` object — simply omits `final_answer` |
| `agent-selection-intent` — Michelle Manning, Project Manager | 2 | 2200 | Cut off mid-word (`…(2) confirmation`), `reasoning` never started |

Two of these are **truncation**. One (Owen Marsh — The Proofreader) is a **genuine schema omission** with room to spare. All three throw byte-identical errors today.

This matters because of what happens next. `AA-182`'s corrective retry message (line ~252) says: *"Return the structured output again, exactly as specified, making sure to include every field named above."* For Owen Marsh — The Proofreader that is exactly right. For Eleanor Voss — The Librarian it is the **worst possible instruction** — she ran out of room, and the harness responds by asking her to write it all again *plus* the missing part, into the identical `max_tokens` ceiling, with a now-longer prompt. Structurally doomed: 0 recoveries in 30 attempts.

**So this session finishes `AA-182`**, which made the retry corrective for schema-shape failures and never handled the truncation case. It is not a new mechanism.

### Why the harness can't tell them apart

`grep -rn "stop_reason"` across `api/` and `src/` returns **zero hits**. The Anthropic Messages API returns `stop_reason: "max_tokens"` on every truncated turn; the platform has never read it. `parseModelTurn()` already receives the full response object — the field is sitting there unused, one property access away.

**Honest limitation this fix exists to remove:** the classification table above is inferred from the *shape* of captured output. No occurrence of this bug can currently be classified with certainty, because the distinguishing signal is discarded.

### Why `max_tokens` alone is not the fix

`library-catalog-intent` at 1500 is the lowest ceiling among the profiles sharing this citations-array schema pattern (`ci-answer-intent` 3000, `data-escalate-intent` 2000, `qa-answer-format` 4000) while carrying the heaviest output demand — a full-catalog enumeration. Bumping it clears today's 28. It does nothing for the 10 *other* profiles sitting at 1500, and leaves the next occurrence just as unclassifiable. Both halves ship together.

### Layer placement

`SCREEN-INVENTORY.md:65` scopes `HAR` to `execute.js`/`request-receivable.js` — "calling the model, checking gates." `ARCHITECTURE.md` §1 defines Harness's **Execution** sub-part as *"calling the model … sends the call … and parses the response."* This change is inside that parse step, and follows the exact precedent already documented there: `postToAnthropicWithRetry()`'s rule that a 429/500/529 is worth retrying and a 400 is not. Same shape — classify the response, then decide whether a retry can possibly succeed. Not `SCA` (scoped to `db-assembly.js`/`ai-enrichment.js`, untouched here).

## 5. TASKS

### Task 1 — `parseModelTurn()`: detect truncation from `stop_reason`

`api/prompt/request-receivable.js`, function starting ~line 128.

Add a single read at the top of the function, then thread it through both existing throw sites. **No slug/agent conditionals** — a generic field read on every response, per `.claude/rules/capabilities-are-data.md`.

```js
// FEATURE: HAR-9 -- Anthropic returns stop_reason:'max_tokens' on every truncated turn; this file
// had never read it (zero references to stop_reason existed anywhere in api/ or src/). Without it a
// response cut off mid-generation and a response the model simply authored wrong throw byte-identical
// errors -- confirmed live against durable_hops: 28 library-catalog-intent failures were truncation
// (cut off mid-word, citations never started) while 5 qg-review-intent failures were complete,
// well-formed 337-1134 char JSON that just omitted final_answer. Completes AA-182, which made the
// retry corrective for schema-shape failures but never handled the truncation case.
export function parseModelTurn(responseData, hasSchemaTool, schemaTool) {
  const wasTruncated = responseData.stop_reason === 'max_tokens';
  const toolUseBlock = responseData.content?.find(b => b.type === 'tool_use');
```

Missing-required-field throw (~line 135) — keep `rawInput` exactly as-is, add the flag and the distinguishing message:

```js
      if (missing.length > 0) {
        throw Object.assign(
          new Error(wasTruncated
            ? `Schema tool "${schemaTool.name}" output was truncated at the model's max_tokens limit before required field(s): ${missing.join(', ')}`
            : `Schema tool "${schemaTool.name}" called with missing required field(s): ${missing.join(', ')}`),
          { rawInput: toolUseBlock.input, truncated: wasTruncated }
        );
      }
```

No-`tool_use`-block throw (~line 149) — truncation can also cut off before any tool call starts:

```js
  if (hasSchemaTool) {
    throw Object.assign(
      new Error(wasTruncated
        ? "No tool_use block in response -- output was truncated at the model's max_tokens limit"
        : 'No tool_use block in response'),
      { truncated: wasTruncated }
    );
  }
```

The existing 422 throws in `callModel()` (~lines 305 and 308) pass `parseErr.message` straight into `detail`, so the new wording reaches `durable_hops.error` with no further change.

### Task 2 — `callModel()`: make the retry correction truncation-aware

Same file, ~line 252. Replace the single `correctionText` assignment with a branch. Owen Marsh — The Proofreader's path (the `else`) stays byte-identical to today's `AA-182` text.

```js
      // FEATURE: HAR-9 -- AA-182's correction text tells the model to return everything again "making
      // sure to include every field," which is correct for a genuine omission and actively harmful for
      // a truncation: the response was cut off for length, so asking for the same content plus more,
      // into the same max_tokens ceiling with a now-longer prompt, cannot succeed. Confirmed live:
      // 0 recoveries across 30 real truncation retries. Same shape as postToAnthropicWithRetry()'s
      // existing rule that a 400 is not worth retrying -- classify first, then retry only what can work.
      const correctionText = parseErr.truncated
        ? `Your previous response was cut off because it exceeded the response length limit. Return the same structured output again, but substantially more concise -- shorten or summarize the longest fields so that the complete response, including every required field, fits within the limit.`
        : `Your response did not conform to the required schema: ${parseErr.message}. Return the structured output again, exactly as specified, making sure to include every field named above.`;
```
