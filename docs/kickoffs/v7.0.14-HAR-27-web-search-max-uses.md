## 2. CONTEXT

### The problem, in one sentence

Jordan Ellsworth — Web Search Expert's `ws-news-search-intent` turn enables Anthropic's
server-side `web_search` tool with no usage cap, so one news-search turn can run unbounded
searches whose full results all bill as input tokens — measured at 344 calls / 36.5M input
tokens / ~$36 = **19% of the entire 30-day Claude spend** (avg 106K input tokens per call), and
worsening: the three most recent live calls were 208K / 282K / 286K input tokens each
(`ai_activity_log` ids 28184, 28081, 27957, verified 2026-07-31).

### Why the backlog row's stated fix direction doesn't apply

`HAR-27`'s row said "shape the tool-result payload before it enters context." Verified this
session: the payload never passes through our code. The tool is Anthropic's **server-side**
`web_search_20250305` (`request-receivable.js` lines ~107 and ~318, built bare with no
`max_uses`); Anthropic injects results server-side and each additional search re-processes all
prior results, which is why cost compounds per search. The lever the API actually offers is
`max_uses` on the tool definition. Full measurement context: `docs/harvests/HAR-02.md`.

### The fix shape (and why no migration is needed)

A new opt-in Skill trait `web_search_max_uses` (positive integer), read in `db-assembly.js`
exactly where `traits.enable_web_search` is already read (`HAR-05` pattern), carried on the
assembled **`llm` config object** — which `durable_hops` already persists wholesale (`llm`
jsonb column; resume rebuilds `enriched.llm` from `row.llm`, `execute.js` ~line 1347). So the
cap survives checkpoint/resume with **no new column, no migration** — unlike `enable_web_search`
itself, which needed its own `HAR-17` column because it's threaded as a standalone scalar.

Skills without the trait are byte-identical to today (no `max_uses` key emitted). The only
Skill getting the trait is `ws-news-search-intent` (value `3`, matching its "exactly 3 stories"
objective) — a **data flip the parent design session runs at QA time, not a coding task**.

### Deliberately untouched (filed as their own rows)

- `api/fetch-article.js:102` and `lib/agent-run.js:218` build their own separate web-search tool
  arrays — different features, not the measured cost line → `HAR-28` (Speed).
- `ws-news-search-intent`'s existing `traits.max_results` / `traits.allowed_domains` are read by
  no code anywhere (verified by repo-wide grep) → `DAT-17` (Data).

## 5. TASKS (4)

### Task 1 — `api/prompt/db-assembly.js`: read the trait into the `llm` object

In `buildSections()`, where `traits.enable_web_search === true` is read (~line 205, the `HAR-05`
gate), also read `traits.web_search_max_uses`: accept it only if `Number.isInteger(v) && v > 0`,
and set it on the returned `llm` object as `llm.web_search_max_uses`. Invalid/absent → key
omitted entirely. Generic read — no capability/agent slug conditionals
(`.claude/rules/capabilities-are-data.md`).

### Task 2 — `api/prompt/request-receivable.js`: emit `max_uses` on the tool definition

- `buildCallBody()`: new optional param `webSearchMaxUses` (default `undefined`). The web-search
  tool entry becomes
  `{ type: 'web_search_20250305', name: 'web_search', ...(webSearchMaxUses ? { max_uses: webSearchMaxUses } : {}) }`.
- `callModel()`: same new optional param, passed through to its own tool construction (~line 318)
  and its `buildCallBody()` call (~line 322).
- `sendRequest()`: already destructures `llm` from `prompt_request` (~line 616) — pass
  `webSearchMaxUses: llm?.web_search_max_uses` at its `callModel()` call (~line 671).

Every existing caller that doesn't pass the param must produce a **byte-identical** request body.

resume-path change — the value rides `enriched.llm`, already persisted/rebuilt (`row.llm`).
