## 1. CONTEXT

**This session builds Elena Cho's (AG-20, The Reasoner, CI-06) real Capability — the last of the six Market Intelligence agents to get one — and makes one small correction to Sam's existing Commit Triage.** Elena's persona-only identity has existed since `S-APPLE-01a` (v5.3.0); nothing has called her since.

**Design resolved this session (long design conversation, full reasoning preserved here since it reverses two things `FEATURES.md`/`ARCHITECTURE.md` currently say):**

1. **Elena's write target was already corrected before this session** (`AA-104`, `S-ARCH-REASONING-LAYER-01-design`, 2026-07-03): she writes to `the_reasoning`, not `knowledge_entries`, and does **not** hand off to Susan Smith/TR-08 for embedding — that was the original `S-APPLE-01a`-era design, superseded. `docs/FEATURES-ARCHIVE.md`'s `AG-20` row still describes the old hand-off; it's a historical record of what shipped in that session (persona only) and is left alone, but `FEATURES.md`'s **live** `AG-24` row described the same stale hand-off and has been rewritten this session to match §5.10's corrected text.

2. **`AA-98` (the logged "third generic Agent Loop primitive") is not being built.** The original idea: Sam self-flags `flags_for_consolidation` on `intake-commit-intent`, and a new harness primitive in `execute.js` automatically dispatches to Elena when true. Walked through at length this design session and rejected for two reasons: (a) Sam predicting whether Elena's synthesis would find something is a strictly worse-informed judgment than Elena just attempting the synthesis and reporting the result — she's the one doing the actual work; (b) an instruction telling Sam exactly which input signals mean "true" vs "false" collapses into deterministic logic wearing an agent costume (the exact anti-pattern `AA-98` itself was created to eliminate, just relocated one level down into a Skill Profile instead of `execute.js`).
   **Resolution:** Elena is invoked directly and deterministically on every commit — same shape as the Proofreader already running on every Q&A answer, which nobody considers a fake decision because the Proofreader's own evaluation genuinely varies. The real judgment lives entirely in Elena's own output: `action: 'consolidate' | 'no_action'`, using the *already-built, already-live* `reasoning-write.js` no-op path (`action: 'no_action'` → `{skipped: true}`, zero writes) — the exact same mechanism Nadia's `data-patch-execute-intent` already proved live. Zero new harness code, zero new `ARCHITECTURE.md` lock section. `AA-98`'s `FEATURES.md` row is marked resolved-differently this session, not built as originally scoped.

3. **Sam's `intake-commit-intent` gets one small, tightly-scoped fix**, unrelated to Elena's invocation: live-queried this design session and confirmed his `method` (instructions) still literally say *"Always include 'reasoner' in route_to — every committed Forecast/Correct feeds Memory Consolidation."* — a hardcoded, deterministic entry that (confirmed via grep of `api/`/`lib/`) nothing has ever read. Since Elena is now invoked independently of Sam entirely, this dead entry is removed: `"reasoner"` drops out of `route_to`'s enum, and the corresponding sentence drops out of his instructions. His Data-Analyst leg (does this dispute a specific existing chunk — already real judgment, already wired to `request_help`/Michelle since `AA-82`) is untouched.

4. **Priya's `hyp-stress-test-intent` has no schema today** (live-queried: `traits: {can_request_help: true}`, `technical_services: []`, `schema: null` — confirmed deliberate per `S-APPLE-03a-2`'s own session description, "no schema", likely because her output goes through Alex's Format Skill rather than a rigid JSON contract). Elena's input therefore receives Priya's stress-test result as **free narrative text**, not the structured `{supports, complicates, override_warning}` object §5.10's schema block implies. Retrofitting Priya's schema is explicitly out of scope this session (see Section 6) — Elena's instructions are written to read and judge free text, consistent with how she already has to judge `correction_text`'s substance.

5. **New future item logged, not built now (`AA-109`, already in `FEATURES.md`):** cross-decision pattern mining (a *different* agent — likely Nadia — analyzing patterns across many accumulated `the_reasoning` records over time) is a distinct, aggregate/statistical kind of learning from Elena's single-instance generalization. It needs real usage volume to produce anything meaningful and isn't demoable in one session with a handful of corrections — logged as `S-future`.

**What Elena's call actually receives** (task_context, rendered via the existing generic TASK DETAILS fallback, `AI-44` — no new plumbing needed): `original_question`, `flagged_answer`, `committed_hypothesis`, `intent` (`forecast`|`correct`), `stress_test` (free text), `was_override` (boolean, if the director overrode a stress-test caution).

**Who reads her output, and when (already live, zero new code):** `AA-107` already wired `the_reasoning` as a generic `fetch_instruction` source in `ai-enrichment.js`, identical to `the_library`. The next time Marcus (`ci-answer-intent`) or Priya (`hyp-stress-test-intent`) answers a related question in the same Data Room, they automatically inherit whatever Elena wrote as context — no trigger, no session-state plumbing. This is the loop-closure demo moment (design doc §9, and finding #8's "repeat stress test finds stronger support" variant) — this session's Node test is what proves it actually works, since `the_reasoning` has never had real content in it before.
