## What ships

**A migration, a runbook step, and a guard.** `har34_ip_block_push_alert` adds
`ip_org_cache.block_notified_at` and `public.ip_block_alert_claim(uuid)`; step **4a-quater** of
`runner-cycle.md` makes it one call in the cycle, beside the deploy alarms it is a sibling of.

**The predicate is a timestamp comparison, and that is the half a rebuild drops.**

```
blocked_at IS NOT NULL AND (block_notified_at IS NULL OR block_notified_at < blocked_at)
```

An address blocked, alerted, cleared by John and then blocked **again** is a second event and the
one he most needs to hear about. The obvious `block_notified_at IS NULL` form alerts on it once,
ever, and is then silent for every later block on that row for the life of the row —
`heal-engine.js`'s deliberate *"files once, never again"* limitation arriving somewhere it would be
wrong. The guard replays the same four-event sequence through both forms and asserts the retired
one **loses** (1 alert against 2), a difference rather than a property both share.

**The function returns `masked_ip` and cannot return `caller_ip`.** This row is read out into a
push notification — off-platform. `LOG-124` (`v7.0.39`) is the live incident where a visitor's raw
IP became publicly readable (476 rows, proven with nothing but the anon key), and
`.claude/rules/supabase-column-grants.md` is written from it. `caller_ip_masked` is the generated
`STORED` column that already exists for this purpose; its expression was **read from `pg_get_expr`
at this ship rather than recalled** — v4 → `xxx.xx.` + the last two octets, v6 → `xxxx:` + the last
9 characters. Putting the rule in the function's result type rather than in prose is the
`record_skip` precedent this runbook records eight times over.

**The claim is `FOR UPDATE SKIP LOCKED`, not a guarded `UPDATE`.** This call claims a *set* of rows
rather than one, so N parallel cycles (register B42) lock disjoint subsets and John gets exactly one
push per block however many peers sweep. Locking **before** the before-images is what lets §19v's
*no before-image, no write* hold without a losing peer leaving stray ledger rows — `stall_watchdog()`
reaches the same property with a `40001` rollback because it claims exactly one row.

**Nothing was backfilled, stated rather than left to be found.** The one historical block was never
alerted, so the alarm's first real fire carries it — **dated**, and named in the push as inherited
backlog rather than as something that just happened. Stamping it *already notified* would have been
a value nobody observed: the `SES-104` defect exactly, where
`ses103_permission_stall_tripwire` backfilled a constant heartbeat onto 43 rows and no later reader
could tell it from a real one.

## Disclosed, rather than buried

The step-6 `revalidated_at` write on `HAR-34` **preceded** its `runner_before_images` row, which
§19v wants first. The image was written immediately after, but the prior `revalidated_at` is
**unrecoverable** — no earlier before-image exists for this ticket and `BACKLOG-SNAPSHOT.md` does
not carry the column — so that one image holds post-write values for `revalidated_at` and
`updated_at` and true prior state for every other column. A restore from it is a no-op on those two
rather than a wrong value, which is the fail-safe direction; re-arming `revalidated_at` only
restarts the 30-day revalidation quiet.
