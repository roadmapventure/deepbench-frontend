## The half that would have shipped wrong

**The naive title pattern is `title !~ '^P[0-9]+ - '`, and it is wrong.** `ADM-1`'s real title is:

> `P2 - Inventive → promoted to AUTOMATION QUEUE #1 (John, 2026-08-20): "Need to have the brief page available through deepbench admin screen via vercel link…"`

That is a genuine title that records a reclassification and happens to *begin* with a class
string. The prefix form rejects it; the migration would have failed outright, or — worse, under
`NOT VALID` — left `ADM-1` un-updatable while reporting success. The ticket had already said which
form was meant (*"with nothing after the class is the import defect, not a title"*), and the live
board agreed: **1 row starts with a class string, 0 rows are one.** The shipped predicate is
anchored to the class-string-**only** form:

```sql
title !~ '^P[0-9]+ - [A-Za-z][A-Za-z''’ ]*\.?$'
```

**Both constraints ship `VALID`, never `NOT VALID`** — the `SES-116` lesson, verbatim: a
`NOT VALID` CHECK is still enforced on `UPDATE`, so historical violating rows become un-updatable
and the next harvest touching one fails. Driving both violation counts to zero in the pre-flight
is what makes `VALID` the safe form. QA arm **H** proves it rather than reasoning about it.

## QA — eight arms, live on a fixture, inside a deliberately rolled-back transaction

Every arm ran against the real table and the real installed constraints; the block ends in a
`RAISE EXCEPTION` so the fixture cannot survive (verified after: 0 residue on both
`backlog_id = 'QA-SES117'` and `source_file = 'QA-SES117-FIXTURE'`).

| Arm | Assertion | Result |
|---|---|---|
| A | control — a legitimate now-tier row still INSERTs | PASS |
| B | `title = NULL` rejected | PASS |
| C | blank title rejected | PASS |
| D | class-string-only title (`'P9 - Bug Fixes.'`) rejected | PASS |
| **E** | **negative control** — a real ADM-1-shaped title ACCEPTED | PASS |
| F | blank `type` on a `now` row rejected | PASS |
| **G** | **negative control** — the same blank `type` on a `later` row ACCEPTED | PASS |
| **H** | the SES-116 hazard — a live pre-existing row (`ADM-1`) still UPDATEable | PASS |

**The first run FAILED, and the control is why it was caught.** Arm A errored on
`source_file` being `NOT NULL`, so the fixture never inserted, every subsequent `UPDATE … WHERE
id = NULL` touched zero rows, and arms B/C/D/F reported "accepted = FAIL" — the *opposite* of a
false pass, but for the same reason a false pass happens: nothing was being tested. Re-run with a
complete fixture. Arms E and G additionally assert `FOUND`, so an "accepted" verdict cannot be
produced by a statement that matched nothing.

*Would these still pass if the change did nothing?* No. With the constraints absent, B/C/D/F all
flip to FAIL. E, G and H are the arms that fail if the constraint is too **broad** rather than
absent — which is the mistake this ticket was actually at risk of.

**Concurrent live evidence:** a peer filed `SES-141` at `03:46:46Z`, after the constraints landed.
It carries `type = 'Tooling'` and a real title and inserted cleanly — the constraint does not
break concurrent ticket filing.
