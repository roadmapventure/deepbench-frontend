## 3. DECISIONS TAKEN IN THIS SESSION (and why, so no later cycle re-derives them differently)

**(a) A table of FKs, not a text array.** The ticket allowed *"a `drain_scope` table or array
column"*. It is a table keyed on `backlog_items.id`, for a measured reason this repo has already
paid for: **`backlog_id` is not unique** — `CHI-48` occupies two rows (`SES-97`), which is why
`recompute_backlog_queue()`'s sixth `ORDER BY` clause is the primary key. A `text[]` of ids would
silently pull in both rows of any such pair. It is also `SES-111`'s own property 1 applied
consistently: *"the epic is an FK, never prose"* — so is a drain's scope. `backlog_id` is stored
**alongside** the FK as a naming-time snapshot for provenance and is never joined on.

**(b) The tier predicate is DROPPED, not kept alongside the list.** The named list *is* the scope.
Keeping `tier = 'now'` in the pick would leave a second moving predicate in place: re-tier a named
ticket to `next` and it silently leaves a drain John declared over it. One fact, one home.

**(c) A drain with no named list returns a new outcome, `unscoped` — it does not fall back to the
old behaviour.** Falling back is the bug wearing a default's clothes. `unscoped` behaves like
`blocked` for the cycle (fall through to the class-sorted board and build normally, so a drain
never ends a cycle build-less, register B24), but it is a **distinct word** because reusing
`blocked` would give one outcome two meanings — the exact drift this platform keeps paying for.
Drain creation stays John-only (`SES-111` property 5), so the only way to reach `unscoped` is a
future drain declared without a list; it fails closed and says so.

**(d) The retirement predicate keeps ignoring claims; the pick keeps honouring them.** `SES-111`
property 4 — the parallel-cycles trap — is unchanged and deliberately preserved: conflating the two
lets two peers holding the last two claims between them each cancel John's standing order.
