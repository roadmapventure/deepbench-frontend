## 1. The ticket's premise is wrong, and that is the headline finding

The ticket says: *"cycles read the platform's own signals — `ai_activity_log` error rates and
anomalies, failed runs, regression trends, Vercel logs."*

**`ai_activity_log` has no error column.** Verified live this cycle: 28 columns, none of them a
status/error/success field. 34,449 rows. The only error-adjacent data in the entire table is
`call_facts.http_status`, present on **28 rows ever**, of which 5 are non-200 — all
`article-extraction`, all late July. There is no error rate to read.

**The platform's real error ledger is `public.durable_hops`.** Verified live:

| status | rows | with error text | oldest | newest |
|---|---|---|---|---|
| `complete` | 1,198 | 0 | 2026-07-07 | 2026-08-18 |
| `in_progress` | 322 | 0 | 2026-07-07 | 2026-08-14 |
| `failed` | **260** | **260** | 2026-07-08 | 2026-08-10 |

Every failed hop carries non-null, mechanically classifiable error text. That is the signal
v1 reads.

## 3. Signature and threshold — grounded in the measured distribution

Signature = `(capability_slug, error_class)`, where `error_class` is the first line of `error`
with digit-runs collapsed to `N`, truncated at 120 chars. `sig_hash` = first 12 hex of
sha256(`capability_slug|error_class`).

Measured live (all 260 failed hops): **30 distinct signatures** — 16 at ≥3 occurrences, 6 at
exactly 2, 8 singletons. Top signatures:

| capability | error class | n | distinct days |
|---|---|---|---|
| `channel-intelligence` | `Anthropic call failed: N` | 67 | 6 |
| `quality-gate` | `Parse failed and retry also failed` | 30 | 8 |
| `data-room-custody` | `Parse failed and retry also failed` | 15 | 4 |
| `quality-gate` | `The operation was aborted due to timeout` | 6 | 6 |

**Threshold: ≥3 occurrences in a 14-day window.** At ≥3 the 16 real signatures fire and all 8
singletons plus the doubleton noise stay quiet. At ≥2 the noise files. At ≥5 the slow-burn
`quality-gate` timeout — 1/day across 6 distinct days, a genuine recurring defect — would never
file. 14 days rather than 7 because slow-burn signatures accumulate across weeks; idempotency
comes from dedup (§4), not from the window.

## 4. Dedup — derivable from existing rows, no new table

Every heal-filed ticket carries the literal line ``Heal signature: `<sig_hash>` `` in its
description. Before filing, the engine queries
`backlog_items WHERE source_file='heal-engine' AND description LIKE '%<sig_hash>%'` — any status.
A signature with any existing ticket never re-files. The 3-hour cadence therefore files each
defect exactly once, forever.

**v1 limitation, stated:** a signature fixed and later recurring will not re-file. Correct
default for an unattended 3-hour loop; recurrence detection is v1.1.

## 5. What it writes

One `backlog_items` INSERT per fired signature, max 3 per run, each preceded by its before-image.

| field | value |
|---|---|
| `id` | uuid generated client-side, so the before-image can name it *before* the insert |
| `backlog_id` | `LOO-<n>` — a block of N claimed in **one** `feature_id_counter` call per run |
| `tier` / `status` | `now` / `missing` — the only open status the live CHECK allows |
| `type` / `priority_class` | `Task Success Rate` / `P9 - Bug Fixes` (named form, register B9) |
| `source_file` / `row_ordinal` | `heal-engine` / numeric part of the LOO id — satisfies `UNIQUE(source_file,row_ordinal)` by construction |
| `title` | `[Heal] <capability>: <error class> (<n>× in 14d)` |
| `description` | `**P9 - Bug Fixes.**` + the sig-hash dedup line, window bounds, count, first/last seen, up to 3 real `durable_hops` UUIDs with verbatim error excerpts, the reproduction SQL, and "Detection never auto-fixes." |

**Write ceremony, fail-closed (§19v):** insert `runner_before_images` first
(`row_data = NULL` = "row did not exist → Reverse is a DELETE"); only on its success, insert the
ticket. Before-image fails → the ticket write does not happen. The engine performs **no UPDATE,
no DELETE, no DDL, ever.**

## 6. Contract

Env `SUPABASE_URL` + `SUPABASE_SERVICE_KEY` from `process.env` only, never printed.
Exit **0** = ran, nothing new to file (or `--apply` filed successfully); **1** = dry-run found
detections not yet filed; **2** = could not run. Exit 2 is never a pass.
Flags: `--apply` (default is dry-run), `--cycle-id=<uuid>` (required with `--apply`),
`--window-days`, `--threshold`, `--max-filings`, `--until=<iso>`, `--json`.
Pure exports (`normalizeErrorClass`, `signatureOf`, `detect`, `buildTicketDraft`) behind a
`pathToFileURL` guard — importing never touches network or disk.

**Dry-run/apply split: yes.** Every apply-write needs a before-image bound to a real open cycle;
a design or QA session must be able to detect with zero writes; and the red control below is only
cheap if detection is side-effect-free by default.

## 9. Flagged — inference, not verification

- **The INSERT before-image convention is invented here.** All 318 existing
  `runner_before_images` rows have non-null `row_data`; there is no INSERT precedent. `row_data
  = NULL` meaning "row absent, Reverse = DELETE" is a reading of the nullable column, not a
  documented rule. Stated in the runbook step and surfaced on the briefing.
- **`status='missing'` reuse** is forced by the live CHECK constraint. Widening it would preempt
  `SES-83` (d)/(e)'s gated design — deliberately not done.
- **Heal tickets are DB-only** while the markdown files remain authoritative, so they will not
  appear in `FEATURES.md` and the layer-3 markdown queue pick will not see them until `SES-83`
  (d)/(e) flips authority. Acceptable by construction — John's queue puts Heal (step 3) after
  "backlog DB used" (step 2) — and the snapshot export gives every heal ticket a git-committed
  copy. **`source_file='heal-engine'` must be added to any future markdown→DB reconciliation's
  ignore-list.**
- **Prefix `LOO`** because `durable_hops` is LOO's documented domain, but an individual root
  cause may be `HAR`-side; `SES-85`'s sweep may rebucket.
