## 1. CONTEXT

Found live 2026-07-16 during a data-model review John requested (`loo-007-confidence-tier-0716`), while investigating whether `the_library`/`the_reasoning`'s schema explains `LOO-007`'s confidence_tier inconsistency. It does, but fixing that requires this session first.

Eleanor Voss's `library-write-intent` — the sole legal write path into `the_library` (`lib/librarian.js`, confirmed no second path exists anywhere in the codebase) — has a `data_type` schema enum of `["sourced","inferred","synthesized","learned",null]`. This is stale against `ARCHITECTURE.md` §19f (locked 2026-07-03): `learned` was explicitly rejected as a `the_library` value there (reserved for `knowledge_entries`, a different table, never built there either), and `consolidated` — the value the whole opinion-to-fact promotion mechanism depends on — was never added.

**Confirmed live consequence:** Nadia Farouk's `data-patch-execute-intent` already has correct `analysis_instructions` telling her to request a promotion with `data_type: consolidated` — but when that request reaches Eleanor, her schema has no such option, so the model falls back to the nearest legal value. A real promoted row exists exactly this way: `the_library.id = 92131ed8-...` (the Vitrine Tech training-completion correction), landed as `data_type: 'synthesized'` instead of `'consolidated'`, with no lineage recorded at all.

**Second, independently-confirmed gap, found by reading the actual insert code before writing this kickoff (not assumed from the schema alone):** `writeLibrary()` (`lib/librarian.js`) spreads its params generically, but the inner `writeTheLibraryEntry()` function it calls uses an explicit destructured parameter list and builds an equally explicit `payload` object for the Supabase insert — `promoted_from_reasoning_id` is a real, already-existing nullable column on `the_library` (`ARCHITECTURE.md` §19f: `"the_library gains one new nullable column... promoted_from_reasoning_id"`) but is in neither the destructure list nor the payload. Fixing only Eleanor's schema would let the model *say* `promoted_from_reasoning_id`, but the insert function would silently drop it before it ever reached the database — the exact "looks fixed, isn't" trap `STANDARDS.md`'s Architect Review step exists to catch. Confirmed via `promoted_to_library_id`/`promoted_from_reasoning_id` both null on every one of 22 live `the_reasoning` rows — promotion cannot structurally succeed today regardless of agent behavior, for two independent reasons, not one.

**Folded in, same doc area, cheap:** `ARCHITECTURE.md` §19e's Resource Ownership registry still lists `the_reasoning`'s broker status as "🔶 Kickoff written, not yet executed" — stale; confirmed live via Supabase that `the_reasoning` has 22 real, well-formed rows in active use.

**Explicitly out of scope, logged separately, not this session:** `AGT-024` (Nadia's `promote` flow doesn't yet reference a specific source `the_reasoning` row at all — a different Skill, a different defect, sequenced *after* this session, not part of it). This session makes the write path *capable* of recording correct lineage; it does not make Nadia's flow *supply* one yet. `DAT-001`/`DAT-002` (unrelated data-hygiene findings from the same review) are explicitly not touched here.
