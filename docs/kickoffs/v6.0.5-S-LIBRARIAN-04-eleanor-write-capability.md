## 2. CONTEXT

**Why an LLM call at all, if Eleanor is just executing a write she didn't decide on?** Every capability in this platform runs through the same three-step pipeline (`assemblePrompt` → `enrichPrompt` → `sendRequest`, `AR-1.2`) — there is no "skip the model, just run a function" path, and inventing one would itself be new capability-specific-shaped logic. Eleanor's Intent Skill Profile schema mirrors `writeLibrary()`'s real parameters almost verbatim; her system prompt's job is narrow and mechanical — reproduce the exact operation and parameters she was asked to execute, never invent content, never soften a `supersede` into an in-place edit. This is a thin pass, priced accordingly (Haiku, see Task 3) — it is the trust-boundary confirmation + structured-parameter step, not creative reasoning. It satisfies `AR-1.3` for real: she now has an actual Competency (Skill Profiles + Capability + assignment), not a bare persona.

**Why a new handler, not reusing `store`.** `sendRequest()`'s Step 3 always calls `storeHandle()`, which always inserts a `deliverables` row (`api/_lib/handlers/store.js`). A Data Room write is not a deliverable — inserting a phantom `deliverables` row alongside the real `the_library` write would be a second, meaningless side effect. `format_contract.handler` is already a data field read generically (`AA-44`); this session adds a second value the dispatch can resolve to (`library-write`), the same pattern `store` already establishes — not a capability-specific conditional (`AR-1.1` stays satisfied: the dispatch keys off `handlerSlug`, a data string, never off `capability_slug === 'data-room-custody'`).

**Which `writeLibrary()` operations this capability may invoke.** `insert` and `update_status` only. **`bulk_reset` is deliberately excluded from this Intent's schema** — Demo Reset (design doc §7) is a human-triggered, deterministic action (`S-APPLE-04c`), not something an agent's own reasoning should ever be able to decide to fire. Excluding it from the schema's `operation` enum makes an accidental agent-initiated full reset structurally impossible here, not just discouraged.

**Composite actions (e.g. "supersede" = insert new row + mark old row superseded) are out of scope for this session.** Eleanor's capability executes exactly one `writeLibrary()` operation per call — the same granularity the broker itself already has. Whether a logical "supersede" becomes two sequential `delegate_to_agent` calls to her, or something else, is `S-APPLE-04b`'s wiring decision, not this session's. This session proves the one-operation-per-call primitive works; composing it is next session's problem to solve with the actual caller (Nadia) in view.

**No `requires_human_confirmation` on this capability.** By the time anything reaches Eleanor in the intended chain, a human has already confirmed the action upstream (at Nadia's gate, once `S-ARCH-HITL-RESUME-01` makes that resolvable). Gating Eleanor's own execution a second time would be a redundant, undocumented second confirmation step nothing in the design calls for — she executes what she was asked, faithfully; she does not re-decide whether it should happen.

**No `can_request_help` either.** Eleanor is a leaf executor in this mechanism — she has nothing to delegate further for this capability.

**Confirmed prerequisite already live:** `eleanor.uber_access = true` in Supabase (set by `S-LIBRARIAN-02`, Task 1) — the only agent row with `uber_access: true`. This means every call through her new capability must supply an explicit `data_room_tag` (the `uber_access` branch in `writeLibrary()` requires it, denies otherwise) — never inferred, never defaulted. This is existing broker behavior, unchanged by this session.

**Design review finding — a real tenant-isolation gap, and the one thing Eleanor actually enforces.** Cross-checking her persona (bio: "she checks the requesting agent's credentials... she does not trust a caller to scope its own query correctly... enforces it herself") against what `writeLibrary()`'s `insert` operation actually does today found a real gap: `the_library.supersedes_id` has a foreign key to `the_library.id`, but that only confirms the referenced row *exists* — not that it belongs to the *same* `data_room_tag`. A superseding insert could legally point at a row in a different Data Room today; nothing catches it (confirmed live against the schema — `information_schema` shows the FK, and neither `insert` nor `update_status` in `writeLibrary()` cross-checks `supersedes_id`'s room). This session fixes it in `writeLibrary()` itself (Task 4c) — the broker file responsible for `the_Library`'s integrity per `§19c` — not scoped only to Eleanor's new handler, so it protects every future `insert` caller the same way. This is the one genuine judgment/enforcement action her capability performs; everything else is faithful execution of what she was asked.

**Considered and explicitly rejected: a separate "Bouncer" agent for access control, splitting credential-checking from Eleanor.** `AR-3.1` already assigns full CRUD gatekeeping to Eleanor alone ("she alone performs the call") — a second persona isn't called for by any existing rule, and would be new architecture the platform doesn't need for this. Checking whether the *original* delegating agent (e.g. Nadia) is itself credentialed for a given Data Room was also considered and rejected for this session: it requires a generic harness change (threading the calling agent's own `agent_id` through `delegate_to_agent`, which nothing does today), touches every existing delegating capability, and has zero practical effect while only one Data Room (`apple-cso-data-room`) exists. Logged as a future consideration, not built here, not urgent.

**Task 4a — new file** `api/_lib/handlers/library-write.js`:
```js
// DeepBench v6.0.5 | api/_lib/handlers/library-write.js | AG-33 -- Eleanor Voss's data-room-custody handler
// FEATURE: AG-33 -- dispatched generically via format_contract.handler === 'library-write', same
// registry pattern as store.js. This file performs no agent-id check of its own -- ARCHITECTURE.md
// §19c's "only Eleanor" rule is enforced by which Skill Profile sets handler: 'library-write' in
// the first place (only library-write-intent does), not by a conditional here. Calls the existing
// writeLibrary() broker unchanged -- this is not a second write path into the_library.

import { writeLibrary } from '../../../lib/librarian.js';

export async function handle({ agent_id, tenant_id, content }) {
  const { operation, data_room_tag, ...params } = content || {};
  if (!operation) throw new Error('library-write handler: operation required in structured output');
  if (!data_room_tag) throw new Error('library-write handler: data_room_tag required in structured output');

  const result = await writeLibrary({
    requestingAgentId: agent_id,
    tenantId: tenant_id,
    operation,
    data_room_tag,
    ...params,
  });

  if (!result.success) {
    throw new Error(`library-write handler: writeLibrary failed -- ${result.error || result._librarian?.tier || 'unknown reason'}`);
  }

  return { deliverable_id: null, entry_id: result.entry?.id || null, handler_result: result };
}
```
