## 1. CONTEXT

**S-APPLE-04b** is the third and last session of the chain opened 2026-07-02 (`S-LIBRARIAN-04` → `S-ARCH-HITL-RESUME-01a` → this session) closing out `AG-34`: Nadia Farouk's Data Integrity Patch (`data-patch-intent`, design doc §5.6) — a director disputes a specific existing Data Room chunk, Nadia decides what should change, a human confirms, and it actually gets written. Both prerequisites are real and done: Eleanor Voss has a working `data-room-custody` capability (`S-LIBRARIAN-04`), and the generic accept/reject/edit resume mechanism exists (`S-ARCH-HITL-RESUME-01a`, `AA-100`).

**The gap this session actually closes (found during design review, not in either prerequisite):** `AA-100`'s accept path treats a human-confirmed decision as final — it dispatches straight to a handler and stops. It never gives the confirming agent a chance to act on what was just approved. That's correct for a capability with nothing further to do once confirmed, but wrong here: once a human accepts Nadia's proposed correction, *something* still has to actually reach Eleanor and get the write(s) done — and per `AR-2.2`/`AR-2.3`, that has to be a real `request_help` → Michelle → `delegate_to_agent` round trip, never a shortcut, not even for a resource with one obvious owner. Nothing in the platform today connects "human clicked accept" to "now go ask for help."

**The fix (`AA-103`) — a new generic hand-off field, plus splitting Patch into a decide step and an execute step:**
- `data-patch-intent` (decide) — the schema from §5.6. Proposes an action; gated by `requires_human_confirmation` exactly like Escalate already is. Deliberately **no** `can_request_help` — Nadia decides entirely from what she's handed (`disputed_chunk_id`/`correction`/`director_reasoning` via `task_context`), the same no-Library-read pattern already established for `data-escalate-intent`. `patch`, `supersede`, and `restore` all execute identically once confirmed (insert a new row + mark the old one superseded) — the action value only changes how Nadia describes the correction, not what Eleanor does. `no_action` means zero Eleanor calls.
- `data-patch-execute-intent` (execute) — new, runs *only* after a human accepts. `can_request_help: true`, not gated. Its only job: take the confirmed decision and get it executed by asking for help to reach Eleanor — never write anything itself.
- A new optional trait, `on_accept_intent_slug`, read generically by a new `resolveAccept()` function in `execute.js`: if the confirmed intent declares one, accept re-enters the loop on that intent instead of terminal-dispatching. If it doesn't (every existing gated intent today), behavior is byte-identical to before — falls straight through to the existing `resolvePendingConfirmation()`. This is the same shape as the already-existing `critique_capability_slug` trait (a data field the harness reads generically, never a capability-specific conditional) — extending shared pipeline code per `§19b`, not bypassing it.

**A second, unrelated gap found in the same review, fixed in this session because it's live risk, not because it's this feature's job:** `data-escalate-intent` (Nadia's other capability, `S-APPLE-04a`) already has `can_request_help: true` on its own decide-step, set back when Eleanor had no real capability to reach. That's no longer true — Eleanor is live now. Left as-is, nothing stops Nadia from asking for help *during her own reasoning, before any human has confirmed anything* — and if that request reached Eleanor, Eleanor would perform a real write immediately, skipping `AR-4.1`'s human-confirmation gate entirely. Task 3 removes it. Escalate does not get `on_accept_intent_slug` or its own execute-intent in this session — that's `S-ARCH-HITL-RESUME-02`, next in the queue (design decision 2026-07-03: fix the safety gap now, complete Escalate's round trip in a follow-up session using the same mechanism this session builds).

**Known, accepted quirk, not fixed this session:** a `no_action` decision still produces a `pending_confirmation` for a human to close out, even though nothing is actually being approved. Fixing that would need a content-aware gate (skip confirmation based on the *value* of the model's own output, not just the intent's static traits) — a bigger, separate harness change. Harmless — an extra click, not a wrong write — so left as documented behavior, not solved here.

**Hop-budget note:** a `supersede`-type action costs 2 delegate round trips inside `data-patch-execute-intent` (`request_help` + `delegate_to_agent`, twice — once per Eleanor operation), 4 hops against the harness's 5-hop `MAX_LOOP_DEPTH` ceiling. This is a fresh hop budget, separate from whatever the original `data-patch-intent` decide-step used — pause/resume across the confirmation boundary is not currently hop-budget-continuous (the hop counter is never persisted to `pending_confirmations`). Documented, not a defect — each side of the pause already comfortably fits under 5 on its own.

```js
// FEATURE: AA-103 -- looks up whether the given intent declares a follow-up intent to run once
// a human accepts (traits.on_accept_intent_slug). Generic: reads a data field on the confirmed
// intent's own Skill Profile row, never a capability- or agent-specific conditional. Returns
// null for any intent that doesn't declare one -- the existing terminal-dispatch accept behavior
// is unchanged for those. ARCHITECTURE.md §19b/§19d.
export async function getOnAcceptIntentSlug(intent_slug) {
  if (!intent_slug) return null;
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  const headers = getSupabaseHeaders(supabaseKey);
  const res = await fetch(`${supabaseUrl}/rest/v1/skill_profiles?slug=eq.${encodeURIComponent(intent_slug)}&select=traits&limit=1`, { headers });
  if (!res.ok) return null;
  const [row] = await res.json();
  return row?.traits?.on_accept_intent_slug || null;
}

// FEATURE: AA-103 -- closes out a confirmation whose accept was fulfilled by delegating to a
// follow-up intent (getOnAcceptIntentSlug found one) rather than by resolvePendingConfirmation's
// own terminal dispatch. Mirrors that function's accept tail exactly, minus the sendRequest call.
export async function markAcceptedDelegated(confirmation_id, result) {
  await updateStatus(confirmation_id, { status: 'accepted', resolution: result });
}
```

2. Add a new exported function, after `runCapability()` (before `export default async function handler`):
```js
// FEATURE: AA-103 -- accept resolution, exported separately so the Node.js test can call it
// directly (same reasoning as runCapability's own export). Checks whether the confirmed intent
// declares a follow-up intent to run now that a human has approved (on_accept_intent_slug)
// before falling back to the original terminal-dispatch behavior (resolvePendingConfirmation) --
// unchanged for any intent that doesn't declare one. This is what lets an agent who needed a
// human's OK before acting actually go act on it afterward, via the same request_help loop every
// other cross-agent hand-off uses -- never a direct call to whichever agent ends up executing it.
// ARCHITECTURE.md §19b/§19d, PLATFORM-AGENT-RULEBOOK.md AR-2.2/2.3/3.1.
export async function resolveAccept({ confirmation_id }) {
  const row = await getPendingConfirmation(confirmation_id);
  if (!row) throw Object.assign(new Error('confirmation not found'), { status: 404 });
  if (row.status !== 'pending') throw Object.assign(new Error(`confirmation already ${row.status}`), { status: 409 });

  const onAcceptIntentSlug = await getOnAcceptIntentSlug(row.intent_slug);
  if (!onAcceptIntentSlug) {
    return resolvePendingConfirmation({ confirmation_id, resolution: 'accept' });
  }

  const result = await runCapability({
    capability_slug: row.capability_slug,
    intent_slug: onAcceptIntentSlug,
    agent_id: row.agent_id,
    task_context: row.proposed_action,
    tenant_id: row.tenant_id,
  });
  await markAcceptedDelegated(confirmation_id, result);
  return result;
}
```
