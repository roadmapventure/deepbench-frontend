## Task 2 — The migration

Apply via `apply_migration` (project `rallojeqnkgtxgsdsnqm`), name `log136_criteria_dotted_path`. `CREATE OR REPLACE FUNCTION public.pattern_criteria_matches(sig jsonb, crit jsonb)` — **identical identity argument list, so it replaces in place (no overload)**; still assert exactly one function of that name remains afterward (`supabase-function-signature.md` discipline). The body change, exactly two edits to the current body read in Step 0:

1. Key resolution becomes path-aware. Where the loop currently does `sval := sig -> k;`, resolve instead:
   ```sql
   if strpos(k, '.') > 0 then
     sval := sig #> string_to_array(k, '.');
   else
     sval := sig -> k;
   end if;
   ```
2. The final else-branch (currently `if not (sig @> jsonb_build_object(k, v)) then return false; end if;`) must use the resolved `sval` so dotted keys work there too:
   ```sql
   if sval is null then return false; end if;
   if not (sval @> v) then return false; end if;
   ```
   (For scalars, jsonb containment is equality — `'true'::jsonb @> 'true'::jsonb` — and for objects it preserves the original recursive-containment semantics; for non-dotted keys `sval @> v` with the null guard is equivalent to the old `sig @> jsonb_build_object(k, v)`.)

Function stays `IMMUTABLE`, `plpgsql`, same name/args/return — nothing else in the body changes. The `"in"` and `">"` branches already read `sval` and need no edit beyond receiving the path-aware value.
