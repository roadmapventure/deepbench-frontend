## 1. CONTEXT

Fifth site, two write sites in one file, both inside `sendRequest()`:

**Guardrails-check row (lines 392-409) — real bug, same class as `AA-190c`'s ai-enrichment fix.** Sums input+output tokens into `gTokens`, logs the sum as `input_tokens`, and the payload doesn't even include an `output_tokens` field (not hardcoded `0` — absent entirely). Anthropic's response already returns the real split (`gData.usage.input_tokens`/`.output_tokens`); it's computed into `gTokens` and the split itself discarded. Fix: capture and pass through both fields separately, same pattern as `AA-190c`.

**STEP 4 row (lines 434-461) — no data bug, architecture-consistency only, same class as `AA-190d`'s execute.js migration.** Already captures real split `input_tokens`/`output_tokens` from `usage`, and `patternsUsed` is built dynamically via the real `buildPatternsUsed(isJson, guardrailsRan, delegation_occurred)` helper plus real `intent_technical_services` — not a hardcoded stale string. `ai_type: capability_slug || 'request-receivable'` is also already dynamic and correct (`AI-41`'s fix). Pure migration onto `logActivity()`.

**Important scope note, confirmed reading this file — do NOT repeat `AA-190c`'s dead-code cleanup here.** In `ai-enrichment.js`, `supabaseUrl`/`supabaseKey` became fully unused after migration and were removed. In *this* file, `supabaseUrl`/`supabaseHeaders` (declared near the top of `sendRequest()`) are **still used elsewhere** — STEP 3's handler dispatch (line ~429-430) passes both directly into `handlerFn({..., supabaseUrl, supabaseHeaders})`. They must stay untouched.

**Behavior note, worth stating explicitly, not hiding:** both current write sites use `await fetch(...)`, blocking `sendRequest()`'s own execution until the log write completes. Every other site in this whole `AA-190` sequence (Librarian, ai-enrichment, execute.js) already logs fire-and-forget (`logActivity()` is deliberately not awaited internally — matches its existing design, not a new choice this session). Migrating these two sites brings them into that same consistent pattern: `sendRequest()` will no longer wait on the Supabase write before proceeding to STEP 3 (guardrails row) or returning (STEP 4 row). This is a minor latency improvement, not a functional risk — nothing in this codebase reads back a freshly-written `ai_activity_log` row synchronously within the same request.
