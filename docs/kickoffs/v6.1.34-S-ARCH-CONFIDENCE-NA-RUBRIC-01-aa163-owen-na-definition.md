## 1. SESSION

**AA-163** — deferred item from `AA-162`'s design session (`docs/kickoffs/v6.1.32-...`): nowhere in the platform — not in code, not in Supabase — is there a written definition of when `confidence_tier: na` is a legitimate value on Marcus's (`ci-answer-intent`) Q&A answers. Owen's guardrail (`qg-review-intent`) checks for a `missing_confidence` violation by name, but has to improvise the actual criterion live, on every call. Confirmed live in the original screenshot: Owen's own improvised reasoning was actually reasonable ("the 'na' tier is only appropriate for meta-commentary or process explanations, not operational guidance") — it just isn't written down anywhere, so it isn't guaranteed consistent call to call, and nothing tells Marcus the same rule *before* he generates an answer.

**Confirmed scope via live Supabase query:** `confidence_tier` exists on exactly 2 Skill Profiles platform-wide — `ci-answer-intent` (produces it) and `qa-answer-format` (passes it through for display, no independent logic). This is not a platform-wide taxonomy question; it is exactly these two fields.

**Confirmed via live `deliverables` history:** every historical `na` answer on record was model confusion mid-test ("I need clarification on what you're asking me to deliver...") — not a genuine, deliberate meta-commentary case. There is no real precedent to preserve; this session is writing the rule for the first time, not codifying an existing pattern.

---

## 2. CONTEXT

**Why this doesn't need a code change.** Both `ci-answer-intent`'s `confidence_tier` schema field and `qg-review-intent`'s `method` text are plain Supabase content — the harness already reads them generically (`db-assembly.js`'s Intent-type branch renders `traits.schema` into the tool schema handed to the model; `qg-review-intent`'s `method` is rendered into its system prompt the same way every other Intent Skill Profile's method is). Writing the rubric into these two existing fields is the entire fix.

**Why both fields, not just Owen's.** Writing the rule only into Owen's `method` teaches the *reviewer* the rule but leaves the *producer* (Marcus) guessing — he'd still have no schema-level signal of when `na` is safe to use, and would keep discovering the boundary only via a block-and-retry cycle. Writing it into `ci-answer-intent`'s schema description too means Marcus is told the rule before he ever generates a response, not after. Same rule, worded consistently in both places (schema description is intentionally the terser of the two — schema field descriptions are read on every single call and inflate prompt size, `method` text is the fuller, one-time-per-review explanation).

**Why this doesn't touch `AA-162`'s fix.** `AA-162` already ensures Marcus never reaches for `na` on a catalog/inventory question — he delegates to Eleanor and gets a real `sourced` answer instead. This session's rubric is a general-purpose backstop for *other* phrasings that could still tempt an `na` guess (a pure clarifying question, a "this is outside what I can help with" case, a mid-hand-off status note) — not a re-litigation of `AA-162`'s already-verified fix.

## 5. TASKS

**Task 1 — Supabase (`execute_sql`, project `rallojeqnkgtxgsdsnqm`): write the rubric into both fields**

```sql
-- 1a. Owen (qg-review-intent): explicit na criterion, appended to the existing method text verbatim
-- (original method text preserved in full -- confirm via Task's own live read before writing, in
-- case a concurrent session has touched this row since this kickoff was written).
update skill_profiles
set method = method || ' confidence_tier: na is legitimate only for genuine meta-commentary -- the answer asks the requester a clarifying question, states plainly that this specific request falls entirely outside what can be answered here, or is a status update about an in-progress hand-off (e.g. "delegated this to X"). Block missing_confidence on any answer that asserts a fact, capability, description, or count as true -- including about the platform or Data Room itself -- without a sourced/inferred/synthesized tier. An na tier on a substantive claim is not fixable by retry; treat it as the same class of violation as synthesized_as_fact.'
where slug = 'qg-review-intent';

-- 1b. Marcus (ci-answer-intent): add a description to the confidence_tier schema field itself, so
-- he sees the rule before generating, not only after a block. jsonb_set targets the exact nested
-- path -- does not touch the enum, any other property, or the required array.
update skill_profiles
set traits = jsonb_set(
  traits,
  '{schema,properties,confidence_tier,description}',
  '"na is legitimate only for meta-commentary -- a clarifying question back to the user, an explicit statement that this falls outside what you can answer, or a status update about an in-progress hand-off. Any answer asserting a fact, capability, description, or count as true must use sourced, inferred, or synthesized instead -- never na."'::jsonb
)
where slug = 'ci-answer-intent';
```
