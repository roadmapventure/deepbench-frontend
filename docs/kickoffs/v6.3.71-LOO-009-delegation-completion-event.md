## CONTEXT

Every hand-off dispatched by `dispatchDelegation()` fires a live `delegation` event the instant it's dispatched (`§19h`). If the delegate's work later returns control to the caller, a `delegation_return` event fires too. But if the hand-off resolves as **final** — the delegate's own output becomes the whole chain's result, nothing returns — no completion event of any kind fires. The client has no live signal for who actually finished a final hand-off; the existing workaround (`CHI-37`, shipped `v6.3.70`) has every caller manually declare in advance who to credit once its call resolves — a per-call-site burden with its own failure mode (a caller that forgets/mis-declares).

This session closes the harness gap at the source: a `delegation_complete` event, fired at the exact two points `dispatchDelegation()` already knows a hand-off is final, naming the real terminal agent — the same information `finalizeDelegation()` already receives as `targetAgentId`/`rec.recommended_agent_id`, just never announced live. Additive only — the existing `delegation`/`delegation_return` firing is completely unchanged.

Found live 2026-07-20 (`design-routing-log-bug-0720`) while root-causing a stuck "Owen is routing this to Marcus…" placeholder in the Agent Routing drawer. That specific bug turned out to be a *different*, client-side gap (tracked separately as `LOO-009b`) — but confirming it required first verifying this harness gap was real and distinct, which it is: `LOO-009` and `LOO-009b` fix two different mechanisms for two different delegation shapes (final vs. returning).
