## The two decisions most likely to be got wrong later

**The 48h stale floor sits ABOVE the box, not below it.** John's spec says it in one clause: *"a
standing number must not defeat the staleness brake."* The obvious reading of *"the box is THE day
cap"* puts it at rung 1 — and that hands a runner with **no idea how much of John's meter is left**
a 25M budget. Proven with a negative control, not reasoned about: box `4` with every reading aged
past 48h returns `3,000,000 / stale-floor` on the shipped build and `4,000,000` on the
box-above-the-brake build, from identical fixtures.

**A one-day override still beats the standing box.** A number he wrote for today is later, more
specific word than a number he left in a box — the same reasoning that puts a pin above the
automation lane and selection layer 1a above 1b.

**`NULL` is never `0`, and that rule has four expressions that must agree:** the DB null,
`settingsNow()`'s `undefined`-not-falsy test, the empty-string render, and the empty-box commit
that stores `null`. A blank box means *"no standing cap, budget as before `SES-147`"*; a `0` would
say *"no tokens allowed today"* — a number John never typed, and one the column's own CHECK
refuses, so the harvest would throw on a tap he had just made.

## QA — discriminating, not merely complete

**The defect this ticket's own QA caught before it shipped**, recorded because a completeness check
passed on the broken build: the first build declared `rest_pct` / `meter_pct` as `numeric` while
`runner_budget.weekly_rest_pct` is `integer`, so **every** `RETURN QUERY` raised `42804` — on
**rung 1**, the rung today takes. A budget check that errors is a cycle that cannot run at all.
Only *calling* each rung found it; the grants, the overload count and the column all asserted clean
on the broken build.

**Seven SQL arms, on fixtures inside a deliberately rolled-back transaction:**

| Arm | Fixture | Result |
|---|---|---|
| A | box 4 + live override | `25,000,000` / `override` ✔ |
| B | box 4, override withdrawn | `4,000,000` / `daily-max-box` ✔ (retired build: `calibrated`/10M) |
| C | box 4, every reading aged 64h | `3,000,000` / `stale-floor` ✔ **not 4,000,000** |
| C2 | box 4, no readings at all | `3,000,000` / `stale-floor` ✔ |
| D | blank box, fresh readings | `10,000,000` / `calibrated` ✔ = pre-`SES-147` exactly |
| E | box `0` / `1001` / `25` | rejected / rejected / stored ✔ |
| F | meter at 90 ≥ rest 85 | `rest_wall_hit=true` **and** a real cap ✔ (reported, not enforced) |

**Arm C failed on its first run and the fixture was wrong, not the function** — aging only the
newest reading promoted a still-fresh one to newest. Recorded rather than quietly re-run.

**Rollback verified clean:** box back to `NULL`, override still queued, 10 readings intact, max
`all_models_pct` back to 37.

**Six page arms** (`tests/regression/SES-147-daily-max-box.js`), each run against the real template.
Assertions 3 and 4 are the discriminating pair and **both were proven to fail on their respective
plausible-wrong builds**, then to pass on the shipped one:

- a `||` fallback in `settingsNow()` → John's cleared box renders `25` straight back, so the
  standing cap can never be removed from the page → **assertion 3 FAILS** ✔
- an in-force line computed as `box × 1,000,000` → prints `4,000,000` on a day an override is
  running → **assertion 4 FAILS** ✔
- assertion 6 is the negative control: strip the `dailyMaxRow(s)` call site and the box is gone.

**Build green** (`npm install && npm run build`). **Regression suite 43/43** with credentials in
env (the one red without them is `CHI-31`, which requires Supabase — unrelated to this change).
