## 2. CONTEXT

**The measurement:** 53 scheduled cycles in the current weekly window booted cold, discovered there was nothing to do, and closed — **32.4M tokens, average 611,321 each, shipping nothing.** That is more than M5's entire 31.9M predicted cost. A chained cycle ships real work for 809K; these spent three quarters of that to decide not to work.

**Why they cost so much:** the decision happens *after* orientation. A fire boots, reads `CLAUDE.md`, `CLAUDE-STATE.md`, the standing brief and this runbook, re-asserts leases, and only then reaches a step that concludes the drain is empty, parked, or wall-stopped. Every one of those reads is paid before the answer is known.

**What this ticket can and cannot do — stated plainly so the result isn't oversold.** The cron trigger lives outside this repo (`claude.ai` routines), so a session boot cannot be prevented from here. What *can* change is when the answer arrives: make the first executable action of a cycle a single cheap query, and exit immediately on `false`. A parked fire then costs one query plus a `runner_cycles` row instead of a full orientation. The measured 611K should fall to a small fraction of that; **the ticket's own QA must measure the real post-change cost rather than assert the saving.**

**Reallocation, recorded rather than silent:** `M5-06` (weekly affordability) and `M5-15` (stale usage reading) were originally scoped to `SES-281`. They moved here because both answer *should a session run at all* — a pre-boot question — not *which ticket*, which is what the pick path decides. `SES-281`'s kickoff records the same reallocation from the other side.

## 5. TASKS

### Task 1 — `public.runner_should_boot()` (migration `ses297_runner_should_boot`)

A `STABLE` function, no arguments, returning one row:

`(should_boot boolean, reason text, detail jsonb)`

It must be **cheap** — no writes, no `drain_epic_next` call (that function retires directives and writes before-images; calling it from a read-only gate would let a probe close John's standing drain). Reuse the `SES-281` pick predicate by reading `prime_directive_queue()`, which is `STABLE` and already carries the M5-01/02/07/08/09 filters.

Refuse to boot, in this precedence, each with a distinct `reason`:

1. `'scheduler_off'` — `runner_settings.scheduler_on` is false.
2. `'usage_reading_stale'` — **`M5-15`**: the freshest `runner_usage_readings.taken_at` is older than 24h. Include the age in `detail`.
3. `'weekly_wall'` — **`M5-06`**: the freshest reading's `all_models_pct` is at or above `runner_budget.weekly_rest_pct` for the current month.
4. `'no_budget_row'` — no `runner_budget` row for the current `America/Chicago` month. *(This is the outage that stopped the runner on 2026-09-01 and sat unread in a card; it must be a named refusal reason, not a silent pass.)*
5. `'nothing_pickable'` — **`M6-09`**: `prime_directive_queue()` returns no `drain` or `selfbuild` lane row.
6. `'unaffordable'` — **`M5-06`**: the cheapest pickable ticket's `predicted_pct_of_week` exceeds the remaining weekly headroom (`100 − all_models_pct`).

Otherwise `should_boot = true`, `reason = 'pickable'`, and `detail` names the ticket that would be picked and its predicted cost.

**Month boundary is `America/Chicago`**, per register `B35` — not UTC.

## 6. DESIGN RULES

- Never call `drain_epic_next` from the gate. It mutates.
- `runner_should_boot` returns a reason for a refusal always — a bare `false` is the "NULL is not zero" defect this codebase has paid for repeatedly.
- Do not change the cron cadence or `runner_settings`. The gate makes a fire cheap; it does not decide how often fires happen.
- Do not touch `scheduler_gate()` — it answers a different question (is this fire admissible on the clock grid) and both can hold.
