cycle after cycle, until none are left* — and then deletes itself.

## The five properties, and why each is deliberate

**(1) The epic is an FK, not prose in `body`.** `runner_directives.epic_id uuid REFERENCES
epics(id) ON DELETE RESTRICT`, plus `CHECK ((type = 'drain-epic') = (epic_id IS NOT NULL))` —
a drain **must** name an epic and nothing else **may**. This is the same correction as `SES-86`
phase 3 (John's automation queue: prose → `automation_rank`) and `v7.0.146` (a card's plain
language: render-time literal → column), for the same measured reason: a rule a cycle has to
re-derive from a sentence is a rule that gets re-derived differently.

**(2) A drain is never consumed.** Layer 1 today reads *"a directive is the mission, mark it
`in_progress`"*. Applied to a drain row, that ends the standing-ness on cycle 1 — which is the
entire feature. `drain_epic_next()` therefore never writes `status` except to retire.

**(3) `now` tier only.** John's boundary on `SES-110`, verbatim: *"finish the `<epic>` tickets"* =
the epic's **NOW-tier members only**. Members in `next` / `later` are outside a drain and do not
hold it open.

**(4) Blocked is not retired — the parallel-cycles trap.** Under register B42, N cycles run at
once. If *"no ticket I can claim"* meant *"epic drained"*, two peers holding the last two claims
between them would each cancel John's standing order while both tickets were still being built.
So the two predicates are deliberately different:

| | asks | claims |
|---|---|---|
| **retire** | does any open `now` member *exist*? | ignored |
| **pick** | which member can *I* claim? | honoured (24h expiry, the B37 bar) |

`outcome='blocked'` means active-but-nothing-for-me: fall through to the class-sorted board and
build normally. **A drain must never end a cycle build-less** — register B24's rule for gated
cards, binding here for the same reason.

**(5) It never self-activates.** Nothing in the migration inserts a drain row, and the function
has no `INSERT` into `runner_directives`. The only way one exists is John writing it. That is the
difference between a mode he grants and a mode the runner grants itself, and it is why this
ticket does not widen the runner's autonomy by a single degree: with no drain declared,
`drain_epic_next()` returns `none` and selection is byte-for-byte what it was yesterday.

Retirement writes **its own before-image first** (§19v: no before-image, no write) instead of
leaving that as a step the calling cycle must remember.
