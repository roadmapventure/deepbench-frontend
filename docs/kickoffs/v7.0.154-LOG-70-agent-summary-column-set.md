**The ticket, and the one part of it that is a clean mechanical job.** `LOG-70` asks that the remaining pattern consumers be pointed at the Log Displayer view, retiring duplicated/hardcoded pattern logic. Two consumers remain in its text: `src/aiPatterns.js` and `src/hooks/useAgents.js`. The ticket already narrows the second one itself: *"once `LOG-112` ships, that file's `patterns_used` SELECT is dead weight — nothing reads it. Drop the column from the query when this row is taken."* `LOG-112` shipped at v6.3.218. `docs/SESSIONS.md` carries the same residue note independently.

**Why the line survived, stated precisely, because it is the whole lesson.** `LOG-112` rewrote `buildActivitySummary()` to stop reading `row.patterns_used` (`src/hooks/useAIActivity.js:269-277` — the per-agent breakdown now records only `{id, latencyMs}` and joins verified names afterwards from the Displayer rollup). But that test's scan roots are `["src/screens", "src/components"]`. `src/hooks/useAgents.js` — `buildActivitySummary()`'s **other** caller — is outside the scanned tree, so it kept `patterns_used` in its `.select()` column list and kept fetching it on every page of every agent-activity query, read by nothing, for six versions.

**The premise was re-verified live before building, not taken from the ticket.** Two independent traces:

1. *Static trace.* `useAgents.js` references `patterns_used` at exactly one site, the `.select()` string. Every field read off those rows — `inScope()`, the scoped filter, the turn-timestamp pass, then `buildActivitySummary()` and its `pairedAgentTurnIds()`/`classifyRow()` helpers — was walked; none touches the field. `useAgentActivitySummary()` has exactly two consumers, both in `MarketIntelligenceScreen.jsx` (`:3041`, `:3761`), and every read of the returned summary is `operations`/`calls`/`avgCost`/`rows`/`byKind`. An independent Fable 5 subagent, instructed to **refute** the claim rather than confirm it, reached the same conclusion and found no path.
2. *Live measurement, which is the one that counts.* 400 real `ai_activity_log` rows were fetched — **305 of them carrying a non-empty `patterns_used`**, across 8 agents — and passed through the real `buildActivitySummary()` twice: once as fetched, once with the column stripped. The summaries are `deepStrictEqual`. **Negative control:** stripping `latency_ms` instead — a column the function demonstrably reads — *does* change the result, so the comparison can detect a real difference and the first assertion is not vacuous.

**One thing this deliberately does not fix, filed instead.** The same trace surfaced a genuine pre-existing defect in code this change does not introduce: `buildActivitySummary()`'s cost fallback reads `row.cache_creation_input_tokens` / `cache_read_input_tokens` (`useAIActivity.js:255`), and the AI Audit's own fetch selects both (`:1128`) while the `useAgents` fetch never has — so the two surfaces price the same NULL-`cost_usd` cached-token row differently. Filed as **`LOG-142`** (`P9 - Bug Fixes`, tier `now`). It is not fixed here because correcting it *moves numbers on an approved surface*, which §19v routes to flagged-or-gated — a different lane from this change, and widening scope to include it would have converted a zero-surface-delta cleanup into an appearance change.
