## CONTEXT

**The bug (`CHI-37`, found 2026-07-19 walkthrough, root-caused live):** `fetchNewsCards()` (`CHI-33`'s background Jordan→Alex news-feed fetch, fires on mount and every Clear) never logs Alex's completion — unlike every other `callCapability()` caller in this file, it fires the live "routing to Alex…" placeholder (`onDelegationProgress`) but never follows up with a completion event. Confirmed live via screenshot with John (2026-07-20): **hop 1 (Jordan, "routing this to Alex…") is correct and must stay exactly as-is — the bug is that Alex's own completion never appears as its own hop 2.** Today the placeholder just sits there forever; Marcus's real answer (and everything after it) starts at hop 2 when Alex's completed hand-off should occupy hop 2, pushing Marcus and everything downstream to hop 3 onward.

**Two corrections to this session's own first-pass scoping, both confirmed live with John — read carefully, the mechanism matters:**

1. **No count exclusion, ever.** An earlier framing (this session's own initial proposal, inherited from the original 2026-07-19 finding) assumed the fix needed to *exclude* Alex's hop from "Total hops"/the drawer's count badge, treating it as non-conversational. Wrong — every agent's real work is a real, normally-numbered, normally-counted hop. No exceptions, no special category.
2. **Jordan's hop and Alex's hop are two separate hops, not one hop that gets relabeled.** This is the more subtle part, and it's why Task 3 below is not simply "reuse the same `logEvent` call the other 3 sites use." `logEvent`'s existing `{ replaces }` mechanism is *designed* to let a live "routing to X…" placeholder resolve into a single collapsed hop once X's real result comes back — and today, because `onDelegationProgress` already registers Alex as the awaited agent for that placeholder, firing Alex's completion through the *ordinary* `logEvent` path would **splice it into Jordan's own row**, overwriting Jordan's hop instead of adding a new one. That's the opposite of what John confirmed: Jordan's hop must remain untouched, and Alex's completion must land as an independent, additional hop. Task 3 uses a small append-only logger for exactly this reason — see below.

**Why this one call site broke and the other three didn't (design-session finding, confirmed against real code, not guessed):** firing a hop-completion event today is a *manual, hand-written responsibility* at every `callCapability()` call site — nothing enforces it. The three existing sites (Marcus's answer, Owen's review, the Display hand-off) each got it right by hand, but they cover only two shapes: "the agent you called is the one who completes it" (Marcus, Owen) and "read the completing agent off the result, because it's dynamically picked" (Display, via `display.display_agent_id`). `fetchNewsCards()` is a third shape neither pattern covers: Jordan is the agent you call, but Alex — a *fixed, hardcoded internal delegate* known only from the capability's own design (confirmed in the `CHI-33` kickoff's Jordan prompt: `delegate_to_agent` targeting `agent_id "alex"`, `is_final: true`) — is who actually completes it, and nothing in the response tells the frontend that. There was no existing template for this shape, so it was never written.

**The fix (John's explicit call, this design session):** make declaring "who completes this and what to call it" a *required* part of every `callCapability()` call, not an optional add-on a caller can forget — closing the gap structurally, not just patching this one site. Built and proven in isolation first (Task 1, Node-tested, zero production wiring), then migrated onto the 3 existing call sites with a live before/after regression check across all 23 real seed questions (Task 2), then finally used to fix `fetchNewsCards()` itself (Task 3) — no count-exclusion logic anywhere.

**Scope boundary, confirmed with John:** the *true* root cause is one layer deeper — the Harness's own live-orchestration mechanism (`ARCHITECTURE.md` §19h, `_onEvent` in `api/capabilities/execute.js`) never emits an explicit "this delegation just completed, here's the terminal agent" event, which is *why* every Screen has to reconstruct that fact client-side in the first place. That's a Harness-layer fix that would close this gap for every current and future Screen, not just Channel Intelligence — logged separately as `LOO-009` (`docs/FEATURES.md`), out of scope here. This session ships the Screen-layer mechanism only.

```js
// FEATURE: LOO-009/CHI-37 — resolves the hop-completion event(s) a callCapability() call produces,
// given its already-resolved result. Every caller must declare hopEvents (see callCapability below —
// enforced, not optional) instead of hand-writing a follow-up onEvent(buildHopEvent(...)) call, which
// is exactly the gap CHI-37 fell through (fetchNewsCards() was the one call site with no existing
// template to copy — see this doc's CONTEXT). Each hopEvents entry:
//   - type: the logged event type string (e.g. "qa_answer", "news_fetch")
//   - resolveAgentId: (result) => string|null — the completing agent's id, or null to skip this
//     entry entirely (covers the conditional "agent_selection" case: null when no internal hand-off
//     happened for this call)
//   - resolveData: optional (result) => any, defaults to the whole result — use to log a narrower
//     object (e.g. a hand-off's own reasoning, not the full answer payload)
function resolveHopEvents(hopEvents, result, t0) {
  const elapsed = Date.now() - t0;
  return hopEvents
    .map(({ type, resolveAgentId, resolveData }) => {
      const agentId = resolveAgentId(result);
      if (!agentId) return null;
      const data = resolveData ? resolveData(result) : result;
      const durationMs = NON_MEASURABLE_EVENT_TYPES.has(type) ? null : elapsed;
      return buildHopEvent(type, agentId, data, durationMs);
    })
    .filter(Boolean);
}
```

Modify `callCapability`'s signature and body to accept and use this generically:

```js
async function callCapability({ capability_slug, intent_slug, agent_id, task_context, runtime_context = null, format_skill_profile_slug = null, display_agent_id = null, onProgress = null, isStale = () => false, onEvent = null, hopEvents = null }) {
  // FEATURE: LOO-009/CHI-37 — structurally impossible to forget completion logging: a caller that
  // passes onEvent must also declare hopEvents. A caller with no interest in hop logging (none exist
  // today, but a future one might) simply omits both.
  if (onEvent && !hopEvents) {
    throw new Error(`callCapability: onEvent supplied without hopEvents for ${capability_slug}/${intent_slug} — every caller must declare how to resolve the completing agent(s). See LOO-009/CHI-37.`);
  }
  const t0 = Date.now();
  const res = await fetch("/api/capabilities/execute", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      capability_slug, intent_slug, agent_id, task_context, runtime_context,
      format_skill_profile_slug, display_agent_id,
      tenant_id: TENANT_ID,
      stream: !!onProgress,
    }),
  });
  if (!res.ok) throw new Error(`${capability_slug} ${intent_slug} failed: ${res.status}`);
  const first = onProgress ? await readSSEResult(res, onProgress) : await res.json();
  const result = await resolveInProgress(first, onProgress, isStale); // FEATURE: CHI-04
  if (result.status) return result;
  const unwrapped = { ...(result.content || {}), patterns_used: result.patterns_used || [] };
  // FEATURE: LOO-009/CHI-37 — fires generically, in place of every call site's old hand-written
  // follow-up. isStale() checked here (not left to the caller) for the same reason every existing
  // manual call site already checked it before firing: never log an event for a call a Clear has
  // already invalidated.
  if (onEvent && hopEvents && !isStale()) {
    for (const evt of resolveHopEvents(hopEvents, unwrapped, t0)) onEvent(evt);
  }
  return unwrapped;
}
```
