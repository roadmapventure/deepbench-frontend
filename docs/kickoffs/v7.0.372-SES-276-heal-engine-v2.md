## 5. TASKS

### Task 1 — Widen the inputs behind one shape

`heal-engine.js` currently has `fetchFailedHops()` feeding a signature-grouping step. Add sibling fetchers for `ci_run_conclusions` (a run whose `jobs` jsonb contains any `conclusion: "failure"`) and `runner_cycles` (`outcome = 'failed'`), and normalise all three into **one internal failure record** carrying at minimum: source stream, occurred-at, a signature, and a link back to the row.

**Keep `durable_hops`.** It is dead today, not retired — a stream that resumes must not need a code change to be seen again.

### Task 2 — Classify, and file only product failures

Every normalised record is classified **`product`** or **`process`**, and the classification and its reason are recorded on the record. **Only `product` records may file a heal ticket.** `process` records are counted and reported, never filed.

Start from what tonight actually demonstrated, and put each rule's evidence in a comment:
- A CI failure whose only failing job is a **known runner race** (e.g. the `CLAUDE-STATE` freshness check racing a cycle's own close — `SES-261`) is `process`.
- A CI failure that reproduces on a commit **the runner did not push** is `product`.
- A failure whose signature matches a ticket already `done` is a **candidate recurrence**, which is Task 3's business.

**Do not invent a confident classifier.** Where a record cannot be classified on evidence, mark it `unclassified` and report it — `unclassified` never files. Guessing here is how the engine heals ghosts.

### Task 3 — Fix-confirmation

v1 files a recurrence once and never learns whether the fix held. Add the second half:

- When a heal ticket's signature stops appearing for a defined window, record **confirmed-fixed** on that ticket.
- When it reappears after the ticket closed, record a **recurrence** against the original rather than filing a fresh duplicate.
- Persist this where it can be queried later — a table or columns, your call, but **it must be readable by `SES-303`'s outcome telemetry**, which is the ticket that will ask "did the fix move the metric."

State the window explicitly and derive it from a column or a named constant, **never a bare literal** — this codebase has paid for that three times (`SES-146`, `SES-269`).

### Task 4 — Prove it on real rows, then verify

The engine must run **read-only (no `--apply`)** against the live tables and report what it *would* file. Record in the ship note: how many records each stream produced, how many classified `product` / `process` / `unclassified`, and how many tickets it would have filed. **A run that would file zero is a legitimate and reportable result** — it is not a reason to loosen the classifier.

Then the new test, `node tests/regression/run-all.js` against the current **132/142** baseline, and `npm run build`.
