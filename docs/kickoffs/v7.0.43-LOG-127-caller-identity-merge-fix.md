## 2. CONTEXT

Two defects, found together, fixed together — both in `identityForRow()`/`buildIdentityIndex()`.

**Defect A — a fourth bucket nobody approved.** John's exact spec, mid-design: *"the UI in By Source broken up between three: me, you, and all others (grouped outside of you and i)."* The shipped code (`S-LOG-121b`) instead produces **four** — it splits the "everyone else" bucket by which host the request hit: `Public` for the production site, **`Internal (QA)`** for anything else (the dev preview). That distinction was never asked for and directly overshoots a rule John stated in absolute terms ("only three").

**Defect B — one label silently claims unrelated traffic.** `identityForRow()`'s third tier lets a row with no name of its own "borrow" a name from *any other row that shares its IP address*, with no check on whether that other row is even remotely the same caller. Verified live 2026-08-01: labelling one QA visitor `Claude (QA)` in `known_callers` caused the By Caller drawer to also claim, under that same name:
- **210 calls from John's own regression driver** — automated traffic, not a browser, at that address.
- **2 other distinct, unlabelled visitor ids** (88 and 34 calls respectively) — real browser visits nobody has identified, silently painted with a name that has no basis for them.

Root cause, read from the actual code (`src/hooks/useAIActivity.js` ~L708–716, ~L736–744, ~L751–771): `derivedNameByIp` is built by scanning every row for a `visitor_id` that matches a `known_callers` label, then recording `ip → name`. `identityForRow()` then applies that name to **any row sharing the ip**, regardless of that row's own `visitor_id` (even a *different*, real one) or `call_source` (even `regression`/`script`). The kickoff that shipped this (`v7.0.39`) only ever asked for the narrower case — a row whose `visitor_id IS NULL` because its cookie hasn't round-tripped yet inheriting the name of *its own later self* — and the harvest doc's own wording says exactly that (`docs/harvests/LOG-121.md`: "NULL there does not mean 'unknown person'... those rows must group by address"). The shipped code generalized past that into "any row at this address, ever," which is not what was specified.

**A second, narrower instance of the same root cause** — verified live at a different address, `xxx.xx.164.217`: one real mobile visit's first 2 requests (before its cookie returned) landed in one row (`ip:` key, labelled by org, "AS54113 Fastly, Inc."); the same visit's next 54 requests (cookie present) landed in a second row (`visitor:` key, labelled "Internal (QA)" by host). One caller, two rows — because the *narrow*, intended gap-bridging case (Defect B's inverse: a genuinely unlabelled visitor's own cookie-less first request never gets folded into that same visitor's later, cookie-bearing requests) was never implemented at all; only donation *from a `known_callers`-labelled name* existed.

**The fix for both is one corrected rule**, replacing the current unconditional IP-donation:

> A cookie-less `ui` request (`visitor_id IS NULL`, `call_source === 'ui'`) is folded into the *one* browser identity already seen at that exact `caller_ip_masked` + `request_host` pair — **but only when there is exactly one distinct `visitor_id`** on record for that address+host. Two or more distinct visitors sharing an address is exactly the case where donation must *not* guess — the row stays in its own address-keyed bucket instead. Never applies to a row that already carries its own (different) `visitor_id`. Never applies to non-`ui` traffic — `regression`/`script`/`session-test` are not a "visit" and must never inherit a human name.

This is strictly narrower than what shipped: it can only ever *reduce* the set of rows a name applies to, never expand it further. Verified by hand against both live examples below (Section 8's test encodes both as fixtures).

**Task 2 — `src/hooks/useAIActivity.js`: donation only bridges one unambiguous gap.**

In `buildIdentityIndex()`, replace the unconditional `derivedNameByIp` construction (~L736–744) with two data structures built from the **same single pass** over `rows`:

1. `uiVisitorsByIpHost: Map<'ip|host', Set<visitorId>>` — for every row where `call_source === 'ui'` and `visitor_id` is non-null, add that visitor id to the set keyed by `` `${ipKeyOf(row)}|${row.request_host || ''}` ``. Skip rows with no resolvable `ip`.
2. `soleVisitorByIpHost: Map<'ip|host', visitorId>` — derived from (1): for every key whose set has **exactly one** member, record that single visitor id. A key with 2+ distinct visitor ids gets **no entry** — that address+host is ambiguous, and ambiguous must never resolve to a guess.

In `identityForRow()`, replace the current three-tier `labelled` check (~L756–759) with:

```js
// Tier 1/2: an explicit known_callers label on THIS row's own visitor id or address always wins.
const directLabel = (vid && idx.nameByVisitor.get(vid)) || (ip && idx.nameByIp.get(ip)) || null;
if (directLabel) return { key: `name:${directLabel}`, name: directLabel, label: directLabel, ip, org, city };

// Tier 3: this row is genuinely the cookie-not-back-yet gap of ONE real visit -- fold it into
// that visit, but only when the address+host has exactly one candidate. Never fires for a row
// that already carries its own (different) visitor id, and never for non-'ui' traffic.
if (!vid && row?.call_source === 'ui' && ip) {
  const soleVid = idx.soleVisitorByIpHost.get(`${ip}|${host || ''}`);
  if (soleVid) {
    const soleLabel = idx.nameByVisitor.get(soleVid);
    const name = soleLabel || PUBLIC_CALLER;
    const key = soleLabel ? `name:${soleLabel}` : `visitor:${soleVid}`;
    return { key, name, label: name, ip, org, city };
  }
}
```

(`host` must be computed before this block, not after — move the existing `const host = row?.request_host || null;` line up.) The rest of `identityForRow()` (the `!ip && !vid` unattributed case, and the final `vid ? {...} : {...}` fallback for a still-unresolved row) is unchanged in shape, only the removed `PRODUCTION_HOST` comparison inside it (Task 1).

**Why "exactly one" and not "first one wins" (the removed code's actual behavior):** "first one wins" is precisely the mechanism that mis-attributed 210 regression calls and 2 real visitors to `Claude (QA)` — it doesn't check whether the donation target is genuinely the same visit, only whether *a* label exists anywhere at that address. "Exactly one distinct visitor" is the narrowest rule that still closes the real gap (Task 2's own motivating example — one visitor, one address, unambiguous) while making the over-broad case (many distinct visitors at one shared address, e.g. John's home network) structurally impossible to mis-resolve, because no entry is ever recorded for it.

// test-log-127.mjs — S-LOG-127 (v7.0.43). Categories B, F.
import assert from 'node:assert';
import { buildBySource, buildByCaller } from './src/hooks/useAIActivity.js';

const KNOWN = [{ match_type: 'visitor_id', match_value: '3dd1a039-1a5c-4fe9-ac42-9144648fc58f', display_name: 'Claude (QA)' }];
const ORGS = [
  { caller_ip_masked: 'xxx.xx.33.12', org: 'AS16591 Google Fiber Inc.', city: 'Austin' },
  { caller_ip_masked: 'xxx.xx.164.217', org: 'AS54113 Fastly, Inc.', city: 'Austin' },

const DEV_HOST = 'deepbench-frontend-git-dev-roadmapventures-projects.vercel.app';
const row = (over) => ({ call_source: 'ui', caller_ip_masked: null, visitor_id: null, request_host: DEV_HOST, device_type: 'desktop', model: 'claude-haiku-4-5', cost: 0.01, ts: '2026-08-01T20:00:00Z', ...over });

// ---- Fixture 1: John's shared home address. 9 distinct real-world groups, reproduced from the
// live query this session ran. Only ONE of the 5 distinct visitor ids at this address is labelled.
const HOME = 'xxx.xx.33.12';
const homeRows = [
  ...Array.from({ length: 616 }, () => row({ caller_ip_masked: HOME })),                                    // cookie-less ui gap, AMBIGUOUS address (5 distinct visitors below) -- must NOT resolve to Claude
  ...Array.from({ length: 210 }, () => row({ caller_ip_masked: HOME, call_source: 'regression', visitor_id: null })), // regression -- must NEVER inherit a human name
  ...Array.from({ length: 202 }, () => row({ caller_ip_masked: HOME, visitor_id: '3dd1a039-1a5c-4fe9-ac42-9144648fc58f' })), // the ONE labelled visitor
  ...Array.from({ length: 88 },  () => row({ caller_ip_masked: HOME, visitor_id: 'cc966bd6-cc88-47ce-9ecc-a95f1945a149' })), // distinct, unlabelled -- must stay separate
  ...Array.from({ length: 34 },  () => row({ caller_ip_masked: HOME, visitor_id: 'f26de17f-ae10-479a-b294-f68db47da2db' })), // distinct, unlabelled -- must stay separate
];

const homeSource = buildBySource(homeRows, KNOWN, ORGS);
const homeCaller = buildByCaller(homeRows, KNOWN, ORGS);

// -- Defect A: no fourth bucket, ever.
assert.ok(!homeSource.some(s => /Internal/i.test(s.source)), 'Internal (QA) must be gone -- John asked for exactly three');
assert.ok(!homeCaller.some(c => /Internal/i.test(c.label)), 'Internal (QA) must be gone from By Caller too');

// -- Defect B, the actual bug: "Claude (QA)" must hold ONLY the 202 calls from its own labelled
// visitor. This is the discriminating assertion -- the old code reports 962-ish (everything at
// the address); anything above 202 here means the over-merge survived.
const claude = homeCaller.find(c => c.label === 'Claude (QA)');
assert.ok(claude, 'the labelled visitor must still produce a Claude (QA) row');
assert.equal(claude.calls, 202, `Claude (QA) must hold exactly its own 202 calls, got ${claude.calls} -- regression/other-visitor traffic leaked in`);

// -- regression traffic must never carry a human name, in either section.
const regressionSource = homeSource.find(s => s.source === 'Regression');
assert.ok(regressionSource, 'Regression must still be its own By Source row');
assert.equal(regressionSource.calls, 210);
// in By Caller, the 210 regression rows must NOT be inside the Claude (QA) bucket (already proven
// by the calls===202 assertion above) -- confirm they exist somewhere else instead of vanishing.
const totalCallerCalls = homeCaller.reduce((n, c) => n + c.calls, 0);
const totalSourceCalls = homeSource.reduce((n, c) => n + c.calls, 0);
assert.equal(totalCallerCalls, totalSourceCalls, 'the two sections must still reconcile exactly after the fix');
assert.equal(totalCallerCalls, 1150, 'no row may be dropped by the corrected logic (616+210+202+88+34=1150)');

// -- the two distinct unlabelled visitors must NOT merge into Claude (QA) or into each other.
const cc = homeCaller.find(c => c.calls === 88);
const f26 = homeCaller.find(c => c.calls === 34);
assert.ok(cc && f26 && cc !== f26, 'the two other distinct visitors must remain separate rows');
assert.notEqual(cc.label, 'Claude (QA)');
assert.notEqual(f26.label, 'Claude (QA)');

// -- the ambiguous 616-call gap (5 distinct visitors share this address) must NOT guess -- it
// lands in its own address-keyed row, never silently attributed to Claude (QA) or anyone else.
const ambiguousGap = homeCaller.find(c => c.calls === 616);
assert.ok(ambiguousGap, 'the ambiguous cookie-less gap must still appear as its own row, not be dropped');
assert.notEqual(ambiguousGap.label, 'Claude (QA)', 'an ambiguous address must never resolve to a specific name');

// ---- Fixture 2: the mobile visit, reproduced exactly -- ONE real visitor id at this address, so
// the gap SHOULD merge (this is the case the mechanism exists for).
const MOBILE_IP = 'xxx.xx.164.217';

];
const mobileCaller = buildByCaller(mobileRows, [], ORGS);
assert.equal(mobileCaller.length, 1, `one real visit must render as ONE row, got ${mobileCaller.length}`);
assert.equal(mobileCaller[0].calls, 56, 'the merged row must hold all 56 calls from both halves of the visit');

// ---- A single distinct visitor id with NO gap-filling needed still resolves correctly (no
// regression in the ordinary case).
const solo = buildByCaller([row({ caller_ip_masked: 'xxx.xx.9.9', visitor_id: 'aaa' })], [], []);
assert.equal(solo.length, 1);
assert.equal(solo[0].label, 'Public');
