## CONTEXT

**One root architectural gap, two live-confirmed symptoms, found via direct `durable_hops`/`ai_activity_log` evidence during a live user question on the Channel Sales Intelligence screen, not guesswork.**

Nested delegate calls (`request_help`'s call into `project-manager`/`agent-selection-intent`, `delegate_to_agent`'s call into whichever agent the model named) inherit the **outer call's own shrinking deadline** (`_deadline: deadline`, passed unchanged at both call sites) rather than getting a fresh budget. Today, the harness fires `onEvent` (announcing the delegation) and dispatches the nested call *immediately* after the model decides — with no check that there's actually enough remaining budget for that nested call to finish. Two things go wrong when it doesn't:

1. **`AA-185` (already logged, unfixed):** if the nested call itself checkpoints mid-flight, the outer call also checkpoints (existing `AA-141` guard). On `continue`, `resumeCapability()` re-enters `runLoop()` from the persisted `conversation_history` — which re-asks the model for a turn it already answered. The model frequently repeats the same tool call, re-firing an identical `onEvent`. That's the duplicate "Owen is routing this to Nadia…" row John saw twice back-to-back.
2. **`AA-187` (new, found this session):** the nested call's own partial work is never resumed — `durable_hops` confirms this directly. Two orphaned rows from the live repro (`8b285839…`, Marcus's `ci-answer-intent`, `hop_counter: 2`; `233c1c9d…`, Nadia's `data-analysis`, `hop_counter: 3`) were created, patched once, and never touched again. On the outer resume, the nested delegate is invoked **fresh from zero** — this was an accepted `AA-141` tradeoff, justified at the time by "delegate turns observed in production run 1-9s." That assumption is false for these two call sites: Marcus's own answer-generation turn and Nadia's `data-analysis` turn are real 12-45s LLM calls. Redoing them from scratch on every checkpoint is real wasted latency and real wasted Anthropic spend, and it's the dominant contributor to the ~2.5-minute total time and inflated Agent Routing drawer count John saw on this one question.

**The fix:** move the budget check to *before* dispatch, not after. If there isn't enough remaining budget to plausibly complete the nested call, checkpoint the outer call **right there** — before `onEvent` fires, before the nested call starts — persisting the already-decided delegation (`via_tool`, the model's own `tool_input`, `tool_use_id`) in a new `pending_delegation` column. On resume, if `pending_delegation` is present, dispatch it directly with a fresh full budget — no re-asking the model, no re-firing `onEvent`, no partial nested work ever started until there's a real budget to finish it. One decision, one `onEvent`, one nested call, however many checkpoints it takes to get there.
