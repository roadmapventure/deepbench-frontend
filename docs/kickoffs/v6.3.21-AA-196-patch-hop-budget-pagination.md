## 1. CONTEXT

`S-ARCH-HOP-BUDGET-01` (v6.3.19, shipped and merged to `dev` earlier this session) requested `limit=3000` rows from `ai_activity_log` to build its per-capability/intent latency cache. Its own live Category L test caught a real anomaly (`data-room-custody` falling back to the flat constant despite real data existing), which the design session then root-caused directly against the live REST endpoint: **this Supabase project's PostgREST silently caps a single request's response at 1000 rows, regardless of a higher `limit=` query parameter.** Confirmed live: `Content-Range: 0-999/3868` was returned for the exact `limit=3000` request the shipped code makes. No error, no warning — the request just silently returns fewer rows than asked for.

**Concrete impact, verified live before this patch:** `getHopBudgetReserveMs('data-room-custody', null)` returns the unchanged fallback (`35000`) in production right now, even though 21 real, recent (2026-07-08 through 2026-07-14, all within the intended window) samples exist with `p99: 46168` — because those 21 rows are older than the current 1000-row cutoff (2026-07-14 01:53), which is now the effective window instead of the intended ~3000. This is exactly the capability class (`AA-196`'s own "under-reserved" finding) this whole feature exists to protect — the bug silently defeats the fix for precisely the cases that motivated it.

**Fix, John's explicit call (Option 1 — fetch everything, not a fixed bounded window):** the table has only 3868 total `agent-turn` rows with `latency_ms` today — small enough to fetch in full via pagination rather than guessing a single-request size that may or may not exceed the server's own cap. Paginate in pages of 1000 (the server's real per-request ceiling) until a page returns fewer than 1000 rows (no more data) or a safety bound (10 pages / 10,000 rows) is hit — comfortably covers "fetch everything" at today's and near-future scale without risking an unbounded loop if the table grows unexpectedly large later.

### Task 1 — `api/capabilities/execute.js`: paginate `refreshHopEstimateCache()` instead of a single capped request

Currently:
```js
async function refreshHopEstimateCache() {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  const res = await fetch(
    `${supabaseUrl}/rest/v1/ai_activity_log?ai_type=eq.agent-turn&latency_ms=not.is.null&select=feature,latency_ms&order=created_at.desc&limit=3000`,
    { headers: { apikey: supabaseKey, Authorization: `Bearer ${supabaseKey}` } }

    (byKey[key] ||= []).push(row.latency_ms);
  }

  for (const [key, latencies] of Object.entries(byKey)) {
    if (latencies.length < HOP_ESTIMATE_MIN_SAMPLES) continue;
    estimates[key] = percentile(latencies, 0.99);

```

Replace with:
```js
// FEATURE: AA-196 patch (S-ARCH-HOP-BUDGET-01-patch) -- a single request's `limit=3000` was
// silently truncated to 1000 rows by this Supabase project's own PostgREST cap (confirmed live,
// Content-Range: 0-999/3868 returned for the original request), excluding older-but-still-real
// samples for infrequently-called capabilities (data-room-custody's 21 real samples, dated
// 07-08 through 07-14, all fell outside the resulting 1000-row window) -- silently defeating
// the fix for exactly the capabilities it exists to protect. Paginate instead: the table has
// ~3900 total agent-turn rows today, small enough to fetch in full. MAX_PAGES is a safety bound
// (10,000 rows), not a targeted window -- stops when a page returns fewer than PAGE_SIZE rows
// (no more data) well before that bound in practice.
async function refreshHopEstimateCache() {
  const supabaseUrl = process.env.SUPABASE_URL;
  const supabaseKey = process.env.SUPABASE_SERVICE_KEY;
  const headers = { apikey: supabaseKey, Authorization: `Bearer ${supabaseKey}` };
  const PAGE_SIZE = 1000; // this project's real per-request PostgREST cap, confirmed live 2026-07-16
  const MAX_PAGES = 10;
  let rows = [];
  for (let page = 0; page < MAX_PAGES; page++) {
    const res = await fetch(
      `${supabaseUrl}/rest/v1/ai_activity_log?ai_type=eq.agent-turn&latency_ms=not.is.null&select=feature,latency_ms&order=created_at.desc&offset=${page * PAGE_SIZE}&limit=${PAGE_SIZE}`,
      { headers }
    );
    if (!res.ok) throw new Error(`Failed to load ai_activity_log for hop estimates (page ${page}): ${res.status}`);
    const pageRows = await res.json();
    rows = rows.concat(pageRows);
    if (pageRows.length < PAGE_SIZE) break;
  }
  const byKey = {};
  for (const row of rows) {
    if (!row.feature) continue;
    const key = row.feature.split(':').slice(0, 2).join(':'); // capability_slug:intent_slug, strips :depthN/:apiRetryN
    (byKey[key] ||= []).push(row.latency_ms);
  }
  const estimates = {};
  for (const [key, latencies] of Object.entries(byKey)) {
    if (latencies.length < HOP_ESTIMATE_MIN_SAMPLES) continue;
    estimates[key] = percentile(latencies, 0.99);
  }
  _hopEstimateCache = estimates;
  _hopEstimateCacheAt = Date.now();
}
```

**Why this design, not bigger:** still zero migration, zero new column/table/function, same cache/TTL/fallback structure — the only change is how the raw rows get fetched. `getHopBudgetReserveMs()` itself, the two `runLoop()` call sites, and every other part of `S-ARCH-HOP-BUDGET-01` are untouched.

import assert from 'node:assert';

// Pagination termination logic is pure and testable as a spec -- the Category L test below is
// what proves the real refreshHopEstimateCache() actually retrieves all real rows.

function paginationPageCount(totalRows, pageSize, maxPages) {
  let pages = 0;
  let fetched = 0;
  while (pages < maxPages) {
    const thisPage = Math.min(pageSize, totalRows - fetched);
    fetched += thisPage;
    pages++;
    if (thisPage < pageSize) break;
  }
  return { pages, fetched };
}

// --- Test 1: fewer rows than one page -- stops after page 1 ---
{
  const r = paginationPageCount(400, 1000, 10);
  assert.equal(r.pages, 1);
  assert.equal(r.fetched, 400);
}

// --- Test 2: real table size (~3868 rows) -- stops after 4 pages, well under MAX_PAGES ---
{
  const r = paginationPageCount(3868, 1000, 10);
  assert.equal(r.pages, 4);
  assert.equal(r.fetched, 3868);
}

// --- Test 3: exactly a multiple of page size -- one extra (empty) page confirms termination ---
{
  const r = paginationPageCount(2000, 1000, 10);
  assert.equal(r.pages, 3); // 1000, 1000, then a 0-row page breaks the loop
  assert.equal(r.fetched, 2000);
}
