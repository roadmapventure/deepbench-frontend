## 2. CONTEXT

### The problem, in one sentence

A CHI regression run reads whatever the previous run left behind, so two runs are not comparable.

### Measured live, 2026-07-29 (not recalled — re-verify any of it before relying on it)

`the_library`, `apple-cso-data-room`, 96 rows total:

|---|---|

| — of those, `status='superseded'` (invisible to retrieval) | **4** |
| `is_baseline=false`, `status='active'` (retrievable leftovers) | **14** |

The 4 hidden seed scenarios: Elevate Mobility (India), Horizon Store (Vietnam), Nordholm Retail
Group (EMEA), Vitrine Tech (Brazil). Each was retired by a legitimate agent supersede during a
regression run — the most recent at 2026-07-29 17:24.

The 14 retrievable leftovers are **entirely test residue and run exhaust**: 2 titled
`DAT-7 End-to-End Live Test — Loop-Closure Confirmed` and `DAT-11 atomicity target`, plus 12
agent-authored `consolidated` rows — **five of which are near-duplicate restatements of one
`upgrade-cycles` answer**, all created 2026-07-29. None of the 14 is demo content.

`match_the_library` filters `status = 'active'` and `limit match_count` (default 5). So run N+1's
`upgrade-cycles` question competes against five copies of run N's own answer for five slots, and
`elevate-mobility` cannot reach its seed scenario at all.

### Why this is not a reset

**John's explicit constraint, 2026-07-29, stated twice:** *"We don't want to change existing data
flow that is working data. That will be a fail."* A regression run must not mutate The Library.
`bulk_reset` is therefore off the table — not because it is broken (it works; 5 lifetime calls, all
2026-07-02), but because mutating shared working data to make a test repeatable is a failure
condition. Demo Reset stays where it belongs, unbuilt, on `MI-08`.

**John's design, adopted:** the regression reads only rows carrying the original tag. `is_baseline`
already *is* that tag — it needs no adding, only reading. Retrieval currently reads `status` and
ignores the tag entirely, which is why the four retired scenarios vanish despite still being tagged.

**Why this beats a reset on the merits** (the argument that settled it): a read scope mutates
nothing, so a run cannot disturb the live screen, cannot be disturbed by concurrent sessions
writing to The Library, and does not have to be scheduled around the demo. Under a reset, a run
would rewrite the corpus another session was reading — anyone on CHI would watch their Data Room
drop from 30 rows to 20 mid-session. Verified property: with a read scope, any number of concurrent
sessions may write during a run, because the run reads only tagged rows and every write lands
untagged.

### Why this is a platform capability, not a test flag

`lib/vector-search.js` is the registered platform service **Embedding Engine**
(`embedding-engine`, layer `platform`). `SCA-1` already generalized it from a hardcoded
`dataRoomTag`/`p_data_room_tag` pair into a generic `scopeParam`/`scopeValue` pair *specifically*
so one primitive could back more than one kind of scoping; `lib/conversations.js:46` is its second
consumer (`p_session_id`). This is the third. Retrieval scope is therefore an existing, proven
platform concern being extended — not a parallel mechanism, and not a test hook wearing production
clothes. Verified against fresh `origin/dev` immediately before this doc was written: no
`retrieval_scope` or `baseline_only` exists anywhere in `lib/`, `api/`, or `scripts/`.

### Naming (John approved, 2026-07-29)

`retrieval_scope`, value `"baseline"`. Chosen to match the `scopeParam`/`scopeValue` vocabulary
already in `vector-search.js` rather than invent a term. Absent/null means today's behavior.

## 4. STUB DEFINITIONS

**The Supabase function, after the change.** Current definition verified live 2026-07-29; the only
edits are the appended parameter and the `where` clause's first line. Everything else is verbatim.

```sql
CREATE OR REPLACE FUNCTION public.match_the_library(
  query_embedding vector,
  match_threshold double precision DEFAULT 0.3,
  match_count integer DEFAULT 5,
  p_tenant_id text DEFAULT 'global'::text,
  p_data_room_tag text DEFAULT NULL::text,
  p_retrieval_scope text DEFAULT NULL::text   -- appended last; existing callers unaffected
)
RETURNS TABLE(id uuid, title text, content text, category text, jurisdiction text,
  priority integer, triggers text[], status text, tenant_id text, data_room_tag text,
  teaching_note text, data_type text, citeable boolean, confidence text, similarity double precision)
LANGUAGE sql STABLE
AS $function$
  select
    id, title, content, category, jurisdiction,
    priority, triggers, status, tenant_id, data_room_tag,
    teaching_note, data_type, citeable, confidence,
    1 - (embedding <=> query_embedding) as similarity
  from the_Library
  where (case when p_retrieval_scope = 'baseline'
              then is_baseline is true
              else status = 'active' end)
    and (tenant_id = p_tenant_id or tenant_id = 'global')
    and data_room_tag = p_data_room_tag
    and 1 - (embedding <=> query_embedding) > match_threshold
  order by embedding <=> query_embedding
  limit match_count;
$function$
```

`is_baseline is true` (not `= true`) so a null never silently passes. **`RETURNS TABLE` is
unchanged** — do not add `is_baseline` to it; nothing downstream reads it and an unused returned
column is dead weight.

**Validation lives in JS, not SQL.** The function handles exactly two states: `null` → today's
`status='active'` behavior; `'baseline'` → the tag. Any *other* value must never reach it — see
Task 2's guard. A typo silently falling through to today's behavior is the failure mode that guard
exists to prevent.
