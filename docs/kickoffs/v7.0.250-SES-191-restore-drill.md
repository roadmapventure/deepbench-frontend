## What the drill found — two fatal defects, both by executing

`schema.sql` cannot rebuild the database on a clean project. Either defect alone is fatal:

| # | Defect | Failure |
|---|---|---|
| 1 | `ai_activity_log.id` / `tasks.id` default to `nextval(...)`; **no `CREATE SEQUENCE` anywhere in the set** | `relation "ai_activity_log_id_seq" does not exist` |
| 2 | The two `GENERATED ALWAYS … STORED` columns emitted as `DEFAULT <expr>` | `cannot use column reference in DEFAULT expression` — kills the whole `CREATE TABLE` |

Both confirmed against the live source before being called defects: `pg_class` shows 2 owned
sequences; `information_schema.columns` shows `is_generated = ALWAYS`, `has_default = false` on
`ai_activity_log.caller_ip_masked` and `ip_org_cache.caller_ip_masked`.

**The root cause is the VIEW, not the script — and this is the thing to get right.** Schema DDL is
generated server-side by `public._backup_schema_ddl` and pulled verbatim by `dump-supabase.mjs`.
Patching the script would have changed nothing. The view's `CASE` handled `a.attidentity` and never
`a.attgenerated`, and it had no sequences branch at all. Fixed in migration
`ses191_backup_schema_ddl_sequences_and_generated_cols`, before-image first.

**Sequences are emitted with `START WITH last_value + 1`, not bare.** A bare `CREATE SEQUENCE`
restores at 1 and looks correct until the first insert collides with the rows the restore just
loaded — superficially working, wrong exactly where it costs.
