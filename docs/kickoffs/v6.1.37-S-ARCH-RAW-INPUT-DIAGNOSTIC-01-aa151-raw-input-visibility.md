## CONTEXT

Per John's standing rule ([[feedback-no-blind-fixes]] — no fix ships without root-cause measurement first), the next step on `AA-151` is to actually see what the model's raw JSON looks like on a failing `agent-selection-intent` call, not guess again. `AI-47`'s fix (v6.1.33, shipped) proved budget isn't the constraint (output_tokens 565-1062, nowhere near the cap) — but that only tells us the model *had room*, not *what it produced instead of the required field*.

Confirmed by direct code read: `parseModelTurn()` (`request-receivable.js` ~line 106) already has the model's raw partial `tool_input` in scope at the exact point it detects a missing required field (`toolUseBlock.input`) — but the thrown error only carries the list of missing key names (`Schema tool "X" called with missing required field(s): Y`), never the raw input itself. That data is discarded, not persisted or logged anywhere. This is a one-line diagnostic gap with a known, understood cause — not a new investigation.

Fixing this makes the raw input visible via the same `.detail` plumbing `AA-157`/`AA-158` already built and shipped (retry-rejection detail → HTTP response `.detail` field) — no new mechanism, just carrying one more piece of already-in-scope data through an existing pipe.

## TASKS (1)

### Task 1 — `api/prompt/request-receivable.js`: attach the raw partial `tool_input` to the missing-field error, surface it in the final 422's `.detail`

**Part A — `parseModelTurn()` (~line 106-125), attach `rawInput` to the thrown error:**

Currently:
```js
      const missing = required.filter(key => !(key in (toolUseBlock.input || {})));
      if (missing.length > 0) {
        throw new Error(`Schema tool "${schemaTool.name}" called with missing required field(s): ${missing.join(', ')}`);
      }
```

Change to:
```js
      const missing = required.filter(key => !(key in (toolUseBlock.input || {})));
      if (missing.length > 0) {
        throw Object.assign(
          new Error(`Schema tool "${schemaTool.name}" called with missing required field(s): ${missing.join(', ')}`),
          { rawInput: toolUseBlock.input }
        );
      }
```

**Part B — `callModel()`'s retry-catch (~line 230-233), include `rawInput` in the final `.detail` when present:**

Currently:
```js
      try {
        turn = parseModelTurn(llmData, hasSchemaTool, schemaTool);
      } catch (retryParseErr) {
        throw Object.assign(new Error('Parse failed and retry also failed'), { status: 422, detail: retryParseErr.message });
      }
```

Change to:
```js
      try {
        turn = parseModelTurn(llmData, hasSchemaTool, schemaTool);
      } catch (retryParseErr) {
        const detail = retryParseErr.rawInput
          ? `${retryParseErr.message} | raw_input: ${JSON.stringify(retryParseErr.rawInput)}`
          : retryParseErr.message;
        throw Object.assign(new Error('Parse failed and retry also failed'), { status: 422, detail });
      }
```

No other throw site changes — the *first* attempt's parse failure (the outer catch, ~line 182) only triggers the retry internally and is never surfaced to the client directly, so it doesn't need this (it would be redundant: if the first attempt also had a missing field, we only care what the *retried* attempt produced, since that's what the user-facing error reports).
