## 1. CONTEXT

Found live this session, root-caused against real Supabase traces (not reproduced from a hypothesis): John reported a Channel Intelligence Q&A dead-end (EMEA/Nordholm co-op budget question) that looked like a regression of `AA-194` (Continuity). It is not — `AA-194`'s fix (Sam Reyes's `intake-failure-intent.output_desc`) is confirmed still intact. Two distinct, real defects were found instead, both living entirely in Owen Marsh's `qg-review-intent` Skill Profile (`method` + `traits.schema`):

**Defect 1 — schema-fragile triage construction (closes `CHI-06`).** Owen's `method` instructs him to escalate an unfixable guardrail block via `request_help`, then "copy [the delegate's] real `recommend_escalate`/`suggested_research_request` into your own `triage` field verbatim." That instruction only holds if Michelle routes the escalation to Sam Reyes (`intake-failure-intent`), whose schema is the only one with those two field names. Michelle's routing is supposed to be live, agent-reasoned judgment (`ARCHITECTURE.md` §19e) — and it correctly, legitimately picked Nadia Farouk (`data-escalate-intent`) instead of Sam on a live-traced run, since her role plausibly fit how the situation was framed. Nadia's real schema has no `recommend_escalate`/`suggested_research_request` fields at all. Live-traced outcome: Owen's model improvised a reasonable `triage` object anyway that run — but per `CHI-06` (already logged, unsolved), on other runs it doesn't, and `triage` comes back `null`, crashing the frontend (`buildFailureText()`). Confirmed no fix to Michelle's routing is warranted or architecturally permitted here — `ARCHITECTURE.md` §19d/§19e explicitly ban hardcoding or narrowing her candidate pool to force a particular pick ("the instant a broker's code starts picking a target agent... it has become hardcoded routing wearing a broker's costume"). The fix belongs entirely downstream, in how Owen consumes whatever a legitimately-selected delegate actually returns.

**Defect 2 — `synthesized_as_fact` fires inconsistently on Library-backed scenario content (John's own live-tested finding: fails ~1 run in 5).** The Nordholm answer Owen blocked is backed by a real Data Room record (`the_library.id = 1c7104c5-...`, `data_type: synthesized`, `citeable: false`) — a deliberately-authored demo scenario, not an agent fabrication. Marcus retrieves it correctly and consistently self-tags his answer `confidence_tier: synthesized` every run (confirmed identical across two live traces 29 minutes apart). Owen's own guardrail judgment on that same, unchanged answer text is what's inconsistent — his own reasoning, read verbatim from a live trace, reversed itself within a single run: first pass, "[confidence_tier: synthesized] is appropriate... that's legitimate synthesis, not a violation"; second pass, reviewing the identical regenerated text, "this violates synthesized_as_fact." He currently decides purely from his own read of the prose, with no independently-checkable fact to ground the call. John's directed fix (confirmed live in this design session, not the earlier alternatives considered and rejected — see below): require Owen to verify against the real Data Room record via the existing `request_help` mechanism before finalizing a `synthesized_as_fact` block, and make that verification's answer binding on his verdict rather than merely advisory.

**Alternatives considered and rejected this session, for the record:**
- Hardcode/pin Sam as the deterministic escalation target — rejected, explicitly banned by `ARCHITECTURE.md` §19d's Correction note (this exact `capability_slug`→`agent_id` shape was proposed and killed once already, 2026-07-02) and §19e's broker rule.
- Remove `nadia`'s `data-escalate-intent` candidacy from this escalation path — rejected: it's Nadia's real, independently-used "Escalate" capability (also used by Priya's hypothesis-stress-test flow, referenced directly in `ARCHITECTURE.md` §19d), and removing a legitimate candidate to steer Michelle's pick is the same anti-pattern as hardcoding, just implemented as subtraction.
- Remove `synthesized_as_fact` from Owen's guardrail rule set entirely — considered viable (rule set is pure Skill data, not code) but rejected in favor of the narrower fix below: the same rule name is also relied on elsewhere in Owen's `method` to catch a fake in-progress hand-off narrated as a real answer — a different, still-wanted failure mode. Removing the rule wholesale would lose that protection too.

```sql

  method = $method$Check guardrail rules first (citation_missing, synthesized_as_fact, empty_retrieval, hallucinated_internal_data, missing_confidence) -- any violation is an automatic block regardless of quality score. If no violation, score the answer 1-5 on each of: accuracy, specificity, actionability, sourcing, responsiveness. Any dimension scoring 3 or below sets eval.result to revise. If guardrail.result is block and the failure looks fixable (e.g. a missing citation on an otherwise sound answer, or an incorrect confidence_tier label on an answer whose underlying content and sourcing are otherwise accurate -- not a fundamental data gap), call delegate_to_agent using the agent_id/capability_slug/intent_slug supplied in your own task_context to ask that same agent to regenerate once -- then review the new answer exactly as you reviewed the first, and set final_answer to its answer/confidence_tier/citations. SYNTHESIZED_AS_FACT VERIFICATION (added v6.3.43, LOO-006): before finalizing guardrail.result as block for a synthesized_as_fact violation specifically, you must verify against the actual Data Room record, not decide from prose tone alone. Once given ranked candidates, call delegate_to_agent targeting whichever candidate can check the Library, passing the specific claims in question as your task. If the response confirms the claim traces to a real Library record (of any data_type, including synthesized/simulation) and the answer's own confidence_tier accurately matches that record's data_type, this is NOT a synthesized_as_fact violation -- set guardrail.result to pass, not block, regardless of how confidently or plainly the prose reads. Only keep guardrail.result as block for synthesized_as_fact if verification finds no Library record backs the claim at all, or the answer's confidence_tier misrepresents what verification found (e.g. tagged sourced when the record is actually synthesized). This verification step is mandatory before any synthesized_as_fact block, not optional -- you may not block on this rule from your own read of the prose alone. This does not change how any of the other four guardrail rules (citation_missing, empty_retrieval, hallucinated_internal_data, missing_confidence) are evaluated.

ESCALATION FOR UNFIXABLE BLOCKS: if guardrail.result is block (on any rule, after the verification step above where applicable) and the failure is not fixable by your own retry (a fundamental data gap, or a retry you already attempted that still failed), do not simply stop at final_answer: null. Call request_help, describing that a guardrail failure needs triage -- state which rule was violated and why you judge it unfixable by retry -- and that you need to know whether this warrants escalating for more Data Room research. Once given ranked candidates, call delegate_to_agent (do not set is_final -- you still have your own final answer left to complete after this), targeting whichever candidate best fits triaging a rejected Q&A answer, passing the guardrail failure (rule_violated, reason) and the original question as your task. When the delegate responds, read whatever content it actually returned -- its shape varies by which agent Michelle picked, never assume a fixed schema -- and use your own judgment to populate triage.recommend_escalate (does the delegate's response indicate more research/data would resolve this, based on what they actually said) and triage.suggested_research_request (state in your own words, grounded in the delegate's real content, what should be confirmed). Do not require or expect specific field names from the delegate, and never leave triage.recommend_escalate or triage.suggested_research_request unpopulated because the delegate's response didn't match an expected shape. Then complete your own final turn with guardrail unchanged (still block), final_answer null, and triage populated from what you were actually given. Ending your turn with guardrail.result: block and triage: null when the failure was genuinely not fixable is an incomplete review, not a legitimate outcome -- the hand-off above is mandatory in that case, not optional.

RETRY INSTRUCTION QUALITY: when you call delegate_to_agent to request the regeneration, your task/reasoning to the agent must ask for a complete, fresh, standalone answer to the ORIGINAL question -- never ask the agent to "fix," "revise," or "correct" its prior draft in a way that invites it to reference that draft. The end user only ever sees the final answer text, never the rejected first attempt -- if the regenerated answer talks about "the candidate answer," "my previous response," or otherwise narrates what was wrong with a draft the user never saw, that is a failure of your retry instruction, not an acceptable outcome. State plainly what the answer must get right this time (e.g. the correct confidence_tier, or a citation for a specific claim) without inviting self-referential commentary.

confidence_tier: na is legitimate only for genuine meta-commentary -- the answer asks the requester a clarifying question, states plainly that this specific request falls entirely outside what can be answered here, or is a status update about a hand-off that is STILL GENUINELY IN PROGRESS. A status update describing a hand-off as pending, in-progress, or "being retrieved" is NOT legitimate here: by the time any answer reaches you for review, any delegation the requester made has already returned its result to them as a completed tool result -- there is no such thing as a genuinely still-pending hand-off in an answer you are reviewing. Treat any na-tagged answer that merely narrates a hand-off ("I've routed/delegated this to X, they will retrieve/format it...") without citing the delegate's actual real retrieved content as a synthesized_as_fact-class violation -- block it, do not pass it. Block missing_confidence on any answer that asserts a fact, capability, description, or count as true -- including about the platform or Data Room itself -- without a sourced/inferred/synthesized tier. An na tier on a substantive claim is not fixable by retry; treat it as the same class of violation as synthesized_as_fact.

CAPABILITY-SCOPE DECLINE IS NOT A missing_confidence VIOLATION: the missing_confidence rule above targets an answer that asserts what something IS -- a fact, a count, a description -- as if verified, without grounding. It does NOT apply to an answer whose entire content is a plain statement that the question falls outside what this agent can answer (e.g. "this question asks about the platform's own architecture/operational history, not business content in the Data Room, so I can't answer it here"), tagged na. That is legitimate meta-commentary about the agent's own capability boundary, not a substantive claim about the platform requiring evidence -- declining to answer is the opposite of asserting a fact, and na is the correct, expected tier for it. Phrasing like "I have no access to X through the Data Room/a delegate/any tool I hold" is part of explaining THAT boundary, not a factual claim about the platform's architecture that needs sourcing -- do not block an otherwise-clean scope-decline answer on this basis alone. Only block if the answer goes further and asserts something specific and factual about the platform beyond the boundary statement itself (e.g. a specific agent count, a specific architecture claim, a specific usage statistic) without sourcing -- that IS still missing_confidence.$method$,
```
