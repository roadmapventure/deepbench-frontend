## 2. The design, and why this layer

The fix is one Skill row: `jm-linkedin-alerts-intent` gains `what_they_sell` on the job item, an `allOf`/`if`-`then` making `competitor_why` and `what_they_sell` required exactly when `competitor` is true, and a method sentence naming both fields and the refusal.

- **pattern:7 / pattern:8** - fix agent behaviour in the agent's own Skill content, at the narrowest layer that works. `assemblePrompt()` renders that row on every `--render` (§19b), so the sub-agent is told on the next run, attended or scheduled, with no code change and no routine edit.
- **pattern:10** - the conditional lives in the schema the render prints, not only in prose. Two guards, and neither asks the model to remember a rule the contract does not state. A flat `required` was rejected: it would refuse every non-competitor job, which is most of them.
- **pattern:2** - `what_they_sell` is not defaulted in code. A code default would be an invented fact about a company; the only honest source is the page the model read.
- **pattern:93 / the AGT-154 precedent** - `docs/design/agt-154-linkedin-alerts-seed.sql` is left alone. It is a dated snapshot that `agt-84` part (i) pins hard (3 fable rows, the `'claude-fable-5-1', 12000, NULL,` tuple, 2 inline knowledge rows, the seven appended `must_not` strings); editing it would break that test for no gain and would make the seed lie about what AGT-154 shipped. The change gets its own mirror, exactly as `v7.0.691` did.
- **Reversible by the existing path** - `record_decision` (`agent-row`) plus one `runner_before_images` row with `row_data = to_jsonb(s.*)`, captured before the UPDATE. `skill_profiles` is in `reversible_tables()` (checked live this cycle).

## 3. Alternatives weighed

1. **Add `competitor_why` to the job item's flat `required`.** Rejected: it would refuse every non-competitor job, i.e. nearly every card, turning a missing optional fact into a total outage.
2. **Default `what_they_sell` in `leadsFromAnswer` (company name, or the posting title).** Rejected: that is the platform inventing a claim about a third party and writing it into a shared inbox another lane treats as evidence. pattern:2 and the ticket's own "public facts only".
3. **Soften `validateLeads` so a bad lead drops silently and the records still land.** Rejected: a silent drop loses market intel with no signal (pattern:34, pattern:51). The refusal is correct; the runbook's (b)5 sentence now names it so the repair loop is obvious.
4. **Wait for AGT-156** (the daily `jerry-linkedin-alerts` routine) to run and see whether the model volunteers `competitor_why`. Rejected: that is designing on a guess about a model, and the first competitor hit is a live refusal on John's own mailbox review. pattern:5 - model how the work actually enters the pipeline.
5. **Do nothing and close AGT-155 on the routine paste alone.** Rejected: pattern:95 - a ticket closes only when every sentence in its own text is satisfied, and "inserts a lead ... with public facts only" is not satisfied by a path that refuses the answer.
6. **Also fix the 1.5 MB alerts render.** Named as residue, not filed and not fixed: it is a different ticket's problem (the render carries 538 records), outside one item (pattern:64).
