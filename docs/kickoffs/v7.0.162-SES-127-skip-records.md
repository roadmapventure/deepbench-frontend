## The six properties the migration header carries

Repeated in `ses127_skip_records`'s own header so they travel with the code, and each was
measured rather than reasoned about:

1. **One open row per `(backlog_id, reason_kind)`** (`uniq_open_skip`). John's standing drain
   re-reads 25 open now-tier members every cycle, eight cycles a day — an INSERT-only table
   shows him the same `SES-110` row 8×/day forever. A repeat bumps `skip_count`/`last_skipped_at`.
2. **`first_skipped_at` never moves, `last_skipped_at` does.** Two different questions: how long
   has this been stuck, and when did it last block.
3. **`briefed_at IS NULL` *is* the NEW chip.** No global last-brief timestamp is needed, a row is
   new exactly once, and a re-skip after briefing does **not** clear it — John has seen it.
4. **Resolution is derived, never maintained.** §10 joins `backlog_items` and filters
   `status NOT IN ('done','removed')`, so a shipped ticket leaves the section with no write and
   no rule for a cycle to remember. `resolved_at` covers only the other case (ticket still open,
   blocker gone).
5. **A skip the runner can resolve itself is never recorded.** `claimed-by-peer` is deliberately
   absent from the `reason_kind` vocabulary — the section says "waiting on **your** input", and a
   contested claim expires on its own in minutes.
6. **`record_skip()` writes its own before-image**, both paths (INSERT → `row_data = NULL`,
   the step-8b convention; UPDATE → the prior row). §19v: no before-image, no write.

## QA bar

- Dedup is the discriminating test: three `record_skip` calls → **two** rows (an INSERT-only
  implementation returns three).
- `last_skipped_at` proven to move independently of `first_skipped_at` across separate
  transactions (10 s apart), with an untouched row as the control.
- `claimed-by-peer` rejected by `ck_skip_reason_kind`; row count stays 2, not 3.
- Grants asserted **both directions** (the `SES-101` lesson): `anon`/`authenticated` hold zero
  privileges on the table and cannot `EXECUTE` the function; `service_role` still can.
- Fixtures and their before-images deleted after.
