## Premise revalidation (`SES-87`, register B7) — HOLDS

Verified this cycle against live code **and** live data, not recalled.

**Code, read on this branch.** `middleware.js:320-325` writes the first-sighting row —
`writeRow(supabaseUrl, supabaseKey, ip, country ? { country } : {}, 'ignore-duplicates')` — a
minimal row carrying `caller_ip` and at most `country`, with no `org`, `city`, `region` or
`resolver`. `lib/ip-org-resolver.js:78-88` then asks only whether a row exists:

```js
`${supabaseUrl}/rest/v1/ip_org_cache?select=caller_ip&limit=1&caller_ip=eq.…`
…
```

`select=caller_ip` cannot distinguish *"resolved already"* from *"a bare row the gate wrote a
millisecond ago"*, so the ipinfo lookup never happens and the location fields stay NULL forever.

**Data, read this cycle.** `public.ip_org_cache` holds **24** rows: **22** resolved, **2** with
`org IS NULL`, and — the discriminating figure — **`attempted_but_unresolved` = 0**. Every NULL-org
row also has `resolver IS NULL`, i.e. the lookup was never *attempted*, which is this defect's
signature and not the signature of a failed lookup. Both are public US IPv4 addresses on `trial`
(`xxx.xx.106.128`, `xxx.xx.106.132` — masked column only, per `LOG-124`), so neither is a row
`isPlausiblePublicIp()` would legitimately decline. Premise holds; `revalidated_at` set.

## The fix, and the invariant it must not break

The module's own header states the property that makes it safe to hang off the logging path:
**steady state is zero outbound lookups**, protected by two rules — a cache hit returns before any
request is constructed, and *"a FAILED lookup still writes its row, with org = null … without it,
one rate-limited or unroutable address would be re-queried on every single call forever."*

So the short-circuit is right; its **test** is wrong. It asks *does a row exist* when it must ask
*was a resolution ever attempted*. The attempted-marker already exists and needs no new column:
`resolver` is written as `'ipinfo.io'` on **both** the success and the failure path (the write is
unconditional, below the `catch` that sets `info = null`). `resolved_at` is **not** usable for
this — both live NULL-org rows carry a non-NULL `resolved_at` while `resolver` is NULL, so keying
on it would read a never-attempted row as attempted and reproduce the bug.

Two edits, one file:

1. **Rule 1 selects `resolver` and short-circuits on `resolver IS NOT NULL`**, not on row
   existence. A row that exists but was never resolved falls through to the lookup exactly once.
2. **The write becomes `resolution=merge-duplicates`.** Without this the fix is inert: the row
   already exists, so PostgREST's `ignore-duplicates` (`ON CONFLICT DO NOTHING`) silently drops the
   result the lookup just paid for. `merge-duplicates` updates **only the columns in the payload** —
   `org`, `city`, `region`, `country`, `resolver`, `resolved_at` — so the gate's own
   `permission`, `spend_limit_usd`, `block_reason` and `blocked_attempts` are untouched.

**The anti-runaway survives, and that is the clause to check twice.** A failed lookup still writes
`resolver = 'ipinfo.io'` with `org = null`, so the very next sighting sees a non-NULL `resolver`
and returns before constructing a request. One attempt per address, forever — unchanged. What
changes is only *which* rows count as attempted.

**`middleware.js` is deliberately NOT edited.** Its `ignore-duplicates` is correct and its comment
is the reason: the gate must never clobber the resolver's location fields. Making the gate resolve
the org instead would put an outbound ipinfo call on the edge request path, which the resolver
exists to keep off it.

## Not claimed

- **No backfill, and none is needed** — which is the fix earning its keep rather than a gap. Both
  live NULL-org rows have `resolver IS NULL`, so under the new Rule 1 the next sighting of either
  address resolves it. A `UPDATE … SET org = …` from this cycle would be a hand-write standing in
  for the code path under test.
- **Two invocations racing the same never-resolved address can each spend one lookup.** Already
  true of the first-sight path and called *"normal and harmless"* by the existing comment; both
  merges write the same values.
