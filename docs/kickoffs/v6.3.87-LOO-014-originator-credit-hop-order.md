# S-LOO-014 — Fix Hop Order: Originating Agent Must Be Credited Before the Target's Placeholder Is Created

**SESSION:** `S-LOO-014` | v6.3.87 | branch: `dev` | worktree: `C:/Projects/deepbench-frontend/.claude/worktrees/design-loo-hop-order-0721/`

## CONTEXT

Found live 2026-07-21, John's own screenshot: after `LOO-011`/`LOO-012`, the Jordan → Alex news-fetch flow shows "2 Jordan... / 1 Alex..." — Jordan numbered *after* Alex, even though Jordan's own work (the web search) genuinely happens first, before Alex ever starts formatting.

**Root cause, precise — this is a hop-numbering bug, not a content bug (Task 3's own content is correct, only its position is wrong):** hop numbers are assigned by array-creation order, oldest first (`groupEventsIntoHops`, unchanged, correct). Two things create array rows for this exchange:
1. The `delegation` announcement (unchanged, pre-existing code, fires immediately when Jordan's model turn decides to delegate) creates a placeholder row *immediately* — this is the EARLIEST row created for this whole exchange.
2. `LOO-011`'s new originator-credit event currently fires *after* the nested call resolves, inside the `if (delegationRequired || tool_input.is_final === true)` block — meaning it creates its own row *later* than the `delegation` placeholder above.

Alex's own credit (`LOO-009`, unchanged) then claims the *early* `delegation` placeholder (row 1) in place — so Alex keeps the early array position even though his content arrives late. Jordan's credit creates a genuinely new, late row (row 2). Hop numbers (oldest = 1) end up backwards from real chronology: Alex = 1, Jordan = 2.

**The fix — move `LOO-011`'s event earlier, not change its content:** `delegationRequired` and `tool_input.is_final` are both already known *before* the `delegation` announcement fires — neither depends on the nested call's result. So the originator's own credit can fire *before* the `delegation` announcement, giving it the genuinely earliest array position (hop 1), while the `delegation` announcement's placeholder (which Alex's own credit will later claim) becomes hop 2 — matching real chronology exactly: Jordan works, then hands off, then Alex works.

**Confirmed safe against the one real risk (duplicate credit on the returning case):** the condition (`delegationRequired || tool_input.is_final === true`) is evaluated once, stored, and used both for the early-fire decision and the existing later branch — identical semantics, just computed once instead of twice. The returning case (e.g. Owen's own retry-via-Marcus) still never enters either branch, exactly as before.
