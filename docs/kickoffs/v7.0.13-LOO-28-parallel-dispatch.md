## CONTEXT

**This is LOO-28 (Architecture): parallel dispatch for the harness Loop — the published pattern name is parallelization (sectioning/voting variants), carried natively by Anthropic parallel tool use.** Design settled live with John 2026-07-31 (`design-loo-28-0731`): today `execute.js` has no concurrent dispatch anywhere — within one trace every delegation is awaited sequentially, so a question needing a data pull *and* a news check pays the sum of both waits. Measured live (14 days): **48% of delegating agent-runs (329 runs) made 2+ sequential asks** — every one is a fan-out beneficiary.

**The design, as agreed (all five points are decisions, not suggestions):**
1. **Model-judged, never harness-forced.** A new Intent Skill Profile trait permits the model to emit several harness-tool calls in one turn; the model decides per turn whether sub-tasks are independent. §19d sniff test passes: fan-out is the model's own logged judgment; who-gets-asked routing is unchanged.
2. **Per-ask hop accounting.** A fan-out of N spends N from the existing shared `MAX_LOOP_DEPTH = 5` pool. No new width limit — the pool bounds the widest possible fan by arithmetic. The pool number stays 5 (measured: only 6 of ~1,540 questions in 14 days legitimately used all 5).
3. **`delegation_required` intents never fan** — their entire job is a single terminal hand-off; two finals is undefined.
4. **`is_final` is honored only on single-call turns.** A multi-call turn is Orchestrator-Workers by construction (results return to the caller); ignore `tool_input.is_final` on fan calls.
5. **Pause/resume: finished prongs stay finished.** The save-record's pending field becomes a per-prong list (done-with-result / waiting-on-job / not-yet-dispatched); resume drives only the unfinished prongs, then folds **all** results into one `tool_result` user message (the Anthropic protocol requires every `tool_use` id in the assistant turn to be answered in the immediately-following user message — partial fold-in is protocol-impossible). A prong that fails permanently comes back as an `is_error` tool_result the orchestrator reasons about — not a thrown failure that kills the question.

**Protocol layer today (verified):** `buildCallBody()` sets `disable_parallel_tool_use: true` on **both** tool_choice branches (`HAR-20`), and `parseModelTurn()` reads only the first `tool_use` block. The forced branch's flag (and the guardrails inline call's) is a real bug fix — multiple emissions of the *same schema tool* were a live failure class. **Only the auto branch (harness tools present) becomes trait-conditional.**

**Known adjacent bug — do not fix here, do not worsen:** `LOO-29` (Task Success Rate, filed this session) — the depth ceiling is breachable live via a suspected non-terminal `depth_exceeded` on the resume path. Out of scope; but nothing you add may create a **new** non-terminal cap-exhaustion path (see Task 2's refusal rule).

The forced branch and the guardrails inline call stay `disable_parallel_tool_use: true` verbatim (`HAR-20` — regression-guarded in the checklist).
- `parseModelTurn()`: collect **all** `tool_use` blocks. Backward-compatible return shape: keep the existing singular `tool_name`/`tool_use_id`/`tool_input` (first block) untouched, add `tool_calls: [{tool_name, tool_use_id, tool_input}, …]`. Every existing consumer keeps working; only `runLoop()` reads the new array.
- **Mixed-emission rule:** if a turn emits the schema (terminal) tool *alongside* harness-tool calls, that is incoherent (a final answer before its inputs exist) — route it through the existing parse-retry correction machinery (`buildParseRetryCorrection()` already answers every `tool_use` id per `HAR-20`) asking for either pure-delegate or pure-terminal; fail loudly on a second occurrence, same one-retry shape as `AA-142`.

**Task 2 — Concurrent dispatch (`execute.js` `runLoop()` + `dispatchDelegation()`).**
- When a turn's `tool_calls` has 2+ entries (all harness tools): **claim the whole fan's hops up front** — pre-check `hopCounter.n + fanSize` against `MAX_LOOP_DEPTH`:
  - Fits → `hopCounter.n += fanSize`, dispatch all prongs concurrently (`Promise.all` over per-prong `dispatchDelegation()` calls, each individually caught).
  - Doesn't fit but hops remain → **clean refusal, once per loop** (mirror the `delegationRetried` one-retry pattern): dispatch nothing, answer every id with a structural "insufficient hop allowance: asked N, M remain" `tool_result`, let the model re-plan. A **second** oversized fan in the same loop → the existing terminal `depth_exceeded` return. Never a partial fan; never a new unbounded refusal loop (the `LOO-29` lesson).
  - No hops remain at all → existing `depth_exceeded` behavior unchanged.
- Per-prong outcomes: `'continue'` carries its `tool_result` content; a thrown permanent failure becomes `{type:'tool_result', tool_use_id, is_error:true, content:<honest §19j-style failure summary>}` — the prong's own child-run transient recovery (§19o, inside its own `runLoop`) has already had its shot before that throw surfaces. `runLoop` assembles **one** user message answering every id **in emission order** (protocol pairs by id; completion order is irrelevant).
- On a fan turn, ignore `tool_input.is_final` (design decision 4) and skip the single-dispatch `'final'` short-circuit; `integratedDelegateResult` flips true when the fan folds in. Do not restructure `dispatchDelegation()`'s single-call path — the fan path may need it to *return* the tool_result content rather than append it; keep the single-call path byte-identical (it is the entire live platform until a trait is enabled).
- Provenance capture (`LOG-77-9`'s `delegationTarget`/`taskProvenance` on the turn row) stays **single-call-only** — a fan's per-prong provenance already lives on each prong's own child span rows; note this as deliberate in a comment, don't silently widen a log schema.
- `onEvent` emissions need no new types: per-prong `delegation`/`delegation_complete`/`delegation_return` events already fire inside `dispatchDelegation()` with correct per-prong spans (§19p); they now interleave — that is truthful chronology.

**Task 3 — Durable pause/resume (`execute.js` `checkpointAndReturn()` + `resumeCapability()`).**
- No DDL — `durable_hops.pending_delegation` is jsonb. New persisted shape for a mid-fan checkpoint: `{fan: [{tool_use_id, status:'done', result} | {tool_use_id, status:'waiting', waiting_on_job_id} | {tool_use_id, status:'pending', via_tool, tool_input}]}`, array in emission order. Completed prong **results are persisted** — a resume must never re-run finished work (§19o: re-rolling completed work can duplicate stored deliverables).
- `runLoop()`'s fan block checkpoints only after **every** prong settles (resolved, or itself returned `in_progress`): any `in_progress` prong → outer checkpoints with the mixed fan list. The outer job_id the client polls is unchanged — no client change.
- `resumeCapability()`: new `row.pending_delegation?.fan` branch — drive every non-`done` entry to completion concurrently (`waiting` → the existing nested-job drive; `pending` → dispatch), supporting re-checkpoint (a resume that runs low re-persists the fan with newly-`done` entries), then assemble the single all-ids `tool_result` message and re-enter `runLoop()` exactly like the existing single branch. The existing singular shapes (`waiting_on_job_id` / `via_tool` objects) must keep working verbatim — old checkpoint rows exist.
- **Outer recovery ledger unchanged** — per-prong transient recovery lives inside each prong's own child run (its own `runLoop` seam); do not extend the outer ledger per-prong.
