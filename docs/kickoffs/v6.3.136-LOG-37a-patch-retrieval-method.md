## 2. CONTEXT

### The bug, in one sentence

`retrieved_chunk_ids` gets populated from a **plain database table read**, so agent ids land in a column that is supposed to hold retrieved-document ids.

### How it happens

`LOG-37a` added this to `fetchSection()` (`api/prompt/ai-enrichment.js`, ~line 75):

```js
_rag_chunk_ids: (result.chunks || []).map(c => c && c.id).filter(Boolean),
```

That is correct for a vector search. But `getRosterCandidates()` (`lib/project-manager.js:145-148`) returns:

```js
chunks: roster.map(a => ({ id: a.agent_id, title: a.name, capabilities: [...] })),
```

**A roster table read returns a field literally named `chunks`, whose `id` is an agent id.** The two are structurally identical at the call site — `LOG-37a` cannot tell them apart, and neither could its author.

**Real consequence:** the next time Michelle Manning — Project Manager runs `agent-selection-intent`, her row writes `retrieved_chunk_ids: ['marcus','eleanor','owen', …]`. Those are not chunk ids and nothing was retrieved.

`describeLibraryCatalog()` (`lib/librarian.js:140-173`) is the same class of operation — a catalog table read, no embedding — though it happens to return no `chunks` key at all, so it is currently harmless. **Do not rely on that**; it is an accident of that function's shape, not a guarantee.

### Blast radius — verified live this session, before writing this doc

- **0 rows** anywhere in `ai_activity_log` have a non-UUID value in `retrieved_chunk_ids`.
- **0 `project-manager` rows** written since `LOG-37a` deployed.

**No bad data exists yet.** The defect is latent and fires on the next routing question. No backfill or cleanup is needed — only the forward fix.

### Why this is also `LOG-37`'s 7th Layer A fact

`LOG-23`'s session added a 7th fact to `LOG-37` the same evening: *record **how** context was fetched (similarity search vs. direct lookup), not just that it was* — with the explicit warning that `§19i`'s worked example `RAG = retrieved_chunk_ids.length > 0` **inherits `LOG-42`'s bug** because a lookup produces chunk-shaped output too.

That is precisely this defect, and it is why the fix is not merely "filter out the roster case": the correct Layer A record is the **method**, captured generically. Chunk ids then become meaningful because they only ever appear alongside a real search.

**This closes the last open fact in `LOG-37`'s scope** (`LOG-49` carries the three deliberately-deferred ones).

## 5. TASKS

### Task 1 — `ai-enrichment.js`: derive the retrieval method per section

`fetchSection()` already branches on `fi.source` at `:45-47`. Derive the method from that same generic trait — **do not add any agent-id or capability-slug conditional** (`.claude/rules/capabilities-are-data.md`):

| `fi.source` | Method | Why |
|---|---|---|
| `roster` | `direct-lookup` | `getRosterCandidates()` — plain table read, no embedding |
| `the_library_catalog` | `direct-lookup` | `describeLibraryCatalog()` — catalog listing, no embedding |
| `the_library`, `the_reasoning` | `similarity-search` | `queryContent()` → real `embedAndSearch()` |
| anything else / null | `similarity-search` | falls through to `queryRAG()` |

Emit as `_rag_method` on the section return, beside the existing `_rag_chunk_ids` / `_rag_chunks`.

### Task 2 — `ai-enrichment.js`: gate the chunk ids on that method

`_rag_chunk_ids` must be `[]` unless the section's method is `similarity-search`. The ids from a direct lookup are discarded, not renamed — they are not chunk ids and have no Layer A home here.

Thread `_rag_method` upward the same way `_rag_chunks` / `_rag_chunk_ids` already are (~`:150`), and surface it on `enrichDebug` (~`:314`) beside `rag_chunk_ids_by_section`. **Follow the existing threading pattern exactly** — no parallel mechanism.

### Task 3 — `request-receivable.js`: record the method in `call_facts`

In `buildCallFacts()`, accept the per-section methods and collapse them: all `similarity-search` → `'similarity-search'`; all `direct-lookup` → `'direct-lookup'`; both present → `'mixed'`; none → omit the key.

`patterns_used` stays **byte-identical** — this patch does not touch pattern naming. `rag`'s own false-positive problem is `LOG-42`/`LOG-53`/`LOG-59`'s scope, deliberately not fixed here.
