## What shipped

One additive migration, `ses155_briefing_comments`:

```
id uuid pk · created_at · target_kind (ticket|question|vision|invention) · target_ref ·
author (john|runner) · kind (question|answer|requirement|routing|note) DEFAULT 'question' ·
body · harvested_cycle · routed_to
```

- **`uniq_briefing_comment (target_kind, target_ref, created_at, md5(body))`** — the harvest
  idempotence, mirroring `runner_card_asks`' `uniq_card_ask`. The page carries every comment in
  `briefing-state` forever, so **every** cycle re-reads comments it already stored; without this the
  log duplicates on every rebuild. `md5(body)` and not `body`: a btree entry is capped, a comment is
  prose.
- **`kind` defaults to `'question'`** — decision 3's cheap failure direction. A Question changes no
  state; a Requirement sends a ticket back for rework. Defaulting the other way turns an unlabelled
  comment into work.
- **Grants: `postgres` + `service_role` only**, matching `runner_card_asks` and `governance_rules`.
  `REVOKE … FROM PUBLIC` is the load-bearing half (`.claude/rules/supabase-column-grants.md`, and
  `SES-101`'s function-level twin): a narrower revoke cannot subtract from the broader `PUBLIC`
  grant and reports success while changing nothing.

**Data migration:** 8 ask rows → **16 comments** (8 John questions + 8 runner answers), each with
its own `runner_before_images` row carrying `row_data = NULL` — the INSERT convention from step 8b,
meaning *"this row did not exist; Reverse is a DELETE of this pk."* Before-images and comments are
written in one atomic statement, so neither can land without the other. `target_kind = 'item'` maps
to the new vocabulary's `'ticket'`.

## QA — discriminating

The question each test must survive is *"would it still pass if the change did nothing?"*

1. **Grants asserted BOTH directions** — never one, and never the migration's own success flag:
   `anon`/`authenticated` SELECT+INSERT **false**, `service_role`/`postgres` **true**.
2. **The discriminating one — idempotence.** Re-running the entire migration inserts **0 rows**.
   Without the unique index this inserts 16 duplicates and the log doubles on every rebuild. A test
   that merely counted 16 rows after the first run passes on a table with no constraint at all.
3. **Negative control**, so (2) does not merely prove the table rejects everything: inside a
   deliberately rolled-back transaction, a genuinely novel comment **does** insert (total 16 → 17),
   and the rollback left **16**, not 17.
4. **John's two "do NOT"s asserted, not assumed:** `runner_card_asks` still present with its **8**
   rows (not retired), and `pg_get_functiondef(briefing_state_seed())` does **not** mention
   `briefing_comments` (not repointed).
5. Ledger clean: 16 before-images for 16 rows, no strays from the fixture.
