**Why one derived field, not a writer change:** "this delegation's result was integrated" is knowable only after the delegation resolves — later rows in the same span carry the proof. Deriving it at read time (like `sub_calls_chained`) covers history automatically and keeps the write path untouched. Emitting it as explicit **true/false** (omitted only when `span_id` is null = unknowable) is what makes the no-synthesis side (Handoff) expressible at all — the grammar has no absence operator, but `@>` containment of `false` works.

## 4. STUB DEFINITIONS

**A. The `rename` decision** (5th branch of `reviewCandidate()`), semantics: *retire an existing gold row's identity and create its governed replacement, keeping history.*

Required inputs when `decision === 'rename'` (throw on any missing; mirror promote's gates):
- `matched_existing_slug` — the row being superseded. Throw if no such row.
- `pattern_slug`, `name`, `citation`, `maturity_status` — the replacement's identity. Throw if `pattern_slug === matched_existing_slug` (that's an `amend`, not a rename). `description` optional, as on promote.
- `criteria` — required, `validateCriteria()`d. The replacement must be matchable, same reasoning as promote's criteria gate.

Effect (in this order):
1. INSERT the new gold row (`promoted_by: 'susan'`, `tenant_id: 'global'`, `Prefer: return=representation`). A PK collision on an existing slug surfaces as the insert error — do not pre-delete anything, ever.
2. PATCH the old row: `{ superseded_by: <new pattern_slug> }`. Leave its `criteria`/`citation` in place — the row is the historical record; the view's `superseded_by IS NULL` filter is what retires it from matching. Throw if 0 rows returned.
3. PATCH the candidate: `status='renamed'`, `reviewed_by='susan'`, `resolved_at`, `resolution` (full payload, same shape as other branches).
4. Return `{ success: true, decision: 'rename', vocabulary_entry, superseded_entry, candidate }`.

A **split** is a `rename` (old row → corrected identity) plus an ordinary `promote` for the second name — no multi-successor mechanism, `superseded_by` stays a single forward pointer per §19i.

**B. The derived signature field `integration_followed`** (Displayer-derived, never written):
- Semantics: *does any strictly-later row in this same span carry `input_references_other_deliverable: true`?* Strictly later = `(created_at, id)` greater — the strictness is load-bearing: a delegating row whose *own* flag is true (a prior delegation integrated) but that hands off terminally must still read `false`.
- Emitted as explicit `true`/`false` whenever `l.span_id IS NOT NULL`; omitted entirely when `span_id` is null (unknowable ≠ false).
- Generic span math only — no `delegate_to_agent` or any tool/pattern name in the view SQL. Criteria combine it with `tool_calls` to scope it to delegations; that composition is Susan's data, not view code.
