## The two decisions this build owns

1. **`promotion ⇔ streak % 5 = 0`, written as the test, never as `>= 5`.** `SES-107` records why:
   left at `>= 5` a streak parked at 5 promotes again on every later Accept — a rung per tap,
   forever. The guard pins the retired `>= 5` form applied to the same fixture and asserted to lose.
2. **IDEMPOTENCE IS STRUCTURAL, not a rule a cycle must remember.** Additive column
   `runner_items.ladder_applied_at`; the function no-ops when it is already set. Without it, a
   re-run — or two peers harvesting the same tap under parallel cycles (register B42) — double-counts
   a streak, and a double-counted streak silently manufactures a promotion. This is the same
   `… AND decision IS NULL` shape the decision harvest already uses, applied one level along.

## Boundaries

- **It writes its own before-image** (§19v), like `record_skip()` / `close_directive()` /
  `stall_watchdog()`, so one call is the whole of a cycle's obligation.
- **Rung floors at 0.** A negative rung is not a state the ladder defines.
- **OUT OF SCOPE, stated rather than drifted into:** `SES-122` is where rungs start unlocking
  autonomy. This ticket is bookkeeping that cannot drift, and the ticket says so itself.
- **The runbook's step-2 harvest text points at the call rather than restating the arithmetic** —
  otherwise the prose and the function become two homes for one rule, which is the defect being
  fixed.
