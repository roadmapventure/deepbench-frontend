## 2. CONTEXT

Found live 2026-07-21 during `LOO-17`'s own design session: while investigating a confirmation-flow bug (`DAT-6`/`LOO-17`), 3 consecutive live Accept attempts hit real `Anthropic 529 overloaded` errors. Checked Supabase before proposing anything, not assumed: `postToAnthropicWithRetry()` (`api/prompt/request-receivable.js`) already retries exactly once on a transient status (`429/500/502/503/529`, flat 1-second pause) before giving up — 2 total attempts. That single retry wasn't enough during today's real capacity event.

**Frequency, checked live against Supabase (`durable_hops`, 14-day history, 647 checkpointed chains, 77 failed):**
- 11 failures were genuine `529` overload — **all 11 from 2026-07-21 only**, zero on any of the prior 13 days. Not a chronic background rate; today looks like a real, if unusual, capacity event.
- 30 failures on 2026-07-20 were an unrelated billing issue ("Your credit balance is too low") — a `400`, already correctly excluded from the existing retry set (`TRANSIENT_ANTHROPIC_STATUS` doesn't include 400), already resolved (none since), and retries would never have helped there regardless.
- The remainder are a handful of unrelated one-offs (structured-output parse failures, which already have their own separate 1-retry-with-correction mechanism; a couple of config typos).

**Conclusion, confirmed with John (design-session walkthrough):** this is cheap, safe, uniform insurance against exactly the kind of spike this session hit live — not a fix for a chronic problem, since none existed before today. Scoped as a **generic Harness/Execution change**, not confirmation-specific: `postToAnthropicWithRetry()` is the one shared wrapper every single model call on the platform goes through (`callModel()`, used by every capability's every turn), so every agent gets the same resilience uniformly, no special-casing per capability or per call site. This is the harness-level counterpart to `LOO-17` (a separate, Loop-layer fix to the confirmation-status bug that surfaced these failures) — sequenced to ship first, since `LOO-17`'s "3rd failure → `accept_failed`" semantics only mean what they're supposed to once the harness itself is actually attempting 3 times.

**Not the same area as `MAX_LOOP_DEPTH`** (confirmed with John): both are Harness-layer, platform-wide, hardcoded constants — but `MAX_LOOP_DEPTH` gates hop count (Evaluation sub-part), this gates a single model call's own resilience (Execution sub-part). Siblings in character, different sub-parts.

**Harness-vs-service check:** `postToAnthropicWithRetry()` is already the single shared harness primitive for this — no extraction needed, no duplicate implementation exists anywhere else (checked: `apiRetryCount`'s only other reference, `execute.js`'s `logAgentTurn()`, is pure observability logging with no assumption about the max value, unaffected by this change).

## 5. TASKS

### Task 1 — `api/prompt/request-receivable.js`: 3 total attempts, escalating backoff

```js
// FEATURE: HAR-8 -- was 1 retry (2 total attempts, flat 1000ms pause). Bumped after 11 real 529-
// overload failures in one day (2026-07-21, confirmed via durable_hops) exhausted the old single
// retry -- uniform, harness-level, applies identically to every model call on the platform, no
// per-capability special-casing. Escalating backoff (was flat) gives a genuinely overloaded API
// more room to recover on the 2nd retry than the 1st.
const MAX_ANTHROPIC_ATTEMPTS = 3;
const API_RETRY_BACKOFF_MS = [1000, 3000];

async function postToAnthropicWithRetry(body, headers, deadline) {
  for (let attempt = 0; ; attempt++) {
    const remainingMs = deadline - Date.now();
    if (remainingMs < MIN_VIABLE_CALL_MS) {
      throw Object.assign(new Error(`Insufficient time remaining for Anthropic call (${remainingMs}ms left)`), { status: 504 });
    }
    const res = await fetch('https://api.anthropic.com/v1/messages', {
      method: 'POST', headers, body: JSON.stringify(body), signal: AbortSignal.timeout(Math.min(55000, remainingMs)),
    });
    if (res.ok) return { res, apiRetryCount: attempt };
    if (attempt >= MAX_ANTHROPIC_ATTEMPTS - 1 || !TRANSIENT_ANTHROPIC_STATUS.has(res.status)) {
      const text = await res.text();
      throw Object.assign(new Error(`Anthropic call failed: ${res.status}`), { status: 502, detail: text });
    }
    await new Promise(resolve => setTimeout(resolve, API_RETRY_BACKOFF_MS[attempt]));
  }
}
```

Only the two new constants and the loop's exit condition / backoff lookup change. `TRANSIENT_ANTHROPIC_STATUS` (the existing `429/500/502/503/529` set) is untouched — this changes *how many times* a transient failure gets retried, not *which* failures are considered retriable.

## 6. DESIGN RULES

- Uniform, harness-level — no per-capability or per-call-site opt-out or override. This is deliberately not confirmation-specific (`LOO-17` builds on top of this, doesn't duplicate it).
- Do not change `TRANSIENT_ANTHROPIC_STATUS`'s membership — only the retry count and backoff timing.
- Escalating backoff (`[1000, 3000]`), not flat — a Tier-2 call (low-stakes, easily retuned later), flagged here rather than asked, since a genuinely overloaded API benefits more from more room on the later attempt.

---

## 7. SCOPE RULES

- Do **NOT** touch `TRANSIENT_ANTHROPIC_STATUS`'s contents (which statuses are retriable) — only how many times and how long between attempts.
- Do **NOT** touch the separate "parse failed, retry once with a corrective message" mechanism (`AA-150`/`AA-182`'s own retry-on-schema-failure logic) — unrelated retry class, out of scope.
- Do **NOT** touch `LOO-17`'s confirmation-status logic — that's a separate kickoff, sequenced to follow this one.
- Do **NOT** add a data-configurable override (e.g. a Skill Profile trait for retry count) — deliberately a hardcoded, platform-wide constant, same character as `MAX_LOOP_DEPTH`.

## 8. NODE.JS TEST

```js
// test-HAR-8.mjs — pure Node.js, no app imports. Tests the retry/backoff logic in isolation
// (inline copy of the post-fix loop shape, not a live network test — Category L below covers that).
let pass = 0, fail = 0;
function assert(desc, cond) {
  if (cond) { console.log(`  ✓ ${desc}`); pass++; }
  else       { console.error(`  ✗ ${desc}`); fail++; }
}

const MAX_ANTHROPIC_ATTEMPTS = 3;
const API_RETRY_BACKOFF_MS = [1000, 3000];
const TRANSIENT_ANTHROPIC_STATUS = new Set([429, 500, 502, 503, 529]);

// Simulates the loop's exit/backoff decision at each attempt, given a sequence of mock statuses.
function simulate(statusSequence) {
  const log = [];
  for (let attempt = 0; attempt < statusSequence.length; attempt++) {
    const status = statusSequence[attempt];
    if (status === 200) { log.push({ attempt, outcome: 'success' }); return log; }
    if (attempt >= MAX_ANTHROPIC_ATTEMPTS - 1 || !TRANSIENT_ANTHROPIC_STATUS.has(status)) {
      log.push({ attempt, outcome: 'throw' }); return log;
    }
    log.push({ attempt, outcome: 'backoff', backoffMs: API_RETRY_BACKOFF_MS[attempt] });
  }
  return log;
}

assert("T1: succeeds on 1st attempt, no retries", JSON.stringify(simulate([200])) === JSON.stringify([{attempt:0,outcome:'success'}]));
assert("T2: 529 then success — 1 backoff then success", JSON.stringify(simulate([529,200])) === JSON.stringify([{attempt:0,outcome:'backoff',backoffMs:1000},{attempt:1,outcome:'success'}]));
assert("T3: 529,529 then success — 2 backoffs (1000,3000) then success on 3rd attempt", JSON.stringify(simulate([529,529,200])) === JSON.stringify([{attempt:0,outcome:'backoff',backoffMs:1000},{attempt:1,outcome:'backoff',backoffMs:3000},{attempt:2,outcome:'success'}]));
assert("T4: 529 x3 — throws after 3rd attempt, no 4th try", JSON.stringify(simulate([529,529,529])) === JSON.stringify([{attempt:0,outcome:'backoff',backoffMs:1000},{attempt:1,outcome:'backoff',backoffMs:3000},{attempt:2,outcome:'throw'}]));
assert("T5: non-transient 400 — throws immediately, no retry at all", JSON.stringify(simulate([400])) === JSON.stringify([{attempt:0,outcome:'throw'}]));
assert("T6: 400 after a transient retry never happens — first attempt already non-transient", JSON.stringify(simulate([400,200])).length > 0 && simulate([400,200])[0].outcome === 'throw');

console.log(`\n${pass + fail} tests — ${pass} passed, ${fail} failed`);
if (fail > 0) process.exit(1);
else console.log("ALL TESTS PASS");
```

**Category L (live API test) does not apply here** — forcing a real `529` from Anthropic on demand isn't controllable; the logic is fully covered by the Node test above (pure function, deterministic), and the real-world proof is the historical data already gathered this session (11 real `529`s in one day, now with 3x the retry budget instead of 2x). No live network test needed for this specific change.
