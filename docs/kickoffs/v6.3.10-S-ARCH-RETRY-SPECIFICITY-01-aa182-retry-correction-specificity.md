## 1. CONTEXT

`callModel()`'s retry-once-on-parse-failure logic (`api/prompt/request-receivable.js`, `catch (parseErr)` block, added by `S-ARCH-RETRY-TOOLRESULT-01`/`AA-150`/`AA-151`) already computes exactly which required field(s) a failed schema-tool call omitted — `parseModelTurn()` throws `Error('Schema tool "${schemaTool.name}" called with missing required field(s): ${missing.join(', ')}')` — but that detail is discarded. The retry's corrective message is a hardcoded, generic string:

```js
const correctionText = 'Your response did not conform to the required schema. Please try again and return the structured output exactly as specified.';
```

The model is never told *what* it got wrong on the one retry it gets. This is a generic harness gap, not specific to any one capability — the same file's own comments already document the identical symptom recurring across multiple unrelated intents (`agent-selection-intent` missing `recommended_agent_id`, `intelligence-review-format` missing `key_data_points`/`override_warning`, both confirmed live on the *retried* attempt, per the `AA-151` comment block a few lines above this session's target).

**Discovery history:** `AA-166` (2026-07-08) first found `library-catalog-intent` and `ci-answer-display-intent` hitting `"Parse failed and retry also failed... missing required field(s)"` and fixed it by pinning `temperature: 0` on both — `AA-154`'s own row already cautioned this "sharply reduces but does not guarantee token-level determinism." `AA-182` (found 2026-07-14, live re-verification of `AA-176`) confirmed that caution was correct: 1/5 fresh live tests on a genuinely novel catalog-question phrasing still hit the identical error, with `temperature: 0` confirmed still in place (not reverted, not regressed) — real residual failure, not a new bug. `AA-182`'s own row flagged an open question — whether `ci-answer-display-intent` shows the same residual rate — as the next session's starting point.

**Today's investigation (`S-AA194-design`, 2026-07-16) found the open question doesn't need a separate per-intent check:** the root cause is the shared retry-message gap above, which affects every schema-tool call platform-wide by construction. Fixing it here should reduce the residual rate on `library-catalog-intent`, `ci-answer-display-intent`, and every other intent the file's own comments already show hitting this same "retry with no specific correction" pattern — one generic fix instead of a per-intent investigation queue.

**Ship-readiness stakes:** a catalog/inventory question (`AA-182`) or a Q&A display hand-off (`AA-160`'s sibling failure mode) can still dead-end today even after the first-layer `temperature: 0` fix — this is a real, currently-open gap in "a question gets answered fully, non-stop" (John's Continuity bar, 2026-07-16).

## 5. TASKS (1 of 4 max, 1 file)

### Task 1 — `api/prompt/request-receivable.js`: make `callModel()`'s retry correction message specific to what actually failed

Currently (inside the `catch (parseErr)` block, `tools.length > 0` branch):

```js
const correctionText = 'Your response did not conform to the required schema. Please try again and return the structured output exactly as specified.';
```

Replace with:

```js
// FEATURE: AA-182 -- parseModelTurn() already computes exactly which required field(s) were
// missing (parseErr.message), but it was discarded before this point -- the retry's corrective
// message was always this same generic string regardless of what actually failed, so the one
// retry a call gets is really just another non-deterministic roll of the dice, not a corrective
// attempt. Confirmed live: 1/5 fresh library-catalog-intent calls still hit this even with
// temperature:0 already pinned (AA-166) -- same generic gap already visible in this file's own
// AA-151 comments on agent-selection-intent/intelligence-review-format. Still retry-once-then-
// throw -- this only changes what the model is told, not how many attempts it gets.
const correctionText = `Your response did not conform to the required schema: ${parseErr.message}. Return the structured output again, exactly as specified, making sure to include every field named above.`;
```

**Why this design, not a bigger one:** still retry-once-then-throw, zero new retry attempts added — matches the platform's established "fail loudly, don't loop" pattern (already locked for `AA-191`, already the norm in Owen's own `qg-review-intent` method: "Never retry more than once"). Does not touch `parseModelTurn()` itself (already correct, unchanged since `AA-147`). Does not touch the `tool_result`-wrapping branch logic `S-ARCH-RETRY-TOOLRESULT-01` added — only the string content fed into whichever message shape that logic already picks (`tool_result` block or plain text). Generic across every capability by construction — no `if(capability_slug===)` needed, so no separate per-intent fix required for `ci-answer-display-intent` or any other intent hitting the same symptom.

```js
import assert from 'node:assert';
import { callModel } from './api/prompt/request-receivable.js';

process.env.ANTHROPIC_API_KEY = 'test-key';

// --- Test 1: retry correction message must name the specific missing field(s) ---
{
  let callCount = 0;
  let capturedRetryBody = null;
  global.fetch = async (url, opts) => {
    callCount++;
    const body = JSON.parse(opts.body);
    if (callCount === 1) {
      // first attempt: tool_use call missing the required "citations" field
      return { ok: true, json: async () => ({
        content: [{ type: 'tool_use', id: 'tu_1', name: 'test-format', input: { headline: 'x' } }],
        usage: { input_tokens: 10, output_tokens: 5 },
      }) };
    }
    if (callCount === 2) {
      capturedRetryBody = body;
      return { ok: true, json: async () => ({
        content: [{ type: 'tool_use', id: 'tu_2', name: 'test-format', input: { headline: 'x', citations: ['id1'] } }],
        usage: { input_tokens: 8, output_tokens: 4 },
      }) };
    }
    throw new Error('unexpected extra call');
  };

  const result = await callModel({
    systemPrompt: 'test',
    model: 'claude-sonnet-4-6',
    max_tokens: 100,
    format_contract: { output_type: 'json', schema: { type: 'object', required: ['headline', 'citations'], properties: {} }, skill_profile_slug: 'test-format' },
    canRequestHelp: false,
    conversation_history: [],
  });

  assert.equal(callCount, 2, 'expected exactly one retry call');
  assert.ok(capturedRetryBody, 'retry body was captured');
  const lastMsg = capturedRetryBody.messages[capturedRetryBody.messages.length - 1];
  assert.equal(lastMsg.role, 'user');
  assert.ok(Array.isArray(lastMsg.content), 'correction message must still be a tool_result content-block array (unchanged shape)');
  const correctionText = lastMsg.content[0].content;
  assert.ok(correctionText.includes('citations'), 'correction message must name the specific missing field ("citations")');
  assert.equal(result.tool_input.citations[0], 'id1');
  assert.equal(result.retryCount, 1);
}

// --- Test 2: retry-once-then-throw is unchanged -- a second bad attempt still throws, no third attempt ---
{
  let callCount = 0;
  global.fetch = async (url, opts) => {
    callCount++;
    if (callCount <= 2) {
      return { ok: true, json: async () => ({
        content: [{ type: 'tool_use', id: `tu_${callCount}`, name: 'test-format', input: {} }],
        usage: { input_tokens: 5, output_tokens: 2 },
      }) };
    }
    throw new Error('unexpected third call -- retry-once semantics violated');
  };

  await assert.rejects(
    callModel({
      systemPrompt: 'test',
      model: 'claude-sonnet-4-6',
      max_tokens: 100,
      format_contract: { output_type: 'json', schema: { type: 'object', required: ['headline'], properties: {} }, skill_profile_slug: 'test-format' },
      canRequestHelp: false,
      conversation_history: [],
    }),
    /Parse failed and retry also failed/
  );
  assert.equal(callCount, 2, 'must not attempt a third call');
}

console.log('ALL TESTS PASS (2/2 -- retry-correction-specificity regression)');
```
