# SESSION: S-MI-29 (v6.1.21) — MI Screen: Surface Real Errors Instead of Silent Reset

## 1. CONTEXT

Found 2026-07-08 while diagnosing "Column 2 charts don't seem to work at all" (design session `charts-column2-0708`). Live-reproduced a stuck durable-resume chain on `hyp-hypothesis-test-display-intent` — logged separately as `AA-151` (`docs/FEATURES.md`), **not fixed in this session**; that's harness/durable-resume territory, flagged for the speed track (`AA-149`/`AA-150`) to check against or root-cause on its own.

Independent of that root cause, this session fixes a real, separate problem found along the way: three of `MarketIntelligenceScreen.jsx`'s four async catch blocks swallow every failure silently — `console.error` only (invisible unless devtools is open) plus a bare state reset, with zero message in the chat and zero record in the existing Pipeline Log. `AA-151`'s stall, a plain network error, or any future regression in this fragile area (`AA-126`/`AA-147`/`AA-148` all landed here in the last few days) all look identical: nothing happened. The fourth catch (`onSend`, line 1167-1169) already does this correctly — shows a user-facing message. This session brings the other three in line with that existing pattern, and additionally captures the real error text into the already-built Pipeline Log (`logEvent()`/`AuditColumn`/Column 3) so a future investigation doesn't require live-reproducing the failure by hand the way this session had to (manual `durable_hops`/`ai_activity_log` queries) — the real error (which, for an `AA-151`-style stall, already includes the `job_id` via `resolveInProgress()`'s own thrown message) becomes visible in-app immediately.

**Not in scope:** root-causing or fixing `AA-151` itself, `AA-124` (latency), or any other open backlog item. This session only changes what happens *after* something throws in these three flows — not why it throws.
