## CONTEXT

Live-diagnosed from John's real "Japan is Apple's fastest-growing GEO" Q&A run (2026-07-07, reported taking ~2 minutes). Direct `ai_activity_log` query for that run's timestamp window (18:02:14–18:04:02, ~107s total) broke the run into 11 real calls. Two dominate: Marcus's `ci-answer-intent` (Sonnet, real RAG+case-based-reasoning analysis) at 33.9s, and Riley's `html-display-format` turn (Sonnet, `ai_type: 'html-display'`) at **37.4s — longer than the actual analysis it's formatting.**

Pulled 5 historical `ai_type = 'html-display'` samples to check whether this is typical:

| latency_ms | input_tokens |
|---|---|
| 39698 | 3301 |
| 21742 | 1708 |
| 1453 | 978 |
| 1568 | 1483 |
| 4470 | 2681 |

Latency does not track input size (1483 input tokens → 1.57s; 1708 input tokens → 21.7s, 14x longer for a smaller input). That variance, uncorrelated with input size, is the same signature as the already-fixed `AA-120`/`AA-124` bug class: an uncapped generation with nothing constraining how much the model writes.

**This is NOT the same fix, though — a different root cause needs to be named, not assumed.** `AA-120`/`LOOP-LATENCY-03` targeted `ci-answer-display-intent`/`hyp-hypothesis-test-display-intent` — Marcus/Priya's own **routing/hand-off** turns, whose entire job is a 1-2 sentence `request_help`/`delegate_to_agent` reasoning field. Blindly copying that fix (`max_tokens` slashed to 800 + a "be brief" instruction) would be patching a symptom onto the wrong kind of call: `html-display-format` (`skill_type_slug: 'format'`) is a genuine content-generation step — Riley's actual job (per its `method`: "Apply document structure hierarchy... convert data lists to appropriate HTML elements... ensure paragraph flow and readability") is to produce real, structurally faithful HTML from the already-written answer. A blanket "be terse" instruction or an 800-token cap risks truncating or degrading legitimate output, not just cutting rambling.

**Root cause, scoped to what this call actually does wrong:** `method` places no ceiling on output scope — nothing tells the model to restructure only, not regenerate or expand the content it's given — and `max_tokens: 4000` is high enough that a verbose run has a lot of room to ramble before hitting a natural stop. The fix targets both: a scope-discipline sentence (preserve input length, don't add new analysis/commentary) plus a moderate `max_tokens` safety cap — not a brevity instruction, which would fight the job this skill actually has.

**Explicitly not decided here, flagged instead:** swapping `llm_model` from `claude-sonnet-4-6` to Haiku for this Format Skill. Mechanical HTML restructuring may not need Sonnet-level reasoning, which could be the bigger win — but that's a quality-risk tradeoff (does Haiku produce structurally correct HTML as reliably?) requiring John's explicit call, same class of decision as `AA-124`'s still-open structural-fix-vs-trim question. Logged to `docs/FEATURES.md` as a new backlog item, not bundled into this session.

  method = method || ' Restructure only -- do not add new analysis, commentary, or content beyond what you were given; output length should track the input''s length, not substantially exceed it.',

// test-s-arch-format-latency-01.mjs — AA-132 verification (pure Node)
let failures = 0;
function check(label, cond) {
  if (cond) { console.log(`PASS: ${label}`); }
  else { console.error(`FAIL: ${label}`); failures++; }
}

const SUPABASE_URL = process.env.SUPABASE_URL;
