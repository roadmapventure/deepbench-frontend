## The one genuinely ambiguous word: "by-hop"

Settled from the codebase, not from taste. The platform's dominant sense of *hop* is a single
delegation-family capability execution keyed by `span_id` (`ARCHITECTURE.md` §19p, "Hop-Event Span
Identity"; one `RoutingHopCard` per hop). **That sense was considered and rejected**, for two
reasons rather than one: it is already served — the per-hop drawer does point lookups against
`ai_call_patterns` by `trace_id`/`span_id` (`LOG-79`/`LOG-131`) — and it is *not aggregable*, since
every span is unique, so a "rollup" over it is 32k groups of one.

The bounded, hop-derived key the platform already buckets on is the `depthN` segment of `feature`
(`useAIActivity.js`'s `byDepth`, feeding `CHI-10`'s p90 waits). **`by-hop` = hop depth.** Rows with
no depth segment — routers, wrappers, embeddings, 18,787 platform-wide — roll up under
`hop_depth IS NULL`: an honest bucket, never a silent filter.

## The change

**One migration, one new view, one new regression test. No `src/`, `api/` or `lib/` change.**

`ses`-style migration `log41_agent_hop_pattern_rollup` creates
`public.ai_pattern_agent_hop_rollup`: the same `sig`/`uniq`/`matched` MATERIALIZED-CTE skeleton the
platform rollup uses, with a `GROUPING SETS` clause producing both cuts and a `grouping()`-derived
`dim` discriminator.

Three properties an editor must preserve — each written into the migration header so it travels
with the code:

- **The signature dedup is untouched, and moving the grouping key into the signature would break
  it.** `agent_id` and `hop_depth` are per-*row* and are deliberately absent from the signature
  (§19k locked constraint 2 — the signature is agent-agnostic). That is *why* the expensive
  `pattern_criteria_matches` still runs once per distinct signature (2,372) rather than once per row
  (34,757). Folding the grouping key into the signature to "simplify" reintroduces the per-row
  evaluation that blew the anon 3-second cap on `LOG-38`'s first attempt.
- **One view with two grouping sets, not two views — measured, not a style call.** Both cuts share
  the identical expensive pipeline. Two separate views pay ~2.2 s **twice** and expose the page to
  the 3-second cap twice per load; the grouping-sets form pays the scan once. The usual objection
  (NULL ambiguity) is answered by the `dim` discriminator.
- **Owner-rights view on purpose — never `security_invoker=true`.** `log_row_signature(l.*)` reads
  the whole row including `caller_ip`, which `anon` has not been able to SELECT since `LOG-124`'s
  column-grant lockdown. An invoker-rights view would 403 for every visitor.

No function is created, replaced or re-signatured, so
`.claude/rules/supabase-function-signature.md`'s overload hazard does not arise — nothing to drop,
no ambiguity to create.

## QA — every assertion with its negative control

1. **Reconciliation identity (the heart).** Per pattern, the agent-cut rows must sum to exactly the
   platform rollup's `call_count` *and* `cost_sum`; likewise the hop cut. **Result: 13 patterns,
   32,441 calls, ZERO mismatches on both cuts, both measures.**
2. **Non-vacuity gate, run first.** Assertion 1 is an equality over a join — an empty view joins to
   nothing and reports zero mismatches, a green line proving the opposite of what it claims. So both
   totals are asserted `> 0` and asserted **equal to 32,441** before any per-pattern comparison is
   trusted.
3. **Grants, both directions** (`.claude/rules/supabase-column-grants.md`): `anon` SELECT returns
   rows (`true`), and `anon` INSERT / UPDATE / DELETE are all **`false`**. The pre-existing rollup
   views still carry table-level `ALL` for `anon`/`authenticated` — a pre-`DAT-18` artifact, latent
   only because a grouped view is not auto-updatable. This view deliberately does not replicate it.
4. **Owner-rights check:** `reloptions IS NULL`. Negative control: `security_invoker=true` makes
   assertion 3's read fail 42501 via the `caller_ip` grant.
5. **The suite-level negative control, run rather than reasoned about.** A deliberately broken
   fixture view (`_negctl`, agent cut only, NULL-agent bucket filtered) was created, the guard was
   pointed at it, and it **FAILED** — *"produced no hop-dimension rows"* — then passed against the
   real view. The fixture was dropped in the same cycle.

## The timing gate — reported honestly, because it did not pass cleanly

**The first anon run under a 3-second cap returned `57014`, statement timeout.** Re-measured:

| Query | As | ms |
|---|---|---|
| new view | owner | 2,326 |
| new view | `anon` | 2,353 |
| **existing shipped platform rollup** | `anon` | **2,194** |

So the new view costs **+159 ms (+7%)** over a query the AI Audit already makes on every load. It is
**not a new class of cost** — but the observed timeout is real evidence that this whole view family
already sits close to the anon cap, with roughly 0.6 s of headroom against a log growing ~3k
rows/month. **That finding belongs to `LOG-132`** (the standing headroom ticket), not to this
ticket, and it is recorded rather than smoothed over.

**It binds the remainder below:** the cutover must *replace* the `log_ids` payload, never add this
query alongside it. Two ~2.3 s queries per page load would be strictly worse than today.

## Named remainder — not shipped, and why

currently serves three distinct client-side jobs — countable-call gating (`LOG-81`),
AI-51-dedup-consistent cost re-derivation (`LOG-97`), and per-agent **latency** joins (`LOG-112`) —
and the rollup replaces the bucketing but *not* the row-level latency join. The cutover must decide
per surface what moves, which is its own session with its own QA. Filed as its own backlog row.
