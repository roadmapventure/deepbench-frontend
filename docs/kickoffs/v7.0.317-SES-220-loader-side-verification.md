## 2. What the remainder actually is, measured rather than inferred

The ticket's code is shipped. What was never done is the thing its own name asks for: **nothing has
ever run the real loader against a real database.**

- `SES-230`'s guard drives `restore-supabase.mjs` against an **HTTP stub** that *hardcodes* the
  strings `428C9` and `23502` (`tests/regression/SES-230-row-level-fallback.js`, the `createServer`
  block). It proves the script's control flow. It cannot prove that a real Postgres produces those
  codes on those column shapes, and it cannot prove that dropping the generated column makes the
  real `INSERT` succeed.
- `SES-223`'s loader arm tested `narrow()` on a fixture manifest with an invented `computed_x`
  column, in a **dry run**. There is no `tests/regression/SES-223-*.js` at all.

So both loader-side halves are, to this moment, **asserted and never executed**. That is the
verification the ship notes left open, and it is what this cycle does.

And it has a live operator cost, which is the second half of the remainder:
`docs/runbooks/restore-from-backup.md` still tells whoever is mid-outage, **unconditionally**, that
*"5 tables and 67% of the rows still will not load"* and that *"Defects (3) and (4) are untouched"*
and that the offsite scripts *"still select `*` and still insert every key"*. All three sentences
were true when written and are false now for a set dumped by today's tooling. `SES-216` already
established the right shape for exactly this — §5b is **conditional on when the set was dumped**,
decided by one operator command — and that shape is what defects (3) and (4) now need too.

## 4. QA — the arms, and the one variable

is whether `manifest.json` carries `loadable_cols`. Fixture tables were created in the drill project
`itcimllfniypelrxsuoh` (never production) reproducing the two real shapes — a
`GENERATED ALWAYS ... STORED` masking column, and a `jsonb NOT NULL` column with 2 of 30 rows
holding the JSON scalar `null` — and dropped afterwards. The NDJSON deliberately **carries** the
generated column in both arms, which is the harder case and the one every set on disk is in.

- **Arm B (negative control = the pre-`SES-223` set):** must reproduce the defect.
- **Arm A (the shipped path):** must load the generated-column table, **and** the generated column
  must **recompute** rather than restore frozen or NULL — the `LOG-124` trap facing the other way,
  which is the assertion that makes this more than a row count.

Exit codes, row counts and the real SQLSTATEs are read back from the target with SQL, not from the
script's own stdout.
