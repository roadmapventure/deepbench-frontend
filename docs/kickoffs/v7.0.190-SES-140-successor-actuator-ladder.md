## Root cause — both actuators refused, for two unrelated reasons

1. **`fire_trigger`** (`SES-139`, `v7.0.176`) — refused: *"this routine was created via http_api,
   not by an agent."* An agent may not fire a routine it did not create. Found live, `SES-140`.
2. **`create_session`** (`SES-141`, `v7.0.180`, John's explicit ruling) — refused **twice** by the
   predecessor cycle `72561db3` at ~14:0xZ, identical message both times: *"the parent session's
   permission mode is not yet available (it is recorded shortly after the parent session starts);
   retry, or run the parent in auto mode."* The parent had been running 25 minutes, so
   *"not yet available"* is **not a warm-up race** — the value appears never to be recorded for a
   session started by a scheduled trigger.

Neither remedy the message offers is reachable from inside a cycle: a retry has already failed at
25 minutes, and *"run the parent in auto mode"* is a property of the routine — which a cycle
**cannot edit** (that is `SES-140`'s original refusal, and `update_trigger` exposes no
`permission_mode`).

## The fix — a two-rung actuator ladder, not a replacement

Tail step (8) keeps Gates A and B, keeps *exactly one* successor, and keeps drain creation
John-only. Only the **actuator** changes, and only by gaining a fallback:

- **Rung 1 — `create_session`, one attempt, now with `permission_mode` passed explicitly.** This is
  still John's ruled actuator (`SES-141`) and costs one call. If the validator only needed a mode it
  could not infer, naming one satisfies it and nothing else in this ticket is needed.
- **Rung 2 — a one-shot Routine, and only if rung 1 was refused.** `create_trigger` with
  `run_once_at` ≈ 2 minutes out and `create_new_session_on_fire = true`. The **scheduler** creates
  the session, exactly as the hourly cron does — which demonstrably works, twelve times today — so
  the parent-permission-mode validation is never reached.

`attempts-per-tier ≤ 1` holds: one attempt per rung, and rung 2 runs only on rung 1's refusal, so at
most one session is ever created.

## Disclosed, rather than left to be discovered

**Rung 2's spawned session is not proven equivalent to a cron-fired one.** The probe's stored
`session_context` inherited the environment and all four connectors, but it carried a **default
`allowed_tools` preset** and **no `sources` entry**, where the runner routine names both
(`Artifact`, `ToolSearch`, `Agent`; and the `deepbench-frontend` git source). Two consequences,
stated as unknowns rather than reasoned away:

- If the clone is absent, the successor fails at step 1 and records it. Recoverable: Gate A means a
  failed cycle fires nothing further, and the :40 cron is untouched.
- If `Artifact` is absent, the successor can do everything except **republish the briefing page**.
  It would still harvest, build, ship and write its ledger row.

Neither is knowable without a real fire, which is exactly what the tail performs. **A failed spawn
is a note, never a wall** — that bound is unchanged, and the cron remains the fallback engine.

are more than 5."* Measured on the board: exactly **one** open ticket is about the drain chain —
`SES-140`, this one. `SES-139`, `SES-141`, `SES-142`, `SES-143` are all `done`; the "more than 5"
are their **briefing cards**, which sit on the page until he taps them and which he has now
Reworked. That distinction is worth his attention and goes on the card, because "five open tickets"
and "five undecided cards about shipped work" call for opposite actions.
