## The canonical query

```sql
SELECT backlog_id, tier, priority_class, status,
       (description ~* '(Beta-gate|Post-beta)') AS beta_marked,
       created_at,
       left(regexp_replace(coalesce(description,''), '^\*\*P[0-9]+[^*]*\*\*\s*', ''), 200) AS gist
  FROM public.backlog_items
 WHERE status <> 'done'
   AND priority_class IS NOT NULL
 ORDER BY CASE tier WHEN 'now' THEN 0 WHEN 'next' THEN 1 ELSE 2 END,
          (substring(priority_class FROM 'P([0-9]+)'))::int,
          (description ~* '(Beta-gate|Post-beta)') DESC,
          created_at DESC,
          backlog_id
 LIMIT 5;
```

Each clause is one of John's rules, in his order: tier `now → next → later`, then
`P1 - Improves John's Skills → P10 - Tooling`, then **beta-marked first, then newest filed, then
oldest** (2026-08-20). `backlog_id` is the final deterministic tiebreak so two cycles reading the
same table always see the same #1.

## Four traps this cycle found live — three of them not in the accepted design

The card's design was verified against the table's *shape*. Running the actual query against the
table's *contents* surfaced four things, and the query above is written the way it is because of
them. All four are `execute_sql` results from this cycle, not recollection.

**(1) The P-class must be ordered numerically, never lexically.** `ORDER BY priority_class`
sorts `'P10 - Tooling'` **before** `'P2 - Inventive'` — it is a text column, and `'1' < '2'`.
The digit is extracted and cast: `(substring(priority_class FROM 'P([0-9]+)'))::int`. A naive
implementation gets this exactly backwards and silently runs the lowest-priority class first.

**(2) `priority_class` is not always one of the ten legend strings.** Live values are
`P2 - Inventive` (1 open), `P9 - Bug Fixes` (43), `P9 - Bug Fixes · FLAGGED` (19),
`P10 - Tooling` (30), and NULL (456). The `· FLAGGED` suffix means equality against the legend
list drops 19 tickets on the floor. Extracting the digit tolerates the suffix; matching the
whole string does not.

**(3) The accepted design's beta predicate is wrong, and this is the substantive correction.**
The card proposed preserving John's beta-first tie order with an `ILIKE '%beta%'` on
`description`. Measured live: `description ILIKE '%beta%'` matches **130** tickets, but the
actual retired declarations (`Beta-gate` / `Post-beta`) appear in only **110**. The 20-ticket
difference is prose that merely contains the letters — **10 of them are the session slug
`beta-doc-0728c`** cited as evidence inside unrelated bug tickets. `AA-161` is the clean example:
its only "beta" is that session reference, and the naive predicate would have promoted it above
genuinely beta-marked tickets. The shipped predicate is
`description ~* '(Beta-gate|Post-beta)'` — 33 of the open classed tickets, against 44 under the
naive form.

**(4) `title` is not a title for imported tickets.** Every ticket imported in phases (a)/(b)
carries the priority-class string as its `title` — literally `'P9 - Bug Fixes.'`,
`'P10 - Tooling.'` — with the human sentence living in the first bolded clause of `description`.
Only tickets *filed* after the import (`HAR-41`, `SES-90`) have a real title. Selection never
reads `title`, so the pick is unaffected, but anything that **displays** the queue does: the
briefing's "Next up" table and its "Next 3" line render this column. Hence the `gist` expression
above, which strips the leading `**P9 - Bug Fixes.**` prefix off the description and shows the
real sentence. Repairing the stored column is follow-up work, filed as a ticket by this cycle.
