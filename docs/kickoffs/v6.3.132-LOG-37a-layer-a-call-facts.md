## 2. CONTEXT

### The problem, stated plainly

Today the write path records its **conclusion** — the string `"tool-use"` — and discards the **evidence** it based that on. Once written, the conclusion is frozen. If it was wrong, or the industry name changes, that row lies forever and nothing can correct it.

This is the single root cause behind all five pattern anomalies logged the same evening this doc was written (`LOG-44` through `LOG-48`), plus `LOG-42`. Live-verified counts from `ai_activity_log` this session:

| Logged slug | Calls | Problem |
|---|---|---|
| `structured-output` | 7,606 | No correct `pattern_vocabulary` destination (`LOG-47`) |
| `tool-use` | 5,576 | **Written for two unrelated mechanisms; which one fired was never recorded** (`LOG-46`) |
| `rag` | 5,799 | 1,199 of them provably false (`LOG-42`); rest need rename (`LOG-45`) |
| `agent-delegation` | 2,796 | May be handoff, routing, or orchestration — undetermined (`LOG-44`) |
| `embeddings` + `intelligent-synthesis` | 1,328 | No vocabulary entry exists at all (`LOG-48`) |

`LOG-46` is the one that proves the point: `tool-use` is set at `request-receivable.js:578` (a JSON schema tool) **and** at `:582` (a web search). Both write the same string. **No override, rename, or audit can ever recover which happened** — the information was never written down. This session stops that from continuing.

### What Layer A is

`ARCHITECTURE.md` §19i (LOCKED) defines six Layer A facts. This session ships **three** — the ones whose data is already computed today and thrown away:

1. **`tool_calls[]`** — the real tool names invoked, instead of one word covering two mechanisms
2. **`retrieved_chunk_ids[]`** — the real chunk ids returned, instead of only a count
3. **`gated_subroutine_fired[]`** — which internal gates actually ran, by name

The other three (`sub_calls_chained[]`, `input_references_other_deliverable`, `self_reported_claims`) have **no existing mechanism anywhere** and need real design. They buy *new* patterns rather than fixing broken ones — explicitly out of scope, John's call. Log them as their own item at close-out if no row exists yet.

### Why these three are genuinely free — verified this session, not assumed

- **`tool_calls[]`** — `rawContent` (the real Anthropic response content blocks) is already in scope at `request-receivable.js:437`/`:449`. Today it is scanned for exactly one boolean at `:457` (`usedWebSearch`) and everything else is dropped.
- **`retrieved_chunk_ids[]`** — `lib/rag.js`'s `queryRAG()` returns `{ context, chunks, matchCount }` (confirmed at `lib/rag.js:12`, `:22`, `:64`, `:66`). `ai-enrichment.js:63-64` keeps `result.context` and `result.matchCount` and **drops `result.chunks` on the floor**. The ids exist and are discarded one line from where they'd be saved.
- **`gated_subroutine_fired[]`** — `guardrailsRan` (`:530`), `enrichDebug.reflect_ran` (`:579`), `enrichDebug.synthesis_ran` (`:580`) are all already in scope at the exact line where the log write is assembled.

### Storage decision (Tier 2 — decided, flagged, not asked)

**One `call_facts` jsonb column**, not one column per fact. Reasons: the remaining three Layer A facts land later and a jsonb object absorbs them with no second migration; `patterns_used` already establishes the jsonb-column precedent on this exact table; Layer B reads the whole object at once anyway.

**Measured, not guessed:** `ai_activity_log` is 19,129 rows / 5.8 MB / ~313 bytes per row, growing ~1,050 rows/day. `call_facts` adds roughly 150–400 bytes typical. Chunk ids are the only unbounded piece — live query of `skill_profiles` shows `match_count` is 10 for one Knowledge profile and 5 for the other six, so a **50-id cap** is generous headroom, not a guess.

## 5. TASKS

### Task 1 — Add the `call_facts` column (Supabase)

```sql
ALTER TABLE ai_activity_log ADD COLUMN IF NOT EXISTS call_facts jsonb;
```

Nullable, no default, no backfill. All 19,129 existing rows get `null`. Postgres does not rewrite existing rows for a nullable column add — no downtime, no lock of consequence. **Do not touch `patterns_used`.**

Confirm with `RETURNING`-style verification: re-query `information_schema.columns` for `ai_activity_log` and confirm 16 columns, the new one being `call_facts` / `jsonb` / nullable.

### Task 2 — `lib/activity-log.js`: accept and write the facts

Add `callFacts = null` to the destructured params of `logActivity()`. In the insert body, add:

```js
call_facts: (callFacts && Object.keys(callFacts).length > 0) ? callFacts : null,
```

**Contract preservation is the whole point of this task:** every existing caller that omits `callFacts` must produce a byte-identical write to today's, plus `call_facts: null`. Do not reorder, rename, or alter any existing field. Do not add validation that could throw — this function is fire-and-forget inside `waitUntil()` and a throw here silently loses the entire row.

### Task 3 — `api/prompt/ai-enrichment.js`: stop discarding chunk ids

At `:63-64`, `fetchSection()` currently keeps `content` and `_rag_chunks` (a count) and drops `result.chunks`. Add a sibling field carrying the real ids:

```js
_rag_chunk_ids: (result.chunks || []).map(c => c.id).filter(Boolean),
```

Thread it upward the same way `_rag_chunks` already is at `:150` (into a by-section map) and surface it on the `enrichDebug` object returned at `:314`, alongside the existing `rag_chunks_by_section`. **Follow the existing threading pattern exactly** — do not invent a parallel mechanism (`CLAUDE-DESIGN.md` Step 4, "search by shape").

Flatten across sections and de-duplicate. Cap at 50 ids; if truncated, that is silent and acceptable — the count already lives in `rag_chunks_by_section`.

### Task 4 — `api/prompt/request-receivable.js`: assemble and pass `call_facts`

Immediately before the `logActivity()` call at `:591`, build the object from data already in scope:

- **`tool_calls`** — from `rawContent`, collect `b.name` for blocks where `b.type === 'tool_use'` or `b.type === 'server_tool_use'`. Reuse the same defensive block-shape handling `:457-459` already uses for `usedWebSearch`; do not duplicate that logic into a second inconsistent check.
- **`gated_subroutine_fired`** — `'guardrails'` when `guardrailsRan`, `'reflect'` when `enrichDebug.reflect_ran`, `'synthesis'` when `enrichDebug.synthesis_ran`.
- **`retrieved_chunk_ids`** — from Task 3's new `enrichDebug` field.

Pass as `callFacts` to the existing `logActivity()` call. **Leave the `patternsUsed` block at `:577-583` completely untouched** — it keeps working exactly as today.

Also pass `callFacts` on the **guardrails-check** `logActivity()` call at `:536` with `{ tool_calls: ['guardrails_check'] }` — that call genuinely made a tool call and today records nothing about it.

## 6. DESIGN RULES

- **Layer A records facts, never names.** If a value being written is a pattern name, it does not belong in `call_facts`. Gate names are internal identifiers, not pattern slugs.
- **No conditionals keyed to agent id or capability slug** in any touched file (`.claude/rules/capabilities-are-data.md`). Capture is generic or it isn't Layer A.
- **Never remove or weaken an existing `logActivity()` call** (`.claude/rules/capability-logging.md`).
- **Additive only.** No existing field changes meaning, type, or nullability.
