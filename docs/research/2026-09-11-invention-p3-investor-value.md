## The pitch

The locked pitch (`VC-THESIS-002`) sells a machine. `VC-EXIT-025` says investors buy a machine whose unit costs are known. Today the platform cannot say what one answer cost. The ledger has carried no dollar figure since August (0 of 12,180 rows priced); cost is recomputed at read time from a JavaScript constant in the browser and, separately, from a five-row `model_pricing` table in SQL — two hand-kept copies of one fact, and neither knows `claude-fable-5-1`, which ran 597 calls in 90 days. `get_ip_stats()` inner-joins the SQL copy and coalesces the sum, so an unpriced model shows as $0.00 on the IP gate: a fabricated zero. And a deliverable cannot be joined to the hops that produced it at all — 7,585 rows in 60 days, none with a task or trace id, while 17,497 log rows in the same window carry a `trace_id` the store handler simply does not write.

The proposal is **Cost per deliverable**: one price book as data, cost computed on the ledger by one SQL function that returns NULL rather than 0 for anything unpriced, `trace_id` stamped on every deliverable at write time, and a `deliverable_cost` view rendered on the deliverable's §19s account as 'what this answer cost' with its defense — hops counted, tokens, priced and unpriced hops, price-book version. John already prices a run before he tests it (`VC-REJECTED-047`: ~$0.31/run); the platform should be able to.

Why P3 and not P1 or P10: the value travels with the asset (`VC-EXIT-027`). An acquirer's architect (`VC-EXIT-007`) runs one query and gets cost per deliverable per agent. The runner's own 'cost per delivery' instrument (P10 row, 2026-09-03) is the factory's cost of a ticket — a different object. The eight P3 pricing rows filed 2026-08-20 (BYOK economics, subscription tiers, margin engine, service catalog, marketplace UI, service profile, deliverable sharing, access tags) all presuppose this number.
