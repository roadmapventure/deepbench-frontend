## The pitch

The exit thesis says the acquirer buys the trained expertise data — "the deeper the DEEP, the more valuable the BENCH" (`VC-THESIS-004`, `VC-EXIT-009`). `VC-LRN-006` says the platform has no denominator for that depth and names the three counts that would have to exist: the share of Skills ever exercised in a logged run, the share carrying a judged score, and whether Skill rows keep a version history. I measured all three today.

- `skill_profiles` holds **117** Skill rows. **46** of them (39%) have ever been assembled into a logged model call — `ai_activity_log.call_facts.assembled_skill_slugs`, written by `api/prompt/db-assembly.js` at the moment the prompt is built, on 18,193 rows since 2026-07-02. **26** were exercised in the last 30 days. **71** have never done work in any logged run.
- **2** Skills have ever been named by the judge (`bench_report_cards.skill_to_improve`); `report_card_usage` shows 3 judge runs all-time, 0 from a real visitor; the rollup covers 2 agents.
- `skill_profiles` has **no version column** (`SES-363`, P10, open, is the row that adds one).

Then I opened the screen a reviewer opens. The Personnel File (`/bench/:agentId`, `PersonnelScreen.jsx`) renders a five-layer "readiness" bar per agent. `computeLayers()` fills it with constants: L1 from `agent.skill`, a hand-kept number in `src/data/agents.js`; L3 fixed at 100; L4 at 72 or 50 and L5 at 68 or 45 by a `trainable` flag. Robyn Castellanos shows skill 88 and Bob Whitfield 71; neither has a single logged run. `agents.usage_count` is 0 on all 30 rows and `rating` is '0'. On the one surface where a buyer's architect would read "what has this agent actually done," the platform shows declared and hardcoded values — the thing `VC-EXIT-023` says must not be true anywhere a diligence engineer looks, and the thing John rejected in `VC-REJECTED-016` (a declared field is a propensity, not evidence).

The proposal is **Personnel File measured from the ledger.** One `security_invoker` view, `agent_skill_exercise` (agent_id, skill slug, logged calls, distinct traces, first and last exercised), computed from `assembled_skill_slugs`; one platform-wide view, `deep_exercise` (Skills total, ever exercised, exercised in 30 days, named by the judge, versioned), for the Agent Roster header. On the Personnel File, the constant readiness bars are replaced by a "Worked" panel beside the Report Card: for each Skill the agent's Capabilities assign, the calls and traces it was assembled into and the last date — and for each Skill assembled that no assignment declares (Alex Reeves: 5 assigned, 6 exercised), the same, labelled as such. An agent whose calls carry no assembly facts (the governance lane today: The Researcher shows 0 exercised on the day it ran) renders "no assembly recorded," never 0 (`VC-INVAR-015`, `VC-JDP-024`). Version reads as an em dash until `SES-363` lands and then becomes a real column. No model call anywhere in it.

Why the platform needs it, in order:

1. **It is the denominator `VC-LRN-006` says the asset cannot be priced without,** produced from what the calls actually did (`VC-INVAR-014`), not from a roster file. Before the feature a buyer cannot tell which of the 117 Skills have ever done work; after it they can, per Skill and per Agent. That is the positive admission criterion `VC-LRN-014` asks for — a named thing a buyer can verify in-product afterwards that they demonstrably could not before — not an argument that the feature is merely not disqualified.
2. **It removes a hardcoded number from the reviewer's screen** (`VC-EXIT-023`, `VC-INVAR-018`). The readiness bar is the kind of value `VC-SYN-001` warns about: the platform cannot say where it came from because it came from nowhere.
3. **It is the market's documentation shape, filled from rows.** Diligence guides now say model cards, dataset manifests and evaluation harnesses are the asset being valued, not a description of it; a 2026 documentation standard for operational agents (Agent Cards) names roles, tool integrations, monitoring hooks and evaluation metrics as what a card must carry; and the model-card literature says the card must become a versioned artifact tied to actual runs. The Personnel File is already DeepBench's agent card. This fills it from the ledger instead of a data file. I searched for a digital-employee product that shows which Skills an agent has actually exercised in production and found none; the nearest neighbour governs skills as a configured dimension.
4. **It is the cheapest thing on the list.** Two views over a column the executor already writes, one panel on a screen that already ships, one constant-filled function deleted. Two cycles. It also gives `AGT-74` (Training Delta) and `LOG-143` their denominator for free: a report-card score means more against "exercised in 804 traces" than against a blank.

The honest risks. `VC-EXIT-026`: read as a stat panel it is a dashboard without new mechanism. What it replaces is the answer — it deletes a hardcoded readiness computation and substitutes rows, which is the mechanism change the lens exists to reward, and it creates the per-Skill exercise record that no later P3 (versions, replay, per-Skill cost) can be built without. Pattern 137: this is not a compliance expectation; no buyer asks for it, which is why none of the surveyed products show it. `VC-LRN-020`, why not P4: a payer picks an agent by what it can do — the capability blurb and the Report Card already serve that reader (`LOG-143`, P1). The exercised-versus-dormant share of the whole corpus is a number only a buyer of the corpus wants; a customer does not care that 71 Skills are dormant, an acquirer prices on it. `VC-EXIT-027`, why not P1: the value travels with the asset — a measured DEEP is worth more to whoever owns it, whether or not John is in the room.
