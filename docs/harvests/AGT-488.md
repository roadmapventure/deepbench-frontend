## §RULES — the five `<from>`/`<to>` pairs, verbatim

`replace()` is exact-substring. Copy each `<from>` byte for byte; it is the live row text as measured above. Marker ownership: **R1-R3 put eight markers in `vc-prioritization-duty`** (`TEN IS A FLOOR`, `5s, then 4s, then 3s`, `creation date is filed_at`, `14 days or less: oldest first`, `validated first (AGT-493)`, `ONLY HER OWN GRADES`, `score a parked ticket 0`, `DUTY ROW WINS OVER THE RUNBOOK`) and **R4 puts the ninth, `lane A names no project`, in `vc-john-severity-tree`**. R5 carries no marker of its own; the gate proves it by the absence of its `<from>`.

### R1 — duty row, the floor and the fill order (d.3)

FROM:
```
WHAT SHE KEEPS. Ten tickets scored 3 or greater in each active (executing) project, at any time. Count a project's open or partial tickets with need_score 3 or greater.
```
TO:
```
WHAT SHE KEEPS. TEN IS A FLOOR, not a cap (John, 2026-10-13): ten countable tickets in each active (executing) project, at any time. Countable is what public.countable_tickets_per_project() counts -- an open or partial ticket scored 3 or greater that carries her own unreversed requirement-check grade, is not blocked, not parked, not claimed and not waiting on John. She fills to ten with the 5s, then 4s, then 3s. A 5 that fits an active project moves in even when that project already holds ten, and the project then holds eleven or more. Nothing is swapped out to make room for it, and a 3 already in is never swapped out.
```

### R2 — duty row, a parked ticket scores 0 (d.33, the tools half)

FROM:
```
carry a parked 0 in the reason ("PARKED (0) until <project> is active") and score the ticket 1, which the pick skips.
```
TO:
```
score a parked ticket 0 and keep "PARKED (0) until <project> is active" first in its reason. Both validators, apply_requirement_verdict() and the ck_backlog_need_score CHECK all take a whole number 0-5 (v7.0.826, v7.0.844), so the old instruction to score it 1 is withdrawn; the pick skips anything under 3 either way, and the PARKED prefix is what the floor's own sensor reads.
```

## §CALLS — mine, recorded and reversible (JOHN-0925-DESIGNER-DECIDES)

1. **Lane A gets no announce sensor.** d.18 leaves the mechanism to me. `projects.john_pinned_at` is set on 2 of the 3 `executing` projects, both stamped 2026-09-28/29, so it cannot mark one top project; `priority` always has a lowest member, so reading lane A off it would announce a top project every single run — the opposite of the rule. A `john-ruling` row would work but nothing writes one for this, so the rule is written to be inert until a run announces one, and the sensor is a finding (pattern:68, pattern:2). Reverse: name a signal and amend R4.
2. **The runbook is not edited; the duty row is given the precedence sentence.** `docs/runbooks/victoria-reorg.md` §(c) is the byte-source the live `victoria-reorg` routine copies, and `scripts/check-routine-prompt.js` compares the two, so editing the repo half alone makes that check red while editing the live routine is John's hand (pattern:166). The ticket's own "the duty row wins over the runbook" is exactly the instrument that resolves the contradiction without touching either. Reverse: John re-words §(c) and the live prompt in an attended session, and the precedence sentence stays true anyway.
3. **The validator is named by ticket, never by agent.** d.30 assigns the 14-day validation to the Governance Architect. Rule #1 (§19d/§19e) forbids one agent's data naming another, so R3 says `validated first (AGT-493)` and nothing else. Reverse: if Rule #1 is ever amended, the row can name the role.
4. **Markers over full-text pins.** The gate, the guard and the prompt proof all assert nine short literals rather than an md5 of the whole method, because the next ticket on this epic will legitimately add sentences to these rows and an md5 pin would make every such ship red (pattern:162 — grade the change, not the clock).

## §ALTERNATIVES considered and dropped

- **Rewrite both methods wholesale from the requirements doc.** Rejected: the duty row is 3,079 bytes of John's own 2026-10-09 wording and the tree is 16,212, much of it verbatim quotation. A wholesale rewrite silently drops his words (pattern:166, pattern:90) and cannot be proven not to have. Five `replace()` statements with a row-count assertion each can.
- **Put the rules in the runbook instead.** Rejected: that is the artefact the ticket demotes, and the live routine copies it.
- **Add a `victoria_fill_rules()` function returning the rules as data.** Rejected: the rules ARE data already — a `skill_profiles` row — and the assembly path already renders them (pattern:17, pattern:8). A second home would be a second source of truth.
- **Pin the methods by md5 in the guard.** See §CALLS 4.

## §ARCHITECTURE — the sentence for §19v, verbatim

THE FILL RULES REACH HER OWN ROWS. `AGT-481`, `AGT-483` and `AGT-485` built the floor's sensor, the parent lift and the daily check, and `AGT-486` put the charters in front of her — but the two rows she actually reads her duty from still carried the 2026-10-09 wording: ten tickets as a target rather than a floor, no fill order, no `filed_at`, no ordering inside a score, no freshness rule, no statement that only her own grades count, lane A still naming "the mcp server", and both rows telling her to score a parked ticket 1 because "the checker does not accept 0 yet" — which `ck_backlog_need_score`, `apply_requirement_verdict()` and both validators have accepted since `v7.0.826`.
