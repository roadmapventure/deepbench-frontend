## 2. The ticket's hypothesis against the numbers

The ticket asks for `pg_constraint` against `pg_index` for every FK whose `confrelid` is either table, plus a trigger check. What this cycle could read, and what it could not:

- **Every FK referencing either table (read from the PostgREST OpenAPI document, which prints `Foreign Key to \`t.c\`` per column, 124 exposed tables):** exactly two — `capability_skill_profiles.skill_profile_slug → skill_profiles.slug` and `agent_skill_pins.skill_profile_slug → skill_profiles.slug`. **No column in any exposed table references `capability_skill_profiles`.**
- **Dependent table sizes (`Prefer: count=exact`):** `capability_skill_profiles` 347 rows, `agent_skill_pins` 14 rows, `skill_profiles` 194 rows.
- **Index on `capability_skill_profiles.skill_profile_slug`:** not readable from here (`pg_index` needs a SQL channel). docs/harvests/AGT-434.md §2 (measured 2026-10-10 over the MCP) says it is unindexed and the table holds one index, its pkey; the same harvest (§1, read live then) says **no triggers exist on `capability_skill_profiles`, `skill_profiles` or `agent_capability_assignments`**. Both are from that record, not re-measured this cycle.

Even taking the FK as unindexed, the cost ceiling of the hypothesis is 49 deletes × a sequential scan of ≤347 rows (and, for the skill row, ≤14 pin rows). That is tens of thousands of row comparisons in total — milliseconds, not sixty seconds. The hypothesis cannot produce the measured symptom on these tables. Adding the index would change nothing measurable and is not proposed (harm needs evidence: north star, "a safeguard that did not act is not harm").

## 3. What actually caused the timeout — measured by sibling cycles, not re-run here

The deletes could not be re-run this cycle: the 48 rows no longer exist, and no rolled-back probe is possible without a SQL channel. The platform's own later measurements isolate the wall to the connector's write path, not to Postgres:

- docs/harvests/HANDOFF-self-completion-session2-1012.md L33: "Supabase MCP hangs at 60 s on any payload containing DELETE or DROP (reproduced 4x by the AGT-455 Builder, **even a one-row delete**). … AGT-465 names the wrong cause (unindexed FK)." A one-row delete has no FK scan to be slow.
- docs/harvests/AGT-434.md §2 (2026-10-10): the connector's own tool text says destructive statements may require confirmation; unattended, nobody confirms. The v7.0.829 migration's lines 272-273 were exactly such DELETEs (arm 6). Design rule adopted there: INSERT/SELECT/UPDATE/DDL only across the MCP; row removal over PostgREST.
- AGT-303 (open): heartbeat UPDATE through the connector timed out 4× at 60 s, same UPDATE instant over PostgREST, `pg_stat_activity` showed no blocker, one trigger on the table.
- AGT-478 (open, revalidated 2026-10-27): five consecutive UPDATEs timed out while SELECTs and INSERTs through the same tool answered; the identical notes append landed over PostgREST in 93 ms with every trigger intact. Its text already names AGT-465 as a connector-side instance alongside AGT-303, and its fix (2) forbids attributing a tool timeout to the database without retrying the identical statement on the second path. AGT-547 (open, 2026-11-03) is the newest instance.

So the honest answer to the ticket's own question is: the deletes were not slow; the connector did not run them. The destructive-statement confirmation prompt is the best-supported mechanism (it fits "DELETE or DROP anywhere in the payload, even one row" and "UPDATE hangs while INSERT answers" only partly — the UPDATE instances show the connector's write ceiling is wider than DELETE/DROP). Settling that differentiator is AGT-478's scope, and this cycle has no instrument to settle it.

This is a conflict between the ticket's wording and a recorded ruling, surfaced here for the removal card rather than re-litigated: the ticket's boundary was written before the ruling and the ruling governs the shipped row.
