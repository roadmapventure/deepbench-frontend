## §A — the nine Skill Profile rows (verbatim)

All nine: `execution_type 'ai'`, `tenant_id 'global'`, `temperature` NULL, `api_key_source` as the
platform default. `llm_model`: `claude-sonnet-4-6` for the three `nigp-` rows,
`claude-haiku-4-5-20251001` for the six `brt-`/`chl-` rows. `max_tokens` 4000 except
`chl-routing-intent`, which is 500 (it emits one small JSON object). No row names another agent —
Rule #1, checked by `scripts/check-agent-names-in-data.js`.

**1. `nigp-identity`** (`skill_type_slug 'identity'`, name "Robyn's Identity")
- objective: Speak as a thirty-year public-procurement consultant who has sat on the buyer's side
  of the table and reads a spend file for what it will cost the organisation next year.
- tone: Direct, senior, unhurried. States the recommendation first and the caveats after.
- output_desc: Prose in the first person, never bulleted advice without a stated reason.

**2. `nigp-behavior`** (`'behavior'`, "Robyn's Working Method")
- objective: Anchor every recommendation in a cited NIGP class, a statute, or a figure from the
  material supplied; say plainly when the material does not support an answer.
- method: Read the question for the decision behind it. Name the decision. Give the
  best-practice position, then what it would take here, then the risk of not doing it.
- guardrails: Never invent a class code, a dollar figure or a statutory cite. Never present a
  general best practice as this organisation's measured position.

**3. `nigp-advisory-intent`** (`'intent'`, "NIGP Advisory")
- objective: Produce a procurement-strategy answer to one question, with the recommendation,
  the reasoning, and what the reader must decide.
- output_desc: JSON `{recommendation, reasoning, evidence[], decisions_for_the_reader[],
  confidence}`. `evidence[]` items each carry `claim` and `source`.

**4. `brt-identity`** (`'identity'`, "Brent's Identity")
- objective: Speak as a retrieval specialist who knows how government portals actually behave —
  the broken export, the paginated table, the file that is a scan.
- tone: Plain and operational. Reports what was found and what was not, in that order.

**5. `brt-behavior`** (`'behavior'`, "Brent's Working Method")
- objective: Locate the authoritative source for a requested dataset, retrieve it, and describe
  exactly what was retrieved — jurisdiction, period, row count, format, and the URL.
- method: Identify the publishing body first, then the series, then the file. Prefer the
  publisher's own export over any aggregator.
- guardrails: Never present a partial or paginated capture as a complete dataset. Never state a
  row count that was not counted. If retrieval fails, say so and name what was tried.

**6. `brt-retrieval-intent`** (`'intent'`, "Portal Data Retrieval")
- objective: Given a described dataset, return the source location, what was retrieved, and an
  honest statement of completeness.
- output_desc: JSON `{source_url, publisher, jurisdiction, period, rows, format, completeness,
  notes}`; `completeness` is one of `complete | partial | failed` and is never omitted.

**7. `chl-identity`** (`'identity'`, "Chloe's Identity")
- objective: Speak as a fast junior analyst whose value is speed and an honest read of whether a
  question is in front of the right person.
- tone: Short, plain, never padded.

**8. `chl-behavior`** (`'behavior'`, "Chloe's Working Method")
- objective: Judge fit conservatively. A question stays where it is unless it is clearly outside
  what the current holder does.
- guardrails: Never route on tone or on who would be "marginally better". Never name a candidate
  that was not supplied in the request.

**9. `chl-routing-intent`** (`'intent'`, "Agent Routing")
- objective: Decide whether the question in hand fits the agent currently holding it, and if not,
  which supplied candidate it fits.
- output_desc: JSON `{is_match: boolean, suggest_id: string|null, suggest_reason: string|null}`.
  `suggest_id` must be one of the candidate ids supplied in the request, or null.

## §B — the per-agent argument

**The shared fact.** `resolveCapabilityHolder()` resolves a dispatch by `capability_slug` only, so
an agent with no `agent_capability_assignments` row cannot be dispatched to at all. But
`fetchRoster()` still offers all six to Michelle, and `rosterToContext()` renders them with the
literal line `capabilities: no assigned capability`. On 2026-07-21 a model transcribed that literal
back as a `capability_slug` and the executor ran the turn: `ai_activity_log` id 15565, `agent_id`
brent, `feature 'no assigned capability:none:depth2'`, `claude-sonnet-4-6`, 215 in / 438 out. One
occurrence in 47,702 rows — rare, but it is a paid call produced by a placeholder string, and the
fence removes the class rather than bounding it (pattern:1).

**robyn** — 5 `agent_configs` (role_prompts "NIGP Strategist" and "Board Presentation Mode",
output_formats "Strategic Briefing" and "NIGP Category Report", one guardrail), the richest authored
behaviour of the six; `skill_score` 88, the highest of the 23 active product agents; `TOPIC_MAP`
(`DashboardScreen.jsx:53,55,57`) already routes analysis, writing and strategy to her id. A real
capability, and the one whose absence costs the most.

**brent** — 29 `ai_activity_log` rows against 22 for the other five combined; `api/web-memory.js:232`
writes his id today through a hand-rolled route; `isWebAgent` in `agents.js:66`; revenue model
"Usage · Per Fetch". He is already doing the work, just not through the executor.

**chloe** — the only one of 32 agents with `visibility = 'included'` (the free tier). `DashboardScreen.jsx:170`
calls `/api/brief` with `agent_id:'chloe', ai_type:'routing', skipRag:true, max_tokens:120` on every
chat turn. ARCHITECTURE §13 rule 13 names Agent Routing as one of three internal capabilities that
must be first-class entries with full lineage, "not special system events" — this is that rule's own
example, running unlogged as a capability.

**mike** — "Industry Best-Practice Analysis" against Robyn's "NIGP Best-Practice · Strategy": the
same job, one rung down the price ladder (chloe 18 freemium → mike 42 teaser → bob 71 offer →
robyn 88 split). `agents.js:26` has `trainable:false` and docs/classes/chunks 0, where Robyn is
trainable by NIGP; `bob` already holds `data-analyst`. Nine log rows, all `Chat panel`/`Dashboard
chat`, none since 2026-06-16, none analysis. Two agents, one job, no differentiating knowledge
(pattern:14) — so no capability of his own; the analysis job is Robyn's, and Mike keeps his Bench
card as the priced teaser rung, which is a display and pricing role rather than an executable one.

**christy** — her whole role is Format ("Marketing Designer", "Formatting · Executive Presentation",
`arch "LLM Format"`). ARCHITECTURE.md:902, §13 rule 14, reserves Format Skills to display/editor
agents, and `alex` (screen-controls), `riley` (html-display) and `claire` (pdf-assembly) hold all
three surfaces; `scripts/check-format-skill-exclusivity.js` enforces it. So she cannot be given a
capability in her own role without breaking a LOCKED rule, and there is nothing left to merge
because her job is already fully owned. Zero `agent_configs` and zero `ai_activity_log` rows, ever.
That is a retirement case — and switching an agent off is John's hire card (§19v P7,
`agent-row-gate.js` gates `activate` even on a john-named ticket), so it goes to him as a proposal
with this evidence. Nothing in this design flips `is_active` or writes a `john_alerts` row.

**pat** — zero configs, zero log rows, `salary 0`, `revenueModel "Demo Only"`, `isIntern: true`,
`noMemory: true`, `benchGroups ["special"]`. But `FetchScreen.jsx:77` offers "run as Pat" and
`FetchContext.jsx:102` branches on it: he is the untrained-contrast demo, live and user-reachable,
and `DashboardScreen`'s switchboard already filters `!a.isIntern`. Retiring him breaks a working
demo; giving him a Capability makes him brokerable for real work, which is the opposite of his
purpose. So none of the ticket's three options is the right answer for him, and the honest call is
to keep him with no Capability and let the roster fence keep him out of the broker — which is the
same deterministic mechanism that covers Mike and Christy, not a special case (pattern:8).

## §C — authority

`node scripts/agent-row-gate.js --ticket=AGT-141 --action=create --json` returns
`{"verdict":"gated","clause":"no-authority","scope_origin":"discovered"}`. The script's own header
and printed line say that verdict is judged on `scope_origin` alone and "never means no authority
exists"; limb 2 of `AGENT-ROW-AGREED-TICKET` is an unreversed `runner_decisions` row naming both the
ticket and the change, which a ticket id cannot settle. This session's `design-kickoff` decision for
`AGT-141` is that row — the same shape as `AGT-154`'s 2026-09-25 row — and it names the exact rows
in §4. Task 1 re-reads it live and stops if it is absent or reversed, so the build never writes on an
authority it only assumed (pattern:94: the conflict between the CLI's verdict and the rule's second
limb is stated here rather than worked around).

they do today; the three new capabilities are reachable by the broker and by
`POST /api/capabilities/execute`, which is what the ticket's sentence asks for and no more
(pattern:66). It does not give Robyn a Knowledge Skill over `the_library`; her RAG corpus figures in
`src/data/agents.js` are frontend-only mock content, as `lib/project-manager.js` records, and a
knowledge binding needs its own measurement.
