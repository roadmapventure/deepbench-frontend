## The question I was asked, and the answer

You asked: is there an admissible redesign that delivers value without the gated DDL apply, or is the only remaining step one an attended session must take?

Neither, as worded. Three measurements changed the question.

1. **"DDL has no unattended path" is no longer true.** The card's ruling (2026-11-13 07:02 UTC) rests on that sentence. `supabase_migrations.schema_migrations` holds 13 migrations recorded after the 2026-11-10 park (`20261111081308` to `20261114091356`). Cycle `53254e08`'s own row says of `agt590_outcome_columns`, an in-place ADD COLUMN on two existing tables, 2026-11-13 08:53 UTC: "the unattended apply_migration went through". The 11-10 cycle's note that "any ticket whose fix alters an existing table is currently unshippable unattended" is contradicted by that row.
2. **The built branch cannot go green even if someone applies it.** `c5de296`'s test, arm 3a, asserts that exactly one migration is recorded past `20261110140629`. Thirteen are. Applying the 11-10 migration from a desktop would leave that arm red on "14 migrations are recorded", so "apply it and let arm 3 go green" cannot happen as written. The test has to be rebuilt whoever applies.
3. **Nothing worth shipping exists without a schema change.** See the candidates below.

So the work that remains is a rebuild either way, and a migration through `apply_migration` is not, on the evidence, closed to an unattended cycle. What is closed is re-sending the 11-10 text. The kickoff is a different migration with a smaller reach, sent once through the same sanctioned tool.

## The redesign and why it differs

Mechanism. The first design gave every one of the then-62 rows a `text_updated_at`: 41 took `created_at`, the rest took `updated_at`, and the column was made NOT NULL. Those values are inferences; none of them is a time the text changed. This design leaves the column NULL until a text change is actually observed by the trigger, and the rule reads NULL as "not changed since tracking began".

- Reach of the apply: 0 of 63 existing rows written today, against 62 of 62. One statement stamps `updated_at` into the new column only for rows the old rule calls due for a reason other than the tagging pass; that set is empty today, and the statement exists so an edit John makes between this design and the apply is not lost (local case E: one such row stays due).
- No inferred value is stored, so the "24 rows inferred unchanged" risk is no longer written into the table as if it were a fact. It remains a risk about the rule, and the STOP LINE names it.
- Undo is the same three drops. The down is card-only, as it was before and as it was for `agt543_napkin_dilbert_note` on this table.
- Behaviour John sees: identical to the first design. A tag, category or archive edit leaves an idea alone; a text edit makes it due; a new idea is due.

The test differs for a second reason. The old arm 3 asserted facts about the live world that the next unrelated ship falsified: "exactly one migration past X", "no null stamp", "every new-due row is old-due". The new arm asserts only what this change makes permanently true (the migration is recorded by name, the column reads) and prints the two due counts. The both-ways proof of the trigger stays inside the migration's gate, where it runs once at apply against a fixture that is rolled back.
