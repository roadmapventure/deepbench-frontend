## 2. Governing architecture

- **§19v** (self-building platform): the record of a run is reviewed by the platform itself; a green/absence declares what it did not grade. The stamp makes "reviewed, nothing found" a fact the record holds.
- **§19j** (deliberately-empty findings): the exact failure of the ticket's predicate — absence of a row is not evidence of absence of a review.
- **§19k**: the reviewer turns the routine loops are the existing `audit-run-review` capability, logged by `scripts/agent-log.js` exactly as today; no new model call shape.
- Rule #1 (§19b/§19d): the pick-up list is data about cycles (ids), never an agent naming another agent.

## 3. The mark — alternatives weighed

1. **`runner_cycles.notes` line via `scripts/cycle-note.js` (chosen).** `cycleNote(argv, env, doFetch = fetch)` is the one PostgREST append the tail already uses for EVERY notes line (runner-cycle.md:4294, AGT-547), with `appendNote()`'s never-twice shape. `doFetch` defaults to the global at call time, so the agt-137 fetch stub drives it. The citation guard (`runner_record_citation_guard`, docs/design/agt-173-card-citation-guard.sql) refuses only (a) newly cited REMOVED backlog ids and (b) `commit <7-40 hex>` tokens no push/graded sha resolves — the stamp text `RUN-REVIEW STAMP: <k> findings, <w> written, <week>` contains neither (no ticket id, no "commit"). Predicate is one `notes.not.like` filter; the precedent of notes-prefix signatures as a run's record is already in `ticket-owner.js`, `requirement-check.js`, `render-standing-brief.js`, `rank-backlog.js` (pattern:17).
2. An `audit_findings` row of a "reviewed, nothing found" kind — pollutes a findings ledger with non-findings; every reader (audit-review.js, the weekly report) would have to learn to skip it.
3. A `runner_decisions` row — `record_decision` kinds are constrained and reversible decisions are not what a review is.
4. A new `runner_*` marker table — a migration plus the SELECT-open default (SES-384) revoke plus grants: a 4th/5th file and a schema for one boolean.

## 4. The window and the cap

- Window: `ended_at >= isoWeekStart(now)` — `isoWeekStart` is exported by `scripts/audit-ledger.js:178` and is the ledger's own unit (fingerprint `seen` is per ISO week; AGT-137's contract is "ONE finished cycle, reviewed the week it ran"). No new constant (pattern:67). Consequence stated in the routine: a cycle still unstamped when its week ends stays unreviewed and the missing stamp says so. The 870 pre-AGT-137 cycles are deliberately NOT a backlog to drain (hundreds of reviewer turns over records from before the capability existed).
- Cap: `BACKLOG_LIMIT = 3` per prepare, matching the Finish line's "<= 3 passes" bound in the same (7e) paragraph. At ~15 cycles/day the 41 drain in about a day; steady state is the one or two chained predecessors of a drain.
- Newest first (`order=ended_at.desc`): the freshest record is the actionable one and is "the one it just closed".
- Exit 3 (this cycle not reviewable) still prints the unreviewed line and the routine still loops — otherwise a day of did_not_run cycles would never drain the backlog. Cost: one or two GETs.

## 5. What this does NOT do (named residue, not filed)

- **A parallel cycle's tail can be reviewed by a sibling before its own (7e) runs** (B42: cycles run in parallel; `ended_at` is written at ship time, before the tail). The second review's findings re-read as `seen` (UNIQUE fingerprint+week), so the record is unharmed; the cost is one reviewer turn. A prepare-time claim would close the window but would make a dead session strand a cycle as "reviewed" — the silent gap this ticket exists to remove — so the stamp stays at ingest time.
- The three clean (7e) cycles of this week are reviewed once more (the one-time cost of the backfill), then stamped.
- `runner-cycle.md` (7e) still says "else exit 3 — nothing to review, no cost"; true of the cycle itself, and the step delegates to the routine. It is untouched because `tests/regression/ses-413d-questions-scoreboard.test.mjs` (`BYTES_AT_SHIP`) and `agt-525-tail-push.test.mjs` (`RUNBOOK_BYTES = 380920`) pin its byte count exactly: editing it is a 5-file build (script, test, runbook, two pins) against a 3-file cap, and the routine is the home of the per-run procedure anyway.
