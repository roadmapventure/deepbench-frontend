## 2. Two things the ticket did not know

**(a) A second truncated read, in the same file.** `career_records?kind=eq.posting&select=data` appears twice (`:960` in `fetchPostings()`, `:1118` in the `knownJobIds` loop) with **no `order=` at all**, and `kind=eq.posting` now stands at **1,062 rows**. Both are already truncated today, so the LinkedIn dedupe set is missing 62 postings. Because the fix pages inside `db.get()`, those reads start paging — and an unordered page boundary may repeat or skip a row, so the kickoff's task 1 refuses a multi-page read with no `order=` and task 2 gives those two reads `&order=id.asc`. That is a red the change itself causes, fixed inside the change (pattern:124), not a widening of AGT-469: neither the posting window nor the dedupe logic moves.

**(b) The suite is already red, with this ticket's own symptom.** `scripts/pre-build-baseline.js` over the graded set reports `agt-84-personal-agent.test.mjs` RED on the UNCHANGED tree: `write_backs went 0 -> 0, expected +1`. Part (e)'s AGT-268 arm writes a `posting` row, re-renders and expects the write-back count to rise by one. The row it writes is the newest row in the table, so it lands past the 1,000-row cut and never reaches the prompt. That red is AGT-569, and the fix must clear it — a second, independent discriminator the ticket did not ask for and did not know it had.

## 3. Why the pager goes in `db.get()` and not in `readRecords()`

`readRecords()` is one of ~20 callers. The ticket's own sentence ("page inside db.get() itself, so every reader in personal-agent.js is covered") is also the cheapest variant that proves the claim: one function, one signature, no caller edited. The alternative — paging the three record queries — leaves `:960`, `:1118`, `readWeek()` and every future read on the same trap.

Two sub-decisions inside that:

- **A `limit=` query gets one page.** `:782` (`capabilities …&limit=1`) and `:1113` (the watermark log row) both carry `limit=1`, and PostgREST reports the FULL count in `content-range` when a limit is set — so a loop driven by that denominator would keep fetching. A caller that named its own ceiling gets exactly one request, which is also the old behaviour.
- **A short read throws, it never shortens the prompt.** The final `out.length !== total` check is the ticket's own requirement and the reason the bug was invisible: the script reported success at 754 for three weeks.

## 4. What this build deliberately does NOT do

- **One shared pager.** `scripts/market-agent.js:…` holds a **byte-identical** unpaged `get()` (`git grep -F -l "async function get(pathAndQuery) {"` → exactly those two files), and `export const PAGE_ROWS = 1000;` is already declared twice (scripts/audit-board.js, scripts/ticket-owner.js) with scripts/audit-headroom.js importing one of them. The right end state is one shared paged helper all four call. That is a 4th file against a cap of 3, and the Designer may not split or widen on his own authority (pattern:172), so it is filed with this evidence. `market_records` is 406 rows, so market-agent.js is latent, not broken, today — which is why shipping the per-instance fix now and filing the normalisation is the right order (pattern:120).
- **A prompt budget.** At the measured ~1,702 bytes per record, the fixed growth-review render is **~3.0 MB** (1,283,258 bytes at 754 records → ~1,775 records post-fix). The record half of that prompt was never inside any model's context window even at 754. Fixing the READ is correct and is what the ticket asks; it converts a silently stale answer into a loud one. But it is NOT a working capability, so the kickoff's STOP LINE forbids the build from claiming it is, and the budget is filed as its own row.
- **Any `&order=created_at.asc` tiebreak beyond the file.** 14 tracked files hold that clause; only `scripts/personal-agent.js`'s 7 are in scope.

## 5. The QA, and why it would fail if the change did nothing

`records_loaded` is `Σ records + corrections.length`. One page caps the records at 1,000, and there are 41 `correction` rows in the whole table, so **1,041 is the arithmetic ceiling of an unpaged read** — unreachable regardless of re-runs, new rows or ordering. Post-fix floor, measured: 2,017 − 283 `status:new` postings dropped by `REVIEWED_POSTINGS` = 1,734, plus the capability's corrections ≈ **1,775**. The test asserts `> 1041` and that the rendered prompt carries the newest `review` row's id (today `f6d47c8f-…`, created `2026-10-26T11:40:19Z` — read live by the test, never pinned), and part (e)'s standing red must go green. Three signals, none of which a no-op can produce.
