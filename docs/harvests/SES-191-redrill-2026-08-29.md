**The two missing views are exactly `_backup_inventory` and `_backup_schema_ddl`** — `SES-214`'s
named defect, reproduced precisely rather than rediscovered: the inventory view's own predicate
excludes `_backup%`, so it cannot describe itself or its sibling. Every other view restored. The
consequence `SES-214` states is confirmed by this drill: **a platform rebuilt from this set restores
once and cannot then back itself up**, because `dump-supabase.mjs` reads its table list from the
first view and its DDL from the second.

**Two failure classes in the apply, and only one of them was known.**

- **`42883 function … does not exist` on 6 views** — `SES-214`'s other half: `schema.sql` emits
  VIEWS before FUNCTIONS. The documented two-step workaround clears it; all 6 applied on the second
  invocation.
- **`42501 permission denied for language c` on ~114 statements — NOT previously recorded.**
  `schema.sql`'s FUNCTIONS section emits the **pgvector extension's own C functions**
  (`halfvec_*`, `array_to_vector`, `cosine_distance`, …) as if they were user functions. They are
  already created by `CREATE EXTENSION vector` at the top of the same file, and no Supabase role may
  create a `LANGUAGE c` function, so every one of them fails on every restore, forever. It is
  **harmless to the outcome** — the extension supplies them — but it means a clean restore prints
  ~114 permission errors that an operator has to know are noise, which is exactly the kind of thing
  that makes a real error invisible. Filed as `SES-241`.

### The finding worth carrying forward: 6 rows needed a second invocation

The first restore pass left **8** rows unloaded, not 2. Six of them were a **self-referential
foreign key ordering** problem, and a second run of the same command recovered every one:

| Table | Pass 1 | Pass 2 | Cause |
|---|---|---|---|
| `backlog_items` | 714 of 719 | **719** | `backlog_items_blocked_by_fkey` — rows whose `blocked_by` points at a row later in the same file |
| `runner_drain_scope` | 103 of 104 | **104** | `runner_drain_scope_item_id_fkey` — cascading on one of those 5 |
| `pending_confirmations` | 310 of 312 | 310 of 312 | the jsonb scalar `null`; unchanged, and unchangeable |

**The multi-pass loop retries whole TABLES, never intra-table row order**, so a self-referential FK
is invisible to it: every pass sends the same rows in the same order and fails identically, and the
row-level fallback then loads each row once, individually, in that same order — which is why the
5 rows whose referent sorts later still miss. Nothing is lost; the operator simply has to run the
restore twice, and **nothing in the runbook says so**. Filed as `SES-242`.
