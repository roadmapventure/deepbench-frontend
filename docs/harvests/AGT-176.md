## 4. The scoping decision, on this ticket's merits

Either the runbook trio (§3) or part (c)'s code fits — never both. Chose **the code**. Four reasons,
in descending weight:

1. **pattern:10** — when a correct value already exists deterministically, no model may be put in
   charge of it, *and after two failed instruction-level guards, go structural, never a third
   wording*. The value is an SQL aggregate over the cycle's own rows. The runbook edit is a third
   wording of an instruction that tells a model to type a number.
2. **The platform has already ruled on this exact step.** `scripts/settle-ship.js`'s own header:
   *"A prose rule a human has to remember at the end of a long cycle is a rule that gets forgotten at
   the end of a long cycle."* That script exists because step 9's prose failed twice in one day. The
   cost line is the same step and the same failure mode.
3. **The architecture names the code, not the prose, as the unbuilt thing.** `ARCHITECTURE.md:4`
   (`LOG-149`, §19t/§19v): the meters reading the ledger — *"the `runner_cycles` close-out sums"*
   among them — *"are slice 2 and still read cycle rows."* This slice is that declared slice 2.
4. **The runbook sentence is, today, descriptively true.** §5 below shows every recent cycle has zero
   billable rows, so *"$0 is the normal value"* currently describes reality. Rewriting prose that is
   presently accurate, at the price of the mechanism that will be needed the moment it stops being
   accurate, is the worse trade.

**What the other half costs, stated plainly:** `runner-cycle.md:4069-4070` keeps a sentence that will
be wrong the first time an executor call is billed, and step 9 keeps hand-typing the card's cost
split, so the card's `cost_usd` stays model-typed until F1 ships. The ledger column
(`api_cost_dev_usd`) does get its deterministic writer this cycle; the *card* only gets it when the
card already exists at step 7. Filed as **F1** with the full file list, the `BYTES_AT_SHIP` value and
the byte headroom, so the next cycle re-derives nothing.

This is the third consecutive turn to lose work to this coupling (AGT-174 and AGT-180 each chose the
code and filed the line; AGT-176's prior slice lost two tasks to it). At six cycles it is a standing
finding, not an accident — the right long-term answer is a cap waiver for the trio, which is a
process call, not a feature call.

## 5. The measurement that changed the design: every 0 on this chain is honest

The ticket implies stored `0`s are wrong. They are not — measured read-only:

- `call_source = 'executor'` has **never** been written to `ai_activity_log`. Zero rows,
  platform-wide, at any date.
- For the eight newest `runner_cycles`, rows at `visitor_id = eq.<cycle id>` number 0-4, and **every
  one carries `call_source = 'session'`** — the runner's own sub-agents on subscription tokens, which
  bill no dollars by construction.
- Priced rows exist, but only on `call_source = 'ui'`: newest `id 45595`, 2026-09-15,
  `cost_usd 0.025557` (also 45493/45492/45478/45448 at $0.026-$0.034).
- Cycle `40d8dfe3-764d-467e-bf2b-7600e522d966`, the prior kickoff's example, reads **4** rows today,
  all `session`, 0 priced. Its *"0 rows of 86"* count does not reproduce; the 0-priced half does.

**Consequence.** A cycle that makes no billable call has a genuinely *measured* zero, and this
chain's four `cost_usd 0` cards with lane `executor none` are honest. The bug is therefore **latent**:
there is no mechanism separating "nothing billable ran" from "something ran and nobody priced it,"
and part (b)'s ship makes the second case more likely, because an unpriceable billed refusal now
lands `cost_usd` NULL rather than a false 0.

So yes — the fix **does** need a way to tell the two apart, and that is D1's four outcomes. It also
means the scope is narrower than the ticket's wording: nothing published needs correcting, and no
historical row is touched.

## 6. Why the discriminator is written as NOT-subscription

The tempting form is `where call_source = 'executor'`. It would match **zero rows** (§5) — a filter on
an empty set, which is how a fix ships looking green and doing nothing. The rule is therefore the
complement: a row is billable unless its lane is in `SUBSCRIPTION_LANES = new Set(['session'])`.

That choice also fixes the fail-direction for the 955 `call_source IS NULL` rows measured in the
newest 1,000: an unknown lane with no price resolves the aggregate to **NULL**, never 0 —
`pattern:44`, the whole resolves to its weakest contributing tier. A positive-filter form would have
silently called them $0.

## 7. Where the resolver lives, and the duplication it closes

The row-level rule already exists in `lib/activity-log.js:209-213` (price from the row's own tokens;
`computeCallCost(model, null, null)` is `null`, `computeCallCost(model, 0, 0)` is `0`). The set-level
rule already exists in `scripts/verifier.js:2016-2024` — `executorCostFor()`, which filters non-NULL,
returns `{usd: null, note}` when none are priced and a sum otherwise. It is **not exported**, so
nothing else can call it.

Putting `resolveCycleCost()` in `lib/activity-log.js` puts the set-level rule beside the row-level one
(`pattern:14`, `pattern:17`). Making `verifier.js` call it too would be correct and does **not fit**:
it is a fourth file. Filed as **F2** — `executorCostFor()` re-implements the shared rule; collapse it
onto `resolveCycleCost()` in the next cost cycle.
