## Designer calls (all reversible)

- **D1, the crawl is a flag on `sales-scan`.** A fourth capability needs a capability row, an intent, five links and an assignment, a fourth file for the seed and a re-pin of `agt-808-bill.test.mjs` (it asserts three assignments and 15 links): five files against a cap of three. The crawl is mechanical (find a site, find its bids page, record yes or no), so it needs no assembled agent prompt: `--crawl` renders a batch as plain JSON and the routine block carries the method, as the career writer's watch does.
- **D2, an amendment is a new rating.** The solicitation key is unique and the store is insert-only, so a second solicitation row for an amended posting would fail the whole insert. The validator refuses a stored key with that reason and accepts a second rating only when its `data.amended` is later than every stored rating of the key.
- **D3**, above.
- **D4, reminders are computed.** Which Interested solicitations are 10 or 3 days out is arithmetic, so the script computes it at render and again at write, and refuses a reminder outside the computed set. Runs are Monday and Thursday, so "10 days out" is a window (4 to 10 days, then 0 to 3), each fired once.
- **No fetch mode.** The routine's own session (cheapest model) reads the one rendered scan task, follows its FINDING and SKIP method and writes a candidates file; one sub-agent on the model the render prints rates only the candidates. No second render shape is needed.
- **`--principal` becomes a store flag** (`principal: true` on the writing and sales entries) so the status, grade, correction and keyword writes of a `/bill` session reuse the existing door. No test pins the old check (`git grep -F "on a writing slug" -- tests` is empty).
- **No live write in the build.** The first scan write and the first crawl batch are AGT-811's attended run, where each result is opened by hand.

## Flags for the Development Manager (not built here)

1. **Crawl pace.** At 5 runs a night of up to 10 batches of 40, the crawl covers about 2,000 agencies a night. The 43,726 agencies with a known website take about 22 nights and the whole list about 46, not the week the design names. The numbers are runbook values the principal can raise; the weekly meter stop bounds them either way.
2. **A source's changed state has no home.** The scan intent asks for "a source record with its new state" when a source fails or moves, but sources are unique by URL and insert-only, so that insert would be refused. The validator refuses it cleanly and the run names the failed source in its summary. Whether a source may be updated in place, like an agency row, is a schema call for its own ticket.
3. **Unproven: a cheapest-model routine launching a stronger sub-agent.** The design assumes the routine's Agent tool can name the printed model. If AGT-811's attended run shows it cannot, the fallback inside the same ruling is the routine on the printed model with cheapest-model sub-agents doing the reading.
4. **Smallest first puts size 0 first.** 'Smallest' is `data.size` ascending; the first rows are school districts with enrollment 0. Kept literal.

# BUILD FACTS NAMED BY THE KICKOFF

### H1

`validateSalesAnswer(capability, answer, stored, { principal = false, today } = {})`. Pure, exported. Returns `{ ok, errors }` and lists every refusal, not the first. `stored` is `readSalesStored`'s object. Every field below is under the record's `data`.

1. The answer is an object with a `records_to_write` array. Each item: a kind in `SALES_MODEL_KINDS`, or with `principal` a kind in `SALES_PRINCIPAL_KINDS` only (a model `status` is refused: "only the principal marks a status"); a non-empty `title`; `data` an object.
2. `solicitation`: `key`, `agency`, `due` as `YYYY-MM-DD`, `url` http(s). A key already stored, or named twice in the answer, is refused ("already stored: write the rating alone with data.amended").
3. `rating`: `key`, `fit` strong|weak, `why`, `profile` company|principal. Its key must be a solicitation, in this answer or stored, that carries a `YYYY-MM-DD` `due` and an http(s) `url`. One rating per key per answer. A key that already has a stored rating is refused unless `amended` is a `YYYY-MM-DD` later than every stored rating of that key, comparing each stored rating's `amended`, else the day of its `created_at`.
4. `source`: `url` http(s), not in `stored.sourceUrls`, not twice.
5. `vocabulary`: `their_term`, `our_term`, `add_to` store_f|keyword|both.
6. `reminder`: `{key, days_out}` equals one entry of `salesRemindersDue(stored, today)`.
7. Principal kinds. `status`: `key` is a stored solicitation key, `status` is New|Interested|Pass|Bidding|Won|Lost, and `Pass` needs `reason`. `grade`: `score` an integer 1 to 10, `phrase`. `keyword`: `status` approved|dropped. `correction`: a non-empty `body`.

`writeSales` rows: `{kind, title, body: item.body ?? null, data: item.data ?? {}, source: '<slug> <YYYY-MM-DD>', session_name}`. `strong` counts rating rows with `fit` strong; `reminders` counts reminder rows.

### H2

`--crawl[=<n>]`: default 40, whole number 1 to 200, else a parseArgs error. Allowed only with `--render` or `--write` and only when `storeFor(capability)?.crawl?.slug === capability`. `render()` and `write()` test `args.crawl` first and return `store.crawl.render(args)` or `store.crawl.write(args)`; nothing is assembled and no model is named.

`renderCrawl(args)`: reads until it holds n rows, each read `sales_records?kind=eq.agency&data->>solicitations_searched=eq.not-yet&select=id,title,data&limit=<left>` plus, in this order:
1. `&data->>website_found=eq.yes&data->>size=not.is.null&order=data->size.asc,id.asc`
2. `&data->>website_found=eq.yes&data->>size=is.null&order=id.asc`
3. `&data->>website_found=eq.not-yet&data->>size=not.is.null&order=data->size.asc,id.asc`
4. `&data->>website_found=eq.not-yet&data->>size=is.null&order=id.asc`

A row whose website is `no` is never selected: it waits for the principal's call. Output, to `--out` or stdout: `{crawl: true, agencies: [{id, title, type, state, city, county, size, website_url}]}`.

`planCrawl(answer, rows, sourceUrls, today)`. Pure, exported. Answer shape `{agencies: [{id, website_found, website_url, solicitations_searched, solicitations_page}]}`. Errors: `agencies` not an array; an id not in `rows`, or twice; `website_found` not yes|no; yes without an http(s) `website_url`; beside yes, `solicitations_searched` not yes|no; beside no, `solicitations_searched` present; `solicitations_searched` yes without an http(s) `solicitations_page`. With no error: one patch per agency, `{id, data}`, where `data` is the row's own `data` with only `website_found`, `website_url`, `solicitations_searched`, `solicitations_page` and `checked_at` (today) set and every other key untouched; website `no` sets only `website_found` and `checked_at`. One source per searched-yes page that is not in `sourceUrls` and not already planned: `{kind: 'source', title: row.title, data: {url: solicitations_page, type: 'agency', state: row.data.state, agency_key: row.data.key, readable: 'yes', checked_at: today}}`.

`writeCrawl(args)`: loads the answer; reads the named rows with `kind=eq.agency` and the stored source URLs; plans; any error exits 2 with nothing written. Then ONE insert of the sources (source `agency crawl <date>`, session_name), then one PATCH per agency at `sales_records?id=eq.<id>&kind=eq.agency` with body `{data, updated_at: <now ISO>}`. A failed PATCH exits 2 and prints how many landed; a re-run is safe because a landed row is no longer not-yet and a stored source URL is skipped. Stdout `{patched, sources}`. This is the only PATCH on the store; no DELETE anywhere.

### H3
