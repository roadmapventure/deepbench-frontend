## 2. The calls I made (JOHN-0925-DESIGNER-DECIDES, reversible)

1. **The stamp is a `runner_decisions` row of kind `fit-stamp`, not a new table.** The grade record already lives in that ledger (5,258 `requirement-check` rows), `kind` is unconstrained, and the row brings `decided_at` (d.5's date), `backlog_id`, `reversed_at` and `reverse_decision()` for free (pattern:17). Undo: reverse the rows and drop the kind.
2. **Never `status = 'removal proposed'`.** A no-fit is not a turn-down: d.33 complains that Victoria's turn-down "sends tickets into the same 'removal proposed' dead end", and AGT-485's harvest repeats it. So `applyList` writes the stamp and touches nothing on the ticket — no PATCH, and therefore no before-image either, because nothing changed.
3. **The stamp's life is a charter FINGERPRINT, not a date window and not a sweep.** `md5` of the `{slug, charter}` array over `executing` projects changes the instant a project becomes active, is paused, or has its charter edited — which is exactly d.5's clearing condition, and d.17's project-agnostic requirement, with no per-project rule and no maintenance job (pattern:16, pattern:18, pattern:9). `expires_at` is deliberately NOT read: d.13 forbids a time-based re-grade. Rejected: a `cleared_at` column plus a trigger on `projects` (two more objects, and a trigger that fires on every project edit); rejected: storing the fingerprint in a new table (call 1).
4. **EXACT `=` on the summary, never LIKE.** The stamp's summary is generated by one exported function, `fitStampSummary()`, so the SQL predicate and the JS writer cannot drift (pattern:14), and a stamp written under a dead fingerprint can never be matched by accident. This is the mutation QA's teeth exercise.
5. **`no-fit` is a LIST-door verdict only.** `VERDICTS` (the single-ticket door) and `tests/regression/agt-280-requirement-check.test.mjs` stay byte-unchanged; a new `LIST_VERDICTS` carries the third value. The narrowest change that meets the Done-when (pattern:65): the list door is the one the weekly routine and AGT-485's prepared daily check actually run. Consequence, filed as a finding not fixed: the single-ticket `--prepare`/`--apply` door is handed no charters and cannot answer `no-fit`.
6. **No new answer field for the project she picks.** d.5 wants the best fit named; her method already has the convention for a judgment the schema cannot carry — `PARKED (0) until <project>` in the `reason` — so the `0. FIT BEFORE GRADE` step tells her to name the project there. Undo/alternative: add `rows.items.properties.fits_project` and a membership refusal against `active_charters`; I rejected it as one more schema surface and one more `agt-281` pin for a value nothing reads yet.
7. **The charter text travels whole, cut by nothing.** 3,041 b of charter against `DESC_CHARS` 1500 per ticket is not a budget question, and a truncated charter is a charter she would misjudge against (pattern:34). `name` and `priority` are left out of the jsonb object: the slug is the identifier every other surface uses, and `priority` only orders the array.
8. **The runbook is not edited in this slice.** `tests/regression/agt-452-victoria-rows.test.mjs` arm C pins `docs/runbooks/victoria-reorg.md` line 1 to AGT-452's stamp byte for byte, and the stamp convention stacks newest first — so documenting the new step costs an edit to another ticket's guard, and the 8,192-byte kickoff cap has no room for the instruction that would keep it safe. Filed in the STOP LINE as a finding instead.

0. FIT BEFORE GRADE. You are also handed every active project's charter. ```

## 5. Why the QA discriminates

On `origin/dev` the rpc does not exist, so arm A answers `PGRST202` and arm D reads the two-value enum: the guard file is red by construction. The Done-when is proved in BOTH directions inside one rolled-back transaction, which is the only way to show it without writing to the live board: a `fit-stamp` recorded at today's fingerprint makes `stamped` name that ticket, and a one-character charter edit in the same transaction moves the fingerprint so `stamped` reads `{}` and the ticket is offered again. Arm B is the fingerprint's own sensitivity, computed offline, so it cannot pass by agreeing with a hardcoded md5 — the kickoff forbids pinning one, because the live charters will change. The teeth each break exactly one arm: `=` to `like` lets a dead-fingerprint stamp count (arm A); dropping the `no-fit` refusal lets a graded no-fit through (arm C); the enum back at two values (arm D and `agt-281`).

## 6. Alternatives weighed and rejected

- **A node-side charter read with the slugs listed in code**: rejected outright by Rule #1 and d.17 — a project slug in `rc` means naming a new active project is a code change.
- **Reusing `not-needed` with a reason prefix** instead of a third verdict: rejected. It writes `status = 'removal proposed'` (call 2) and makes `runLine`'s turn-down count wrong, which is a reported number that would then be false (pattern:41).
- **A `victoria_fit_stamps` table**: rejected, call 1 — the ledger already fits and brings reversal with it.
- **Clearing stamps with a trigger on `projects`**: rejected, call 3 — a fingerprint compare at read time is the same guarantee with no write path and nothing to get out of step.
- **Charters into the single-ticket door as well**: deferred, call 5, filed as a finding. It needs its own verdict value and its own guard edits, and the Done-when does not reach it.
