## Where the section goes, and why there

Three candidates were weighed.

1. **`assemblePrompt()` in `api/prompt/db-assembly.js` (chosen).** It is the single function called by the executor (`execute.js`), `api/plan.js` (two calls), and every session driver (`scripts/agent-prompt.js`, `market-agent.js`, `personal-agent.js`, `rank-backlog.js`, `requirement-check.js`, `design-ruling.js`, `decide-gated-card.js`, `model-assignment.js`, `ticket-owner.js`, `run-project.js`, `verifier.js`, `prioritizer-first-run.mjs`). The section is a `stored` section whose content is filled at assembly time - the SES-341 precedent - so a driver that renders without enriching shows the same bytes the executor's model sees. It is pushed outside `buildSections()`, like `current-task` and `voice`, so it does not depend on the agent holding any Skill row: Brittany gets it.
2. **A `rag`-type section resolved in `enrichPrompt()`.** Rejected: the session drivers do not enrich, so Nathan Laan or Jerry Maguire taught through the Training tab would silently miss their items; and it would need a new `fetch_instruction.source` branch in a second api/prompt file.
3. **Inside `buildSections()` under the identity branch.** Rejected: an agent with no identity Skill (Brittany) would get nothing - the exact gap `agent-bundle.js`'s header already documents.

**Order 3.5, stable phase.** The stable run is format 1, identity 2, behavior 3, guardrails 4, intent 5. Intent must stay the last stable section (HAR-02b-patch3: intent-to-task adjacency; `AGT-44` asserts it). Taught material is "what the agent knows and how it behaves", so it sits after behavior and before guardrails, which keeps the constraints as the later word. Stable because the text changes only when a trainer edits an item, never per call, so it stays in the cacheable prefix.

**Byte-identity for everyone else.** No user-taught rows -> `buildTaughtSection()` returns null -> nothing is pushed and the extra sort does not run. The return object gains no key. `signature_config` is built from Skill Profiles only and is untouched (the taught text is agent-specific; the signature is agent-agnostic, §19k). The one cost every caller pays is one extra PostgREST read per assembly.

**The bundle.** `agent-bundle.js` calls `assemblePrompt({ agent_id })` for its `sections` and already returns `taught` separately. Without an opt-out the bundle would carry every short item twice and read the table twice. `include_taught: false` skips the read entirely. A request-level argument, not an identity conditional (§19b).

**Rules checked.** `.claude/rules/capabilities-are-data.md`: no conditional on an agent id or capability slug is added; adding determinism is not the gated direction. `.claude/rules/capability-logging.md`: the read is not a capability execution; nothing new is logged and no logging call is removed. `.claude/rules/library-access.md` and `scripts/check-library-access.js`: the check matches `the_library` primitives and `librarian.js` imports only; `lib/read-taught.js` (shipped AGT-342) is the existing direct reader of an agent's own rows, which §19c allows.

## Calls made, all reversible

- **A failed read warns and continues.** Every other read in `assemblePrompt()` degrades on a non-ok response; throwing here would let a `knowledge_entries` hiccup stop every governance agent that has nothing taught. The cost is one call that misses its taught items, visible only in the server log.
- **Copy.** Label `WHAT THIS AGENT WAS TAUGHT`; item heading `--- <title> ---`; the too-long sentence promises nothing about search, so it is true in slice 1 and stays true in slice 2. The sentence lives in `db-assembly.js` because the file cap leaves no room to put it beside the two framings in `lib/read-taught.js`; slice 2 may move it.
- **Baseline without credentials for two tests.** `agt-162` and `agt-342` live arms run the bundle, which writes `ai_activity_log` rows; this design turn was read-only, so their live arms were NOT RUN at baseline. The build runs them the same way.

## What slice 1 does not do

- **Similarity search for the long items.** `queryRAG()` puts a matched row's WHOLE content in the prompt (finding `b111863d`): wiring it for Bob would put up to 216,720 characters into a prompt. That needs a bound in `lib/rag.js` or the `match_knowledge` RPC - a fourth file or a migration. Slice 2.
- **Double appearance.** Michelle's `capability-registry-knowledge` Skill already runs an agent-scope `queryRAG()`, so one of her four short items can now appear twice in one prompt - once always, once as a match. Repeated text, not wrong text. The fix is the same `lib/rag.js` change. Slice 2.
- **Identity for an agent with no Skill rows.** Brittany's prompt is the taught section, the task and VOICE - no name, no role. Pre-existing and outside this ticket; a finding for Development Manager review.
