## 3. The structural facts that shaped the design

- **One scope, no dynamic SQL.** `drain_epic_next` has exactly one `DECLARE` (:29) and one `BEGIN` (:97), and no `EXECUTE`/`format()`-into-SQL anywhere in the pick path. So `c_flagged` and `c_lane_cut` are in scope at :217, :249, :273 and :350. That makes the four inline sites a **by-name substitution** rather than four repeated subselects — cheaper, and it removes the possibility of the constant and the inline copies disagreeing again, which is the whole point of the ticket (`pattern:14`, `pattern:15`).
- **plpgsql `DECLARE` initialisers run at block entry**, so `constant text[] := public.pick_blocking_flags()` and `constant date := (SELECT …)` are both legal and evaluated once per call. No new variable is needed.
- **`drain_chain_gate` is nearly done already.** Slice 1 converted its `c_flagged` (:23 now reads `pick_blocking_flags()`); only the `COALESCE(v_set.chain_max_noship_streak, 2)` at :35 remains. `chain_max_noship_streak` is `NOT NULL DEFAULT 2`, so the `COALESCE` cannot fire — removing it is provably value-preserving and provably **unobservable**. The kickoff says so rather than inventing a behavioural arm for it (`pattern:33`, `pattern:34`): its whole proof is the zero-occurrence count.
- **`backlog_mode` is a 4-arg SQL `STABLE` function** that already reads `public.runner_items`, so adding a `runner_settings` subselect does not change its volatility class.
- **No signature changes anywhere** — all three are pure body edits — so `.claude/rules/supabase-function-signature.md`'s overload trap does not bite. The kickoff still asserts `count(*) = 1` per name afterwards, because that rule's whole lesson is that an overload break is invisible from the new call path.
- **`runner_settings` has no anon grant**, so `.claude/rules/supabase-column-grants.md` does not apply.

## 4. The QA problem, and why the ticket's blocker dissolves

The ticket cut this work out of slice 1 because `drain_epic_next()` "is VOLATILE *and* writes before-images and retirements on every call, so 'call, apply, call again, compare' is not the same experiment twice, and calling it mid-chain mutates the runner's own record."

Both halves are true and both are removed by wrapping each call in `BEGIN; … ROLLBACK;`:

- `drain_epic_next` is a **FUNCTION**, not a PROCEDURE, so it cannot `COMMIT` internally. Every before-image and retirement it writes is inside the caller's transaction and is discarded by the `ROLLBACK`. Nothing durable is mutated, so it can be called mid-chain without touching the runner's own record.
- Because nothing commits, every arm starts from byte-identical state, so the experiment **is** repeatable.

Measured this cycle rather than argued: the same rolled-back call returned digest `76c2e7d24deac0a39f1907a559630bd1` on two successive runs.

### 4a. The degenerate-probe trap

The first probe returned `outcome='none'` with every column null. Reading the body, :109–:125: with no `runner_directives` row of `type='drain-epic' AND status='queued'`, the function returns early and **never reaches the pick predicate at all**. A knob arm against the live board is therefore worthless — it would have "passed" identically before and after, and would have certified a broken migration.

This is why every arm in the kickoff seeds its own directive plus `runner_drain_scope` rows **inside the transaction**. Two dead ends found on the way, both recorded so a later session does not repeat them:

- Scoping `LOG-88` + `SES-288` (epic `eeda31e6…`) returned `blocked` with `2 outside an executing project` — the project fence. Only **Auditor Enhancements** (`d4b8ac06…`) is `executing`; every other project is `paused` or `planned`.
- Every open member of that executing project is filed `2026-09-23`/`2026-09-24`, i.e. all post-cut, so no naturally occurring pair discriminates on the lane cutoff. The date arm has to move `filing_lane_cutoff` forward (to `2027-01-01`) instead of backward.
