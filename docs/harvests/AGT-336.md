## 2. The data model and why

| Thing | Where | Default | Why |
|---|---|---|---|
| owner | `agents.owner_id text`, `teams.owner_id text` | null | null means the platform's own. `text`, not `uuid`: ARCHITECTURE section 10 names Clerk as the login provider and its user ids are strings; `agents.tenant_id` being `uuid` is the odd one out (most tables use the text `'global'`). |
| sharing level | `agents.sharing`, `teams.sharing`, CHECK `private`/`users`/`public` | column default `private`; the 33 existing agents `public` | John: "visible to those who logged in and agents have been assigned to, or they were assigned public to all". The two-step default (`add column ... default 'public'` then `set default 'private'`) fills existing rows with pure DDL - no UPDATE, no before-images. A row nobody classified is private: the mistake fails closed. |
| shared with these users | `shared_with text[]` on both, default `{}` | empty | The cheapest "place" that the check can read straight off the row with no join. A join table is the normalized form; nothing reads it yet, and an array converts to one with an additive migration when sharing is built. |
| team | `teams(id, name, address, owner_id, sharing, shared_with, tenant_id, created_at)` | | `unique nulls not distinct (owner_id, name)`: "once they create the first team name, it is available for any new agent" - one name per owner, and with no login (owner null) one name platform-wide. |
| membership | `agent_teams(agent_id, team_id)` primary key the pair | | many-to-many; cascades on either side. Index on `team_id` for the team-address lookup (`AGT-338`). |
| team address | `teams.address`, `not null unique`, default two `gen_random_uuid()` concatenated without dashes | 64 hex characters, 244 random bits | Made by the database, so no code path can create a team without one and nothing derives it from the team name. Core function - no extension schema in a column default. |

Hiding the address. `.claude/rules/supabase-column-grants.md` is explicit that a column REVOKE does nothing under a table grant, so the migration revokes the table-level SELECT from `anon`/`authenticated` and grants a column list that omits `address`. Consequences, all intended: `select=*` on `teams` is refused for the anon key; a column added to `teams` later is hidden until granted. The alternative considered was a separate `team_addresses` table with no anon grant; rejected because "one address per team" would then need a trigger or a writer's discipline instead of a NOT NULL default.

Not stored, on purpose: pricing or monetization fields (`ai_activity_log` already records each MCP call per agent with caller attribution, AGT-163); a per-agent address (`AGT-333`, claimed by session ux-ui-1003, undesigned - it could take the same pattern: a database-made column behind a column grant).

`capture_migration_down`: the runbook says in-place ALTERs of an existing table and grant changes come back `refused` by design. So this migration is card-only on a red range - stated in the kickoff, not worked around. The two new tables down to a drop by identity.

## 3. Where the check lives, and the alternatives

Chosen: one pure JS module, `shared/agent-visibility.js`, exporting `canSeeAgent(agent, viewer)` and `visibleAgents(rows, viewer)`. A `null` viewer means "no login system exists" and answers everyone - that is today's only caller state. The rule for a real viewer (public, or owner, or named in `shared_with` when sharing is `users`) is written and unit-tested but unreachable in production until a caller has a viewer to pass. Writing it costs six lines and is what makes the QA discriminating: with a viewer, a private agent's capability drops out of the MCP tool list; on the unchanged tree it does not.

Rejected: a Postgres function `visible_agents(p_viewer)` called through PostgREST `rpc` by both readers. It would have kept the build to three files in one slice, but (a) `tests/regression/agt-006-agents-table-authoritative.test.mjs:127` pins `.from('agents')` in the hook, so the Bench change would have moved a fourth file anyway; (b) a function missing at deploy time takes `/api/mcp` down entirely; (c) when RLS arrives (`DAT-29`) the policy wants a row predicate, not a set-returning function over the same table.

Honest limit: a filter in browser JS is a seam, not security. When logins exist the Bench read needs a server-side floor (RLS under `DAT-29`); the module is where the rule is stated so the policy and the MCP server say the same thing.

Team-derived visibility (an agent seen because its team is shared) is not in the rule. It needs membership rows in the check's input and a decision about whether a team's sharing overrides an agent's; nobody can exercise it until logins exist.

## 4. Why two slices

Full scope touches five files: the module, its test, `api/_lib/mcp.js`, `src/hooks/useAgents.js`, `api/_lib/handlers/agent-bundle.js`. The cap read off the cycle is 3 files / 4 tasks, and the cap is John's to waive (pattern:72), so the ticket is split the way `AGT-332` was in this same epic: slice 1 is the schema, the check and the MCP server's roster read; slice 2 is the Bench read and `agent-bundle.js`. MCP goes first because `AGT-338` (team address) builds directly on that seam, and because `useAgents.js` is about to be rewritten by `AGT-335`'s build (v7.0.753), whose `tableOnlyAgent()`/`buildRoster()` are not in the tree to anchor on.

The `benchGroups: ["private"]` derivation for table-only agents goes to slice 2 of this ticket, not `AGT-337`: slice 2 is the change that puts `sharing` into the roster read, so it is the one holding the fact. `AGT-337` then only writes rows.

## 7. The migration, verbatim (`docs/design/agt-336-agent-sharing.sql`, migration `agt336_agent_sharing`)

```sql
-- DeepBench v7.0.754 | docs/design/agt-336-agent-sharing.sql | AGT-336 slice 1
-- Mirror of migration agt336_agent_sharing, applied by the attended session through the Supabase
-- MCP apply_migration. Additive only. Owner and sharing level on agents and on
-- teams, agent-to-team membership, and a database-made address per team that the anon key cannot
-- read. Nothing is enforced: shared/agent-visibility.js answers "everyone" until a caller has a viewer.
-- agents.visibility (config / create / included) is a different fact and is not touched.

-- The 33 existing rows become 'public' through the first default; rows inserted later are 'private'.
alter table public.agents
  add column owner_id text,
  add column sharing text not null default 'public',
  add column shared_with text[] not null default '{}';
alter table public.agents alter column sharing set default 'private';
alter table public.agents add constraint ck_agents_sharing check (sharing in ('private','users','public'));

create table public.teams (
  id uuid primary key default gen_random_uuid(),
  name text not null check (btrim(name) <> ''),
  address text not null unique default replace(gen_random_uuid()::text || gen_random_uuid()::text, '-', ''),
  owner_id text,
  sharing text not null default 'private' check (sharing in ('private','users','public')),
  shared_with text[] not null default '{}',
  tenant_id text not null default 'global',
  created_at timestamptz not null default now(),
  constraint uq_teams_owner_name unique nulls not distinct (owner_id, name)
);

create table public.agent_teams (
  agent_id text not null references public.agents(id) on delete cascade,
  team_id uuid not null references public.teams(id) on delete cascade,
  tenant_id text not null default 'global',
  created_at timestamptz not null default now(),
  primary key (agent_id, team_id)
);
create index agent_teams_team_id_idx on public.agent_teams (team_id);

-- .claude/rules/supabase-column-grants.md: a column is hidden only by replacing the table grant
-- with a column list. Every anon reader of teams must name its columns; select=* is refused.
revoke select on public.teams from anon, authenticated;
grant select (id, name, owner_id, sharing, shared_with, tenant_id, created_at) on public.teams to anon, authenticated;
```

## S2.2 How a private table-only agent reaches the Private filter

`AGT-332` did not build Private from the database. It built it from one roster-entry value: `BENCH_PRIVATE = { id: "private", label: "Private" }` and `isPrivateAgent(a)` = `a.benchGroups` includes `"private"` (`src/data/agents.js:306-307`). `RosterScreen.jsx` opens on `useState(BENCH_PRIVATE.id)`, counts Private as `agents.filter(isPrivateAgent).length`, makes "All" every non-private agent, and the grid for Private is the generic `a.benchGroups.includes(activeFilter)`. `PersonnelScreen.jsx` reads the same predicate for the "Connect ... to AI" button (line 425), the Connect popup (1917) and the Activity tab (1735).

So the whole job is one expression in `tableOnlyAgent()`: `benchGroups: t.sharing === SHARING.PRIVATE ? [BENCH_PRIVATE.id] : []`, plus the three access columns in the roster select so `t.sharing` exists. No screen file changes. A consequence, recorded as call (vi): the created agent also gets the Connect button and the Activity tab on its Personnel file, because those were built for "private agents" and this makes it one. That is the approved `AGT-334` / `AGT-339` behaviour applying to a new member of the group, not a new element.

An `AGENTS` entry keeps its static `benchGroups` (call iii). Deriving Private from `sharing` for code agents too would be a `mergeRoster()` edit, would move Brittany out of Private today (her row reads `public`), and `agt-164` pins her at `["private"]` - a fourth file and a visible change. Left as the open finding it already is.

## S2.3 Where the Bench filter sits, and why not at the hook's call

The ticket text says the hook "passes rows through `visibleAgents()`". The literal reading is `buildRoster(AGENTS, visibleAgents(data, null))` at the hook. Rejected for two measured reasons: (1) `agt-335` asserts the literal `buildRoster(AGENTS, data)` in the hook source (line 140) and the cap leaves no room to edit that test; (2) a filter at the React call site can only be tested by rendering the hook, and with a `null` viewer it does nothing observable - the QA could not fail. Inside `buildRoster(codeAgents, tableRows, viewer = null)` it is pure, and arm (b) fails on the unchanged tree (26 and 24 instead of 25 and 23).

Filtering the rows alone would not hide a code agent: `mergeRoster()` leaves an `AGENTS` entry standing when its row is absent, so a hidden row would simply show un-overlaid. Hence call (ii): an `AGENTS` entry whose own row was dropped is dropped too. With no viewer the hidden set is empty and the output is identical to today's (agt-335 arms a-f unchanged).

Honest limits: the hook still renders `AGENTS` before the fetch lands (D4), so when logins exist a hidden code agent would flash; and the whole filter is browser JS over an anon-key read - a seam for the rule, not a security floor (`DAT-29`).

## S2.4 agent-bundle

The three-part condition becomes one exported pure predicate, `bundleTargetReadable(agentRow, handler_context)`, which keeps the existing three facts and adds `canSeeAgent(agentRow, handler_context?.viewer ?? null)`. Reasons: the handler itself cannot be unit-tested without a database (it reads through `fetch`), and the earlier verdicts on this repo criticised tests that mutate `process.env` to fake one; a pure export is testable with nine plain assertions. The viewer rides on `handler_context` because that is the envelope `mcp.js` already uses for `governance_unlocked` (line 777) - the same "decided once in mcp.js, forwarded" shape. `mcp.js` is not edited (cap, and nothing has a viewer to send), so `viewer` is absent and `canSeeAgent` answers true: live behaviour is unchanged. The error message stays `Unknown agent: <id>` so a hidden agent is indistinguishable from a missing one, the property the file's header insists on. `agt-162`'s static arm refuses `agent_id ===` and `slug === '` conditionals in this file; the new code has neither.

## S2.5 The test file

A new file rather than more arms in `agt-336-agent-visibility.test.mjs`: importing `useAgents.js` needs the two `VITE_SUPABASE_*` placeholders set first, and slice 1's test uses the presence of those same two variables to decide whether its live arm runs - placeholders there would point its live arm at `http://localhost`. The new file reads `LIVE` before setting placeholders for the same reason.

Arm (e) exists because the one way this slice can break the Bench silently is a bad column in the widened select: PostgREST answers 400, the hook's `error` branch returns, and the Bench stays on the bare array with no error shown. The dev check on Nadia's role (`Data Analyst` from the table vs `Data Expert` from the array) is the same proof by eye.
