## The note-or-file fact (what AGT-344's NOTE / FILE chip reads)

Chosen: `category = 'Note'`, set by the server when the POST carries `kind: "note"`, returned by GET as `kind`.

Why this one:
- No schema change. John's approved layout (decision 3.8 b) gives the note form a title and the text only - no category picker - so the category column is free on a note. The upload form keeps its picker, whose 17 options do not include `Note`, so a file cannot become a note by accident.
- The fact is owned by the server (one constant, one function), so the screen holds no rule about what a note is (pattern:12).

Rejected:
- `source = 'note'`: `lib/read-taught.js` treats only `source === 'user'` as taught. A note would become a "record" and stop being always given. Breaks John's decision 3.1 (one treatment).
- A new `kind` column: a migration plus a column-grant review for a fact an existing free column can hold.
- `steps_taken`, `triggers`, `teaching_note` as carriers: each already means something else.
- Inferring from content shape or length: not a stored fact.

Known limit, stated in the kickoff: rows saved before this ticket return `kind: file`. Most were uploads through the Teach screen, which has only ever had an upload path. A few were written straight to the database (Michelle's three registry rows, Brittany's test row). AGT-345 repairs Brittany's row and can set its category there. AGT-344 should know the chip on those few old rows says FILE.

## The re-embed

One shared function (`embedEntryText`) owns truncate, clean, embed and log, and both the save and the edit call it (pattern:14). The alternative - a second copy of the embed code inside the PATCH handler - is what `lib/librarian.js` and `lib/knowledge-write.js` already are to each other, and is the duplication AGT-342 reported.

The log moves from "after a successful save" to "when the embedding returns". Reason: the embedding call is the spend; if the save then fails, the call still happened and should be counted (pattern:32). `latencyMs` becomes the embedding's own time rather than embed plus save.

An edit re-embeds only when the title or content actually differs from what is stored. The current edit form sends the title on every save, so without the comparison every metadata save would spend an embedding call. The comparison costs one small row read (title, content, agent_id - not the vector). A PATCH that carries neither title nor content does no read at all, so the Active/Disabled toggle is byte-identical to today.

Not handled here: an edit that changes no text on a row that has no embedding stays without one. That is AGT-345's check and repair.
