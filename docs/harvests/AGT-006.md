## 2. The decision and why (Designer's call under JOHN-0925-DESIGNER-DECIDES)

The table must be the authority, not the array, because the platform's reasoning already treats it that way: Michelle's broker ranks candidates on `skill_score`/`situational_awareness` from the table (§19e), `execute.js` gates on `is_active` from the table, and every agent's prompt identity card is assembled from the table. The array is client-only and cannot be read by any of those. Retiring the table is therefore impossible; retiring the array is a 37-file job (`AGT-57`, filed, Post-beta). pattern:2 (data-driven over code), pattern:11 (no content judgments hardcoded — the array's salaries and skill numbers are exactly that), pattern:93 (point at the live source), pattern:40 (two surfaces showing one meaning must show one number: the Bench card and the broker's ranking disagree on dan's skill, 80 vs 0).

Why seed the blanks rather than just switch the read: switching alone would paint 19 Bench cards with 0 skill and blank salary/architecture — a visible regression John never approved (pattern:97 forbids altering what the approved design shows without asking). Filling the table's blanks from the array's values, once, makes the switch visually identical for every number, and moves the hand-authored values out of code and into data where the next hire edits a row, not a file. Where the table already holds a value the table wins (D2): the five affected strings are what each agent's own prompt already says about itself — the Bench aligns to the agent (pattern:53), not the other way round.

Why this is build work and not a card: rule `AGENT-ROW-AGREED-TICKET` (second arm) — an unreversed `runner_decisions` row names the ticket (this cycle's `design` decision, the same shape AGT-020 relied on) and the seed records its own `agent-row` decision naming the change, with a `runner_before_images` row per changed agent row (`to_jsonb(a)`, `cycle_id` set, `session_name` NULL). `reverse_decision()` lists `agents` as a restorable table and its Guard A never moves `is_active`; the seed never touches `is_active`, `name`, `role`, `specialty` or `code`, so nothing John owns is written.

## 3. Alternatives weighed

- **Array authoritative, sync table from it** — rejected: the server can't read the array; every hire would still need a deploy (AGT-57's own reason).
- **Guard test that fails on drift, no code change** — rejected: bounds the problem instead of removing it (pattern:1), and every future hire would fail the guard until someone edited both stores.
- **Switch `useAgents()` to an async table read with an empty first render** — rejected: 19 call sites `.find()`/`.filter()` on the array synchronously; an empty frame would crash or flicker. D4 keeps `AGENTS` as the initial state.
- **Put `mergeRoster` in `src/data/agents.js`** — rejected for this slice: it would be a 4th file. `useAgents.js` imports cleanly under Node with the two placeholder VITE_ env values (measured: `node --input-type=module -e "await import('./src/hooks/useAgents.js')"` → ok), so the pure core can live beside the hook and still be tested.
- **Also fix the `agents.js` header and `ARCHITECTURE.md` L1059** — over cap (files 4 and 5). Carried to AGT-57, which already owns the array's retirement.
