## 2. The 34 "closed over red" are mostly John's own ratified closes

All 34 latest-block verdicts carry the verifier's boilerplate (`scripts/verifier.js:1003`): *"block: RED: regression suite … A block is the status quo — the cycle ships delivered and cards John."* 185 of the platform's 195 block verdicts read that way; it is not a per-row classification, it is what every block says.

How a block-graded ticket becomes `done` today: `record_ship_decision()` refuses a non-approve verdict, so `sweep_decision_windows()` (SES-320) never closes one; the SES-311 trigger `backlog_done_requires_verdict` requires *a* verdict, and its own test (`ses-311-done-requires-verdict.test.mjs:25`, `:340`) states *"a verdict='block' row SATISFIES the gate (a block is still a verdict)"*; the remaining paths are John's Accept on the shipped card (runbook L891–895: "AN ACCEPT ON A `shipped` CARD NOW WRITES THE TICKET `done` — IT IS THE ONLY THING THAT EVER DOES") and an attended session's write (session-setup.md §3e says a block writes `delivered`, not `done`).

Measured against that: of the 34, **23** have a `runner_items` row `kind='ship'`, `decision='accept'`, `decided_at >= verdict.created_at` — John accepted the shipped card after seeing the block; **5** have a `ship` or `ticket-status` `runner_decisions` row dated at/after the verdict; **6** have neither (`AGT-69`, `LOG-104`, `LOG-145`, `LOG-149`, `SES-360`, `SES-373`; four of these — AGT-69, LOG-149, SES-360, SES-373 — got their block *after* they were already done, a re-verification landing on a closed row; LOG-104 and LOG-145 were closed by an attended session on 09-03 with no decision and no card). So the auditor's check contradicts a rule the platform keeps on purpose, and 28 of its 34 hits are false. Pattern:94 — surface and amend in the same session, not silently patch either side.

**The call (iii):** a close over a standing block is legal only when *ratified* — a non-reversed `ship`/`ticket-status` decision, or a `ship`-card Accept, dated at or after the verdict. The trigger gains that clause (the fence the ticket asks for), the check learns the same predicate (so it flags only the unratified), the runbook states it beside the SES-154 passage, and the six unratified rows get one reversible `ticket-status` decision each — reversing one puts that row straight back into the census, which is exactly the semantics a Reverse should have.

Rejected: **re-open** the 34 (they are shipped code on `dev`, several are the platform's live rules — SES-311, SES-376, SES-389; re-opening puts built work back in the pick queue as if unbuilt); **record an approve that supersedes** (`ck_runner_verdicts_fail_closed` makes `approve` equal to all three gates green — an approve row for a tree nobody re-ran is a fabricated measurement, pattern:33/162); **a `block_kind` column on `runner_verdicts`** (nothing in the verifier distinguishes a status-quo red from a caused one; the label would be boilerplate again); **`directive` decisions as ratification** (AGT-70, SES-344, SES-367 carry directive rows dated after their block that are John's directives about other things, not about the close). The two-home predicate (SQL trigger + JS check) was weighed against a shared SQL function/view; kept as two homes because `audit-board.js` is read-only JS by AGT-86's design and the regression test drives both with the same four cases.

## 3. Homing — under a planned project, by prefix, deterministically

`prime_directive_queue()` admits only `epic_project_executing(b.epic_id)` rows (plus the EL-01 enhancement fence). Executing projects tonight: Auditor Enhancements (1), Dev Manager Capabilities (2), Agent Training (3), MCP POC (4), Trainer-Authored Agents (5). 37 rows are admitted. Homing 546 legacy rows — 261 of them tier `now` — under any executing project would hand the runner a different backlog overnight; the project layer (SES-340) is John's admission lever and this ticket must not pull it for him.

**The call (i):** one new project `backlog-intake`, status `planned`, priority 10 (NOT NULL; last), 36 epics `Intake — <PREFIX>` created from the live prefixes by SQL rather than an enumerated map (pattern:99 — a structural rule over provable facts; pattern:16 — self-maintaining). The check reads zero because every row has an epic whose project exists; the pick reads exactly what it read before (37). John admits a family with one `UPDATE epics SET project_id = …` — per family, which a single "Legacy" epic could not offer. Epic names carry the prefix rather than the FEATURES.md legend area name because the legend is a 36-entry enumeration that would have to live in the kickoff; the epic description points at the legend instead.

Rejected: per-family projects (36 projects; the priority column and `project_progress` would fill with noise); homing the 86 terminal homeless rows too (no census counts them; images ×632 for no gain); a `NOT NULL` on `epic_id` or a refusing trigger (SES-279's own ticket text: a fail-closed column breaks the runner's INSERT mid-drain and parks the platform — the fence auto-homes instead, and fails *open* if the intake project is ever gone so filing never stops; the census would show the row again). The trigger creates a missing `Intake — <prefix>` epic on the fly (`ON CONFLICT (name) DO NOTHING` over `epics_name_key`) so a new prefix never lands homeless.

**Write discipline (measured, not recalled):** `backlog_items` has no `updated_at` trigger (pg_trigger: one row, the SES-311 gate), so the UPDATE must not name `updated_at` — `reverse_decision()` refuses a row whose `updated_at` postdates the decision (SES-316). One `record_decision(kind='hygiene', backlog_id NULL)` + 546 `runner_before_images` (cycle_id set, session_name NULL — `ck_before_image_attribution` takes exactly one) is the Ticket Owner's own shape (one decision for the night, one Reverse undoes it all).

**Consequence stated in the kickoff (iv):** the SES-311 gate's condition is "epic has a project"; with every row homed, every `done` write on the board now needs a verdict. That is the direction the rule already pointed (session-setup §3e runs the verifier on every attended close), but it is a behaviour change for a session closing an old `AA-*` row without one — fail closed, and named.

## 4. Arm (b) is slice 2, and why

441 rows past the 30-day fence with `revalidated_at IS NULL`. Writing `revalidated_at` without re-reading each premise would make the column a lie (pattern:33); the runbook's own 8c sweep does ≤3 per cycle by design because a revalidation is a judgment. The honest shape is a Ticket Owner check (`ticket-owner.js` already has the census → `--judge` sub-agent → `apply: true` merge under one decision) over `revalidated_at IS NULL AND filed_at < now() - 30 days`, batched at 25 a night (the auditor's E2BIG note is the reason for the batch), writing `revalidated_at` on a live premise and `removal proposed` on a dead one. That is 18 nights of work, not one cycle, and it is a different file set. `decideStatus()` reads `slice 1 of 2` from section 1 and `partial` from the STOP LINE, so the settle writes `partial` by construction.
