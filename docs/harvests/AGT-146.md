## §S — steps 0-6 of the runbook, verbatim (Task 1 of the kickoff names this section)

  0. `export D=$(TZ=America/Chicago date +%F) N=model-watch-$D S=$(mktemp -d); WEEKLY=$([ "$(TZ=America/Chicago date +%u)" = 5 ] && echo yes || echo no)`; `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` by name from `runner_secrets` over the MCP, exported inline, never printed; `git fetch origin dev && git checkout -B session/$N origin/dev`; write the prompt this run was given to `$S/prompt.txt` verbatim; `node scripts/check-routine-prompt.js --routine=model-watch --prompt=$S/prompt.txt --out=$S/prompt-drift.json; echo "prompt-drift exit $?"` (exit 1 = a step-6 note, never a stop; exit 2 = could not run, noted); the builder's step-1 meter command verbatim (the one Bash command in `routine-prompt.md`'s block, step 1, acted on by its LAST line: an `INSERT` runs as one `execute_sql`, `NO_READING` writes nothing); then the auditor's room query with four more columns: `detail->>'all_models_pct'`, `detail->>'pace_limit_pct'`, `detail->>'fable_pct'`, `detail->>'fable_share'`. Stop iff `weekly_wall` is true, or `meter_stale` is true AND the self-read printed `NO_READING`: step 6 writes `model-watch did not run — weekly wall: <gated_pct>% ≥ <wall_pct>%` or `— meter unreadable: <age_hours> h old, NO_READING <reason>`, and the run ends. `scheduler_off`, `nothing_pickable`, `weekly_pace` are the builder's refusals and never stop this routine.

`## On demand`: "Run now" on the routine, or any Claude session told "run model-watch", follows steps 0-6 with `N=<its own session name>` (a session name, never a cycle id — `ck_decision_attribution`); a second run on one day re-trials nothing (the 28-day dedupe) and writes its own report row.

## One routine, two modes — why not two routines

A claude.ai routine holds one cron. The ticket names two times (daily 4:30 AM Central, Friday 2:00 AM Central). Options: two routines from one block, or one routine whose Friday fire runs the weekly mode. Chosen: one routine, `30 9 * * *`, `WEEKLY=yes` when the fire's America/Chicago weekday is Friday.

- The pace week starts Friday 01:00 Central (`week_started_at 06:00Z`); 02:00 and 04:30 are both `week_day_index 1` with the same `pace_limit_pct` (14.29), so the room arithmetic John approved is identical; the only difference is 2.5 hours of clock.
- The release-found path already runs trials inside the daily fire ("a release found on the daily check runs its trials the same morning"), so the trial mode exists in the daily routine either way; a second routine would duplicate it and double AGT-145's pin registry and the drift-check entries (pattern 17, 67).
- The block would have to be byte-identical for two routines, which is why the block carries no trigger id.
- It is reversible for the price of one create: a second routine `model-watch-weekly` on `0 7 * * 5` from the same block, plus one `ROUTINES` entry. The kickoff's STOP LINE tells the attended session to tell John the Friday cron was not created and why (pattern 89 — his approved wording differs from what the platform can hold; surface it, never silently correct).

## The block carries no trigger id and no model id

AGT-102 found the Auditor ran a week on the placeholder `DEEPBENCH-AUDITOR-<routine id>` because the block was written before the routine existed and the id was never filled. AGT-146 is the same sequence (build, then create). So: the block has no id; `ROUTINES["model-watch"].id` is `null` and `finding()` falls back to the routine name (`routine/model-watch/prompt`) — the fingerprint is stable whether or not the id is ever filled, and filling it later is a one-line edit, not a drift. No `claude-…` id in the block either: AGT-147 strips them from the other prompts, and a routine that switches models must not name one in its own prompt (pattern 2, 11).

## Reporting — one mechanism

Every fire ends in one `record_decision(NULL, 'model-watch-<D>', 'model-report', …)` row. That row IS the daily list line (the brief renders every kind), the Friday line (the same row with the model-per-job-type list appended) and the did-not-run line (pattern 16, 34, 141). Switches, keeps and reverts are their own decisions written by `apply_model_assignment()` / `review_model_watch()` (AGT-144) with undo handles the brief already prints — no rendering code is added. Money asks: `apply_model_assignment()` writes `john_alerts` (`john_call 'money'`, `source 'model-assignment'`); the brief does not render that table, so until it does the `model-report` summary begins with `MONEY waiting on John: … (about $<n>/week)` for every unacknowledged row — "at the top" of the only line John reads for this routine. The STOP LINE has the attended session file the brief gap as its own ticket (pattern 96) rather than adding a fourth file here.

The dedupe of trials uses the report row's `reasoning` (`trials: lane/orchestrator->claude-opus-5-5, …`) with a 28-day window: AGT-144's `model-keep` decision has no fixed summary format and `trial_evidence` is written only on a switch, so the routine's own row is the one record it controls (pattern 93 — a live source, not a doc). A kept pair is re-tried after 28 days, so a model that improves or a job whose mix changes gets a second look monthly; a switched pair never matches (the row's model changed).

## The first run is the Opus 5.5 trial by construction

The step-3 release query (newest same-family catalog model with a dated release later than the row's model's `coalesce(released_on, first_seen::date)`, not deprecated, `claude-%`) returns exactly one pair on the live rows: `lane/orchestrator -> claude-opus-5-5` (opus-5 `first_seen` 2026-09-09 < 2026-09-22). Fable has no newer family member; sonnet-5 has no `released_on` so it is not a release candidate for bench-report-card until the watch dates it. "Every job type currently on claude-opus-5" is the orchestrator row alone — the 30 Skill rows on opus-5 (nine `dm-*` among them) follow the lane by AGT-143's trigger. Opus 5.5 is priced below Opus 5 (0.004 < 0.005), so under AGT-144's rule the move is a DOWN switch: all three trials `passed`. Nothing in the playbook names Opus 5.5.

**Discovered against AGT-148's kickoff (v7.0.592, read after this design was drafted):** `scripts/model-trial.js` replays a job's *recorded agent turn* and its `REPLAYABLE` map holds one feature, `design-kickoff:ds-kickoff-intent:depth0` — a judgment-lane turn. `pickJobs` selects `ai_activity_log` rows whose `model` equals the row's current model, so for `lane/orchestrator` (`claude-opus-5`) it finds zero replayable rows and exits 4; AGT-148's own live QA proves `--dry-run` on `lane/judgment`, not the orchestrator. So on the first fire the release pair is found, `model-trial.js` exits 4, and the report row carries `skipped: lane/orchestrator->claude-opus-5-5 (exit 4 …)` — every fire, until a replayable orchestrator-lane feature exists (a build turn, or a `run-project`/`decide-gated-card` turn the manager already runs on the orchestrator lane, added to `REPLAYABLE`). The routine does its part of the ticket's first-run sentence (the pair is queued and tried through the process, never a hand switch); the evidence path is AGT-148's to extend. The STOP LINE hands it to the attended session as a discovered gap for The Development Manager, not to John (`feedback-dev-manager-owns-discovered-work`). Meanwhile the judgment row's Friday downgrade pair (`lane/judgment -> claude-opus-5`, the next-cheaper model) IS replayable and is the first trial that can actually run.

Friday's downgrade query (highest-priced cheaper catalog model) returns 4 pairs today: judgment→opus-5, mechanical→haiku, bench-report-card→sonnet-5, orchestrator→opus-5-5 (deduped against the release pair). Each trial costs about 3 re-runs; on day 1 with 7% used the room gate in `model-trial.js` (AGT-148) admits roughly two before `no-room`, and the playbook stops trials at the first exit 3 rather than reordering the queue (pattern 147).

## What it does not do

- It does not create the routine (the attended session does, John's switch) and never edits one (must_not, AGT-144).
- It does not add a "waiting on John" section to the standing brief (filed by the attended session).
- Cross-family "strongest model for hard judgment" trials (Q1's ranking) are not generated by the queries; a release in the Fable family or a downgrade from Fable to Opus (the Friday query does produce judgment→opus-5) is what reaches the judgment row. A cross-family UP rule needs a ranking the catalog does not hold; AGT-142's `stated_strengths` is prose.
- The cheap exit reads two Anthropic pages with `curl` and compares model ids against the catalog: a curl failure or an empty id set is "could not read" and runs the watch Intent once (fail toward one call, never toward silence — pattern 165's direction, at the cost of one call, not a stop).
