## Decision 1 — what fable_pct holds when the Fable window is absent

Live `judgment_model()` takes `fable_pct` from the newest row, whatever wrote it, and maps NULL to `lane` (Fable). The self-read runs at every fire, so its row is nearly always the newest. A NULL there hides a backup's same-week Fable number and lifts the degrade.

When is the window absent? It was measured only at 94%. On the Fable call, the second event carried `seven_day_overage_included` with status `allowed_warning` and `surpassedThreshold 0.75`. The first event on the same call did not, and the Opus and Haiku calls never did. The window may appear only past 75%, which would make it absent for most of the week after Friday 2026-09-18's reset. That is not measured, so nothing in the design relies on it.

- (a) NULL, function unchanged — rejected: while the window is absent, Fable runs with no pace check up to the 75% line. That drops the pace half of John's 2026-09-14 ruling ("if Fable is past its daily limit, drop down to Opus").
- (b) Copy the newest backup's Fable number into the self-read row — rejected: one row would carry two writers' numbers, and its note would no longer describe it.
- (c) NULL means degrade to Opus — rejected: it reverses SES-395's explicit NULL → lane direction, which only John can change, and it would idle Fable for most of a fresh week.
- (d) CHOSEN: NULL in the row. `judgment_model()` grades the newest row that carries a Fable number and was taken since this week's Friday 01:00 America/Chicago start. Within one week Fable usage only rises, so an older same-week number is a floor on the truth and degrading on it is never wrong. A pre-reset number never carries past the reset. With no same-week number, NULL → `lane`, so SES-395's direction is unchanged.

Still open: below the possible 75% line, the pace is graded only from backup rows. The laptop CLI always prints the Fable line; whether GitHub's `7d_oi` header appears below 75% is unmeasured. Both become visible after the 2026-09-18 reset. `runner_should_boot().detail.fable_pct` keeps reporting the newest row, so it can read NULL while `detail.judgment_reason` says `fable_rest`. I left the gate function alone so the migration touches one function. If that is confusing on the brief, pointing that key at `judgment_model().fable_pct` is a one-line follow-up.
