**Why a card and not a ticket.** `reverse_decision()` Guard B refuses to erase a
`gated_before_build` card, so a card outlives the ticket id that filed it. A new ticket would be
re-picked, re-discovered and re-reported every cycle, which is the loop the consolidation existed
to end.

**Why every card carries `backlog_id` NULL — and this is the load-bearing detail.**
`scripts/settle-ship.js:216` computes `gatedOpen` as `cards.some(c => c.backlog_id === ticket)`,
and an open card on the ticket forces `decideStatus()` to `partial`. A card naming `SES-424` would
therefore have held open the very id it was filed to outlive, and the close-out would have refused
to settle. The migration's `G2` guard asserts NULL on all three, and `ses-424h` arm B proves the
consequence through the script's own exported `decideStatus()` rather than a re-implementation.

**What each card had to carry.** All seven text fields written (`runner_items` permits NULL on six
of the seven, so a blank card can be filed and nothing stops it), in plain language (`pattern:81`,
`pattern:154`), with each `value_case` **opening with its clause verbatim** from the description
read live this build — never retyped from the kickoff. Evidence measured this build, not recalled:

## Two things the guards caught that reasoning had not

**1. The first migration attempt was rejected by its own guard, and it was right to be.** `G1`
requires exactly one undecided card per phrase. It read **2** for `judged-lane` and the whole `DO`
block rolled back. The cause was in the card text, not the board: card 2's `qa_evidence` had
enumerated all three phrase names while explaining where they did *not* appear, so two cards
matched each phrase and none was answerable alone. Card 2's evidence was rewritten to cite only its
own clause. A guard that only counted "at least one" would have shipped three cards with the
phrases smeared across them.

**2. "step 9" is not a discriminating phrase on this board, and a census keyed on it grades the
live world.** The bare token appears in the descriptions of five live tickets (SES-198, SES-225,
SES-237, SES-427, SES-428) and one open `runner_questions` row — every one a reference to a
numbered runbook step, none of them this item. Both the migration's guards and `ses-424h` key on
the full phrase **`routine-prompt step 9`**, which is unique to the clause (`pattern:162`: a check
grades the change, never the live world).

**A related correction in `ses-424h` arm B.** The kickoff's §4 words arm B as "**0** `backlog_items`
rows outside `{done,delivered,removed,removal proposed}` hold any of the three phrases". SES-424
itself holds all three — they are its own text — and `bd-guardrails` forbids the Builder writing the
ticket's status, so it still reads `partial` when the test runs and a literal zero would be red on
the very change that satisfies it. The test asserts the census is a **subset of `{SES-424}`**
instead: green now, green after the close-out writes `delivered` and the set empties, and red the
moment any other id re-files one of the three. That is the property `pattern:95` actually names.
