## 2. Design choices and the alternatives weighed

1. **One capability, three new Skills, four reused.** The ticket names the shape and it is the AGT-82 shape: a capability is rows (§19b). The three new Skills are one Intent (`jm-linkedin-alerts-intent`) and two Knowledge Skills (`jm-knowledge-posting-verification`, `jm-knowledge-act-call`), both `traits.source` inline (SES-341). Type justification (pattern:136): the legit rules and the act-call cut-offs are reference content the model applies — not who the agent is (identity), not how it reasons or writes (behavior), not a hard prohibition (guardrails). They are separate Skills rather than one because John may correct one without the other and because AGT-156's Sunday market watch may later link the verification Skill alone.
2. **Fit method reused, not restated.** The intent says "exactly as Posting Review: must-haves met / must-haves, cited" and the schema's `must_haves[{phrase, met, evidence_ids}]` and `fit` string are copied from `jm-posting-review-intent`. One method, two callers (pattern:14).
3. **Where the file count went.** Files: the seed, `scripts/personal-agent.js`, and `tests/regression/agt-84-personal-agent.test.mjs`. A new `agt-154` test file was the first draft; it is dropped because adding a 12th `READ_MAP` key turns `agt-84` (b) red on its literal list and its live arm, and a bug the feature itself introduces is fixed inside the feature (pattern:124) — that edit alone consumes the third file. Extending the AGT-84 suite with parts (f)–(i) keeps every proof in one place (pattern:17) and stays at three files with no split.
4. **`SERVICE_CATALOG` sentence, discharged without a file.** The ticket says "SERVICE_CATALOG entry; runs logged with agent-log.js". Measured: none of the 11 career capabilities has a catalog slug; the personal lane logs `--ai-type=agent-turn`, an existing catalog slug, with the capability in `--feature`. A per-slug entry for the 12th capability alone would be inconsistent with the other 11 and would cost the fourth file. The ticket's sentence is satisfied by the existing slug; nothing is dropped.
5. **Runbook row deferred to AGT-156.** `docs/runbooks/personal-agent.md` (a) would gain `linkedin alerts` → `career-linkedin-alerts`; AGT-156 already rewrites that runbook's schedule section, so the row lands there, not as a fourth file here.
6. **`KIND_FILTERS` becomes per-capability, not a special case.** The narrowest change that works (pattern:65): the existing filter stays exactly as it is for match-finder; the map is keyed by capability slug so no `if (capability === …)` enters the script. Alert review needs every posting row: reposting history (SUSPECT rule "same role reposted 3+ times over 60+ days") and the already-applied SKIP rule read old rows, not only `status=new`.
7. **Intake through the existing `--input-file`, parsed when it is JSON.** `loadInput` returns `{input, intake}`; a file that parses as JSON with a `cards` array becomes `task_context.intake`, anything else stays raw text. No new flag, no capability-keyed branch: the shape of the file decides (pattern:2). The prompt therefore carries AGT-153's cards as structured data the intent can address by `job_id`.
8. **Competitors are read data, the flag is output only.** `task_context.competitors` comes from `market_records` (`kind=competitor`, not retired) as `[{name, domain}]` — public facts, the table AGT-120 created. The intent flags a job's company; it never names the agent that receives the lead (Rule #1); AGT-155 owns `market_leads` and the send.
9. **Tracking URLs are refused before any write** (pattern:10 — structural, not an instruction). `validateAnswer` refuses any `data.url` carrying `trackingId=`, `otpToken=` or the `/comm/jobs/` path, and a `posting` whose `data.linkedin_job_id` does not match its `data.url` `https://www.linkedin.com/jobs/view/<id>/`. John's "click email links (tracking)" never-rule thus holds at the write path as well as in the guardrails.
10. **`market_requirement` only from legit / could-not-verify jobs.** Enforced in the intent method and stated in the kickoff; a schema-level cross-item rule is not expressible in JSON Schema and a validator rule would need the per-job verdict alongside each record — not worth a second mechanism for a rule the corrections loop will catch (pattern:66).
11. **Guardrails append, not rewrite.** `jm-guardrails.must_not` gains seven entries (6 → 13); the existing six stay byte-identical. The existing "read a job network that forbids automated reading" stays: the alert mailbox is exactly the path `jm-knowledge-method` already allows ("forwards alerts to a mailbox … the platform reads"), and the public job page is read by web search without login — the verification Skill says so.
12. **Before-images.** 12 inserted rows get `row_data NULL` images (the reversal deletes them); the `jm-guardrails` UPDATE gets a real pre-image (`to_jsonb(row)`), so `reverse_decision()` restores the 6-entry list. Total 13, one `agent-row` decision handle, `cycle_id` set and `session_name` NULL because this build runs under the cycle.
13. **Model.** Judgment lane `claude-fable-5-1`: Skill authoring against John's verbatim rules and a schema that the platform enforces is judgment-dense (pattern:125). The capability's own call runs on the session sub-agent (subscription), as every Jerry run does.

### 3a. `jm-linkedin-alerts-intent` — name "Review the LinkedIn Alerts" (intent, max_tokens 12000, technical_services `["structured-output","web-search"]`)

objective: `Turn the intake of LinkedIn job-alert cards into verdicts the principal can act on: legit or not, fit, and an act call — with the records to keep.`

method: `Your task_context carries intake (the platform's intake file: fetched_at, since, sender, cards — each card job_id, url, title, company, location, message_uid, alert_date), the target, resume_fact, ladder_rung, evidence, network_contact, posting and log records, competitors (public company names and domains), and the corrections. Read the corrections first. For EVERY card, in order: (1) VERIFY — read the public job page at the card's url (web search; never log in, never follow an email link) and apply the Posting Verification rules to reach one verdict: legit, suspect, or could not verify, with the reason and the sources you read; when web search is absent say so and mark could not verify. (2) FIT — extract the must-haves in the posting's own phrases, match each to cited evidence, and state fit as must-haves met over must-haves, exactly as Posting Review does; name the target row the posting belongs to. (3) ACT — apply the Act Call rules to reach one call: apply now, apply with prep, watch, or skip, with the reason; for apply with prep name the one material gap and the prep that closes it; for apply now and apply with prep name the nearest network_contact, or say there is none. (4) COMPETITOR — set competitor true when the company appears in competitors or its public page sells what the platform sells; give the public fact that says so; never send anything — the platform routes the lead. (5) PAY — report stated pay only; never estimate. Put every suspect card in scam_warnings, first. records_to_write: one posting record per card with data {linkedin_job_id, url (plain, rebuilt from the id), title, company, location, alert_date, status: reviewed, legit, legit_reason, act, act_reason, fit, must_haves, gap, prep, nearest_contact, competitor, stated_pay, target_row}; market_requirement records ONLY from cards whose legit verdict is not suspect. Never invent a company, a page, a figure or a URL; an unread page is could not verify, not legit.`

output_desc: `Per job: company, title, plain url, must-haves, fit, legit verdict and reason, act call and reason, gap and prep, nearest contact, competitor flag; scam warnings first; a one-paragraph summary; records_to_write.`

traits (JSON):

### 3b. `jm-knowledge-posting-verification` — name "Jerry Maguire Knowledge — Posting Verification" (knowledge, max_tokens 8000, traits `{"source":"inline"}`, description "The legit / suspect / could-not-verify rules and the sources allowed for them.")

objective: `Hold the rules that decide whether a job-alert posting is real, and which public sources may be read to decide it.`

method: `THE VERDICTS. LEGIT = the same role is found on the company's own careers page or applicant-tracking system (Greenhouse, Lever, Workday, Ashby) AND the company has a real domain that matches. SUSPECT = any one of: money, a bank account, an ID document or a purchase asked for before an interview; contact moved off LinkedIn to WhatsApp, Telegram or a personal Gmail; the company cannot be found or its domain does not match the posting; the same role reposted three or more times over sixty or more days (count the posting records); the title and the pay do not match. COULD NOT VERIFY = no proof either way — never promote it to legit. THE SOURCES, all public and read without any login: the LinkedIn job page rebuilt from the job id as https://www.linkedin.com/jobs/view/<id>/ (never a link from an email — those carry tracking); the company careers page or ATS board; the company domain, size and recent news; reposting history from the posting records supplied; the pay stated on the posting only — pay is never estimated. Every verdict names the sources read with the date; a page that would not load is recorded as not read.`

### 3c. `jm-knowledge-act-call` — name "Jerry Maguire Knowledge — the Act Call" (knowledge, max_tokens 8000, traits `{"source":"inline"}`, description "The four act calls and their cut-offs.")

objective: `Hold the rule that turns a verdict and a fit into one of four calls.`

method: `FIT is must-haves met over must-haves, stated as a fraction, exactly as Posting Review scores it; "minor" means a must-have the evidence nearly meets; "material" means one it does not. THE FOUR CALLS, tested in this order: SKIP when the posting is suspect, or fit is below one half, or the title sits below Senior Product Manager, or the stated pay is below the target row's pay floor, or the principal already applied (a posting record for the same job id or company and title with an applied status, or a log record saying so). APPLY NOW when every must-have is met or all but one minor one, the title is on the target row's rung, and the posting is at most fourteen days old. APPLY WITH PREP when fit is at least two thirds and exactly one material gap can be named together with the prep that closes it. WATCH when fit is below two thirds, or the posting is more than thirty days old, but the company or role is worth tracking — it goes on the watch list. Age is counted from the posting's own date when the page states it, else from the alert date. Every call carries its reason in one sentence and, for apply now and apply with prep, the nearest network contact or the statement that there is none.`

### 3d. `jm-guardrails` — UPDATE

`must_not` = the existing six entries, byte-identical, followed by exactly these seven strings in this order: `apply to, message or contact anyone`; `click an email link - rebuild the job URL from the id`; `log into LinkedIn or any job site`; `change the mailbox (flag, move, delete, reply)`; `share personal data outside career_records`; `spend money`; `estimate pay - stated pay only`. `must` unchanged.
