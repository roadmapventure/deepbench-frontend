## Why the ordering half is a runbook byte, and why not this cycle
The only place the re-render can be ordered after the card is the runbook's serial tail (4) — the one sanctioned second push, already re-exporting the snapshot on diff. A byte in `runner-cycle.md` re-renders `docs/runbooks/cycle-card.md` (sha-pinned, `render-cycle-card.js:169`) and requires the gated `--repin --cycle-id` (`:220-226`), "build work only under a ticket that names the write". With the renderer, the verifier and the guard that is 5 files and a gated write against a 3-file cap. Alternatives rejected: (a) a second refusal in the renderer when the top row has no card — at 7a the card never exists, so it would block every close-out by construction; (b) hooking the re-render into `export-backlog-snapshot.js` because tail (4) already runs it — one script would own two derived files and step 7 would also run it (pattern:53, pattern:15); (c) a new script — still needs a runbook line to be invoked. So: the check ships now with the remedy naming tail (4); the sentence is the ticket's declared remainder and the ticket settles `partial` via `settle-ship.js --remainder`, never refiled under a new number (pattern:95).
