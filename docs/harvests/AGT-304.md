## 4. Why ONE file this slice, and not two

Caps were NOT the binding constraint — `class_autonomy('P9 - Bug Fixes')` gave **3 files / 4 tasks** (bug_fix, rung 4, streak 4, auto_done true) and this slice uses 1 / 2. **The byte cap was.** I assembled the two-arm kickoff (ses-378d + agt-487) in full and measured it repeatedly against `KICKOFF_BYTE_CAP = 8192`: it would not go below **9,065 bytes** with both arms' facts intact — four edit sites, five anchors, the 740-byte BASELINE block and three code stubs. Getting under the cap meant cutting a task's line numbers, its exact strings or its QA numbers, which is the one thing the Designer's own rule forbids ("move reasoning to the harvest, never drop a task's facts"). So this follows slice 21's precedent exactly: ship what fits with its facts intact, carry the rest forward diagnosed. The shipped kickoff is **8,140 bytes**.

This is the second consecutive slice where the byte cap, not the file/task cap, set the slice boundary. It is worth John or the Development Manager knowing that AGT-304's remaining arms are individually small but each costs ~2 KB of kickoff, so the ticket will take roughly one arm per slice until a cheaper hand-off than a full kickoff exists for a one-line test repair. That is an observation, not a `pattern:172` case: the file/task caps were never reached, so there is nothing for the Development Manager to split or waive.

## 5. The structural question the orchestrator put to me — my answer is NO, and why

Slice 21 raised a real finding: an equality pin on live agent content is a standing-red generator, and `agt-132-finding-routes` and `ses-378d` both pin `dm-guardrails`, so one of John's appends reds two suites at once. I was asked whether slice 22 should be that structural fix (a Skill-row count reported, never asserted) instead of another one-off. I measured before answering, and I recommend against it as this slice, for three reasons:

1. **It clears no more reds than the one-off.** `const MUST_AFTER = 5;` resolves in exactly **2** tracked files (`ses-378d` and `agt-132`). Fixing both would clear `ses-378d` and remove ONE of `agt-132`'s five failing arms — `agt-132` stays red on arms B, C, D and G regardless. So the structural pass costs two files to deliver the same single green suite, and it would collide with `agt-132`'s own future slice.
2. **The class is far wider than Skill rows, so a Skill-row mechanism would be the wrong mechanism.** Reading all 31 `[FAIL]` messages, the dominant failure mode is a test grading live world state, not a Skill-row count: `agt-173` ("that is a real finding about the board, not a bug in this guard"), `agt-166` ("a zero here is either a finished drain or a broken predicate"), `agt-245` ("a re-freeze is due"), `agt-267` (9 of 19 companies), `agt-277` (a missing 04:00 reading), `ses-332` (2 board rows), `agt-70` (live ledger weeks), `ses-424h` (a live card count), `agt-487` (a live list size), `agt-314` (`runner_settings`), `ses-84` (a live claim), and `ses-424g` (a live board edge). A mechanism scoped to `skill_profiles` counts would address two of those.
3. **`pattern:65` and `pattern:120`** both point the same way: take the narrowest fix that resolves the flagged red and file the general mechanism as its own ticket, sized to the real class. `pattern:123`'s "fewer future tickets" argues for the mechanism, but only once it is scoped to the class that actually generates the reds.

**Recommendation to file (not filed by me — this is a design turn):** one ticket for "a regression arm reports live world state and asserts only the change", scoped from the twelve arms listed above rather than from Skill rows, to be designed after AGT-304's per-arm reds are down. Each per-arm fix this ticket ships — floors plus a declared `notRun`, a reported count — is already that ticket's shape applied at one site, so nothing shipped here has to be undone.
