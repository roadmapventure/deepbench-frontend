## 2. The diagnosis — two reds, ONE root, measured not inherited

Slice 23 §4 flagged `agt-490-parked-home` and `agt-493-ticket-validation` as possibly sharing a `projects` status fact and told the next Designer to check the board before touching either. Checked, and the hypothesis is confirmed and sharpened — the two arms assert **opposite** things about the same slug:

- Live `projects` (read-only, 18 rows): **`go-to-market` is `paused`** with 1 epic. The only `executing` projects are `dev-manager-capabilities` (2 epics) and `tooling` (2 epics).
- `tests/regression/agt-490-parked-home.test.mjs:55` — `const EXEC_HOME = "go-to-market";  // executing -- the refusal`. Arm C case 4b asserts a park into it is REFUSED. Run this cycle: `(4 the three refusals) a park into go-to-market must be REFUSED; got HTTP 200`. `park_target()` refuses only `v_status not in ('paused','planned')`, so a paused home now **accepts** the park.
- `tests/regression/agt-493-ticket-validation.test.mjs:59-60` — `const HOME = "go-to-market";` / `HOME_EPIC_EXPECTED = "589f2d4b-…"`. Arm C asserts a move into it LANDS. Run this cycle: `HTTP 400 code=23514 "AGT-309: home_project go-to-market is not an executing project with an epic"`. `placement_target()` resolves the epic only `where pj.slug = p_home and pj.status = 'executing'` and raises AGT-309 otherwise.

Both files are therefore correct about the *door* and wrong only about the *subject*: each hardcodes one project slug as a permanent property of the board. One `UPDATE projects SET status` — the platform doing exactly what it is for — reds both. That is the standing-red generator this ticket exists to remove (docs/STANDARDS.md:238; pattern:162).

**Why a live resolver and not a board write.** Setting `go-to-market` back to `executing` would green both tests today and red them again the next time John pauses it; it also asserts a product fact (which project is running) on the authority of a regression test, which is backwards. Rejected. **Why not re-pin to `dev-manager-capabilities`.** Same defect, new slug. Rejected. **Why not delete the arms.** They grade real refusal/placement behaviour that nothing else covers; the ticket forbids clearing a red by weakening an assertion. Rejected.

**The resolver mirrors the database rule rather than inventing one.** `placement_target()` picks `order by e.created_at, e.id limit 1` over an `executing` project; `park_target()` only needs *any* executing slug. So one function answering "first executing project by slug, and its oldest epic" serves both doors. Run live this cycle, the exact code in T1 returns `{slug:"dev-manager-capabilities", epicId:"e0335c39-0728-4ff1-99ca-232a02912176"}` — that project's two epics are `e0335c39` (2026-09-25) and `d1010f89` (2026-10-13), oldest wins, matching the function. It returns null rather than throwing when no executing project has an epic, because that is a live board state (board-state.js already calls it `drained`/`starved`), not a regression — the caller `notRun`s.

It lands in `tests/regression/_lib/board-state.js` because that module already exists for exactly this (live board facts read through *the caller's own* `pg`/`req` helper, "passed in rather than re-implemented so this module cannot become a second HTTP client") — pattern:14, pattern:17.
