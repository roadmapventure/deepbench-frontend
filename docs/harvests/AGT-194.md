## 1. Premise: ALIVE, and measured three ways

The chain handed me three pointers and told me to verify them rather than trust them. All three hold.

**Pointer 1 — the workflow.** `.github/workflows/ci.yml:187-190` reads exactly `concurrency:` / `group: ci-${{ github.ref }}` / `cancel-in-progress: true`. `on: push: branches: [dev, main]`. Confirmed by reading the file this cycle.

**Pointer 2 — the chain's own ship.** Queried `public.ci_run_conclusions` by sha. `d524d6d0` (AGT-172's ship): `Build (blocking)` = `success`, `Tripwire + regression (blocking)` = `cancelled`, `concluded_at` `2026-09-27T01:53:42Z`. This chain's own close-out `034876e5` concluded `01:59:48Z` — 366 seconds later — and is *itself* cancelled (superseded in turn). So the claim is stronger than "peers cancel each other": **a cycle's own second push cancels its own ship's grade.** That matters for the business case, because it means the fix pays even for a lone cycle, and it is the line I put in the kickoff's CONTEXT rather than the harvest.

**Pointer 3 — the population.** 535 rows, every one `ref='dev'`, `2026-08-31` → `2026-09-27`. Job/conclusion histogram:

That distribution is the mechanism's signature — these are supersessions minutes apart, not infrastructure flakes.

## 2. What I did NOT design, and why

**The re-grade path.** The ticket's title ends "and no re-grade can clear it." I read `regradeBranch()` (verifier.js:2172-2336) and could not prove that clause as written. The ancestry check (`git merge-base --is-ancestor graded_sha ci_sha`) passes fine for a landed sha with no conclusion of its own; what actually starves the re-grade is `regradable_ships()` requiring the *newest* `ref='dev'` conclusion to be `success` on the mapped job — and `Tripwire + regression (blocking)` is `failure` on 337 of 535 runs, so dev is usually red there for unrelated reasons. That is a real second problem, but it is a different one, it is not what the caller scoped, and designing it would blow the 3-file cap. I did not file it as a new ticket either: pattern:95 forbids discharging a ticket's own acceptance criterion under a new number, and half (b) makes the gap visible, which is the part of that clause this cycle can honestly close. I am flagging it here so the next reader of AGT-194 does not think I measured it and agreed.

**A second concurrency knob.** Rejected: pattern:67 — every proposed cap or knob must justify itself against a bound that already exists. `github.ref` is already in the key.

**Keying only `dev` by branch name.** Rejected: `github.ref` already separates `refs/heads/dev` from `refs/heads/main`, so a branch test is a second expression term that changes no behaviour except to leave `main` pushes cancellable. A main push's sha deserves a conclusion for the same reason a dev push's does. This is a Designer call on record (JOHN-0925-DESIGNER-DECIDES), not a John question — it is neither money, nor `dev → main`, nor hiring.

## 3. The four things the caller told me to weigh honestly

**(1) The live two-push proof is OUT of this cycle.** Not because it is expensive — because it is *structurally unavailable here*. Proving (a) end to end requires the new workflow to already be on dev, then two dev pushes a minute apart, then both runs to conclude. The ship's own verdict is written before either conclusion exists, so no QA inside this cycle can assert it; and a design session does not push at all. What I designed instead is real evidence rather than a restatement: **the workflow file is data**, so the test extracts the `group:` expression from the file on disk and evaluates it for two synthetic contexts, asserting the push pair *differs* by sha and the pull_request pair *matches*. On the pre-ship file the push pair is identical (`ci-refs/heads/dev` both times), so that arm fails before the change and passes after — which is exactly the discriminator the role demands. The live pair is then named as an arm a later cycle discharges, and this cycle's own two pushes are that pair. I have not run it and the kickoff says so twice, including "Never claim a live pair you did not run."

**(2) The CI-minutes cost, named rather than discovered later.** After the change, the ~82 runs that were cancelled would instead finish: **mean 3.4 extra blocking-suite completions/day, worst observed 12/day (2026-09-23)**. Total conclusions peak at 65/day (2026-09-02) ≈ 2.7/hour, so the number of runs in flight at once stays in the low single digits for any plausible suite duration — nowhere near GitHub's smallest concurrent-job allowance. The honest caveat, stated in the kickoff: **I did not verify the account's plan tier or its concurrent-job ceiling** — I have no read on the billing surface and would not guess one. The reason I am comfortable shipping without it is the *failure direction*: a concurrency ceiling makes a run **queue**, it never makes a conclusion disappear. So the worst case of being wrong about minutes is a slower grade, while the bug being fixed is a lost grade. That asymmetry is what makes the trade one-way.

**(3) Failure direction of a CI-workflow edit.** A malformed `${{ }}` expression makes the whole workflow file invalid and *nothing runs for anyone* — strictly worse than the bug. Two guards, both before the push: the new test's part (C) spawns `python3 -c "import yaml…"` on `ci.yml` and asserts it parses, that `concurrency.group` is a single string, and that `jobs` still lists `build`, `checks`, `report-conclusion`; and the regression suite runs locally as task 4 before `git push`. I verified the exact replacement string parses this cycle, against the real file: PyYAML reads the whole group as one plain scalar and the job list is unchanged. Part (C) calls `notRun("C", …)` if `python3`/PyYAML is missing rather than passing — a validity check that silently passes is the one shape worse than no check (pattern:34, and SES-393's lesson about CI's own environment).

**(4) Routing around `docs/runbooks/runner-cycle.md` — yes, cleanly.** Four cycles in this chain have lost a slice to the SES-377 coupling (cycle-card re-render + BYTES_AT_SHIP re-pin), filed as open finding `99cf0b5b`, John's to waive. I did not need the waiver. AGT-174 (`0f1957be`, v7.0.622) shipped *exactly* the shape half (b) needs — a `state_render_cycle` finding computed in `verifier.js`, surfaced as one always-printed prose line plus one `--json` key plus one key in each judge context — and `git show --stat` on that commit lists `scripts/render-claude-state.js`, `scripts/verifier.js`, its test, and its own kickoff/harvest: **no `runner-cycle.md` edit, no migration, no new `runner_verdicts` column.** Half (b) follows it verbatim, so the trio is not engaged and the cap holds at 3 files (pattern:17 — extend a structure that already fits).
