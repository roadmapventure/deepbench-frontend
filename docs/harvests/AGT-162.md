## 2. The no-inference seam: why `execution_type`, why not `resources/*`

Both routes are generic (no slug conditional). The tie-breaker is who pulls the bundle.

- **MCP resources are application-driven.** The spec makes `resources/read` a client-side act: the user (or the host app) attaches a resource to the context; the model does not call `resources/read` the way it calls a tool. Claude Desktop shows resources in the attachment picker; a custom connector on claude.ai exposes tools to the model. AGT-165's demo is "start a new chat and ask Brittany something" -- the calling model must fetch the bundle on its own, which only `tools/call` gives it. The ticket text itself says "exposing one read-only tool".
- **A resource is not a capability.** `resources/list` would be a second inventory that `visibleRows()` does not govern (new lane-leak surface), with no `capabilities` row describing it and nothing in `agent_capability_assignments` holding it -- the opposite of §19b. It would also need `resources/templates/list` for the per-agent URI, three new methods and a new `initialize` capability, for the same bytes returned.
- **`execution_type` is already the platform's word for this.** The column exists with default `'ai'`, `dan-db-assembly` has been `'deterministic'` since AG-13, `buildSignatureConfig()` stamps it into every `call_facts`, `scripts/run-project.js:903` already routes deterministic capabilities to `engines: ["executor"]`, and `toTool()` already prints it in the description. A branch on it is a column read, exactly what `.claude/rules/capabilities-are-data.md` allows ("a generic trait/field read") and what `tests/regression/mcp-3-server.test.mjs` part (d)'s no-slug-conditional regex permits.
- **The handler is named in data**, `traits.handler` on the Intent row, mirroring `request-receivable.js`. `DETERMINISTIC_HANDLERS` is keyed on the handler NAME the row declares, never on a slug -- the same shape as `HANDLERS`. Why a second map rather than exporting `HANDLERS`: request-receivable.js's handlers take the MODEL's structured output as `content` after a model call; a deterministic tool takes the CALLER's `task_context` as `content`. Same signature, different provenance, and touching request-receivable.js would be a fourth file. Merging the two maps is filed residue.
- **Not `runCapability()` itself.** Branching on `execution_type` inside `execute.js` would serve every caller, but `execute.js` is 188 KB, the ticket is MCP-scoped, nothing else calls a deterministic capability today, and pattern 65/120 say ship the per-instance version and file the normalization. Filed.

## 3. The Designer's calls, with the reversal handle for each

1. Route = `execution_type` (above). Reversal: revert the `mcp.js` commit; the data rows are inert without it.
2. Reuse `dan-db-assembly` rather than a new capability: it IS the deterministic prompt-assembly capability (AG-13, `docs/kickoffs/v5.2.26-AG13-dan-bingham-bench.md`), held by Dan Bingham, the Prompt Architect (§19). A second deterministic capability under Dan meaning the same thing is the duplication pattern 14/17 forbids. Its name/description become tester-facing so a calling model picks it by description. Reversal: `reverse_decision()` restores the `capabilities` row from the before-image; `delete from capability_skill_profiles where skill_profile_slug='agent-bundle-intent'; delete from skill_profiles where slug='agent-bundle-intent'`.
3. The bundle reads the primitives Teach writes, not the assembled prompt alone: `agents`, `agent_configs`, Skill sections (via `assemblePrompt()`), `knowledge_entries`, and the Library catalog. On §19c: `knowledge_entries` is "self only, no cross-agent access" -- here the requester IS the target (the id comes from the caller, `requestingAgentId: t`), and the reader is the platform's scaffold assembly acting for that agent, exactly as `api/plan.js` and `lib/agent-run.js` read the running agent's own rows. No Dan row names any agent (Rule #1). `the_library` is reached only through `lib/librarian.js` (`describeLibraryCatalog`), so a blank agent with `data_room_access []` gets `denied-no-access` and the bundle says so (pattern 34) rather than pretending a Library exists. No semantic retrieval: there is no question to embed, and an embedding call would be inference on DeepBench's side.
4. Input contract in data: `traits.input_schema` on the Intent row is the home `TOOL_INPUT_SCHEMAS`'s own comment (mcp.js 234-240) names for "the SECOND capability that needs one". This IS the second. `verify-ship`'s entry stays in code because moving it edits `vf-verdict-intent`, a governance agent's Skill row (`.claude/rules/agent-roster-inert.md`, SES-337 self-certification). Filed: move it and delete the table.
5. Lane rule for the TARGET agent: same predicate as `visibleRows()` (`lane === 'product' || governanceUnlocked`), applied by the handler from `handler_context.governance_unlocked`; a hidden agent and a missing agent get the identical `Unknown agent: <id>` so the tool is not an agent-inventory oracle.
6. Logging: one `ai_activity_log` row per bundle call, `ai_type 'deterministic'`, `feature 'dan-db-assembly'`, no tokens, no model, no cost (`.claude/rules/capability-logging.md`); `call_source 'mcp'` and `screen_origin 'mcp'` from `runWithCallSource`. `agentId` is the holder (Dan) -- the capability that executed -- with `target_agent_id` in `call_facts`, so the AI Audit never shows deterministic plumbing as the target agent acting (pattern 42).
7. Brittany (AGT-164) is not designed around: the tool takes any agent id; live QA uses `bob` (3 role/guardrail/knowledge numbers measured) and `designer` (governance, for the lane rule).

## B. Task 2 -- the handler's exact strings

Service-key REST (`process.env.SUPABASE_URL` + `SUPABASE_SERVICE_KEY`, headers `apikey` and `Authorization: Bearer`), `t` = `content.agent_id`, `tenant` = `tenant_id || 'global'`:

1. `agents?id=eq.<t>&select=id,name,role,specialty,bio,lane,is_active,data_room_access&limit=1` -- no row, `is_active !== true`, or `lane !== 'product' && handler_context?.governance_unlocked !== true` -> `throw new Error(\`Unknown agent: ${t}\`)`. `agent` = `{ id, name, role, specialty, bio }`.
2. `agent_configs?agent_id=eq.<t>&tenant_id=eq.<tenant>&select=type,name,text&order=type,name` -> `role_prompts` = rows with `type 'role_prompt'`, `guardrails` = `type 'guardrail'`, `output_formats` = `type 'output_format'`, each `{ name, text }`.
3. `assemblePrompt({ agent_id: t, tenant_id: tenant, task_context: {} })` (import from `../../prompt/db-assembly.js`) -> `sections.filter(s => !['current-task','task-details','prior-conversation','voice'].includes(s.slug)).map(s => ({ slug: s.slug, label: s.label, type: s.type, content: s.content, fetch_instruction: s.fetch_instruction }))`.
4. `knowledge_entries?agent_id=eq.<t>&tenant_id=eq.<tenant>&status=eq.active&select=id,title,category,content,teaching_note,source,created_at&order=created_at.asc`.
5. `describeLibraryCatalog({ requestingAgentId: t, tenantId: tenant })` (import from `../../../lib/librarian.js`) -> `library = { data_room_access: agentRow.data_room_access || [], catalog: r.context || '', records: r.matchCount || 0, tier: r._librarian?.tier || null }`.

Return `{ agent, role_prompts, guardrails, output_formats, sections, knowledge_entries, library, no_inference: true }`.

`logActivity` (import from `../../../lib/activity-log.js`) once, after the reads: `{ tenantId: tenant, agentId: agent_id, aiType: 'deterministic', feature: 'dan-db-assembly', latencyMs: Date.now() - startTime, callFacts: { target_agent_id: t, role_prompts: role_prompts.length, guardrails: guardrails.length, sections: sections.length, knowledge_entries: knowledge_entries.length, library_records: library.records, library_tier: library.tier } }`. No tokens, no model, no cost -- the `.claude/rules/capability-logging.md` deterministic shape, same as `api/_lib/handlers/library-lookup.js:65`.
