## 2. What this cycle builds, and why only that

The ticket carries the Development Manager's ruling on the cap (pattern:172): the cap is not waived, the helper lands in one cycle, the suites follow in slices of three, agt-86b first. This kickoff is that first cycle: one helper, one test of the helper, 2 files / 3 tasks against caps 4 / 5.

I did not add agt-86b to this cycle. Helper plus its test plus the first slice of three is 5 files; taking one file out of a slice the Manager grouped would be me re-slicing on my own authority. The helper is still proved against live PostgREST without a consumer: the test's arm L reads the nil decision's own rows through it.

Design, in order of what each part buys:
- `countScoped` refuses a read with no filter before any network call. This is the structural half: once a suite counts through the helper, the whole-table read cannot be written.
- `gradeOwnWrites` reads the scopes, asserts the precondition (the probe's key owns exactly the declared rows, zero by default), runs the probe, reads again and asserts the declared delta (zero by default). The precondition is what makes "unchanged" mean something, and it is what catches a scope that is not really the probe's own -- the helper cannot judge that from the query text.
- HEAD with `Prefer: count=exact` (the reader `agt-86b` already uses): an exact count with no body, so the 1000-row cut AGT-530 describes cannot occur in a count taken this way.
- `fetchImpl` is injectable, so the grade is tested against a fake ledger where peers write between the reads: the whole-table count moves 100 -> 103 while the scoped grade passes, and a probe that writes its own row is caught.
