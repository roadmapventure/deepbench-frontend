## The wording conflict in the ticket (pattern:89, pattern:102)

The ticket says "when settle-ship.js settles that ticket done". Measured: settle-ship.js writes `delivered` or `partial` only; `done` is in `UNSETTLEABLE` (:122, "John's word, SES-154"). The move `delivered → done` is made by `public.sweep_decision_windows()` (runbook :4285) once the ship decision finalises unreversed. So "settles done" cannot be implemented as written. Decision: the trigger is the close-out's `delivered`, which is the finished state the script owns and the state both found cases turn on — `0078af4d` sat `in_progress` with AGT-432 `delivered`; `418095d5` was closed while AGT-427 settled `partial` (slice 1 of 2 → trigger 1). The existing runbook practice already closes the directive in the shipping cycle (step 9), before `done`. Outcome `shipped` matches the runbook's own example ("shipped as SES-125").

Alternative weighed: put the close in `sweep_decision_windows()` (SQL, fires on `done`). Rejected for this ticket — it names settle-ship.js and the guard test "a second settle changes nothing" is a settle-ship test; and a directive would then sit open for the whole reversal window after its ship, which is the symptom the ticket reports. If a reversed ship ever needs the directive reopened, that is a new row with the evidence; `close_directive()` has no reopen path and SES-129 says a verdict on John's card is never overwritten.

## Design choices (recorded, reversible)

1. Pure plan + thin IO, the file's own shape: `planDirectiveClose()` is pure so arm A asserts by value; `closeDirectives()` is the only network path and runs LAST in `main()` (after `writeCost`), so a failed close can take neither the status nor the cost write with it — the same ordering argument the file already makes for cost.
2. The close predicate filters `type = 'directive'` and `status in ('queued','in_progress')` in the pure function, not only in the REST filter: standing decisions (`status='standing'`, SES-353), drain-epics (never consumed, SES-111) and budget overrides can never be closed by a ticket settle even if someone sets `item_ref` on them.
3. Idempotent twice over: the pre-filter finds no open row on a second settle (0 RPCs), and `close_directive()` itself answers `already_closed` if called anyway.
4. `--resettle` writes no directive: it only moves `delivered → partial`, and reopening is not a thing this build owns.
5. No runbook edit: `runner-cycle.md` is 380,978 of 381,000 bytes (agt-138 ceiling; 2 bytes of headroom). Step 9's manual call stays valid as the idempotent fallback. No cycle-card edit: `render-cycle-card.js:148` is pinned verbatim by `agt-391-selective-regression.test.mjs:218`; changing it adds two files for a sentence. The script's own stdout line is the record of the close.
6. `a738da38`'s governing ticket is not named anywhere in the repo (only `docs/harvests/HANDOFF-product-team-self-completion-1009.md:12`: "rule every gate card — done"). T1 reads its `body`; if no finished ticket matches, it stays open and `item_ref` NULL, reported — never a guess.
7. `418095d5` is already closed (ticket text) while AGT-427 is partial. It is linked (`item_ref`) but not touched otherwise: there is no reopen, and the rule "partial never closes" is forward-looking.
8. RPC argument names: the repo holds only the positional form `close_directive(cycle, directive, outcome, note)` (runbook :4136, SESSIONS.md:14115). PostgREST `rpc/` needs the named parameters, so T1 (a) measures `pg_get_function_identity_arguments` and the kickoff defines ARGS from it rather than guessing `p_*`.
