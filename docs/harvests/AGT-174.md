## 3. Where the check goes, and the variants rejected

**Chosen: a pure `renderingCycleFinding()` in `render-claude-state.js`, consumed non-gating by
`scripts/verifier.js`.** The pin (`ledger-pin:` in CLAUDE-STATE.md's trailing comment, written by
`renderPin`) is the render's ledger rows **in order**, so `pin[0]` *is* the render's top ledger row
and `parsePin` already exists to read it. The verifier is the one production caller that already
receives `--cycle-id` (runbook step 7a's second line, immediately after the render), so the check
arms itself with no runbook edit and no new command line.

Rejected, with reasons:

- **`--cycle=<uuid>` on the renderer itself.** Nothing would pass it: every production invocation is
  the runbook's own command line, so arming it needs the runbook edit above. An optional flag no
  caller sets is unreachable code that reports nothing (pattern:33).
- **Deriving "the rendering cycle" from git inside the renderer** (HEAD == the pushed sha). It adds a
  `child_process` dependency to a script that has none, and CI clones at depth 1 (SES-393), so the
  ancestry walk is unreliable there. Also false-positives at step 7's second, no-op render, where
  close-out commits have moved HEAD past the ship sha.
- **Inferring it from "a row with a `version` but no `push_sha`".** Every in-flight peer cycle looks
  exactly like that (this cycle and `c1d1fb0c` both did, live), so it cannot identify *self*.
- **A new standalone `check-state-freshness.js`.** Nothing would call it; a rule each cycle must
  remember is the rule that gets silently forgotten (the `record_skip` precedent the runbook cites
  eight times over).
- **Making it gate.** Explicitly refused. `render-claude-state.js` already owns one deliberate
  exit-2 refusal — a body that lost the standing-brief link, John's condition on gated card
  `37b22393` — and a second refusal path in the close-out chain is a second way to wedge every
  ship. Under parallel cycles (register B42) a peer that pushes and writes its sha between your push
  and your render legitimately takes `pin[0]`, which is why the finding distinguishes
  `lag: true` (absent from the pin — this ticket's bug) from `lag: false` (present but not first — a
  peer, expected).
