Root cause, read in code rather than inferred: `docs/design/agt-140-project-priority-pick.sql:295`
and `:561` admit a row only when `b.claimed_by IS NULL OR b.claimed_at < now() - make_interval(hours
=> runner_settings.claim_stale_hours)`. The filter is **holder-blind** — it does not compare
`claimed_by` to the asking cycle, and `runner_should_boot()` takes no arguments, so it cannot. The
cycle's own claim therefore evicts its own ticket from the pick between the two passes.
`detail.pick` carries only `lane,title,backlog_id,predicted_cycles,predicted_pct_of_week` — no
`claimed_by` — so pass 2 has no way to distinguish its own claim from a peer's without a new read.

Confirmed the claim is the *cycle's*, not the driver's: `runner-cycle.md` step 5's block runs
`--dry-run`, and `ses-378-manager-takes-the-pick.test.mjs` pins the reason —
"the claim is the cycle's own (register B42); a driver-made claim breaks the push gate".

## Alternatives weighed, and why they lost

1. **Make `runner_should_boot()` holder-aware (a `p_cycle_id` parameter).** Rejected. This is the
   most direct fix and the most dangerous one: `.claude/rules/supabase-function-signature.md`
   records that adding a parameter creates a *new overload*, `CREATE OR REPLACE` does not replace
   the old one, and PostgREST then cannot resolve the omitted-parameter call — DAT-12 returned 0
   chunks on every unscoped retrieval for ~90 seconds. `runner_should_boot()` is the function every
   cycle boots through and several tests read directly; an ambiguity there stops the runner
   platform-wide, not one ticket. Narrowest layer that actually works is the driver (pattern:8).
2. **Have pass 1 stop writing the pick, or pass 2 stop re-reading it.** Rejected: the re-read is the
   negative control that makes the state file evidence rather than an instruction (header note 3).
   Removing it would let an edited state file claim any ticket.
3. **Trust `state.pick_row.claimed_by` (pass 1 already read it).** Rejected for the same reason —
   it comes from the file under test. The holder must be read live in pass 2.
4. **Let the manager assign any admitted row and record the reason.** Rejected: that is a re-rank
   with extra words. The chosen shape keeps ordering entirely in `prime_directive_queue()`'s own
   output and only checks a *prefix* property — every row before the assignment is blocked — which
   is pattern:147 ("skipping a blocked item never reorders the queue") expressed as a check.
5. **Widen to the manager's Skill rows in this ticket.** Rejected on caps. Until `dm-run-intent` /
   `dm-guardrails` teach the manager to emit `passed_over`, behaviour is byte-identical to today
   (no `passed_over` ⇒ the present refusal), so the driver half is safe to ship alone and the Skill
   half is its own ticket (pattern:120, pattern:65). Verified the driver half needs no schema
   change: `validateAgentVerdict(dm-run-intent.traits.schema, <answer carrying passed_over>)`
   returned `{ok:true, errors:[]}` — `additionalProperties` is undefined on the stored schema, which
   is also how SES-403's `regrades` ships.

## Why the QA is discriminating

Both discriminators were run against the *unchanged* tree this session and returned the refusal
strings quoted above, so each is red before the change by measurement rather than by argument. Each
is driven through the driver's own exported `stateDrift` / `answerErrors` — not a reimplementation —
and each ships with controls in the opposite direction (a peer's claim, a stale claim, an absent
reading, an unblocked skip) so a change that simply deleted the refusals would fail the controls.
A check grades the change, never the live world (pattern:162): every case uses fixture values, and
the one live assertion is the pass-1 exit-3 smoke test.
