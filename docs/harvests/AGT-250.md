## 2. The one thing the ticket got slightly wrong, in the platform's favour

The ticket says "today nothing reads them into structure." The *derivation* is absent, but the *read*
is already built: `api/_lib/handlers/agent-bundle.js` (`AGT-162`, v7.0.682) returns
`{ agent, role_prompts, guardrails, output_formats, sections, knowledge_entries, library,
no_inference: true }` for one agent with no model call, reached by handler NAME through
`api/_lib/mcp.js`'s `DETERMINISTIC_HANDLERS` (never by capability slug — `.claude/rules/capabilities-are-data.md`).
Its own header records why it reads the primitives rather than the assembled prompt: `buildSections()`
renders the `agents` row and `role_prompt` configs only inside an identity-type Skill's branch, so an
agent with no Skill rows assembles to no identity at all — exactly the agent this capability is for.
Standing up a second reader would be pattern 14/17 backwards. So the design consumes it.

## 4. Why this shape and not the others

- **Proposal, not write.** §19u decision 6 assigns writes to `skill_profiles`/`capabilities`/
  `capability_skill_profiles`/`agent_capability_assignments`/`agents` to one brokered module
  (`HAR-39`, `open`/`later`); decision 5 says every hire is signed. A capability that wrote roster
  rows would ship the broker by the back door. The cheapest variant that proves the ticket's claim —
  *Susan can read the documents and decide what to build* — is one structured proposal on the
  `deliverables` table behind the existing confirmation gate. What it does **not** do: create the
  agent. That is `HAR-39` + `AGT-56`.
- **`store`, not a new handler.** Adding a handler means editing the `HANDLERS` map — harness code,
  for a capability whose whole point is being data (§19b, pattern 8). `store` already writes
  `deliverables` and already accepts `task_id: null`.
- **One pass, no interrogation** is John's own words (2026-09-26). The honest cost is that a silent
  document yields a guess, so the schema forces `assumed: true` on any element the documents did not
  support — the proposal tells John which parts it invented instead of hiding them (pattern 34).
- **`source_document_id` on every element** is what makes the QA discriminating rather than
  decorative: without it, a model that read nothing and wrote a plausible scaffold from the role title
  would pass. With it, that run goes red.
- **No `SERVICE_CATALOG` row** — `.claude/rules/platform-services-directory.md` / §19m: a capability is
  never a service row; it displays under its agent via the assignment. This is what keeps the build
  inside 3 files.
- **Model.** `runner_model_lanes` read live: orchestrator `claude-opus-5`, judgment `claude-fable-5-1`,
  mechanical `claude-sonnet-5`. Susan's own row is pinned to `claude-opus-5` (present in
  `shared/models.js` `MODEL_PRICING` at $0.005/$0.025 per 1k): one call authors an entire agent, so the
  expensive model is the cheaper choice (pattern 125). Her existing `pattern-vocabulary-review-intent`
  runs `claude-haiku-4-5-20251001` at `max_tokens: 1500` — the right size for judging one candidate,
  the wrong size for authoring a scaffold.

## 5. Rejected alternatives

1. **Write the taxonomy rows directly, gated by `requires_human_confirmation`.** Rejected: the gate
   governs *whether* the write runs, not *who owns* it; §19u decision 6 wants one broker so every
   roster write has one auditable home.
2. **Interview first, then author** (a `can_request_help` round trip to gather what the documents
   lack). Rejected: John's 2026-09-26 words are one pass, no up-front interrogation. `assumed: true`
   carries the same information without the round trip.
3. **A new deterministic reader inside `scripts/`.** Rejected: duplicates `agent-bundle.js`.
4. **Storing the derived structure in `agent_training_sessions`.** Rejected: it is an hours/cost
   ledger (§1b). Its emptiness is a separate observation, not this ticket's fix.
5. **Extending `pattern-vocabulary-review`.** Rejected: one capability, one job; its schema binds the
   17-field pattern signature and has nothing to do with authorship.
