## Decisions I made (reversible; recorded here and named in the STOP LINE)

- **D1 privacy.** Memory stays in two places: your machine and the private mirror. The build copies it nowhere new -- no table, no third store, no cost.
- **D2 limit 48 hours.** The sync is daily (13:00Z), so one missed sync is tolerated and two are a finding. It is a flag in the runbook (`--root-max-age=claude-config=48`), not a constant in code, and it is per root: `interviewquestions` is a repository, not a daily mirror, so it gets an age line and no limit. A root whose age cannot be read is treated as stale (pattern:165: a sensor that cannot read fails closed).
- **D3 three reserved clusters, beside the 12.** Three more judgment calls a week on subscription tokens. Beside, not inside: taking slots from the 12 would cost the prior-finding controls that run first. Pattern:67 -- the bound it answers to is the existing `max-clusters`.
- **D4 cadence stays weekly.** Memory changes when your sessions run, not when a build ships, so a per-run read would re-read an unchanged corpus after every cycle.
- **D5 one slug.** `config-memory-vs-memory` covers both a duplicate and a contradiction; the finding's `kind` says which.

## Why this shape, and what I rejected

- **Reserve, not re-rank.** Changing the spread ranking would change which 12 clusters the whole Auditor runs each week -- a process that just stabilized (pattern:121). `reservedClusters()` is three lines that reuse `buildClusters()` over the statements under one location prefix (pattern:14, pattern:17). The prefix is a flag; no slug and no repository name is hard-coded in the script (pattern:2).
- **The check in the Auditor's own rows, not in the harness** (pattern:7, pattern:8). The script only decides which statements sit in one cluster; what to look for is Skill text.
- **Limit of the reserve, said plainly.** Two memory files are compared only when they share an anchor (a `snake_case` name, a ticket id, or a backticked identifier). Two files that contradict each other in plain prose with no shared anchor are still not compared.
- **`config-mirror-stale` is not added to the checklist row.** It is a code check, and code checks such as `config-headroom` and `suite-red` already file without a checklist line. Adding it would also have meant editing the checklist's `[code]` sentence.
- **A live model call as QA -- dropped.** I had a QA step that ran one real judgment call on two opposite memory files. It did not fit the 8,192-byte kickoff with every task fact kept, and a model's answer is not a stable assertion. The deterministic proof is: the cluster is built and routed (test arm B), and the assembled prompt names the check twice (QA 3, 0 today). What the model then files is first seen in Monday's report, and the STOP LINE says so. Anyone who wants the live check: write two opposite lines naming one backticked identifier to `$Q/cc/memory/a.md` and `b.md`, run `audit-corpus.js --no-db --extra-root=claude-config=$Q/cc --out=$Q/s.json`, then `audit-cluster.js --build --no-db --statements=$Q/s.json --week=<W> --out-dir=$Q/c --max-clusters=1 --reserve=claude-config:memory/=1`, delete `$Q/c/01-*`, and `audit-cluster.js --run --dir=$Q/c --session-name=<name>` (I dry-ran this sequence on a copy carrying the stubs: it builds `02-weekly_wall.task.json` for `audit-config-review`).
- **Quoting the age in the weekly summary row -- dropped for bytes.** The age line prints in step 1 for every root and a stale mirror is a finding in the report. A fresh mirror's age is not repeated in the summary row. Small; worth a line in a later runbook edit.
- **No live-row pins in the new test** (pattern:162). The Development Manager's learning loop edits these rows on purpose; AGT-625 was the cost of pinning one.

## Part (3), the part this build does not reach

A correction to a memory file has to land on your machine: the folder is there, and so is the sync job (`C:/Projects/claude-config/sync.mjs`). No cloud run can write either, and a builder cycle holds only this repository. Two things are needed and both are yours: a push grant on `roadmapventure/claude-config` for a cloud routine, and a change to the sync job. That touches your account, which the ticket itself reserves to you.

The mechanism I would build once you say yes (my call, reversible, for whoever picks it up): the cloud side never edits memory in place. It pushes each correction as a commit on a `corrections` branch of the mirror -- target file, the old line, the new line, the finding id. Your machine's sync applies a correction only where the old line still matches, then syncs back; a mismatch is left unapplied and reported. Every correction is a git commit, so undoing one is a revert on your side, and nothing is ever deleted by a cloud agent. If the answer is no, corrections stay a list an attended session on your machine works through, and the ticket should say that plainly.

The ask, as the kickoff words it: "May a cloud routine push correction commits to a `corrections` branch of roadmapventure/claude-config, applied by your machine's sync only where the old line still matches? Yes or no."
