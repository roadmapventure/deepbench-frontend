### Why this slice, and not another

The ticket's BUILD has six parts against caps of 3 files / 4 tasks. The claim the ticket makes — *the platform builds itself with its own staff, at the top of the loop* — becomes literally true the moment a cycle's step 5 asks GV-01 and executes the assignment. That is part 3. The other five are either (i) improvements to how well the manager reasons (parts 1-2: Knowledge and Guardrails rows) or (ii) visibility and supervision of an already-working call (parts 4-6). None of them makes the claim true on its own, and parts 1, 2 and 6 all edit an **active agent's rows**, which the roster rule gates on John's word; part 3 edits no agent row at all, so slice 1 ships without that gate. That ordering also gives the staff watch something to watch.

Rejected alternatives:

- **Knowledge + Guardrails first (parts 1-2).** Two Skill-row edits with before-images, John's word required, and at the end of it the manager is still never asked. The claim stays untrue for a whole cycle.
- **Everything, thinly.** Six parts over four tasks is four thin tasks; the mismatch rule, the logging and the live proof are exactly the parts that would be dropped, and they are the parts the QA discriminates on.
- **Let the driver claim the ticket (drop `--dry-run`).** See below — it breaks the push gate.

### The claim hazard, in full

`scripts/run-project.js` pass two claims with `claimed_by = 'run-project:${project}:${step}'` (one atomic PATCH carrying rule B40's 24h expiry filter). The runbook's own claim (B40, L2708) writes `claimed_by = '<your cycle id>'`, and register **B42** (L344) re-asserts `claimed_by = '<your cycle id>' AND claimed_at > now() - INTERVAL '24 hours'` immediately before every irreversible act, reading 0 rows as **do not push** and **do not claim a counter**. A driver-made claim therefore leaves the cycle unable to push its own ship, and its own B40 claim would read 0 rows and be interpreted as *a live peer holds this ticket* — the cycle would drop to the next ticket. `--dry-run` skips only the claim PATCH (`if (args.dryRun) console.error("--dry-run, so the claim on X was NOT made")`); schema validation, the live `runner_should_boot()` re-read, `stateDrift`, `answerErrors`, the wall re-read and the next capability's prompt all still run, and the exit code still distinguishes assign (0) / stop (1) / refused (2). Rewiring the claimer string so the manager's claim *is* the cycle's claim is cycle 2 and touches `scripts/run-project.js`.

### Card mechanics the build depends on (why the renderer is not a fourth file)

`scripts/render-cycle-card.js` parses step markers as `^\*\*(\d+[a-z]?(?:-bis)?)\. ` and requires a hand-written `NOTES` entry per step — so **adding a new step marker would force a renderer edit** (and the throw is deliberate). Putting the manager block *inside* step 5 avoids that: `NOTES["5"].block = 1` already selects the step's first fenced block, and `stepTitle()` cuts the card's title at the first `.`, so appending prose after `**5. Pick ONE item.**` leaves the card title unchanged. The new block becomes block 1 and is carried byte-identical if it is ≤ `FULL_BLOCK_MAX` (400 B); the drafted block is ~334 B. Card headroom: 7,950 → ~8,310 against `CARD_BYTE_CAP` 10,240. `tests/regression/ses-377-cycle-card.test.mjs` asserts the committed card equals a fresh render and that every carried block is the runbook's bytes, so Task 2 is enforced rather than trusted.

Two other pins the build must not trip: `ses-333-step5-handoff.test.mjs` part (d) caps `runner-cycle.md` at **5** `<!-- DeepBench v… -->` header stamps and the file already has 5 (use an inline `<!-- FEATURE: SES-378 … -->` marker instead); the same test pins step 5's layer (3) text and the `(3-legacy)` retired-in-place block, both of which the insert leaves untouched.

## Build (one ship; the Skill edits on the session lane under one decision with before-images — John's word is required to edit an active agent's rows, roster rule)

5. **Tests.** ses-297's oracle still grades the pick; a new test asserts the assignment equals the queue's first row on the live board and that the Guardrails row carries the chain rule byte-for-byte.

After each cycle the manager reads the four handoff rows, the verdict and the Builder's deviations and records per-agent findings as rows — kinds: over-cap refusal; kickoff lacked a fact the build needed; verdict block attributable to the kickoff; assignment mismatch. The standing brief (SES-360 block) shows them per role for the last 7 days. A finding repeated across 3 cycles becomes a proposed Skill edit written to a card for John with the exact drop-in text. ## Promotion bar — drafted for John's ratification, not built here
