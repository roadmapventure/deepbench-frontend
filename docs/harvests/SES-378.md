## Why these two files and not others

- `scripts/render-cycle-card.js` already owns the card and exports `runbookSha()`. A one-time paste
  of 8,536 bytes into a row would rot silently the next time `runner-cycle.md` changes; a
  `--sync-knowledge` flag on the script that already re-renders the card makes drift a **detectable,
  exit-1 state** instead. That is the cheapest variant that proves the claim.
- A second file (`tests/regression/ses-378d-manager-skill-rows.test.mjs`) carries the assertions.
  2 of 3 files spent; the third is deliberately unspent.

**What this slice does not do:** it does not wire runbook step 5 to assemble `run-project`, does not
write the handoff rows, does not widen `target_kind`, and does not add the brief block. The manager
gains the two rows it must hold before any of that is worth wiring.

## Alternatives considered

- **Paste the card into the row by hand, no script change.** One file instead of two, but the
  byte-pin then has no owner and no drift check — exactly the failure `SES-377` built the card
  renderer to prevent.
- **Put the chain rule in `notes` rather than `guardrails.must`.** `db-assembly.js`'s guardrails
  branch renders `guardrails` only; `notes` is swept by the name check but never reaches the
  assembled prompt, so the rule would be recorded and not obeyed.
- **Shrink `routine-prompt.md` step 9 to a pointer in the same ship.** The ticket pairs the two, but
  thinning the prompt an unattended cycle is running under is John's own call and belongs to a
  session he attends. Carried as a card in the STOP LINE, not scoped.
- **Scope a `.claude/` write.** Out of bounds for an unattended cycle; nothing here needs one.
