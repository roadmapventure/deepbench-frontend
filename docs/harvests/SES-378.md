### The design calls, and which are derived and which are judgments

- **The four `kind` values are the ticket's, verbatim**, held as a CHECK constraint so an unknown
  kind is refused rather than silently stored. Derived, not invented.
- **The repeat unit is `count(distinct cycle_id) >= 3`, never `count(*) >= 3`.** A judgment, and the
  one the test's `SES-158` control exists to protect: three rows in one cycle is one bad cycle, not a
  pattern, and the ticket says "repeated across 3 cycles".
- **The fingerprint normalises uuids away** (`<uuid>`), lowercases and collapses whitespace. A
  judgment. Without the uuid rule the same defect carrying this cycle's id never matches itself next
  cycle, and the three-repeat rule silently never fires — the failure mode is invisible, which is why
  the test asserts it directly. The separator is `|`, safe because `agent_id` and `kind` are
  constrained vocabularies that cannot contain it.
- **`unique (cycle_id, fingerprint)`** makes a re-record inside one cycle a no-op, so a chained
  continuation that re-runs the watch cannot inflate a count into a false promotion.
- **`agent_id`, not a new `role` column.** `ai_activity_log.agent_id` already holds `devmanager`
  (row 46453). A second vocabulary for the same fact is the `SES-45` defect. Rule #1 is not engaged:
  `scripts/check-agent-names-in-data.js` sweeps `skill_profiles`, `agent_configs`, `capabilities`,
  `the_library` and `knowledge_entries` — an agent's own prompt-reaching rows — and derives its
  allowlist from ownership data. An evidence table about a call is none of those.
- **NOT on `reverse_decision()`'s allowlist.** Deliberate, and consistent: `audit_findings` and
  `ticket_owner_findings` are absent from `k_allowed` too. Evidence is appended, not un-decided.
- **`runner_card_asks` is the card surface**, columns `target_kind`, `target_id`, `question`,
  `status` — read live this cycle. `--promote --apply` writes one row per fingerprint and never
  touches `skill_profiles`, which is the ticket's own line: "the manager never edits a live agent's
  rows."

### The grants clause, and why it is a task rather than a footnote

`SES-384` (2026-09-12): *every new public table is born readable by `anon` — the default ACL grants a
SELECT no migration asked for.* This table will carry per-agent performance findings. The migration
therefore carries `revoke all … from anon, authenticated`, and the kickoff's QA asserts **both
directions** in one pair — zero `anon`/`authenticated` rows in `information_schema.role_table_grants`
*and* a service-role `select` that still returns the rows Task 4 wrote — because
`.claude/rules/supabase-column-grants.md` records a migration that reported success and left the data
fully exposed. Note also, from that rule's addendum: `role_table_grants` does not report PG17
`MAINTAIN`, so this assertion is about DML reachability through PostgREST, not the complete ACL.
