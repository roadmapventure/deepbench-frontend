## Use case

Today the orchestrator is an Opus 5 session following the runbook in prose; it decides the pick, delegates to the Designer and the Builder, and decides whether to chain. The Development Manager (GV-01, AGT-68, capability `run-project`) exists, returns an assignment from the same instruments, and has never been asked by a cycle. Moat AGT-77 claims "the platform builds itself with its own staff"; this ticket makes that literally true at the top of the loop, which is the demo no competitor on the 2026-09-11 matrix can reproduce.

**Why it depends on SES-377.** An agent's Knowledge is a Skill row. The 365 KB runbook cannot be one; the cycle card can.

## Build (one ship; the Skill edits on the session lane under one decision with before-images — John's word is required to edit an active agent's rows, roster rule)

1. **Knowledge.** The cycle card (`docs/runbooks/cycle-card.md`) rendered into a `dm-knowledge` row by a marker, the same way `{{rule:ID}}` blocks render, byte-pinned by a test.
2. **Guardrails.** The chain rule moves here from `routine-prompt.md` step 9 verbatim — close the row, then the gate; a continue is executed in the same turn with no report between; the only stop after it is `runner_should_boot()` false — and step 9 of the prompt shrinks to a pointer.
3. **Runbook step 5.** The cycle assembles `run-project` via `scripts/agent-prompt.js --agent=devmanager --capability=run-project` with the instruments as task_context, runs it on the orchestrator lane, and executes the returned assignment (ticket, capability, engine) — never re-deriving the pick. An assignment that names a ticket other than `prime_directive_queue()`'s first admitted row is a finding on the Skill text, recorded, and the queue's row is built (the SES-45 boundary).
4. **Handoff rows.** The four handoff rows and the agent-log row (`scripts/agent-log.js`, call_source session) are written for every manager call so the Bench Governance section (AGT-69) shows it working.
5. **Tests.** ses-297's oracle still grades the pick; a new test asserts the assignment equals the queue's first row on the live board and that the Guardrails row carries the chain rule byte-for-byte.
6. **The staff watch** (amended 2026-09-12). After each cycle the manager reads the four handoff rows, the verdict and the Builder's deviations and records per-agent findings as rows — kinds: over-cap refusal; kickoff lacked a fact the build needed; verdict block attributable to the kickoff; assignment mismatch. The standing brief (SES-360 block) shows them per role for the last 7 days. A finding repeated across 3 cycles becomes a proposed Skill edit written to a card for John with the exact drop-in text. The manager never edits a live agent's rows itself (roster rule).

## Promotion bar — drafted for John's ratification, not built here

The manager becomes the whole orchestrator (the M8 shape, SES-235) only after 20 consecutive cycles where its assignment matched the queue's first row or was recorded as a better pick John accepted, and every continue it returned ran to a close — the same trust-ladder shape every other governance agent climbs.

## QA that discriminates

- On the first cycle after the ship, the manager's assignment and the queue's first row are the same ticket, and the cycle row names the manager's `ai_activity_log` id. Before the ship, no cycle row names the manager.
- A fixture state with a different queue head makes the assignment change with it.
- After three cycles the brief shows a per-role finding count; a fixture Builder deviation "the kickoff did not name the file" produces one Designer finding row.
