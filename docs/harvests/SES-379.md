## Alternatives considered and why they lost

1. **`--base=<pre-build sha>` captured by the orchestrator before it spawns the Builder.** The
   ticket names this first. Rejected as the primary: if the Builder rebases onto a newer
   `origin/dev` (the normal push path), the pre-build sha stops being an ancestor of HEAD and the
   three-dot diff falls back to an older merge-base, so the list silently grows to include *other*
   cycles' commits. That is over-broad refusal — quieter than the current bug but still a wrong
   answer, and it needs a new value carried across three runbook steps.
2. **A new `runner_cycles.base_sha` column.** Same defect as (1) plus a migration, a down
   classification and a schema change the ticket did not ask for.
3. **Derive the range from `runner_cycles.push_sha`.** `push_sha` is the tip, not the base; a
   multi-commit push has no fixed `HEAD~n`.
4. **Flip empty → block and stop there.** This is the trap. Post-push the git list is empty on
   *every* cycle, so with nothing supplied the bar becomes permanently unreachable — the ticket
   explicitly forbids a refusal switch, and the QA's control arm is what catches it.
5. **Chosen: pass the list in.** The Builder's `build-ticket` output schema already *requires*
   `files` (`docs/design/ga-agents-seed.sql:133`), so nothing new is collected, and the direction
   matches step 4a's CI conclusion and `heal-engine.js` / `tripwire-to-backlog.js`: the engine holds
   no fact it cannot bound, so the fact is handed in. Git stays the fallback for attended runs.

## The boundary that constrains the implementation

`tests/regression/SES-181-verifier.js:354-359` asserts, with a comment, that `[]` is a *real answer*
and must never be coerced to `null` — "coercing the two together would block every clean delivery
forever — the SES-147 NULL-is-not-zero boundary in a second costume." That assertion is right and
stays. What changed since it was written is the *observation*, not the boundary: after `SES-336`
gave the Builder the push, an empty observation at step 7a no longer means "nothing relevant
changed", it means "I looked after the evidence was gone." So the conversion belongs at the
resolution seam in `main()` — `resolveDeliveryFiles()` — and `selfCertificationBlock()` keeps its
two-answer contract untouched. The new test's job is to pin that split so a later reader does not
"simplify" it back into one place.

## Union, not replacement

`resolveDeliveryFiles()` unions the explicit list with whatever git can still see rather than
replacing it. Rationale: every extra path can only *add* a self-certifying hit, never remove one, so
the union is monotone in the fail-closed direction. It also covers the real step-7a tree, where
`CLAUDE-STATE.md` from the orchestrator's own render is often the only thing `git status` reports.

## Cost of the runbook edit

`docs/runbooks/cycle-card.md` is a generated view carrying a `sha256` of `runner-cycle.md`, held
byte-identical by `tests/regression/ses-377-cycle-card.test.mjs`. Any runbook edit that skips
`node scripts/render-cycle-card.js --write` turns the regression gate red — which would, ironically,
block this ship for the wrong reason. Hence task 4 as an explicit task rather than a footnote. The
new regression test needs no registration: `run-all.js` discovers by `readdirSync` filter
(`:123-124`), and `run-all.js` is itself one of the three self-certifying paths, so it must not be
touched.

## Why this ship is its own witness

The fix edits `scripts/verifier.js`. Once it works, this delivery must be refused the auto-done bar
by the code it ships — the same self-witnessing shape as `SES-181` and `SES-122` (b). That is why
the STOP LINE requires the verifier's own printed line about this push, and why the ticket closes
`delivered`: a `done` here would be the bug reproducing itself one last time.
