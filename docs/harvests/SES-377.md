## 3. Why generator + guard, and not a hand-written card

The orchestrator's steer matches the codebase's recorded defect (SES-45, SES-175, check 13): one fact, two homes, drifting. A hand-maintained card would be the runbook's second home for 25 commands. So:

- **Every byte of command text on the card is copied from the runbook at render time.** The only hand-maintained content is `NOTES` — 25 one-line outcomes and two block-index overrides — and `NOTES` cannot invent a command, only choose which runbook block to show.
- **The guard is equality, not presence:** `render(runbook) === card` byte-for-byte (test A). That single assertion subsumes "every step has a line", "every block is identical" and "the card is current" — but tests B, C and F restate them independently so a bug in `render` itself cannot make A vacuous (the SES-158 lesson: a control that changes nothing proves nothing). The runbook's sha256 in the card header makes staleness a one-line diff.
- **The cost is honest:** any edit to runner-cycle.md that moves a line above a step turns the suite red until `node scripts/render-cycle-card.js --write` is run. The failure message names that command. This is the same contract `render-rule-blocks.js` already imposes for `{{rule:…}}` blocks.

## 4. The two checks that would have bitten, and how the kickoff routes around them

- **check 13 (duplicate procedure homes)** hashes every fenced block ≥ 60 normalised chars across root `*.md`, `docs/*.md`, `docs/runbooks/*.md` and FLAGs identical bodies in two docs. The card would produce ~15 FLAG lines per session. It is **not** in `GATING_CHECKS` (9/10/11), so CI would stay green, but a hygiene check that cries wolf on every run is one nobody reads. Task 6 adds `PROCEDURE_GENERATED_DOCS` — an explicit, exported, one-entry set — rather than a marker-comment exemption anyone could paste onto a real duplicate. `SES-200-rule-copy-and-procedure-homes.js` drives `duplicateProcedureHomes` with explicit fixture maps, so the exemption inside `buildProcedureDocs` cannot disturb it.
- **check 9 (retired rule in live voice) IS gating.** It flags a retired rule's ID appearing in a doc without retirement vocabulary in the enclosing block. Step headings carry IDs (`register B12 — superseded 2026-09-01` on 4b). If a title were copied whole and cut before "superseded", the card would fail CI. Hence the title rule: cut at the first ` — `, `(`, `.` or `:` — no ID survives in any of the 25 headings measured. Copied SQL comments could still carry an ID; task 7 names the remedy (that step's `block: 0`, a pointer) so the Builder never edits copied text to appease a check.

## 5. Alternatives considered

1. **Add anchor comments or a top-of-file pointer to runner-cycle.md.** Rejected: any body edit to that file forces a stamp rotation (session-hygiene check 7, SES-164 step 2 by grep), ses-336's 381,000-byte ceiling is 17 KB away, and the ticket names shortening the runbook as out of scope — touching it at all for this ticket is scope the card does not need. Line-number anchors plus the step's own marker text are enough to `grep -n` to.
2. **Carry every fenced block.** 14,880 B before prose; over the ceiling. Rejected by arithmetic (§2).
3. **A card with no code, pointers only.** Meets the size trivially but fails the ticket's "exact command per step" — the cycle would open the runbook 25 times, which is the read the ticket exists to end.
4. **Run the generator in CI to write the card (option A of SES-175's history).** Rejected for the same reason John chose expand-in-place then: the committed file must be the one a cycle reads at `git checkout`, with no build step between.
5. **A separate manifest JSON file.** One more file for 27 short entries; embedding `NOTES` in the script keeps the outcome text next to the code that renders it and one fewer file inside the cap.
