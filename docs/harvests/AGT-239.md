## Why these shapes

- **One column, not a naming convention (D1).** Ranking (d) and the weekly move (c) both need to know what kind of problem a finding is. A `check_slug` prefix is a convention nothing enforces. A column with a CHECK, filled at INSERT from a data table (`finding_families`, pattern:2), gives one home that every writer shares: the tick's direct INSERT, `ingestFindings`, staff-watch and ticket-owner. It is immutable after insert, the same as the rest of the append-only row. The guard gets the column only after the backfill, because otherwise the backfill UPDATE would be refused.
- **Flow checks in SQL, filed from (7e)'s prepare (D2).** They are four deterministic reads (pattern:9), so there is no model. (7e) already runs `audit-run-review.js --prepare` after exactly the runs that built or stopped something (`REVIEWABLE` = shipped, gated_before_build, reverted, failed), which is the ticket's trigger set word for word. Filing there needs no `runner-cycle.md` edit, and that file sits 95 B under its 381,000 B ceiling. The filing goes through `ingestFindings`, the one intake with a before-image per append (§19v, pattern:14). The weekly de-dup comes from the fingerprint (`kind | location keys | governing_fact`). With a fixed governing_fact and a stable location, each project or gate files once per ISO week, then shows up as `recurring` the next week. The live numbers ride in `locations[].text`.
- **Thresholds (D5, pattern:67).** ship_open_days 1 and gate_red_days 1 are the ticket's own "> 1 day". window_hours 24 is the ticket's "overnight". wasted_pct 25 with at least 8 cycles fires today at 27.7%. That is on purpose: 18 of 65 cycles produced nothing, and the manager decides whether it matters. filing_min 10 and ratio 2 keep a quiet project from firing on 2 filed and 0 closed. They catch 71:1. All of these are data in `runner_settings`.
- **Moved, not removed (D3).** Paperwork findings keep being filed wherever they are found today. What moves is the review and the ticketing. The per-run (7f) manager review, which runs after every reviewable cycle, now covers every family except `paperwork`. The weekly Auditor step 4 passes `--weekly` and covers all of them, so nothing is lost and the weekly corpus pass stays the paperwork home. `--prepare` defaults to `outcomes` so that (7f)'s command in `runner-cycle.md` does not change. The weekly command lives in `auditor-routine.md`, which has no ceiling, and the routine prompt block is untouched, so there is no routine drift. `apply_audit_review` reads the scope from `p_review` and treats a missing scope as weekly, the old behavior.
- **(7e)'s model tags family (the answer schema).** The reviewer must say `outcome` for a finding to reach the per-run manager. An untagged finding, or anything that is not `outcome`, falls to the settings default for `auditor:run-review:%`, which is paperwork. That is the structural guard (pattern:10). The method line does not have to be obeyed perfectly.
- **Rank (D4).** Service 0 (`runner:db-health`), blocked-from-closing 1 (`flow-ship-not-closed`, `flow-verdict-gate-red`), everything else 2. The sort is stable within a rank. It is a deterministic ordering of the manager's worklist, not a model instruction.
- **(a) additions (D6).** `db-restarted` makes the restart itself a finding with numbers. `db-pressure-red-repeat` separates "red again today" from a first red. Both reuse the tick's existing fingerprint and ON CONFLICT path.
