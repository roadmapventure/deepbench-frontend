## Why a function, not a trigger

An AFTER INSERT trigger on runner_items would also fire inside `design_only_stop()`, which inserts the card
BEFORE imaging the ticket and writing `designed`; the trigger's `needs-desktop` write would then be captured as
the "prior" state by design_only_stop's own image, so a reverse_decision() would restore `needs-desktop` instead
of NULL. A function with its own refusal for design-only tickets keeps the two lanes separate. It also keeps the
pattern the runbook already teaches (record_skip(): "this one call is the whole of your obligation").

## What this does NOT do

- It does not catch a cycle that classifies a ticket gated and calls nothing. No SQL can see a classification that
  was never written. The runbook sentence (T2) is the only guard for that case; a second instance is the trigger
  for a structural step (pattern:10) — e.g. step 9's close refusing a `gated_before_build` outcome with zero cards.
- It does not mint a runner_decisions handle (design_only_stop does, via apply_gate_rulings, because it needs an
  open question). The three images carry cycle_id, which is the reversal path the hand-typed act already had.
- It does not renumber the queue (pattern:147, D3).
