## 2. The second half: nothing re-settles it when the card is ruled

`pg_get_functiondef('public.apply_gate_rulings')`, §3b, read live (8,691 bytes; the ticket side of
every ruling):

- `rework` → `scope_rationale` appended, `design_status = NULL`, `updated_at = now()`.
- `retired` → `status = 'removal proposed'`.
- `needs-desktop` → `design_status = 'needs-desktop'`.
- `accept` → the ticket is not touched at all.

So of the four rulings that reach a ticket, **only `retired` writes `status`**. A card filed after
the close-out and later ruled `rework` leaves the status exactly where the too-early census put it,
forever, and `recompute_backlog_queue()` at the end of the function does not look at it either.

`scripts/ticket-owner.js` check 12 `remainder-stranded` already *detects* this: it re-derives with
the same exported `decideStatus()` over the row's own `kickoff_link` text plus a fresh card census
(`:483-510`). It is deliberately `judgment` with no `fix` — "the census writes neither `status` nor
`design_status`, ever" (`:497`). So the platform can already see the contradiction and has no hand
that writes.

## 3. Why the fix is one direction only

The obvious symmetric design — re-derive and write whichever way the census now points — is wrong
here, and the reason is worth recording because it is not obvious.

A re-settle that may write `partial → delivered` has to decide that nothing remains. The three
non-card triggers of `decideStatus()` (slice *N of M*, a STOP LINE closing this ticket `partial`, a
declared `--remainder`) are read from the kickoff, which is available via `kickoff_link` — but the
card trigger itself becomes ambiguous the moment the card is stamped. A card ruled `rework` is the
Dev Manager saying *more work*, which is unbuilt work by definition; a card ruled `accept` is not.
Treating "decided" as "clear" would flip a reworked ticket to `delivered` at the exact moment it was
told to do more. Treating a `rework` stamp as permanently `partial` would mean the ticket can never
be `delivered` again, because the stamp never expires.

Resolving that needs a machine-readable "done when this reads zero" predicate per ticket — which is
precisely what this ticket's own gate ruling (card `e221020c`, 2026-09-27 13:00Z) parked as its own
row under `pattern:65`. So the build takes the half that needs no predicate:

- **`delivered → partial` only.** The harmful direction is a finished-looking row that nothing will
  re-pick; the safe direction is already the safe side.
- `rework` and `needs-desktop` (which `k_stamp` maps to the same `rework` stamp) are the two rulings
  that mean unbuilt work, and they are the only ones that trigger a re-settle.
- `accept` writes nothing; `retired` already moved the row to `removal proposed`, which `UNSETTLEABLE`
  refuses.

Live consequence worth stating plainly: run against `AGT-167` today this mechanism writes nothing,
because the row already reads `partial`. That is correct — the ship is the guard, not a backfill.

## 4. Alternatives considered and rejected

1. **A Postgres trigger on `runner_items`.** Fires at exactly the right instant for both moments and
   needs no caller to remember. Rejected: the status decision rests on the *kickoff document's text*,
   which Postgres cannot read, so a trigger could only ever implement the card third of
   `decideStatus()` and would have to guess the rest — two homes for one rule, and the weaker one
   wins by running first (`pattern:8`, `pattern:14`).
2. **Make check 12 `derivable` and let the nightly census write the status.** Cheapest possible
   patch. Rejected: it reverses an invariant stated in the file and defended in its header, and it
   moves a reversible ticket write into a sweep that batches 25 rows a night under one decision.
   That is a separate architectural call, not this ticket's.
3. **Re-run the close-out at the end of every cycle.** Would catch the filed-after-close-out case,
   but not the ruled-later case (the ruling often lands in a different cycle, hours later), and it
   doubles the `ticket-status` decision count on every clean ship.
4. **A new `runner_settings` knob / a `cards_final_at` column on `runner_cycles`.** Rejected under
   `pattern:67`: the bound already exists — the card row's own `created_at` and `decided_at`.
5. **Editing `docs/runbooks/runner-cycle.md` to add a "re-settle" step.** Rejected on two grounds:
   the file is 380,902 B against the `SES-336` ceiling of 381,000 so a step edit must first remove
   bytes, and more importantly no *human* step changes — the re-settle fires inside the
   `decide-gated-card.js --apply` the runbook already invokes (`pattern:9`: never a model call, and
   never an instruction, where a deterministic mechanism serves).
