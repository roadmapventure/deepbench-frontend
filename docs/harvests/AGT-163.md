The 32 `mcp` rows, individually: 28 written 2026-09-28 08:12-08:54Z with `request_host NULL`, `caller_ip NULL`, `ai_type deterministic|librarian` -- the AGT-162 test's live arm driving `runDeterministic()` in-process, so no headers exist to derive from; 3 written 2026-09-12 from `request_host deepbench-frontend-git-dev-…vercel.app` with `caller_ip` set and `device_type desktop` (SES-339's verifier over MCP); 1 from `deepbench.local` (MCP-3's first call). So `caller_ip` is already derived on every real remote MCP call (`lib/request-context.js` `deriveCallerIp`, x-forwarded-for) and the count of 3 is an artefact of 28 in-process rows. No IP code is needed; only identity is missing, on 32 of 32.

Why identity is missing: `derive()` fills `visitorId` from the `db_visitor` cookie (a browser only) or the `x-db-visitor-id` header (LOG-130, a self-declaring script). Claude's custom-connector UI lets a user set a URL and a bearer/custom header for the key, not an arbitrary second identity header per person; and even if it did, a self-declared header is exactly the spoofable slot LOG-121's own header comment describes. The key is the one signal every MCP caller presents and the one the server already verifies -- `api/_lib/mcp.js` lines 445-459 read `runner_secrets` by the constant `SECRET_NAME = 'MCP_API_KEY'`, compare with `keysMatch()` (constant-time), and reduce the answer to `governanceUnlocked: boolean`. The name of the matched row is discarded at that line. AGT-163's code half is to stop discarding it.

Ticket text check: part (1) "a URL he adds as a custom connector in Claude plus a key the server checks, so his tool calls are attributable to him" -- the URL and the key check exist (MCP-3, SES-346); attribution does not. Part (2) "his training work is attributed the way platform traffic already is, via visitor_id cookie and caller_ip, with a visitor_labels row for him" -- the mechanism exists and works (4,283 `ui` rows); the row is John's per `visitor_labels`' own comment, rule (3): "any NEW visitor_id first seen after [2026-08-10]: never auto-attribute, ask John per visitor." AGT-164 does not exist on the board (verified: `backlog_items` has no such row); nothing here designs around it.

## 2. The governing sections and the variant chosen

- §19b: the branch stays a data read (`execution_type`) and the new resolver is keyed on rows, never on a slug or an agent id. No slug conditional is introduced; arm (c) pins that.
- §19k / LOG-121's writer comment: `visitor_id` is a plumbing column, never a signature key. Writing a key name into it changes no signature and no Layer A fact.
- §19t: the gate's IP and the log's `caller_ip` must stay the same derivation; this ticket does not touch `deriveCallerIp`.
- `.claude/rules/supabase-column-grants.md`: `caller_ip` was LOG-124's public exposure. Live grants today (`role_column_grants`): `anon`/`authenticated` SELECT on `ai_activity_log` is a column list that EXCLUDES `caller_ip` and includes `caller_ip_masked`, `visitor_id`; the only table-level grant is INSERT (DAT-18's append-only posture). `runner_secrets` carries no public grant at all. `known_callers`: anon SELECT (the audit reads it from the browser). Nothing in this design changes a grant; arm (e) asserts the rule in both directions so a future loosening turns this test red.

Variants weighed:
1. **Matched key NAME -> `visitor_id` (chosen).** Zero new columns, zero grants, zero UI: `useAIActivity.js:756` already maps a `known_callers` row with `match_type 'visitor_id'` to a display name, so the tester appears by name the day John adds one row. `visitor_id` is `text`, no length constraint; a name like `MCP_KEY_ALEX` fits the LOG-130 posture of "the fallback identity slot a non-browser caller has no other way to fill". Data-driven: any number of keys, each a row, none in code (pattern:2, pattern:17).
2. A second constant beside `SECRET_NAME` (`TESTER_KEY_NAME = 'MCP_TESTER_KEY'`). Rejected: one tester today, two next month, and each is a code deploy (pattern:11).
3. A `visitor_labels` / `known_callers` row written by the build for the key name. Rejected: the row needs the tester's display name, which is John's to give, and rule (3) on `visitor_labels` says ask John per visitor. The build writes the card instead.
4. Ask the tester's connector to send `x-db-visitor-id`. Rejected: not settable per person in the Claude connector UI, and self-declared.
5. A new column (`caller_key_name`). Rejected: a second identity column the audit would have to learn; the ticket's own words are "attributable … via visitor_id".

Precedence call (ii): when both a matched key and an `x-db-visitor-id` header are present, the key wins. The key is verified by the server; the header is self-declared. Recorded as reversible; the swap is one `||` order.

Attribution for `MCP_API_KEY` itself: a governance-key call now logs `visitor_id 'MCP_API_KEY'` too. That is John's or a governance agent's own MCP call, and measuring it is pattern:41 -- never exclude real work from a count. A `known_callers` row on that name is John's option, not this ticket's.

Failure posture: `readMcpKeys()` fails closed exactly as `readGovernanceSecret()` did -- unreadable secrets mean product lane only and `visitor_id` falls back to the header/null. Attribution stays observability and never blocks a call (request-context's own header rule).
