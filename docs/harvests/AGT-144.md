## §B — the three Skills: methods and schemas

**`dm-release-watch-intent`** (Intent). Objective: *Record every Claude model Anthropic ships or retires, from Anthropic's own pages, into the catalog.* Method: read the model list, the release-notes overview, the model-deprecations status table, the pricing page and the plan/limits page (WebFetch/WebSearch; the four URLs the W39 finding `961caae922b0381a` cites are the starting set); for every Claude model id seen, return a catalog row; ids that are not `claude-*` are ignored; a model with a `retire_not_before` or `deprecated_on` earlier than any current assignment's is a retirement to name; a model absent from the catalog task_context is a new model to name. Schema (`traits.schema`, all four required):

```
{ "catalog": [ { "model_id", "family", "released_on"?, "retire_not_before"?, "deprecated_on"?,
                 "input_per_1k"?, "output_per_1k"?, "plan_availability"?, "stated_strengths"?, "source_url" } ],
  "new_models": [ "model_id" ], "retirements": [ { "model_id", "date", "source_url" } ],
  "summary_for_john": string(<=600), "patterns_applied": [int] }
```

**`dm-knowledge-model-trial`** (Knowledge). Objective: *The trial protocol and the switch rule, verbatim.* Method body, verbatim into the row:

1. A job type is a `model_assignments` row. A trial of a candidate model takes the 3 most recent real jobs of that type: for a lane row, the last 3 `runner_cycles` on that lane's model with an outcome other than `did_not_run` and an `item_id`; for a capability row, the last 3 `ai_activity_log` rows whose `feature` starts `<job_key>:`.
2. Each job is re-run on the candidate in a scratch branch: no push, no `runner_cycles`, no `runner_decisions`, no `backlog_items` write, no ship. The run's tokens and minutes are measured; the outcome is `passed` when the re-run reaches the same or a later stage than the real job did; the Verifier verdict is taken from a Verifier pass over the re-run (`approve`/`block`/`none`).
3. Room: a trial runs only when `runner_should_boot().detail` says `all_models_pct < pace_limit_pct` and `all_models_pct < wall_pct` (`weekly_rest_pct`, `final_day_rest_pct` on the last day), and never on a Fable model when `fable_pct >= fable_share`. Every trial run is logged with `scripts/agent-log.js --capability=model-assignment`.
4. Switch UP (candidate priced higher on `model_pricing.input_per_1k`): all 3 match-or-beat — `candidate.passed` and (`baseline.verdict <> 'approve'` or `candidate.verdict = 'approve'`) — and `sum(candidate.tokens) <= 1.10 * sum(baseline.tokens)`; on a `hard-judgment` row a clearly better result on one passed trial wins even at higher cost. Switch DOWN (candidate cheaper): all 3 `candidate.passed`. Otherwise keep, and record why.
5. Evidence shape, one entry per trial: `{ "job_ref", "run_at", "hard"?, "clearly_better"?, "baseline": { "passed", "verdict", "tokens", "minutes" }, "candidate": { "passed", "verdict", "tokens", "minutes" } }`.
6. After a switch, the first 5 real runs are the watch window; if blocks, escalations or failures rise above the baseline the switch reverts itself with a recorded reason. A retiring model's jobs move before its date; if no candidate passes, a ticket is filed.

**`dm-model-assign-intent`** (Intent, the capability's default). Objective: *Decide every model switch, keep, money ask and retirement move for the job types in task_context, one action per row, each with its evidence.* Method: for each `model_assignments` row in task_context, with its trial evidence (from `scripts/model-trial.js`, the remainder ticket), the catalog and the room numbers, apply the trial Knowledge's rule and answer one action; `money` when the candidate needs a plan upgrade, paid extra usage or API dollars beyond the walls (`weekly_cost_usd` required); `file-ticket` when a retiring model has no passing replacement (`ticket_title` required). Schema:

```
{ "catalog": [ ...as release-watch... ],
  "actions": [ { "job_kind": "lane"|"capability", "job_key", "action": "switch"|"keep"|"money"|"file-ticket",
                 "to_model"?, "reason": string(<=1200), "trial_evidence"?: [ ...§B.5... ],
                 "weekly_cost_usd"?: number, "ticket_title"?: string(<=200) } ],
  "summary_for_john": string(<=600), "patterns_applied": [int] }
```

## §C — counting real runs, blocks, escalations, failures (both functions, one definition)

For a `lane` row on model M since instant T: runs = `runner_cycles` where `model = M` and `started_at > T` and `outcome is not null` and `outcome <> 'did_not_run'`; blocks = `runner_verdicts` rows with `verdict = 'block'` whose `cycle_id` is in those runs; escalations = `runner_questions` rows whose `asked_cycle` is in those runs; failures = runs whose `outcome <> 'shipped'`. For a `capability` row with key K: runs = `ai_activity_log` rows where `feature like K || ':%'` and `created_at > T` and `model = M`; blocks and escalations are 0; failures = 0 (no per-row outcome exists; the watch on a capability row is a run counter only, stated so nobody expects more). Rates are `count / runs`; the baseline takes the last 5 runs on the old model before the switch (T = the 6th most recent run's start, or the row's `since` when fewer exist) and the watch takes the first 5 on the new model after `since`. "Rises" means any of the three rates on the new model is strictly greater than the baseline's.

## Why one capability, three Skills, one write path

The ticket names three Skills. In DeepBench terms a Skill is a `skill_profiles` row and its type is part of the change (pattern 136). Release Watch reads pages and answers a contract: Intent. Assign Models answers the decision contract: Intent. Model Trial is a protocol and a rule the manager must read every time it decides, and its execution is deterministic (pick jobs, re-run, measure) — a Knowledge row is what the manager reads, and the script is its hands; giving it an Intent would spend a model call to do what a script does (pattern 9, 10). All three hang under one capability, `model-assignment`, because they are one job with one write path (§19b): every table write goes through `apply_model_assignment()`, which owns the before-images, the decision handles, the switch rule and the refusals — the `apply_gate_rulings()` / `apply_audit_review()` shape (pattern 17, 19). The Skill rows carry no other agent's name (Rule #1).

`runner_model_lanes` is never written here: AGT-142's guard refuses it, and the AGT-142 mirror trigger plus AGT-143's Skill-row trigger carry a `model_assignments` write everywhere a reader looks. That is why a switch images every `skill_profiles` row the AGT-143 trigger will move — 54 Fable rows today for a `judgment` switch — under the switch's own decision, so `reverse_decision()` restores both the assignment and the rows (AGT-143 STOP LINE, §19v P6).

## Why the rule lives in SQL and not in the Intent's judgment

The switch rule (Q3) is arithmetic over evidence: 3 trials, match-or-beat, 10% tokens, all-pass for a downgrade. A rule that a model applies is a rule that can be misapplied; a rule the function enforces refuses the answer instead (pattern 10, 19). The one judgment limb — "a clearly better result on a hard job wins even at higher cost" — is a boolean the manager sets on a trial with its reason, and the function honours it only on a `hard-judgment` row. The manager's judgment still chooses *which* rows to trial, *when* (the room gate), and *keep vs switch* within the rule.

## The watch window and self-revert

`watch_runs_observed` and `watch_baseline` exist on the AGT-142 row for this. `review_model_watch()` is a second function rather than a trigger because runs land in three tables over days; a daily call (AGT-146's 4:30 AM check) is the honest cadence, and it is idempotent — a row past 5 runs is never re-graded. The revert writes its own `model-revert` decision carrying both rate sets, so the daily list (SES-424, rendered from `runner_decisions`) shows the switch, the revert and the undo handle with no extra reporting code (pattern 16, 92).
