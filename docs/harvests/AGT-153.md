## 2. The dependency decision — zero new packages

The ticket suggests "a standard maintained IMAP client (e.g. imapflow) + mail parser, added to package.json". Measured against the caps that is not the cheaper honest variant:

- `package.json` + `package-lock.json` are two of the three files. With the script edit that is the cap, leaving no file for the test the ticket itself requires (the STORE/COPY/MOVE/EXPUNGE/APPEND/DELETE/CREATE/SELECT refusal, the fixture parse, the 7-day window and the dedupe). The library route therefore forces a split (cycle A: dependency only; cycle B: script + test) and still needs a fourth file in B.
- imapflow (Node ≥ 20, ESM + CJS) pulls roughly nine transitive packages and mailparser roughly ten more (html-to-text, iconv-lite, libmime, mailsplit, nodemailer, …) — about twenty new supply-chain entries in a public repo whose cloud routine would install them unattended, for one sender's plain-text mail.
- The subset this ticket needs is small and fixed: greeting, `LOGIN`, `EXAMINE`, `UID SEARCH FROM/SINCE`, `UID FETCH BODY.PEEK[]`, `LOGOUT`, `{n}` literals, and a MIME decoder for multipart/alternative with quoted-printable/base64. That is a few hundred lines over `node:tls`, with no behaviour a maintained client would add here (no IDLE, no extensions, no writes).
- The read-only guarantee is STRUCTURAL in the zero-dependency variant (pattern:10): `send()` holds an allow-list of six verbs and refuses anything else before a byte is written, and the test proves it by splicing `SELECT INBOX` into a copy and by calling `send('SELECT INBOX')` against a fake server that logs every command. With imapflow the same test could only grep call sites for `messageFlagsAdd`/`messageMove`/… — a weaker, forever-growing deny-list.
- Naming the choice per pattern:101: this is a homegrown minimal IMAP client (RFC 3501 subset) rather than the industry library; the reason is the cap arithmetic plus the structural read-only invariant, not novelty. If a later ticket needs more of IMAP (IDLE, multiple mailboxes, flags) the library route should be re-evaluated then, with its own two-file dependency cycle.

Files: `lib/imap-readonly.js` (the one reusable service, §19m — mail read is a seam the market lane could reuse), `scripts/personal-agent.js` (the flag, as AGT-84 built the others), `tests/regression/agt-153-linkedin-alerts.test.mjs` (the fixture lives inline so no fourth file exists). Tasks: 4.

## 3. Design choices the kickoff states without argument

- **Credentials read in-process, never into a session.** The script reads both `runner_secrets` rows by name over service-key REST (the `api/_lib/mcp.js:410` pattern) so no session ever exports or sees them — tighter than AGT-84's export-inline rule and what John's "never read into a session" asks. The connect/auth failure maps to exit 3 and the one sentence John named; every lib error passes `redact()`.
- **The watermark never narrows the search.** John: "always look at least a week backwards in case anything is ever missed". So the scan is always `SINCE now-7d`; the watermark (`uidvalidity`, `last_uid` on the latest `fetch-linkedin-alerts ran` log row) only skips messages a COMPLETED run already emitted, and it is written only after the intake file exists — a failed run leaves it untouched and the next run re-covers the week. A changed UIDVALIDITY invalidates it (RFC 3501 §2.3.1.1). Job-id dedupe against `posting` rows (`data.linkedin_job_id`, and ids found in `data.url`) catches the same job repeated across alerts; AGT-154's records write the id back.
- **Intake file, not posting rows.** The ticket says "emit an intake file for the render": the script writes `--out` JSON and inserts only its own run log; AGT-154's capability decides verdict and act call and writes the `posting` records through `--write`, keeping one write path for judged records.
- **Date filter client-side too.** IMAP `SINCE` is day-granular in the server's zone; the lib also drops anything whose `Date` header is older than the window, so the 7-day proof in the test does not depend on the fake server honouring SINCE.
- **Parser keyed on the one stable fact.** The job-view href is the only structure the public record confirms; title/company/location are taken as the three lines preceding the link (badge line dropped) and left `null` when absent (pattern:34). The first real run is where the shape gets confirmed; a mis-parse shows as nulls, never invented text.
- **Fixture hygiene.** `scripts/audit-private-scan.js` flags personal-mail domains and 16+-character token-shaped values next to PASSWORD-like names; the fixture therefore uses `fixture@example.com`, `fixture-user`, `fx-pw-1`, and Task 4 runs the scan before commit.
- **Model.** Judgment lane (`claude-fable-5-1`): a protocol client with a security invariant and literal parsing is not a mechanical sweep (pattern:125).
