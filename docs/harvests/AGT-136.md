## 2. What decide-gated-card and the findings review actually hand over (the thing to check before designing a seam)

`public.apply_gate_rulings(p_rulings jsonb, p_cycle_id uuid, p_session_name text)`, step **3a**, read from `pg_get_functiondef`:

> `if v_ruling = 'john' then v_qid := 'gate-card-' || left(v_id::text, 8); insert into public.runner_questions (qid, question, context, asked_cycle, status) values (…, 'open') on conflict (qid) do update …; continue; end if;`

It writes **no card** — the card stays undecided on purpose, and the OPEN question is what stops `runner_should_boot()` re-firing the same branch. So **the handover mechanism already exists**: a parking lot (`runner_questions`) with exactly one addressee. This is why slice 1 needs no new seam and does not touch either peer script — it gives the existing lot a second addressee and the desk that empties it. `audit-review.js`'s `escalate` path is the same story one level up and is not touched this slice.

Answering a parked `gate-card-…` question also un-sticks its card: once the question is no longer open, `rulableCards()` (`decide-gated-card.js:78`) admits the card again. The desk therefore returns work to the board rather than only closing rows.

## 3. The design choice: the ruling vocabulary is read off the schema, not invented

`runner_questions` CHECK constraints, live: `answer = ANY (ARRAY['yes','no'])`, `status = ANY (ARRAY['open','answered','withdrawn'])`, `UNIQUE (qid)`, pk `id`, and it has `updated_at`. The questions are already yes/no-shaped (pattern:152 — tappable options), so the Designer's call is `yes` / `no` with the reasoning in `answer_note`, `withdrawn` for a moot one, and `john` for the three subjects John kept. A free-text `answer` would be rejected by the CHECK at write time; an invented fifth ruling would have nowhere to land. This is the whole reason the kickoff carries those CHECKs verbatim.

Making `JOHN_CALLS` an enum of exactly three is the structural half of John's ruling (pattern:99): a feature or functionality question **cannot** be addressed to him, because the vocabulary has no value for it.

## 4. Reversibility was the hidden cost — and it is the QA discriminator

`public.reverse_decision(p_decision uuid, p_actor text, p_reason text, p_actor_cycle uuid)` restores only the tables in its `k_allowed` array. Read live, that array ends:

> `'runner_items' …, 'audit_findings' …, 'model_assignments' -- IN: AGT-152 … ];`

`runner_questions` is **absent**, and it is *not* in the OUT list either (that names `runner_cycles`, `runner_before_images`, `runner_decisions`, `runner_ladder`, `runner_verdicts` and the counters) — it was simply never needed. Consequence, and it is the exact failure SES-320 and SES-364 both recorded: the images would be `refused` at the top of the restore loop while the call still returned `applied`. "Recorded as reversible decisions" would have been false on the day it shipped. One appended line fixes it, on the AGT-152 precedent, and `runner_questions` having `updated_at` means the restore lands in `restored` rather than `restored_unverified` — a countable, discriminating number.

Two sub-facts the Builder needs and the kickoff carries:
- `CREATE OR REPLACE` keeps the identity list `(uuid, text, text, uuid)`. Changing it would create a second overload and PostgREST would resolve neither (`.claude/rules/supabase-function-signature.md`, found live as `match_the_library` in DAT-12).
- The written-since guard is `if v_updated is not null and v_updated > v_decided then` (line 300 of the definition). `record_decision` and the row update both run inside one transaction, so `now()` is identical for both and the guard cannot fire — but `clock_timestamp()` would move and the reversal would refuse its own rows. Hence the explicit instruction.

## 5. Scope: what slice 1 is not

The ticket's BUILD has four parts. Slice 1 takes the first one only.

- **In:** a Designer capability that rules the product and functionality questions the platform has parked, each ruling one reversible decision; the runbook step that runs it; the catalog entry that lets it log.
- **Out, named in the STOP LINE:** (a) gap findings attributed to The Designer; (b) the SES-397 repeated-pattern → Designer Knowledge edit. Both are slice 2. (b) is agent-row build work under §19v P6/P7 — `runner_card_asks` holds **15 open `skill-edit` rows over 3 designer fingerprints** today (`2fb97122c84a986b` 7 cycles, `e7393ed419f16617` 5, `a05f97ba602f2e21` 4), re-filed on every cycle, and `runner-cycle.md` step 9 (7d) still says a promotion asks *John* to rule. Whether that ask is now the Designer's is itself a call the new desk can make — which is the right order, and a reason not to hand-write the Knowledge edit path into this slice.
- **Out, report-only:** `decide-gated-card.js:59`'s four John calls and `audit-review.js:57`'s five both predate John's 2026-09-25 narrowing to three. Editing them is a second feature in two files two peers read; it is filed as a finding (`JOHN-0925-DESIGNER-DECIDES` is the live source of truth either way). Likewise `design-kickoff` is itself missing from `SERVICE_CATALOG` — the same class of defect AGT-137 hit with `audit-run-review` — and `design-ruling` gets no `model_assignments` row this slice (the `agt-143` arm (d) coherence check iterates `model_assignments` rows, so a capability without one is simply not checked).

## 6. Alternatives considered and rejected

1. **Rule `audit_findings` instead of `runner_questions`.** Findings are already in `reverse_decision`'s allow-list, so reversibility would have been free. Rejected: findings belong to the Development Manager's weekly review (`JOHN-0925-FINDINGS-STANDARD` — only he files tickets), so a Designer desk over the same rows would collide with `apply_audit_review()`; and the ticket's use case is a *question*, not a finding.
2. **Add a `designer` value to `decide-gated-card`'s RULINGS and route cards directly.** Rejected: it changes `apply_gate_rulings`'s signature-adjacent vocabulary and a live peer's validator for no gain — the `john` branch already parks the question where a desk can read it (pattern:17, extend what fits).
3. **Add an `asked_of` column to `runner_questions` and classify each row.** Rejected as a fifth wheel (pattern:67): the Designer is the default addressee and hands up only the three John kept, so the enum already carries the routing without a new column or a text classifier.
4. **Fold the Knowledge-edit half in to "finish the ticket".** Rejected: two features, and the caps are per cycle, not per ticket.
