## 2. Rulings made without John (each reversible)

1. **A sibling script, not a generalized `personal-agent.js`.** Generalizing it would edit that script and `tests/regression/agt-84-personal-agent.test.mjs`, which pins READ_MAP to exactly the 11 `career-*` keys. The write validator also differs in almost every rule. And it would put the market read path and the `career_records` read path in one module, which is the boundary John drew. The duplicated seam (argument parsing, `rest()`, render header) is small. Pulling it into a shared core (pattern:14) is filed as a follow-up, because doing it here would break the caps.
2. **A separate clone, `C:/Projects/deepbench-market`, for the loader.** The Jerry clone is named for the personal lane, and sharing it would tie two agents' pull and `npm ci` timing together. The cost is one more `node_modules`. Reversible.
3. **Tryout order.** The ticket says run 1 is the competitor study from the 2026-09-24 Grok Bot research. The AGT-120 harvest (ruling 13) says `pmm-why-deepbench` is the first run. Both hold if run 1 is `pmm-competitors`, which writes the Grok Bot competitor record (AGT-120 ruling 11), followed in the same sitting by `pmm-why-deepbench`, which reads competitor records. Run 2 is `pmm-messaging`. The whole Napkin is read once, in run 1.
4. **`since` is deterministic.** It is the newest `ai_activity_log` row for the agent with `feature like <slug>:%`, which is the agent-log.js row every run writes. So a run that writes zero records still moves `since`. The session uses the printed `since` to filter Napkin entries, and the script uses it for shipped rows (pattern:9).
5. **What the script reads and what the session passes.** The script reads market_records per READ_MAP, corrections, backlog `shipped`/`open`/`inventive`, and the capability catalog. The session passes, through `--input-file`/`--ask`: web research, the Grok Bot text, cost and usage figures, samples of delegation reasoning, lineage and grading, the locked pitch, repository visibility, and the owner's patents. Moving those into the script would break the caps, so a follow-up is filed to make the cost and lineage samples a scripted read.
6. **Corrections.** John's cuts are written with the same `--write`: one `correction` item whose `data.capability` equals the slug (refused otherwise). `--render` then reads them on the next run.
7. **Napkin write-back.** `--write` prints `napkin_notes` after the insert. The session writes back ONLY each entry's `note`, with ArtifactData. The script never reaches the artifact.
8. **Left to the Skill guardrail because no script can check it:** a `conversation` record that names a person instead of a role and company. No regex reliably tells a person's name from a company's.
9. **"ONE push with the link"** (the first-Monday refresh) is kept word for word (pattern:90). What the link points to is decided by the session at run time. A private Artifact is not "publishing" under John's keep, but anything public is. Flagged, not decided further.
