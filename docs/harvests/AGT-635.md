## 3. Why AGT-519 and AGT-547 are NOT in the set (decision D1)

The ticket's title asserts all three of AGT-552/519/547 are permanently ungradable and its Fix admits `delivered OR partial`. Those two sentences disagree, because 519 and 547 are at neither status. The board says why:

- **AGT-519** — `runner_decisions` holds `kind='ticket-validation'`, decided 2026-11-09 11:51:31Z, summary *"AGT-519 validated: not-real"*. Its `removal proposed` status is a validation ruling, not residue from a refused settle. Admitting it would write a ship decision for a ticket the platform has decided to remove.
- **AGT-547** — status `open`. `scripts/ticket-owner.js` and `scripts/audit-board.js` both read `["open","partial"]` as the pick path, so an `open` ticket can be picked while it sits in the lister. A cycle could be building it as a ship decision lands on an old commit.

So D1 admits `delivered|partial` only, which is the ticket's own Fix sentence and excludes both. AGT-552 alone is unstuck by this build. The decision row of 2026-11-03 10:25:36Z already records that these three "are blocked_by AGT-595: each one's fix is already on dev and only its RECORD is owed" — AGT-547's owed record is a status question, filed as its own item, not this function's.

## 4. The consumer, which the ticket does not mention (decision D3)

Adding the SQL branch alone would NOT make AGT-552 gradable. `scripts/verifier.js regradeBranch()` consumes the lister's row and:

- (b) ancestry needs `row.graded_sha` — supplied by branch 2 as the ship sha (hence D2's sha validation);
- (c) reads the prior verdict **by primary key** from `row.verdict_id`; a null id returns no row and exits 2 with "no runner_verdicts row null";
- then grades through `regradeGateResults({ gates, jobs })`.

The cheapest variant: branch 2 returns `verdict_id = null` as the lane signal, and `regradeGateResults` is passed `gates: {}`. With an empty prior-gate map no gate is `skipped` (no refusal), none is carried forward as `green`, and each of build/regression/hygiene resolves from its own CI job — exactly the "every gate graded from CI" semantics wanted. **The helper needs no edit, and `red_gates` returning all three keys makes the existing `ciJobsForGates` call correct unchanged.**

`record_ship_decision()` needs no change either: it requires a non-null `p_verdict_id` whose verdict is `approve` and whose `backlog_id` matches, and the lane already passes the *newly inserted* verdict's id (`ins.rowId`), not the absent prior one.

What this does NOT do: the regrade lane adopts the *regrading* cycle's before-images into the ship decision (`record_ship_decision` updates `runner_before_images where cycle_id = p_cycle_id and decision_id is null`), so the Reverse handle undoes the regrade cycle's writes, not AGT-552's original build. That is pre-existing AGT-609 behaviour, named here and left alone.
