## Why these shapes

- **A batch is an epic (D1).** Projects already own epics, `project_progress` groups by them, `epic_project_executing` gates the pickers through them, and `epics` is already on `reverse_decision`'s allowlist. A `project_batches` table plus a membership column would be a parallel structure (pattern:17), and it would not be reversible without a second allowlist edit. A perpetual project gets a new epic per batch.
- **Finished = every locked member `done` or `removed` (D2), revised.** The first draft counted `delivered` and `removal proposed` as finished, because at the time no ship had been approved since 09-16 and the literal rule could never fire. That premise is gone: AGT-170 armed delta grading and closed `done` on an approve verdict today. So the rule is now the ticket's own wording (pattern:90), which is also the reading that makes "Once a project is finished" mean what it says. The consequence is named rather than hidden: after (f), 54 AE members are not done/removed (43 delivered, 5 partial, 5 removal proposed, AGT-239). The delivered ones close through their own ship windows or AGT-245's re-grade, and the five removal-proposed ones need their removal ruled. The Q6 success check therefore depends on AGT-245 landing within the week; that dependency is AGT-245's scope, not this ticket's.
- **`listed` status + `list` kind (D3).** Q2: "anything found goes into a list". Open/carried findings are re-ruled every review, and carry caps at three weeks. `listed` is ruled once ("waits for the next proposal") and drops out of the review's coverage set, so a batch can run for any length of time without the list re-litigating itself. The trigger on `backlog_items` is the structural guard (pattern:10). The review kind and the `finding_group_epic` refusal are how the manager complies without the whole review raising. The security route is kept: `security` is `planned`, so filing there is still allowed (John's 09-25 rule is not weakened, pattern:166).
- **John-named exemption.** John naming a ticket into a running project is his own call, and AGT-240 itself was filed that way. The lock binds findings-born filing, which is what grew AE.
- **Two turns (D4).** John's words name both: "the auditor and dev manager review the current functionality, review the auditor list". The Auditor turn only grades what the batch built (working/broken/missing). The manager turn owns the proposal. They run only at a finish, so they are rare and cheap. Invocation rides (7e) via `auditor-routine.md`, so it is checked after every reviewable run, and the weekly routine can call the same block.
- **Only a session starts a project (D5).** Q3=A: his yes flips it. `start_proposed_project` requires `p_session_name` and his words. No cycle attribution is possible, so the runner cannot start work John has not approved.
- **Perpetual (D6).** (e): DMC and Agent Training are "perpetual routine projects" by charter. On finish they go `paused` rather than `done`, and the manager may propose their next batch under the same slug (a new epic).
- **reverse_decision gains `projects` (D8).** Without it, a Reverse of a proposal or start would restore the tickets and findings but leave the project status wrong while reporting itself applied-with-refusals. This is pattern:124: the feature introduces project status writes, so it makes them reversible itself.
