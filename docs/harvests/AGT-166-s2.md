## 2. The 34 "closed over red" are mostly John's own ratified closes

All 34 latest-block verdicts carry the verifier's boilerplate (`scripts/verifier.js:1003`): *"block: RED: regression suite … A block is the status quo — the cycle ships delivered and cards John."* 185 of the platform's 195 block verdicts read that way; it is not a per-row classification, it is what every block says.

How a block-graded ticket becomes `done` today: `record_ship_decision()` refuses a non-approve verdict, so `sweep_decision_windows()` (SES-320) never closes one; the SES-311 trigger `backlog_done_requires_verdict` requires *a* verdict, and its own test (`ses-311-done-requires-verdict.test.mjs:25`, `:340`) states *"a verdict='block' row SATISFIES the gate (a block is still a verdict)"*; the remaining paths are John's Accept on the shipped card (runbook L891–895: "AN ACCEPT ON A `shipped` CARD NOW WRITES THE TICKET `done` — IT IS THE ONLY THING THAT EVER DOES") and an attended session's write (session-setup.md §3e says a block writes `delivered`, not `done`).

Measured against that: of the 34, **23** have a `runner_items` row `kind='ship'`, `decision='accept'`, `decided_at >= verdict.created_at` — John accepted the shipped card after seeing the block; **5** have a `ship` or `ticket-status` `runner_decisions` row dated at/after the verdict; **6** have neither (`AGT-69`, `LOG-104`, `LOG-145`, `LOG-149`, `SES-360`, `SES-373`; four of these — AGT-69, LOG-149, SES-360, SES-373 — got their block *after* they were already done, a re-verification landing on a closed row; LOG-104 and LOG-145 were closed by an attended session on 09-03 with no decision and no card). So the auditor's check contradicts a rule the platform keeps on purpose, and 28 of its 34 hits are false. Pattern:94 — surface and amend in the same session, not silently patch either side.

**The call (iii):** a close over a standing block is legal only when *ratified* — a non-reversed `ship`/`ticket-status` decision, or a `ship`-card Accept, dated at or after the verdict. The trigger gains that clause (the fence the ticket asks for), the check learns the same predicate (so it flags only the unratified), the runbook states it beside the SES-154 passage, and the six unratified rows get one reversible `ticket-status` decision each — reversing one puts that row straight back into the census, which is exactly the semantics a Reverse should have.

Rejected: **re-open** the 34 (they are shipped code on `dev`, several are the platform's live rules — SES-311, SES-376, SES-389; re-opening puts built work back in the pick queue as if unbuilt); **record an approve that supersedes** (`ck_runner_verdicts_fail_closed` makes `approve` equal to all three gates green — an approve row for a tree nobody re-ran is a fabricated measurement, pattern:33/162); **a `block_kind` column on `runner_verdicts`** (nothing in the verifier distinguishes a status-quo red from a caused one; the label would be boilerplate again); **`directive` decisions as ratification** (AGT-70, SES-344, SES-367 carry directive rows dated after their block that are John's directives about other things, not about the close). The two-home predicate (SQL trigger + JS check) was weighed against a shared SQL function/view; kept as two homes because `audit-board.js` is read-only JS by AGT-86's design and the regression test drives both with the same four cases.

## 10. AGT-169 is the binding constraint, and it decides the mechanism

`ticket_owner_findings` open rows: **259**, over **10** slugs — `actual-unknown` 103, `verdict-missing` 45, `size-missing` 33, `delivered-unaccepted` 24, `type-off-taxonomy` 20, `designed-closed` 12, `quote-missing` 10, `remainder-stranded` 8, `cycles-over-quote` 3, `claim-on-closed` 1. Nothing rules them.

Reading `planWrites` (`:440`) settles the design: a `derivable` finding carrying `fix` never enters the ledger at all — `applyPlan` (`:813`) images the full row, PATCHes the cell, reads the representation back key by key, and the whole night hangs on one `record_decision` handle. Only `judgment` findings are inserted into `ticket_owner_findings`. So:

- A **confirmed** revalidation writes `revalidated_at` and files nothing. The pile does not grow.
- A **refused** one degrades to a judgment finding whose detail is `judge refused: <reason>` (`ingestJudgment`, `:625`), and `applyPlan` step 6 raises one `gap` per still-open slug into `audit_findings`, which the Development Manager reviews. That is the correct home for a removal proposal.

Filing all 438 as judgment findings would have taken the unruled pile from 259 to ~697 — the 2.7× the Development Manager warned about. The fix path avoids it by construction, not by intention.

`applyPlan` has **no column whitelist** on `fix.patch`, so `{ revalidated_at: <iso> }` needs no new write path. What it does have is a decision narrative that says *"Each fix is arithmetic (cost_pct_snapshot = …)"* and *"no status, quote or design_status written"*. A revalidation fix riding under that sentence would make the decision row lie, so `p_summary`/`p_reasoning` move in the same task — pattern:33.

## 11. Two facts that shaped the build, both found by reading rather than recalling

**The judge has never been shown a premise.** `readBoard`'s items select (`:716-719`) names 18 columns and neither `title` nor `description`; `judgeTask` (`:522`) passes exactly `{census, window, prior}` and deliberately strips row ids. A capability asked to confirm `revalidated_at` on that input would be guessing, and `ingestJudgment` would happily write the guess. Hence `premises`, read for the ≤25 batch only — full descriptions for 438 rows would be a prompt nobody can afford (AGT-166's own description is ~10 KB), and `PREMISE_EXCERPT = 600` bounds it deterministically. Every other `[A-Z]{2,4}-\d+` the text names is annotated with that row's live `status` from the board already read: that is the one piece of evidence that makes "superseded" a checkable claim rather than an impression, and it costs no extra request.

**A 13th slug is a night-losing change until the CHECK moves.** `pg_get_constraintdef` on `ticket_owner_findings_check_slug_check` lists exactly the twelve `CHECKS` slugs, and `applyPlan` step 4 still POSTs the findings as ONE array — SES-418's constraint half shipped, its tolerant-insert half did not. So the slug and the migration must land together, and `agt-79-ticket-owner.test.mjs` part N (`:946`) is already the guard that proves it: it inserts one row per `CHECKS` slug and asserts the returned slugs equal `[...CHECKS].sort()`. Adding the slug alone turns it red. That is the ticket's own self-made bug prevented inside its own ship (pattern:124), and it is why the migration is Task 1.

## 12. The batch, the carry-over, and the stall

25 a night, oldest-first by `(coalesce(filed_at,created_at), backlog_id)` — a total order over provable columns, so the same board yields the same batch whatever order the rows arrive in. The population count stays whole in `backlog.unrevalidated_30d`; only the *findings* are batched, so the census never narrows its own measurement (pattern:38).

The carry-over rule is the part that is easy to leave out and fatal to leave out. A refused row stays `open` and unrevalidated, so an oldest-first selector picks it again tomorrow, and the judge refuses it again. After enough dead premises the head of the queue is entirely dead and the drain stops advancing while every night still reports work. So rows holding an open `unrevalidated-30d` finding are excluded from the 25 and re-filed as `judgment` — `planWrites` then sees the key in `prior`, touches `last_seen_at`, and keeps the removal proposal alive without re-spending a judgment on it (pattern:9). `board.ownerFindings` carries them; `--board=<json>` can supply them, so the regression arm runs offline.

**Rejected.** Writing `status = 'removal proposed'` on a refusal (it would drop the row out of the population for free, but the Intent's own guardrail refuses a fix touching `status`, and "the census writes no status" is a standing property of this script). A separate `revalidate.js` (a second board reader is a second census; `ticket-owner.js` already holds the statistic, the ledger, the judge and the decision). Writing `revalidated_at` across all 438 in one sweep (the column would mean nothing — pattern:33; and the ticket's arm (b) says "or removal", which is a per-row ruling). A Designer-strength revalidation at 3 rows a cycle (the runbook's 8c rate): 146 cycles.

## 15. How the ticket closes, and why not a third slice

AGT-166's own text says "done means the checks return zero rows". Slice 2 ships the mechanism; the rows drain over ~18 nights after it. A `done` on ship day would be false, and a third slice (or a new ticket for the remaining rows) would discharge the ticket's own acceptance criterion under a new number, which pattern:95 forbids by name.

So: `partial` a second and final time, with the close condition made mechanical instead of remembered. `censusLine` now carries `revalidation <N> left` into `runner_cycles.notes` every night, where the standing brief already prints it, and the ticket is written `done` by the first cycle whose nightly reads 0 and whose `audit-board.js` reads `board-stale: 0 rows`. The stall condition is stated in the same breath: two consecutive judged nights at the same `N` means the drain is not draining, and arm (b) is re-designed rather than waited on. `settle-ship.js` records the STOP LINE's remainder verbatim on the ticket-status decision, which is how slice 1's remainder reached this cycle — the mechanism is proven, not proposed.
