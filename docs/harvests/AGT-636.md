## 3. The design, and what it does not do

One change in one branch: push `sp.objective`, then `sp.method`, between the role prompts and the trait lines (D1). That is the order identity uses (role prompts, objective, method) and intent uses (objective, method, traits), so the three branches read alike. A generic field read, no slug / agent / capability conditional (`capabilities-are-data.md`, §19b). Each Skill's text renders only in its own section, so nothing gains a second home (`agent-data-visibility.md`, §19w); the role-prompt claim AGT-552 built is untouched and `agt-552-role-prompt-once.test.mjs` stays green on the patched copy.

Not done, on purpose:
- `tone` and `output_desc` (AGT-400 clause 3) -- a different seam.
- §19w's "Behavior Skills' own objective and method unread" bullet (ARCHITECTURE.md:3040) is a dated measurement under "Current state" (2026-10-06); its sibling "role prompts rendered twice" was left as written when AGT-552 shipped. Not edited (D3). If the Auditor wants that list reconciled it is one ticket for the whole bullet, not a third file here.
- No kept live test (D4, pattern:162). A permanent test asserting "every live behavior row renders exactly once" would go red on another cycle's data edit. The kept test is pure (`buildSections()` fixtures, no database); the live proof is the build's own before/after snapshot.
