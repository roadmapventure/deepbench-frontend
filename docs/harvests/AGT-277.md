## 2. The finding this revalidation added to the ticket's own story

The ticket says nothing filed. That is nearly true and the difference matters to the design.

`db_health_tick()` **does** file findings of its own — `pg_get_functiondef` confirms the body contains both `audit_findings` and the literal `db-health-readings-gap`, which matches the AGT-239 amendment ("`db_health_tick()` also files `db-restarted` and `db-pressure-red-repeat`"). Row `b8dd013e-a2d4-411b-9819-ca4f9f759de2` (kind `other`, check_slug `db-health-readings-gap`, family `service`, finding_type `defect`, confidence `high`, location `public.db_health_readings/417`) carries this very outage, worded: *"No completed health reading between 2026-09-29 04:00:00.657808+00 and 2026-09-29 04:45:00.487736+00 (45.0 min; the window is 15 min)."*

So the outage **was** eventually filed — by the patient, once the patient woke up. That is exactly the premise the ticket names, sharpened: the inside filer is **retroactive**. It cannot fire during the silence, and if the tick never returns it never fires at all. This is the strongest argument for the outside probe, and it is also the reason the new check must use a **different slug** (`db-health-silent`): an identical slug would collide conceptually with a filer that means something different (a gap observed after the fact, versus a silence observed while it is happening).

## 3. Design choices and the alternatives rejected

**Where the probe lives.** GitHub Actions, per the ticket and per `meter-reader.yml`'s precedent — the only always-on host this platform already uses that is not the database and not John's laptop. Rejected: a second pg_cron job (same patient), a claude.ai routine (measured dead for meter reading in SES-388's probe run `cse_01XgcrXWKfp2qZ4BokzfrL22`, and a routine that must also run when the database is down is the same class of dependency), a Vercel cron (`api/` sits at the 12-function Hobby cap, recorded in SES-78's design).

**How the silence reaches a person.** Two channels, deliberately, because they fail in different places:

- *Readable database, stale readings* → one `audit_findings` row via `ingestFindings`, which is the weekly review's own list. Evidence travels in the finding's `locations[0].text`.
- *Unreadable database* → the script cannot file anything, so it exits non-zero, the job fails, and GitHub emails the failure. This is `meter-reader.yml`'s documented "FAILURE IS VISIBLE" contract reused rather than a new alert destination invented (pattern:17, pattern:68). Rejected: a Slack/webhook alert — that is a new destination, a new secret, and attended configuration outside the repo, for a channel GitHub already provides.

**Why the fingerprint must be stable.** `fingerprint()` is `kind|locationKeys|normalize(governing_fact)`, and `locationKey()` reads `loc.location` only (`scripts/audit-ledger.js:190-197`). Put a timestamp in `location` and a 45-minute outage probed every 10 minutes files four rows; put it in `text` and it files one, with the rest classifying `seen`. The accepted cost: a second, separate outage in the same ISO week appends nothing. That is the ledger's own design (UNIQUE `(fingerprint, iso_week)`), not a new compromise, and the weekly review is the audience either way.

**Cadence.** 10 minutes against a 15-minute window. Equal-to-window would let one late GitHub fire (their schedules are best-effort) skip a silence entirely; much shorter buys nothing, because the tick itself only runs every 5 minutes.

**Window read live.** `runner_settings.db_health_thresholds->>'window_minutes'`, never a literal 15 in the script — the same number `db_health_level()` grades against, so the probe and the gates cannot disagree (pattern:14, pattern:2). A missing `window_minutes` is exit 2, not a default.

## 4. The scope boundary, stated precisely

The repo half ships from an unattended cycle. The workflow half cannot:

- the sessions' PAT has **no workflow scope** — `docs/runbooks/session-setup.md:732` and `docs/SES-78-RUNNER-DESIGN.md:14` both record it, and `docs/FEATURES-ARCHIVE.md` records SH-13 being re-planned around the same blocker in July;
- GitHub schedules **only from the default branch**, which is `main`, and pushing `main` needs John's sign-off (CLAUDE.md hard rule).

So the YAML ships as `docs/design/agt-277-db-health-watch.yml` — a normal repo file, pushable — and John copies it to `.github/workflows/db-health-watch.yml` on `main`. **No new secret is needed**: `.github/workflows/ci.yml:299-300` shows `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` are already repository secrets. That keeps John's step to one copy-and-push in plain words (pattern:91), and the build's tests never depend on it.
