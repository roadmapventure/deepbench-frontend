## 1. Premise — ALIVE, and what exactly is alive

The ticket makes two claims. Both were re-measured on tree `fd4a0d4` (= origin/dev at branch time).

**(a) "Every ledger write goes through one tool and nothing checks a second path before a cycle attributes a timeout to the database."** Partly overtaken, mostly alive:

- `docs/runbooks/runner-cycle.md` L422-424 (step 0b) is the ONLY timeout rule in the file: *"`db_level` red/unsafe, or the heartbeat failed or took > 10 s: finish the step, run `db-pressure.js --hold`; exit 4 → close `failed`, `last_step 'held: db_pressure'`"*. A failed or slow heartbeat is routed to the hold with no retry on a second path and no reading recorded beside the claim. `--hold` does read `db_health_level()` over PostgREST (scripts/db-pressure.js), so a green releases at once — but nothing tells the cycle to retry the statement itself, and nothing tells it what it may conclude from the timeout. Cycle `1ff72a96` (2026-10-22) verified the same gap live and wrote it into its notes.
- `grep -n "cycle-note.js\|cycle-heartbeat.js\|PostgREST" docs/runbooks/runner-cycle.md`: the PostgREST notes path is named at exactly ONE site, L4291 inside step 9's (7b) (AGT-547, v7.0.929). (7c) L4359 says *"appending, the same statement as (7b)'s numbers"*; (7f) L4423, (8) L4568 and the close-out record never name a path. The heartbeat has a REST script (`scripts/cycle-heartbeat.js`, SES-423) but step 0b's text never names it. So fix (1) — "step 9 names a fallback write path for the tail record" — is half-done for (7b)'s three numbers and undone for every other tail line.

**(b) "The 60-second ceiling belongs to that connector's write statements."** Alive and sharpened. This cycle, over PostgREST with the service key:

| Statement | Path | Result |
|---|---|---|
| the step-0b heartbeat UPDATE, identical values, on this cycle's own row | PostgREST PATCH `runner_cycles?id=eq.fe5bbc48…` | HTTP 200 in 0.227 s |
| `db_health_level()` | PostgREST `rpc/db_health_level` | `green`, reading 10541, 9.4 min old, in 0.220 s |
| one-row DELETE on `runner_before_images` | `mcp__Supabase__execute_sql` | hung 60 s: *"timed out after 60s / the server asked the user a question, and no answer came before the time limit"* — reported first-hand by the orchestrator this cycle; the MCP is unauthorised in the Designer's session, so NOT re-run here |
| SELECT / INSERT / non-destructive UPDATE | same MCP tool, same session | well under a second (orchestrator's report) |

The DELETE/DROP wall therefore has a measured mechanism — the connector's destructive-statement confirmation prompt, which an unattended session can never answer (AGT-434 harvest §2 recorded the same tool text in October; HANDOFF-self-completion-session2-1012.md L33 reproduced it 4× on a one-row delete). The UPDATE wall (AGT-303's heartbeat, AGT-547's two notes appends, the ticket's five UPDATEs) has the same 60 s shape but NO measured mechanism: scripts/cycle-note.js's header records the connector landing the same ~2 KB append in under 1 ms server-side on another attempt, so the loss does not reproduce on demand. The kickoff is worded for that honesty: the rule it writes is *"a timeout alone is never db_pressure, a lock or a restart: retry it identically over PostgREST, read db-pressure.js --check, record both"* — it names what a cycle must DO and may CONCLUDE, not a mechanism it cannot prove. The ticket says "write statements"; the measured truth is "destructive statements provably (confirmation prompt), other writes intermittently, cause unestablished, database exonerated every time it was measured".

**(c) The "3 of 3 false alarms" sentence — a wrong causal link, which does not weaken the fix.** `audit_findings` where `check_slug like 'db-pressure%'`: 8 rows, all `found_by = runner:db-health` — the in-database tick filing from its OWN readings (e.g. reading 7961: REST probe 20,071 ms, iowait 1.09%; reading 8821: probe no answer), never from a cycle's tool timeout. 7 ruled `not-a-defect`, 1 ticketed (AGT-366, the repeat). In the ticket's window (2026-09-22..10-12) there were exactly 3 `db-pressure-red` rows (09-29, 10-03 ×2), all not-a-defect — the count is right, the attribution is not: those alarms are the tick's probe leg, not a cycle misreading a connector. Pattern:32 — attribute from what the call did. The kickoff therefore does NOT claim the fix will change that check's grade; it fixes the two things it can measure: the rule at 0b and the path at step 9.

**(d) Harm so far, measured.** `runner_cycles.last_step = 'held: db_pressure'`: 1 row ever (`f0e11bcd`, 2026-09-29 21:52Z — the genuine outage day; a true hold). `notes ilike '%timed out after 60s%'` since 2026-09-20: 4 cycles (`6abe3e65`, `efedb242`, `f0d501a0`, `68372c07`). At least five cycles (`8cb00c9b`, `ef508dc9`, `7d72b823`, `3a9c2d63`, `ba3fa407`) improvised the second-path check on their own and wrote both readings into notes — the rule is already the staff's practice; the runbook just does not carry it, which is why every cycle re-derives it under time pressure.

## 3. Design choices (each a recorded, reversible call — JOHN-0925-DESIGNER-DECIDES)

1. **Byte-neutral edit instead of re-pinning.** `docs/runbooks/runner-cycle.md` is 380,920 B and that number is an EQUALITY pin in three test files (`ses-413d`:273 `export const BYTES_AT_SHIP`, `agt-253`:73, `agt-525`:57 `RUNBOOK_BYTES`) plus a one-way ratchet (`agt-138`:186, `bytes < 380980`) and the SES-336 ceiling 381,000. Re-pinning would make the ticket 6 files (runbook, card, 3 pins, test) against a cap of 3 — a cap case under pattern:172. A byte-neutral edit keeps every pin green and the ticket inside the cap; AGT-547 (v7.0.929), AGT-506 and AGT-525's T3 shipped the same way. Reverse by re-pinning the three tests in one commit if a later edit cannot be made neutral.
2. **Where the bytes come from.** The v7.0.641 (AGT-171) header stamp, 463 B + newline, rotates out for a 110 B + newline AGT-478 stamp (−353). It is the only one of the five that can go: agt-133 asserts line 1 stays `v7.0.658` and the `v7.0.610` stamp stays present; ses-424c pins `v7.0.658` as LATER_STAMP; agt-171's test pins its facts in its own header, not in the runbook stamp (`grep steals 17 tests/` → only agt-171's own comment). Stamp count stays 5 (agt-133 STAMP_COUNT).
3. **Accounting.** stamp 464 → 111 (−353); step 0b L422-424 230 → 498 (+268); (7b) splice `--note=<text>\`. The connector \`UPDATE\` is\na documented FALLBACK:` 64 → 149 (+85). Sum 0; `wc -c` 380920 measured on a scratch copy; `render()` of that copy gives an 8,943 B card (unchanged size: no L-anchor changed digit count) with sha256 `814940cfd378e571`. Old literals after the edit: `or the heartbeat failed or took > 10 s` 0, `a documented FALLBACK` 0.
4. **Scope of fix (1): the tail's NOTES lines.** The ticket's own words — "the PostgREST write that was measured at 93 ms", i.e. the notes append — and the (7b) sentence is the home the other sites already defer to (AGT-547 kickoff §2: "L4291 is the one that instructs the statement, and L4357's (7c) plus four later sites defer to it"). The (6) close (lease release + `ended_at` in one CTE) stays on the connector: no RPC closes a cycle (cycle `1ff72a96` checked pg_proc; `rpc/exec_readonly_sql` is 404), and two PATCHes would split an atomic write. A PostgREST close is a new function + script — a separate ticket if a close is ever lost; none has been measured lost.
5. **Scope of fix (2): one home, step 0b.** `db_pressure` is written in exactly three places in the runbook (L175 pre-boot refusal, L419-423 the heartbeat rule, L4468 Gate F table); only the heartbeat rule turns a tool timeout into a claim. The new sentence is headed "Heartbeat (or any write) failed or > 10 s" so the (7b) fallback inherits it without a second copy (pattern:8, pattern:163).

It is commentary pointing at the runbook, not procedure; editing it is a 4th file. The kickoff tells the Builder to report it, not touch it. If John wants it aligned, it is a one-line follow-up with no QA that could fail.
7. **The BASELINE block is pasted with basenames and without the five red lines' messages.** `scripts/pre-build-baseline.js` prints absolute paths (`/home/user/deepbench-frontend/tests/regression/…`); the paragraph is 8,716 B as printed — larger than the whole 8,192 B kickoff cap. `scripts/verifier.js` `measuredTestsFrom()` / `baselineCoverageFinding()` compare `path.basename()` of each `- <name> — green|RED` line, and `PER_TEST_LINE` accepts a bare name, so the 81 names, the `Red set: 5 of 81` line and the `Instrument:` line carry the whole measurement at 3,997 B. ## 4. Alternatives rejected

- Add the rule to `scripts/db-pressure.js` / `cycle-heartbeat.js` code (e.g. the heartbeat script retrying itself): the scripts already ARE the second path; the defect is the runbook sending a cycle to `--hold` without them. Narrowest layer is the doc (pattern:8).
- An RPC `close_cycle()` so (6) also has a PostgREST path: no measured loss of a (6) close; 4th/5th file; a migration with a function needs the REVOKE-by-name pattern (.claude/rules/supabase-column-grants.md addendum) — real work for an unmeasured harm.
- Index on `capability_skill_profiles.skill_profile_slug` (the AGT-465 hypothesis): retired by AGT-465's harvest §2 (two FKs, 347/14/194 rows, one-row delete reproduced) — nothing to add.
