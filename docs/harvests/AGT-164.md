## 2. Column and constraint checks behind §4's SQL

- `public.agents` NOT NULL columns: `id`, `name`, `lane` only (`lane` defaults `'product'`). Every
  other column in the INSERT is optional, so the omitted score columns land NULL.
- Only one CHECK on the table: `ck_agents_lane` ∈ {`product`,`governance`,`personal`}.
- `tenant_id` is NULL on **all 32** rows, so hers is NULL too — STANDARDS §11 names `tenant_id` in
  its declared remainder, and matching the platform beats inventing a value for one row.
- `runner_before_images`: `ck_before_image_attribution` = `(cycle_id IS NOT NULL) <> (session_name
  IS NOT NULL)`. An automated cycle sets `cycle_id` and leaves `session_name` NULL.
- `public.record_decision(uuid,text,text,text,text,text[,text])` returns `uuid` (last arg defaults
  NULL), is not SECURITY DEFINER, and `kind='agent-row'` is a live value (92 rows). `summary` and
  `reasoning` both have non-empty CHECKs; `backlog_id` must match `^[A-Z]+-[0-9]+[a-z]?$`.
- One transaction with the decision, the INSERT, the before-image and the assertion means a failed
  gate leaves no half-created agent — the reason the SQL is a `DO` block and not four statements.

## 3. Why the roster entry is the whole of "Teach-screen access"

`src/hooks/useAgents.js:271` is `return useMemo(() => AGENTS, [])` — a static import from
`src/data/agents.js`, with the Supabase query still a TODO. `src/main.jsx:55` routes
`/bench/:agentId/teach`; `src/screens/TeachScreen.jsx:81` resolves the agent from that array and
`:165` posts `agent_id: agentId` (the URL's id) to `/api/load-entries`, which reaches
`lib/knowledge-write.js` — an upsert into `knowledge_entries` with no FK and no agent validation.
So nothing under `api/` needs to change and no `agents` row is strictly required for teaching; the
row exists because §19v P7 and STANDARDS §11 require an agent to have one, and because AGT-162's
MCP path reads it.

`SE-03-agent-fields.js` grades every roster entry against STANDARDS §11's 23-field table (it
asserts the parse yields exactly 23) plus a five-key `AVATAR_CFG` entry and three pronouns, so the
entry is complete or the suite goes red. The 23 fields, verified against the live §11 table: id,
name, role, code, hiredOn, trainer, arch, specialty, salary, value, hourly, reportHrs, reportCost,
docs, classes, chunks, skill, situational, trainable, trainableBy, revenueModel, quip, color.
