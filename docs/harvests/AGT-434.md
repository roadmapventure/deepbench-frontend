## 2. The reversal would delete the north star — and the FK is what stops it

`public.reverse_decision(p_decision, p_actor, p_reason, p_actor_cycle)` (source read via `pg_get_functiondef`) walks every image under the decision, newest-first, and for an INSERT image (`row_data NULL`) executes `delete ... where pk = ...`. It has no table filter. Both `skill_profiles` and `capability_skill_profiles` are on its `k_allowed` list (SES-364). So a bare Reverse of `5b4f3dd2` would delete the 48 links AND the north star row — the opposite of "Do not change the text of the north star row".

Each row's write runs in its own sub-block: a schema refusal (an FK that still points at the row, SQLSTATE 23503) counts that row as `refused`, rolls back only its before-image, and the loop continues. Neither table has `updated_at`, so the written-since guard cannot fire and the outcome is `applied` with `restored_unverified 48, refused 1`. Because all 49 images share one `created_at`, the order in which the Skill row's delete is attempted is not determined — but the result is: if attempted before the link deletes, the 48 link FKs and the 11 pin FKs refuse it; if after, the 11 pin FKs refuse it. Hence the kickoff's T1 creates `agent_skill_pins.skill_profile_slug references skill_profiles(slug)` with no `on delete cascade` and inserts the 11 pins BEFORE T4's reversal. The FK is a structural guard (pattern:10/19), not an instruction.

`reverse_decision()`'s reason string will carry its `READ THE COUNTS, NOT THE OUTCOME` hint because `v_ref > 0` while `v_refw = 0`; the kickoff names this as expected so the Builder does not treat it as a failure.

## 3. Why a table, and why these grants

- Pattern:17 (extend what fits) was weighed against `knowledge_entries` (the agent-level taught items, `lib/read-taught.js`). Rejected: a taught item is agent-authored free text with its own framing section; the north star is a Skill row with a type, a `traits.source` and a slug that `buildSections()` already knows how to render. Pinning the Skill row keeps one edit of the row reaching every pinned agent on the next call, which the ticket requires.
- `reverse_decision()` k_allowed does not include the new table. The 11 pin INSERTs are still imaged (`row_data NULL`) under the T1 decision so that, once slice 2 widens `k_allowed` and `reversible_tables()`, a Reverse of the T1 decision deletes them; until then the captured migration down (drop table) is the undo, and `reverse_decision()` would report the 11 as `refused`. Widening a 300-line function was not going to fit the 3-file cap and is the first item of slice 2.
- Grants: `pg_default_acl` grants `anon`/`authenticated` `rm` (SELECT + MAINTAIN) on every new table (SES-384, `supabase-column-grants.md` addendum). The four sibling tables (`skill_profiles`, `capability_skill_profiles`, `agent_capability_assignments`, `knowledge_entries`) hold exactly `anon/authenticated SELECT` and nothing else — the Personnel page reads them with the anon key (`src/screens/PersonnelScreen.jsx:131`), and §19w says every piece of agent data is visible in DeepBench. So the pin table gets `REVOKE ALL` then an explicit `GRANT SELECT`, and the GATE asserts exactly 2 `role_table_grants` rows, both SELECT (both directions: readable, not writable).
- The pin read is placed AFTER `buildSignatureConfig()` because LOG-67 defines the signature as the primary capability's own config, agent-agnostic (`.claude/rules/ai-pattern-signature.md`: never an identity/behavior or agent-specific input in the signature). A pin is agent configuration. Today the 48 links DO sit in `assembled_skill_slugs`; after T4 they leave, restoring the pre-2026-10-09 signatures.
- `mergePinnedSkills()` skips a pin whose slug is already loaded, so during the window between T2 and T4 (links still present) nothing renders twice because of the pin; the capability-link duplicates in the agent-wide path end at T4.
