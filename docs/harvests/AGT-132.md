## 4. Designer decisions (JOHN-0925-DESIGNER-DECIDES; recorded here and in the STOP LINE, reversible with the ship decision)

1. **Routing is a table, not a CASE.** `finding_routes` with precedence tiers 10/20/30 (pattern:2, pattern:11, §19b). A new source is a row, never a migration of the function. Explicit source rows for the manager-picks tier, and no `('*','*')` row, so "an unmapped source stops" is a real refusal naming the source, not a silent fall-through.
2. **A group's route is the lowest precedence over its findings.** Root-cause grouping crosses sources by design; a group holding one security finding is a Security ticket, one holding an Auditor finding and a Ticket Owner finding is Auditor Enhancements. Alternative rejected: refusing mixed groups — it would force the manager to split one root cause into two tickets.
3. **The manager's pick is explicit.** `project` = a live `projects.slug` or the literal `general`; missing → refused. Alternative rejected: "omitted means general backlog" — an oversight would read as a choice (pattern:10). A slug whose project has ≠1 epic is refused rather than guessed; `governance-agents-ii` (no epic) and the multi-epic paused projects therefore cannot be picked today — the right direction, since project structure is John's.
4. **Rulings go into the Intent row, not `dm-guardrails`.** The ticket allows either; `ses-378d` pins `must` at 6 and the chain sentence is another capability's, so the review's own procedure row carries the standard and the routing (pattern:7, pattern:136 — Intent: procedure and output contract of this capability).
5. **A separate resolver function.** `finding_group_epic(jsonb)` rather than inline PL/pgSQL, so the routing is provable read-only over `rpc/` with live ids (the test's arm C) instead of only inside a rolled-back DO. EXECUTE is revoked from PUBLIC/anon/authenticated so the service key is the only caller, as for `apply_audit_review` (agt-86b arm A precedent).
6. **Grants:** SES-384 says a new table is born anon-readable; `finding_routes` holds no secret, so no column lockdown. DAT-18 says default write privileges are closed; the migration asserts it rather than assuming.
