## 2. Why each guard was classified as it was

- **ses-285 assertion 6 (`6-nothing-blocks-on-a-human`) — BOARD STATE.** `design_status='needs-john'`
  is written by no code under `api/`, `src/`, `shared/`, `lib/` or `scripts/` (grep, this cycle);
  the three files that mention the string only read it (`export-backlog-snapshot.js`,
  `check-session-docs.js`, `render-standing-brief.js`). A new `needs-john` row can therefore only
  come from a human hand or a migration, so the assertion can never catch a code regression. Its
  "measured before the work: 33 and 44" is the outcome of a one-time M6 migration, already
  achieved.
- **ses-373 assertion 1 — a DUPLICATE of the above**, and its own comment says so ("the same query
  ses-285 assertion 6 runs, so a pass here and a fail there is impossible by construction"). Two
  live queries for one property is the duplication the ticket names.
- **ses-281's `lane.length > 0` — BOARD STATE under B42.** B42 (live, `enforcement=script`): *"Let
  cycles run in parallel with no cycle-level mutex, coordinating only via atomic ticket claims…"*.
  An empty lane whose every admitted member is claimed is the ordinary steady state of a platform
  running 5–7 cycles. The assertion's own message already concedes the ambiguity ("either no
  project is executing or every in-scope ticket is unbuildable"), and only one of those two is a
  finding.
- **ses-285 assertion 7 (`7-nothing-evaporated`) and ses-373 assertions 2–3 — CODE/history, kept
  graded.** They grade a fixed set of historical rows (the M6 close-outs; the five ids SES-373
  backfilled) whose only way to change is a deletion. Those are invariants, not weather.

## 3. Why retarget rather than delete or flag

`docs/STANDARDS.md` Section 4 clause 1 is dispositive and was read this session, not recalled:
deleting, skipping, quarantining or `.skip`-ing a guard to get a suite green is forbidden; the
sanctioned move is *"fix the code, or fix the guard's assertion and say in the ship what changed
and why"*, citing `SES-197`'s *retargeted, not deleted*. So every change in the kickoff keeps the
assertion's id and changes its subject — the shape `ses-334` itself used when the re-rank moved
from a Vercel cron to `scripts/rank-backlog.js`.

**The `LIVE_BOARD=1` candidate the ticket offers was rejected.** The precedent exists
(`SES347_LIVE_REFUSAL=1` gates a real-money arm), but that flag guards *spend*, not *meaning*. A
flag the verifier never sets makes the assertion permanently dark, which is the ticket's own
"skipped is not green" complaint pointed the other way. The brief makes the same number a reading
that someone actually sees, which is what the ticket asks for.

**Why the monitor needs a new block at all.** Half the signal already has a home: the brief's
`design_status`-among-open table prints the `needs-john` count with its selection effect
(`scripts/render-standing-brief.js:983`). The other half has none — `Open decisions` renders
`runner_decisions`, not `runner_items`, and `docs/backlog/BACKLOG-SNAPSHOT.md` carries no card
rows. `renderHumanGates` puts both counts in one place so ses-285's retargeted assertion has a
single artifact to grade.

## 4. Why half (b) is plumbing, not a bug in `tokensFrom`

`tokensFrom()` is correct and stays untouched: it returns `null` (never `0`) when nothing was
reported, which is SES-147's distinction and worth keeping. The hole is upstream — it reads
`input_tokens`/`output_tokens` off the **answer JSON**, and `pz-rank-intent`'s schema has no such
properties, so the pair is structurally always absent. Passing the Agent tool's own reported usage
in on the command line is the smallest change that makes the row measured, and it keeps the
"unreported stays NULL" rule intact for the case where the runner has no usage figure to hand.

A malformed `--input-tokens` must refuse (exit 2) rather than degrade to `null`: a silent
degradation re-creates exactly the invisible hole this half exists to close.

## 5. Scope this design deliberately does not take

- Relaxing the verifier's fail-closed rule — out of scope by the ticket's own words, and correct.
- Re-pointing ses-334 (d) at `ai_activity_log` instead of `runner_cycles`. It would also measure
  the run, but it changes what the guard is about; the cycle row is the artifact the ship reads.
- Auditing the other 51 tests that declare not-run parts for the same board-vs-code confusion. That
  is a real sweep and a separate ticket if anyone wants it; nothing measured this session suggests
  it is urgent, because only these four were implicated in the four verdicts the ticket recorded.

## 6. What the build cannot prove this cycle

The first *measured* `est_tokens_dev` lands on the next cycle's step 4c, not this one — the ticket
says so itself ("so the row is measured from the next cycle on"). The dry-run QA in the kickoff
proves the plumbing end to end without waiting; a NULL row after this ship is not evidence the fix
failed, and the ship must not claim the reverse.
