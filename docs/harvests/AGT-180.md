## 2. Why this is not SES-019's forbidden move

The denied action was the engine's `--apply` **bundle**: read the anchors, insert a decision, image rows, insert/patch a card. Re-issuing that bundle from PowerShell, from a different node entrypoint, or under a flag renamed to dodge the matcher is routing around the deny, and it stays out of bounds however the deny was reasoned.

What this design does instead: the engine stops being a writer on this path and becomes what its own header already claims — the pure assessor — and hands the ledger write back as **data**. The cycle then performs it with `record_decision()` through the Supabase tool it already holds and already uses for every other decision it records in a cycle. Nothing about *who decided*, *what is written*, or *under which cycle id* changes; only which process issues the INSERT, and it is the process the platform's own §19v ledger path names. `pattern:17` (extend a structure that fits), `pattern:8` (narrowest layer), `pattern:9` (no model where a deterministic mechanism serves).

§19v's *no before-image logged → the write does not happen* does not bite: this is an INSERT of a new `runner_decisions` row, which has no prior state. That is why the engine's own card-only branch images nothing either, while `--settle` images the card row it **patches**.

## 3. Alternatives considered and rejected

- **Write the hold on the no-apply path inside the script.** Cheapest of all, and it is the forbidden move wearing a different spelling: the same process performing the same insert under a command spelled to pass the classifier. Rejected on SES-019 grounds, not on taste.
- **Narrow the classifier rule that produced `[Modify Shared Resources]`.** Rejected on evidence: the same command was denied for `[Blind Apply]` two hours earlier. A fix keyed to one reason string would leave the other live, and it also widens a shared harness (`pattern:8`).
- **Edit `docs/runbooks/runner-cycle.md:1590` to stop printing `--apply`.** Correct in spirit, unaffordable here: any byte change to that file forces `docs/runbooks/cycle-card.md` re-rendered in the same commit (`SES-377`, its header carries the runbook's sha256) and `BYTES_AT_SHIP` re-pinned in `tests/regression/ses-413d-questions-scoreboard.test.mjs` (`ses-424f` asserts the pair agrees) — three files of a three-file cap, with nothing left for the engine or the guard. `docs/SESSIONS.md:44` records this exact chain being paid for once already. It is also not load-bearing: the engine's output now instructs its caller at the moment of use, and a permitted `--apply` still writes the row itself, so both paths record the hold. Filed as its own row.
- **A new flag (`--emit-hold`).** Rejected under `pattern:67` — a knob that must justify itself against a bound that already exists. The no-apply path has exactly one honest thing to say about a card-only outcome; say it always.
- **Also record `action: none`.** Rejected and named in the STOP LINE so a later cycle does not "finish" it: `none` means *not this machine's to undo*, there is no hold to hold, and filing one per unattributable red would have written 8 rows in the last day alone for decisions that declined to decide. Its own row, with this measurement.

## 4. The 2026-09-26 backfill — OUT OF SCOPE, and why plainly

I read `d60e404b` in full before deciding, which is what made the answer clear.

- **It is not one hold.** 2026-09-26 carried **26** reds, not "the missing hold". The ticket's singular is wrong about the live count (`pattern:89` — surface it rather than implement the wrong string).
- **The form cannot be honestly reproduced.** `d60e404b`'s `reasoning` interpolates the attributing cycle id and the range-span verdict **as they stood at that minute**. The green anchor has not moved since 2026-09-16, so that clause is stable — but the attribution depends on which cycle claimed the sha at the time, and the range span on a `git rev-list` nobody ran. Reconstructing 26 of those and writing them as decisions the machine made is fabrication in the ledger that also carries the 72-hour reversal handle. `pattern:32`: attribute a fact from what the call actually did, never from declared configuration. No call was made.
- **It is a data write about a day this cycle did not observe.** `pattern:157` keeps a dated remediation scoped to its dates; it does not license inventing the dated rows themselves.
- **It would not fit anyway.** 26 rows, each needing its own before-image reasoning and its own attribution read, inside a 4-task cap whose whole point is the forward fix.

Honest cost of saying no: 2026-09-26's reds stay unrecorded for ever. That is a real loss and it is smaller than 26 invented decisions. The forward fix is what stops tomorrow's from joining them.
