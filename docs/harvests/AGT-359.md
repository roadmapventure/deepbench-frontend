## Why this is small, and what makes it fit

The handler is already right; only the published description is behind. So no `api/` file changes. Two new files: one script that holds the contract and writes it, one test that pins the handler's return line to it. 2 files / 4 tasks against caps of 3 / 4. Not a cap case, and nothing was shaved from the ticket's own sentences to get there (see "What I cut" for what I removed of my own additions).

## Decisions (mine, reversible)

- **D1 -- three rows, not one.** The ticket's text names `agent-bundle-intent`. One handler serves all three Intents, so fixing one leaves two tools publishing the same wrong contract -- the ticket's own argument about `capabilities` ("fixing two of the three would leave the contract wrong") applied to rows. Same script, same decision handle, no extra file or task. The live test asserts EVERY row with that handler, so a fourth row added later is covered.
- **D2 -- `knowledge_entries` stays.** It is a `required` key of the published contract, `scripts/pull-scaffold.mjs:124` and `agt-162`'s live arm read it, and the audit row counts it. Retiring it is a breaking handler change the contract does not need in order to be true. The schema now says what it is: an index, never the text, kept and not retired.
- **D3 -- no `additionalProperties: false`.** MCP clients validate `structuredContent` against `outputSchema`. A strict schema would turn the next undeclared key from a harmless extra into a client refusing the whole bundle, in the window between a handler deploy and a row write. "A key the handler does not return is still rejected" is carried by the test: `contractGap()` names an undeclared returned key AND a declared key nobody returns.
- **D4 -- `output_desc` in the same write.** It enumerates the output keys and omits the same three; it reaches clients inside `capabilities[].skills[]`. `method` is left: its sentence is not false.
- **D5 -- types only where the code computes the value** (`text`, `chars`, `always`, `framing`, `kind`, the arrays). Database columns (`title`, `description`, a Skill's text fields) get key presence only, so a NULL column can never make a client refuse a bundle. `capabilities[].description` is NULL-able by `lib/skill-write.js` (`description: fields.description ?? null`).
- The three new keys join `required`: the handler returns them unconditionally. `output_formats` and `no_inference` stay optional as they were (not this ticket).
