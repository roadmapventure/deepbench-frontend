## The live regression arm, and why it lands nothing
The ticket asks for an arm that posts a follow-up finding against the live table. The table refuses every DELETE (`audit_findings_guard()`), `Prefer: tx=rollback` is not honoured on this project (agt-280, agt-273, agt-450 all probed it), and the suite runs many times a day, so a landed row would be a permanent junk finding per run in the manager's worklist. The arm instead aims a complete follow-up row at an existing `(fingerprint, iso_week)` pair: BEFORE triggers run, then NOT NULL and CHECK constraints, then the unique index -- so a row that clears every required column is refused `23505` and one that misses a column is refused `23502`. Both directions, zero rows. A NOT NULL column added later turns the first answer into `23502` and the test red. Precedent for refused live POSTs: `agt-131-findings-intake.test.mjs` arm D.
Constraints read live: `audit_findings_fingerprint_iso_week_key UNIQUE (fingerprint, iso_week)`; CHECKs on confidence, finding_type, kind (`other` allowed), iso_week form, locations array, status, family. Triggers: `audit_findings_family` (BEFORE INSERT), `audit_findings_guard` (BEFORE INSERT/UPDATE/DELETE), `audit_findings_gap_to_designer` (AFTER INSERT, gap + cycle_id only -- never reached by a refused row).
NOT measured by me: the `409 23505` answer itself -- I was held to no writes, so I did not send the POST. The `23502` half is measured 19 times in the reasoning rows. The Builder's first credentialed run of T1 measures the other half; the STOP LINE says what to do if it is not `409`.
