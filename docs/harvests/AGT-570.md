## C. The call I made, and the reading I did not take

**D1 — the held stage runs now, once.** The only unbuilt act is applying `agt570_own_row_exemption`. A build containing that act was refused at the Builder launch twice: 2026-11-06 (the v7.0.964 design, a new signature plus a dropped overload) and 2026-11-13 12:11Z (ledger attempt 1, a guarded in-place replace bundled with the driver change, the test and the push). Ledger attempt 2 (`922fd8e1`, "differs: staging", still `open`) shipped the inert half and held the gate replacement out "as its own guarded step". That step has never been sent.

Why I design it rather than name it blocked a second time:

1. John's standing decision 6e94edcb gives the team two redesign attempts, the second different from the first, and then asks for data on why it was blocked. The ledger encodes that: `open_redesign_attempt()` refuses a third attempt, and `close_refusal_diagnostic()` refuses to run before a second refusal. Today AGT-570 has one recorded redesign refusal and an open second attempt whose risky stage was never tried — so it can neither be redesigned again nor diagnosed. Every cycle that reaches it re-discovers this (b1fa88ed did on 2026-11-15; this cycle did today), and the 2026-11-13 gate card was ruled back into the queue with "not needs-desktop". Running attempt 2's own held stage is the one move the ledger still allows, and both of its outcomes end the loop: applied, the fix is live; refused, `--refuse` lands on attempt 2, `--diagnose` becomes legal, John gets the data he asked for and the ticket parks for good.
2. The difference from attempt 1 is the one recorded on 2026-11-13 before the stage was held, for an engineering reason: the sender has now been live and inert for three days (measured again today: same answer with the header as without), so this step carries nothing else — no code change the gate depends on, no deploy — and its captured down alone undoes it.
3. It is not routed around anything. Same path every migration build uses (capture the down, then `apply_migration`), stated in plain words at the top of the kickoff, with the instruction that a refusal is final. Two unattended cycles applied function migrations through that path since the refusal — AGT-291 on 2026-11-14 replaced this very gate's body, AGT-495 on 2026-11-15 replaced `drain_epic_next` — so "an unattended build may not replace the boot gate" is not what the two refusals show.
