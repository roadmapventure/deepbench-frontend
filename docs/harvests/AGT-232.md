## 3. Why the card re-pin is in scope when the Skill rows are not

The card (`docs/runbooks/cycle-card.md`) carries the runbook's sha256 on line 1, so any runbook byte moves it. `scripts/render-cycle-card.js writeGate()` refuses a changed `--write` without `--cycle-id` and `--ticket`, and on success re-pins `skill_profiles.dm-knowledge-cycle-card` (`method`, `traits.source_sha256`) in the same run under one `agent-row` decision with a full-row before-image.

That write is an agent Knowledge row, and the 2026-09-28 skip treated it as needing an attended session. The live rule says otherwise: `governance_rules.MANAGER-AUTHORITY-MATRIX` row 1 (status live, updated 2026-09-20) — "the Builder re-pins skill_profiles.dm-knowledge-cycle-card … under the ticket whose edit moved the card … the manager's, never a card, never John's." `AGT-96`, which argued the two rules conflict, was removed on 2026-09-29 because the re-pin already writes the decision row. Recent re-pins under `victoria-placed` tickets: `b6577905` (AGT-538, 2026-11-11), `f9c18fb2` and `7fc95a2a` (AGT-595, 2026-11-08), none reversed. The Manager's ruling `a05deb8e` also names this re-pin as part of the waived build.

The difference from the gated half is kind, not degree: the re-pin copies a generated view of a document into the row that mirrors it; the gated rows change what the manager is told to do.

One caution carried into the kickoff: `node scripts/render-cycle-card.js --sync-knowledge` was declined by the platform's safety check earlier in this cycle and I did not run it or any variant. The pin was read by SQL (`4c9dc49877aa1826`). The build's `--write` reaches the same re-pin code, so an unattended Builder may be refused at T2. The kickoff tells it not to retry or route around, to restore the runbook, push nothing and record the refusal with `redesign-pickup.js --refuse`.
