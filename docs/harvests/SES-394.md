## The environment constraint and how the design routes around it

Register B39 (`docs/runbooks/runner-cycle.md:236`, rule row `B39` in the snapshot) forbids an unattended cycle from entering the `.claude/` write gate. The ticket's part (1) names `.claude/rules/agent-roster-inert.md` directly, so that half cannot ship here.

I checked whether `.claude/rules/*.md` is *rendered* rather than hand-written, because that would have let the cycle ship the text by writing a registry row alone: it is not. `scripts/render-rule-blocks.js` walks the whole worktree (`listMarkdown()` from `WORKTREE`, excluding only `node_modules`, `.git`, the two snapshots, `docs/backlog/BACKLOG-SNAPSHOT.md`, `docs/SESSIONS-ARCHIVE-*` and `docs/kickoffs/`), so `.claude/` IS in scan scope — but `grep -rn "{{rule:" .claude/rules/` returns **zero matches**: no rule file carries a marker today, and the renderer only ever *verifies or repairs a block that is already committed under a marker*. It cannot create the file's prose.

So the design splits the rule's two homes:

- The **registry row** and the **byte-pinned rendered block** land in `docs/ARCHITECTURE.md` §19v, which this cycle may write. That satisfies the ticket's "the byte-pinned rule block matches the registry row" QA without a `.claude/` write.
- The **`.claude/rules/` prose** is handed to an attended session as a `runner_card_asks` row carrying the exact replacement bullets *and* the marker, so the attended session pastes rather than re-derives.

`canonical_doc` is still `.claude/rules/agent-roster-inert.md`: the file exists, so check 10's pointer resolution passes with no anchor to go stale, and the rule's authoritative home is named honestly even before the card is applied.

## The self-reference, and why it is not circular

Task 5 edits an ACTIVE agent's `skill_profiles` row — the very act the un-shipped rule would authorise. The authority I leaned on is **not** the rule: it is John's decision `38a1c566`, which names `SES-394` and names guardrail edits explicitly. The kickoff says so in CONTEXT so the build does not cite its own output as its permission.

One fact the build must not lose (`docs/runbooks/runner-cycle.md:4563`): `reverse_decision()`'s allowlist is `backlog_items, runner_directives, runner_drain_scope, runner_settings, governance_rules, epics, vision_claims` — **`skill_profiles` is not on it**. The before-image is written and readable, but a Reverse reports `refused`. The registry row (task 1) IS auto-reversible; the guardrail edit (task 5) is not, and the ship report should not imply otherwise.

## Alternatives considered and dropped

1. **Amend `docs/runbooks/runner-cycle.md` too.** Dropped: grep shows the runbook carries no carding instruction for agent seeds (only the allowlist warning at 4563). The gate lives in the rule file and §19v and is applied by judgment, so a runbook edit would be a fourth file changing nothing.
2. **Extend `scripts/check-session-docs.js` instead of a new script.** Dropped: that file's checks read the snapshot and grade docs; a ticket-scoped `create`/`edit-active`/`activate` verdict is not a doc check, and folding it in would make the discriminating test assert through 1,400 lines of unrelated harness.
3. **Make the gate a Postgres function.** Dropped as more than the claim needs: the consumer is a Builder reading its guardrails and, at QA, a CLI. A JS helper plus CLI is testable at both ends with no migration to reverse.
4. **Ship the `.claude/` text as a `docs/` mirror file.** Dropped: two homes for one rule is exactly the drift `render-rule-blocks.js` exists to stop.
