## 2. Governing architecture and the shape chosen

- §19b: Victoria's turn is assembled by `assemblePrompt()` only; the Knowledge row is DATA (`skill_profiles`, `traits.source = inline`, SES-341) linked to the capability, never prompt text in a script. The intent `vc-requirement-intent`'s method step 2 already scores 5 when "the cited row asks for exactly this and the platform is blocked without it"; the Knowledge row gives her the class test to apply to the cited row.
- §19d/§19e Rule #1: nothing names another agent in data; the manager's group carries a `need_source` and a `home`, not Victoria.
- §19k: the seven turns are logged by the executor path (`agent-log.js`), one `ai_activity_log` row each.
- §19v Operations: AGT-240 (locked lists), AGT-264 (`accepts_findings`), AGT-280 slices 1–2 (`requirement_gate`, `apply_requirement_verdict`, the `requirement-check` door), AGT-281 (the list door). The class path is built ENTIRELY out of these: no new function, no new table, no new capability.

Why this shape and not the ticket's literal (b): the ticket asks `apply_audit_review()` to let a root-cause group "enter the appropriate executing project". John's addendum (decision `6a24f412`) requires Victoria's verdict BEFORE the ticket enters, and a SQL function cannot make a model call. So the filing stays exactly as today (the routed planned list), the manager's group only DECLARES the claim (`need_source` + `home`), and the move is owned by the one writer that already records her verdict: `apply_requirement_verdict()` on `pass` with `home_project`. The two existing triggers fire on that UPDATE, so AGT-240's lock and AGT-280's traceability keep their sentences unchanged (pattern:8, pattern:17, pattern:19).

Why `requirement_gate()` gains a clause: "no path moves a discovered ticket into an executing project without a requirement-check decision on that ticket" is a structural invariant, so it lives in the trigger that already guards the move, reading the decision ledger rather than a column anyone can write (pattern:10). Decision `35980d96` is the counter-example that motivated it: a traceable source written by hand, no verdict, ticket moved.

## H6 — `scripts/audit-review.js` exact strings (T4)

- Shape check on `need_source`: `/^[a-z]+:[a-z_]+:[^:]+$/` (the `who:table:id` text; traceability stays the function's and `requirement-check.js --prepare`'s).
- Refusal 1 (`need_source` present, `home` blank): `a root-cause group citing need_source needs home (an executing projects.slug that accepts findings)`
- Refusal 2 (`home` present and `need_source` blank or malformed): `home needs need_source (the text who:table:id)`
- Refusal 3 (`home` names no context `projects` row with `status === "executing" && accepts_findings === true`): `` `home ${slug} is not an executing project that accepts findings (AGT-240)` ``
- Both keys apply only to `kind === "root-cause"` (filing or reuse); on any other kind either key is refused with: `need_source/home apply only to a root-cause group`
- `--apply` prints, after the `Counts:` line, one line per group carrying both keys, pairing the i-th FILING group (root-cause without `reuse_backlog_id`, or cleanup, in group order — the order `apply_audit_review()` appends to `tickets`) with `tickets[i]`, and a reuse group with its `reuse_backlog_id`:
  `next: node scripts/requirement-check.js --prepare --ticket=<id> --source=<need_source> --home=<home>`
