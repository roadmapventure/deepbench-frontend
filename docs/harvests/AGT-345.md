## The repair path: automatic, not a flag

Chosen: `reembedOnEdit` treats a stored null embedding as "needs embedding" on any PATCH that carries a title or content.

Why:
- It removes the stuck state rather than adding a tool to get out of it (pattern:1). The Training tab's edit form sends the title on every save, so a trainer who opens and saves any such item repairs it without knowing there was a problem.
- One file. `api/load-entries.js` is untouched, so the route's request shape does not grow a `reembed` key that only an operator would ever send (pattern:8, pattern:17).
- It goes through `embedEntryText`, so the one `knowledge-write` log is written exactly as on a save.

Rejected:
- An explicit `reembed: true` flag on PATCH: a second file, a new request field, and the stuck state stays stuck for every row nobody thinks to flag.
- Having the check script write the embedding itself: a second writer of `knowledge_entries.embedding` outside the trainer write path, unlogged - the same shape as the write that caused this row.
- Embedding on a PATCH that carries no text (a status toggle): the toggle would start reading the row and could spend an embedding call; AGT-343 pinned the toggle as zero reads.

The cost, stated: the row read now selects `embedding`, so each text-carrying edit pulls one stored vector (about 19 KB as text) that it previously did not. Edits are typed by a person; this is not a hot path. A filter-only second read (`embedding=is.null&select=id`) would avoid the payload but adds a request to every unchanged-text edit and would break `agt-343` arm (g), which pins exactly one row read.

Why `!== null` and not a falsy test: PostgREST always returns a selected column, null when the value is null. `agt-343`'s stub rows carry no `embedding` key at all (undefined). A falsy test would make arm (g) of that file embed and go red, and that file is outside this ticket's three. `!== null` is both the accurate reading of the wire and the one that leaves `agt-343` untouched and green.

## The check: where it lives, what runs it

Chosen: `scripts/check-taught-embeddings.js` (the same family as `scripts/check-agent-names-in-data.js`, which sweeps live data and exits 0 / 1 / 2), with its logic in an exported `sweep()` that takes its fetch as an argument; and one regression test whose offline arms grade the logic and whose live arm runs the real sweep.

What runs it: `tests/regression/run-all.js` discovers tests by reading the directory, so the new test's live arm runs on every credentialed suite run with no manifest edit - the same arrangement as `SES-51-agent-names-in-data.js` over its script. By hand: `node scripts/check-taught-embeddings.js`.

Why not the alternatives:
- A database trigger or NOT NULL on `embedding`: `source = 'agent'` writers and the upsert path would need review, and a constraint refuses the write rather than reporting it - a different ticket, and it needs a migration. Worth a finding for the Development Manager if direct writes recur.
- The database-health watch (`scripts/db-health-watch.js`): it watches one signal on a schedule from a workflow file John copies to main; adding a second signal there is a workflow change this session cannot push.
- The Auditor's playbook: a fourth file, and a daily cadence for something the suite sees on every run.

pattern:162 (a check grades the change, never the live world) and how this design answers it: the arms that grade THIS change are offline (a-f). The live arm (g) declares NOT RUN without credentials or when the table cannot be read, and its failure text says "live data, not this build" and names the row and the one-request repair, so a future builder who meets it red knows it is not their change. The known window: between this build's push and the parent's repair request, arm (g) is red for any credentialed suite run. That is the check doing what the ticket asks ("red today on Brittany's row").

Scope of the check: active `source = 'user'` rows. `source = 'agent'` rows are written by one code path and all 26 have an embedding; a disabled item is not searched.

The second read (`select=id` over all active user rows) exists so the green line says how many items it looked at - a pass over zero rows reads differently from a pass over eleven.
