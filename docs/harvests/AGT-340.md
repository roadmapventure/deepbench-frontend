## 2. Feasibility (the ticket said it was never checked)

- `/api/mcp/<id>` -> `visibleRows()` narrows to the rows that agent HOLDS; every private agent holds `<id>-knowledge` (`lib/private-agent-create.js:136-141`, `default_intent_slug: "agent-bundle-intent"`), whose Intent row names handler `agent-bundle`; `tools/call` on a deterministic row goes to `runDeterministic()` -> `DETERMINISTIC_HANDLERS['agent-bundle']` with `content = task_context` (`api/_lib/mcp.js:851-879`). So the lookup is reachable on the agent address and the team address today as a new optional input on that tool.
- `toTool()` publishes `traits.input_schema.properties` / `required` as the tool's `task_context` schema and leaves extra keys open (`mcp.js:544-583`); `validateToolInput()` checks only `required` (`mcp.js:519-542`). An optional `topic` therefore needs exactly one data edit (the two Intent rows) and no `mcp.js` change; without the edit the tool works but no AI client would know the input exists, which is why the migration is in scope.
- `lib/rag.js` `queryRAG({ queryText, agentId, tenantId, scope: 'agent' })` embeds with `text-embedding-3-small`, logs its own row BEFORE the RPC (`ai_type 'similarity'`, `feature 'knowledge-retrieval'`, model, `input_tokens` from `usage.total_tokens`, `patterns_used ['rag','embeddings']`, `call_facts.retrieval_method 'similarity-search'`, `agentId` = the target), then POSTs `rpc/match_knowledge` with `{ query_embedding, match_threshold: 0.3, match_count: 5, p_tenant_id, p_agent_id }` and returns `chunks: [{ id, title, similarity, agent_id }]` -- the ids are `knowledge_entries.id`, the same ids `readTaught()` returns. Through `runWithCallSource('mcp', ...)` the row carries `call_source 'mcp'`. This is the ticket's "first MCP path with a model and tokens".

- `OPENAI_API_KEY` is absent in the cloud clone (present on Vercel, where `lib/knowledge-write.js` already embeds). The real embedding path cannot be exercised by this cycle's tests; T1 stubs OpenAI and the RPC as agt-390's recorder does.

## 3. Alternatives considered

- A third capability per agent (`<id>-lookup`, new Intent, new handler file): needs `mcp.js`, the handler, `lib/private-agent-create.js`, a migration for the existing agents and the test -- over the cap with no rung, and new agents would lack the tool until a second slice (pattern:163). Rejected.
- `embedAndSearch()` (`lib/vector-search.js`) called directly, logging one row from the handler: duplicates `queryRAG`'s logging (pattern:14) and leaves the path the ticket names. Rejected.
- A new `lookup` key in the return (topic echoed, match count): `.claude/rules/agent-data-visibility.md` forbids a scaffold key the Personnel page does not show. Rejected; the framing sentences carry the narrowing instead.
- Storing the asked topic in `call_facts`: §19k forbids free text there (LOG-91), and `ai_activity_log` has no text column, so any storage is a schema addition AND a customer-data decision. Not designed; gated (§8).
- Keeping the narrowing in `lib/read-taught.js` (the first assembly's shape): it costs a fourth file once the migration mirror is counted (`docs/design/*.sql` is where every migration's bytes live -- `agt-434`, `agt-433`, `agt-390`, `agt-338-own-knowledge`), and the cap is 3 with no rung. The handler already composes the two objects from `kn`, and it is the only caller that ever narrows, so `narrowKnowledge()` lives beside `bundleTarget()` as a pure export. `lib/read-taught.js` keeps "the two framing sentences live here" true for the whole-package case.

## 4. Designer calls (JOHN-0925-DESIGNER-DECIDES; reversible; recorded here and in the STOP LINE)

1. One tool, not two: the Knowledge tool takes an optional `topic`. Without it the handover is byte-identical to today, so "whether the whole-package hand-over stays" is answered yes.
2. A topic returns the same package shape with `taught`, `records` and `knowledge_entries` narrowed to the matches; the framing sentences say the list is narrowed and, when nothing matched, say so (pattern:34/113).
3. `queryRAG` defaults kept (`match_count 5`, threshold 0.3) -- no new knob (pattern:67).
4. The lookup's facts reuse the two existing §19k signature keys, `retrieval_method` and `retrieved_chunk_ids` (`lib/pattern-vocabulary.js:40-41`; LOG-37c convention: method present with no ids = searched, found nothing). A lookup row therefore has a different signature from a handover row, and most-used lessons / no-match count / lookups per connection are derivable from rows alone.
5. No topic text is stored anywhere -- the cautious default while John's answer is pending (pattern:156) and the status quo.
6. A missing `OPENAI_API_KEY` is refused with a clear error rather than presenting as "nothing matched".
7. The narrowing lives in the handler, not the shared reader (§3, last bullet) -- forced by the file cap once the mirror is counted; a later ticket may lift it into `lib/read-taught.js` if a second caller appears.
8. The Intent-row edit is build work under AGENT-ROW-AGREED-TICKET (gate verdict `build`), recorded as a `kind 'agent-row'` decision with a `to_jsonb(sp)` before-image per row, the AGT-391/AGT-434 form; `skill_profiles` is in `reversible_tables()`, so `reverse_decision()` restores both rows.

-- The Knowledge tool's two Intent rows gain the optional input `topic`. Data only, no DDL; rolls
-- back unless the trailing GATE passes. Down: reverse_decision(<the decision the NOTICE prints>).

  k_slugs constant text[] := array['agent-bundle-intent', 'agent-bundle-any-intent'];
  v_dec uuid;

  v_dec := public.record_decision(
    k_cycle, null, 'agent-row', 'AGT-340',

  select k_cycle, null, 'skill_profiles', sp.id::text, to_jsonb(sp), v_dec
    from public.skill_profiles sp
   where sp.slug = any(k_slugs);
  get diagnostics n = row_count;
  if n <> 2 then raise exception 'AGT-340: imaged % Intent rows, expected 2', n; end if;

  select count(*) into n
    from public.skill_profiles
   where slug = any(k_slugs)
     and traits->'input_schema'->'properties'->'topic'->>'type' = 'string'
     and traits->'input_schema'->'properties' ? 'agent_id'
     and traits->>'handler' = 'agent-bundle'
     and traits->'input_schema'->'required' = (case slug when 'agent-bundle-any-intent' then '["agent_id"]'::jsonb else '[]'::jsonb end);
