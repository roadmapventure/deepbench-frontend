## 2. What the probes WOULD write, read off the deployed function bodies -- the key per count

The rule the kickoff applies (pattern:162): a count is scoped to the rows the probe's own write would create or touch, never to a table. Keys were derived from the function bodies and then checked live (PostgREST, service key, `Prefer: count=exact`, `Range: 0-0`, 12:35Z); every key below reads `*/0`.

**ses-399** -- `attach_before_images(NIL, '{}')`: its only write is `UPDATE runner_before_images SET decision_id = p_decision`, never a `runner_decisions` row. Keys: images `decision_id=eq.${NIL}`, decisions `id=eq.${NIL}` (slice 34 §3's proven edit, unchanged).

**ses-315** -- `record_ship_decision(NIL, 'SES-999', ..., NIL)` inserts a `kind='ship'` decision with `cycle_id = p_cycle_id` and `backlog_id = p_backlog_id`, and adopts the cycle's images (`UPDATE runner_before_images ... WHERE cycle_id = p_cycle_id`, SES-399 kickoff §); `reverse_decision(NIL, '', ...)` writes a `kind='reversal'` row with `reverses = p_decision`, before-images under the reversal's own id, and a `runner_directives` row `type 'directive', status 'queued', body 'REVERT-FORWARD REQUESTED: <ticket> <version> <sha> -- reversal <id>'` (SES-315 kickoff §2 item 2, SES-353 kickoff); `apply_ladder_decision(NIL, NIL)` writes under `cycle_id = p_cycle_id`. Keys: decisions `or=(id.eq.NIL,reverses.eq.NIL,cycle_id.eq.NIL)`; shipDecisions `kind=eq.ship&backlog_id=eq.SES-999`; images `or=(decision_id.eq.NIL,cycle_id.eq.NIL)`; directives `body=like.REVERT-FORWARD*&created_at=gte.${t0}` with `t0` taken just before `before`.
- **Deviation from the ruling's illustrative key `ticket_ref=eq.SES-999`, recorded:** live, `runner_directives.ticket_ref` and `item_ref` are `uuid` (`?ticket_ref=eq.SES-999` -> HTTP 400 `22P02 invalid input syntax for type uuid`), and `reverse_decision()`'s insert sets neither (SES-353 kickoff: "no `item_ref`"). The directive's only probe-specific content is the body's `reversal <id>`, an id that does not exist until the write happens, so the honest key is the body prefix bounded to the probe window. Live: 0 `REVERT-FORWARD*` directives exist at all among 111 rows; 8 directives since 2026-10-01. The residual exposure (a peer reversing a ship inside the ~2 s window) is strictly smaller than the whole-table read it replaces, and the reversal row itself is caught by `reverses.eq.NIL` regardless.

**ses-320** -- `sweep_decision_windows(null, 'ses-320-guard-probe')` writes only inside its loop over expired open decisions: for each, a `runner_before_images` row `(cycle_id, session_name, 'runner_decisions', ...)` with `session_name = p_actor_session`, then `UPDATE runner_decisions SET status='final'`, and for a `kind='ship'` row a second image `(..., 'backlog_items', ..., decision_id = r.id)` then `UPDATE backlog_items SET status='done'` (SES-320 kickoff §1; `docs/design/agt-423-sweep-fault-isolation.sql` :94-96, :135-137 carry the same shape). The UPDATEs move no count and carry no probe key; the images carry the probe's `session_name`. `reverse_decision(NIL, '', ...)` as above. Keys: decisions `or=(id.eq.NIL,reverses.eq.NIL)`; finalDecisions = images `session_name=eq.ses-320-guard-probe&table_name=eq.runner_decisions`; images `or=(decision_id.eq.NIL,session_name.eq.ses-320-guard-probe)`; delivered = images `session_name=eq.ses-320-guard-probe&table_name=eq.backlog_items`.
- **Deviation from the ruling's words "ses-320's delivered counts ... scoped to the probe's own key", recorded:** `backlog_items` has no column the sweep probe owns -- the only ticket it could close is one behind an expired ship decision, and `expired` is already read first. The before-image the sweep takes of every row it finalises or closes IS the probe-keyed record of that write, so the two counts read `runner_before_images` under the probe's session. The object keys `finalDecisions` / `delivered` keep their names so the `MOVED THE LEDGER` assert and its message stay byte-identical; the reason comment says what they now read.

Why `reverses.eq.NIL` and not only `id.eq.NIL`: a reversal is a `runner_decisions` row pointing at the original (`ses-286a` :736-752 asserts exactly this; live, `reverses=not.is.null` rows exist), so a `reverse_decision(NIL)` that got past its blank-actor guard would show up there, not as a row with id NIL.

## 3. Teeth: query flips, not inserted rows -- the one place this design departs from the ruling's discriminator wording

The ruling's discriminator says "a row inserted under the key reds the precondition with its own message". Measured live through PostgREST embedding (read-only): `runner_before_images?select=id,runner_decisions!decision_id(id)` and `...,runner_cycles!cycle_id(id)` both resolve, and `runner_decisions?select=id,runner_cycles!cycle_id(id)` resolves -- so `decision_id` and `cycle_id` are foreign keys, and no row can be inserted under NIL on either (no NIL decision, no NIL cycle exist: `*/0` both). The only insertable key is ses-320's text `session_name`. An inserted tooth row also has a failure mode this ticket exists to end: if its DELETE were refused or forgotten, that one row would red the precondition in every future run of that home. So each tooth is a query flip on the built tree -- the slice-34 form, proven there and again here -- which writes nothing and reds the precondition with the same message an inserted row would produce. Reversible call; if the Manager wants the insert form for ses-320, it is `POST runner_before_images {session_name:'ses-320-guard-probe', table_name:'backlog_items', pk_value:'tooth', row_data:{}}` then DELETE by the returned id.
