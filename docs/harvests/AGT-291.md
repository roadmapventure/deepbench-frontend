The rule has a sensor-shaped function but (a) the predicate counts `delivered` as unfinished, so a project whose every ticket is built and waiting on John's dev→main release never reads finished; (b) `paused` is excluded, so AE can never finish; (c) nothing reads the predicate automatically — neither the hourly boot nor every cycle's tail.

## 2. Why `delivered` counts as built (D1)

`delivered` = built, pushed to `dev`, verifier-verdicted; it becomes `done` only on John's release gate (`settle-ship.js` / AGT-245 regrade). John keeps releasing dev→main for himself (John 2026-09-25), so a finish line that waits on `done` waits on John, inverting his 2026-09-27 rule ("once a project is finished … propose … then I decide"). The ticket's own measurement ("0 open and 0 partial tickets", leverage_reason) names the predicate: LEFT = `open` + `partial`. `removal proposed` is excluded from LEFT deliberately — it is a decision pending, not build work; a refused removal reopens into a finished batch harmlessly (finished_at stays set, the batch is never due again).

AGT-240's own DO asserted the inverse ("1 delivered row → NOT due"); the new DO asserts "1 delivered row → due", which is the discriminator against origin/dev.

## 3. Why `paused` can finish (D2)

A perpetual project's finish sends it to `paused` with `epics.finished_at` set (AGT-240 D6), so `finished_at IS NULL` already separates "paused because finished" from "paused by John". Only AE qualifies today (other paused projects' epics are unlocked or have left > 0).

## 4. The sensor and the trigger (D3)

- `review_due` = `proposal_due AND FRESH` is the only new column; `proposal_due` keeps its meaning so `finish_project_batch()`'s due check is unchanged.
- Every cycle's step 9 (7e) now runs `propose-project.js --prepare` on any outcome (exit 3 = no cost). An idle fire (`work_to_find`, AGT-314) runs the same block, and `runner_should_boot()` counts `review_due` batches in `detail.finish_due` so the nothing-pickable / nothing-to-find / batch-due corner still boots. No new verdict or mode: `work_to_find` + `find-work-only` already mean "go and do the deterministic chores, build nothing" (pattern:17).
- Alternatives rejected: a DB trigger on `backlog_items` (cannot run the three model turns; the review needs a cycle), a new `finish_review` boot verdict (a fourth verdict/mode to teach ses-297, agt-127, agt-314 for no behavioural gain), a `projects.finished` column (a second name for a state `proposal_due` already states; pattern:53/93).

## 5. The 24-hour claim (D4)

Without a bound, a batch Victoria disagrees with twice "stays due for the next run" — with the hourly runner that is up to 24 × 3 model turns a day, forever. The claim is stamped by the same door that starts the review (`--prepare`, PostgREST conditional PATCH on `epics.proposal_attempted_at` with `Prefer: return=representation`, `[]` = another lane holds it), so it is structural (pattern:10, pattern:138 claims not locks) and also keeps two parallel lanes from reviewing one batch. A crash mid-block leaves the stamp; the batch retries the next day. 24 h is a declared constant (pattern:18), justified against the only existing bound (the weekly auditor run) — one review a day per batch is 7× that cadence and 24× cheaper than hourly. An earlier draft used a SQL function `claim_proposal_review(uuid)`; the kickoff cap made the PATCH form the cheaper proof.
