## 2. THE TRAP — why "one catch-up sweep" cannot simply be run

4,234 of the 6,007 open rows carry `ladder_work_class` with `ladder_applied_at` null, so the sweep would hand `ladder_apply_signal(class,'promote',…)` 4,234 signals in one call. That function promotes a rung on every 5th signal (`v_streak % 5 = 0`) and deliberately never resets the streak (SES-107, John's "no reset"). `class_autonomy()` then pays `extra_files = greatest(0, rung - runner_settings.cap_relax_rung)` with `cap_relax_rung = 13` and **no ceiling**.

Measured arrears by class: `bug_fix` 1,942 · `tooling` 1,562 · `enhancement` 391 · `determinism_removal` 234 · `invention` 105. Current ladder: `bug_fix` 6/7, `tooling` 60/0, `enhancement` 1/4, `determinism_removal` 0/3, `invention` 2/11, `agent_creation` 2/5.

So an unguarded catch-up lands `bug_fix` at rung ~394 (extra_files 381) and `tooling` at ~372 (extra_files 359). John's hard rule — `HR-SCOPE` / `CAP-SCOPE-FILES`, "at most 3 modified files" — would stop binding for every later cycle. A fix that detonates the cap rule is a worse defect than the one it repairs (pattern:124, pattern:166).

**What makes the call clean rather than a judgment about the ladder:** 4,142 of the 4,234 are `kind='requirement-check'`, a kind that first carried a `ladder_work_class` on 2026-10-02 and has **never** promoted anything. The finalised class-bearing population is ship 73, filing 38, directive 32, ticket-scope 30, agent-row 24, ticket-status 23, design-kickoff 20, gate 15, design-ruling 9, removal 8 — and zero `requirement-check`. Stamping `ladder_applied_at` on exactly those 4,142 therefore preserves the platform's actual history instead of changing a rule: the ladder keeps its forward semantics untouched, and the remaining 92 genuine signals still pay out (`bug_fix` → rung 10, `tooling` → rung 74, the other four unmoved). Decision volume bears the same reading: 10-16 alone recorded 1,438 decisions, 1,163 of them class-bearing, against ~30-50/day before 2026-10-09.

This is pattern:120 — ship the per-instance act today, file the standing rule as its own ticket — and pattern:157: the remediation is scoped to the rows of one named outage window, never generalised.

## 3. Alternatives weighed and rejected

- **Loosen `backlog_done_requires_verdict()`** — forbidden by the ticket and wrong; the guard is the only thing stopping a block being papered over.
- **Write a decision over AGT-281's block to clear it** — forbidden by the ticket, and it would fabricate a ratification nobody gave.
- **Finalise the decision but skip only the ticket close** — rejected: the ticket says a savepoint PER DECISION, and per-row rollback is also better behaviour, because the decision stays `open` and the same sweep closes AGT-281 automatically the hour after its ratification arrives, with no second ticket.
- **`record_skip()` for the refusal** — rejected on a measured blocker: `record_skip` writes its before-image with `cycle_id` only, and the pg-cron path has no cycle (`runner_before_images.ck_before_image_attribution` demands exactly one of cycle/session), so the cron caller would raise inside the reporter. The refusal therefore travels as OUT columns in `record_skip`'s own `(backlog_id, reason_kind, reason)` SHAPE, written to `runner_finaliser_runs` by `run_window_finaliser()`.
- **A per-call row limit (`p_limit`)** — rejected as unjustified (pattern:67). With the 4,142 ladder calls neutralised the catch-up is ~6,007 decision updates plus before-images; `statement_timeout` is 120,000 ms cluster-wide (`pg_settings.source = configuration file`; the `postgres` role carries no override, so pg_cron inherits it). The kickoff gives the Builder the one-line fallback instead of a new parameter.
- **Editing `docs/runbooks/runner-cycle.md` (7b)** — dropped deliberately. The file is 380,920 B of its 381,000 ceiling, its sha256 is pinned in `docs/runbooks/cycle-card.md` and mirrored in the `dm-knowledge-cycle-card` skill row, and `ses-413d` pins `BYTES_AT_SHIP`: a one-line edit is a four-file job, which is the standing collision `AGT-288` and `AGT-466` own and which AGT-174/180/176 each dropped on the same merits. Nothing in (7b) becomes FALSE — the sweep still returns those three numbers and the fenced call still runs — it becomes incomplete.

## 4. Grants and signature, read rather than assumed

`information_schema.role_routine_grants` for `sweep_decision_windows`: `service_role` and `postgres` only, no `anon`/`authenticated`. A DROP + CREATE re-opens it, because `pg_default_acl` grants EXECUTE to `anon`, `authenticated` and `service_role` **by name** (`.claude/rules/supabase-column-grants.md`, SES-315 addendum), and `REVOKE … FROM PUBLIC` does not remove a named grant — hence (d) and the two-direction assertion. `run_window_finaliser()` is replaced in place, so its ACL survives. `role_table_grants` for `runner_finaliser_runs` returns zero `anon`/`authenticated` rows, so (a)'s new columns need no grant and expose nothing. Only four functions mention the sweep (`reverse_decision`, `file_invention_proposal`, `run_window_finaliser`, `apply_ladder_decision`) and only `run_window_finaliser` calls it, by named columns — so the new OUT columns break no caller.

`reversible_tables()` returns 17 tables and `runner_decisions` is not among them, so `reverse_decision()` cannot undo (f). The undo is the before-image set, and the decision's reasoning must say so rather than implying a Reverse that would silently do nothing (SES-399's shape).

## 5. AGT-281's own exit — FOLLOW-UP, not this slice

Its exit needs a non-reversed `ship`/`ticket-status` decision, or a harvested `runner_items` Accept, dated at or after verdict `38959e02`. `regradable_ships()` returns 0 rows, so 7a-bis cannot produce one. Supplying it is a ratification judgment about a blocked delivery — a verdict-side act — and the ticket itself names it a separate matter. Folding it in would mean exactly the write the ticket forbids. After this ship the platform is in the right state for it: AGT-281 stays `delivered`, its decision stays `open`, and it is NAMED in every hourly run row instead of silently wedging the whole sweep.

## 6. Discoveries to file (evidence attached, outside this slice)

1. **`requirement-check` decisions carry a `ladder_work_class` that was never a promote signal** — 4,142 open rows since 2026-10-02, zero finalised precedent. Either the kind should stop setting the column, or the sweep's promote branch should name the kinds that count. A governance-semantics call (M6-07), not a bug fix.
2. **`class_autonomy.extra_files` has no ceiling** — `tooling` at rung 60 already grants +47 files / +47 tasks today, i.e. the file cap does not bind for tooling work at all, and after this ship it is +61. Worth a cap on the pay-out or a demote path.
