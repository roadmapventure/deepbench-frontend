## Why a drill

The organic supply of product failures was **zero** at the M4 gate (`durable_hops` had not written a
row since 2026-08-23), so a healing milestone that waited for a real failure to certify itself might
never certify. The charter permits a *deliberately seeded* failure. **The bar was that the drill must
be able to FAIL** — the runbook's own "would it still pass if the change did nothing?" test — and it
did fail, once, at exactly the step that mattered.

## The seeded shape

Three `public.durable_hops` rows, `status = 'failed'`, `tenant_id = 'drill-ses-277'`,
`capability_slug = 'drill-ses-277-seeded-capability'`, error text
`DrillError: seeded failure for the SES-277 closed-loop drill`, dated 1, 2 and 3 days back (inside the
engine's 14-day window). Nothing was pre-registered: the engine had to find the signature itself.
Signature hash as computed by the engine: **`d09e012505d9`** (the normaliser reads the error class as
`DrillError: seeded failure for the SES-N closed-loop drill` — ticket numbers are stripped, by design).
Every seeded row was ledgered in `runner_before_images` (`session_name = 'design-ses-277-0902'`) the
moment it was written, for cleanup.

## The defect, and the fix

**Step 5 failed** — the verdict was printed and did NOT persist. `scripts/heal-engine.js` `main()`: the `detections.length === 0` branch called `finish()` before the
block that upserts occurrence state and PATCHes verdicts, so under `--apply` a run with nothing new
to file wrote nothing — including `confirmed_fixed` and `recurred`. `tests/regression/ses-276-heal-v2.test.mjs`
graded `assessConfirmations()` purely and never the CLI path, which is why v2 shipped `done` with the
loop's last third unwired. Fix (same commit as this record): `persistSignatureState()` is the one
write path for both branches; `verdictPatches()` is pure and graded by
`tests/regression/ses-277-seeded-failure-drill.test.mjs`, whose source-shape arm pins that the
nothing-to-file branch persists under `--apply`, with a mutation control.

One quirk recorded, not fixed: after a recurrence the row's `occurrences` reads the *in-window*
count (1), not the lifetime count — `recurrence_count` carries the history. Reading `occurrences`
as lifetime would mislead; the column comment should say so (`SES-303`'s read seam).

## What this certifies for M5

Charter success measure 4 — *"a production failure travels detect → file → fix → confirm by the
loop itself"* — is now demonstrated end to end on the real engine against real Supabase, with a
seeded failure the engine was not told about, and the drill proved it could fail. `M5-12`'s 72-hour
observation has its instrument (`SES-303`, `ticket_outcome`); the confirmation window itself is a
per-signature column and the engine honours it, as this drill's 7-day window against a 20-day quiet
period shows.
