# LOG-138 — screen-origin attribution in `ai_activity_log`

Design session `design-log-138-0810`, 2026-08-10. Kickoff: `docs/kickoffs/v7.0.90-LOG-138-screen-origin-attribution.md`.

## The gap

Every screen funnels through `/api/capabilities/execute` (§19b). `feature` records
`<capability>:<intent>:<depth>` — *what* ran. `call_source` records `ui`/`script`/`regression`/
`session-test` (`LOG-121b`) — *how*. Nothing records *where from*, so a Channel Sales Intelligence
run and a Live Agent Console run log identically.

Reproduced live during the design session: loading Channel Sales Intelligence on dev wrote 7 rows
(Jordan — Market Analyst's news search, Michelle Manning — Project Manager's agent-selection turn,
Alex Rivera — Content Strategist's card formatting, plus the guardrails/similarity/directory rows),
every one `call_source: ui`, same `request_host`, none naming the screen.

## The direction change, and why

The filed row proposed a frontend-set `x-db-screen-origin` header, threaded like `call_source`.
Rejected after measurement:

- The frontend sets **no** custom headers anywhere today — `x-db-call-source`/`x-db-visitor-id`
  appear only in `scripts/`, `lib/`, and docs. So this is not "extend the existing pattern," it is
  new plumbing at ~10 `fetch("/api/…")` call sites across 8 files.
- The 3-file session budget covers Channel Sales Intelligence and the Agent Console and stops.
  Teach, Personnel File, Agent Roster, Add Agent, Project Management, Create Work Order, Task
  Instructions, Spend Analysis and Fetch would stay unattributed until separately funded — and
  §19i means no backfill, so every run in that window is permanently unattributable.

Shipping instead: derive the screen from the `Referer` path the browser already sends, inside the
existing `lib/request-context.js` choke point. Zero frontend files, all 12 screens at once.

## What was proven live before the kickoff (both halves, with controls)

**1. The header survives into our code.** Two identical POSTs to `/api/rag-query` on the live dev
deployment, 4 seconds apart, differing by nothing but a `Referer`:

| probe | `Referer` sent | logged `call_source` |
|---|---|---|
| `log138-probe-a` | none | `script` |
| `log138-probe-b` | `https://<dev-host>/channel-intelligence` | `ui` |

The flip is only possible if the header reached `lib/request-context.js` intact through Vercel's
edge, the `HAR-33` gate, and the function boundary. The control is what makes it evidence: if the
header were being stripped, both rows read `script`. (Both probe rows remain in `ai_activity_log`
under those tenant ids — real calls, honestly logged.)

**2. The browser sends the full path, not the bare origin.** Navigating `/channel-intelligence` →
`/bench` in a real browser, the destination reported its referrer as
`https://<dev-host>/channel-intelligence`. The deployment serves no `Referrer-Policy` response
header (measured on the document) and `index.html` carries no meta referrer, so the browser
default applies.

What remained unmeasurable until the code exists: the column itself populating. That is the
kickoff's Category L test and Manual QA items 2–5, not an assumption carried forward.

## The map — name, never address

The recorded value is the screen's canonical **name**. Two load-bearing reasons: `/bench/<agent>`
and `/work/<task>` carry identifiers and this column is anon-readable from the browser (the
`LOG-124` lesson); and the address deliberately disagrees with the name in two places, because the
nav label is canonical and the route is not.

| Address | Recorded as |
|---|---|
| `/`, `/live-agent-view` | `live-agent-console` |
| `/channel-intelligence` | `channel-sales-intelligence` |
| `/work` | `project-management` |
| `/work/new` | `create-work-order` |
| `/work/<task>` | `task-instructions` |
| `/work/<task>/analyze` | `spend-analysis` |
| `/work/<task>/fetch` | `fetch` |
| `/bench` | `agent-roster` |
| `/bench/new` | `add-agent` |
| `/bench/test` | `test-my-team` |
| `/bench/<agent>` | `personnel-file` |
| `/bench/<agent>/teach` | `teach` |

Three deliberate properties: **ordering is significant** (`/bench/test` and `/bench/new` must be
tested before `/bench/<agent>`, or "test"/"new" read as agent ids — the same specificity ordering
`react-router` applies in `src/main.jsx`); **an unrecognized path records `null`**, never a guess or
an "other" bucket, same posture as `ALLOWED_CALL_SOURCES`; and **the raw path is discarded** after
matching.

**Paired-edit precondition for `LA-01`:** `/` maps to `live-agent-console` because that is what it
genuinely serves today. The session that repoints `/` to Home must update the map in the same
commit. Written into `docs/SCREEN-INVENTORY.md`'s Home Screen entry, where that session will
already be reading. Adding Home's own route is safe unpaired (unmapped → `null`); it is the
re-point specifically that needs it.

## Grant + ordering findings

Both folded into `DAT-23`, which already owns amending
`.claude/rules/supabase-column-grants.md`, rather than filed separately:

- On `ai_activity_log`, `SELECT` is **column-scoped** (only `caller_ip` withheld, `LOG-124`) but
  `INSERT` is **table-level** (`DAT-18`'s append-only exception). A new column therefore fails
  closed for reads and fails **open** for writes, in the same migration. `screen_origin` inherited
  anon INSERT without being granted it; left inherited rather than revoked, since singling out one
  column would silently reverse `DAT-18` and anon can already insert every other column here.
- `lib/activity-log.js` POSTs to PostgREST with a swallowed `.catch(() => {})`, so code that writes
  a not-yet-existing column makes PostgREST reject the insert and **silently lose every audit row**.
  The column must land before the code deploys. This session applied it ahead of the kickoff for
  exactly that reason.

`§19k` safety was verified by reading `pg_get_functiondef('log_row_signature')`: it builds from
named columns only, never `to_jsonb(row)`, so a new column cannot perturb any signature.
