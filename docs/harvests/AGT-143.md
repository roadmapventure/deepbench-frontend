## Premise revalidation (alive)

The four importers (`decide-gated-card.js:264`, `market-agent.js:341`, `personal-agent.js:283`, `run-project.js:582`) pass the same assembly and inherit the same answer. So today a switch in the table is cosmetic for every script-run agent, which is the ticket's use case verbatim.

## The decision: a trigger carries the table into the Skill rows

Three ways to make "the Skill's lane row" resolvable after a switch were weighed:

1. **History in the resolver** — keep a previous-model column or an audit trail so `agent-prompt.js` can find which lane a Skill *used* to equal. Needs schema AGT-142 does not have, and only the scripts would follow; `api/prompt/db-assembly.js` (the executor, 298 and 388) would still read the stale `llm_model`. Rejected.
2. **Every reader re-derives membership** — `db-assembly.js`, the resolver, the four `agt-6x` tests and `audit-*` each learn the new rule. Six homes for one seam (pattern 14, 15). Rejected.
3. **Trigger** — `model_assignments_sync_skills()` AFTER UPDATE OF `model_id`: a lane row's change rewrites `skill_profiles.llm_model` for every row equal to the old id; a capability row's change rewrites its capability's default Intent Skill. Equality — the membership rule AGT-142's seed and `resolveJudgmentModel()` already share — stays true by construction, so `db-assembly.js`, the SES-395 fence, `agt-66/67/68`'s "every dm-* Skill equals the orchestrator lane" assertions and the audit readers all follow with zero code (pattern 8, 10, 16). Chosen.

Blast radius, stated so nobody is surprised: lane membership is equality, so a `judgment` switch moves all 54 Fable Skills, product ones included — that is what "one table names the model for every job type" (walkthrough Q3) means, and it is the same population SES-395's degrade already governs. Capability rows are the per-job override for anything that must not move with its lane (AGT-144 may add them).

Reverse is symmetric: reversing the `model_assignments` row (new → old) fires the trigger the other way. AGT-144's switch must still write `runner_before_images` for the Skill rows the trigger will touch (`AGENT-ROW-AGREED-TICKET`, §19v P6), named in the STOP LINE.

## Why (b) and (d) change no text

After AGT-142, `runner_model_lanes` is a mirror kept by `trg_model_assignments_sync_lanes` and guarded against every other writer. A function or script that reads the mirror reads the assignments table's answer, provably: the migration's proof block switches the `judgment` row inside a rolled-back sub-block and asserts `judgment_model()` and the mirror both report the new id. Rewriting five readers to name `model_assignments` in their SQL/URL would be byte-neutral for every caller, would make `export-governance-snapshot.js` map `job_key → lane` to keep the snapshot sha stable, and would invalidate nothing the proof does not already prove. The ticket's sentence "the table must be the only authority" is true at the database because of AGT-142's guard; this ticket proves it rather than restating it. If the mirror is ever retired, the readers re-point then.

## The proof block, and why it is in the migration

A regression test over REST cannot open a transaction, and a live switch during a test collides with parallel cycles (SES-382). A plpgsql nested block that ends in `raise exception 'agt143-proof'` rolls back its own writes atomically, so the switch, the four asserts and the undo are one statement — recorded in the migration output, repeatable on any re-apply, and never visible to another session. The offline seam test proves the resolver's code path with a stub; the two together are the ticket's "a switch in the table changes what agent-prompt.js prints with no other edit".

## Resolver shape (why the return contract is preserved)

`ses-331` part (f) stubs `fetchImpl` to answer the LANES array for every non-RPC URL and calls the function without `capability_slug`; the capability GET is gated on `assembly.capability_slug`, so that test never sees it and its `deepStrictEqual` shapes hold. When a capability row is found, the candidate still runs through the judgment-equality/degrade step, so a capability pinned to the judgment model still degrades under SES-395 (a reading outranks a stored answer, same as today). The text header's `# lane:` degrade line is byte-identical; the capability line is added only when the answer differs from the Skill's, matching the "only when it actually moved" rule at L318.
