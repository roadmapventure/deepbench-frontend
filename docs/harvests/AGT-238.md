## Corpus columns

The table `project_concurrency_corpus()` returns, copied verbatim into the migration. One row per project, `projects p LEFT JOIN epics e ON e.project_id=p.id LEFT JOIN backlog_items b ON b.epic_id=e.id`, `GROUP BY p.slug, p.status, p.priority`, `ORDER BY (p.status='executing') DESC, p.priority`.

| column | type | expression |
|---|---|---|
| `slug` | `text` | `p.slug` |
| `status` | `text` | `p.status` |
| `priority` | `int` | `p.priority` |
| `epics` | `int` | `count(distinct e.id)::int` |
| `locked` | `int` | `count(distinct e.id) filter (where e.locked_at is not null)::int` |
| `finished` | `int` | `count(distinct e.id) filter (where e.finished_at is not null)::int` |
| `open_tickets` | `int` | `count(b.id) filter (where b.status in ('open','partial','discovered'))::int` |
| `partial_tickets` | `int` | `count(b.id) filter (where b.status = 'partial')::int` |
| `blocked` | `int` | `count(b.id) filter (where b.blocked_by is not null and b.status not in ('done','removed'))::int` |
| `leverage_tickets` | `int` | `count(b.id) filter (where b.leverage_reason is not null and b.status not in ('done','removed'))::int` |
| `done_7d` | `int` | `count(b.id) filter (where b.status='done' and b.updated_at > now() - interval '7 days')::int` |
| `done_30d` | `int` | `count(b.id) filter (where b.status='done' and b.updated_at > now() - interval '30 days')::int` |
| `proposal_due` | `bool` | `p.status='executing' and bool_and(e.locked_at is not null) and bool_and(e.finished_at is null) and count(b.id) > 0 and count(b.id) filter (where b.status not in ('done','removed')) = 0` — the same clause `project_batch_state()` uses |

`done_7d`/`done_30d` are the close rate: `backlog_items` has no dedicated closed-at column, so `updated_at` on a `done` row is the honest proxy and is labelled as such wherever it is shown.

## Intent copy

The paragraph appended to `skill_profiles.method` for `dm-run-intent`, verbatim:

> CONCURRENCY FROM THE CORPUS (John 2026-09-27): how many projects execute at once, and in what order, is yours to decide from `concurrency_corpus` — tickets left, blocked counts, leverage marks, close rate and the capacity the walls report — not from a fixed rule. Put the decision in `concurrency` as `{execute, pause, order, why}`; `order` must name exactly the projects in `execute`, and `why` must say what in the corpus decided it. Starting a `proposed` project is not yours: that stays John's words through `start_proposed_project()`.

## Why this shape

- **The count and the order already have a home.** `projects.status='executing'` IS the count (`epic_project_executing()` gates every pick on it) and `projects.priority` IS the order (`prime_directive_queue()`'s `sort_project`, `drain_epic_next()`'s `pj.priority`). A `runner_settings.max_concurrent` knob would be a second home for a number the board already carries, and the first disagreement between them would be silent (pattern:67, pattern:17).
- **The decision is model judgment; the evidence is not.** John's Q4 is "the dev manager should look at the corpus and decide what is best" — so the corpus is a deterministic read and the choice is the manager's recorded reasoning, never a rule in code (pattern:9, pattern:6).
- **Reversibility comes free.** `projects` is already in `reversible_tables()`, `projects_status_check` already admits `paused`, and `projects` has no triggers — so one `runner_before_images` row per changed row makes the whole decision Reversible with no schema change (§19v).
- **The slice-1 boundary is enforced, not just written.** Slice 1's STOP LINE said starting a `proposed` project stays John's (AGT-240). Prose cannot hold that; a RAISE on any `proposed`/`planned` slug can (pattern:10).

### Alternatives rejected

1. **A `max_concurrent` setting the runner reads.** Rejected: a fixed rule is exactly what John's Q4 excludes, and it duplicates `projects.status`.
2. **Letting `record_concurrency()` also start a `proposed` project.** Rejected: AGT-240 and slice 1's STOP LINE reserve that for John's words.
3. **Having this build make the first real concurrency call.** Rejected: the Builder is not the manager, and a deterministic script recording a judgment as the manager's would misattribute it (pattern:42). The mechanism ships; the next manager turn decides.
4. **Fixing `trainer-authored-agents` (executing, no epic) in this build.** Rejected as out of scope (pattern:64/96) — filed as a finding, and it is the corpus's own first piece of evidence for the next manager turn.
