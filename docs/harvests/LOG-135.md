## Task 3 — After-state

**Re-run of Task 1's count:**
```sql
SELECT count(*) FROM ai_call_patterns WHERE ai_activity_log_id IN (37603,37640,37644,37670,37682);
```
Result: **0** — unchanged. The amend did not clear the gap it was meant to close.

**Blast-radius query (grouped by feature), platform-wide:**
```sql
SELECT l.feature, count(*) FROM ai_call_patterns p JOIN ai_activity_log l ON l.id = p.ai_activity_log_id
WHERE p.pattern_name = 'Function Calling' GROUP BY l.feature ORDER BY 2 DESC;
```
Result: **zero rows** — `function-calling`'s new criteria matches **nothing at all**, platform-wide. Not a narrow blast radius; a null one.

**Root cause, isolated and confirmed live (not speculation):** `pattern_criteria_matches(sig, crit)` (the SQL function every `ai_call_patterns` row is matched through) resolves each criteria key with a flat lookup, `sval := sig -> k`. That is a literal top-level-key lookup, never a dotted-path traversal. Susan's `traits.schema` conjunct is exactly the kind of key `lib/pattern-vocabulary.js`'s own `SIGNATURE_FIELDS` allowlist (and the Skill Profile's field reference she was given) documents as legal — but the live signature nests it as `sig->'traits'->'schema'`, never a flat `sig->'traits.schema'` key. Isolated by direct test against row 37603's real signature:

```sql
SELECT
  pattern_criteria_matches(log_row_signature(l.*), '{"tool_calls":{"in":["ci-answer-intent","channel-intelligence:ci-answer-intent"]},"traits.schema":true}'::jsonb) AS full_criteria,   -- false
  pattern_criteria_matches(log_row_signature(l.*), '{"tool_calls":{"in":["ci-answer-intent","channel-intelligence:ci-answer-intent"]}}'::jsonb) AS tool_calls_only,                    -- true
  pattern_criteria_matches(log_row_signature(l.*), '{"traits.schema":true}'::jsonb) AS traits_schema_only                                                                              -- false
FROM ai_activity_log l WHERE l.id = 37603;
```
The `tool_calls` conjunct alone matches (confirmed true); the `traits.schema` conjunct alone never matches anything (confirmed false on a row whose real signature has `traits: {schema: true}`); the `AND` of both is therefore always false. Informational count (not a fix, not acted on): `tool_calls` alone would match **604** rows platform-wide today. `channel-intelligence:ci-answer-intent` — the second value Susan enumerated — never appears as a literal `tool_calls` array entry anywhere (`0` rows), so it contributes nothing; the 604 figure is carried entirely by the bare `ci-answer-intent` value.

**This was not Susan's judgment failing.** She correctly resolved the declared-context-vs-emission question (chose emission, the more precise reading) and her criteria is internally consistent with the pattern's real definition. `validateCriteria()` also did its job correctly — it checks a key is in the allowlist and the value is grammar-legal, not whether the matcher can actually resolve that key against a real signature shape, so it had no way to catch this. The gap is in `pattern_criteria_matches()` itself: it has never actually implemented matching for any of the three dotted keys the allowlist documents as legal (`traits.schema`, `traits.source`, `traits.intent_allowlist`) — `function-calling` is the **first** gold-row criteria ever authored using one of them (confirmed live: no other `pattern_vocabulary` row's criteria contains a `traits.`-prefixed key), so this defect was latent and unexercised until this session's own amend triggered it. **Not fixed here** — out of this session's scope (harvest-doc-only, zero repo code, one file) and not this session's governance charter (it's a SQL/matcher defect, not a `pattern_vocabulary` content question for Susan). Flagging for the parent design session to triage/file.

**No other gold row changed vs. snapshot:** `reviewCandidate()`'s `amend` branch is structurally a single-row `PATCH ... WHERE pattern_slug = eq.<matched_existing_slug>` (confirmed by direct code read this session, `lib/pattern-vocabulary.js`) — it cannot touch a second row. Confirmed live: re-read of every non-`function-calling` `pattern_vocabulary` row's `criteria` is byte-identical to `S-LOG-133`'s own recorded end-state (`agent-handoff`, `agents-as-tools`, `brokered-delegation`, `evaluator-optimizer`, `handoff`, `orchestrator-workers` all match; every other row's `criteria` is still `null`, unchanged); `function-calling` is the only row anywhere carrying a `traits.`-prefixed criteria key.

## Round 2 — grammar re-expression

Filed after the parent design session independently verified the Task 3 root-cause isolation and found the decisive extra fact: the **nested** criteria form works today. Confirmed fresh, live, before filing anything:

```sql
SELECT
  pattern_criteria_matches(log_row_signature(l.*), '{"traits":{"schema":true}}'::jsonb) AS nested_form,        -- true
  pattern_criteria_matches(log_row_signature(l.*), '{"traits.schema":true}'::jsonb) AS dotted_form,             -- false
  pattern_criteria_matches(log_row_signature(l.*), '{"tool_calls":{"in":["ci-answer-intent","channel-intelligence:ci-answer-intent"]},"traits":{"schema":true}}'::jsonb) AS full_nested_form  -- true
FROM ai_activity_log l WHERE l.id = 37603;
```
The nested object form of the same fact matches via the matcher's generic containment branch (`sig @> jsonb_build_object(k, v)`), the same branch every non-dotted bare-scalar key already goes through. This looked like a pure syntax fix, landable without any SQL/code change tonight — Susan re-issuing the same conjunct in nested form instead of dotted form.

**Candidate filed:** `pattern_candidates` id `d6527773-b330-4439-800a-7fc1a9445b7d` (`submitted_by: 'S-LOG-135-run'`, `source_ai_activity_log_id: 37603`, `status: 'pending'` at file time). `observed_description` quoted her own Round 1 amend criteria verbatim, stated the verified mechanism fact (flat-lookup matcher, dotted key never matches, nested form does — both grounded live, not asserted), framed it explicitly as a syntax re-expression of an already-made judgment (her `tool_calls` enumeration and her emission-vs-declared-context reading both untouched, not reopened), and asked her to re-issue in matcher-resolvable form or decline. Per the instruction, only the nested FORM of her one conjunct (`{"traits":{"schema":true}}`) was shown as a grammar illustration — her full criteria was never composed for her.

**Invocation:** same real path, `intent_slug` set, deploy re-verified current (`9d12f27`) immediately before the call.

**Result: the call itself failed — `reviewCandidate()` threw, nothing written.**

```

{"error":"reviewCandidate: criteria key \"traits\" is not in the signature-field allowlist (intent, retrieval_method, tool_calls, gated_subroutine_fired, sub_calls_chained, integration_followed, delegated_to_provenance, retrieved_chunk_ids, assembled_skill_slugs, model_modality, capability_slug, traits.schema, traits.source, input_references_other_deliverable, self_reported_claims, traits.intent_allowlist, execution_type)"}
```

Susan did real work and made a real decision — a genuine Anthropic call is logged (`ai_activity_log` id `37692`, `agent_id: 'susan'`, `feature: pattern-vocabulary-review:pattern-vocabulary-review-intent:depth0`, real `web_search`) — and she evidently *did* re-issue her conjunct in the nested form we illustrated (the error is `validateCriteria()` rejecting a criteria object whose top-level keys include a bare `"traits"` key, which only a nested-form payload would produce). But `lib/pattern-vocabulary.js`'s `SIGNATURE_FIELDS` allowlist (the same list quoted in the error) only contains the literal dotted string `"traits.schema"` as a legal key — never bare `"traits"` — so `validateCriteria()` throws before any write, on any criteria object that nests under a `traits` key at all.

**This closes the loop the parent design session's finding opened, with the opposite conclusion: no syntax fix lands this tonight.** The two forms are not two options where one works — they are the only two forms the grammar admits, and each fails a different gate:
- **Dotted (`"traits.schema": true`)** — passes `validateCriteria()` (it's the literal allowlisted key), never matches at read time (the matcher does a flat lookup, the signature nests it).
- **Nested (`"traits": {"schema": true}`)** — matches at read time (containment branch, confirmed live above), rejected by `validateCriteria()` (its top-level-key allowlist has no `"traits"` entry).

Per this session's governance rule — a 4xx/5xx on a live call is a FAIL to report, never retried with altered criteria — this was not retried with a third variant. `function-calling`'s `pattern_vocabulary` row is confirmed unchanged (still Round 1's dormant dotted-key criteria); the candidate stayed `pending`, `reviewed_by: null`, `resolution: null` (the throw fires before either write in the `amend` branch).

**What this actually resolves for the parent design session's ticket:** the defect isn't only "the matcher can't resolve a dotted key" — it's that **`validateCriteria()`'s allowlist and `pattern_criteria_matches()`'s matcher disagree about which SHAPE the three `traits.*` fields should be authored in**, and neither shape satisfies both gates simultaneously. A real fix needs one of: (a) the matcher gains real dotted-path traversal so the already-allowlisted dotted string form actually resolves against the nested signature, or (b) the allowlist is changed to accept a nested `traits` object (with `schema`/`source`/`intent_allowlist` sub-keys) and the three dotted `SIGNATURE_FIELDS` entries are retired in favor of it — either is a code change, not a governance call, and not something this session (or Susan) can resolve through another candidate.
