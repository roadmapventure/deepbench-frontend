## The variant chosen, and what it does not do

Chosen: one health-indexed allowance function, `public.runner_concurrency_allowance()`, that both
gates read (pattern:14 — two code paths computing the same thing get one shared core), fed by one
new data column `runner_settings.db_health_ladder` (pattern:2 — the numbers are data, not a CASE in
two function bodies). Green stays defined by the existing `max_lanes` / `test_slot_capacity`
columns, so no number gains a second home (pattern:93).

Rejected — **a new refusal literal** such as `db_narrowed` for the amber-lanes-full case. SES-411
keeps the gate's refusal set in four homes (the `THEN '<literal>'` set in the body, the function
COMMENT enumeration, the `governance_rules` rows, and `REASONS` in
`ses-297-pre-boot-pickability.test.mjs`) and its live arm G grades drift to zero. A ninth literal is
a four-home edit plus two pinned copies in `ses-411-rule-vs-function.test.mjs`, for a P10 tooling
ticket whose behaviour change is one boolean. Reusing `db_pressure`, narrowed, costs nothing in
those homes and the refusal is still auditable from `detail.db_level` +
`detail.db_lane_allowance` + `detail.live_lanes` (pattern:65).

Rejected — **scaling `test_slot_capacity` down at amber**. It is already 1; the line cannot narrow.
What changes at amber is that the line KEEPS MOVING instead of granting nothing. That is the honest
description and the kickoff says it that way rather than claiming a reduction that is not there.

Rejected — **touching `drain_chain_gate()` Gate F**. It stops a running chain on non-green, which is
a different question from how many cycles may start. Out of scope (pattern:65); if it should narrow
too, that is its own ticket.

**What this does not do.** It does not adapt — the ladder is declared, not learned. It does not
change red or `unsafe` behaviour at all. It does not narrow anything other than boot concurrency and
the test-slot line; a cycle already running when the database turns amber is untouched.

## The locked rule this amends

`governance_rules` M6-14 currently states that anything but green across the last 15 minutes makes
`runner_should_boot()` refuse as `db_pressure`. After this change that is true only when the
narrowed allowance leaves no lane free. Per pattern:94 the rule is amended in the same migration
that changes the behaviour, rather than the behaviour drifting from the register — which is the
exact defect SES-410 recorded and SES-411 was built to detect.

  (docs/runbooks/runner-cycle.md:175) is edited.

  true: the narrowed refusal only ever fires off a non-green level.

  disagree with the function the moment the database is amber.
