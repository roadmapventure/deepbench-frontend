**The inconsistency flagged for Susan, not resolved by this session:** her Round 1 `merge` resolution on the `orchestrator-workers` candidate said (verbatim, from `pattern_candidates.resolution`, id `4b908f80-f637-4e10-b7d3-6988e6ff005f`): *"The observed instance (row 37374) carries tool_calls=request_help with integration_followed=false. This exactly matches the already-governed brokered-delegation pattern, which covers the manager-mediated selection case where control transfers to the target agent's output. The orchestrator-workers pattern (delegating directly via delegate_to_agent with integration_followed=true) remains distinct and correctly specified. The unclassified 1417 rows with request_help represent instances of brokered-delegation, not orchestrator-workers."* That reasoning names the full 1417-row broker population as `brokered-delegation`'s territory, but the criteria she actually wrote for it (`{"tool_calls":{"in":["request_help"]},"integration_followed":false}`) structurally excludes anything with `integration_followed:true` — the 744-row integrated bucket her own stated intent claimed to cover. Removing the integration_followed constraint allows brokered-delegation to span both transfer and integrated cases, leaving orchestrator-workers distinct (delegate_to_agent with integration_followed:true, direct dispatch only). This resolves all 744 broker rows without creating a third pattern."*
