## 3. What this assembly found that the cap case did not

1. **A fifth pinned file in part A.** `tests/regression/ses-399-attach-fails-closed.test.mjs:142` asserts its list deep-equals `K_ALLOWED` imported from `tests/regression/ses-364-reverse-agent-rows.test.mjs`, which pins 17 at lines 179 and 183. Widening one test list without the other reddens ses-399. Part A is therefore five files (mirror, ses-399, ses-364, agt-470, session-decisions.md), not four. My cap case under-counted by one; the Manager's ruling stands either way (it was already over the cap).
2. **A write path already exists for part of this, and it is not reversible.** `AGT-390` (v7.0.792) shipped `lib/knowledge-write.js` (`embedAndUpsertEntry`, `insertAgentConfig`) and `lib/skill-write.js` (`addCapabilityToAgent`, `addSkillToCapability`), reached by the MCP Teach tool. They write over REST one row at a time, with `origin`, and write no before-image and no decision. So "No handler writes skill_profiles" in AGT-250's kickoff is no longer true. I did not reuse them as the write core, for one reason: five destinations must land or fail together and reverse on one handle, and a sequence of REST calls cannot do either (pattern:19). I did reuse their **conventions** so the screen reads Susan's rows exactly as it reads everyone's: `origin` in the mirror's CHECK vocabulary, guardrail rows named `always`/`never`, the role prompt never displacing an existing default, author tags from `AUTHOR_TYPES`.
3. **The knowledge write needs no embedding.** `knowledge_entries` has a `teaching_note` column, and AGT-250's `knowledge_entries[]` are "title + teaching_note per document", each carrying `source_document_id` — the id of a row that already exists and is already embedded. So the write is an UPDATE of that row's `teaching_note`. This removes the prior kickoff's required 1,536-float embedding, the "who embeds" question, and every model or embedding call from this ticket. The title is left alone: changing it would stale the stored embedding.
4. **The confirmation gate already runs a handler on accept.** `api/_lib/handlers/confirmation.js` `resolvePendingConfirmation()` replays the paused step through `sendRequest()` with the proposal as `precomputed_turn`, which dispatches to `traits.handler`. So "the write fires only after the card is signed" needs no new mechanism: AGT-250's intent row keeps `requires_human_confirmation: true` and its `traits.handler` moves from `store` to the new handler (T8).
