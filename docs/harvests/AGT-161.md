## 2. The skill-edit rule and how it scopes this ticket

`docs/runbooks/runner-cycle.md` (7d): "A promotion is a `runner_card_asks` row of kind `skill-edit` asking John to rule, NEVER a Skill edit this cycle performs … it is John who changes that text (the `SES-45` boundary, Rule #1)." Independently, `node scripts/agent-row-gate.js --ticket=AGT-161 --action=edit-active --json` answers `{"verdict":"gated","rule":"AGENT-ROW-AGREED-TICKET","clause":"no-authority"}` because `scope_origin` is `discovered` — the same verdict AGT-160 got and resolved with a card ask (`runner_card_asks` id `98137400-b56d-4e9b-9d4e-2ab92247c006`, open, target `AGT-160`).

So the rule binds the ticket's first done-when clause ("each active agent's guardrails direct findings to the intake") but NOT the whole ticket. The mechanism — a finding row derived by the platform from a record the model already returns — needs no Skill text: the guardrails already say "return every record to persist in records_to_write and nothing else — the platform writes, the model never does", and `feature_signal` records already carry `proposed_ticket`. That is pattern:9/pattern:10 (a correct value exists deterministically; no model is put in charge of it) and it is what makes the ticket buildable unattended without touching a Skill row.

Precedent that a cycle *can* edit a Skill row: AGT-154 (`v7.0.599`) appended seven `must_not` bullets to `jm-guardrails` under a recorded `agent-row` decision with a pre-image — but that ticket held authority. AGT-161 does not, so the wording goes on a card.

## 3. Alternatives weighed

1. **Add a `findings[]` array to the answer schema and let the model author findings.** Rejected: needs the Intent Skill text to ask for it (gated), spends judgment on a value the record already holds, and invites the `kind` CHECK failure this cycle hit (a descriptive `kind` fails the insert after writing an orphan before-image). The derived finding fixes `kind:'other'`, `finding_type:'proposal'`, `confidence:'high'`.
2. **Backfill by hand with `audit-ledger.js --ingest`.** Rejected as the mechanism (a hand-rolled JSON per run is not a path the routine follows), kept as the shape: the build's Task 4 backfill goes through the same `raiseFindings()` the routine will use.
3. **Route row per agent (`nathan`, `jerry`, …).** Rejected: Rule #1 — a route naming an agent id is an agent named in data. Source `agent` is one row for the whole `agent:<id>` convention personal-agent's session ingest and the Builder already use.
4. **Extend `scripts/check-findings-intake.js` (AGT-160) to grade `nl-`/`jm-guardrails` and file the card.** Deferred: its `CARD_TARGET_ID` is a constant (`AGT-160`), so the change is a 4th file for one ask; the ask is a plain INSERT (AGT-160 CONTEXT 4). If a later cycle generalises the check, the AGT-161 ask row is already there to be read.
5. **Runbook edit (`docs/runbooks/market-agent.md` step 6).** Skipped (pattern:93): the script's usage header is the live source and the routine already runs `--write`; the raise is automatic.
