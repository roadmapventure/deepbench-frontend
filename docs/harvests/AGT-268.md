# AGT-268 - the measurements, the alternatives, and why the premise is alive

## 1. Premise revalidation (2026-09-29, live REST reads with the service key)

`career_records?kind=eq.posting`, 310 rows, projected as `id, source, data->>url, data->>status, data->>text`:

| population | rows | text present | status |
|---|---|---|---|
| `fetch-postings 2026-09-25...` | 148 | 148 of 148 | all `new` |
| `career-market-watch 2026-09-27` | 100 | 0 | `read` / `lead-unverified` |
| `career-market-watch 2026-09-24` | 45 | 0 | `read` |
| `career-match-finder 2026-09-27` | 16 | 0 | `scored` (9), absent (7) |
| `career-posting-review 2026-09-28` | 1 | 0 | `applying` |

- Text-less rows: **162**, every one a `career-*` source. Text-less fetch rows: **0**. The ticket's claim holds exactly, and the population has grown since it was filed (216 -> 310), so the reported ratio is now further from the truth, not closer.
- 209 distinct urls across 310 rows. **79** capability rows carry a url that already exists on a fetch row (62 market-watch, 16 match-finder, 1 posting-review) - the write-back that should have been an update.

## 2. What the code does, read this session

- `scripts/personal-agent.js:547` `fetchPostings()` - the only creator of a fetched row: `source = 'fetch-postings <date>'` (:557) and `data.text` from the board (:578).
- `scripts/personal-agent.js:513` `write()` - maps every `records_to_write` item straight into an INSERT (:520-529). There is no PATCH anywhere in this file; `rest()` (:362) exposes `get` and `insert` only. `target_row` is the persona a record applies to, not a row to update.
- `scripts/market-agent.js:98` `KINDS` has no `posting`, and `:401` already carries the `patch()` helper this build mirrors, plus the "one PATCH per `lead_reviews[]` entry" precedent (:581-590).
- So both populations are created by one file, and nothing on the row distinguishes them except the `source` string - which no reader reads.

## 3. The second defect the same root cause produces

`KIND_FILTERS` (personal-agent.js:144-149) splits postings by `data.status`. Because a write-back never touches the fetched row, all 148 fetch rows stay `status='new'` forever:

- `career-match-finder` (`status === 'new'`) re-serves every already-reviewed posting on every run.
- `REVIEWED_POSTINGS` (`status !== 'new'`) serves `career-posting-review`, `career-strengths-gaps` and `career-growth-review` **exactly the 162 text-less rows and never a row with text**. The reviewer's "no text" report is structurally guaranteed.

The PATCH path fixes both with one mechanism, which is why it was chosen over stamping a provenance field.

## 4. Alternatives weighed

1. **Stamp `data.origin` and filter reads on it.** Cheapest edit, but it leaves the duplicate rows and leaves every fetch row at `status='new'`, so the reviewers keep reading zero text. Bounds the problem instead of removing it (pattern:1). Rejected.
2. **Own kind only, no PATCH path.** Satisfies the count, but after the backfill the `REVIEWED_POSTINGS` readers see zero postings permanently, because nothing ever moves a fetch row off `new`. Rejected as a half fix.
3. **Merge the 79 duplicates into their fetch rows and delete them.** Makes history look like the new code path, at the cost of a destructive, hard-to-reverse migration over live personal data. Rejected; reclassification is one reversible statement and loses nothing (pattern:19).
4. **Chosen:** PATCH on a url match, `posting_note` otherwise, plus a reclassifying backfill. `kind='posting'` gains exactly one creator, so "count only fetch-sourced rows" needs no counting code at all - there is nothing else in the population to count (pattern:39, pattern:99).

## 5. Naming

`posting_lead` was the obvious name and was rejected: `public.market_leads` already owns "lead" on this platform and a second meaning would collide (pattern:118). `posting_note` reads for both members of the population - a title seen on a search page but not opened, and a scored verdict.

## 6. Consequences named for the Builder

- Widening the de-dup reads at :551 and :709 to `kind=in.(posting,posting_note)` is what stops the backfill re-opening 162 reviewed jobs on the next Sunday run. The price is that a surfaced-but-unopened title never later gains text - which is what the ticket already states ("only fetch-sourced rows ever carry text to read"), not new residue.
- Immediately after the backfill and before the next review runs, the `REVIEWED_POSTINGS` capabilities read zero postings. That is the honest state of the data (pattern:34), and the first write-back through the new path ends it.
