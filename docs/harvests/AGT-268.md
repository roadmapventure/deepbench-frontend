## 2. Where the conflation lives in code

`scripts/personal-agent.js:167`

```js
const RECORD_FIELDS = 'id,kind,title,body,data,target_row';
```

`source` is never selected, and `readRecords` (~line 392) projects to
`{ id, title, body, data, target_row }`. So the field that already separates the two populations on
every one of the 310 rows is dropped before the record reaches `task_context`. There is no code
anywhere in the repo that computes a "fetched postings" count — the 2026-09-27 number was produced
by the model reading undifferentiated rows and calling all of them fetched. Nothing to correct in a
query; the correction is that the count must stop being a model's count at all (pattern:10).

## 3. The near-miss: today's split is accidental

AGT-106 (`v7.0.697`) re-keyed `KIND_FILTERS` by capability:

- `career-match-finder`: `rec?.data?.status === 'new'` → today exactly the 148 fetch rows.
- `career-strengths-gaps` / `career-posting-review` / `career-growth-review`: the mirror
  (`status !== 'new'`) → today exactly the 162 write-backs.

That looks like the fix already landed. It has not. The split holds only because no capability has
yet written back a posting with `status:'new'`, and `status` is a free-form field any capability may
write through `records_to_write`. The moment one does, it joins match-finder's "new postings" and is
counted as fetched again. It also means `career-growth-review`'s *entire* posting population today is
write-backs — so the surface most likely to report a coverage figure is the one with zero fetched
rows in its prompt, and it has no way to know that.

## 4. Alternatives considered, and why they lost

**(a) Give capability-written rows their own `kind`** (what the stale `kickoff_link` slug implies).
Costs a migration to widen `career_records_kind_check` (11 kinds, measured 2026-09-23 from
`pg_constraint`), a 12th entry in `KINDS`, a re-point of every `READ_MAP` entry that reads `posting`,
a change to `validateAnswer`, **and** a backfill of the 162 existing rows — which would still be
mis-kinded until it ran. Four+ files against a 3-file cap, and the new kind would carry exactly the
information `source` already carries. Rejected on pattern:8 / pattern:17 / pattern:65.

**(b) Have the capability UPDATE the fetched row instead of inserting a new one.** This is the
ticket's first suggestion and it cannot cover the data: the 16 `career-match-finder` rows are
*search-surfaced titles* — postings discovered by the capability that have no fetched row to update.
It also turns `records_to_write` from an append-only path into a read-modify-write one, which is a
much larger change to `--write` than a P9 bug fix should carry. Rejected.

**(c) Re-key `KIND_FILTERS` from `status` to provenance.** Tempting, and structurally the "right"
long-term shape — but it changes no row today (the two partitions are already identical, §3), and it
would break `partF` of `tests/regression/agt-84-personal-agent.test.mjs`, whose fixtures pass rows
carrying no `source` at all: `mf.posting({ data: { status: "new" } })` would flip to `false`, and the
mirror controls `mf.posting(row) === !f.posting(row)` would fail on both rows. Fixing that means
editing six fixture literals for zero behavioural gain. **Filed as residue in the kickoff's STOP
LINE** rather than done here (pattern:65, pattern:120).

**(d, chosen) Derive provenance from `source`, label the row, compute the count deterministically.**
Two exported pure functions, one field added to a SELECT list, one key added to `task_context` and to
the `--json` output. No migration, no backfill, no constraint change; correct for all 310 existing
rows the moment it ships and for every future row by construction.

## 5. The decision I made rather than routing to John

Per JOHN-0925-DESIGNER-DECIDES, the feature call — *which of the ticket's two proposed fixes, or a
third* — is mine, recorded and reversible. Recorded: **provenance is derived from `source`; no new
`kind`; write-backs keep inserting their own rows; only the COUNT is split, and the row is labelled
`origin` so the capability can still see and use write-backs.** Reversible by deleting `postingOrigin`
and `postingCoverage` and their three call sites — the SELECT list returning to its current value is
the only other change, and it is inert on its own.

One sub-call worth naming: `postingCoverage` counts over **the posting records this prompt carries**,
not over the whole table. That is one explicitly chosen semantic (pattern:39) and it is the honest
one — a capability may only claim about what it was handed. It is also why `career-growth-review` will
correctly print `fetched: 0` rather than 148: it genuinely has no fetched postings in front of it, and
saying so is the whole point of the ticket.

## 6. Why the QA is discriminating

The ticket asks for "an arm that writes a capability row and asserts the fetched count does not
change." A naive implementation would pass that arm by keying on `data.text` instead of `source`,
because every write-back observed so far is text-less. The kickoff's fixture therefore writes a
capability posting **carrying `data.text` and `status:'new'`** — a row that enters match-finder's
population and that any text-based or unfiltered count would pick up. Only a count keyed on `source`
leaves `fetched` unchanged while `write_backs` rises by exactly 1. The arm also asserts
`before.posting_coverage.fetched >= 1` as a control premise, so an implementation returning all zeros
cannot pass vacuously.
