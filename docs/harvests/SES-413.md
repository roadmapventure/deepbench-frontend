## Premise revalidation — ALIVE, measured live 2026-09-18 over MCP

The rule (`governance_rules.MANAGER-DECIDES-BY-DEFAULT`, sentence 3) promises John that "a question that still reaches him is counted weekly, target zero." Slice 3 made that number *visible* on the standing brief (`docs/runbooks/standing-brief.md:177`, "0 question(s) reached you in the last 7 days — target zero"). Slice 4's claim is that it is not yet *graded*: the platform cannot hold a ticket to it.

- `public.platform_scoreboard` has 14 columns — `id, taken_at, week_start, trigger, backlog_id, push_sha, noship_cycles_week, noship_tokens_week, shipped_cycles_week, tokens_per_shipped_cycle, cycles_per_shipped_ticket, cron_silence_hours, hygiene_flags, notes`. Seven are metrics; none counts questions. 52 rows, newest `2026-09-16 16:37Z`.
- `public.outcome_claim_is_valid(text)` — one overload, `claim text`, IMMUTABLE — hard-codes exactly those seven names, and `ck_backlog_outcome_claim` on `backlog_items` is `CHECK (outcome_claim_is_valid(enhancement_claim))`. So today a ticket that tried to claim `questions_to_john_week: down` would be **rejected at filing**, which is the sharpest possible proof the premise is alive. 118 rows carry a claim.
- `public.snapshot_platform_scoreboard` — one overload, identity `(p_trigger text, p_backlog_id text, p_push_sha text, p_hygiene_flags integer, p_notes text)`; `docs/runbooks/runner-cycle.md:3364` and `docs/runbooks/session-setup.md:732` both call it with four arguments.
- `public.runner_questions`: 40 rows, 17 open, newest asked `2026-08-31`, **0 in the last 7 days** and 0 since `enhancement_week_start()` (`2026-09-18 07:00Z`).

Verdict: **alive**, and closable in one cycle.

## The defect a naive version would ship, and the one that would be invisible

`public.ticket_outcome` grades a claim with `(to_jsonb(sh.*) ->> c.metric)::numeric`, where `sh` is a CTE reading `SELECT DISTINCT ON (s.backlog_id) s.id, s.taken_at, … s.notes FROM platform_scoreboard s` — **fourteen columns enumerated by name**, not `s.*`. Add the column to the table and the function, leave the view alone, and `before_value` is NULL for every ship while `after_value` (which joins `platform_scoreboard af` directly) resolves fine: the CASE falls to `'unmeasurable'` and stays there permanently. Nobody gets an error; the metric simply never grades. That is why the view is replaced in the same migration, and why the migration's own DO block asserts the viewdef names every metric column rather than trusting a reviewer to remember next time.

Writing the CTE as `s.*` does **not** future-proof it: Postgres expands `*` at view-creation time, so the next column added is missing again. The loop assertion is the durable guard; the star is not.

## Design choices

- **Compute inside the function, add no parameter.** `.claude/rules/supabase-function-signature.md`: a new parameter is a new overload, both live, PostgREST can no longer resolve the four-argument call the runbooks make, and the failure presents as an empty result. Nothing about this measure needs an input — it is a count over `runner_questions`, exactly as `cron_silence_hours` is a window function over `runner_cycles`.
- **Trailing 7 days, not `enhancement_week_start()`.** Two reasons. (1) It is the window slice 3's brief line already uses (`since = now − 7d`), so the graded number and the rendered number agree by construction instead of by coincidence. (2) `ticket_outcome` compares a ship row with the newest row at least 72 hours later; a calendar-week counter resets mid-comparison, so a claim could read `held` because the week rolled over rather than because the work landed. `cron_silence_hours` in the same body is already trailing-7-day, so this is a precedent, not an exception. The cost, stated plainly: the column's name ends `_week` while its window is rolling, exactly like `cron_silence_hours`' "worst silence over 7 days".
- **Every row asked in the window counts, whatever its `status`.** The ask is the event the rule counts; answering it does not un-ask it. Same predicate as the brief.
- **Nullable, no backfill.** The 52 historical rows never measured this, and `ticket_outcome` reads a NULL `before_value` as `unmeasurable` — the honest verdict for "not measured then". A `DEFAULT 0` would manufacture a measured zero for two months of history nobody counted.
- **No `d_questions_to_john_week` delta column.** Dropping it keeps `runner-cycle.md`'s "all five deltas beside it" true, which keeps that file's edit to a single byte-neutral word swap (it sits 24 bytes under the `SES-336` ceiling of 381,000, at 380,976). The metric still grades — `before_value`, `after_value` and `verdict` all come from the jsonb lookup, not from the delta columns. Worth filing later if a questions regression ever needs to show unclaimed.
- **No grant work, verified rather than assumed.** `information_schema.role_table_grants` for `platform_scoreboard` returns rows only for `postgres` and `service_role` (7 privilege types each) — no `anon`/`authenticated` row at all, so there is no column-list grant that a new column could fall outside of (`.claude/rules/supabase-column-grants.md`'s fail-closed case does not apply here). `ses-303`'s existing arm — anon cannot read the table — stays green.

## The down capture, and why it comes back `refused`

`capture_migration_down()` classifies the **whole call**: one refusal sets `classification = 'refused'` and `down_sql = NULL` for every object in it. An `ALTER` of an existing table is always refused (`kind: table` + `to_regclass(...) is not null` → refusal), so naming the table refuses the call. The three capturable objects still have their prior definitions recorded in `prior_ddl`, and `runner-cycle.md`'s own `4a-quater` note sets the precedent for the consequence: a red range containing this migration is **card-only**, and the ship is not auto-rollbackable. Splitting the capture into two calls to manufacture an `auto-downable` row would be gaming the mechanism; hand-writing a down is explicitly forbidden.

## The QA problem this ticket has that most do not

The live count is **0** and has been since 2026-08-31, so "the number is 0" is exactly what a column that was added and never computed would also show — except that one reads `NULL` and the other reads `0`. The kickoff's probe therefore asserts both halves: a fresh snapshot reads `0` (not NULL) on an untouched database, and the same call reads `1` with one fixture question inserted. It runs inside a `DO` block that ends in `raise exception`, so the fixture question, both probe scoreboard rows and everything else roll back — no `runner_before_images` obligation, no residue, and the two numbers arrive in the error message.

## Alternatives considered and dropped

1. *A parameter on `snapshot_platform_scoreboard`.* Rejected on the signature rule above; nothing needs an input.
2. *A `questions_to_john` view plus a scoreboard read of it.* Rejected: the scoreboard's whole contract is that the function computes its numbers from live tables at stamp time; a view adds a second home for one `count(*)`.
3. *Counting only `status = 'open'` questions.* Rejected: the rule counts asks, and an answered question still reached John.
4. *Making the brief read the scoreboard instead of `runner_questions`.* Rejected as scope: slice 3 shipped three days ago and its number is already correct; two readers of one predicate is acceptable while the predicate is one line, and the trailing-7-day choice keeps them equal.
