## 3. The design (the Designer's calls, recorded and reversible -- JOHN-0925-DESIGNER-DECIDES)

**Mechanism: a dedicated Postgres role switched by a JWT role claim -- PostgREST's standard, documented pattern (pattern:101: standard practice, not homegrown).** Live this turn, `get_publishable_keys` shows the legacy HS256 anon JWT still enabled (`type legacy, disabled false`) beside the `sb_publishable_…` key, so this project's PostgREST still verifies HS256 tokens signed with the project JWT secret; a token whose `role` claim is `lean_lane` switches the connection to that role, and Postgres grants -- not function bodies -- are the gate.

- **Call 1 -- role `lean_lane`**: `CREATE ROLE lean_lane NOLOGIN NOINHERIT; GRANT lean_lane TO authenticator;` (authenticator's members today: anon, authenticated, service_role). `statement_timeout=3s` like anon.
- **Call 2 -- four SECURITY DEFINER functions, `SET search_path = public, pg_catalog`, owner postgres**, each the exact SQL `scripts/lib/session-db.mjs` `SQL` already carries verbatim from `docs/runbooks/session-setup.md`, with no `updated_at` bump (SES-316):
  1. `lean_claim_ticket(p_ticket text, p_session text, p_write boolean default true) returns jsonb` -- when p_write: the §2c UPDATE (`status <> 'done' AND claim_exclusion_reason(claimed_by, claimed_at) IS NULL`) RETURNING; then always returns `{claimed, backlog_id, claimed_by, claimed_at, status}` read from the row, so a 0-row claim names the holder without the role needing SELECT on backlog_items. `p_write=false` is the register-B42 re-assert: a READ, never a re-claim (claimed = claimed_by = p_session).
  2. `lean_release_claim(p_ticket text, p_session text) returns integer` -- the holder-guarded release, rows affected (q-claim-release-order: after the push, never in the status write).
  3. `lean_claim_version(p_session text) returns text` -- `UPDATE dev_version_counter SET patch = patch + 1, updated_at = now(), updated_by_session = p_session WHERE id = 1 RETURNING 'v'||major||'.'||minor||'.'||patch` (the `trg_dev_version_counter_issue` trigger records it in `issued_versions` as today).
  4. `lean_file_ticket(p_session text, p_prefix text, p_title text, p_description text, p_priority_class text, p_tier text default 'now', p_type text default 'bug') returns text` -- ONE id from `feature_id_counter` by `INSERT … ON CONFLICT (prefix) DO UPDATE SET last_issued_number = GREATEST(feature_id_counter.last_issued_number, (select max(split_part(backlog_id,'-',2)::int) from backlog_items where backlog_id like p_prefix||'-%')) + 1` (environment fact 2026-09-15: the counter drifts behind the board), then one `backlog_items` INSERT with `status 'open'`, `scope_origin 'john-named'` (the lane is John typing on his phone; this also passes `backlog_requires_finding` -- which otherwise RAISES "only The Development Manager files tickets" -- and `epic_lock_guard`/`requirement_gate`, both of which pass john-named; `backlog_home_intake` fills epic_id), `source_file 'lean-lane'`, `row_ordinal` = the id number (UNIQUE(source_file,row_ordinal)), `tier` in now/next/later (CHECK), `type` non-null when tier <> later (CHECK `ck_backlog_type_when_promoted`), title not a bare class string (CHECK `ck_backlog_title_not_class_string`). Returns the backlog_id. The id block for N>1 rows stays the connector's SQL (§3b) -- the lane files one ticket per call, which is what a phone session does.
- **Call 3 -- grants, asserted both ways in the migration's trailing DO block, never trusting the success flag (SES-315, `.claude/rules/supabase-column-grants.md`)**: for each of the four: `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated; GRANT EXECUTE … TO lean_lane, service_role;` then `has_function_privilege('anon', …, 'EXECUTE')` must be false and `('lean_lane', …)` true or the block RAISES and the migration rolls back. `pg_default_acl` live grants EXECUTE to anon/authenticated/service_role BY NAME on every new function (row `f`/postgres: `{postgres=X,anon=X,authenticated=X,service_role=X}`), which is why the revoke names the roles. lean_lane additionally gets: `GRANT SELECT (id, meter_stale_hours, session_max_tickets, session_max_context_tokens, daily_max_tokens_millions, claim_stale_hours) ON runner_settings`, `GRANT SELECT ON runner_usage_readings` (what `meter()`/`budget()` read), `GRANT EXECUTE ON FUNCTION recompute_backlog_queue() TO lean_lane` (close-session step 5). Nothing else: no SELECT on backlog_items, runner_secrets, or any other table; zero write grants. Not a widening of any existing grant -- every grant is to the NEW role.
- **Call 4 -- the key**: a JWT `{"role":"lean_lane","iss":"supabase","iat":<now>,"exp":<now+365d>}` HS256-signed with the project's JWT secret, named `SUPABASE_LEAN_KEY`. Minting needs the JWT secret, which lives only in the Supabase dashboard (Project Settings -> API -> JWT Settings); the migration cannot mint it. So the close of P1 hands John ONE plain-words chore (pattern:91): copy the JWT secret from that page, run the one-line Node command the runbook gives (prints the token, nothing else), add the token under the name `SUPABASE_LEAN_KEY` and `SUPABASE_URL` to the cloud environment's settings (environment menu -> Edit -> Network secrets / environment variables), and store the same token in `runner_secrets` by name (so the record of what exists is complete and a scheduled lane could use it). Rotation = mint again, replace in both places; revocation = `REVOKE lean_lane FROM authenticator`. **Known dependency, stated:** if the project's legacy HS256 keys are ever disabled in the dashboard, custom HS256 tokens stop verifying; the fallback is the same four functions taking a `p_key` argument compared against a `runner_secrets` row (the ADM-2 owner-passcode precedent, directive b2252555) with EXECUTE granted to anon. Reversible; not built now.
- **Call 5 -- the scripts keep ONE Postgres caller** (pattern:17, `session-db.mjs` header's own rule): `credentials()` accepts `SUPABASE_LEAN_KEY` first, `SUPABASE_SERVICE_KEY` second (the routine and GitHub lanes keep working unchanged); `claimTicket`/`reassertClaim`/`releaseClaim` POST `rpc/lean_claim_ticket` / `rpc/lean_release_claim`; `claimVersion()` becomes a real `rpc/lean_claim_version` call returning `{claimed:true, version}` (its `claimed:false … channel supabase-connector` shape was the honest answer to "no RPC exists", which P1 ends); new `fileTicket()` -> `rpc/lean_file_ticket`. `open-session.js` prints the claimed version instead of "run over the supabase-connector" SQL (its §3 print path at the `out.version_claim` lines) and gains `--file=<title>` for the lane's filing step. `close-session.js` needs no edit (it only calls session-db exports whose signatures are unchanged).
