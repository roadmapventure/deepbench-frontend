## Design choices, and what this ship does not do

1. **Type is a new column; source reuses `found_by`.** A new `source` column would duplicate `found_by` for 92 rows and force every reader (`render-standing-brief.js:1883`, `audit-ledger.js --report` line 241) to change. The CHECK is `not valid` so the 27 joined rows stay legible history — the guard forbids rewriting `found_by` anyway.
2. **Backfill `'defect'`** is a statement about 92 rows that are all governance-audit findings (duplicate/contradiction/redundant/stale/other from the Auditor, carries and one hand review). After the backfill there is no default: a writer that names no type is refused (fail closed, the same direction as `.claude/rules/supabase-column-grants.md`).
3. **One ingest core** (pattern:14). `auditor-write.js` today re-implements `doIngest()`'s loop; the two agree only by discipline. `ingestFindings()` with injected `get`/`post` lets the CLI, the handler, `staff-watch.js` and `ticket-owner.js` share it without importing `process.env` into the handler (its header's own reason for existing).
4. **The Auditor's type default lives at the source boundary** (handler default `'defect'`, merge default `'defect'`), not in the schema. The intent schemas do not yet carry `finding_type`; letting the model name `security` is an Auditor Enhancements change to `au-*-intent` traits, which is a Skill-row edit and not this ticket's (pattern:8, and SES-355's gate on prompt/skill pushes).
5. **`runner_staff_findings` is not dropped.** The promotion bar counts distinct cycles per fingerprint; `audit_findings` holds one row per (fingerprint, iso_week), so three cycles in one week would collapse to one `seen`. The raw log stays as evidence and every `--record` raises the finding into the one list — the same shape the ticket itself prescribes for `ticket_owner_findings`. Stated as a designer call, not John's.
6. **One owner finding per check, not per row.** 222 open rows would flood the manager with 222 findings whose locations churn nightly (a new fingerprint each night). A per-slug location `ticket_owner_findings:<slug>` with the count in `text` gives a stable fingerprint per (slug, week) and a finding that clears when the slug has no open rows.
7. **No SQL-side writer.** No in-database process reports findings today (`apply_gate_rulings`, `apply_audit_review`, `runner_should_boot` file tickets or rule; none observes). A plpgsql `report_finding()` would need a second fingerprint implementation (sha256 over normalised material) — two copies of the one rule. If an in-DB source appears, that is the moment to build it, with a cross-check test between the two fingerprints.
8. **Runner/builder residue filing** moves to findings in `AGT-133` (its BUILD text: "remove the runner's own residue-ticket filing"), which this ticket unblocks. `runner-cycle.md` has 24 bytes of headroom under the SES-336 ceiling (`SES-425` records the same constraint); editing it here would be a byte-freeing pass this ticket does not own.

## Alternatives rejected

- Widen `kind` to admit staff/owner kinds — mixes two taxonomies in one column; `kind:'other'` + `check_slug` keeps the Auditor's fingerprint semantics and names the source's check.
- A separate `findings` table with a view over three — three writers, three reviewers, the same hole one level up.
- Deleting `runner_staff_findings` and counting cycles from `audit_findings.cycle_id` — undercounts within a week (see 5).
