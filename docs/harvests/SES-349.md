## 3. Why this is staged, and what is blocked

Two different levels of risk sit in one ticket:

- **Stage A (this kickoff).** Three new tracked files nothing runs. Reach: zero sessions, zero agents. Undo: one git revert by any cycle.
- **Stage B (blocked here).** Adding the `hooks` block to `.claude/settings.json`. Reach: every Claude Code session whose working directory is this repo -- which is every cloud cycle. A false deny there stops Bash, Edit or Write in every cycle at once, and the cycles cannot repair it, because the repair is itself a `.claude/` write (register B39, runner-cycle.md step 0). Undo: an attended session only.

An unattended build cannot perform Stage B and must not try (CLAUDE.md, runner-cycle.md step 0: "an unattended cycle has no bounded recovery from this gate, so it does not enter it"). No task in the kickoff writes, stages, copies, symlinks or generates anything under `.claude/`; no task re-routes the edit through another tool. The test only READS `.claude/settings.json`.

My call on the RISK RULE's "changes agent autonomy" clause: Stage B does not grant or remove a decision any agent holds -- it mechanises rules already binding in CLAUDE.md -- so I did not return a cap case. It is still the part with the wide reach and the hard undo, which is why it is not in this build. If you read wiring deny-hooks into every cycle as an autonomy change, the right door is rule-cap-case with the two stages above as the parts; Stage A is unaffected either way.

What stays unused if only Stage A ships: all of it. The guards deny nothing until Stage B. The ticket's own discriminating QA (a fresh clone denies `cd x && git status`) is NOT met by this build and the ticket must not settle `done`.
