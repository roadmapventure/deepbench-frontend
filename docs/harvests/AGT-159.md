## 2. Alternatives weighed

- **Hand-rolled reviewer** (a script that rules tickets itself, or a second capability): refused by the ticket's own words and Rule #1 (§19b/§19d): the review is one capability and its effects live in the function.
- **A standalone `apply_backlog_review()` function**: a second write path over the same `audit_findings` rows and the same before-image discipline. Pattern:14/17 — extend the structure that fits. The limb is ~40 lines inside the loop the function already runs per finding.
- **Raise all 578 at once**: the coverage rule (`finding % not covered`) demands every open/carried finding be ruled in ONE call, and the manager prompt would carry 578 rows. 15 per `(7f)` run matches the ticket's "batching across cycles is fine" and keeps the manager's per-run cost bounded (today's outcomes worklist is 9 rows). Pattern:67 — the cap justifies itself against the coverage rule.
- **A once-per-Chicago-day guard or its own scheduled step**: more mechanism than the claim needs (pattern:66). `(7f)` already runs only when a run shipped/gated/reverted/failed.
- **`gap` as the default type**: refused. `audit_findings_gap_to_designer` (AFTER INSERT, `finding_type='gap' AND cycle_id IS NOT NULL`) writes a `runner_staff_findings` row charging The Designer a "gap finding" per cycle (AGT-136). A legacy ticket is not the Designer's miss; typing 400 of them `gap` would falsify the Designer's score (pattern:32, pattern:39). `proposal` is the honest default: a ticket is a request for change nobody has yet judged.

## 3. The Designer's calls (JOHN-0925-DESIGNER-DECIDES), all reversible through decision `D` and the ship decision

1. **Type rule** (pattern:99, structural over provable facts): project `security` → `security`; `priority_class 'P9 - Bug Fixes'` or `type in (Bug, Defect)` or `scope_origin 'discovered'` → `defect`; else `proposal`; never `gap`. Measured: 169 open tickets meet the defect rule, 8 the security rule.

3. **John's tickets are never closed by the manager.** `scope_origin='john-named'` (27 open) may be homed (`epic_lock_guard` already lets john-named rows into locked epics), listed, or escalated with `john_call 'rules'`; supersede and not-a-defect RAISE. The manager "works inside his rules and never overrules them" (`JOHN_CALLS.rules`, audit-review.js:74).
4. **`general` writes nothing.** A ticket in an Intake epic stays there; a homeless one stays homeless and AGT-166's nightly homing places it. The ruling is recorded on the finding (`ticketed`, `filed_backlog_id = <itself>`, ruling text carrying the project pick) — that is the "recorded general-backlog ruling" the ticket's done-clause names.
5. **A reviewed ticket is never re-filed.** `root-cause` without `reuse_backlog_id`, or `cleanup`, over a backlog-review finding RAISEs: the ticket already exists.
6. **One `filing` decision per review call**, as AGT-132 shipped it, carries every group line; the ticket's "every ruling is a runner_decisions row" is met by that row's reasoning listing each group, not by one row per ticket (pattern:17, pattern:126).
7. **Skip rule**: a ticket that is any finding's `filed_backlog_id` already carries a manager ruling (21 open today) and is not raised again.

## 5. Intent paragraph — appended to `dm-audit-review-intent.method` by task 5, byte-for-byte

THE BACKLOG REVIEW (AGT-159, 2026-09-28; rules JOHN-0925-FINDINGS-STANDARD, JOHN-0925-ROUTING-PRECEDENCE). A finding whose check_slug is backlog-review IS an existing ticket: its locations[0].location reads backlog_items:<ID>, its text is the ticket's title, its governing_fact the ticket's own description. Tickets filed before the findings process existed, and every ticket AGT-166 homed into a backlog-intake epic by prefix, reach you this way, fifteen per run. Rule each one with the kinds you already use, and the platform lands the ruling on the ticket: root-cause with reuse_backlog_id equal to the ticket's own id plus a project (a projects.slug whose charter fits, or general) HOMES it — general leaves it where it is and is itself the ruling; root-cause with reuse_backlog_id naming ANOTHER open ticket SUPERSEDES it (status removed, the reused id written into its description); not-a-defect CLOSES it with your reason; list parks it when the fitting project's list is locked; escalate with john_call rules when only John can decide. Never widen a project's charter to make a ticket fit (John 2026-09-25). Never file a ticket for a backlog-review finding — the ticket exists; root-cause without reuse_backlog_id and cleanup are refused for it. A ticket whose scope_origin is john-named is John's: home it, list it or escalate it, never close or supersede it. Each finding's location text carries the ticket's scope_origin and current epic in brackets, so you rule from data, not memory.

## 5b. Why (d) is not mirrored offline

`validateReview()` mirrors only what a worklist row can answer alone: (a) and (e) key on `check_slug` and `locations[0].location`, both on the row. (d) needs the ticket's `scope_origin`, which lives on `backlog_items`; like the existing `reuse_backlog_id must be an open backlog row` rule it stays the function's. The manager still sees it: the location text carries `[<scope_origin>; epic <name|none>]`, so a john-named ticket is visible before he rules.
