# AGT-112 — which side is right, the pin or the card? (harvest)

Not required reading. The kickoff carries every fact its tasks depend on.

## The design question

`skill_profiles.dm-knowledge-cycle-card.traits.source_sha256` pins `fbe7fb2b340fd4f8`;
`docs/runbooks/cycle-card.md` renders `8e57fb17a0710310`. Repinning blindly would launder whatever
the card currently says into the Development Manager's Knowledge, so the card had to be proved
correct first.

## Verdict: THE CARD IS RIGHT, THE PIN IS STALE

Three independent measurements, all on this worktree at `a3c4ac6d`:

1. `node scripts/render-cycle-card.js` (check mode) exits **0**:
   `docs/runbooks/cycle-card.md is current — 8633 bytes, 27 steps, docs/runbooks/runner-cycle.md
   sha256 0e551729478e04cd`. Check mode renders the card from the runbook in memory and diffs it
   against the committed bytes; exit 0 means they are identical. The card is a pure view of the
   runbook, so "correct" is exactly this equality.
2. `tests/regression/ses-377-cycle-card.test.mjs` is **green** on the unchanged tree — the same
   equality asserted from the suite rather than the CLI.
3. `docs/runbooks/runner-cycle.md` itself is at its last-shipped bytes: 380,667 B, exactly
   `ses-413d`'s `BYTES_AT_SHIP` (a `strictEqual`, green) and 333 B under SES-336's 381,000 ceiling
   (`ses-336-runbook-orchestration`, green). Nothing is half-edited underneath the render.

So the repair is "repin to the card", not "regenerate the card then repin".

couples the repin to the render.

Confirming there is no guard to strengthen:
`grep -n "sync-knowledge\|repin" docs/runbooks/runner-cycle.md` → **0 hits**. The runbook never
asks any cycle to repin. This is not a weak instruction that failed twice; there is no instruction.

## What `--sync-knowledge` / `--repin` actually do (read first-hand)

`scripts/render-cycle-card.js`, lines ~247-415 and 417-490:

- `knowledgeRow(cardText)` builds the target row from the card's **current** bytes every time —
  `method` = the card, `traits.source_sha256` = `runbookSha(method)`. No literal, so the pin can
  never disagree with the text it pins.
- `knowledgeSyncState(live, cardSha)` → `absent` | `current` | `drifted`.
- Bare `--sync-knowledge`: prints the intended row and the live classification; **exit 0** for
  absent/current, **exit 1** for drifted (writes nothing), **exit 2** if it cannot read (missing
  card, missing env, REST failure). Deliberately not self-healing.
- `--repin`: refuses *before writing* if `--cycle-id` or `--ticket` is missing (exit 2), or if the
  row is not drifted (exit 2 when already current via `repinPlan()` returning null — the CLI's
  not-drifted branch exits 0 with "already current", the plan-null branch exits 2). Then:
  `record_decision()` (`kind='agent-row'`, `p_backlog_id=<ticket>`) → one
  `runner_before_images` row with `row_data` = the **full live row** (an UPDATE's undo is a
  restore) → `PATCH skill_profiles?slug=eq....` moving `method` **and** `traits` together
  (`repinPlan().patch`) → read-back that throws unless the row classifies `current`, naming the
  `reverse_decision()` call if it does not. Exit 0 on success, 2 on failure.

## Does the build touch `docs/runbooks/runner-cycle.md`? NO

Stated explicitly because it decides three other things. It does not, and must not:

- `ses-413d`'s `BYTES_AT_SHIP = 380667` is a `strictEqual` against the live file, which reads
  exactly 380,667 B. Any edit reddens it until the constant moves.
- SES-336's ceiling is 381,000 B → **333 bytes of headroom**. An edit would likely have to remove
  bytes first.
- An edit forces a card re-render → a new sha → a **second** repin inside the same session, with a
  hard ordering constraint (repin must follow the render, and the QA's expected sha changes).

Keeping the runbook out is what makes this a one-command repair with a stated expected sha on both
sides. It is also why the recurrence guard below is deliberately *not* a runbook step.

## Recurrence guard: warranted, and repo-side

Yes. Two drifts in one night, from two different tickets, by the same mechanism. Options weighed:

- **Runbook step telling cycles to repin.** Rejected. It is a third wording where there were zero
  (pattern:10 — go structural), it costs bytes from a 333 B budget, and it re-renders the card,
  which re-drifts the pin the same session.
- **DDL / trigger.** Not permitted this cycle, and the pin is a repo-derived value; the database
  cannot see the card.
- **A ship-time check running `--sync-knowledge`.** Already exists in effect — `ses-424e` runs the
  real `--sync-knowledge` in the suite and is one of tonight's three reds. Detection is not the
  gap; detection works. The gap is that detection fires *after* the drifted card has shipped.
- **Chosen: gate `--write`, the single point where the card can change.** `writeGate()` — a pure
  export, so the test drives it without Supabase — refuses a *changing* `--write` that has no
  `--ticket` / `--cycle-id` / credentials, before a byte is written; a passing changed write then
  falls straight into the existing `repinKnowledge()` under the same handle. Render and repin
  become one operation, which is the coupling that is missing (pattern:19 — gate the dangerous path
  through an atomic correct path rather than blocking it; pattern:14 — one shared seam). A no-op
  re-render still needs no flags, so the common "re-render to check" case is untouched.

Checked before proposing: **no test in the repo executes `--write`** (`grep` over
`tests/regression/*`: `ses-377`, `agt-79-ticket-owner` and `ses-385b` reference it only in message
strings or run the renderer *without* the flag). Nothing existing depends on the old behaviour.

## Not done, and named

- The eight unrelated reds are untouched; each is its own ticket.
- `writeGate()` gates `--write` only. `--sync-knowledge --apply` (the seed path) is unchanged; a
  fresh seed still needs its own `--cycle-id`.
- This does not make the pin self-healing on a tree with no credentials — that case fails closed
  (refuse to change the card), which is the platform's stated direction but is a behaviour change
  a future ticket may want to soften with an explicit opt-out flag.
