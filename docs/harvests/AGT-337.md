## A session note that did not hold

The session note said "RLS is off on agents, so the browser COULD insert directly with the anon key". Measured: `anon` and `authenticated` hold SELECT only on `agents` and `agent_teams` (`information_schema.role_table_grants`), and column-level SELECT on `teams` (every column but `address`). ## Live schema the save writes against

- `agents`: `id text` PK, `name text` NOT NULL, `lane` NOT NULL default `product` (CHECK product / governance / personal), `sharing` NOT NULL default `private` (CHECK private / users / public), `shared_with text[]` NOT NULL default `{}`, `is_active` default true, `agent_origin` default `system`, `owner_id text` null, `tenant_id uuid` null, `skill_score` default 0. No triggers.
- `teams`: `id uuid` default, `name` NOT NULL (CHECK not blank), `address` default made by the database, `owner_id text`, `sharing` default `private`, `tenant_id text` default `global`; UNIQUE NULLS NOT DISTINCT (`owner_id`, `name`). No triggers.
- `agent_teams`: PK (`agent_id`, `team_id`), both FKs ON DELETE CASCADE.
- `capabilities`: `slug` UNIQUE, `name` NOT NULL, `execution_type` default `ai`, `default_intent_slug`. `agent_capability_assignments`: `agent_id`, `capability_slug` (FK to `capabilities.slug`), `tenant_id` NOT NULL, no default. No triggers on either.
- Foreign keys into `agents` without cascade: `agent_revenue_splits`, `briefings`, `customer_agents`. A new agent has no rows there, so the compensating delete is safe.

## What an agent needs to be reachable at its own MCP address

`vercel.json` rewrites `/api/mcp/:agent` to the executor with `agent=<id>`. `api/_lib/mcp.js` `fetchCapabilityRows()` builds one row per CAPABILITY whose first assigned holder is an active agent; `visibleRows()` keeps a row when `lane === 'product'` (or the governance key is held) and the row's `agent_id` equals the addressed id. So an agent is reachable only when all four hold:

1. `agents.lane = 'product'` (no key needed);
2. `agents.is_active = true`;
3. a `capabilities` row exists whose holder is that agent (`agent_capability_assignments`);
4. if that capability is `deterministic`, its `default_intent_slug` names an Intent with `traits.handler` (else the row is dropped).

Brittany satisfies it with one row made today in session ux-ui-1003: capability `brittany-knowledge` (deterministic, `default_intent_slug = 'agent-bundle-intent'`, whose traits name handler `agent-bundle` and require `agent_id` as input) and one assignment.

A blank created agent (an `agents` row alone) satisfies 1 and 2 and fails 3: its address answers an empty tool list, and Personnel's "Connect <first name> to AI" popup (shown for every private agent) would hand out an address with nothing behind it. That is a defect this ticket would introduce (pattern:124), so the save writes the agent's own `<id>-knowledge` capability and assignment, modelled on Brittany's row. The description states the id to pass, because a generated id cannot be guessed the way `brittany` can.

Not changed: the bundle tool takes the target `agent_id` from the caller, so a caller on one agent's address can ask for another product agent's bundle. That is AGT-333's existing behaviour, not this ticket's.

## How the create rides the route (alternatives)

- A new `api/` file: refused, the deployment is at 12 of 12 (`ses-346` pins it).
- A capability through the generic executor: this is not an agent acting, and a route per capability is the banned shape; a deterministic handler under `api/_lib/handlers` is reached only through MCP today.
- A query parameter (`?resource=agent`) versus a body `action`: the body form keeps one URL and leaves `middleware.js` untouched. Chosen: body `action: "create_private_agent"`.
- A Postgres function for atomic writes: needs DDL, a down-capture and grants (functions default open, SES-315). Chosen instead: ordered PostgREST writes with a compensating delete, all in the module. HAR-39 can replace it with one transaction.

`middleware.js` (HAR-33) gates every POST under `/api/`, so a visitor outside the US or over the trial cap gets the existing access popup instead of a save. That is existing, approved behaviour and it is also the only brake on anonymous row creation. No rate limit exists beyond it.

## Id scheme

`<slug of the name, 24 characters at most>-<6 random characters a-z0-9>`, always suffixed.

- Every existing id is a bare word with no hyphen, so a suffixed id cannot collide with one, and can never equal the route words `new` and `test` (`/bench/new`, `/bench/test`).
- A bare slug would be dangerous: `agt-120` and `agt-164` word-match every live agent id against seed text (Rule #1), so a user agent with id `marketing` would turn them red. A suffixed id cannot appear as a word in prose.
- 36^6 is about 2.2 billion per slug; the primary key is the authority, and one retry covers a collision.
- A name with no Latin letters or digits slugs to `agent`.

## Owner

The day a login exists the route passes the signed-in user's id from the session, never a value the browser sends. Consequence to know: under `canSeeAgent()`, a private agent with a null owner is visible to nobody once viewers arrive, so the rows created before login need an owner backfill at that time. Filed as an open item below.

## Slice 2 (v7.0.763)

Design reasoning for the broker fence. Not required reading for the build.

### Premise: alive

Measured 2026-10-03 on tree `397d4f06` (branch `session/user-agents-1003-coding`) and the live database.

- `lib/project-manager.js:51` reads `agents?is_active=eq.true&lane=eq.product&select=id,name,role,skill_score,situational_awareness,rating,is_active`. It never reads `sharing`, and the file imports nothing from `shared/agent-visibility.js`.
- Slice 1 (`lib/private-agent-create.js`, v7.0.762) writes `lane: "product"`, `is_active: true`, `sharing: "private"`, so every created agent matches that read today.
- Live: 33 agents; 24 are active and product-lane; 24 of those 24 are `sharing = 'public'`.

### The fence, and why it is not a filter in the fetch string

The fence is `visibleAgents(agentRows, { id: null })`, applied to the fetched rows before anything is derived from them.

- One rule. `shared/agent-visibility.js` is the one "who may see this agent" check, and `api/_lib/mcp.js`, `api/_lib/handlers/agent-bundle.js` and `src/hooks/useAgents.js` already ask it. A `sharing=eq.public` clause in the fetch would be a second copy of that rule (pattern:14, pattern:17).
- What "visible" means for the broker today: the delegation roster is shared by everyone, so it is read as a viewer with no identity. `canSeeAgent()` gives such a viewer `public` rows only. `agt-336-agent-visibility.test.mjs` already pins that branch (`canSeeAgent(PUB, {})` true, `canSeeAgent(PRIV, {})` false). Passing `null` would mean "no login exists" and show everything, which is the wrong reading for a shared roster.
- The existing pins force the same choice. `ses-330-governance-lane.test.mjs` matches `/agents\?is_active=eq\.true&lane=eq\.product&select=/` and its control replaces the literal `is_active=eq.true&lane=eq.product&select=`; `agt-69-governance-section.test.mjs` holds the same literal as `BROKER_FILTER`; `agt-120-nathan-laan.test.mjs` needs both clauses and a select starting `id,name,role`. A clause placed before `is_active` or between `lane` and `select` turns one of them red. Appending columns to the select list touches none of them.
- LOO-37 says filter at the source so the roster context, the chunks and `matchCount` describe one set. The filter runs on the agents array before the map that builds all three, so they still describe one set.
- It can be tested without a database. A fetch filter is applied by the database, so only a live fixture insert could prove it; the function filter is proven by a stubbed fetch. The stub was dry-run against the unchanged tree: public-only rows give `matchCount` 2 and the expected roster line; rows with a private and a users-shared agent give `matchCount` 4.

### Proof it changes nothing for today's agents

- By measurement: all 24 roster rows are `public`, so the filter keeps all 24, in the order the database returned them.
- By construction: the map that builds the roster reads only `id`, `name`, `role`, `skill_score`, `situational_awareness`, `rating`, `is_active`. The three added columns are read by the visibility check and nowhere else, so no roster line changes.
- By test: arm (b) pins a public agent's full roster line and is green before and after the edit.

### The private agent's knowledge capability

`fetchRoster()` reads every `capabilities` row, but a capability reaches the prompt only through an agent that is in the roster. With the agent filtered out, `<id>-knowledge` has no holder in the roster and is never printed. Arm (a) checks the context holds neither fixture id, which covers the capability slug because it starts with the id.

### Designer's calls (reversible)

1. Shared check with a no-identity viewer, not a fetch filter.
2. `users`-shared agents are out of the roster as well. They are opened to named people, not to everyone's delegation.
3. A row with no sharing level is not offered (fail closed). The column is NOT NULL live, so this cannot happen from data; it happens only if a later edit drops the column from the read, and the control in arm (c) catches that as an empty roster.
4. `isActiveAgent()` is unchanged: a private agent may still ask for the roster. A blank created agent holds one deterministic capability and runs no delegation, so nothing reaches this today.
5. No live test arm. A check that every live roster row is `public` would turn red the day a user makes an agent (pattern:162), and the shared test slot is jammed today. The Builder re-measures the count once at ship instead.

### Coupled files checked and left alone

- `.claude/rules/agent-roster-inert.md`: the rendered `AGENT-ROW-AGREED-TICKET` block is not touched. `docs/governance/RULES-SNAPSHOT.md` names the file only as that rule's home.
- `api/prompt/ai-enrichment.js` is the one caller of `getRosterCandidates()`; its inputs and outputs are unchanged.
- `src/data/agents.js:3` and several kickoffs quote the fetch filter in prose; the filter text is unchanged.

### Not done here

- When logins arrive, the broker could pass the signed-in viewer so a user's own private agents join that user's roster. That is a product call for then.
- The executor's holder lookup has no sharing check, so a direct executor call naming a private agent's capability still resolves. The MCP path already applies the visibility check. Not this slice.

### Could not verify

- Whether `--check-kickoff` graded the anchors block: its output names only the byte count and the Lanes line. The four anchors were resolved by hand with `git grep -F -l` (excluding `docs/kickoffs/` and `docs/harvests/`): each is in exactly the one file named.
- The baseline ran without credentials in the child processes, so the live arms of the four named tests declared themselves not run.
- The rule file's new bullet was not run against the corpus and tripwire checks that read `.claude/rules/`.

Patterns leaned on: pattern:14, pattern:17, pattern:65, pattern:66, pattern:85, pattern:162.

### How the roster is re-read after a save

No `useAgents.js` edit. Measured: `useAgents()` fetches `agents` in a mount effect with an empty dependency list, and `/bench` and `/bench/new` are separate `<Route>` elements in `src/main.jsx`, so `RosterScreen` unmounts when the user opens the create screen and mounts again on `navigate("/bench")`. The alternative was an exported `refreshRoster()` in `useAgents.js` awaited before the navigate. It costs a file, which would push the empty-quip fix out of the slice, and the save would wait on a second round trip. If live QA shows the gap is noticeable, that function is a one-file follow-up.

The session note "after a save the roster must be re-read or the new card will not appear" is true of the cache alone and already satisfied by the mount fetch.
