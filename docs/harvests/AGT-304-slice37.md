## 3. Design and alternatives

- **Arm E grades both doors against one live read.** The live read gains `family`; `live` = all ids, `outcomes` = ids with `family !== "paperwork"`. The `--weekly` run keeps every existing assertion verbatim (exit 0/3 branch, worklist deepEqual, `weeks_seen >= 1`, `john_calls` keys, `open_audit_tickets` array) and adds `scope === "weekly"`; a second default run asserts exit `outcomes.length ? 0 : 3`, `scope === "outcomes"` and the worklist deepEqual to `outcomes`. 59 -> 63 asserts. The exit-3 branch for "all live findings are paperwork" is the AGT-239 D3 contract (`buildTaskContext` returns null -> `die(3, NOTHING_TO_REVIEW)`), so the arm cannot red on a live world with only paperwork open (pattern:162).
- Rejected: asserting only the `outcomes` door (drops the arm's original sentence); filtering the live read to `family <> paperwork` and keeping one run (hides the weekly door, which the Auditor routine's step 4 uses); `notRun` when paperwork is present (hides a real contract behind the transport, pattern:166).
- **`allRows` is paged by `id`, not filtered.** `getPage(offset)` + `for (let page = await getPage(0); page.length; page = await getPage(allRows.length))` -- 4 GETs at 2,399 rows (1000/1000/399/0), correct under any server `max-rows` at or below 1,000 because the offset is the rows actually received, and correct at 24,000 rows (pattern:1). Rejected: `fingerprint=in.(<worklist fingerprints>)` (slice 33's form) -- `promotableOthers()` needs rows across ALL fingerprints, so a named filter changes what `promotions` means; a `limit=10000` single read -- PostgREST caps the reply server-side regardless; `Range` headers -- `rest()` takes no headers and the query-string form is equivalent.
- Siblings that spawn `--prepare` live and were run on the rendered script from a scratch tree: agt-86i-learning-loop `[PASS]`, agt-133-run-tail-review `[PASS]` (both read `promotions`/worklist shape only). agt-239-outcomes-first imports `buildTaskContext`, which is unchanged.
