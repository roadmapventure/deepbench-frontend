# LOG-121 — Caller Attribution on Every AI Call

Design harvest, `design-log-121`, 2026-08-01. The `docs/FEATURES.md` row points here.

## Scope

John's ask 2026-08-01, scope approved same day (`design-scaling-arch-0731`): build **(a)**
`call_source` and **(b)** IP/org logging now, defer **(c)** the full identity model until
accounts/billing matter. Designed 2026-08-01 and split into two coding sessions along the
write/read seam. **`Post-beta`** — call attribution, nothing on the beta demo surface.

## The three measurements that forced the mechanism

The obvious cheap options were both ruled out by data, not preference:

| Option | Why it fails |
|---|---|
| Thread `call_source` as a `logActivity()` parameter, like `retrieval_scope` (`DAT-12`) | **45 call sites across 15 source files** — `lib/librarian.js` alone has 25. An order of magnitude past any session's file budget. |
| Log once per request, join the rest by `trace_id` | **58.3% of the last 30 days' rows carry no `trace_id`**, and they are not a clean class — spread across every `ai_type`, including `agent-turn` at 30%. The join would drop most of the log. |

What made the chosen mechanism viable:

> **`logActivity()` is a genuine single writer — 27,948 of 27,948 rows in the 30 days to
> 2026-08-01.** The client-side browser insert in `src/hooks/useAIActivity.js` (~L779) wrote
> **zero**. So a request-scoped context read *inside* `logActivity()` covers 100% of traffic
> with no call-site edits at all.

Hence `AsyncLocalStorage` (Node's standard request-context mechanism; all 12 routes are already
`runtime: "nodejs"`). Verified absent from the repo — nothing to reuse or extend.

## `S-LOG-121a` — capture side (v7.0.34)

Kickoff: `docs/kickoffs/v7.0.34-LOG-121a-caller-attribution-capture.md`.
Migration `log_121a_caller_attribution_columns` applied by the design session — five nullable
columns on `ai_activity_log`: `call_source`, `caller_ip`, `device_type`, `visitor_id`,
`request_host`.

- New `lib/request-context.js` wraps all 12 `api/` route handlers (three mechanical edits each,
  no body restructuring). `logActivity()` reads the store as its first statement.
- Regression driver tagged by **header** in its single `HDRS` constant, never a body field —
  that is precisely what clears the `SES-57` mirror-payload trap, since the driver hand-rebuilds
  the screen's *body* and has no second header constructor to drift.
- **Zero `src/` changes.** The visitor cookie is server-minted (`Set-Cookie`, `HttpOnly`) and
  returns automatically on same-origin `/api/...` fetches; `call_source` defaults to `ui`, so the
  UI never declares anything. Only non-UI callers opt out.
- `caller_org` is deliberately **not** a column — it lives in `ip_org_cache`, joined at read time,
  so an org can be re-resolved later without rewriting log rows.

### The cookie-rejection rule (John's question, 2026-08-01)

**Only a visitor id the browser actually sent back is logged.** A freshly minted id is set on the
response but written as NULL on that request.

| Case | Behavior | Result |
|---|---|---|
| Cookies accepted | Request 1 logs NULL; requests 2..N log the real id | Costs the first row of each new visitor |
| Cookies rejected | Every request logs NULL | Collapses to **one** honest bucket, grouped by IP |

Writing the minted id instead would render a single cookie-blocking visitor as **one distinct
platform user per request** — the drawer's central number, silently and unfalsifiably wrong.
`visitor_id IS NULL` therefore means exactly one thing: *this browser has not demonstrably stored
an identity.* Nothing in the path may throw or block: attribution is observability and must never
become a failure mode for the platform.

### Accepted limits

- `call_source` is self-declared and therefore spoofable — a hostile caller could claim
  `regression`. Not defended: its job is separating traffic John controls, and `caller_ip` /
  `visitor_id` would still expose an imposter. An unrecognized value lands as `null`, never
  silently as `ui`, so a spoof attempt reads as unattributed rather than trusted.
- Tablets commonly report desktop (modern iPad Safari sends a desktop UA). Desktop-vs-mobile is
  reliable; tablet is not a category to trust.
- `src/hooks/useIsMobile.js` is a 768px **viewport** query and is deliberately not reused — a
  narrowed desktop window reports mobile there. The two are expected to disagree.
- IP-level identity remains coarse (office NAT collapses many people; phones hop addresses).
  The visitor id is what carries identity across IP rotation on one browser.

## `S-LOG-121b` — read side (not yet designed)

- `ip_org_cache` table + IP→org resolver, resolved **once per distinct IP**, with its own
  `platform_services` row per §19m. The resolver must never call `logActivity()` — it is called
  *from* the logging path, so a logging call inside it is infinite recursion.
- **By Platform User** drawer in AI Audit, positioned after By Agent, holding two sections:
  *By Source* (`ui` split three ways — John / Claude (QA) / Public — plus `regression`,
  `session-test`, `unattributed`) and *By Caller*.
- **The two sections' totals must reconcile exactly** — they are two cuts of the same rows.
  Worth a regression assertion rather than a convention.
- Must group NULL-`visitor_id` rows by `caller_ip` rather than dropping them or rendering them as
  one anonymous lump.
- Splitting John from Claude: the public hits `deepbench.roadmapventure.com`, QA hits the dev
  preview, so `request_host` separates them; scripted Claude traffic self-tags via `call_source`;
  and Claude's browser-driven QA runs in a *separate browser profile* from John's Chrome, so it
  earns its own `visitor_id` automatically.

## No history is recoverable

None of the five facts was ever written anywhere, and none is derivable. The most promising
derivation — fingerprinting past regression runs by their `quality-gate` / `hypothesis-evaluation`
rows — was tested and fails twice over: the UI references those capabilities too, so the
fingerprint is not exclusive, and there have been **zero of either since 2026-07-18**, so it would
attribute nothing in the recent window anyway. Vercel's own access logs do carry request IPs but
share no request identifier with `ai_activity_log`, so they cannot be joined even in principle.

Per §19i, historical rows stay NULL. The drawer therefore carries a dated
`Unattributed (pre-<date>)` bucket — **23,392 all-time countable calls** at design time (first row
2026-04-23) — so it still reconciles with the header tile instead of reading as a broken drawer.

**Consequence: every day the capture side is undeployed is attribution that cannot be recovered.**
That is why `a` ships first and alone.
