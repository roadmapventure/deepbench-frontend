4. FEATURE DETAIL

**Mechanism (verified via code read, `api/prompt/request-receivable.js`):**
- `parseModelTurn()` (~L128-153) validates a schema-tool call's `required` fields present-only; throws `Schema tool "<name>" called with missing required field(s): <list>` with `rawInput` = the actual (possibly partial) `tool_use.input` if any are missing.
- `callModel()` (~L209-313) retries exactly once on this error: sends a corrective message back to the model (AA-182's fix — cites the exact missing fields), retries the Anthropic call once. If the retry's own response *also* fails `parseModelTurn()`, it throws `Parse failed and retry also failed` (status 422), with `detail` built from the retry's own `rawInput` (~L299-306) — this is the exact error shape recorded in `durable_hops.error` for every real HAR-9 failure.
- `library-catalog-intent`'s schema (from Supabase `skill_profiles.traits.schema`): `required: ["answer", "citations"]`, `citations` is the last property. `max_tokens: 1500`, `temperature: "0"` (already pinned by prior fix AA-166).

**Root cause (verified against real Supabase data, not assumed):**
`max_tokens: 1500` is undersized for this intent's real output — cataloging/verifying up to 22 real `the_library` entries with per-entry `[id: ...]` citations routinely needs close to or over 1500 tokens. The model's tool-call JSON gets cut off before it can emit the trailing `citations` field (last in the schema), on both the initial call and the retry alike (retrying doesn't reduce the length need) — producing the recorded two-strike failure.

Evidence pulled live from Supabase (project `rallojeqnkgtxgsdsnqm`):
- Every examined `durable_hops` failure row (14 read in full) shows `raw_input.answer` cut off mid-word/mid-sentence (e.g. "...Horizon Store (Vietnam) [id: bda49008-c") — never a clean, complete answer simply missing citations.
- Two failure rows have `raw_input: {}` (both `answer` and `citations` missing) — consistent with the retry attempt truncating even earlier.
- `ai_activity_log.output_tokens` for `data-room-custody:library-catalog-intent:*` cluster near/at 1500 on many single-attempt successes (e.g. 1442, 1436, 1429, 1426) and near double (2830, 2850, 2852) on calls that needed the built-in retry — confirming this call routinely runs close to or over the 1500 ceiling.
- **Corrected impact count:** searching `durable_hops.error` for the literal string `Schema tool "library-catalog-intent"` (regardless of the row's own `intent_slug` column) returns **28 real failed rows**, not the 14 filed directly under `intent_slug = 'library-catalog-intent'`. The other 14 are filed under the *delegating* intent's own hop (e.g. `qg-review-intent`, `ci-answer-intent`) — when Owen or Marcus delegates to Eleanor mid-chain and her call fails, the failure is recorded against the delegator's hop, not hers. This is one call site, not several — not a multi-site bug pattern.
- Comparable sibling intent `ci-answer-intent` (Marcus's own verbose grounded-answer intent) is already set to `max_tokens: 3000` — the proposed fix reuses this existing number rather than inventing a new one.
