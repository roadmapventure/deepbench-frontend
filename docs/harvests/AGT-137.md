## Premise revalidation — ALIVE, both halves

**Half 1, the per-run review.** `capabilities` holds seven `audit-*` slugs live — `audit-agent-data`, `audit-governance-corpus`, `audit-board`, `audit-board-health`, `audit-work-quality`, `audit-config-review`, `audit-advisor` — and no `audit-run-review`; `agent_capability_assignments` gives `auditor` six of them. `grep -rn "run-review|au-run-intent|per-run" scripts docs/runbooks api` returns one unrelated line (`tripwire-to-backlog.js:34`). Nothing in `runner-cycle.md` step 9 calls an Auditor. The weekly pass's only runner-operations input is the advisor job's `limits_hit`, defined in the runbook as `select outcome, last_step, count(*) from runner_cycles where started_at >= now() - interval '7 days' and outcome in ('did_not_run','failed') group by 1,2` — the ticket's sentence, verbatim in the file. Measured over the same window I could read: **139 cycles since 2026-09-18 — 67 `shipped`, 53 `did_not_run`, 8 `gated_before_build`, 3 `failed`, 8 still open.** Every ship's verdict gates, every gated card's reason and every filing made inside those runs are outside any reviewer's input today.

**Half 2, the pushes.** `docs/runbooks/auditor-routine.md` still ends in two push steps: line 120 (`Step 6 — John's calls`, `SELECT * FROM public.claim_john_alerts()`, "one push per row") and line 122 (`Step 7 — the summary, always. One push`). The prompt block repeats both (lines 26-27), and step 0's stop is "one push to John". `claim_john_alerts()` is `UPDATE public.john_alerts SET notified_at = now() WHERE notified_at IS NULL RETURNING *` (`v7.0.542`, AGT-86 slice 1a) — a claim, not a read. So the naive edit (delete the push, keep the call) would stamp every alert as notified with nobody notified; `john_alerts` is empty today, so nothing has been lost yet. AGT-146's harvest recorded the same hole from the other side: `render-standing-brief.js` has zero hits for `john_alerts`, so an unclaimed money ask has no surface either.

## The design, and why this shape

- **Where the invocation goes.** The ticket says the runner tail. Step 9's serial tail already ends `(7d) THE STAFF WATCH PROMOTES` → `(8) A DRAINING CYCLE`, and (7d) is the precedent: a tail step that reports and never gates. (7e) sits between them. The runbook is 380,976 B against SES-336's 381,000 ceiling, so the task removes 163 B of dead history from (7d) first — the same "remove before adding" AGT-79 already did in this step. `ses-378f-staff-watch-caller.test.mjs` pins only `--promote --apply` inside step 9's span, and `ses-423b` pins a `v7.0.516` *stamp header*, not this parenthetical, so the deletion is safe.
- **Which runs are reviewed.** `drain_chain_gate()`'s gate A already defines "ran a cycle" as `outcome ∈ shipped / gated_before_build / reverted` — a live rule, not a new one. `failed` is added (a run that died stopped something, and the ticket's use case names failures); `did_not_run` is the one exclusion, which is the ticket's own lean rule and costs nothing on the 53 no-op cycles a week.
- **Script before model (pattern 9).** `--prepare` is deterministic: it decides reviewability and assembles the context; only exit 0 spends a model call. This is `audit-review.js`'s `--prepare` / exit 3 / `--apply` shape, already proven in step 4 of the weekly routine (pattern 17).
- **One intake.** AGT-131 shipped `ingestFindings()` (`audit-ledger.js:426`) at `v7.0.596`; the per-run review writes through it with `found_by 'auditor:run-review:<cycle>'` and a per-finding `finding_type`, which is exactly the ticket's "source + type + location" rule. No second write path, no new table.
- **Where the report lands instead of John's phone.** `record_decision(NULL, '<session>', 'audit-report', …)`: `runner_decisions.kind` is free text, ten rows already carry `session_name like 'auditor-%'`, and `render-standing-brief.js:1543` ("Decided for you") renders every row by CST day with its reverse handle. Step 6 stops claiming and only reads `notified_at is null`, so an alert stays unnotified until John has a notification path again — his switch, not the platform's (pattern 166). The same mechanism AGT-146 chose for the model-watch routine, so both routines report one way (pattern 163).
- **Attribution.** `runner_before_images` has the CHECK refusing `cycle_id` and `session_name` together; the tail passes `--cycle-id`, an attended run passes `--session-name`, both is exit 2.

## What it does not do

- It does not touch the runner's own pushes (cycle-open, stall, close-out). The ticket's sentence is about the Auditor's, and pattern 90 says implement it literally; the rest is John's to ask for.
- It does not update the live routine. Editing the block puts the runbook and the routine out of step until John runs the `RemoteTrigger update`; `check-routine-prompt.js` will report exit 1 (a finding, never a stop) at the next fire, and the STOP LINE tells him so.
- It does not build the Development Manager's per-run review of findings (the ticket's cadence sentence). The manager's `review-audit-worklist` already reads `audit_findings` weekly; pointing it at a per-run window is its own item once findings from this path exist.
- It does not add a "waiting on John" section to the brief — AGT-146 already filed that gap.
