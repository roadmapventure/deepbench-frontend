## 3. The home, and what "daily" means here

AGT-239 is done and its frame is live: `scripts/audit-run-review.js --prepare` calls
`audit_flow_checks()` on every reviewable cycle, files each element through `ingestFindings()` as
`auditor:flow:<cycle>`, and the elements ride in `au-run-intent`'s task_context under the `flow`
key. That job runs per cycle -- many times a day -- so a check whose window is 24 hours is asked at
least daily without a new routine, a new cron or a new script. The Auditor's own weekly routine
(`0 10 * * 1`, `docs/runbooks/auditor-routine.md`) is the wrong home: it would ask once a week.

One row per day comes from the ledger, not from a scheduler: `fingerprint()`
(`scripts/audit-ledger.js:195`) is `sha256(kind | sorted locationKeys | normalized
governing_fact)`, `locationKey()` strips only a trailing `:<digits>`, and `audit_findings` is
`UNIQUE (fingerprint, iso_week)`. Putting the America/Chicago date in the location therefore makes
the day's first file the row and every later file that day a no-op `seen`.

## 4. The five calls (JOHN-0925-DESIGNER-DECIDES, each reversible)

1. **One slug, `flow-nothing-produced`, family `blocked`.** `audit-review.js` ranks service 0,
   blocked 1, everything else 2. A platform that produced nothing is a blocked pipeline, so it
   should reach the review ahead of `flow` and `other`. AGT-239's guard accepts `blocked` or
   `flow` for a flow check, and `runner_settings.finding_families` maps on `found_by`
   (`auditor:flow:% -> flow`) while an explicitly-set family lands as written, so `blocked` holds.
2. **Four answers in one finding, not four slugs.** The four questions are only meaningful read
   together: pickable 6 with zero done is a different day from pickable 0 with zero done. Four
   slugs would also file four rows a day into a ledger John reads.
3. **America/Chicago for the day and the week** (pattern:140). "Did anything happen today" is
   John's day, not UTC's. `date_trunc('week', ...)` on the local timestamp gives his Monday.
4. **No new threshold key** (pattern:67). `window_hours` is already 24 in
   `runner_settings.flow_check_thresholds` (`{filing_min:10, wasted_pct:25, filing_ratio:2,
   window_hours:24, gate_red_days:1, ship_open_days:1, wasted_min_cycles:8}`). A new knob would
   need to justify itself against a bound that already exists; it cannot.
5. **The `au-run-intent` edit is not in this build, and is not routed around.** AGT-496 asks for
   the slug to be added to the `au-*-intent` row whose task_context carries it -- that row is
   `au-run-intent` (`skill_profiles`, `skill_type_slug='intent'`), whose `method` already says
   "read `service` and `flow` before the record" and enumerates the task_context's reads.
   Editing it is an agent-row write on an ACTIVE agent, governed by
   `public.governance_rules.AGENT-ROW-AGREED-TICKET`. Measured this cycle:

   ```
   node scripts/agent-row-gate.js --ticket=AGT-496 --action=edit-active --json
   {"ok":false,"exitCode":1,"kind":"verdict","ticket":"AGT-496","action":"edit-active",
    "scope_origin":"victoria-placed",
    "need_source":"nathan:market_records:b46b817b-71ee-4f1e-9221-6be16f2c636d",
    "decision_names_ticket":false,"verdict":"gated","rule":"AGENT-ROW-AGREED-TICKET",
    "clause":"no-authority", ...}
   ```

   The precedent agrees: every ticket that has edited an active agent's intent row -- AGT-486,
   AGT-487, AGT-490 -- was `scope_origin='john-named'` with a `john:runner_decisions:` source, and
   AGT-516, which is `victoria-placed` exactly as AGT-496 is, edited only functions. The check
   does not need the row: `--prepare` files flow findings before any model turn, so the slug
   reaches `audit_findings` either way; the row edit only changes how the Auditor's model frames
   it. So AGT-496 settles `partial`, the gate verdict and the exact sentence are reported, and the
   sentence is NOT refiled under a new ticket id -- it is AGT-496's own acceptance criterion
   (pattern:95), and the gate is John's rule, not weakened by a degrade (pattern:166).

## 5. The alternative I rejected

I first specified a second function, `public.platform_produced_answers()`, returning the four
answers as jsonb for `audit_flow_checks()` and the test to share (pattern:14, one home). I dropped
it. The four existing checks all compute inline, so the helper was a parallel structure where one
already fits (pattern:17); as a NEW function it would have been born EXECUTE-able by `anon` and
`authenticated` by name (`.claude/rules/supabase-column-grants.md`, addendum 2026-09-02, found
live by SES-315), so it would have added a grant surface and two assertion arms to guard it; and it
pushed the kickoff past the 8,192-byte cap. The control it bought -- an independent oracle -- is
kept through the test's own arm B, which recomputes the four counts from its own REST reads and
asserts them against the finding's text, plus arm C's four degraded fixtures over the OR. No
function is created, so grants and the AGT-239 anon-denial arm stay as they are.
