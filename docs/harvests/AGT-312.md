## Why this shape (the Designer's recorded, reversible calls)

1. **The manager's proposal IS his agreement.** His turn exists only to say "this is what should reach John next" — `dm-propose-intent` already returns `summary_for_john`. Adding a second boolean to his schema would be an unrequested extra field (pattern:90) that can only ever be true when a proposal exists at all. The two agreements John named are therefore: the proposal (his), and `review.verdict = 'agree'` (hers).
2. **Her answer travels as `p_proposal.review`, and both agreements sit on the ONE `proposal` decision.** Rule #1 (§19d/§19e): the proposal reaches her as `task_context.proposal`, a row of her task file written by `--for-review`, never agent to agent; her answer reaches the function as a key of the same `p_proposal` the manager's answer already rides. The decision's reasoning then carries his reason and hers (`Review: agree -- <reason>`), so one `reverse_decision()` undoes the whole finish exactly as today. A second decision kind or a `projects` column would be a parallel structure (pattern:17) with nothing to reverse that the first does not already cover.
3. **The refusal is the function's, checked before the due read.** `finish_project_batch()` is SECURITY DEFINER, `service_role` only, and already the one writer of `proposed` — the narrowest layer that actually works (pattern:8, pattern:19). Placing the review check after attribution but BEFORE `project_batch_state()` is what makes the live, no-write regression possible: any non-due epic answers the new sentence to a review-less call and `not due` to the agreed control, over PostgREST, with zero fixtures. The cost is one line in agt-240's arm D (T5), which must now send an agreed review to keep reading `not due`. `propose-project.js` mirrors the texts offline (`validateAgreement()`), the shape `validateProposal()` already has, so a dry-run shows the refusal without a request.
4. **A `disagree` refuses the write; the batch stays due; the manager re-proposes ONCE with her reason; a second disagree stops the run.** This is the smallest thing that must be decided for the function and the runbook to be well-defined, and it reuses the loop the runbook already has for a `--dry-run` refusal rather than inventing one. Deliberately NOT designed here: negotiation between the two, escalation to John on a split, a third agent, a tie-breaking rule — John's ruling says a split does not reach him, and nothing he said asks for more. If a richer protocol is ever wanted it is a new ticket with his words.
5. **A new capability, not a sibling intent on `requirement-check`.** AGT-281 added a sibling intent because the judgment was the same (does a cited source support a ticket) at a different unit. Here the judgment is different: does this proposal need John's attention. A capability is a row (§19b): one `capabilities` INSERT, one intent Skill, one link, one assignment — the AGT-240 shape — plus one `SERVICE_CATALOG` line so `agent-log.js` accepts `--ai-type=review-proposal` (SES-338). Zero harness change.
6. **No model turn in the build.** Nothing is due, so her turn cannot run live; the migration's trailing DO (rolled back by a sentinel, AGT-240's own probe fixture) and the live PostgREST pair prove both directions the ticket asks for: an agreed proposal is written `proposed`; a manager-only one is refused and never reaches John's list.

A `--dry-run` refusal → re-run the manager ONCE with the refusal lines appended; a second refusal → no review turn, no `--apply`, the summary quotes the refusals, and the batch stays due for the next run. Sub-agent on the printed model → `$S/review-answer.json` (`{verdict, reason, account}`); log it: `node scripts/agent-log.js --agent=victoria --capability=review-proposal --model=<printed> --ai-type=review-proposal --feature=review-proposal:vc-proposal-intent:depth1 […]`. Then:
```
node scripts/propose-project.js --dry-run=$S/proposal.json --context=$S/propose.json --agreement=$S/review-answer.json
node scripts/propose-project.js --apply=$S/proposal.json --context=$S/propose.json --agreement=$S/review-answer.json --cycle-id=<the cycle id>
```
A `disagree` → nothing is sent; re-run the manager ONCE with her reason appended, then her turn again on the new answer; a second `disagree` → no `--apply`, the summary quotes her reason, and the batch stays due for the next run. `--apply` is `public.finish_project_batch()`: it refuses any proposal without an agreed review, then ONE `proposal` decision carrying both agreements (the manager's reason, then `Review: agree -- <her reason>`), before-images first — the finished project goes `done` (`paused` when perpetual), the proposed project and its tickets are written `proposed` (not picked), its findings `ticketed`.
