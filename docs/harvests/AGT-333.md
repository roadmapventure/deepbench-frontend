## 2. Where the server reads which agent ids may be addressed -- the decision

Three candidates were on the table:

1. **`src/data/agents.js isPrivateAgent()`** (benchGroups includes "private", AGT-332 slice 1). Frontend data; the server cannot import it, and the ticket's own text says the address is for private agents but the "private" fact is being moved to table rows by AGT-335..338. Reading it server-side would stand up a second home for one fact (pattern:14/17 violated) that is about to move anyway.
2. **A new column / allowlist on `agents`** ("may_have_address"). A new fact, a migration, and a thing to keep in sync -- and AGT-336 ("owner and sharing level on agents ... one 'who may see this agent' check") is the ticket that will own exactly this fact. Building it here would widen into AGT-336's charter (project scope is fixed).
3. **No new fact: any `agents.id`, fenced by the lane rule that already exists.** `visibleRows()` gains an optional `agentId` and keeps the lane predicate first, so `/api/mcp/<id>` shows the intersection of (what this caller may see on `/api/mcp`) and (rows whose holder is `<id>`). A product agent is open keyless, a governance agent needs the key, an unknown id matches nothing. This is pattern:68 (the simple mechanism that works today over scoping to a dependency that hasn't landed), pattern:65 (narrowest fix), pattern:63 (read paths open, nothing new gated), and it is the same posture AGT-162's agent-bundle handler already takes for the agent it is asked about.

Chosen: 3. When AGT-336 ships its "who may see this agent" check, it belongs in the same `visibleRows()` predicate -- one visibility function, three consumers, as today.

Why `addressedAgentId()` returns `''` (not `null`) for a present-but-malformed `agent`: `null` means "admin address", so a caller hitting `/api/capabilities/execute?transport=mcp&agent=a&agent=b` directly (array) must not fall back to everything. `''` matches no `agent_id` and the list is empty -- fail closed, which the ticket requires.

Why the filter compares `r.agent_id === agentId` and not a literal: `tests/regression/mcp-3-server.test.mjs` part (d) refuses any `agent_id === '<literal>'` in code lines (`.claude/rules/capabilities-are-data.md`). A comparison to a request value is not an identity conditional and passes the regex.

## 3. Alternatives rejected

- **Per-agent access switch instead of a per-agent address.** John chose the address (session ux-ui-1003, 2026-10-03). Not reopened.
- **A new `api/` file per agent or one `api/mcp/[agent].js`.** api/ is at 12/12 serverless functions (SES-346); a 13th refuses every dev deploy. The rewrite onto the executor's function is the only shape that fits.
- **A new MCP `serverInfo.name` per address (e.g. "deepbench-brittany").** Would make `initialize` differ by address and is attribution AGT-341 owns. Kept identical.
- **Defaulting `task_context.agent_id` to the address's agent for `brittany-knowledge`.** Tempting (the address knows who it is), but it is handler-specific behaviour wired from the transport, and AGT-340 ("a private agent's MCP address answers lookups") is where the address learns about its agent. Filed as Designer's call (iii), not built.
