## 2. Alternatives weighed

1. **Extend `pick_exclusions()` / `prime_directive_queue()`** and count rows with zero reasons per project. Rejected: the pick's predicate is a different semantic (queue number, scope rationale, enhancement cap, exclusive drain, 24-hour claim) — decision 1's "countable" would then move every time the pick's rules move, and today the exclusive drain alone would empty every project. pattern:40: two meanings, two names.
2. **A view instead of a function.** Rejected: the 6-hour claim rule and the "newest grade reason" lookup make it a function in practice, and the project's convention for every governance sensor (`runner_should_boot`, `pick_exclusions`, `project_batch_state`) is a function with its down captured.
3. **Hours as a `runner_settings` column.** The convention (SES-146) says cadence numbers live there, but an `ALTER TABLE` is refused by `capture_migration_down()` by design, making the migration card-only. A constant-returning function (`pick_blocking_flags()`'s shape) is captured cleanly, is one home `AGT-482` can read, and pattern:18 covers a fixed value John declared. If John later wants to tune it live, `AGT-482` or a successor can move it to a column.
4. **Build the STOPPED-BY-JOHN never-release here.** `AGT-482`'s own text names "the pick and the countable function" for both the 6-hour release and the STOPPED-BY-JOHN exception; `AGT-481`'s text names only "claim under 6 hours". Building it here would discharge half of another John-named ticket (pattern:64/95). Effect of leaving it: zero today (no STOPPED claim sits in an executing project). Named in the STOP LINE.
5. **Agent-named function (`victoria_countable…`).** Rejected under §19d/e Rule #1 and pattern:13: the sensor is the platform's, read by whatever routine or report asks.
