The 2,987 `call_source='mcp'` rows carry no client name anywhere: distinct `call_facts` keys on 1,000 sampled mcp rows are the bundle's own (`sections`, `guardrails`, `library_tier`, `role_prompts`, `library_records`, `target_agent_id`, `knowledge_entries`, plus `traits`/`tool_calls`/`execution_type`/`capability_slug`/`assembled_skill_slugs` on the 4 agent-turn rows). - `api/_lib/mcp.js` greps clean for `clientInfo` and `user-agent` (only the comment block that documents the handshake). `lib/request-context.js` reads `user-agent` once, for `deviceType` only, and discards it.

## 2. Which field — measured vs unverifiable

**Measured from code (file:line, tree `ad901741`):**
- `api/_lib/mcp.js:130-133` — stateless by construction, no `Mcp-Session-Id` is minted.
- `api/_lib/mcp.js:744-750` — `initialize` answers with version/capabilities/instructions and reads nothing from `params.clientInfo`; `:148-157` — the file writes no `ai_activity_log` row of its own, so a handshake can never produce a row.
- Therefore `clientInfo` is reachable only on the one message that logs nothing, and cannot be joined to the `tools/call` that does log, because nothing links the two requests. The `tools/call` request carries headers and the JSON-RPC body; the body has no client identity field in the handshake revisions this server speaks (`2025-11-25`, `2025-06-18`). `User-Agent` is the one client-naming field present on the logged request.
- The header survives the edge: `lib/request-context.js deriveDeviceType()` sets `device_type` from `sec-ch-ua-mobile` or the UA regex, and 46 mcp rows carry `device_type='desktop'` on hosts `deepbench.roadmapventure.com` and `deepbench-frontend-git-dev-roadmapventures-projects.vercel.app`. So a UA reaches the handler on real deployments.

**Not verifiable from this environment:** what Claude (claude.ai connectors / Claude Desktop) and ChatGPT actually put in `User-Agent` or `clientInfo.name`. No real client connection can be made from the cloud clone, and no existing row stores either string. The 46 rows above may be John's own curl/Node checks rather than an AI client — the `device_type` column cannot tell them apart. Consequence for the design: capture the raw string (pattern:43 — real value in the data, masking/normalising at display), and write the Claude/ChatGPT/other rule in slice 2 from strings actually observed, never from a guess pinned into a test (pattern:33, pattern:37, pattern:99).

## 3. Mechanism — the cheapest variant that proves the claim

- One handler-level wrap: `runWithCallSource('mcp', () => dispatchJsonRpc(...), mcpRequestContext(getRequestContext(), req.headers))`. `runWithCallSource()` spreads `extra` first (`lib/request-context.js:~330`), both seams call `getRequestContext()` and spread it through `mcpAttribution()` (`api/_lib/mcp.js:812-828, 852-876`), so the slot rides to the logger with no signature change on either seam and no edit to `mcpAttribution()` — agt-163's `mcpAttribution(ctx` ≥ 2 invariant stands.
- Rejected: reading the UA in `lib/request-context.js derive()` for every call source. A 4th file (cap 3, no rung), out of the ticket's "MCP boundary" scope, and it would start storing every browser's UA on `ui` rows — a new question AGT-341 did not ask.
- Rejected: a `call_facts` key. §19k: per-caller attribution values are plumbing columns "exactly like" `call_source`/`screen_origin`, never signature keys (the LOG-91 blast radius, 720 → 24,826 signatures). Also `call_facts` on MCP rows is written by the handler/`request-receivable.js`, not by `mcp.js`, so a key would need handler edits anyway.
- Rejected: a second row on `initialize`. Would double the audit's call count (the `rank-backlog.js` defect) and still not join to the call.
- Conditional body key (`...(ctx.userAgent ? { user_agent } : {})`) rather than `?? null`: a deploy racing the migration must not 400 every web-path insert (PostgREST refuses an unknown column). Ordering T1→T2 is still required for the MCP rows themselves.
- 256-char cap mirrors `deriveVisitorTag()`'s length-cap posture (nonsense guard, not a security boundary — attribution is observability).

## 4. Grants and the migration

Live (`information_schema`, `pg_class.relacl`): anon = `am` (table INSERT + MAINTAIN, the DAT-18/DAT-20 exceptions) plus a 27-column SELECT list (`caller_ip` excluded, LOG-124); `has_column_privilege('anon', …, 'caller_ip','select')` = false, `call_source` = true. service_role holds the full table grant. No triggers on the table. So a new column is unreadable by anon by construction; the gate asserts it both ways. Deliberately NOT granted this slice: no reader exists yet, and an unknown client's UA could carry anything — slice 2 grants it alongside `ACTIVITY_COLUMNS` once values are seen (supabase-column-grants.md: land the grant with the reader). `ALTER TABLE ADD COLUMN text` with no default is catalog-only (62,860 rows, instant) — well inside the connector's 60-second ceiling. `capture_migration_down` on an existing table's in-place ALTER returns `refused` by design; the runbook says record it and never hand-author a down.

## 5. Scope — why two slices under one ticket

Capture (mcp.js, activity-log.js, test) is already 3 files. The display half needs `src/lib/personnelActivity.js` (+ its test) at minimum — a 4th and 5th file with no rung for P4. STANDARDS §2's split rule (S[X]a/S[X]b) is the sanctioned mechanism, and AGT-338 shipped "slice 2" under its own id (v7.0.771) — so AGT-341 stays open rather than refiling its own acceptance criterion (pattern:95). Capturing now is also the §19i argument from LOG-121b: every day without capture is permanently unlabelled history. Slice 2 contents: `ACTIVITY_COLUMNS` + `user_agent`; a "Connected from" row per observed tool (name rule from observed strings, else the raw string, else `Unknown tool` — pattern:34); `grant select (user_agent) on public.ai_activity_log to anon, authenticated` with a both-ways gate.
