## A — the ticket's headline defect is not an estimator problem, it is one `if`

SES-409 reads as "build a measured estimator." The thing actually stopping self-observation is
narrower and cheaper, and the wrapper's first-hand report is exactly right.

`scripts/agent-log.js` is the only way a session-run governance agent lands an `ai_activity_log`
row. `parseCount()` (`:81-84`) is `/^\d+$/` on `String(value ?? '')`, so `undefined` fails; `parseArgs()`
calls it unconditionally at `:117-122`. No unmeasured path exists — the run exits 2 and writes nothing.

The file's header at `:57` justifies the requirement as *"(the DB's own CHECK constraint)"*. Checked:

```
ai_activity_log_tokens_nonneg_chk:
CHECK ((COALESCE(input_tokens,0) >= 0) AND (COALESCE(output_tokens,0) >= 0)
   AND (COALESCE(cache_creation_input_tokens,0) >= 0)
   AND (COALESCE(cache_read_input_tokens,0) >= 0)) NOT VALID
```

The `COALESCE` is there on purpose: **NULL passes.** `information_schema.columns` gives
`input_tokens` / `output_tokens` both `is_nullable = YES`. And the table already holds
**16,502 NULL `input_tokens` rows out of 44,033**. So the constraint the script cites as its reason
says the opposite of what the script does.

The whole downstream already speaks the language the script refuses:

- `lib/activity-log.js:90-91` — `inputTokens = null, outputTokens = null` are the parameter defaults.
- `shared/models.js:113-123` `computeCallCost()` — `if (!any) return null; // no tokens at all: unknown, never 0`.
- `scripts/agent-log.js:163` already passes `costUsd: null` explicitly (SES-383).

`scripts/rank-backlog.js:186-205` solved this exact problem under SES-386 and documents the reasoning
in its own comment: the absent pair returns `{}`, and `tokensFrom()` (`:247-253`) then yields `null`
rather than 0, *"because a stored 0 says the run was free"* (SES-147). That is the shape to port —
which is why slice 1 ports it rather than inventing one.

**The consequence, counted rather than asserted.** `runner_cycles`: 11 cycles started between
2026-09-18 18:00Z and now (first 18:41:18Z, last 2026-09-19 09:10:05Z). `ai_activity_log` with
`ai_type='agent-turn'` and `agent_id in ('designer','builder','devmanager')` in that same window:
**0 rows.** Lifetime totals are designer 60, builder 48, devmanager 25, and the newest of any of them
is 2026-09-18 13:06:56Z — before the chain started. At three mandatory rows per cycle that is
**33 rows that should exist and do not.** `docs/runbooks/runner-cycle.md:2878` already wrote down
what that means: *"the row did not land, so this run is unattributable and the Designer's own
throughput cannot be read off the log at all."*

**Alternative rejected: invent a split.** The harness reports one combined per-subagent total. Writing
`input=total, output=0`, or any ratio, would put a fabricated number where the platform's own cost
story reads. SES-147's rule already decided this class: NULL is *unmeasured*, 0 is *free*, and the two
must not be confused. Refusing to invent a split was correct; refusing to write the row at all was the bug.

**Alternative deferred, not rejected: a `--total-tokens` flag.** A single combined figure is genuinely
more informative than NULL, and `cache_read_input_tokens` exists as a plumbing column. But it changes
what a token column *means* mid-table, and the AI Audit's By-Service and cost views read those columns.
That is a data-semantics decision with a real audit blast radius and belongs in its own slice with
John on record, not smuggled into a slice whose job is to stop losing rows.

## B — SES-406 is alive, and SES-248 fixed the neighbouring half

Reproduced exactly, from this clone:

```
$ node scripts/tripwire-to-backlog.js --json 2>err
{"ok":true,"exitCode":0,"apply":false,"findingsTotal":118,"eligibleFindings":107,...,"detections":[]}
$ cat err
fatal: cannot change to 'C:/Projects/deepbench-frontend': No such file or directory
```

118 / 107 / `detections: []` and one `fatal:` line — identical to what SES-406 recorded on 2026-09-16.

Where it comes from is not where SES-406 guessed. `scripts/tripwire-to-backlog.js` contains no
`C:/Projects` literal at all; it shells the check suite. `SES-248` (v7.0.331) already fixed
`freshDevRoot()` — a candidate list, `SHARED_CHECKOUT` first, the running worktree behind it, plus an
aggregated WARN from `checkFreshDevReader()` when neither resolves. Two call sites were left behind:

- `scripts/check-session-docs.js:689` — `gitWorktreeList()` shells
  `execFileSync("git", ["-C", SHARED_CHECKOUT, "worktree", "list", "--porcelain"], {encoding:"utf8"})`
  with no `stdio` redirect (hence the inherited-stderr `fatal:`), and its `catch` returns `null` with
  the comment *"not fatal -- git may be unavailable in some sandboxes"*.
- `scripts/check-session-docs.js:968` — check 5b's `wtRoot = path.join(SHARED_CHECKOUT, ".claude", "worktrees")`.

And the WARN cannot save it: `checkFreshDevReader()` only fires when `freshDevRoot()` returns `null`,
and here it resolves fine — to this worktree. So checks 5/5b/5d are dead **with no warning at all**,
which is strictly worse than the state SES-248 was written to fix. This is `SES-245`'s
silent-all-clear class one directory further down, and it is why the slice requires the unresolvable
case to produce a *declared* "could not look" finding rather than an empty list.

`SES-248`'s header names one forbidden edit — reordering the candidates so the worktree is tried
first — and the kickoff repeats it, because the obvious "just use the worktree" fix is the one thing
that would break John's machine.

## C — LOG-150's cause is misstated, which changes which file gets edited

LOG-150 blames `api/_lib/handlers/prioritizer-write.js:165` for *"calling logActivity() with no
call-source context."* Read live, the handler is right and the callers are wrong:

- The HTTP path is already wrapped: `api/prompt/request-receivable.js:1500` is
  `export default withRequestContext(handler)`, and `prioritizer-write` is in its `HANDLERS` map (`:123`).
- The in-process callers are not wrapped, and do not even import the module:
  `scripts/rank-backlog.js:97` and `scripts/prioritizer-first-run.mjs:46` import `handle as prioritizerWrite`
  and call it bare. `grep runWithCallSource\|withRequestContext` over both files: **no hits.**

So the handler is correctly context-neutral — it inherits whatever ambient source its caller
established — and hardcoding a value inside it would be exactly the "central service before
hardcoding" mistake, and would label an HTTP call as a script. The fix belongs in the two scripts.
Pleasant consequence: **slice 1 touches no file under `api/`** and therefore sits outside the 12-function
cap question and outside `.claude/rules/capability-logging.md`'s `api/` surface entirely.

Live, 14 days, `feature like 'prioritizer:%'`: one row group — `call_source` NULL, **1,216 calls,
1,216 of them with NULL `input_tokens`**, latest `2026-09-19 08:58:11Z`. Not a historical tail: it is
still growing today, and LOG-150's filed figure (723 NULL of 1,299) has since become all of them.

`'session'` needs no new allowlist entry — `lib/request-context.js` added it under SES-331, and
`scripts/agent-log.js:73` already exports `CALL_SOURCE = 'session'` for precisely this caller class.
Nothing is back-filled: LOG-121's forward-only rule stands, so the NULL bucket stops growing rather
than disappearing, and the QA asserts exactly that.

## F — SES-412 is alive, and is deliberately not in slice 1

The false push is real and the mechanism is plain: probe (d), `docs/runbooks/runner-cycle.md:456-466`,
selects any open peer where `coalesce(heartbeat_at, started_at) < now() - interval '20 minutes'`.
The runbook's own heartbeat rule (`:404-408`) says a cycle heartbeats *"at every numbered step
boundary"* — and a Builder sub-agent occupies one step for its whole run, writing nothing. A normal
long build is therefore indistinguishable from a frozen one by construction.

Two reasons it is the STOP LINE's and not this slice's:

1. **The fix is not a threshold tweak.** A stall has to be judged against a signal a working build
   actually emits — the sub-agent still running, or an orchestrator heartbeat written while it waits.
   That is a new mechanism plus a change to how `stall_notified_at` is claimed, and SES-104's history
   on that same probe shows how easily two readers of one column drift apart.
2. **The byte ceiling.** `docs/runbooks/runner-cycle.md` is **380,976 B** against SES-336's
   **381,000 B** cap — 24 bytes. `tests/regression/agt-79-ticket-owner.test.mjs:827` and
   `tests/regression/ses-413d-questions-scoreboard.test.mjs:24-25` both pin it. Any runbook edit must
   remove bytes before it adds them, which is a real sub-task with its own review surface.

SES-409's second half (measure `est_tokens_dev`/`est_tokens_qa` from the session's own usage at close,
replacing `:4131`'s *"estimated is fine, labeled estimated"*) is a runbook edit for the same reason,
and pairs naturally with it. Slice 1 leaves the runbook untouched on purpose: **every runbook line
remains true after slice 1**, because the token flags stay accepted — only their absence stops being
fatal. That is what makes deferring the runbook safe rather than merely convenient.

## Scope note

uses 6 and 6. The three sub-defects it takes share one sentence — *a governance write that records
