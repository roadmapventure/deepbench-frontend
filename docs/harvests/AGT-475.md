## 1. Premise revalidation — ALIVE

**Function source, not ticket text.** `pg_get_functiondef` for both functions was read in full.

- `public.sweep_decision_windows(p_actor_cycle uuid, p_actor_session text)` returns
  `TABLE(finalized integer, promoted integer, closed integer)`. Its body is a single
  `for r in select d.* from public.runner_decisions d where d.status='open' and d.expires_at<=now()
  order by d.expires_at for update skip locked loop … end loop` with **no nested block and no
  exception handler anywhere**. The ship branch ends in `update public.backlog_items b set
  status = 'done' where b.id = v_item.id;`.
- `public.backlog_done_requires_verdict()` is a `BEFORE UPDATE OF status` trigger on
  `public.backlog_items` (`tgenabled = 'O'`, i.e. enabled). On `new.status='done'` over a homed
  epic it reads the latest `runner_verdicts` row and, when that verdict is `block` without a
  non-reversed `ship`/`ticket-status` decision or an `accept` `runner_items` row dated at or after
  it, raises with `errcode = 'check_violation'` (SQLSTATE 23514).

Because the raise is unhandled, it propagates out of the function and aborts the whole statement —
every earlier iteration's writes roll back with it. That is the defect, exactly as the ticket says.

**Direct probe (nothing committed).** Rather than calling the sweep — which would have finalised
6,007 real decisions had it *not* raised — I probed the trigger alone, inside a `DO` block whose
final statement always raises so the block can never commit:

```
do $$ declare s text; m text; n integer;
begin
  begin
    update public.backlog_items set status='done' where backlog_id='AGT-281' and status='delivered';
    get diagnostics n = row_count; s := 'NO_ERROR'; m := format('rows=%s', n);
  exception when others then s := sqlstate; m := sqlerrm; end;
  raise exception 'AGT-475 PROBE (nothing committed) sqlstate=[%] message=[%]', s, m;
end $$;
```

Result: `sqlstate=[23514]` with
`AGT-166: AGT-281 cannot be written done over its latest verdict block
(38959e02-fdd5-4858-bf19-11fc48fdc5d2) — record a ship/ticket-status decision or harvest John's
Accept dated at or after it first.` — the exact verdict id the ticket names. `AGT-281` is `status
= 'delivered'` and its epic is homed (`epics.project_id is not null`), so the guard's precondition
holds.

**The board.** 6,007 `runner_decisions` are `open` past `expires_at` (oldest
`2026-10-05 09:24:41Z`); 25 are `kind='ship'`; 16 of those sit behind a `delivered` ticket.
Of those 16, exactly one is unratified: decision `199f27ef-218c-4e56-991c-98992aaea425` /
`AGT-281`. Every other one has `ratified_by_decision = true`. Its ship decision expired
`2026-10-05 09:25:04Z`, making it the earliest ship row in the loop's `order by d.expires_at`.

**Independent confirmation from the suite.** `node scripts/baseline-red-set.js` on the unchanged
tree: `ses-320b-window-finaliser.test.mjs` is **RED (exit 1)** — "the decision-window finaliser is
NOT healthy: newest run carries an error: AGT-166: AGT-281 cannot be written done over its latest
verdict block". And `runner_finaliser_runs` shows **24 of 24** runs in the last 24 hours carrying
that message in `error` — the hourly pg-cron finaliser is failing 100% of the time.

## 3. The coupled file AGT-423's kickoff missed

`tests/regression/ses-320-delivered-exit.test.mjs` line 84 declares
`export const SWEEP_OUT = ["finalized", "promoted", "closed"];` and its credentialed arm asserts
`deepStrictEqual(Object.keys(rows[0]).sort(), [...SWEEP_OUT].sort())` against the **deployed**
function. A five-column sweep contradicts it. AGT-423's kickoff named only its own SQL mirror and
its own new test, so this would have surfaced as an unexplained red at the gate.

Why it is green today, and why it still must be fixed: that arm first counts decisions past
`expires_at` and, when the count is above zero, declares itself NOT RUN rather than writing the
live board (the SES-196 refusal). With 6,007 expired, the arm never runs. After the catch-up the
count is **1** — AGT-281's refusing decision stays `open` and past expiry by design — so it stays
NOT RUN. The red is therefore *latent*: it fires the moment AGT-281 is ratified. pattern:124 says a
defect a change introduces is fixed inside that change, so the kickoff spends a file on it.

The minimal edit preserves SES-320's own grading. `sweepOutDiff()` and
`assert.strictEqual(SWEEP_OUT.length, 3, …)` are historical controls: they prove SES-320 added
exactly one column. Re-pointing them would destroy that evidence. So the kickoff adds a *new*
constant, `SWEEP_OUT_LIVE`, for the deployed column set and re-points only the one deepStrictEqual.

## 5. The regression arm, and why it is the live board rather than a fixture

The brief asks for an arm putting one refusing ticket in a window beside two finishable ones. The
catch-up *is* that arm at scale and for real: 16 ship windows behind delivered tickets, one
refusing, the rest finishing. A synthetic three-row fixture would be weaker and actively unsafe
here — `SES-382` records that cycles run in parallel and shared-database regression fixtures collide
between them, and `SES-196` keeps permanent tests off the live write path. So the test grades the
*record* the run leaves: the newest `runner_finaliser_runs` row must carry `error` null **with**
`refused >= 1`. That pair is the whole claim — a refusal present while the run succeeded is
precisely what fault isolation means, and either half alone proves nothing. It then cross-checks
that every `backlog_id` in `refusals` still reads `status <> 'done'`, which is the "never silently
written done" direction.

## 6. Rules applied

- `.claude/rules/supabase-function-signature.md` — two new OUT columns are a new return type, so
  the sweep is `DROP` + `CREATE` by its full identity argument list, never `CREATE OR REPLACE`, and
  part (g) asserts exactly one `pg_proc` row remains. Part (e)'s `run_window_finaliser()` keeps its
  return type, which is why REPLACE is correct there and the DROP is not needed — the contrasting
  case, named so it is not copied by analogy.
- `.claude/rules/supabase-column-grants.md` (SES-315 addendum) — `pg_default_acl` grants EXECUTE on
  a new function to `anon`, `authenticated` and `service_role` **by name**, so the revoke names all
  three and (g) asserts both directions: EXECUTE false for the two public roles, true for
  `service_role`. The SELECT-side column-list trap does not apply: `refused`/`refusals` are added to
  a table whose grants are table-level to `service_role` only, which I checked rather than assumed.
