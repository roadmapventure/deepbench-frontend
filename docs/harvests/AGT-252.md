## 2. The design in one line, and why it is cheap

**Built vs. not covered is not a judgment. It is a join.** `AGT-250`'s proposal gives every element a
`source_document_id` and an `assumed` boolean. An element is *built from your documents* exactly when
that id is one of **this agent's own** `knowledge_entries.id`. Everything else — `assumed: true`, a
missing id, an id belonging to another agent — is *not covered*. So the panel computes the partition
deterministically and no model is put in charge of a value that already exists (pattern:9,
pattern:10); the one model call does the only judgment left, turning each not-covered element into a
question a trainer can answer in a sentence. Susan's call never sees the supported elements, so she
cannot narrate a document she did not read, which is the ticket's own guardrail made structural
rather than instructional.

**That is also what makes the QA discriminating.** A build that trusts the proposal's own claim
instead of proving `source_document_id` against this agent's rows passes every count until you hand
it an element carrying another agent's document id — michelle's
`49586170-2e0d-4702-9729-4b3ec7fe8384` in the fixture. Then it reports as *built for bob* something
bob's documents never said. That is precisely "inventing answers the documents do not support," and
it goes red.

## 3. Three sections, and no new screen

John's words name three things: what she built, what the documents did not cover, her questions.
An element that fails the `source_document_id` proof is tempting to give a fourth bucket
("unverified"). It does not get one: an unprovable element **is** not covered, which is literally
true, so it joins that list and earns its question. Three sections, his spec implemented literally
(pattern:90), and an empty section stays visible carrying Susan's own reason rather than vanishing
(pattern:34, pattern:113).

**On "the one new surface."** §19u rules out a dedicated Recruiter screen — *"the agent is the maker
experience; v1 interviews run on existing surfaces. (A dedicated screen is later polish, not
architecture.)"* The ticket asks for one new surface. Both are satisfied by a panel, not a route:
`/bench/:agentId` is `PersonnelScreen.jsx`, `TrainingTab` is defined in that same file, and
`TeachScreen.jsx:172` already returns the trainer to `/bench/${agentId}` the instant an upload saves.
The trainer therefore lands on Susan's report by doing nothing new. One file, no route — which also
matters because `scripts/check-api-function-count.js` reads **12/12 (Vercel Hobby limit), 0
remaining**: there is no API route left to add, so the panel reads Supabase from the browser. That
read is already open and needed no migration: `deliverables` grants table-level `SELECT` to `anon`
and `authenticated` (`information_schema.role_table_grants`), `relrowsecurity` false, 0 policies
(`pg_class`) — so `select=*` works and `.claude/rules/supabase-column-grants.md`'s column-list trap
does not apply here.

**Its own capability, not a second intent on `agent-authoring`.** `resolveDispatchIntent()`
(`api/capabilities/execute.js:597`) resolves a capability holding more than one intent-type Skill
Profile to its `capabilities.default_intent_slug`, which `AGT-250` sets to `agent-authoring-intent`.
A report intent added there would be catalogued and never dispatched. The `capability_skill_profiles`
rows are the Skill Profiles that assemble ONE prompt, not a sequence of runs — verified against
`api/prompt/db-assembly.js:657`, which orders them by `display_order` into a single assembly.

**Model.** `runner_model_lanes` read live: orchestrator `claude-opus-5`, judgment `claude-fable-5-1`,
mechanical `claude-sonnet-5`. `AGT-250` pins Susan's authoring call to `claude-opus-5` because one
call authors a whole agent. This call is much smaller — N questions, one per not-covered element, with
the partition already decided — so it pins `claude-sonnet-5` ($0.002/$0.010 per 1k in
`shared/models.js` `MODEL_PRICING`, against opus's $0.005/$0.025). Paying authoring prices for
phrasing would be pattern:125 run backwards. `claude-sonnet-5` is absent from
`NO_FORCED_TOOL_CHOICE_PREFIXES` (`["claude-fable-", "claude-opus-5-"]`), so the forced
structured-output tool call works.

## 4. Rejected alternatives

1. **Let the model write all three sections.** Rejected: it hands a model a partition that already
   exists in the data, and it is the exact mechanism by which a report invents a source.
2. **A second intent on `agent-authoring`.** Rejected — unreachable, §3 above.
3. **A dedicated report route/screen.** Rejected by §19u, and impossible within the API budget
   without a new page anyway; the Training tab is where the trainer already is.
4. **Collect the answers too.** Out of scope: the ticket says *ask*. Answering is its own surface
   (an interaction thread that survives being answered, pattern:142) and belongs with `HAR-39`'s
   write broker, not here.
5. **A fourth "unverified" bucket.** Rejected, §3.

## 6. The two interface facts `AGT-250`'s build now owes

Neither ticket is built, so this is a design-time fix, not a retrofit.

1. **`deliverables.title = 'agent-authoring:<target_agent_id>'`.** The proposal row carries
   `agent_id='susan'` (the author), and nothing on it names the agent it is *about*. `title` is the
   only free column the `store` handler writes (`api/_lib/handlers/store.js:16`), and it is sourced
   from the model's own output (`parsedResponse.title`, `api/prompt/request-receivable.js:1381`).
   So it is the panel's index and never its evidence — a model-written key gets you to the row, and
   the `source_document_id` proof decides what the row is allowed to claim.
2. **`source_document_id` on every element, and `assumed` as a boolean.** `AGT-250`'s kickoff already
   specifies both; this ticket is the consumer that makes them load-bearing, so its QA is where a
   regression in them surfaces.
