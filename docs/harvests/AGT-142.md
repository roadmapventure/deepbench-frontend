## Premise revalidation (alive)

- `public.runner_model_lanes` is a plain table (`pg_class.relkind='r'`), three hand-set rows, last written by hand SQL on 2026-09-09 (`updated_by` carries a decision id, no script owns a write). Readers found: `judgment_model()` and `orchestrator_model()` (function bodies via `pg_get_functiondef`, `prokind='f'`), `scripts/agent-prompt.js:138`, `scripts/audit-cluster.js:629`, `scripts/audit-corpus.js:682`, `scripts/export-governance-snapshot.js:265` (columns `lane, model_id, purpose`, fixed order orchestrator/judgment/mechanical). No view depends on it (`pg_depend` via `pg_rewrite`: none).
- `model_catalog` / `model_assignments` do not exist.
- `claude-opus-5-5` is unpriced in `shared/models.js` `MODEL_PRICING` and absent from `public.model_pricing`, while the cycle row for this very ticket (`runner_cycles` `777c9812`) records `model='claude-opus-5-5'` — the id has reached platform data without a price. `computeCallCost` returns `null` for it, which the LOG-149 header calls the "a logged model has no price" failure.
- The ticket's mechanism therefore still has nothing to stand on: the gap is real.

## The one thing the ticket did not know: `public.model_pricing` already exists

Eight rows (`model` PK, `input_per_1k`, `output_per_1k`, `updated_at`), relacl postgres + service_role only, read by `get_ip_stats()` (§19t, the IP gate's spend source) and reconciled against `MODEL_PRICING` by `tests/regression/log-149-api-dollars-ledger.test.mjs` part (e), which also requires every lane model to have a row there. A catalog with its own `list_price_in/out` columns would be a second home for the same number (pattern 14, 40, 93). Decision: `model_catalog.model_id` is a foreign key to `model_pricing(model)`. The ticket's "list price in/out" is satisfied by join, a catalog row cannot exist unpriced, and the existing gate and test keep their source. The migration adds the `claude-opus-5-5` row to `model_pricing` (0.004 / 0.020 per 1k) in the same transaction, before the catalog insert, so the FK holds.

`model_pricing` has no cache-read column; `get_ip_stats()` applies the 0.10x convention. Opus 5.5 publishes $0.20/MTok (0.05x of input). The JS constant carries `cache_read_per_1k: 0.0002` as Fable's row does; the table is left alone (an in-place ALTER is refused by `capture_migration_down` and the gate's approximation for existing models is unchanged). Filed nowhere: it is a rounding difference on a model no lane runs yet; AGT-146's watch is the place that learns rates.

## Why "kept in sync" rather than "becomes a view"

The ticket allows either. `capture_migration_down` (function body read live) refuses `kind='table'` when the table already exists — "the up ALTERs it, a lossless down is not derivable". Dropping `runner_model_lanes` and creating a view of the same name is exactly that refused shape: the migration would classify `refused`, the ship becomes card-only and not auto-rollbackable (runner-cycle.md step 6). Keeping the table and adding two NEW functions and two NEW triggers makes every object in the migration a fresh object, classification `auto-downable`, six captured, zero refusals. The down drops the triggers, functions and tables; `runner_model_lanes` keeps its rows, which the mirror kept identical, so a rollback is byte-neutral for every reader. The `model_pricing` row for opus-5-5 survives a down (rows are not objects); harmless, and LOG-149 (e) tolerates JS keys the table lacks and table rows the JS prices.

The guard trigger makes the sentence "one table is the single source" (walkthrough Q3) true at the database, not by convention: a direct write to `runner_model_lanes` raises unless the sync function set `deepbench.lane_sync=on` for the transaction. AGT-144's capability writes `model_assignments` and never the mirror. The guard is created after the seed so the seed's own mirror write passes through the sync path once.

## Seed choices

- Lane rows copy `updated_at` and `updated_by` verbatim so the mirror row after the migration equals the row before it — QA (c) asserts the three CONTEXT values, which is what "today's behavior unchanged" means measurably. `since` = the lane's `updated_at`.
- Complexity bands are the walkthrough's three (hard judgment / orchestration / mechanical) mapped to the lanes by the register B21 purposes. The two capability rows (`data-room-custody` on haiku, `bench-report-card` on sonnet-4-6) get `mechanical` because their models sit below every lane's model; AGT-144 may re-band with trial evidence. "A capability whose job differs from its lane" is measured as "its default Intent Skill's `llm_model` equals no lane row" — the same equality `resolveJudgmentModel()` uses to decide lane membership (`agent-prompt.js:144`), so the seed and the runtime agree on what a lane is. 30 capabilities on `claude-opus-5` and the Fable ones are lane members and get no row.
- Catalog: six canonical ids. The short-form aliases (`claude-haiku-4-5`, `claude-sonnet-4-5`) are normalization keys (STANDARDS §12, `MODEL_ID_NORMALIZE`) and stay out. `first_seen` from `min(ai_activity_log.created_at)` where logged; `claude-sonnet-5` has never produced a logged call (zero rows all time) so its first sight is the lane row of 2026-09-02; `claude-opus-5-5`'s is today's cycle row. `family` is Anthropic's own family name; no invented tier column (pattern 57, 67, 87). Release dates, retirement dates, plan availability and strengths are filled only where this session measured them (W39 finding `961caae922b0381a`); everything else is NULL for AGT-146's watch to fill (pattern 33, 34).
