## The calls, and what I turned down

**D1 — score from own rows; do not hide the card.** Hiding removes a visual element, which is John's to approve (pattern:97) and there is no such decision on record (26 decisions on this ticket; none is an approval). Scoring from rows keeps every element where it is.

**D2 — the rule applies to created agents only: `tableOnly && trainable`.** `tableOnlyAgent()` sets `trainable` from `agent_origin = 'customer'` (`src/hooks/useAgents.js:348`), so the pair means "a row a customer made, with no code entry". Turned down:
- *Every trainable agent.* 18 of the 24 code agents are `trainable: true`, and only 9 agents hold any `agent_configs` row. Their formats and guardrails live in Skill Profiles, so reading `agent_configs` would show 0 for agents that are configured: a wrong fact in the other direction.
- *Every table-only agent.* The 10 system agents (the governance staff) are configured through Skill rows too. Same problem.
- *Every agent, rebuilt on the Skill Type model.* That is AGR-001 (open, filed 2026-07-15), a redesign of the whole meter. The validation decision of 2026-11-04 suggested grouping AGR-001 with this ticket; I did not, because one kickoff carries one item and AGR-001 changes what the card shows for all 44 agents.

**D3 — presence, at today's values.** A layer a created agent holds a row for reads what it reads today (L2 `20 + 6n`, L3 100, L4 72, L5 68); a layer with no row reads 0. I did not invent a new scale: the scale is AGR-001's question, and keeping today's values means a configured created agent (malcolm) does not move at all. L3 "Analysis Payload" has no table of its own. I scored it from the taught items that are handed over on every run: active, taught by the trainer, 12,000 characters or fewer (`taughtCounts(entries).always`, the same rule `lib/read-taught.js` applies). Turned down: L3 always 0 for a created agent (a layer the trainer can never fill), and L3 = 100 once anything exists (derived from the other layers, so it measures nothing).

**D4 — an empty-text config row is no row.** The Playbook's Always and Never boxes can save a row with empty text; `brittany` holds one live (`guardrail`, `always`, `text` ''). Counting it would move L5 off 0 for an agent with no guardrail.

**D5 — unread reads 0.** The two config reads land a moment after the page opens. Until then, and if they fail, L4 and L5 read 0 for a created agent and the page shows the existing "Could not load playbook configs" toast on failure. The other choice was an em dash (pattern:35), which needs the card, the trio and the Intelligence Configuration card to learn a non-number state: more of the screen changed than this ticket needs. Understating for a moment is the safe direction.

**L1 is left alone.** It reads `agents.skill_score`, which is the agent's own row and already 0 for a blank agent. It does not read the role prompt, so malcolm (one role prompt, skill 0) reads L1 = 0. That is a real gap, outside this ticket's three layers; named in the STOP LINE.

## Why the calc moves to its own file

The ticket asks for an arm that asserts a blank agent scores 0. `computeLayers` sits inside a 2,623-line JSX file that node cannot import, and the screen's other tests grep its text. A grep cannot prove a score. `src/lib/taughtItems.js` already sets the pattern (a pure module the screen and its test both import), so the calc moves to `src/lib/readinessLayers.js` and the test calls the real function (pattern:14).
