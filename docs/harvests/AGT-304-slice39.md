## 3. Design and alternatives

- **One paging helper per home**, both by `id` with `limit=1000&offset=<rows received>`: `getAll(url, key, q)` in the test (module level, beside `restHeaders`) and `restGetAll(base, key, q)` in the script (beside `restGet`, which it calls so `fail(2, ...)` on a bad read is unchanged). Offset = rows actually received, so the loop is correct under any server `max-rows` at or below 1,000 and at 24,000 rows (pattern:1). Rejected: `Prefer: count=exact` + `content-range` for the two invariance counts (a second read shape for one fact; paging serves both); `fingerprint=in.(...)` filters in the test (the derivation must see EVERY row, that is the point); a `limit=10000` single read (PostgREST caps server-side).
- **Step (5) mirrors the guard** (`openLatest.filter(r => r.iso_week < "2026-W38")`) rather than pinning a count (pattern:162). Rejected: asserting `0` (a pin on today's W37 statuses); dropping the W38 probe (loses the ingest seam it feeds).
- **The far-week probe** at `2099-W01`: `--week` must match `^\d{4}-W\d{2}$` (`requireWeek`, audit-cluster.js:513), `carryForward()` compares week strings, and `--collect` over the empty dir makes no model call (the cluster bands count answer files in the dir). The literal is "after every row" by construction, so the assertion `carried + gone == every latest-open row` is derived live on both sides and never pinned (pattern:18, pattern:162). Rejected: computing "the week after the newest row" (ISO-week arithmetic for one comparison); a second W38-shaped ingest of `far.json` (the seam is already graded at W38).
- Siblings in the related set (agt-129, agt-146, agt-170, agt-457, agt-502, agt-86h) run green on the rendered tree (§6); agt-86h is in the set because it names `audit-cluster.js`, and its reads are unchanged.
