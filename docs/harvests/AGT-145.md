## VERIFY FIRST — can a cloud run call the triggers API?

What is **proven** (measured earlier, recorded in the repo):

1. The runner's `Claude_Code_Remote` connector (`https://api.anthropic.com/v1/code/mcp/meta`) exposes trigger tools: `list_triggers` (used by runner-cycle.md:255 for the stamp check), `create_trigger`, `update_trigger`, `fire_trigger`, `create_session`, `get_session`.

3. `RemoteTrigger` (the attended-session tool) authenticates in-process — the `schedule` skill says "auth is handled in-process — do not use curl" — and is not reachable from node (`tests/regression/ses-355-routine-prompt.test.mjs` header: "the live routine cannot be read from node (RemoteTrigger is a session tool)"; `docs/harvests/AGT-102.md:14`: "the routine sessions have no RemoteTrigger tool").
4. The other 7 routines carry only the Supabase connector (parent session, `get`), so they have no trigger tool at all.

What is **assumed** (stated plainly):

- That the http_api refusal still holds today for all 8. The runner was created via http_api (measured). The 7 created 2026-09-25 were created through `RemoteTrigger create` from attended sessions, which the platform reports as http_api by the same mechanism — inferred from the runner's case, not re-measured on the 7. A cheap check exists: any cloud cycle's `list_triggers` result shows the creator field; no update is needed to read it.
- That the routines API has no documented public HTTP endpoint a node script could call with a bearer token. No such endpoint appears in the repo, the schedule skill, or the connector's observed tool names; `runner_secrets` holds `ANTHROPIC_API_KEY`, `MCP_API_KEY`, Supabase keys, Vercel keys — nothing that has ever been used against a routines endpoint. Designing a caller against an unproven endpoint would be a pattern:21 violation (a risky mechanism retrofitted into infrastructure without a POC).

The script is deterministic (pattern 9, 10): it never chooses a model — `model_assignments` does — and it never calls the API; it builds the exact body the session sends and grades the read-back.

## Why the shape — five modes, one script

- `--plan` writes the update body to disk instead of printing it, so the session's `RemoteTrigger update` call reads a file byte-for-byte and no hand-typing of a 10-tool array or an events block happens between plan and send. The body has exactly one top-level key, `job_config`, because the API's update is partial at the top level (schedule skill: "All fields optional (partial update)") while `job_config.ccr` is replaced whole — so sending only `job_config` is what leaves `enabled`, `cron_expression`, `name`, `mcp_connections` untouched (Q4, pattern 166).
- The partial-ccr refusal (exit 2 on a `get` without `session_context.allowed_tools`/`.model`) encodes the 2026-09-11 gotcha as a gate, not a comment (pattern 19): the file that would produce a pin-resetting update cannot produce a body at all.
- `--verify` reads a **second** `get` (`.after.json`) rather than trusting the update's HTTP 200 — the 2026-09-11 incident returned 200 with the pin emptied. It grades all four fields the ticket names and fails on the first difference so the session sees the field, not a summary.
- `--record` writes the decision first and the image second, the `render-cycle-card.js` order, with `table_name 'routine'` and `pk_value <trigger id>` — `runner_before_images.table_name` has no CHECK (measured: only the attribution xor, the non-empty session name, and the two FKs). `reverse_decision()` will not restore a `routine` row (its allowed-table list, SES-399), which is why `--undo` exists: it turns the image back into an update body for the session to send. The decision row is what SES-424's daily list renders, so John hears about a pin change with its undo handle at no new code (pattern 16, 17).
- `--pending` is the manager's half. It writes a `routine-pin-pending` decision when an assignment row's `since` (set by `apply_model_assignment`, AGT-144) is newer than the last `routine-pin-sync` decision naming that trigger id, and dedupes on an `open` pending row naming the same id, so a daily model-watch run does not pile up duplicates. Status values are `open|final|reversed` (CHECK measured); the existing ladder finalizes them like any other decision.
- Registry in the script, not a table: the 8 rows are stable by construction (pattern 18) and change only when a routine is created or deleted, which is a John act at claude.ai/code/routines. AGT-146 adds one line when the `model-watch` id exists. A table would be a second home for ids that already live in the routines product.
- Job type: all 8 routines' main session is the orchestrator lane (runbook step 8, auditor step 4; the Jerry/Nathan/Researcher routines run their agents through `scripts/agent-prompt.js`, whose model comes from AGT-143's reader, not from the pin). The pin is the session's own model, so `lane/orchestrator` is the job for every row — the instruction "unless the assignments table says otherwise" was checked: no capability row names a routine.

## Alternatives weighed

- **A node caller against the routines HTTP API.** Unproven endpoint, unproven credential; rejected above.
- **The runner cycle updating the routines itself through `update_trigger`.** Measured refusal (http_api creator). Rejected on evidence, not on caution.
- **A model-watch routine that creates its own routines so it can update them.** It could update only routines it created, never the 8 that exist; and John's Q4 keeps routine on/off and crons out of the manager's hands, which a routine-creating agent would blur. Rejected.
- **Storing the intended pin in a new table column.** `model_assignments` already names it; a column would be a second home (pattern 93).
