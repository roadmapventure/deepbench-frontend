## 2. The design questions, settled

### 2.1 How a team address is told from an agent id
One resolver, `resolveAddress(query)`, returns the SET the address stands for: `null` (admin, every agent), or an array of agent ids. `visibleRows()` filters on membership in that set after the lane rule — the same single visibility function for `tools/list` and `tools/call`.

The segment's SHAPE picks the read: exactly 64 lowercase hex asks `teams` for that address and returns the member ids from `agent_teams`; any other non-empty string is the one-element set holding that string; empty or a repeated parameter is the empty set. This is a format test on the request's value, not a slug or id conditional — no agent, team or capability is named in code (§19b), and the `agt-162` / `agt-163` / `mcp-3` static guards stay meaningful.

Alternative weighed and not taken: no shape test at all — always ask `teams` and union the result with `[segment]`. It is branch-free, but it adds a database read to every per-agent request and places an arbitrary caller-supplied string inside a PostgREST filter. With the shape test, the only string ever interpolated into the `teams` filter is 64 hex characters. The two namespaces are disjoint in live data (longest agent id 40 characters; created ids are slug + 6, at most 31).

Known limit: the column has no CHECK, so a hand-written address that is not 64 lowercase hex would never resolve. Every address is born from the default today; a CHECK is a candidate for the docs slice, not this one.

### 2.2 How the connection lists who is available
Smallest thing that works: nothing new in the tool list. Each team member's own capability appears as its own tool — a created agent holds `<id>-knowledge`, titled `<Name>'s Knowledge`, whose description already says `Run by <Name> -- New Agent (product lane)` and `Pass agent_id "<id>"`. An outside model picks an agent by picking that agent's tool.

One addition: on any non-admin address, the `initialize` instructions gain one sentence built from the live rows — `Agents available on this connection: A, B. When the user names one, call that agent's tool.` — or `No agent is available at this address.` for an empty set (pattern:34, honest absence; it also tells a tester a mistyped URL is why nothing is listed). The admin address's instructions are byte-identical and cost no new read. If the read fails during `initialize`, the handshake still answers with the base instructions; `tools/list` then reports the real error.

This sentence is text for the outside model, not a DeepBench screen. It is the Designer's reversible call; removing it is deleting one dep.

### 2.3 Unknown or malformed address
- 64 hex that no team carries -> `[]` -> 0 tools; `tools/call` answers the same `Unknown tool: <name>` as a name that does not exist (no inventory oracle).
- Uppercase hex, 63 or 65 characters, any other string -> treated as an agent id -> matches no row -> 0 tools.
- Empty value or a repeated `agent` parameter -> `[]`, never `null` — a malformed address can never become the admin address (AGT-333's rule, kept).
- A failed `teams` read throws -> JSON-RPC internal error. An outage is reported as an error, never as an empty team and never as a wider list.
- The lane rule still applies: a governance-lane agent placed in a team is not listed without the key.

### 2.4 Secrecy of the address
`readTeamAgentIds()` filters on `address` and selects only `id`; `sbSelect()`'s error message prints the table name only. The address is still in the request path, so Vercel's request log holds it, exactly as it holds every agent id today. No test message prints it.

- Not verified here: whether an agent's knowledge tool, called with another agent's id in `task_context.agent_id`, returns that other agent's material. If it does, a team connection can read a non-member the same way an agent's own address can today. That is AGT-340's subject, pre-existing, not introduced by this slice.
- `viewer` is still null everywhere (§10 Auth): Private is a label until accounts exist. Anyone holding a team address sees the team.

## S2.2 The data fact

**No fact in today's rows separates the two kinds of tool.** An agent's own knowledge capability and the general bundle capability share one Intent row, one handler and one execution type; they differ only in slug, name, description and holder — and a conditional on any of those is exactly what §19b forbids. So one new data fact is needed.

**Chosen:** a second Intent row for the general tool, carrying `traits.any_agent = true`. The existing Intent row keeps every other bundle capability and gains no trait. The code reads the trait generically (`assembleCapabilityRows()` already reads `traits.handler` and `traits.input_schema` from the same row) and hands it to the handler in `handler_context`.

Why this direction and not the mirror image (a new "own" Intent):
- **It fails closed.** Absence of the trait means own-knowledge only. A capability created tomorrow on the existing Intent is own-only without anyone remembering to mark it. The general tool is the single marked exception.
- **Existing rows need nothing.** Brittany's capability and every agent `lib/private-agent-create.js` creates already point at the existing Intent. No write to Brittany's rows, and no edit to `lib/private-agent-create.js` — which would have been a fourth file against a cap of three.
- **Each Intent carries its own input contract.** The own tool's `agent_id` becomes optional in data (`required: []`); the general tool keeps `required: ["agent_id"]`.

Weighed and not taken:
- A new column on `capabilities` — DDL for one boolean, and a second home for a fact the Intent's traits already carry.
- Deriving "own" from the holder (`agent_origin = 'customer'`, or the slug ending `-knowledge`) — a conditional on identity in disguise.
- Enforcing only on non-admin addresses — John's rule says the admin address alike.

## S2.3 What each case returns

| Call | Result |
|---|---|
| Own tool, own id | the holder's bundle |
| Own tool, no `agent_id` (absent, empty, blank, not a string) | the holder's bundle — an outside model need not know the id |
| Own tool, another agent's id (member, non-member, missing, hidden) | tool result `isError: true`, text `Unknown agent: <id>` — the same message a missing agent gets, decided before any database read |
| General tool, admin address, any id | that agent's bundle, as today; no id is `-32602` naming the field, as today |
| General tool on a team or single-agent address (its holder's own included) | not listed; a call is `-32602 Unknown tool: <name>`, the same answer as a name that does not exist |

`visibleRows()` stays the one visibility function: on any non-admin set it drops a row whose `any_agent` is true. Listing and calling still cannot disagree.
