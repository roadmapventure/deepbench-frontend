Governing: ARCHITECTURE.md §19b (`:1110`, capabilities are data, no capability-specific route — the lane is a script door of the existing `verify-ship` grading code, no new `skill_profiles` row: creating or changing an agent is John's clause 7); §19v (`:2565`; the verifier at step 7a `:2753`; the trust ladder `:2831` — the verdict is the ladder's input, so a re-grade never sets `auto_done_eligible`); `.claude/rules/supabase-column-grants.md` (new table SELECT is born open; functions default OPEN — revoke by name, assert both directions); `.claude/rules/supabase-function-signature.md` (new function, one identity, asserted).

Calls made here (Designer's, reversible, JOHN-0925-DESIGNER-DECIDES):
1. ONE RULE HOME is structural, not a guard: the grading span of `main()` (coverage → gates → delta → verdict) is extracted into `export async function gradeDelivery()` and both verify-ship and the new lane call it. A lane that merely imported the pieces would drift the first time 7a's sequence gained an input (AGT-529 will).
2. Build and hygiene are graded at dev HEAD for every re-grade; only regression is per ticket (SES-403's reasoning: the ship is in dev; a red build/tripwire there is nobody's ship). A red there is `ungradable`, never block.
3. Regression per ticket: PAIR mode when the ticket's own commits isolate (AGT-245's own resolver `ownCommitRange`/`cohortRow`, both shas present, no package.json/package-lock.json in the pair's diff); otherwise DEV-HEAD mode over the related set of the ticket's kickoff-declared files (`declaredFiles()` from scripts/pre-build-baseline.js), full suite when none, declared as a baseline omission (AGT-245's `--no-baseline` mechanism) and said so in the row.
4. Outcome mapping (the ticket's own sentences): coverage refusal → `ungradable`; pair delta green → approve; pair `newlyRed` non-empty → block; pair red with nothing newly red (unverified / never measured / absolute stands) → `ungradable`; dev-head absolute green → approve, red → `ungradable` naming the reds. A suite that ran nothing → exit 2, nothing recorded.
5. `ungradable` is a `runner_regrades` row and never a verdict: `ck_runner_verdicts_verdict` (approve|block) and every reader of it stay untouched. The ledger's `unique (prior_verdict_id, rules_fingerprint)` IS "once per rule set, again after a change".
6. The fingerprint is sha256 over seven RULE_FILES' disk content, CRLF-normalised (deterministic across John's Windows checkout and the cloud; no git call; works before a commit). package.json and ci.yml are excluded: a dependency bump is not a grading rule.

8. A block records its row only; no card (directive 6f33ec28, as (7a-bis)); the team ballot is a capability only John may create — reported in the STOP LINE, not built.
9. Kickoff-document findings (cap, lanes, anchors, risk) are not re-applied to historic kickoffs: they grade the Designer's draft at step 6, not the delivery.
