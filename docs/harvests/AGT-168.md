## 2. The trap this design exists to avoid (pattern:162)

The obvious build — "run the existing scanner in CI" — is wrong, and wrong in a way that would
have been discovered only after it turned `dev` red. `scanTree()` grades the live world, and the
live world has 48 standing bypass lines plus 16 more across the other three detectors. The job
would be red on its first run and on every run after, with nothing a Builder could do to make it
green short of the ~46-file purge that is explicitly John's call to authorise.

A second, subtler form of the same trap: grading whole *changed files* rather than added *lines*.
Any future session that edits one line of any of those 46 historical kickoffs would go red for a
literal it did not write. D1 in the kickoff is that distinction.

A third form, checked and cleared: if a **generated** file carried the literal, its per-cycle
regeneration would re-add those lines in the diff and paint every routine close-out red. Measured
— all 46 carriers are hand-written historical kickoffs, and neither `CLAUDE-STATE.md` nor
`docs/backlog/BACKLOG-SNAPSHOT.md` carries the value. The change-scoped gate is therefore quiet on
an ordinary close-out.

## 3. Alternatives weighed

**A new top-level CI job vs. a step in `checks` (chose the step, D2).**
`tests/regression/SES-255-ci-conclusion-reporting.js` computes the blocking-job set from the
shipped YAML and asserts `report-conclusion` names every other job in `needs`. A new job is
therefore three edits, not one: the job, the `needs` list, and the jq payload that names each job
for the runner ledger — and a miss there is not a red test but a silently forgetful green anchor.
A step inside `checks` is already blocking, already reported, and costs one hunk. pattern:17.

**`fetch-depth: 0` on the checkout vs. a targeted shallow fetch (chose the targeted fetch).**
Setting `fetch-depth: 0` would give the diff its history, but SES-393 records that the depth-1
clone is *why* several history-reading regression tests declare themselves NOT RUN in CI. Deepening
the clone would silently un-skip that whole set inside this bug-fix slice, and any of them that is
red would land on AGT-168's ship. `git fetch --no-tags --depth=1 origin "$BASE_SHA"` fetches
exactly the one commit object the diff needs and changes nothing else. `git diff A B` needs only
the two trees, not a connected history, so a shallow base is sufficient.

**Exit 0 vs. exit 2 on an unresolvable base (chose exit 2, D3).**
A gate that passes when it cannot see the change is the "could-not-run reads as pass" failure the
module already refuses by name in its own header. The cost of failing closed is a red run on a base
GitHub cannot name; `on: push` is filtered to `dev` and `main`, both of which always exist, so
`github.event.before` is a real sha on every push this workflow sees, and the zero-sha
first-push-of-a-branch case cannot reach it.

**Rotating the value / purging the 46 files (not designed, by instruction and by pattern:72).**
Rotation is a production credential operation and is John's. The purge is 46 files against a 3-file
cap, and the cap is John's to waive, never a session's. Both are named in the kickoff's §1 and §7
as never-done rather than left as implied residue, so the Builder cannot drift into either.
